17 调度系统数据库设计：选型、表结构与持久化策略

数据库设计，说白了就是AGV调度系统的“记忆系统”。

我做了这么多年调度系统，见过太多因为数据库没设计好导致系统崩掉的案例。有一次，一个客户现场AGV跑着跑着突然全部停摆，查了半天——MySQL连接池爆了，因为历史轨迹数据没做归档。嗯，从那以后，我对数据库设计就格外上心。

1.1 数据库选型：各司其职

调度系统里，数据种类很多。有实时性要求极高的，有需要持久化存储的，有时序性很强的。指望一个数据库搞定所有，不现实。

我个人习惯用“三库协同”的方案：

数据库 核心用途 我为什么选它
MySQL 结构化业务数据 任务单、AGV档案、地图配置、用户权限。关系型数据，事务支持好，查起来方便。
Redis 高速缓存与状态 AGV实时位置、任务队列、锁。毫秒级响应，扛高并发。
InfluxDB 时序数据存储 AGV电量、速度、温度、路径耗时。按时间戳写入，压缩率高，查询快。

核心原则：热数据放Redis，温数据放MySQL，冷数据放InfluxDB。别混着用，也别指望一个库包打天下。

1.2 MySQL：业务数据的基石

MySQL主要存那些“丢了会出大事”的数据。比如任务记录、AGV配置、地图拓扑。

我设计表结构时，会特别注意索引和分表策略。举个例子，任务表如果单表存几百万条，查询会越来越慢。

-- 任务主表（按日期分表）
CREATE TABLE task_202501 (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    task_id VARCHAR(64) NOT NULL COMMENT '任务唯一ID',
    agv_id VARCHAR(32) COMMENT '执行AGV',
    task_type TINYINT COMMENT '1-取货 2-送货 3-充电',
    status TINYINT COMMENT '0-待分配 1-执行中 2-完成 3-取消',
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    finish_time DATETIME,
    INDEX idx_agv_id (agv_id),
    INDEX idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

避坑指南：我曾经因为没给status字段加索引，导致任务分配时全表扫描，AGV等待时间从50ms飙升到2秒。后来加了索引，问题秒解。

1.3 Redis：调度系统的“神经中枢”

Redis在调度系统里，地位极高。AGV的实时位置、任务队列、分布式锁，都靠它。

我常用的数据结构：

  • String：存AGV最新位置，key为agv:pos:{agv_id}，value为JSON字符串。
  • List：做任务队列，左进右出，实现FIFO。
  • Sorted Set：按优先级排序任务，score就是优先级数值。
  • Set：存空闲AGV集合，方便快速分配。
// 伪代码：AGV位置更新与读取
// 写入（每100ms更新一次）
redis.set("agv:pos:AGV001", "{x:12.5, y:34.2, angle:90}");

// 读取（调度器分配任务时）
String posJson = redis.get("agv:pos:AGV001");

注意：Redis虽然快，但它是内存数据库。如果没做持久化，宕机就会丢数据。我建议开启AOF+RDB混合模式，兼顾性能与安全。

1.4 InfluxDB：时序数据的归宿

AGV跑起来，会产生海量的时序数据。电量每100ms采集一次，一天下来就是86万条。用MySQL存？查询会慢到怀疑人生。

InfluxDB就是为这种场景设计的。它按时间戳组织数据，写入快，查询也快。

-- 写入AGV电量数据
INSERT INTO agv_metrics,agv_id=AGV001,metric=battery value=85.2 1704067200

-- 查询最近1小时的电量变化
SELECT mean(value) FROM agv_metrics 
WHERE agv_id='AGV001' AND metric='battery' 
AND time > now() - 1h

你想想看，如果这个查询放在MySQL里，得写多复杂的SQL？而且随着数据量增长，性能会急剧下降。InfluxDB自带数据压缩和自动过期策略，省心很多。

1.5 数据持久化策略

数据怎么存、存多久、什么时候删，这些都需要提前规划好。

我一般这样设计：

数据类别 存储位置 保留周期 归档策略
AGV实时位置 Redis 实时（秒级） 过期后丢弃
任务记录 MySQL 3个月 按月分表，过期归档到HDFS
AGV轨迹点 InfluxDB 7天 自动过期（RETENTION POLICY）
系统日志 Elasticsearch 30天 按索引滚动删除

我的经验：别把所有数据都往一个库里塞。实时数据用Redis，历史数据用InfluxDB，业务数据用MySQL。各司其职，系统才能跑得稳。

1.7 避坑总结

最后，分享几个我踩过的坑：

  • 别把Redis当主库用：Redis宕机丢数据是常态，一定要有MySQL兜底。
  • InfluxDB的保留策略要提前配：不配的话，磁盘会被时序数据撑爆。我见过一个现场，7天没管，磁盘直接满了。
  • MySQL分表要趁早：数据量超过500万条再分表，迁移成本很高。最好一开始就按时间分表。
  • 连接池别设太大：MySQL连接数不是越多越好。我一般设20-50个，配合连接池复用，性能反而更好。

数据库设计这块，说白了就是“把合适的数据放到合适的地方”。想清楚数据流向，设计好存储策略，调度系统才能跑得稳、跑得快。
