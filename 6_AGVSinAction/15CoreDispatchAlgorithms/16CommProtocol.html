16 调度系统通信协议：通信方式、协议设计与消息队列

大家好，我是老张。今天咱们聊聊AGV调度系统里最基础、也最容易踩坑的一个话题——通信协议。

说实话，我见过不少团队，算法写得漂亮，路径规划跑得飞起，结果一到现场就掉链子。为什么？通信没搞好。AGV调度系统说白了就是“大脑指挥手脚”，如果神经传导出问题，再聪明的大脑也没用。

这一章，我会从三个维度展开：通信方式（用什么传）、协议设计（传什么格式）、消息队列（怎么保证不丢消息）。

核心观点：通信协议的选择，决定了调度系统的实时性、可靠性和可维护性。选错了，后面全是坑。

1.1 通信方式：WiFi、5G、ZigBee

先聊通信方式。你想想看，AGV在车间里跑来跑去，信号不能断。我最早做的一个项目，用的是WiFi，结果AGV一拐弯进到金属货架后面，信号就掉到-80dBm，调度指令直接超时。那叫一个惨。

WiFi（最常用，但别大意）

WiFi是当前AGV调度系统的主流选择。802.11ac/ax的吞吐量足够，延迟在10-30ms之间。但有个问题——漫游切换。

AGV移动时会在不同AP之间切换。普通手机切换AP也就几百毫秒，但AGV不行。我记得有一次，AGV在切换AP时丢了3条指令，结果两辆车差点撞上。后来我们强制启用了802.11r快速漫游，才把切换时间压到50ms以内。

我的建议：如果车间面积大、AGV数量多（20台以上），优先考虑WiFi 6（802.11ax）。它的OFDMA技术能同时服务多台设备，延迟更稳定。

5G（贵，但真香）

5G在AGV场景里属于“降维打击”。1ms级别的延迟，99.999%的可靠性，而且没有漫游切换的问题——因为基站天然支持移动性。

但代价也大。我参与过一个港口AGV项目，部署5G专网，光基站就花了200多万。如果你只是几十台AGV在几千平米的车间跑，说实话，没必要。

ZigBee（小众，但特定场景好用）

ZigBee的优点是功耗低、自组网。但它的带宽只有250kbps，延迟在30-100ms。说实话，不适合做实时调度。

不过，我在一个仓储项目里用过ZigBee——不是传调度指令，而是传AGV的电池电压、温度等状态信息。这些数据不要求实时，但节点多、电池供电，ZigBee反而很合适。

通信方式 带宽 延迟 覆盖范围 适用场景
WiFi 6 ~1Gbps 10-30ms ~100m（室内） 中小规模AGV调度
5G ~10Gbps 1-5ms ~500m（室外） 大规模、高实时性场景
ZigBee 250kbps 30-100ms ~100m（多跳） 状态监控、低功耗传感器

1.2 协议设计：JSON vs Protobuf

通信方式定下来，接下来就是“说什么语言”。这里有两个主流选择：JSON和Protobuf。

JSON（简单，但别滥用）

JSON的好处是人可读、调试方便。我刚开始做AGV调度时，所有消息都用JSON。开发阶段确实爽，抓包一看就知道发了什么。

但到了量产阶段，问题来了。一个AGV状态消息，JSON序列化后可能2KB，而Protobuf只要200字节。你想想，100台AGV，每100ms上报一次状态，光序列化开销就差了10倍。

// JSON 格式的AGV状态消息
{
  "agv_id": "AGV-001",
  "timestamp": 1695000000,
  "position": {
    "x": 12.5,
    "y": 34.2,
    "theta": 1.57
  },
  "battery": 85.3,
  "status": "moving",
  "task_id": "TASK-12345"
}

Protobuf（高效，但需要管理）

Protobuf是二进制协议，体积小、解析快。我现在的项目，核心调度指令全部用Protobuf。一个路径规划指令，JSON要1.5KB，Protobuf只要300字节。在WiFi环境下，这0.5ms的差距可能不明显，但在5G场景下，这就是质的区别。

// Protobuf 定义
message AGVStatus {
  string agv_id = 1;
  uint64 timestamp = 2;
  Position position = 3;
  float battery = 4;
  enum Status {
    IDLE = 0;
    MOVING = 1;
    CHARGING = 2;
    ERROR = 3;
  }
  Status status = 5;
  string task_id = 6;
}

message Position {
  float x = 1;
  float y = 2;
  float theta = 3;
}

避坑指南：我曾经在一个项目里，团队一半人用JSON、一半人用Protobuf，结果接口对不上，调试了三天。后来我强制统一：内部通信用Protobuf，对外接口用JSON。这样既保证了性能，又保留了可调试性。

1.3 消息队列：MQTT vs Kafka

最后聊消息队列。为什么需要消息队列？因为AGV调度系统是典型的“发布-订阅”模式。调度中心发布指令，AGV订阅指令；AGV发布状态，调度中心订阅状态。如果直接点对点通信，系统耦合度太高，扩展性极差。

MQTT（轻量，适合边缘）

MQTT是物联网场景的标配。它的协议头只有2字节，支持QoS 0/1/2三种可靠性级别。我习惯用QoS 1——至少一次送达，配合去重逻辑，既保证可靠性，又不会像QoS 2那样增加两倍延迟。

MQTT的Broker（如Mosquitto、EMQX）可以部署在边缘服务器上，延迟极低。我在一个工厂项目里，MQTT端到端延迟稳定在5ms以内。

Kafka（高吞吐，适合中心）

Kafka的强项是海量数据吞吐。如果你有500台AGV，每台每秒上报10条消息，那就是5000条/秒。MQTT Broker可能会扛不住，但Kafka轻松应对。

不过Kafka的延迟比MQTT高，通常在10-50ms。所以我的做法是：边缘用MQTT做实时控制，中心用Kafka做数据分析和日志存储。两者互补，各司其职。

特性 MQTT Kafka
协议开销 2字节头部 ~20字节头部
延迟 1-10ms 10-50ms
吞吐量 ~10万条/秒 ~100万条/秒
消息持久化 有限（取决于Broker） 强（磁盘持久化）
适用场景 实时控制、指令下发 日志收集、数据分析

我的经验：别试图用一个消息队列解决所有问题。MQTT和Kafka不是二选一，而是搭档。MQTT负责“快”，Kafka负责“稳”。

小结

通信协议这块，说白了就是三个选择：

  • 通信方式：WiFi够用就用WiFi，预算充足上5G，ZigBee只做辅助
  • 协议设计：内部用Protobuf，对外用JSON，别混着来
  • 消息队列：实时控制用MQTT，数据分析用Kafka，各取所长

嗯，这一章就到这里。记住，通信协议是调度系统的“血管”，血管堵了，再好的算法也白搭。
