21 调度系统安全设计：访问控制、数据加密、通信安全、物理安全

说实话，安全这个话题在AGV调度系统里，经常被当成「锦上添花」的东西。我见过不少项目，前期只顾着把车跑起来，等上线了才发现——嗯，谁都能连上调度服务器，报文明文传输，甚至有人能直接改数据库里的路径数据。那场面，想想都头疼。

今天咱们就把这块掰开揉碎了讲。安全不是单独的一个模块，它应该渗透到系统的每个角落。我个人习惯把它分成四个维度：访问控制、数据加密、通信安全、物理安全。下面一个个说。

核心观点：安全设计不是「加锁」，而是「建墙」。每一层都设防，才能挡住大多数攻击。

1. 访问控制：谁可以进来？

访问控制是安全的第一道门。说白了，就是搞清楚「谁」能「做什么」。我在项目里见过最离谱的事——一个操作员账号居然有管理员权限，能改路径、删任务。后来排查发现，是开发阶段为了方便，直接给了所有人 root 权限，上线后忘了改回来。

我个人习惯用 RBAC（基于角色的访问控制）。把用户分成几类：

  • 操作员：只能查看任务状态、手动启停车辆
  • 调度员：可以创建/修改任务，但不能改系统配置
  • 管理员：能改配置、管理用户、查看日志
  • 审计员：只读，专门看日志和操作记录

你想想看，如果每个角色都只能做自己分内的事，就算某个账号被盗了，损失也有限。这就是「最小权限原则」——给每个人刚刚好的权限，不多给一分。

避坑指南：我曾经在一个项目里，把权限写死在代码里。后来要加一个新角色，得改代码重新部署。那叫一个痛苦。建议把权限配置放到数据库或配置中心，动态加载。

2. 数据加密：存着和传着都要安全

数据加密分两块：存储加密和传输加密。很多团队只关注传输加密，忽略了存储。我记得有一次做安全审计，发现数据库里用户的密码居然是明文存的。嗯，那感觉就像把家门钥匙挂在门外。

先说存储加密。敏感数据比如密码、路径配置、任务日志，建议用 AES-256 加密。密码本身一定要加盐哈希，别用 MD5，那玩意儿早就不安全了。我个人推荐 bcrypt 或 Argon2。

再说传输加密。AGV 和调度服务器之间的通信，必须走 TLS 1.3。别用 1.2 以下版本，有已知漏洞。而且证书要定期轮换，我见过一个项目用了三年没换证书，结果证书过期了，所有车都连不上服务器——那叫一个惨。

// 伪代码示例：AES-256 加密存储路径数据
public class PathEncryptor {
    private static final String ALGORITHM = "AES/GCM/NoPadding";
    private static final int KEY_SIZE = 256;
    
    public byte[] encryptPathData(PathData data, SecretKey key) {
        // 初始化向量随机生成，每次不同
        byte[] iv = generateRandomIV(12);
        Cipher cipher = Cipher.getInstance(ALGORITHM);
        cipher.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, iv));
        byte[] encrypted = cipher.doFinal(serialize(data));
        // 返回 iv + 密文
        return ByteBuffer.allocate(iv.length + encrypted.length)
            .put(iv).put(encrypted).array();
    }
}

注意：密钥管理是加密的命门。别把密钥硬编码在代码里，也别和数据库放在同一台机器上。建议用专门的密钥管理服务（KMS）或硬件安全模块（HSM）。

3. 通信安全：车和服务器怎么说话？

AGV 和调度服务器之间的通信，是安全的重灾区。为什么？因为无线环境太容易被监听了。你想想看，如果有人在车间里放一个嗅探器，所有报文都能被截获。

我建议用 mTLS（双向 TLS）。普通的 TLS 只验证服务器身份，mTLS 要求客户端也出示证书。这样就算有人伪造了一个客户端，没有合法证书也连不上服务器。

另外，通信协议里要加 防重放攻击 的机制。每个报文带一个时间戳和序列号，服务器检查是否在有效窗口内。我曾经遇到过一个问题：有人截获了一个「停止车辆」的指令，反复重放，导致车辆频繁急停。后来加了序列号校验，同一个序列号的报文只处理一次，问题就解决了。

安全机制 作用 实现方式
mTLS 双向身份认证 客户端和服务器各持证书
时间戳+序列号 防重放攻击 报文头携带，服务端校验
心跳保活 检测连接断开 每 5 秒发送心跳包
报文签名 防篡改 HMAC-SHA256 签名

个人经验：通信超时时间别设太长。我一般设 3 秒超时，重试 3 次。如果还连不上，就认为车辆离线，触发安全停车。别让车在没收到指令的情况下一直跑，那太危险了。

4. 物理安全：别小看「摸得着」的风险

物理安全往往被忽略，但恰恰是最容易出问题的。AGV 调度系统的核心——工控机、交换机、路由器——都部署在车间里。车间是什么环境？灰尘、震动、温度变化，还有可能被人误碰。

我建议做这几件事：

  • 工控机加固：用工业级设备，防尘防震。系统盘用 SSD，别用机械硬盘，AGV 跑起来震动大，机械盘容易坏。
  • 网络隔离：调度网络和办公网络物理隔离。别图省事用同一个交换机，万一有人从办公网渗透进来，整个调度系统就暴露了。
  • 防拆设计：AGV 上的控制器和通信模块，加防拆螺丝或封条。我曾经遇到一个项目，有人把 AGV 上的无线模块拆下来换了个山寨的，结果通信不稳定，车到处乱跑。
  • 环境监控：机柜里装温湿度传感器，温度过高自动告警。别等设备烧了才发现。

重要提醒：物理安全不只是防人，还要防环境。车间里的电磁干扰、电源波动，都可能让设备出问题。建议所有关键设备都接 UPS，并做电磁屏蔽。

小结

安全设计没有「一劳永逸」的方案。它是个持续的过程，需要不断评估、改进。我个人习惯每半年做一次安全审计，看看有没有新的漏洞，权限有没有被滥用，证书有没有快过期。

记住一句话：安全不是功能，是习惯。把安全融入到开发的每个环节，比事后打补丁强一百倍。
