25 通信模块与监控模块实现

各位同学，今天我们来聊聊AGV调度系统里两个最“接地气”的模块——通信模块和监控模块。

说实话，很多刚入行的朋友容易忽略这两个模块。大家总觉得，算法写好了，路径规划出来了，系统就差不多了。但我做了这么多年调度系统，可以负责任地告诉你：通信和监控，才是决定系统能不能真正跑起来的命门。

为什么这么说？你想想看，AGV调度系统本质上是一个分布式系统。几十台、上百台AGV同时在车间里跑，每台车都在实时上报位置、状态，调度中心要下发指令、调整任务。这中间要是通信断了、数据丢了、延迟高了，再好的算法也是白搭。

监控模块就更不用说了。没有监控，你就像闭着眼睛开车——出了故障都不知道问题出在哪。我曾经在一个项目里，就因为监控没做好，排查一个偶发性的死锁问题花了整整三天。那滋味，真不好受。

好，咱们直接进入正题。

二、通信协议选型

选通信协议，说白了就是选“车和调度中心怎么说话”。我见过不少项目，一开始图省事用HTTP轮询，结果AGV一多，服务器直接被打趴下。

我个人推荐的做法是：

  • 控制指令：用MQTT协议。轻量、支持发布/订阅模式、有QoS保证。AGV多的时候，MQTT的吞吐量优势非常明显。
  • 状态数据：用Protobuf序列化。相比JSON，Protobuf的编码体积小30%-50%，解析速度也快得多。AGV每秒上报一次位置，数据量积少成多，这个优化很值得。
  • 大文件/日志：走HTTP/2。比如AGV的固件升级包、历史日志回传，这些不适合走MQTT。
小技巧： 我在项目中遇到过一个问题——AGV在WiFi信号弱的区域频繁断连。后来我们在MQTT客户端里加了“自适应心跳间隔”机制：信号好时心跳间隔3秒，信号差时自动缩短到1秒。这样既保证了及时性，又不会在信号好时浪费带宽。

三、通信模块核心代码实现

下面这段代码，是我在实际项目中提炼出来的通信模块核心框架。注意看消息的序列化和反序列化部分：

// 通信模块核心类（C++示例）
class CommunicationModule {
public:
    CommunicationModule(const std::string& broker_url, const std::string& client_id)
        : mqtt_client_(broker_url, client_id) {
        
        // 注册回调
        mqtt_client_.set_connected_callback([this]() {
            on_connected();
        });
        
        mqtt_client_.set_disconnected_callback([this](int reason) {
            on_disconnected(reason);
        });
        
        mqtt_client_.set_message_callback([this](const std::string& topic, 
                                                  const std::vector<uint8_t>& data) {
            on_message(topic, data);
        });
    }

    // 发送AGV状态（使用Protobuf序列化）
    bool send_agv_status(const AGVStatus& status) {
        std::vector<uint8_t> buffer;
        if (!status.SerializeToArray(&buffer)) {
            log_error("序列化AGV状态失败");
            return false;
        }
        
        // 发布到MQTT主题
        std::string topic = "agv/" + status.agv_id() + "/status";
        return mqtt_client_.publish(topic, buffer, QOS_AT_LEAST_ONCE);
    }

    // 接收调度指令（使用Protobuf反序列化）
    bool receive_command(const std::vector<uint8_t>& data, DispatchCommand* cmd) {
        if (!cmd->ParseFromArray(data.data(), data.size())) {
            log_error("反序列化调度指令失败");
            return false;
        }
        return true;
    }

private:
    void on_connected() {
        log_info("MQTT连接成功");
        // 订阅所有AGV相关的主题
        mqtt_client_.subscribe("agv/+/status", QOS_AT_LEAST_ONCE);
        mqtt_client_.subscribe("agv/+/command", QOS_EXACTLY_ONCE);
    }

    void on_disconnected(int reason) {
        log_warn("MQTT连接断开，原因码：%d", reason);
        // 启动重连（指数退避策略）
        start_reconnect_with_backoff();
    }

    void on_message(const std::string& topic, const std::vector<uint8_t>& data) {
        // 根据topic分发消息
        if (topic.find("/status") != std::string::npos) {
            AGVStatus status;
            if (receive_agv_status(data, &status)) {
                status_callback_(status);
            }
        } else if (topic.find("/command") != std::string::npos) {
            DispatchCommand cmd;
            if (receive_command(data, &cmd)) {
                command_callback_(cmd);
            }
        }
    }

    MQTTClient mqtt_client_;
    std::function<void(const AGVStatus&)> status_callback_;
    std::function<void(const DispatchCommand&)> command_callback_;
};
关键点解析：
  • QoS级别选择：状态上报用QoS 1（至少一次），指令下发用QoS 2（恰好一次）。为什么？状态丢一帧问题不大，但指令丢了可能出大事故。
  • 断线重连用指数退避：第一次重连等1秒，第二次2秒，第三次4秒...最大不超过30秒。避免网络波动时大量客户端同时重连造成“雪崩”。
  • 主题命名规范：agv/{agv_id}/{message_type}。这样既方便订阅，也方便后续扩展。

四、监控模块的设计思路

监控模块，说白了就是给调度系统装上一双“眼睛”。我见过太多系统，上线第一天跑得挺好，第二天开始出各种诡异问题——AGV突然不动了、任务卡住了、路径死锁了。没有监控，你连问题出在哪都不知道。

监控模块我一般分三层：

监控层级 监控内容 采集方式 告警阈值
设备层 AGV电量、速度、温度、传感器状态 MQTT实时上报 电量<20%、温度>60°C
通信层 消息延迟、丢包率、连接状态 心跳检测+消息追踪 延迟>500ms、丢包率>5%
业务层 任务完成率、路径阻塞、死锁检测 调度日志分析 完成率<90%、阻塞>30s

嗯，这里要特别说一下业务层的监控。我曾经在一个项目里，AGV数量从20台增加到50台后，系统突然频繁死锁。排查了整整两天，最后发现是路径预留算法在高并发下有个边界条件没处理好。要是当时有完善的死锁监控，这个问题半天就能定位到。

五、监控模块核心实现

监控模块的代码，我习惯用“生产者-消费者”模式。AGV上报的数据是生产者，监控分析线程是消费者。中间用无锁队列缓冲，避免阻塞AGV的通信线程。

// 监控模块核心类
class MonitorModule {
public:
    MonitorModule() : running_(false) {}

    void start() {
        running_ = true;
        // 启动监控分析线程
        analyzer_thread_ = std::thread([this]() {
            while (running_) {
                analyze();
                std::this_thread::sleep_for(std::chrono::seconds(1));
            }
        });
    }

    // 接收AGV上报数据（由通信模块调用）
    void feed_data(const AGVStatus& status) {
        std::lock_guard<std::mutex> lock(mutex_);
        // 更新AGV最新状态
        agv_status_map_[status.agv_id()] = status;
        
        // 记录历史数据（用于趋势分析）
        if (status_history_.size() > 10000) {
            status_history_.pop_front();
        }
        status_history_.push_back(status);
    }

private:
    void analyze() {
        std::lock_guard<std::mutex> lock(mutex_);
        
        auto now = std::chrono::system_clock::now();
        
        for (const auto& [agv_id, status] : agv_status_map_) {
            // 1. 心跳超时检测
            auto last_heartbeat = status.timestamp();
            auto elapsed = std::chrono::duration_cast<std::chrono::seconds>(
                now - last_heartbeat).count();
            
            if (elapsed > HEARTBEAT_TIMEOUT_SECONDS) {
                trigger_alarm(AlarmType::HEARTBEAT_TIMEOUT, 
                    "AGV " + agv_id + " 心跳超时 " + std::to_string(elapsed) + "秒");
            }
            
            // 2. 电量过低告警
            if (status.battery_level() < 20.0f) {
                trigger_alarm(AlarmType::LOW_BATTERY,
                    "AGV " + agv_id + " 电量不足: " + 
                    std::to_string(status.battery_level()) + "%");
            }
            
            // 3. 路径阻塞检测
            if (status.motion_state() == MotionState::BLOCKED) {
                auto block_duration = std::chrono::duration_cast<std::chrono::seconds>(
                    now - status.block_start_time()).count();
                if (block_duration > BLOCK_TIMEOUT_SECONDS) {
                    trigger_alarm(AlarmType::PATH_BLOCKED,
                        "AGV " + agv_id + " 路径阻塞 " + 
                        std::to_string(block_duration) + "秒");
                }
            }
        }
    }

    void trigger_alarm(AlarmType type, const std::string& message) {
        // 记录告警日志
        log_alarm(type, message);
        
        // 推送到告警队列（供前端展示）
        alarm_queue_.push({type, message, std::time(nullptr)});
        
        // 严重告警直接触发回调（比如发短信、打电话）
        if (type == AlarmType::HEARTBEAT_TIMEOUT || 
            type == AlarmType::PATH_BLOCKED) {
            if (critical_alarm_callback_) {
                critical_alarm_callback_(type, message);
            }
        }
    }

    std::atomic<bool> running_;
    std::thread analyzer_thread_;
    std::mutex mutex_;
    std::unordered_map<std::string, AGVStatus> agv_status_map_;
    std::deque<AGVStatus> status_history_;
    std::queue<AlarmEvent> alarm_queue_;
    std::function<void(AlarmType, const std::string&)> critical_alarm_callback_;
};
避坑指南： 我曾经犯过一个错误——监控分析线程里直接调用了外部告警接口（比如发短信API）。结果有一次短信服务挂了，监控线程卡在HTTP调用上，导致整个监控模块“假死”。后来我改成异步告警：监控线程只负责把告警事件丢到队列里，由专门的告警发送线程去处理。这样即使外部服务挂了，也不影响监控核心逻辑。

六、通信与监控的联动

通信模块和监控模块不是孤立的。它们之间有一个非常重要的联动机制——自适应降级。

什么意思呢？当监控模块检测到通信质量下降（比如丢包率超过5%），它会通知调度中心自动降低AGV的运行速度，同时增加安全距离。等通信恢复后，再逐步恢复到正常模式。

这个机制我在一个大型仓储项目里用过。当时仓库的WiFi覆盖有盲区，AGV经过时经常断连。加了自适应降级后，AGV在盲区自动减速到0.5m/s，安全距离从2米扩大到5米。虽然效率降低了，但至少不会撞车。等出了盲区，再自动恢复。

嗯，说白了就是：通信不好，就别让AGV跑太快。这个道理很简单，但很多系统就是没做。

七、总结

通信模块和监控模块，看起来不像路径规划、任务调度那么“高大上”，但它们是整个调度系统的“地基”。地基不稳，上面盖再漂亮的房子也是白搭。

最后送大家一句话：好的调度系统，不是算法多牛，而是出了问题能快速发现、快速定位、快速恢复。而这一切，都离不开扎实的通信和监控设计。
