6 交通管制策略

交通管制，说白了就是解决「多辆车抢路」的问题。

我在做第一个AGV项目时，觉得调度算法写好了就行。结果一上线，三台车在十字路口堵死，整个仓库瘫痪了半小时。嗯，从那以后，我把交通管制当成了调度系统的核心命脉。

今天聊三种主流策略：基于锁的、基于时间窗的、动态优先级调度。每种都有适用场景，也有坑。

6.1 基于锁的交通管制

这是最朴素的方法。把地图上的关键区域（交叉口、窄道）当成「锁资源」。AGV要进入，必须先申请锁。拿到锁才能进，出来就释放。

听起来像操作系统的互斥锁？没错，思路一模一样。

核心逻辑：

  • 每个冲突区域对应一把锁
  • AGV进入前尝试加锁
  • 加锁失败则等待或绕行
  • 离开后释放锁
// 伪代码示例：基于锁的通行控制
bool RequestLock(AGV agv, Zone zone) {
    if (zone.lockOwner == NULL) {
        zone.lockOwner = agv.id;
        return true;
    }
    // 锁被占用，加入等待队列
    zone.waitQueue.push(agv.id);
    return false;
}

void ReleaseLock(AGV agv, Zone zone) {
    if (zone.lockOwner == agv.id) {
        zone.lockOwner = NULL;
        // 唤醒下一个等待的AGV
        if (!zone.waitQueue.empty()) {
            NotifyAGV(zone.waitQueue.pop());
        }
    }
}

优点很明显：实现简单，逻辑清晰。我早期项目里就用这个，三天搞定。

但缺点也致命：容易死锁。两台车互相等对方释放锁，谁也动不了。我曾经遇到过四台车在环形路口死锁，排查了一整天才发现是锁申请顺序的问题。

避坑指南：我曾经在锁策略里忘了处理「优先级反转」。低优先级车拿着锁，高优先级车在后面干等。后来加了优先级继承才解决。

6.2 基于时间窗的交通管制

这个方法更优雅。不给AGV上锁，而是给每台车规划「时间窗」——也就是它占用某个路段的时间段。

你想想看，如果每台车都知道其他车什么时候经过哪里，那就可以错开时间，根本不用抢。

时间窗的核心要素：

  • 路段ID
  • 进入时间
  • 离开时间
  • AGV编号
// 时间窗冲突检测
bool CheckTimeWindowConflict(Path path, AGV agv) {
    for (auto &segment : path.segments) {
        TimeWindow proposed = {
            .segmentId = segment.id,
            .enterTime = agv.estimatedEnterTime,
            .exitTime = agv.estimatedExitTime
        };
        
        // 检查是否与已有时间窗重叠
        for (auto &existing : timeWindowTable[segment.id]) {
            if (IsOverlap(proposed, existing)) {
                return true;  // 冲突
            }
        }
    }
    return false;  // 无冲突
}

我个人习惯用时间窗处理高密度场景。比如仓库里有20台车同时作业，用锁的话早就乱成一锅粥了。时间窗可以提前规划，避免大部分冲突。

但时间窗也有麻烦：计算量大。每台车路径变了，所有相关时间窗都要重新算。我记得有一次优化，把时间窗重算从O(n²)降到了O(n log n)，系统吞吐量直接翻倍。

小技巧：时间窗不用算得太精确。留10%-20%的余量，应对AGV加减速、通信延迟等不确定因素。我吃过亏，算得太死，结果一台车慢了0.5秒，后面全乱了。

6.3 动态优先级调度

前面两种方法都是「平等对待所有车」。但现实中，车和车不一样。

有的车运的是紧急订单，有的车在空载回程，有的车电量不足需要赶紧去充电。这时候就需要动态优先级。

优先级动态调整的因素：

因素 权重 说明
任务紧急度 高 订单剩余时间越短，优先级越高
电池电量 中 低于20%时提升优先级
空载/重载 低 重载车优先通行
等待时间 中 防止饥饿，等待越久优先级越高 
// 动态优先级计算
int CalculatePriority(AGV agv) {
    int priority = 0;
    
    // 任务紧急度：剩余时间越少，优先级越高
    priority += (100 - agv.task.remainingTime) * 10;
    
    // 电池电量：低于20%时紧急提升
    if (agv.batteryLevel < 20) {
        priority += 500;
    }
    
    // 等待时间：每等待1秒加1分
    priority += agv.waitingTime;
    
    // 空载降权
    if (agv.isIdle) {
        priority -= 200;
    }
    
    return priority;
}

动态优先级和前面两种策略可以结合使用。比如：基于锁的管制里，高优先级车可以插队；基于时间窗的规划里，高优先级车的时间窗优先安排。

我建议你在实际项目中，把三种策略组合起来：

  • 简单场景（车少、路宽）：只用基于锁的管制
  • 复杂场景（车多、路窄）：时间窗 + 动态优先级
  • 混合场景：核心区域用时间窗，边缘区域用锁

注意：动态优先级有个陷阱——优先级反转。低优先级车拿着资源不放，高优先级车干等。我曾经在项目里加了个「优先级天花板」机制，才彻底解决。

三种策略对比

策略 优点 缺点 适用场景
基于锁 实现简单、响应快 容易死锁、吞吐量低 小车队、低密度
基于时间窗 无死锁、吞吐量高 计算量大、对延迟敏感 大车队、高密度
动态优先级 灵活、适应性强 实现复杂、有饥饿风险 任务多样、实时性要求高

知识体系总览

下面这张图，把三种策略的核心逻辑串起来了。我画图时习惯把「冲突检测」放在中间，因为不管哪种策略，本质都是在回答同一个问题：怎么让车不撞车？

说实话，没有哪种策略是银弹。我做了这么多年AGV调度，最大的体会是：理解业务场景比理解算法更重要。工厂里和仓库里，交通管制的侧重点完全不同。工厂追求稳定，仓库追求吞吐量。

选策略之前，先问自己三个问题：

  1. 有多少台车同时运行？
  2. 路网结构是简单还是复杂？
  3. 任务紧急程度差异大不大？

答案清楚了，策略自然就出来了。
