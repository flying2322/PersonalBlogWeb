5 多AGV路径规划：冲突类型与解决策略

各位同学好，我是老张。今天咱们聊聊多AGV路径规划里最头疼的问题——冲突。说实话，单台AGV跑起来很简单，但一旦多台车同时作业，冲突就不可避免了。我最早做AGV调度系统时，就吃过这个亏，当时觉得路径规划算法写得挺完美，结果一上线，几台车在交叉口堵成一锅粥。

嗯，今天的内容，就是把我这些年踩过的坑、总结的经验，掰开揉碎了讲给你听。

冲突的三种基本类型

先说说冲突的分类。我个人习惯把冲突分成三类：节点冲突、相向冲突、追赶冲突。你想想看，AGV在工厂里跑，跟汽车在路上跑其实很像，只不过AGV更死板——它必须沿着预设路径走，不能随便变道。

1. 节点冲突

节点冲突是最常见的。两辆AGV同时要经过同一个路口，或者要占用同一个工位。说白了，就是资源竞争。

典型场景：AGV-A要从(1,2)去(5,2)，AGV-B要从(3,4)去(3,0)。两条路径在交叉点(3,2)相遇。如果时间窗口重叠，就撞上了。

我在项目中遇到过这种情况：一个仓库有8台AGV同时作业，交叉路口就那么三四个。高峰期时，节点冲突能占到总冲突的60%以上。怎么解决？后面会细讲。

2. 相向冲突

相向冲突，就是两辆车在同一条直线上，面对面行驶。这在双向通行的路径上特别容易发生。

注意：相向冲突是最危险的。节点冲突最多是剐蹭，相向冲突搞不好就是正面碰撞。我曾经见过一台AGV直接把另一台的货叉撞弯了，维修费花了小两万。

为什么会这样？因为AGV的传感器通常装在前后两端，但侧向感知能力有限。两辆车面对面高速接近时，留给系统反应的时间很短。

3. 追赶冲突

追赶冲突，说白了就是追尾。前车慢，后车快，后车就怼上去了。

这种情况在环形路径或者长直道上很常见。比如AGV-A载重货，速度只有0.5m/s，AGV-B空载，速度1.5m/s。如果路径规划没考虑速度差异，B很快就会追上A。

冲突类型 发生条件 危险程度 典型场景
节点冲突 路径交叉/汇合 中 路口、工位入口
相向冲突 同一直线、方向相反 高 双向通道、窄巷道
追赶冲突 同一直线、方向相同、速度不同 低 长直道、环形路径

冲突解决三大策略

冲突检测出来了，怎么解决？我总结了三种策略：等待、绕行、重规划。这三种策略各有适用场景，也各有优缺点。

策略一：等待

等待是最简单粗暴的方法。检测到冲突后，让其中一辆AGV停下来，等另一辆通过后再走。

我的经验：等待策略适合解决节点冲突和追赶冲突。对于相向冲突，等待往往不是好选择——两辆车面对面停着，谁先走？这需要额外的协商机制。

等待策略的优点是实现简单，计算量小。缺点是会降低系统效率。你想想看，如果一台AGV在路口等10秒，后面可能堵一串车。

// 等待策略伪代码
function resolveConflict(agvA, agvB, conflictPoint):
    // 计算两车到达冲突点的时间
    timeA = calculateArrivalTime(agvA, conflictPoint)
    timeB = calculateArrivalTime(agvB, conflictPoint)
    
    // 让后到的车等待
    if timeA < timeB:
        agvB.addWaitPoint(conflictPoint, timeA - timeB + safetyMargin)
    else:
        agvA.addWaitPoint(conflictPoint, timeB - timeA + safetyMargin)

策略二：绕行

绕行就是让AGV走另一条路，避开冲突区域。这需要系统有备用路径。

我建议在路径规划阶段就为每个任务生成2-3条备选路径。主路径有冲突时，直接切换到备选路径。这样做的好处是响应快，不需要重新规划。

关键点：绕行策略依赖路径拓扑的冗余度。如果仓库里只有一条主干道，绕行就无从谈起。所以，好的AGV调度系统，在设计阶段就要考虑路径的冗余性。

绕行策略的缺点是什么？路径变长了，能耗和耗时都会增加。而且，如果多台AGV同时绕行，可能把冲突转移到其他区域。

策略三：重规划

重规划是最彻底的解决方案。检测到冲突后，重新为AGV规划一条全新的路径。

重规划通常使用A*算法或者Dijkstra算法，但需要把当前其他AGV的占用信息作为约束条件。说白了，就是在地图上标记出哪些路段已经被占用了，新路径不能走这些路段。

// 重规划策略核心逻辑
function replanPath(agv, occupiedEdges):
    // 构建带约束的路径图
    graph = buildGraphWithConstraints(occupiedEdges)
    
    // 使用A*算法搜索路径
    newPath = aStarSearch(
        graph, 
        agv.currentPosition, 
        agv.targetPosition,
        heuristic = manhattanDistance
    )
    
    if newPath is not None:
        agv.setPath(newPath)
    else:
        // 无路可走时，回退到等待策略
        agv.waitAtCurrentPosition()

注意：重规划的计算开销比较大。如果系统里有几十台AGV，每秒钟都要重规划，CPU可能扛不住。我曾经在一个项目里遇到过这个问题，后来加了缓存机制，把最近规划过的路径存起来，重复利用。

三种策略的对比与选择

说了这么多，到底该用哪种策略？我个人的经验是：没有银弹，得看场景。

策略 适用冲突类型 计算开销 系统效率影响 实现复杂度
等待 节点冲突、追赶冲突 低 中 低
绕行 所有类型（需备选路径） 低 低-中 中
重规划 所有类型 高 低（路径最优） 高

我建议这样组合使用：

  • 轻度冲突（比如只有1-2台AGV可能冲突）：用等待策略，简单高效
  • 中度冲突（3-5台AGV在同一个区域）：用绕行策略，避免长时间等待
  • 重度冲突（多台AGV形成死锁）：用重规划，彻底解决问题

避坑指南

最后，分享几个我踩过的坑：

  • 我曾经在一个项目里只用了等待策略，结果高峰期AGV排长队，效率惨不忍睹。后来加了绕行策略，效率提升了30%。
  • 我曾经在重规划时没考虑计算开销，导致系统卡死。后来加了超时机制，如果重规划超过50ms，就回退到等待策略。
  • 我曾经忽略了相向冲突的检测，结果两辆AGV在窄巷子里面对面停住了，谁也过不去。后来加了相向冲突的专门检测逻辑，提前让一辆车倒车让行。

嗯，今天就讲到这里。冲突处理是AGV调度系统的核心难点，没有之一。你把这些基础打牢了，后面学死锁检测、交通管制这些高级话题时，就会轻松很多。
