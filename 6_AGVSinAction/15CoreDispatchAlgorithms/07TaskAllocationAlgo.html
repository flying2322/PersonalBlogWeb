7 任务分配算法：从建模到实战

大家好，我是老张。今天咱们聊聊AGV调度里最核心的一环——任务分配。说白了，就是「哪个车去干哪个活」。这个问题看着简单，实际坑不少。我做了这么多年调度系统，光任务分配这块就踩过好几个大坑。

一、任务分配问题建模

先说说怎么把实际问题变成数学问题。你想想看，一个仓库里几十台AGV，几百个任务，怎么分最合理？

我个人习惯用指派问题来建模。核心要素就三个：

  • 任务集：T = {t₁, t₂, ..., tₙ}，每个任务有起点、终点、优先级
  • 车辆集：V = {v₁, v₂, ..., vₘ}，每辆车有当前位置、电量、状态
  • 代价矩阵：C[i][j] 表示车辆i执行任务j的代价

代价怎么算？我一般用加权综合指标：

代价 = α × 行驶距离 + β × 等待时间 + γ × 能耗 + δ × 优先级惩罚

α、β、γ、δ是权重系数，需要根据实际场景调。我在项目里遇到过，光调这四个参数就花了两周。

关键点：建模时一定要考虑动态性。任务会随时到达，车辆状态会变，所以模型必须是在线可更新的。

二、贪心算法：简单但够用

贪心算法是最直观的思路。每次来任务，找最近的车去执行。代码写起来也简单：

def greedy_assign(tasks, vehicles):
    assignments = []
    for task in tasks:
        best_vehicle = None
        min_cost = float('inf')
        for vehicle in vehicles:
            if vehicle.is_available():
                cost = compute_cost(vehicle, task)
                if cost < min_cost:
                    min_cost = cost
                    best_vehicle = vehicle
        if best_vehicle:
            assignments.append((best_vehicle, task))
            best_vehicle.assign(task)
    return assignments

嗯，这里要注意。贪心算法有个致命问题——局部最优不等于全局最优。我曾经在一个项目里用贪心，结果发现后面的任务因为车都被占用了，等待时间暴涨。

我的经验：贪心适合任务量小、实时性要求高的场景。比如产线边物料配送，任务来得快，必须马上响应。

三、匈牙利算法：全局最优解

如果任务和车辆数量固定，而且要求全局最优，那就得上匈牙利算法了。这个算法能解决最小化总代价的指派问题。

算法核心步骤：

  1. 构建代价矩阵（n×n，如果任务数≠车辆数，补0）
  2. 每行减去最小值
  3. 每列减去最小值
  4. 用最少的线覆盖所有0元素
  5. 如果线数=n，得到最优解；否则调整矩阵，重复步骤4

代码实现（简化版）：

def hungarian_algorithm(cost_matrix):
    n = len(cost_matrix)
    u = [0] * (n + 1)
    v = [0] * (n + 1)
    p = [0] * (n + 1)
    way = [0] * (n + 1)
    
    for i in range(1, n + 1):
        p[0] = i
        j0 = 0
        minv = [float('inf')] * (n + 1)
        used = [False] * (n + 1)
        while True:
            used[j0] = True
            i0 = p[j0]
            delta = float('inf')
            j1 = 0
            for j in range(1, n + 1):
                if not used[j]:
                    cur = cost_matrix[i0-1][j-1] - u[i0] - v[j]
                    if cur < minv[j]:
                        minv[j] = cur
                        way[j] = j0
                    if minv[j] < delta:
                        delta = minv[j]
                        j1 = j
            for j in range(n + 1):
                if used[j]:
                    u[p[j]] += delta
                    v[j] -= delta
                else:
                    minv[j] -= delta
            j0 = j1
            if p[j0] == 0:
                break
        while True:
            j1 = way[j0]
            p[j0] = p[j1]
            j0 = j1
            if j0 == 0:
                break
    return p[1:]

避坑指南：匈牙利算法时间复杂度O(n³)，当任务数超过100时，计算时间会明显增加。我曾经在200个任务的场景下跑，一次分配花了3秒多，这在实时系统里是不可接受的。

四、基于拍卖的分配策略

拍卖算法是我个人比较喜欢的一种方法。它模拟了真实拍卖的过程：每个任务「拍卖」，车辆「竞标」，价高者得。

核心流程：

  • 招标阶段：每个任务发布招标信息（位置、类型、优先级）
  • 投标阶段：每辆车计算自己执行该任务的代价，作为投标价
  • 评标阶段：选择投标价最低的车辆（或者综合评分最高的）
  • 中标阶段：分配任务，更新车辆状态

拍卖算法的优势在于分布式和可扩展。每个车辆可以独立计算投标价，非常适合大规模系统。

实战技巧：我在一个电商仓库的项目里，用了改进版的拍卖算法。加入了防饥饿机制——如果某个任务连续几轮没被分配，就提高它的优先级权重。这样避免了低优先级任务永远得不到执行的问题。

五、算法对比与选型建议

算法 时间复杂度 最优性 适用场景
贪心算法 O(n×m) 局部最优 实时性高、任务量小
匈牙利算法 O(n³) 全局最优 任务数固定、离线分配
拍卖算法 O(n×m×k) 近似最优 大规模、动态场景

选型时我一般遵循这个原则：

  • 任务数<50，用匈牙利算法，追求最优
  • 任务数50-200，用拍卖算法，平衡性能和效果
  • 任务数>200，用贪心算法，保证实时性
