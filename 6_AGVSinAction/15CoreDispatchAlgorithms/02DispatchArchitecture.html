2 调度系统架构：分层架构、核心模块与数据流设计

大家好，我是老张。今天咱们聊聊调度系统的骨架——架构设计。

很多人一上来就写代码，结果写到一半发现模块之间耦合得跟麻花似的。我早期也犯过这个错，后来被坑了几次，才慢慢摸清楚该怎么搭这个架子。

说白了，调度系统架构的核心就三件事：怎么分层、怎么划模块、数据怎么流。咱们一个一个说。

一、分层架构：为什么非要分三层？

我个人习惯把调度系统分成三层：接入层、调度层、执行层。你想想看，如果不分层，所有逻辑揉在一起，改一个功能可能牵动全局。我见过一个项目，就因为改了个任务优先级，结果把地图模块也搞崩了。

这三层各干各的：

  • 接入层：负责跟外部系统打交道。比如MES下发任务、WMS要搬运指令，都走这层。说白了就是“接客”的。
  • 调度层：核心大脑。任务分配、路径规划、交通管制，全在这层。我习惯把这层做得尽量“无状态”，方便水平扩展。
  • 执行层：跟AGV硬件通信。下发指令、接收状态、处理异常。这层要处理很多底层细节，比如通信超时、重连机制。

重要原则：每一层只依赖下一层，绝不跨层调用。接入层不能直接调用执行层，必须经过调度层。这个规矩破了，后面维护起来会非常痛苦。

二、核心模块划分：调度系统的“五脏六腑”

分层是骨架，模块才是血肉。我一般把调度层拆成这几个核心模块：

模块名称 核心职责 我踩过的坑
任务管理器 任务接收、拆分、合并、优先级排序 曾经没做任务拆分，一个长任务堵死了后面所有短任务
车辆管理器 车辆注册、状态维护、电量监控 忘记处理车辆离线重连后的状态同步，导致调度混乱
路径规划器 A*寻路、路径平滑、动态避障 地图更新时没加锁，路径规划读到一半的地图数据，直接飞出去了
交通管制器 路口分配、死锁检测、资源锁管理 死锁检测算法写得太简单，两个车互相等，系统直接卡死
异常处理器 任务超时、车辆故障、通信中断处理 异常处理没做分级，小故障也触发全局重置，搞得鸡飞狗跳

嗯，这里要注意：模块之间不要直接调用。我习惯用事件总线来解耦。比如任务完成事件，任务管理器只管发，谁关心谁订阅。这样加新功能的时候，不会动到老代码。

三、数据流设计：数据是怎么“跑”起来的？

数据流设计，说白了就是搞清楚“谁产生数据、谁消费数据、数据长什么样”。我一般画数据流图来理清关系。

一个典型的数据流是这样的：

  1. 外部系统（比如MES）通过接入层下发一个搬运任务
  2. 任务管理器收到后，先校验任务合法性，然后放入待分配队列
  3. 车辆管理器根据车辆状态（位置、电量、当前任务）选出最合适的车
  4. 路径规划器为这辆车规划一条从当前位置到目标点的路径
  5. 交通管制器检查路径上有没有冲突，分配路口资源
  6. 执行层把最终指令下发到AGV

你看，数据从接入层流到调度层，再流到执行层，每一步都有明确的处理逻辑。

关键设计点：数据流中一定要有回滚机制。比如路径规划失败，任务要能回到待分配状态，而不是直接丢弃。我曾经因为没做回滚，导致任务丢失，产线停了半小时，被老板骂得狗血淋头。

四、接口设计：模块之间怎么“说话”？

接口设计我遵循三个原则：简单、稳定、可扩展。

举个例子，任务分配接口我一般这么设计：

// 任务分配请求
{
  "taskId": "TASK_20240101_001",
  "type": "transport",        // 任务类型
  "priority": 5,              // 优先级 1-10
  "source": {"x": 10, "y": 20},
  "target": {"x": 50, "y": 80},
  "payload": "pallet_001",    // 搬运的货物
  "timeout": 300              // 超时时间（秒）
}

// 任务分配响应
{
  "code": 0,                  // 0成功，非0失败
  "message": "success",
  "data": {
    "vehicleId": "AGV_003",
    "path": [[10,20], [15,25], [30,40], [50,80]],
    "estimatedTime": 120
  }
}

我的习惯：接口字段尽量用全称，别用缩写。我曾经见过一个接口用"src"和"dst"，结果新来的同事猜了半天是"source"和"destination"还是"start"和"end"。这种歧义在线上出问题的时候特别要命。

模块之间的内部接口，我推荐用protobuf定义。好处是：

  • 字段可以加注释，生成代码后文档自动同步
  • 版本兼容性好，加字段不影响老版本
  • 序列化效率高，比JSON快3-5倍

避坑指南：我曾经在接口里直接传了AGV的IP地址，结果后来换网络架构，IP全变了，改接口改到吐血。记住：接口里只传逻辑标识（比如车辆ID），不要传物理地址。物理地址应该由配置中心管理。

五、总结一下

调度系统架构设计，说白了就是三件事：

  • 分层：接入层、调度层、执行层，各司其职
  • 划模块：任务管理、车辆管理、路径规划、交通管制、异常处理
  • 定接口：简单、稳定、可扩展，用事件总线解耦

架构设计没有银弹，每个项目都有自己的特点。但把基础框架搭好了，后面加功能、修bug都会轻松很多。我见过太多项目，前期图省事不分层，后期维护成本高得吓人。
