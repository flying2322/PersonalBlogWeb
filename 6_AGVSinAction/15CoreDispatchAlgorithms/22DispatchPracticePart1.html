22 AGV调度系统实战（一）——需求分析、系统设计、技术选型

大家好，我是老张。在AGV调度这个领域摸爬滚打了十几年，踩过的坑比走过的路还多。今天咱们正式开始实战篇，聊聊一个AGV调度系统从零到一，到底该怎么下手。

说实话，很多新手工程师一上来就急着写代码，结果做到一半发现需求没理清，架构撑不住，最后推倒重来。我见过太多这样的案例了。所以，咱们先沉住气，把地基打牢。

1.1 需求分析：别急着动手，先搞清楚要做什么

需求分析是第一步，也是最容易被忽视的一步。你想想看，如果连客户要什么都不知道，你写出来的调度算法再牛，也是白搭。

核心问题清单：

  • 场景是什么？ 是仓储、工厂产线，还是医院物流？不同场景对实时性、精度的要求天差地别。
  • AGV数量多少？ 10台以内和100台以上，调度算法的复杂度完全不是一个量级。
  • 地图多大？ 是几千平米的仓库，还是几万平米的园区？地图规模直接影响路径规划效率。
  • 任务类型有哪些？ 是简单的点对点搬运，还是需要多车协同、举升、对接等复杂动作？
  • 实时性要求多高？ 是秒级响应，还是毫秒级？这决定了你用什么样的调度策略。

我记得有一次，一个客户说“很简单，就几十台车，在仓库里跑跑”。结果我们去了现场才发现，仓库里全是狭窄通道，而且有大量人车混行。如果按常规的路径规划来做，肯定天天撞车。所以，现场调研比看图纸重要一百倍。

我的个人习惯： 每次做需求分析，我都会画一张“业务流程图”，把AGV从接单到完成任务的全过程走一遍。这样能发现很多隐藏的细节，比如“充电桩不够用怎么办？”、“任务优先级怎么定？”等等。

1.2 系统设计：搭好骨架，才能盖高楼

需求理清了，接下来就是系统设计。说白了，就是决定你的调度系统长什么样，各个模块怎么分工。

一个典型的AGV调度系统，我习惯把它拆成这几个核心模块：

  • 任务管理模块： 负责接收、解析、分配任务。说白了，就是“谁去干什么”。
  • 路径规划模块： 负责给每台AGV算出一条最优路径。这是调度系统的“大脑”。
  • 交通管理模块： 负责解决多车冲突，防止撞车和死锁。这是调度系统的“交警”。
  • 车辆控制模块： 负责与AGV硬件通信，下发指令，接收状态。这是调度系统的“手脚”。
  • 监控与日志模块： 负责实时展示系统状态，记录运行数据。这是调度系统的“眼睛”。

下面这张图，是我个人比较推崇的一种分层架构设计。你看，它把调度逻辑和底层硬件解耦了，这样换AGV品牌或者改地图，都不需要动核心算法。

你看，这个架构的好处是：每一层只关心自己的事。业务层不用管AGV怎么走，调度层不用管通信协议是什么。这样后期维护和扩展都方便得多。

避坑指南： 我曾经在一个项目里，把调度逻辑和通信协议写死在了一起。结果后来客户要换AGV品牌，我几乎重写了整个系统。从那以后，我再也不敢忽视分层设计了。

1.3 技术选型：选对工具，事半功倍

架构定好了，接下来就是选技术栈。这里没有银弹，只有最适合你场景的方案。我根据自己的经验，整理了一个对比表：

技术维度 推荐方案 备选方案 我的建议
编程语言 Java / Go C++ / Python Java生态成熟，Go并发性能好。我一般用Java做调度核心，Python做算法原型验证。
数据库 PostgreSQL + Redis MySQL + MongoDB PostgreSQL支持GIS扩展，适合地图数据。Redis做缓存和实时状态，速度飞快。
通信框架 gRPC / Netty WebSocket / RabbitMQ gRPC性能高，适合内部服务调用。Netty适合处理大量AGV的长连接。
路径规划库 自研 + JGraphT Boost Graph / OSRM JGraphT轻量好用，适合快速实现A*。但复杂场景还是得自己写优化。
部署方式 Docker + K8s 裸机部署 容器化部署方便扩缩容，尤其是多车场景下，调度节点可以动态扩展。

嗯，这里要注意一点：不要盲目追求新技术。我见过有人用Kubernetes部署一个只有5台AGV的系统，结果运维成本比开发成本还高。小项目用Docker Compose就够了。

我的一个小技巧： 在技术选型时，我会先问自己三个问题：

  1. 这个技术团队里有人熟悉吗？没人熟悉的话，学习成本有多高？
  2. 这个技术的社区活跃吗？遇到问题能不能快速找到答案？
  3. 这个技术能支撑未来2-3年的业务增长吗？

这三个问题想清楚了，选型基本不会出大错。

1.4 小结：从需求到落地，一步都不能少

好了，这一章的内容就到这里。咱们回顾一下：

  • 需求分析要深入现场，搞清楚场景、规模、实时性等关键指标。
  • 系统设计要分层解耦，让每个模块各司其职。
  • 技术选型要务实，选团队熟悉、社区活跃、能支撑未来发展的方案。

说实话，这些看起来都是“软技能”，但往往决定了项目的成败。我见过太多人把精力花在调参和优化算法上，结果系统上线第一天就崩溃了——因为架构根本扛不住压力。
