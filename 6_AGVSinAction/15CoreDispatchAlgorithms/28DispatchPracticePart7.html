28 AGV调度系统实战（七）：部署上线、运维保障

兄弟们，终于走到这一步了。

前面我们聊了算法、聊了架构、聊了仿真。但说句实在话，那些都还是在“温室”里。真正见真章的，是今天要讲的——部署上线和运维保障。

我见过太多系统，仿真跑得飞起，一上线就崩。为什么？因为现场环境太复杂了。灰尘、震动、网络波动、甚至工人不小心踢了一脚路由器……这些在仿真里可模拟不出来。

1. 部署策略：别想着“一步到位”

我个人习惯，部署一定要分阶段走。千万别搞“Big Bang”式上线，那是给自己挖坑。

推荐的三阶段部署法：
  1. 灰度部署（1-2台车）：先让一两台AGV跑起来，观察调度系统的响应。这时候出问题，影响面最小。
  2. 小批量部署（10-20台车）：验证多车协同、交通管制、死锁恢复等核心逻辑。
  3. 全量部署：确认没问题后，再放开所有车辆。

我在项目里遇到过最惨的一次，就是客户催得急，直接全量上线。结果调度系统因为数据库连接池配置太小，所有AGV同时请求任务时，直接把数据库打挂了。嗯，那晚我陪着运维大哥熬到凌晨三点。

2. 配置管理：环境差异是魔鬼

开发环境、测试环境、生产环境，这三者之间总有差异。你想想看，开发时用的Wi-Fi，现场可能是工业5G；开发时地图是干净的，现场可能有临时堆放的物料。

我的做法是：所有环境相关的参数，必须外置到配置文件。比如：

# 调度系统核心配置示例
[network]
scheduler_host = 192.168.1.100  # 生产环境IP
scheduler_port = 8080

[database]
connection_string = postgresql://user:pass@prod-db:5432/agv
max_connections = 50  # 生产环境要调大

[agv]
default_speed = 1.2  # m/s，现场实测后调整
collision_margin = 0.5  # 米，安全距离
避坑指南：我曾经因为配置文件里忘了改数据库IP，导致灰度部署时，测试车连到了生产数据库，把正式任务表给污染了。从那以后，我强制要求每个环境必须有独立的配置文件，并且用Git管理版本。

3. 监控告警：没有监控，就是盲人摸象

系统上线后，你不可能24小时盯着屏幕。所以，监控和告警就是你的眼睛和耳朵。

我一般会监控这几个核心指标：

指标 说明 告警阈值
任务响应时间 从下发任务到AGV开始执行的时间 > 2秒
调度队列长度 等待调度的任务数量 > 100
AGV心跳超时 AGV超过多久未上报状态 > 5秒
死锁发生次数 单位时间内死锁次数 > 3次/小时
CPU/内存使用率 调度服务器资源占用 CPU > 80%, 内存 > 85%

说白了，告警不是越多越好。告警太多，运维人员会麻木，最后变成“狼来了”。我建议只对直接影响业务的指标设置告警。

4. 日志体系：出问题时的救命稻草

系统出故障时，第一件事就是查日志。但如果你日志打得乱七八糟，查起来比登天还难。

我个人的日志规范：

  • 统一格式：[时间] [级别] [模块] [请求ID] 消息
  • 分级清晰：ERROR（系统不可用）、WARN（异常但可恢复）、INFO（关键流程）、DEBUG（调试用）
  • 带上上下文：比如AGV ID、任务ID、路径点坐标等

举个例子，一个合格的日志应该是这样的：

2025-03-15 14:23:45.678 ERROR [TaskDispatcher] [req-abc123] 
任务T-20250315-001分配失败，AGV-05当前状态：BLOCKED，位置：(12.5, 34.2)，原因：目标路径被AGV-08占用

你看，这条日志包含了时间、级别、模块、请求ID、任务ID、AGV ID、位置、原因。拿到这条日志，你基本不用看代码就能定位问题。

注意：生产环境不要打DEBUG日志，否则磁盘会很快写满。我见过一个团队，上线时忘了关DEBUG，结果一天就写了200GB日志，直接把磁盘撑爆了。

5. 容灾与备份：别等出事了再想

系统跑着跑着，服务器突然宕机了怎么办？

我的建议是：

  • 调度服务器主备切换：主节点挂了，备用节点自动接管。AGV会短暂失联几秒，但不会停摆。
  • 数据库定时备份：任务记录、地图数据、AGV配置，这些丢了就麻烦了。我习惯每小时增量备份，每天全量备份。
  • AGV本地缓存：如果网络断了，AGV至少能执行完当前任务，然后停在安全位置等待恢复。

说白了，容灾设计就是“最坏情况下的兜底方案”。你永远不知道意外什么时候来，但你可以提前准备好。

7. 写在最后

部署上线，说白了就是把你的代码放到真实世界里去接受考验。这个过程会暴露很多你在开发时根本想不到的问题。

我的经验是：不要怕出问题，但要确保出了问题能快速恢复。灰度部署、完善的监控、清晰的日志、可靠的备份，这些就是你的安全网。
