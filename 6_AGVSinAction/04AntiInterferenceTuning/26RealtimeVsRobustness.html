26 实时性与抗干扰平衡：算法复杂度与实时性约束，多线程与任务优先级调度，硬件加速（FPGA、GPU）在抗干扰中的应用

做AGV导航系统这么多年，我越来越觉得——实时性和抗干扰，就像跷跷板的两头。你压下去一头，另一头就翘起来。

你想想看，AGV在工厂里跑，传感器数据哗哗地来。你要是把抗干扰算法做得太复杂，CPU算不过来，控制周期就拉长了。车都撞上了，你还在算那个滤波器的系数——这有什么意义？

反过来，你要是为了实时性，啥滤波都不做，直接拿原始数据去控制——嗯，一个电磁干扰脉冲过来，电机就抖一下，定位就跳一下。搞不好货架都给你撞歪了。

所以今天咱们就聊聊，怎么在这两头之间找到平衡点。

算法复杂度与实时性约束

先说说算法复杂度这件事。

我个人习惯，在选型阶段就会把实时性约束定死。比如激光SLAM的定位更新周期，我一般要求10ms以内。为什么是10ms？因为AGV跑1m/s的时候，10ms才走1cm。这个精度够用了。

但问题来了——你用的抗干扰算法，能在10ms内跑完吗？

我举个例子。卡尔曼滤波，复杂度是O(n³)，n是状态维度。你要是用15维状态（位置、姿态、速度、陀螺偏置...），一次更新大概要算几千次浮点运算。在ARM Cortex-A72上，大概0.5ms搞定。没问题。

但你要是用粒子滤波，粒子数一上5000，一次更新就要几十毫秒。这就超标了。

核心原则： 抗干扰算法的计算时间，不能超过控制周期的20%。留出余量给其他任务。

我在项目中遇到过一件事。有个客户，AGV在仓库里老是定位跳变。我一看代码，他们用了三层嵌套的滑动窗口滤波，每个窗口长度200点。算一下——O(n³)复杂度，一次滤波要算800万次乘法。控制周期是50ms，根本跑不完。结果就是滤波没跑完，下一帧数据又来了，队列越积越长，最后定位直接卡死。

后来我把三层滤波改成两层，窗口长度降到50点，复杂度降了两个数量级。定位稳了，实时性也保住了。

所以我的建议是：先算复杂度，再选算法。别一上来就上重型武器。

算法 时间复杂度 典型耗时（ARM A72） 适用场景
卡尔曼滤波 O(n³) 0.3-1ms 线性系统，高斯噪声
扩展卡尔曼滤波 O(n³) 0.5-2ms 弱非线性系统
粒子滤波 O(N·n) 10-100ms 强非线性，非高斯
滑动窗口平均 O(W) 0.01-0.1ms 简单平滑，低延迟

多线程与任务优先级调度

算法选好了，接下来就是怎么调度。

说白了，AGV的软件系统就像个厨房。传感器数据采集是切菜，定位解算是炒菜，控制输出是装盘。你不能让切菜的占着灶台，也不能让炒菜的等着切菜。

我一般把任务分成三个优先级：

  • 高优先级（实时线程）：传感器数据采集、电机控制输出。周期1ms以内。必须保证。
  • 中优先级（准实时线程）：定位解算、抗干扰滤波。周期10ms以内。可以偶尔抖动。
  • 低优先级（非实时线程）：路径规划、日志记录、通信。周期100ms以上。可以等。

这里有个坑——优先级反转。我曾经在一个项目里吃过亏。高优先级的控制线程，等一个被低优先级线程占用的互斥锁。结果低优先级线程又被中优先级线程抢占了CPU。高优先级线程活活等了50ms才拿到锁。AGV直接冲出去了。

避坑指南： 我曾经在实时线程里用了malloc分配内存——这是大忌。malloc可能触发系统调用，导致线程被挂起。后来我改用预分配内存池，再也没出过问题。

我的做法是：实时线程里不要用任何阻塞操作。不要加锁，不要malloc，不要printf。数据交换用无锁队列。我习惯用环形缓冲区，生产者消费者模式，原子操作控制读写指针。

代码大概长这样：

// 无锁环形缓冲区，用于传感器数据传递
#define BUF_SIZE 256

typedef struct {
    float data[3];  // x, y, theta
    uint64_t timestamp;
} PoseData;

typedef struct {
    PoseData buffer[BUF_SIZE];
    atomic_int head;
    atomic_int tail;
} LockFreeQueue;

// 生产者（传感器线程）
void producer(LockFreeQueue* q, PoseData* pose) {
    int next = (atomic_load(&q->head) + 1) % BUF_SIZE;
    while (next == atomic_load(&q->tail)) {
        // 队列满，丢弃旧数据
        atomic_thread_yield();
    }
    q->buffer[atomic_load(&q->head)] = *pose;
    atomic_store(&q->head, next);
}

// 消费者（定位线程）
bool consumer(LockFreeQueue* q, PoseData* pose) {
    if (atomic_load(&q->tail) == atomic_load(&q->head)) {
        return false;  // 队列空
    }
    *pose = q->buffer[atomic_load(&q->tail)];
    atomic_store(&q->tail, (atomic_load(&q->tail) + 1) % BUF_SIZE);
    return true;
}

这个结构我在三个项目里用过，从来没丢过数据。而且延迟稳定在微秒级。

硬件加速：FPGA、GPU在抗干扰中的应用

软件优化做到极致了，有时候还是不够。这时候就得请硬件出场了。

我最早接触硬件加速，是在一个视觉导航项目里。AGV要实时处理640×480的图像，做特征点提取和匹配。CPU上跑，一帧要80ms。控制周期是20ms——根本没法用。

后来我把特征提取算法移植到FPGA上。流水线架构，每个像素时钟周期处理一个。结果一帧只用了3ms。快了26倍。

为什么会这么快？因为FPGA是硬件并行。你想想看，CPU是串行的，一条指令一条指令地跑。FPGA不一样，它可以同时做几百个乘加运算。像卡尔曼滤波里的矩阵乘法，在FPGA上可以做到一个时钟周期算完一个4×4矩阵。

GPU呢？GPU适合做大规模并行计算。比如粒子滤波，5000个粒子，每个粒子独立计算权重。在GPU上可以同时跑5000个线程，一次搞定。CPU上要跑几十毫秒，GPU上可能只要1-2毫秒。

我的经验： 如果算法是数据并行（每个数据点独立计算），用GPU。如果算法是流水线并行（每个阶段依赖上一阶段结果），用FPGA。

但硬件加速也有代价。FPGA开发周期长，调试困难。GPU功耗高，散热是个问题。我一般只在实时性要求极高（1ms以内）或者计算量极大（每秒几亿次运算）的场景下才用硬件加速。

嗯，关于实时性与抗干扰的平衡，今天就聊到这儿。核心就三句话：算法选型要算复杂度，多线程调度要防优先级反转，硬件加速要用在刀刃上。
