24 多AGV协同抗干扰：多车通信干扰与协调调度，协同定位中的相对观测抗干扰，分布式地图更新与一致性维护

多AGV协同，说白了就是让一群小车像蚂蚁一样干活。但蚂蚁之间靠信息素沟通，AGV之间靠无线通信。这通信一旦被干扰，整个车队就乱套了。我这些年调试过多车系统，踩过的坑真不少。今天咱们就聊聊怎么让多台AGV在干扰环境下还能好好配合。

24.1 多车通信干扰与协调调度

多车通信干扰，最常见的就是同频干扰。你想想看，十几台AGV在同一个车间里跑，每台都在发定位数据、状态信息，信道挤得跟早高峰地铁似的。我有个项目，车间里还有几台变频器，那电磁环境，啧啧，通信丢包率能到30%。

核心问题：通信干扰导致调度指令丢失、状态不同步，严重时引发碰撞或死锁。

24.1.1 通信抗干扰策略

我个人习惯用这么几招：

  • 跳频通信：检测到某个频点干扰严重，自动跳到干净频点。我在一个汽车零部件仓库用过，效果不错。
  • 时分多址（TDMA）：给每台AGV分配固定的时隙，避免同时发送。说白了就是排好队，一个一个来。
  • 冗余通信链路：主链路用Wi-Fi，备用链路用LoRa或UWB。主链路挂了，自动切到备用。

我的经验：别迷信单一通信技术。我见过一个项目只用Wi-Fi，结果车间里一台大型焊接设备启动，整个Wi-Fi网络瘫痪了半小时。从那以后，我坚持至少双链路冗余。

24.1.2 协调调度抗干扰

通信有干扰，调度算法就得扛得住。我常用的方法是：

  1. 本地决策优先：每台AGV本地维护一个任务队列，通信中断时按优先级执行本地任务。
  2. 心跳超时机制：如果连续3个心跳周期没收到调度中心指令，AGV自动降速并进入安全模式。
  3. 动态路径重规划：检测到某区域通信质量差，调度中心主动避开那片区域。
// 伪代码：通信中断时的本地决策
if (heartbeat_timeout > 3) {
    set_speed(0.5);  // 降速
    enter_safe_mode();
    execute_local_task_queue();
    // 持续尝试重连
    while (!reconnect()) {
        wait(100ms);
    }
    resume_normal_mode();
}

24.2 协同定位中的相对观测抗干扰

多车协同定位，核心是相对观测。每台AGV通过UWB、激光雷达或视觉，测量自己与邻居的相对位置。但干扰一来，这些观测值就变得不可靠。

为什么会这样？我遇到过UWB信号在金属货架间反射，测距误差能到2米。还有一次，两台AGV的激光雷达互相照射，导致对方雷达数据全是噪点。

24.2.1 相对观测的鲁棒处理

我的做法是：

  • 一致性检验：对同一邻居的多次观测做卡方检验，剔除异常值。
  • 多传感器融合：UWB测距 + 激光雷达测角 + 里程计推算，用扩展卡尔曼滤波融合。
  • 置信度加权：根据当前干扰强度，动态调整各传感器的权重。

注意：千万别在干扰强的时候完全相信某个传感器。我曾经吃过亏，一台AGV的UWB被干扰，测距值跳变，结果它以为邻居突然靠近，急刹车导致后车追尾。

24.2.2 协同定位的抗干扰架构

我推荐用图优化框架来做协同定位。每台AGV是一个节点，相对观测是边。干扰导致某些边不可靠，就降低它的权重或直接剔除。

// 图优化中的鲁棒核函数
// Huber核函数：对大的残差进行抑制
double huber_loss(double residual, double delta) {
    if (fabs(residual) <= delta) {
        return 0.5 * residual * residual;
    } else {
        return delta * (fabs(residual) - 0.5 * delta);
    }
}

24.3 分布式地图更新与一致性维护

多车协同，地图必须一致。否则，A车认为这里有路，B车认为这里是墙，那肯定要出问题。分布式地图更新，难点在于怎么让所有AGV的地图最终收敛到同一个版本。

24.3.1 地图更新的抗干扰策略

我常用的方法：

  • 增量式更新：每台AGV只更新自己观测到的局部地图，然后广播给邻居。
  • 版本号机制：每个地图块带一个版本号，只接受版本号更高的更新。
  • 冲突解决：如果两台AGV对同一区域的地图更新冲突，用时间戳+优先级裁决。

一个小技巧：地图更新不要全量广播，太占带宽。我习惯用差分更新，只发送变化的部分。在通信干扰环境下，这能省下不少带宽。

24.3.2 一致性维护算法

分布式一致性，说白了就是让所有AGV对地图的认知达成一致。我推荐用Raft或Paxos的简化版。但说实话，在工业现场，完全严格的共识算法太重了。我一般用Gossip协议 + 定期全量同步。

// Gossip协议伪代码
// 每台AGV定期随机选择一个邻居，交换地图更新
void gossip_update() {
    neighbor = select_random_neighbor();
    send_local_updates(neighbor);
    receive_remote_updates(neighbor);
    merge_maps();
}

24.3.3 抗干扰的一致性维护

通信干扰下，一致性维护要更鲁棒：

  1. 冗余传播：每个地图更新至少发送给3个不同邻居，确保即使部分通信中断，更新也能扩散。
  2. 超时重传：如果某个邻居长时间没回应，标记为不可达，换其他邻居。
  3. 定期全量同步：每10分钟做一次全量地图同步，纠正累积误差。

核心原则：在干扰环境下，宁可地图更新慢一点，也不能让地图不一致。我见过一个项目，因为地图不一致，两台AGV同时认为同一块区域是自己的专属通道，结果在路口僵持了20分钟。

下面这张图，是我对多AGV协同抗干扰的整体理解。你可以把它当作一个检查清单，调试时对照着看。

这张图把三大块串起来了。通信干扰影响调度，调度又影响定位，定位又影响地图更新。一环扣一环，哪个环节出问题，整个系统就崩。所以调试时，我习惯从通信层开始排查，一层一层往上走。

最后提醒一句：多AGV协同抗干扰，没有银弹。每个现场的环境都不一样，干扰源也不同。我建议你到现场先做一周的电磁环境摸底测试，搞清楚干扰的频谱特征和时序规律，再针对性地设计抗干扰方案。别一上来就套模板，容易翻车。
