29 项目实战：从零搭建AGV控制器固件、功能模块联调、现场部署与维护

说实话，前面讲了那么多理论，这一章才是真正见真章的时候。

从零搭建AGV控制器固件，听起来挺唬人。但拆开来看，无非就是：搭框架、填模块、联调、下地干活。我这些年带团队做AGV项目，最怕的不是技术难，而是大家把简单事情搞复杂了。

29.1 固件架构设计——先把骨架立起来

我个人习惯，写固件之前先画图。不是画代码流程图，而是画模块依赖图。AGV控制器说白了就这几大块：

  • 运动控制层：电机驱动、编码器、PID调节
  • 感知层：激光雷达、IMU、超声波、碰撞传感器
  • 决策层：路径规划、避障逻辑、任务调度
  • 通信层：WiFi、CAN、串口、Modbus
  • 管理层：电池管理、状态监控、日志系统

嗯，这里要注意：不要一开始就想着把所有功能都塞进去。我在项目中遇到过，有人一上来就把激光SLAM、视觉识别全加进去，结果光调试就花了三个月。先跑通基础运动控制，再往上叠功能，这才是正道。

核心原则：先让车能动，再让车跑好，最后才让车聪明。

29.2 从零搭建——先让电机转起来

你想想看，AGV最核心的是什么？是动。所以第一步，先把电机驱动搞定。

我一般会先写一个电机抽象层，把PWM、方向、编码器反馈封装成统一接口。这样后面换电机驱动芯片，只需要改底层，上层代码纹丝不动。

/* 电机抽象接口示例 */
typedef struct {
    void (*set_speed)(int16_t speed);      /* 设置目标速度 */
    int16_t (*get_speed)(void);            /* 获取当前速度 */
    void (*set_direction)(uint8_t dir);    /* 设置方向 */
    void (*emergency_stop)(void);          /* 急停 */
} motor_drv_t;

/* 左轮电机实例 */
motor_drv_t motor_left = {
    .set_speed = left_motor_set_speed,
    .get_speed = left_motor_get_speed,
    .set_direction = left_motor_set_dir,
    .emergency_stop = left_motor_emergency_stop
};

小技巧：编码器读取建议用硬件定时器捕获，别用外部中断。我曾经用外部中断读编码器，结果电机一转，中断风暴直接把系统干崩了。换成定时器捕获后，世界清净了。

29.3 功能模块联调——让各个模块说上话

模块联调是最容易出幺蛾子的阶段。我总结了一套三步走策略：

  1. 单模块自测：每个模块单独跑，确认功能正常。比如激光雷达能出数据，电机能转，IMU能输出姿态。
  2. 两两联调：把两个模块串起来。比如运动控制+编码器，看闭环能不能稳住。
  3. 全系统联调：所有模块一起跑，模拟真实场景。

这里有个坑，我踩过好几次——任务优先级冲突。举个例子，激光雷达数据采集任务优先级设得太高，结果电机控制任务抢不到CPU，车跑起来一抖一抖的。

注意：RTOS的任务优先级不是越高越好。运动控制任务建议最高优先级，传感器采集次之，通信任务可以放低。但急停任务必须最高，这是安全底线。

29.4 现场部署——从实验室到工厂

实验室里跑得好好的，一到现场就出问题。这种事我见得太多了。

现场部署有几个致命差异：

项目 实验室环境 现场环境
地面 平整、干燥 有坡度、油污、金属碎屑
光照 稳定 强光、阴影、频闪
电磁干扰 低 电机启停、变频器、焊接机
WiFi信号 稳定 多AP切换、信号衰减

我建议，现场部署前一定要做环境摸底。拿个示波器去测一下电源纹波，拿频谱仪扫一下WiFi信道。别嫌麻烦，这些数据能帮你省下至少一周的调试时间。

29.5 维护与远程升级——让固件能"自我进化"

AGV一旦部署下去，你不可能每次都跑现场去升级固件。所以OTA升级是必须的。

我常用的方案是：

  • 固件分两个区：Bootloader区和App区
  • Bootloader负责校验和跳转，App负责业务逻辑
  • 升级时，新固件先下载到备份区，校验通过后再切换
/* Bootloader跳转逻辑简化版 */
void bootloader_jump_to_app(void) {
    uint32_t app_addr = 0x08020000;  /* App起始地址 */
    
    /* 校验App区CRC */
    if (crc32_check(app_addr, APP_SIZE) != 0) {
        /* CRC校验失败，进入固件恢复模式 */
        enter_firmware_recovery();
        return;
    }
    
    /* 关闭所有中断，设置堆栈指针，跳转 */
    __disable_irq();
    SCB->VTOR = app_addr;
    asm volatile("ldr sp, [%0]" : : "r"(app_addr));
    asm volatile("ldr pc, [%0, #4]" : : "r"(app_addr));
}

经验之谈：OTA升级一定要有回滚机制。我曾经有一次升级后，发现新版本有bug导致AGV原地打转。幸好保留了上一版固件，远程回滚后车才恢复正常。从那以后，我每个版本都保留至少两个历史固件。

29.6 日志系统——调试的"黑匣子"

现场出问题，你不在旁边，怎么办？靠日志。

我设计的日志系统有三级：

  • 运行日志：记录任务切换、传感器数据、电机指令。循环写入，保留最近30分钟。
  • 错误日志：记录异常事件，比如电机过流、通信超时、急停触发。掉电不丢失。
  • 调试日志：开发阶段用，发布版本关闭。

日志格式我建议用二进制+时间戳，别用字符串。字符串太占空间，而且解析慢。二进制日志配合上位机解析工具，效率高得多。

29.7 最后说几句

从零搭建AGV控制器固件，说白了就是把复杂问题拆成小块，一块一块吃掉。别想着一步到位，也别被各种高大上的算法吓住。

我见过太多团队，花三个月研究路径规划算法，结果车都跑不起来。先把基础打牢，让车能动、能停、能避障，后面再慢慢优化。

嗯，这一章就到这里。记住：嵌入式开发，动手比动嘴重要一万倍。
