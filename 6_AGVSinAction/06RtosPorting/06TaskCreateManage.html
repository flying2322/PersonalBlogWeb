6 任务创建与管理：任务控制块（TCB）设计、任务栈空间分配、任务创建API实现

各位同学，咱们今天聊点硬核的。任务创建与管理，说白了就是RTOS的「心脏起搏器」。你想想看，一个实时操作系统要是连任务都管不好，那还谈什么实时性？

我个人习惯把任务管理比作「公司人事部」。TCB就是员工的档案袋，栈空间就是工位，创建API就是招聘流程。这三样东西搞明白了，RTOS的调度基础就稳了。

6.1 任务控制块（TCB）设计

TCB是什么？每个任务在系统里都有一个「身份证」。这个身份证记录了任务的所有关键信息。我在项目中遇到过最坑的事，就是TCB设计得太臃肿，导致内存碎片化严重。

一个典型的TCB结构体，我一般这样设计：

typedef struct tcb {
    uint32_t    *stack_ptr;      // 当前栈指针
    uint32_t    *stack_base;     // 栈底地址
    uint32_t    stack_size;      // 栈大小（字节）
    
    uint8_t     priority;        // 任务优先级
    uint8_t     state;           // 任务状态
    uint8_t     task_id;         // 任务ID
    
    char        task_name[16];   // 任务名称（调试用）
    
    void        (*entry)(void*); // 任务入口函数
    void        *param;          // 入口参数
    
    uint32_t    delay_ticks;     // 延时计数
    struct tcb  *next;           // 链表指针
} TCB_t;

嗯，这里要注意几个关键点：

  • 栈指针和栈底：这两个字段必须紧挨着，因为上下文切换时频繁访问
  • 优先级字段：我建议用uint8_t，够用且节省内存
  • 任务名称：调试利器！没有它，你查bug时会想哭

核心原则：TCB设计要「小而精」。每个字段都有明确用途，不要为了「以后可能用到」而加冗余字段。我见过有人把任务历史统计也塞进TCB，结果一个任务控制块占了128字节，简直是浪费。

我的小技巧：TCB结构体最好用__packed或#pragma pack(1)对齐。为什么？因为RTOS里TCB经常被批量创建，内存对齐浪费会累积。我曾经在一个项目里，就因为没做紧凑对齐，8个任务多占了64字节的RAM——在资源紧张的MCU上，这可不是小数目。

6.2 任务栈空间分配

栈空间分配，这是新手最容易翻车的地方。你想想看，每个任务都需要自己的栈空间，但到底给多大？给多了浪费，给少了栈溢出。

我一般遵循这个经验法则：

任务类型 推荐栈大小 说明
简单任务（LED闪烁等） 128-256字节 几乎没有局部变量
中等任务（传感器读取） 512-1024字节 有少量局部数组
复杂任务（通信协议栈） 2048-4096字节 可能有递归调用
控制任务（PID运算） 1024-2048字节 浮点运算消耗栈空间

我曾经在一个AGV控制器项目里，有个任务负责路径规划，我给了2KB栈空间。结果跑着跑着就死机了。查了三天，发现是递归调用时栈溢出了。后来改成4KB，问题解决。所以我的建议是：先给大一点，稳定后再优化。

避坑指南：我曾经在STM32F4上移植RTOS，默认给每个任务分配了1KB栈。结果有个任务调用了printf，直接栈溢出。为什么？printf内部会分配一个很大的缓冲区。所以，凡是涉及标准库函数调用的任务，栈空间至少翻倍。

栈空间分配还有一个关键点：栈对齐。ARM Cortex-M要求栈指针必须8字节对齐。如果你分配栈空间时没注意对齐，任务切换时就会触发硬件异常。我一般这样分配：

// 栈空间分配函数
static uint32_t *stack_alloc(uint32_t size) {
    // 确保8字节对齐
    size = (size + 7) & ~7;
    
    uint8_t *mem = (uint8_t*)malloc(size);
    if (mem == NULL) {
        return NULL;  // 内存不足
    }
    
    // 返回栈顶地址（栈向下生长）
    return (uint32_t*)(mem + size);
}

6.3 任务创建API实现

好了，TCB和栈空间都准备好了，接下来就是创建任务。任务创建API，说白了就是「把TCB和栈空间绑定在一起，再初始化一些关键字段」。

我设计的任务创建函数长这样：

int task_create(
    void (*entry)(void*),   // 任务入口
    void *param,            // 入口参数
    uint8_t priority,       // 优先级
    uint32_t stack_size,    // 栈大小
    const char *name        // 任务名称
) {
    TCB_t *tcb;
    uint32_t *stack_top;
    
    // 1. 分配TCB
    tcb = (TCB_t*)malloc(sizeof(TCB_t));
    if (tcb == NULL) return -1;
    
    // 2. 分配栈空间
    stack_top = stack_alloc(stack_size);
    if (stack_top == NULL) {
        free(tcb);
        return -2;
    }
    
    // 3. 初始化TCB字段
    tcb->stack_base = stack_top - stack_size/4;
    tcb->stack_ptr  = stack_top;
    tcb->stack_size = stack_size;
    tcb->priority   = priority;
    tcb->state      = TASK_READY;
    tcb->entry      = entry;
    tcb->param      = param;
    tcb->delay_ticks = 0;
    
    // 复制任务名称（最多15字符+'\0'）
    strncpy(tcb->task_name, name, 15);
    tcb->task_name[15] = '\0';
    
    // 4. 初始化任务栈（模拟第一次上下文切换）
    // 这里会填充初始寄存器值
    tcb->stack_ptr = init_task_stack(
        tcb->stack_ptr,
        entry,
        param
    );
    
    // 5. 加入就绪队列
    task_ready_queue_add(tcb);
    
    return 0;
}

这里最关键的是第4步——初始化任务栈。为什么？因为任务第一次运行时，CPU需要从栈里恢复「初始上下文」。说白了，就是假装这个任务之前被切换出去过，现在要切换回来。

init_task_stack函数的具体实现，我一般这样写：

static uint32_t *init_task_stack(
    uint32_t *stack_top,
    void (*entry)(void*),
    void *param
) {
    // 模拟异常压栈顺序
    // 对于ARM Cortex-M，异常时自动压栈顺序：
    // R0, R1, R2, R3, R12, LR, PC, xPSR
    
    stack_top--; *stack_top = 0x01000000;  // xPSR（默认使用Thumb模式）
    stack_top--; *stack_top = (uint32_t)entry; // PC（任务入口地址）
    stack_top--; *stack_top = 0xFFFFFFFD;  // LR（异常返回，使用主栈）
    stack_top--; *stack_top = 0x00000000;  // R12
    stack_top--; *stack_top = 0x00000003;  // R3
    stack_top--; *stack_top = 0x00000002;  // R2
    stack_top--; *stack_top = 0x00000001;  // R1
    stack_top--; *stack_top = (uint32_t)param; // R0（第一个参数）
    
    // 剩余的通用寄存器（R4-R11）
    for (int i = 0; i < 8; i++) {
        stack_top--; *stack_top = 0x00000000;
    }
    
    return stack_top;
}

重点提醒：xPSR寄存器的bit24必须置1，表示使用Thumb指令集。我见过有人忘了这个，结果任务第一次切换时直接进HardFault。嗯，这个坑我踩过，所以特别提醒你们。

任务创建完成后，TCB会被加入就绪队列。就绪队列我一般用双向链表实现，按优先级排序。这样调度器每次找最高优先级任务时，直接取链表头就行，时间复杂度O(1)。

我的经验：任务创建API最好支持「静态创建」和「动态创建」两种方式。静态创建在编译时分配TCB和栈空间，适合确定性要求高的场景。动态创建用malloc，灵活但可能产生碎片。在AGV控制器里，我一般把关键任务（如电机控制）用静态创建，非关键任务（如日志输出）用动态创建。

嗯，任务创建这块内容就这些。说白了就是三板斧：分配内存、初始化结构体、挂入队列。但每一板斧都有细节，细节决定成败。你们在实际移植时，建议先把TCB和栈分配这两个基础模块调稳了，再去做任务创建API。地基不牢，后面调度器写得再漂亮也是白搭。
