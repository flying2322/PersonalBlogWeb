25 系统集成测试：单元测试框架（Unity/CMock）、硬件在环（HIL）测试、压力测试

系统集成测试，说白了就是把所有零件拼起来，看看能不能跑得转。我见过太多项目，每个模块单独测都没问题，一合起来就崩。嗯，这里要讲的就是怎么避免这种尴尬。

25.1 单元测试框架：Unity + CMock

先说说单元测试。很多人觉得嵌入式搞单元测试太麻烦，我一开始也这么想。直到有一次，一个定时器中断的bug让我调了三天，最后发现是某个状态机跳转条件写反了。从那以后，我再也不敢跳过单元测试。

Unity：轻量级测试框架

Unity是专门为嵌入式设计的测试框架，说白了就是一套宏定义，帮你做断言和测试管理。我习惯把它直接放到工程目录下，不依赖任何操作系统。

// 一个简单的Unity测试用例
#include "unity.h"
#include "motor_controller.h"

void setUp(void) {
    // 每个测试用例执行前调用
    motor_init();
}

void tearDown(void) {
    // 每个测试用例执行后调用
    motor_deinit();
}

void test_motor_set_speed_should_set_correct_pwm(void) {
    motor_set_speed(50);
    TEST_ASSERT_EQUAL_UINT16(500, pwm_get_duty());
}

void test_motor_set_speed_should_clamp_to_max(void) {
    motor_set_speed(150);  // 超出范围
    TEST_ASSERT_EQUAL_UINT16(1000, pwm_get_duty());
}

int main(void) {
    UNITY_BEGIN();
    RUN_TEST(test_motor_set_speed_should_set_correct_pwm);
    RUN_TEST(test_motor_set_speed_should_clamp_to_max);
    return UNITY_END();
}

你看，代码量不大，但能覆盖边界情况。我遇到过最坑的一次，就是速度值没做限幅，电机直接满速转，差点把测试台掀了。

CMock：自动生成桩函数

CMock是配合Unity用的，专门处理模块间的依赖。比如你的电机模块调用了ADC，测试时总不能真去采样吧？CMock会自动生成ADC的桩函数。

// 使用CMock生成的桩函数
void test_motor_should_stop_when_adc_reading_high(void) {
    // 模拟ADC返回高值
    adc_read_ExpectAndReturn(ADC_CHANNEL_CURRENT, 3000);
    
    motor_update();
    
    TEST_ASSERT_EQUAL_UINT16(0, pwm_get_duty());
}

我个人习惯是，每个模块至少写5个测试用例：正常值、边界值、异常值、空指针、超时。别嫌多，这些测试在后期能救你命。

小技巧： 测试用例命名用"模块_功能_预期行为"的格式，比如 motor_set_speed_should_clamp_to_max。这样看测试报告时一目了然。

25.2 硬件在环（HIL）测试

单元测试跑完了，但代码最终是要跑在硬件上的。HIL测试就是把真实控制器连到仿真环境里，模拟各种工况。说白了，就是让控制器以为自己在真车上跑。

HIL测试架构

我参与过一个AGV项目，HIL测试平台长这样：

+------------------+       CAN/IO       +------------------+
|   AGV控制器       | <----------------> |   HIL仿真器       |
|   (真实硬件)       |                   |   (实时仿真模型)   |
+------------------+                   +------------------+
        |                                       |
        | 调试串口                               | 上位机
        v                                       v
   +----------+                          +----------+
   | 调试终端  |                          | 监控界面  |
   +----------+                          +----------+

HIL仿真器里跑的是车辆动力学模型、传感器模型、执行器模型。控制器发一个PWM信号，仿真器就计算电机转速、车轮位置，再通过CAN总线把编码器值返回给控制器。

关键点： HIL测试必须保证实时性。仿真步长通常设为1ms，如果仿真器计算超时，整个测试就废了。我遇到过仿真器CPU过载导致时序错乱，查了两天才发现是模型里有个死循环。

HIL测试用例设计

我一般把HIL测试分成三类：

  • 功能测试： 验证基本控制逻辑，比如直线行驶、原地转弯
  • 故障注入： 模拟传感器断线、电机堵转、通信超时
  • 极限工况： 满载爬坡、急刹车、连续颠簸路面

举个例子，故障注入测试：

// HIL测试脚本片段（Python）
def test_encoder_failure():
    # 正常行驶
    hil.set_motor_speed(1000)
    time.sleep(2)
    
    # 注入编码器故障
    hil.inject_fault("encoder_left", FAULT_DISCONNECT)
    time.sleep(1)
    
    # 检查控制器是否进入安全模式
    assert hil.get_controller_state() == STATE_SAFE_STOP
    assert hil.get_alarm_code() == ALARM_ENCODER_LOST

我曾经在HIL测试中发现一个bug：编码器断线后，控制器没有立即停车，而是继续用最后一次有效值推算位置，结果车子跑偏了半米才触发保护。这个bug要是到真车上才暴露，后果不堪设想。

注意： HIL测试不能完全替代实车测试。仿真模型再精确，也模拟不了真实的轮胎磨损、路面摩擦系数变化。HIL的作用是提前暴露逻辑错误，而不是验证物理特性。

25.3 压力测试

压力测试，说白了就是往死里整你的系统。看看它在极限负载下会不会崩，崩了之后能不能自己恢复。

压力测试类型

测试类型 测试方法 通过标准
CPU负载测试 同时运行所有任务，最高优先级任务占满CPU 低优先级任务不饿死，系统不崩溃
内存压力测试 反复申请释放内存，模拟内存碎片 无内存泄漏，无野指针
通信压力测试 CAN总线满负载发送，模拟总线冲突 关键消息不丢失，延迟在容忍范围内
长时间运行测试 连续运行72小时以上 无死机，无看门狗复位

我印象最深的一次，是给一个AGV控制器做72小时压力测试。跑到第48小时，系统突然死机了。查日志发现是某个定时器任务里有个除法操作，除数为0导致硬件异常。这个bug在正常测试中根本不会触发，因为除数为0的条件极其罕见。但压力测试下，各种极端情况都出现了。

压力测试脚本示例

// 内存压力测试
void memory_stress_test(void) {
    uint32_t *ptr;
    uint32_t total_alloc = 0;
    
    while (1) {
        // 随机大小申请内存
        uint32_t size = rand() % 1024 + 1;
        ptr = (uint32_t *)malloc(size * sizeof(uint32_t));
        
        if (ptr != NULL) {
            // 写入并校验
            for (uint32_t i = 0; i < size; i++) {
                ptr[i] = 0xDEADBEEF;
            }
            total_alloc += size;
            
            // 随机释放
            if (rand() % 2) {
                free(ptr);
                total_alloc -= size;
            }
        }
        
        // 打印内存使用情况
        if (total_alloc > 100000) {
            printf("Memory allocated: %lu bytes\n", total_alloc);
        }
        
        // 延时防止看门狗复位
        vTaskDelay(pdMS_TO_TICKS(10));
    }
}

这个脚本看起来简单，但跑起来能暴露很多问题。我遇到过malloc返回NULL后没有处理，导致后续代码直接写空指针。也遇到过内存碎片化严重，明明总空闲内存还有，但就是申请不到连续大块。

建议： 压力测试最好在开发早期就开始跑。别等到所有功能都做完了再测，那时候改代码的成本太高了。我习惯每个迭代都跑一次72小时压力测试，虽然费时间，但能省下后期排查问题的精力。

25.4 测试报告与问题追踪

测试做完了，得有个报告。我一般用表格记录每个测试用例的结果：

测试ID 测试名称 结果 备注
UT-001 电机速度设置-正常值 通过 -
UT-002 电机速度设置-超限值 通过 -
HIL-001 编码器断线故障注入 失败 控制器未及时进入安全模式，已修复
STR-001 72小时长时间运行 通过 第48小时出现一次看门狗复位，已修复

每个失败的测试用例，我都会记录根因分析和修复方案。这样下次回归测试时，能快速定位问题是否复发。

总结： 单元测试保证代码质量，HIL测试验证系统集成，压力测试暴露极限问题。三者缺一不可。我见过太多项目只做单元测试，结果集成时崩得一塌糊涂。也见过只做HIL测试，结果代码里一堆低级bug。记住，测试不是走过场，是帮你省时间的。
