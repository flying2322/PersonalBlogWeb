10 内存管理：静态内存池分配、动态内存分配（malloc替代方案）、内存碎片处理

内存管理，说白了就是给任务分配“干活的地方”。在AGV控制器这种实时系统里，内存管理要是搞砸了，系统跑着跑着就挂了。我见过不少项目，前期功能调得挺好，一跑长时间稳定性测试，就出问题。十有八九，都是内存管理埋的雷。

今天咱们就把这块硬骨头啃下来。我会把静态内存池、动态分配替代方案、还有内存碎片处理，一个一个说清楚。

10.1 静态内存池分配：最靠谱的老办法

静态内存池，我个人最喜欢用的方式。为什么？因为它简单、粗暴、有效。

做法是这样的：系统启动时，一次性从RAM里划出一大块区域。然后按照固定大小切成很多个小块。每个小块大小一样，比如64字节、128字节、256字节。任务需要内存时，直接拿一个块。用完还回来。

你想想看，这样做有什么好处？

  • 执行时间确定：拿一个块的时间是固定的，不会像malloc那样越找越慢
  • 没有碎片：所有块大小一样，不存在外部碎片问题
  • 实现简单：一个链表就能搞定

核心要点：静态内存池适用于系统中频繁申请/释放、且大小固定的数据结构。比如AGV的路径点缓存、传感器数据帧、通信协议包。

我在项目中遇到过一个问题：有个同事把所有的通信包都用了动态分配，结果系统跑了几个小时，内存碎片化严重，最后连一个64字节的包都申请不到了。后来改成内存池，问题立刻解决。

下面是一个简单的内存池实现示例：

/* 内存池控制块 */
typedef struct {
    void *pool_start;       /* 池起始地址 */
    uint32_t block_size;    /* 每个块大小 */
    uint32_t block_count;   /* 块总数 */
    void *free_list;        /* 空闲块链表头 */
} mem_pool_t;

/* 初始化内存池 */
void mem_pool_init(mem_pool_t *pool, void *mem, 
                   uint32_t blk_size, uint32_t blk_cnt) {
    pool->pool_start = mem;
    pool->block_size = blk_size;
    pool->block_count = blk_cnt;
    pool->free_list = mem;
    
    /* 将空闲块串成链表 */
    uint8_t *p = (uint8_t *)mem;
    for (int i = 0; i < blk_cnt - 1; i++) {
        *(void **)p = (void *)(p + blk_size);
        p += blk_size;
    }
    *(void **)p = NULL;  /* 最后一个块指向NULL */
}

/* 从内存池申请一个块 */
void *mem_pool_alloc(mem_pool_t *pool) {
    if (pool->free_list == NULL) {
        return NULL;  /* 池已耗尽 */
    }
    void *block = pool->free_list;
    pool->free_list = *(void **)block;
    return block;
}

/* 释放块回内存池 */
void mem_pool_free(mem_pool_t *pool, void *block) {
    *(void **)block = pool->free_list;
    pool->free_list = block;
}

实用技巧：我习惯在内存池头部加一个魔数（Magic Number），用来检测野指针释放或者重复释放。调试阶段特别有用。

10.2 动态内存分配的替代方案

有些场景下，你确实需要不同大小的内存块。比如AGV接收到的路径数据长度不固定。这时候不能用静态池，但直接用malloc又怕碎片。

怎么办？我推荐几个替代方案：

10.2.1 伙伴算法（Buddy System）

伙伴算法是折中方案。它把内存按2的幂次分成不同大小的块。比如系统有64KB内存，可以分成1KB、2KB、4KB、8KB...最大64KB。

申请内存时，向上取整到最近的2的幂次。比如申请3KB，就分配4KB的块。释放时，如果相邻的“伙伴”也是空闲的，就合并成更大的块。

这样做的好处是：碎片比标准malloc少很多，分配速度也快。坏处是：内部碎片（浪费的空间）最多有50%。

注意：伙伴算法不适合申请大小非常随机的场景。如果频繁申请3字节、5字节这种小内存，内部碎片会非常严重。我建议最小块至少32字节起步。

10.2.2 栈分配器（Stack Allocator）

这个思路更简单。如果你能确定内存的申请和释放是“后进先出”的顺序，那就用栈分配器。

比如AGV处理一帧传感器数据：先申请一个缓冲区放原始数据，然后处理过程中申请几个临时缓冲区，处理完依次释放。释放顺序和申请顺序正好相反。

栈分配器只需要一个指针，指向当前栈顶。申请时指针上移，释放时指针下移。完全没有碎片，速度极快。

/* 栈分配器 */
typedef struct {
    uint8_t *base;      /* 栈底 */
    uint8_t *top;       /* 当前栈顶 */
    uint32_t size;      /* 总大小 */
} stack_alloc_t;

void *stack_alloc(stack_alloc_t *sa, uint32_t size) {
    if (sa->top + size > sa->base + sa->size) {
        return NULL;  /* 溢出 */
    }
    void *ptr = sa->top;
    sa->top += size;
    return ptr;
}

/* 注意：只能释放栈顶的内存 */
void stack_free(stack_alloc_t *sa, void *ptr) {
    sa->top = (uint8_t *)ptr;
}

我的建议：在AGV控制器中，我通常这样搭配使用：

  • 固定大小的数据结构 → 静态内存池
  • 临时处理、后进先出 → 栈分配器
  • 大小变化较大、但频率低 → 伙伴算法

这样组合下来，基本可以告别malloc。

10.3 内存碎片处理：预防胜于治疗

内存碎片，说白了就是内存被切得七零八落。明明总空闲空间够用，但就是申请不到一块连续的大内存。

为什么会这样？因为每次申请和释放的大小不一样，释放后留下的空洞大小不一。时间长了，内存就像一块被狗啃过的蛋糕。

我曾经在一个项目中吃过这个亏。AGV跑了三天三夜，突然报内存不足。查了半天，发现空闲内存还有30%，但最大的连续块只有128字节。而系统需要申请一个256字节的路径缓存...直接死机。

10.3.1 碎片预防策略

最好的办法，是从设计上避免碎片：

  • 统一大小：尽量把不同长度的数据统一成几个固定长度。比如通信包统一用64字节、128字节、256字节三种
  • 避免频繁申请释放：能复用的内存就复用，不要用完就释放、下次再申请
  • 使用内存池：前面说的静态池，天然无碎片

10.3.2 碎片整理（Compaction）

如果碎片已经产生了，怎么办？那就得做碎片整理。但注意，RTOS里做碎片整理要非常小心。

碎片整理的核心思路：把已分配的内存块移动到一端，把空闲空间集中到另一端。就像整理书架，把书都推到左边，右边就空出一大块。

但问题来了：移动内存块之后，所有指向这些块的指针都得更新。在实时系统里，这非常麻烦。因为你不知道哪个任务正在用这块内存。

重要提醒：在RTOS中做碎片整理，必须暂停所有任务，或者使用内存句柄（Handle）而不是直接指针。我个人不太推荐在AGV控制器里做全量碎片整理，风险太高。

10.3.3 我的实战经验

说了这么多理论，讲讲我实际怎么做的吧。

在AGV控制器项目中，我用了三层内存管理：

层级 用途 管理方式 碎片风险
第一层 任务栈、系统控制块 编译时静态分配 无
第二层 通信包、传感器数据 静态内存池（64/256/1024字节） 无
第三层 路径规划、地图数据 伙伴算法（最小32字节） 低

这样设计之后，系统跑了几个月，内存状况一直很稳定。偶尔用伙伴算法分配的大块内存，释放后也能正常合并回去。

避坑指南：我曾经在第三层用过标准malloc，结果系统运行一周后必出问题。后来换成伙伴算法，问题消失。记住：在RTOS里，确定性比灵活性更重要。

嗯，内存管理这块就聊到这儿。核心就一句话：能用静态就不用动态，能用池就不用堆，能预防碎片就别等整理。你按照这个思路去设计AGV控制器的内存系统，基本不会出大问题。
