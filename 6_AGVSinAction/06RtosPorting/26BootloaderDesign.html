26 Bootloader设计：固件升级流程、双备份区切换、CRC校验与回滚机制

说到Bootloader，很多刚入行的朋友觉得它就是个「跳板」——上电后跳转到主程序就完事了。但做AGV控制器这么多年，我越来越觉得Bootloader才是整个系统的「守门员」。固件升级要是翻车了，AGV在仓库里趴窝，那可不是闹着玩的。

今天咱们就聊聊Bootloader里最核心的三个东西：固件升级流程、双备份区切换、CRC校验与回滚机制。说白了，就是怎么安全地把新固件刷进去，万一刷坏了还能自己救回来。

一、固件升级流程：从接收到生效

先画个流程图，让大家对整体有个感觉。

这个流程看起来简单，但每个环节都有坑。我一个个说。

1.1 接收阶段：别急着写Flash

固件包一般通过CAN、以太网或者串口传过来。我个人习惯是先收到RAM缓冲区里，等整个包收完了再开始写Flash。

为什么？你想想看，如果边收边写，写到一半通信断了，Flash里就留下一个半残的固件。虽然我们有备份区，但能避免的麻烦何必自找呢？

我的经验：RAM缓冲区至少分配固件包大小的1.2倍。因为除了固件本身，还要存包头、CRC值、版本号这些元数据。我曾经因为缓冲区算得太紧，结果一个带扩展头的包直接溢出，查了两天才找到原因。

1.2 写入阶段：按扇区擦除

写Flash之前要先擦除。注意，擦除是按扇区（Sector）来的，不是按字节。不同芯片扇区大小不一样，STM32F4一般是16KB或128KB。我建议写个抽象层，把擦除和写入封装好，这样换芯片时不用改上层逻辑。

/* 伪代码：固件写入备份区 */
int write_firmware_to_backup(uint32_t addr, uint8_t *data, uint32_t len) {
    uint32_t sector_size = get_sector_size(addr);
    uint32_t offset = 0;
    
    while (offset < len) {
        // 按扇区擦除
        if (addr % sector_size == 0) {
            flash_erase_sector(addr);
        }
        // 写入当前扇区
        flash_write(addr, data + offset, min(sector_size, len - offset));
        addr += sector_size;
        offset += sector_size;
    }
    return 0;
}
注意：写Flash期间绝对不能断电！虽然我们有回滚机制，但频繁的异常断电会磨损Flash。我一般在写入前会检查电源电压，低于阈值就拒绝升级。

二、双备份区切换：A/B分区策略

双备份区，说白了就是准备两个「坑」：分区A和分区B。一个跑着当前固件，另一个等着被覆盖。

分区 起始地址 大小 用途
Bootloader 0x08000000 64KB 启动管理、升级逻辑
分区A（当前） 0x08010000 512KB 运行中的固件
分区B（备份） 0x08090000 512KB 待升级或回滚用
配置区 0x08110000 16KB 存储启动标志、版本号

2.1 切换逻辑：谁才是「当前」？

每次启动时，Bootloader先读配置区里的「启动标志」。这个标志告诉它：从A启动还是从B启动。

升级完成后，Bootloader不会立刻切换。它会先标记「新固件已就绪」，然后重启。重启后Bootloader检查新固件的CRC，通过了才正式切换。这步叫「延迟切换」，能防止「刚写完就崩」的情况。

核心原则：永远保证至少有一个分区是可启动的。升级过程中如果出问题，就回滚到另一个分区。

2.2 我踩过的坑：标志位被意外擦除

有一次，我在升级时把配置区和分区B放在同一个扇区里。结果擦除分区B时，顺手把配置区也擦了。重启后Bootloader找不到启动标志，直接死在那了。

从那以后，我强制要求配置区必须独占一个扇区。哪怕浪费点空间，也比出问题强。

三、CRC校验与回滚机制

CRC校验是固件升级的「安检门」。没有它，你根本不知道写进去的东西对不对。

3.1 CRC怎么算？

我一般用CRC32，多项式用0x04C11DB7（标准CRC32）。计算范围是整个固件区，包括代码和数据。算出来的CRC值存在固件包的末尾。

/* CRC32计算示例 */
uint32_t calculate_crc32(uint8_t *data, uint32_t len) {
    uint32_t crc = 0xFFFFFFFF;
    for (uint32_t i = 0; i < len; i++) {
        crc ^= data[i];
        for (int j = 0; j < 8; j++) {
            if (crc & 1) {
                crc = (crc >> 1) ^ 0xEDB88320;
            } else {
                crc >>= 1;
            }
        }
    }
    return crc ^ 0xFFFFFFFF;
}
小技巧：很多MCU有硬件CRC模块，速度比软件快10倍以上。我建议能用硬件就用硬件，尤其是固件比较大的时候。STM32的CRC外设直接算32位，省心。

3.2 校验时机：三次校验

我个人习惯做三次CRC校验：

  1. 接收时校验：固件包传完后，先算一遍CRC，确认传输没出错。
  2. 写入后校验：写进Flash后，再读出来算一遍，确认写入正确。
  3. 启动前校验：每次启动时，Bootloader对当前分区做CRC校验，防止Flash老化导致数据损坏。

你可能会问：「三次是不是太多了？」嗯，对于AGV这种动辄几十万的设备，多花几秒钟校验，换来的是几个月不出故障，值不值？我觉得值。

3.3 回滚机制：最后的救命稻草

回滚的逻辑其实很简单：如果新固件启动失败，就切回旧固件。但怎么判断「启动失败」？

我常用的方法是「看门狗+心跳」：

  • Bootloader启动新固件后，启动一个短时看门狗（比如5秒）。
  • 新固件正常运行后，会定期喂狗，并清除「启动失败计数」。
  • 如果新固件卡死了，看门狗超时复位。Bootloader检测到「启动失败计数」增加，超过阈值（比如3次）就自动回滚。
/* 回滚逻辑伪代码 */
void bootloader_main() {
    uint8_t fail_count = read_config(FAIL_COUNT_ADDR);
    
    if (fail_count >= MAX_FAIL_COUNT) {
        // 启动失败次数过多，回滚
        switch_to_backup_partition();
        clear_config(FAIL_COUNT_ADDR);
    } else {
        // 正常启动当前分区
        if (crc_check(current_partition) == OK) {
            jump_to_app(current_partition);
        } else {
            // CRC校验失败，直接回滚
            switch_to_backup_partition();
        }
    }
}
曾经我犯过的错：有一次我把回滚阈值设成了1次。结果新固件第一次启动时因为外部传感器没初始化好，看门狗超时了，直接回滚。其实固件本身没问题。后来我改成3次，并且每次失败后增加延时，给外部设备足够的初始化时间。

四、总结一下

Bootloader设计说白了就是三件事：安全地写进去、可靠地切过来、万一不行还能退回去。双备份区是骨架，CRC校验是眼睛，回滚机制是保险绳。三者缺一不可。

最后送大家一句话：Bootloader的代码量可能只占整个项目的5%，但它决定了另外95%能不能跑起来。多花点心思在这5%上，绝对值得。
