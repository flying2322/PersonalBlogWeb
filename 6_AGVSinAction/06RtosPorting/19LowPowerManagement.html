19 低功耗管理：休眠模式与唤醒源、动态频率调整、外设电源管理

做AGV控制器，功耗是个绕不开的话题。

你可能觉得，AGV嘛，拖着个大电池，还怕费电？其实不然。我见过不少项目，电池容量算得死死的，结果控制器功耗一测，比预期高了30%。最后要么加电池，要么砍功能。说白了，低功耗管理做不好，产品就得打折扣。

这一章，咱们就聊聊AGV控制器上的低功耗三板斧：休眠与唤醒、动态调频、外设电源管理。

19.1 休眠模式与唤醒源

先说说休眠。RTOS里的休眠，不是简单的“CPU不干活”。它分好几个层级。

19.1.1 常见的休眠模式

我习惯把休眠模式分成三种：

  • 浅睡眠（Idle/Sleep）：CPU停掉，但RAM保持，外设时钟还在跑。唤醒最快，几微秒就能恢复。
  • 深睡眠（Deep Sleep/Stop）：CPU停，RAM保持，大部分外设时钟关掉。唤醒需要几十到几百微秒。
  • 待机（Standby/Shutdown）：CPU停，RAM掉电，只有少数唤醒逻辑在工作。唤醒最慢，但功耗最低，能到微安级别。

你想想看，AGV在等待任务时，用哪种模式？

我个人建议：等待时间超过1秒，用深睡眠；超过10秒，可以考虑待机。但要注意，待机模式下RAM内容会丢失，你得把关键数据存到非易失存储器里。

核心原则：休眠越深，唤醒越慢。要在功耗和响应速度之间找平衡。

19.1.2 唤醒源设计

唤醒源，说白了就是“谁能把控制器叫醒”。

常见的唤醒源有：

  • GPIO中断：比如急停按钮、限位开关。这是最常用的。
  • 定时器：比如每隔100ms唤醒一次，检查任务队列。
  • 通信接口：比如CAN总线有数据来了，唤醒控制器。
  • RTC闹钟：比如每天早上8点自动唤醒，执行巡检任务。

我在项目中遇到过一个问题：AGV在深睡眠时，CAN总线来了一个报文，但控制器没醒。为什么？因为CAN的唤醒引脚没配置对。后来我查了芯片手册，发现CAN模块需要单独使能“唤醒中断”功能。嗯，这里要注意，不是所有外设都能在深睡眠下唤醒CPU，得看芯片的具体设计。

小技巧：设计唤醒源时，尽量用“边沿触发”而不是“电平触发”。电平触发容易在休眠时产生误唤醒，我吃过这个亏。

19.2 动态频率调整

动态频率调整，英文叫DVFS（Dynamic Voltage and Frequency Scaling）。说白了，就是根据负载调整CPU的主频和电压。

19.2.1 为什么需要动态调频？

AGV控制器的负载不是恒定的。比如：

  • 直线行驶时，只需要简单的PID控制，CPU负载低。
  • 转弯或避障时，需要处理激光雷达数据、路径规划，CPU负载高。

如果全程跑最高频率，功耗自然就上去了。动态调频的目的就是：低负载时降频省电，高负载时升频保证性能。

19.2.2 实现方式

在RTOS里实现动态调频，通常有两种思路：

  1. 基于负载的调频：每隔一段时间（比如100ms），统计CPU空闲率。如果空闲率高于某个阈值，就降频；低于阈值，就升频。
  2. 基于任务的调频：在任务切换时，根据下一个任务的优先级或类型，动态调整频率。比如，高优先级的控制任务来了，立刻升频。

我个人更倾向于第一种。简单，稳定。第二种虽然响应快，但实现复杂，容易引入抖动。

下面是一个简单的调频逻辑示例：

// 伪代码：基于CPU负载的动态调频
void dvfs_task(void *arg) {
    while (1) {
        uint32_t idle_ticks = osKernelGetTickCount() - last_idle_ticks;
        uint32_t total_ticks = osKernelGetTickCount() - last_total_ticks;
        float cpu_load = 1.0f - (float)idle_ticks / total_ticks;

        if (cpu_load < 0.3f) {
            // 负载低于30%，降频到100MHz
            set_cpu_freq(100000000);
        } else if (cpu_load > 0.7f) {
            // 负载高于70%，升频到400MHz
            set_cpu_freq(400000000);
        }
        // 30%~70%之间，保持当前频率

        last_idle_ticks = osKernelGetTickCount();
        last_total_ticks = osKernelGetTickCount();
        osDelay(100); // 每100ms检查一次
    }
}

注意：频率切换时，要确保外设时钟不会跑飞。比如，串口波特率是基于外设时钟的，频率一变，波特率就变了。我建议在切换频率前，先暂停所有通信外设，切换完再恢复。

19.3 外设电源管理

外设电源管理，是低功耗里最容易出效果，也最容易出问题的地方。

19.3.1 外设的分类管理

AGV控制器上的外设很多：电机驱动器、激光雷达、IMU、显示屏、Wi-Fi模块……每个外设的功耗都不一样。

我习惯把它们分成三类：

类别 典型外设 管理策略
常开型 电机驱动器、急停电路 始终供电，但可以进入低功耗模式
按需型 激光雷达、Wi-Fi模块 不用时完全断电
休眠型 IMU、显示屏 进入休眠模式，保留唤醒能力

举个例子。AGV在充电时，激光雷达和Wi-Fi模块其实可以关掉。我见过一个项目，充电时激光雷达还在转，白白浪费了5W的功率。后来加了一个MOS管开关，充电时直接切断雷达电源，功耗降了20%。

19.3.2 电源域设计

要实现外设的精细管理，硬件上需要做电源域划分。简单说，就是把外设分成几组，每组用一个独立的电源开关（比如MOS管或PMIC通道）。

软件上，RTOS需要提供接口，让任务可以申请和释放外设电源：

// 伪代码：外设电源管理接口
void peripheral_power_on(peripheral_id_t id);
void peripheral_power_off(peripheral_id_t id);
bool peripheral_is_powered(peripheral_id_t id);

我曾经踩过一个坑：某个外设断电后，它的GPIO引脚还连着CPU。结果CPU的IO口漏电，导致整个系统功耗异常。后来我学乖了，外设断电前，先把对应的GPIO设置为高阻输入，防止漏电。

避坑指南：外设电源管理，一定要考虑“上电时序”。有些外设，比如激光雷达，上电后需要几百毫秒才能稳定工作。如果你刚上电就去读数据，大概率会读到乱码。我习惯在电源管理接口里加一个“等待稳定”的延时。

19.5 实战要点总结

最后，我把这一章的核心要点再捋一遍：

  • 休眠模式：根据等待时间选择合适的休眠深度。唤醒源要配置正确，尤其是深睡眠下的外设唤醒能力。
  • 动态调频：基于CPU负载调整频率，简单有效。切换频率时，注意外设时钟的稳定性。
  • 外设电源管理：分类管理，按需供电。硬件上做电源域划分，软件上提供统一接口。别忘了GPIO防漏电和上电时序。

嗯，低功耗管理这块，说起来不难，但细节很多。我每次做新项目，都会先画一张电源树，把每个外设的功耗和供电关系理清楚。这样后面写代码时，心里才有底。

一句话总结：低功耗不是把CPU睡死，而是让该睡的都睡，该醒的能醒，该跑的跑在合适的频率上。
