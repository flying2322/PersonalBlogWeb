9 同步与通信机制：信号量（二值/计数）、互斥锁（优先级继承）、消息队列、事件标志组

各位同学，咱们今天聊点硬核的——RTOS里的同步与通信。说实话，这部分是嵌入式开发的灵魂。你想想看，一个AGV控制器里，电机控制任务、传感器采集任务、路径规划任务，它们之间怎么协调？怎么传数据？怎么避免打架？

嗯，这就是我们今天要解决的问题。

我在做第一个AGV项目时，就吃过亏。当时任务间通信没设计好，结果小车跑着跑着突然卡死，差点撞墙。从那以后，我对同步与通信机制的理解就深刻多了。今天我把这些经验分享给你们。

9.1 信号量：二值与计数

信号量，说白了就是一个“资源计数器”。它用来管理有限资源的访问。RTOS里最常见的就是两种：二值信号量和计数信号量。

9.1.1 二值信号量

二值信号量只有两个状态：0和1。0表示资源被占用，1表示资源可用。它常用于“事件通知”场景。

举个例子：AGV的急停按钮被按下时，中断服务程序释放一个二值信号量，主控任务等待这个信号量。一旦信号量变为1，主控任务立即执行急停逻辑。

// 二值信号量示例
osSemaphoreId_t emergencySem;
osSemaphoreAttr_t semAttr = { .name = "EmergencySem" };

// 创建二值信号量，初始值为0
emergencySem = osSemaphoreNew(1, 0, &semAttr);

// 中断服务程序中释放信号量
void EXTI_IRQHandler(void) {
    osSemaphoreRelease(emergencySem);
    // 清除中断标志...
}

// 主控任务等待急停信号
void ControlTask(void *arg) {
    while(1) {
        // 等待信号量，超时设为永久等待
        if(osSemaphoreAcquire(emergencySem, osWaitForever) == osOK) {
            // 执行急停逻辑
            EmergencyStop();
        }
    }
}

我个人习惯把二值信号量用在“一次性的同步”场景。比如任务A做完初始化，通知任务B开始工作。这种场景下，二值信号量非常轻量，效率很高。

小技巧： 二值信号量释放后，如果多个任务都在等待，只会唤醒优先级最高的那个任务。这是RTOS内核的调度策略。

9.1.2 计数信号量

计数信号量可以管理多个同类资源。它的值从0到最大值N。比如AGV的串口缓冲区有10个槽位，就可以用计数信号量来管理。

我曾经在一个项目中，用计数信号量管理DMA缓冲区。数据到来时释放信号量，处理任务获取信号量后处理数据。这样既不会丢数据，也不会过度占用CPU。

// 计数信号量示例，管理5个资源
osSemaphoreId_t countSem;
countSem = osSemaphoreNew(5, 5, NULL);  // 最大值5，初始值5

// 任务A：获取资源
void TaskA(void *arg) {
    if(osSemaphoreAcquire(countSem, 100) == osOK) {
        // 成功获取一个资源
        UseResource();
    } else {
        // 超时处理
        HandleTimeout();
    }
}

// 任务B：释放资源
void TaskB(void *arg) {
    // 使用完资源后释放
    osSemaphoreRelease(countSem);
}
核心区别： 二值信号量用于“事件通知”，计数信号量用于“资源管理”。别搞混了，否则调试起来很痛苦。

9.2 互斥锁与优先级继承

互斥锁，英文叫Mutex，是专门用来保护共享资源的。它和二值信号量很像，但有个关键区别：互斥锁支持优先级继承。

为什么要优先级继承？我给你们讲个真实案例。

有一次，AGV的路径规划任务（高优先级）和传感器采集任务（低优先级）共享一个数据缓冲区。低优先级任务拿到了互斥锁，但被中优先级任务抢占了CPU。高优先级任务等着锁，却一直拿不到。这就是经典的“优先级反转”。

互斥锁的优先级继承机制，就是解决这个问题的。当高优先级任务等待锁时，持有锁的低优先级任务会临时提升到高优先级，快速执行完并释放锁。

// 互斥锁示例
osMutexId_t dataMutex;
osMutexAttr_t mutexAttr = {
    .name = "DataMutex",
    .attr_bits = osMutexRecursive  // 支持递归锁
};

dataMutex = osMutexNew(&mutexAttr);

// 高优先级任务
void HighPriorityTask(void *arg) {
    osMutexAcquire(dataMutex, osWaitForever);
    // 访问共享数据
    AccessSharedData();
    osMutexRelease(dataMutex);
}

// 低优先级任务
void LowPriorityTask(void *arg) {
    osMutexAcquire(dataMutex, osWaitForever);
    // 处理数据
    ProcessData();
    osMutexRelease(dataMutex);
}
注意： 互斥锁只能在任务中使用，不能在中断服务程序中使用。因为中断里不能阻塞等待。如果你需要在中断和任务间同步，请用信号量。

嗯，这里要特别强调：互斥锁的优先级继承不是万能的。如果系统里有多个高优先级任务同时等待同一个锁，还是会出现问题。设计时尽量让临界区代码短小精悍。

9.3 消息队列

消息队列是RTOS里最常用的通信方式。它像一个管道，任务A往里扔数据，任务B从里取数据。数据是按顺序传递的，先进先出。

我在AGV项目中，用消息队列传递传感器数据。激光雷达每10ms发一帧数据，通过消息队列传给定位算法任务。这样两个任务解耦了，各自专注于自己的事。

// 消息队列示例，每条消息32字节，队列深度10
osMessageQueueId_t sensorQueue;
sensorQueue = osMessageQueueNew(10, 32, NULL);

// 发送任务：激光雷达数据采集
void LidarTask(void *arg) {
    LidarFrame_t frame;
    while(1) {
        ReadLidarFrame(&frame);
        // 发送消息，超时10ms
        if(osMessageQueuePut(sensorQueue, &frame, 0, 10) != osOK) {
            // 队列满了，丢弃旧数据
            osMessageQueueReset(sensorQueue);
            osMessageQueuePut(sensorQueue, &frame, 0, 0);
        }
        osDelay(10);
    }
}

// 接收任务：定位算法
void LocalizationTask(void *arg) {
    LidarFrame_t frame;
    while(1) {
        if(osMessageQueueGet(sensorQueue, &frame, NULL, osWaitForever) == osOK) {
            ProcessLidarData(&frame);
        }
    }
}
经验之谈： 消息队列的深度要合理设置。太浅容易丢数据，太深浪费内存。我一般根据数据产生速率和处理速率来估算，再留20%的余量。

消息队列还有一个好处：支持广播。有些RTOS支持“发布-订阅”模式，一个消息可以发给多个接收者。这在AGV的多传感器融合场景中特别有用。

9.4 事件标志组

事件标志组，说白了就是一组二进制标志位。每个位代表一个事件。任务可以等待多个事件同时发生，或者等待其中任意一个发生。

举个例子：AGV要开始自主导航，需要同时满足三个条件——定位完成、地图加载完成、电机初始化完成。用事件标志组，一个任务就能优雅地等待所有条件。

// 事件标志组示例
#define EVENT_LOCALIZATION  (1 << 0)
#define EVENT_MAP_LOADED    (1 << 1)
#define EVENT_MOTOR_READY   (1 << 2)

osEventFlagsId_t navEvents;
navEvents = osEventFlagsNew(NULL);

// 各个初始化任务设置事件
void LocalizationInitTask(void *arg) {
    InitLocalization();
    osEventFlagsSet(navEvents, EVENT_LOCALIZATION);
}

void MapLoadTask(void *arg) {
    LoadMap();
    osEventFlagsSet(navEvents, EVENT_MAP_LOADED);
}

void MotorInitTask(void *arg) {
    InitMotor();
    osEventFlagsSet(navEvents, EVENT_MOTOR_READY);
}

// 导航任务等待所有事件
void NavigationTask(void *arg) {
    uint32_t flags;
    // 等待三个事件全部发生
    flags = osEventFlagsWait(navEvents, 
                             EVENT_LOCALIZATION | EVENT_MAP_LOADED | EVENT_MOTOR_READY,
                             osFlagsWaitAll, 
                             osWaitForever);
    if((flags & (EVENT_LOCALIZATION | EVENT_MAP_LOADED | EVENT_MOTOR_READY)) == 
                 (EVENT_LOCALIZATION | EVENT_MAP_LOADED | EVENT_MOTOR_READY)) {
        // 所有条件满足，开始导航
        StartNavigation();
    }
}
事件标志组的优势： 一个任务可以同时等待多个条件，而且支持“与”和“或”两种模式。这在复杂的状态机设计中非常有用。

我曾经在一个项目中，用事件标志组管理AGV的充电流程。需要同时满足“电量低于20%”、“当前位置可充电”、“无紧急任务”三个条件，才触发自动回充。用事件标志组，代码清晰又高效。

9.6 避坑指南

最后，我总结几个实战中容易踩的坑，都是我曾经的血泪教训。

  • 不要在中断里使用互斥锁。 互斥锁的获取可能阻塞，中断里不能阻塞。用信号量代替。
  • 注意优先级反转。 即使有优先级继承，也不能完全避免。设计时尽量让临界区短小。
  • 消息队列的深度要合理。 太浅丢数据，太深浪费内存。我一般用“生产者速率 × 最大延迟时间”来估算。
  • 事件标志组不要超过32位。 大多数RTOS支持32位，超过的话要考虑扩展方案。
  • 信号量和互斥锁不要混用。 二值信号量不能替代互斥锁，因为不支持优先级继承。
曾经我犯过的错： 在一个AGV项目中，我用二值信号量保护共享缓冲区，结果高优先级任务被低优先级任务阻塞了整整200ms。后来换成互斥锁，问题立刻解决。记住：保护共享资源，请用互斥锁。
