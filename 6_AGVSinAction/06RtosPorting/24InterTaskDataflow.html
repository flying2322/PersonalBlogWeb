24 任务间数据流设计：全局数据结构体、发布-订阅模式、数据一致性保护

各位同学，今天我们来聊聊任务间数据流设计。说实话，这是RTOS移植里最容易出问题的地方之一。我在项目里见过太多因为数据流没设计好，导致整个系统跑飞的情况。

你想想看，AGV控制器里同时跑着好几个任务：传感器采集、路径规划、电机控制、通信上报。这些任务之间怎么交换数据？用全局变量？用消息队列？还是用共享内存？每种方式都有它的适用场景，也有它的坑。

24.1 全局数据结构体：最直接的方式

先说说全局数据结构体。这是最原始、最直接的方式。我早期做的一个AGV项目，就是用一个大结构体来存放所有共享数据。

/* 全局数据共享结构体 */
typedef struct {
    /* 传感器数据 */
    float    left_wheel_speed;      /* 左轮速度 */
    float    right_wheel_speed;     /* 右轮速度 */
    uint16_t battery_voltage;       /* 电池电压 */
    uint8_t  obstacle_distance;     /* 障碍物距离 */
    
    /* 控制指令 */
    float    target_speed;          /* 目标速度 */
    float    target_angle;          /* 目标转向角 */
    
    /* 系统状态 */
    uint32_t system_tick;           /* 系统滴答 */
    uint8_t  error_code;            /* 错误码 */
    uint8_t  run_mode;              /* 运行模式 */
    
    /* 互斥保护 */
    osMutexId_t mutex;              /* 互斥锁 */
} AGV_SharedData_t;

AGV_SharedData_t g_agv_data;        /* 全局实例 */

嗯，这里要注意。全局结构体虽然简单，但有个致命问题——数据一致性。我遇到过这样一个场景：传感器任务正在更新障碍物距离，写到一半，控制任务突然读取了这个半成品数据，结果AGV直接撞墙了。

警告：全局数据结构体必须配合互斥锁使用。不要以为单核MCU就不需要锁，任务切换随时可能发生。

24.2 发布-订阅模式：解耦的艺术

后来我学乖了。在第二个AGV项目里，我引入了发布-订阅模式。说白了，就是数据生产者只管发布，数据消费者只管订阅，两者互不关心对方是谁。

为什么会这样设计？因为AGV的功能越来越多，任务之间的依赖关系越来越复杂。如果用全局结构体，改一个字段就要改所有相关的任务，维护成本太高了。

/* 发布-订阅核心结构 */
typedef struct {
    uint32_t    topic_id;           /* 主题ID */
    void*       data_ptr;           /* 数据指针 */
    uint16_t    data_size;          /* 数据大小 */
    uint32_t    timestamp;          /* 时间戳 */
    uint8_t     checksum;           /* 校验和 */
} PubSub_Message_t;

/* 订阅者回调类型 */
typedef void (*Subscriber_Callback)(PubSub_Message_t* msg);

/* 发布函数 */
void PubSub_Publish(uint32_t topic_id, void* data, uint16_t size) {
    PubSub_Message_t msg;
    msg.topic_id  = topic_id;
    msg.data_ptr  = data;
    msg.data_size = size;
    msg.timestamp = osKernelGetTickCount();
    msg.checksum  = calculate_checksum(data, size);
    
    /* 遍历订阅者列表，分发消息 */
    for (int i = 0; i < MAX_SUBSCRIBERS; i++) {
        if (subscriber_list[i].topic_id == topic_id) {
            subscriber_list[i].callback(&msg);
        }
    }
}
我的经验：发布-订阅模式里，时间戳和校验和很重要。我曾经因为没加时间戳，导致控制任务用了过期的传感器数据，AGV在转弯时反应慢了半拍。加了时间戳后，消费者可以判断数据是否新鲜。

24.3 数据一致性保护：三种武器

数据一致性保护，说白了就是防止数据被撕成两半。我总结了三种武器，你们可以根据场景选用。

保护方式 适用场景 性能开销 实现复杂度
互斥锁（Mutex） 大块数据、写操作频繁 中 低
临界区（Critical Section） 小数据、实时性要求高 低 低
无锁数据结构（Lock-Free） 高频读写、不能阻塞 高（但无阻塞） 高

互斥锁是最常用的。但要注意，不要在中断服务函数里用互斥锁，会死锁。我有个同事就犯过这个错，查了两天才找到原因。

/* 互斥锁保护示例 */
void SensorTask(void* argument) {
    while (1) {
        /* 采集传感器数据 */
        float distance = read_obstacle_sensor();
        
        /* 加锁保护 */
        osMutexAcquire(g_agv_data.mutex, osWaitForever);
        g_agv_data.obstacle_distance = (uint8_t)distance;
        osMutexRelease(g_agv_data.mutex);
        
        osDelay(10);  /* 10ms采集一次 */
    }
}

临界区适合保护非常小的数据。比如一个标志位、一个计数值。它的好处是快，坏处是不能嵌套，也不能在里面做耗时操作。

/* 临界区保护示例 */
void ControlTask(void* argument) {
    uint8_t local_distance;
    
    while (1) {
        /* 进入临界区 */
        taskENTER_CRITICAL();
        local_distance = g_agv_data.obstacle_distance;
        taskEXIT_CRITICAL();
        
        /* 根据距离做控制决策 */
        if (local_distance < 20) {
            emergency_brake();
        }
        
        osDelay(5);
    }
}

无锁数据结构是高级玩法。我建议新手先别碰，容易翻车。但如果你做的是高频数据采集，比如IMU数据每秒1000次更新，用互斥锁会导致任务频繁阻塞，这时候无锁设计就派上用场了。

核心原则：数据一致性保护不是越强越好。过度的保护会降低系统实时性。我的做法是：先分析数据流，找出真正的竞争条件，然后针对性地加保护。不要一上来就给所有共享数据加锁。

24.4 实战中的选择策略

说了这么多，到底怎么选？我给你们一个决策流程：

  1. 数据量大小：小于4字节？用临界区或原子操作。大于4字节？用互斥锁或发布-订阅。
  2. 访问频率：低频（<100Hz）用互斥锁。高频（>1000Hz）考虑无锁设计。
  3. 任务数量：2-3个任务共享数据，用全局结构体+互斥锁。超过5个任务，用发布-订阅模式。
  4. 实时性要求：硬实时任务（如电机控制）尽量用临界区，避免被高优先级任务抢占。

我记得有一次，一个AGV项目在调试阶段频繁死机。查了三天，最后发现是传感器任务和控制任务共用一个全局变量，但没有加任何保护。传感器任务在更新数据时被中断，控制任务读到一半的数据，直接算出了一个荒谬的控制量，电机瞬间反转，AGV原地打转。

嗯，从那以后，我养成了一个习惯：每个共享数据都要问自己三个问题——谁在写？谁在读？写和读会不会同时发生？如果会，就必须加保护。

最后说一句，数据流设计没有银弹。全局结构体简单但脆弱，发布-订阅灵活但复杂，无锁设计高效但难调试。我的建议是：从简单的开始，随着系统复杂度增加，逐步演进。不要一开始就搞个大而全的框架，容易把自己绕进去。
