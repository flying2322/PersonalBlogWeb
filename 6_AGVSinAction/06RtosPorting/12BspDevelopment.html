12 板级支持包（BSP）开发：GPIO驱动封装、UART驱动（中断+轮询）、定时器驱动

各位同学，欢迎来到BSP开发的核心环节。说实话，很多初学者觉得BSP就是写几个寄存器，没什么技术含量。但我在项目中踩过的坑告诉我——BSP写得好不好，直接决定了你上层应用是「如丝般顺滑」还是「天天加班找bug」。

今天我们就来聊聊三个最基础的驱动：GPIO、UART和定时器。别小看它们，你想想看，一个AGV控制器里，传感器信号采集靠GPIO，与上位机通信靠UART，任务调度和PWM生成靠定时器。这三板斧耍好了，你的RTOS才算真正跑起来了。

12.1 GPIO驱动封装——别再用裸寄存器了

我个人习惯，写GPIO驱动第一步不是写代码，而是先画个「引脚资源表」。你想想看，一个AGV控制器少说几十个GPIO，电机方向、编码器输入、限位开关、蜂鸣器……如果不统一管理，后期维护就是灾难。

我建议的封装思路是这样的：

  • 结构体抽象：把GPIO的端口、引脚号、模式、上下拉、速度等信息打包成一个结构体
  • 初始化函数：传入结构体指针，一次性配置所有参数
  • 读写接口：PinWrite(pin, level) 和 PinRead(pin)，简单明了
  • 中断回调：注册中断服务函数，支持上升沿/下降沿/双边沿触发

核心要点：GPIO驱动要「面向对象」一点。别在应用层直接操作寄存器，否则换个芯片平台，你所有代码都得重写。

来看一个简化的GPIO驱动结构体定义：

/* gpio.h */
typedef struct {
    uint32_t port;      /* GPIOA ~ GPIOH */
    uint16_t pin;       /* 0 ~ 15 */
    uint8_t  mode;      /* 输入/输出/复用/模拟 */
    uint8_t  pull;      /* 上拉/下拉/浮空 */
    uint8_t  speed;     /* 低速/中速/高速 */
    void     (*irq_callback)(void);  /* 中断回调函数指针 */
} gpio_cfg_t;

/* 初始化接口 */
int32_t gpio_init(gpio_cfg_t *cfg);

/* 读写接口 */
void    gpio_pin_write(gpio_cfg_t *cfg, uint8_t level);
uint8_t gpio_pin_read(gpio_cfg_t *cfg);

避坑指南：我曾经在一个项目中，把GPIO中断回调函数直接放在了中断向量表里。结果后来要支持多个引脚中断，代码改得面目全非。后来我改用「回调函数注册表」的方式，每个引脚可以独立注册回调，清爽多了。

12.2 UART驱动——中断和轮询，两手都要硬

UART驱动是BSP里最「人格分裂」的一个模块。为什么这么说？因为你要同时支持两种模式：中断模式和轮询模式。

轮询模式简单粗暴，适合调试阶段或者低速率通信。但AGV控制器在运行时，你不可能让CPU一直傻等着串口数据——这时候就必须上中断了。

我一般这样设计UART驱动：

  • 环形缓冲区：接收和发送各一个环形缓冲区，中断服务程序只管往缓冲区里塞数据
  • API分层：底层是寄存器操作，中间层是缓冲区管理，上层是标准接口（如printf重定向）
  • 超时机制：接收数据时加个超时判断，防止死等

来看UART中断接收的核心逻辑：

/* uart.c - 中断接收示例 */
static uint8_t rx_buffer[UART_RX_BUF_SIZE];
static volatile uint16_t rx_head = 0;
static volatile uint16_t rx_tail = 0;

void uart_irq_handler(void)
{
    uint8_t data;
    if (USART->SR & USART_SR_RXNE) {
        data = USART->DR;
        /* 计算下一个位置，环形缓冲 */
        uint16_t next = (rx_head + 1) % UART_RX_BUF_SIZE;
        if (next != rx_tail) {  /* 缓冲区未满 */
            rx_buffer[rx_head] = data;
            rx_head = next;
        }
        /* 如果满了，可以置一个溢出标志，或者丢弃旧数据 */
    }
}

/* 应用层读取一个字节，非阻塞 */
int32_t uart_read_byte(uint8_t *byte, uint32_t timeout_ms)
{
    uint32_t tick_start = get_sys_tick();
    while (rx_head == rx_tail) {
        if (get_sys_tick() - tick_start > timeout_ms) {
            return -1;  /* 超时 */
        }
    }
    *byte = rx_buffer[rx_tail];
    rx_tail = (rx_tail + 1) % UART_RX_BUF_SIZE;
    return 0;
}

注意：中断服务程序里千万不要做复杂操作！我见过有人直接在UART中断里调用printf，结果递归中断直接死机。记住：中断里只做数据搬运，处理逻辑放到任务里。

轮询模式就简单多了，适合打印调试信息：

/* 轮询发送 - 简单粗暴 */
void uart_poll_send(uint8_t data)
{
    /* 等待发送寄存器空 */
    while (!(USART->SR & USART_SR_TXE));
    USART->DR = data;
}

嗯，这里要注意：轮询发送在RTOS里要加个任务延时或者信号量，别让低优先级任务把CPU占死了。

12.3 定时器驱动——RTOS的心脏起搏器

定时器驱动是BSP里最容易被低估的模块。说白了，没有定时器，你的RTOS就是个「死系统」——任务调度靠它，延时靠它，PWM生成也靠它。

我一般把定时器驱动分成三个层次：

  1. 系统节拍定时器：通常用SysTick或者一个通用定时器，产生1ms或10ms的周期性中断，驱动RTOS的调度器
  2. 硬件定时器管理：封装多个硬件定时器，提供开启、停止、设置周期、获取计数值等接口
  3. 软件定时器：基于硬件定时器，实现多个软件定时器，支持单次和周期模式

我个人习惯，系统节拍定时器用SysTick就够了，简单可靠。但如果你需要高精度的PWM或者输入捕获，那就得用通用定时器了。

来看系统节拍定时器的初始化：

/* systick.c - 系统节拍初始化 */
void systick_init(uint32_t tick_hz)
{
    /* 假设系统时钟为 72MHz */
    uint32_t reload = 72000000 / tick_hz - 1;
    SysTick->LOAD = reload;
    SysTick->VAL  = 0;
    SysTick->CTRL = SysTick_CTRL_CLKSOURCE_Msk |
                    SysTick_CTRL_TICKINT_Msk   |
                    SysTick_CTRL_ENABLE_Msk;
}

/* SysTick 中断服务程序 */
void SysTick_Handler(void)
{
    /* 递增系统滴答计数 */
    sys_tick_count++;
    /* 通知RTOS内核：一个节拍过去了 */
    if (xTaskGetSchedulerState() != taskSCHEDULER_NOT_STARTED) {
        xPortSysTickHandler();
    }
}

关键点：系统节拍中断的优先级要设置好。我一般把它设为RTOS允许的最高优先级，但比硬实时中断（比如电机急停）低一级。这样既保证了任务调度的实时性，又不会阻塞关键硬件中断。

对于通用定时器，我封装了这样一个接口：

/* timer.h */
typedef void (*timer_callback_t)(void *arg);

typedef struct {
    TIM_TypeDef *instance;   /* TIM1 ~ TIM8 等 */
    uint32_t     period_us;  /* 周期，单位微秒 */
    uint8_t      auto_reload;/* 是否自动重装载 */
    timer_callback_t callback;
    void        *arg;
} hw_timer_t;

int32_t hw_timer_init(hw_timer_t *tmr);
int32_t hw_timer_start(hw_timer_t *tmr);
int32_t hw_timer_stop(hw_timer_t *tmr);

经验之谈：我曾经在一个AGV项目里，用定时器做超声波传感器的触发信号。一开始直接用软件延时，结果测距数据抖动得厉害。后来改用硬件定时器产生40kHz的方波，数据稳如老狗。所以说，能用硬件定时器解决的问题，别用软件去扛。

12.4 三个驱动的协同工作

最后，我想聊聊这三个驱动怎么配合。你想想看，一个典型的AGV控制场景是这样的：

  • GPIO检测到限位开关被触发（中断）
  • UART把状态信息发送给上位机
  • 定时器产生PWM信号，控制电机减速停止

这三个驱动不是孤立的。我建议在BSP层提供一个统一的「中断管理」机制，把GPIO中断、UART中断、定时器中断都注册到一个表中，方便调试和优先级管理。

嗯，今天就先聊到这里。驱动开发没有捷径，多写多测，慢慢就有感觉了。记住我一句话：BSP写得好，应用层开发就像在高速公路上开车；BSP写得烂，那就是在泥巴地里推车。
