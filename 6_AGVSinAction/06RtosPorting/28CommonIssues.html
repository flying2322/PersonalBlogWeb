28 常见问题与解决方案

各位工程师朋友，这一讲咱们来聊聊RTOS移植中最让人头疼的几个“坑”。任务死锁、优先级反转、中断延迟过高、内存泄漏——这四个问题，我敢说每个做嵌入式的老手都至少被其中两个折磨过。我自己在AGV控制器项目里，就曾因为一个优先级反转的问题，让小车在仓库里原地打转了整整一个下午。

别担心，今天我把这些问题的根因和解决方案掰开揉碎了讲给你听。你想想看，搞懂了这些，以后调试起来能省多少时间？

4.1 任务死锁

死锁，说白了就是两个或多个任务互相等待对方释放资源，结果谁也动不了。就像两个人过独木桥，你让我先过，我让你先过，结果都堵在桥上。

4.1.1 死锁的四个必要条件

我记得教科书上讲了四个条件：互斥、持有并等待、不可剥夺、循环等待。但在实际项目中，你不需要背这些。你只需要记住一个场景：任务A拿了锁1，等锁2；任务B拿了锁2，等锁1。嗯，这就是最常见的死锁。

典型场景：AGV控制器中，路径规划任务持有“地图数据锁”，等待“电机控制锁”；而电机控制任务持有“电机控制锁”，等待“地图数据锁”。两个任务就这么僵住了。

4.1.2 解决方案

  • 固定锁顺序：我个人的习惯是，所有任务在申请多个锁时，都按照相同的顺序申请。比如先申请锁A，再申请锁B。这样就不会出现循环等待。
  • 使用超时机制：在RTOS中，可以用osMutexAcquire(mutex, timeout)这样的API。如果超时没拿到锁，就释放自己已经持有的锁，然后重试。
  • 避免嵌套锁：能用一个锁解决的问题，绝不用两个。我在项目中见过有人为了“性能优化”搞了五六个锁，结果死锁排查了三天。
小技巧：调试死锁时，可以打开RTOS的锁追踪功能。FreeRTOS的configUSE_TRACE_FACILITY打开后，能看到每个任务在等哪个锁。

4.2 优先级反转

优先级反转，这是个经典问题。高优先级任务被低优先级任务阻塞，因为中间有个中等优先级任务在“插队”。

4.2.1 问题本质

举个例子：任务A（高优先级）和任务C（低优先级）共享一个互斥锁。任务C先拿到了锁，然后任务A来了，等锁。这时候任务B（中等优先级）开始运行，它不拿锁，所以一直占着CPU。任务C拿不到CPU，就释放不了锁。结果任务A这个高优先级任务，被中等优先级的任务B给“反转”了。

我曾经在一个AGV的传感器融合任务中遇到过这个问题。传感器任务优先级最高，但被一个日志打印任务（低优先级）的锁给卡住了，中间还有个网络通信任务（中等优先级）一直在跑。结果传感器数据更新延迟，小车差点撞墙。

4.2.2 解决方案

方案 说明 适用场景
优先级继承 低优先级任务持有锁时，临时提升到高优先级任务的优先级 大多数RTOS原生支持，如FreeRTOS的互斥量
优先级天花板 锁的优先级设置为所有可能申请它的任务中的最高优先级 锁的使用场景固定，任务集合已知
关中断保护 在临界区关中断，避免任务切换 临界区代码极短（<10微秒）
注意：优先级继承不是万能的。如果系统中有多个锁嵌套使用，优先级继承可能导致“连锁继承”，反而增加系统复杂度。我建议在AGV控制器中，尽量使用优先级天花板方案，简单可靠。

4.3 中断延迟过高

中断延迟，就是从硬件中断触发到中断服务程序（ISR）开始执行的时间。这个时间如果太长，实时性就没了。

4.3.1 常见原因

  • 关中断时间过长：有些工程师在临界区里关中断，一关就是几十微秒甚至上百微秒。你想想看，这期间所有中断都进不来。
  • ISR本身执行太久：在ISR里做复杂计算、打印日志、甚至调用阻塞API。这是大忌。
  • 中断嵌套：高优先级中断被低优先级中断阻塞，或者中断嵌套层数太多。

4.3.2 优化方法

我个人习惯遵循一个原则：ISR里只做最必要的事。比如，在AGV控制器的编码器中断里，我只读取计数值并存入缓冲区，然后发一个信号量给任务。真正的数据处理，交给任务去做。

// 好的做法：ISR只做标记
void Encoder_ISR(void) {
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    g_encoder_count = TIM->CNT;  // 只读寄存器
    xSemaphoreGiveFromISR(xEncoderSemaphore, &xHigherPriorityTaskWoken);
    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

// 坏的做法：ISR里做复杂计算
void Encoder_ISR_Bad(void) {
    // 千万别这么干！
    g_encoder_count = TIM->CNT;
    calculate_speed(g_encoder_count);  // 浮点运算，耗时！
    log_to_console("Encoder value: %d", g_encoder_count);  // 打印，更耗时！
}
避坑指南：我曾经在调试一个AGV时，发现中断延迟从5微秒飙升到200微秒。查了半天，发现是某个驱动库在临界区里调用了printf。printf内部会等待串口发送完成，而串口中断优先级比当前中断低，结果就死锁了。嗯，从那以后我再也不在临界区里调打印函数了。

4.4 内存泄漏

内存泄漏，就是动态分配的内存没有释放，导致可用内存越来越少。在AGV控制器这种长期运行的系统中，内存泄漏是致命的——跑着跑着就崩了。

4.4.1 泄漏来源

  • 忘记调用free：malloc了但没free，这是最常见的。
  • 异常路径未释放：函数在中间return了，但前面的malloc没释放。
  • RTOS内部泄漏：比如任务删除时，任务栈没有正确回收。

4.4.2 检测与修复

我建议在AGV控制器开发中，遵循以下几条铁律：

  1. 谁分配谁释放：哪个模块malloc的内存，就由哪个模块负责free。不要跨模块传递所有权。
  2. 使用内存池：对于固定大小的数据结构（如消息队列、任务控制块），用静态内存池代替动态分配。FreeRTOS的pvPortMalloc底层就是内存池。
  3. 开启内存统计：在FreeRTOS中，可以开启configUSE_MALLOC_FAILED_HOOK，当内存分配失败时触发钩子函数，打印当前内存使用情况。
实战技巧：我习惯在代码中封装一个内存调试宏： 
#define MALLOC(size)  malloc_debug(size, __FILE__, __LINE__)
#define FREE(ptr)     free_debug(ptr, __FILE__, __LINE__)

void *malloc_debug(size_t size, const char *file, int line) {
    void *p = malloc(size);
    printf("[MEM] %s:%d malloc(%d) = %p\n", file, line, size, p);
    return p;
}
这样每次分配和释放都有日志，配合脚本分析，很容易找到泄漏点。
