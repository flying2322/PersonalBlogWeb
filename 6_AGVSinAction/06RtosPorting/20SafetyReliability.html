20 安全与可靠性：看门狗（IWDG/WWDG）配置、数据校验（CRC）、异常处理与系统恢复

做AGV控制器，最怕什么？

我最怕车跑到一半，控制器死机了。AGV在仓库里高速穿梭，一旦失控，撞货架、撞人，后果不堪设想。所以，安全与可靠性，是AGV控制器的生命线。

这一章，我们就来聊聊怎么给系统上“保险”。说白了，就是三件事：用看门狗防止程序跑飞，用CRC校验数据有没有被篡改，以及设计一套异常处理机制让系统能自己“活过来”。

核心思想：嵌入式系统不可靠是常态，我们要做的不是避免故障，而是让故障发生时，系统能安全地恢复。

20.1 看门狗：系统的“最后一道防线”

看门狗（Watchdog）是什么？你可以把它想象成一个脾气暴躁的保安。你每隔一段时间必须去“打卡”（喂狗），告诉它“我还活着”。如果你没按时打卡，它就认为你出事了，直接按复位键重启系统。

STM32里有两个看门狗：独立看门狗（IWDG）和窗口看门狗（WWDG）。我个人习惯，在AGV主控制器上，两个都用。

20.1.1 独立看门狗（IWDG）—— 防死机利器

IWDG由独立的40kHz内部低速时钟驱动。即使主时钟挂了，它照样工作。这特性太重要了。你想想看，如果主时钟都停了，系统肯定已经崩溃了，这时候只有IWDG能救你。

配置IWDG很简单，就三步：

  1. 取消写保护： 操作IWDG的键寄存器（KR），写入0x5555解锁。
  2. 设置分频和重装载值： 决定喂狗的时间窗口。
  3. 启动看门狗： 写入0xCCCC启动。

来看个实际代码：

// IWDG配置函数
void IWDG_Config(uint8_t prescaler, uint16_t reload) {
    // 1. 解锁IWDG
    IWDG->KR = 0x5555;
    
    // 2. 设置预分频器
    // prescaler: 0-6，对应4/8/16/32/64/128/256分频
    IWDG->PR = prescaler;
    
    // 3. 设置重装载值（12位，最大0xFFF）
    IWDG->RLR = reload;
    
    // 4. 等待寄存器更新完成
    while (IWDG->SR & 0x01);
    
    // 5. 启动看门狗
    IWDG->KR = 0xCCCC;
}

// 喂狗函数
void IWDG_Feed(void) {
    IWDG->KR = 0xAAAA;
}

经验之谈：喂狗时间别设太短。我曾经在一个项目里设了100ms，结果主循环里一个耗时操作稍微超了点，系统就反复重启。后来我改成500ms，留足余量。AGV控制器的控制周期一般是10-50ms，所以设个200-500ms比较合理。

20.1.2 窗口看门狗（WWDG）—— 防程序跑偏

WWDG比IWDG更“聪明”。它不光要求你按时喂狗，还要求你在一个特定的时间窗口内喂狗。喂早了不行，喂晚了也不行。

为什么需要这个？因为程序跑飞后，有可能碰巧执行到了喂狗代码。如果只是IWDG，它可能刚好在复位前喂了狗，系统就永远无法恢复。但WWDG的窗口机制，让这种巧合几乎不可能发生。

配置WWDG稍微复杂一点：

// WWDG配置函数
void WWDG_Config(uint8_t counter, uint8_t window) {
    // 1. 使能WWDG时钟
    RCC->APB1ENR |= RCC_APB1ENR_WWDGEN;
    
    // 2. 设置窗口值（WWDG->CFR的低7位）
    // 喂狗必须在计数器值 < 窗口值 且 > 0x3F 时进行
    WWDG->CFR = (window & 0x7F) << 7;
    
    // 3. 设置分频（WWDG->CFR的bit8-9）
    // 00: 1分频, 01: 2分频, 10: 4分频, 11: 8分频
    WWDG->CFR |= 0x00;  // 1分频
    
    // 4. 设置计数器初始值（WWDG->CR的低7位）
    WWDG->CR = counter & 0x7F;
    
    // 5. 使能WWDG（WWDG->CR的bit7）
    WWDG->CR |= 0x80;
}

// WWDG喂狗
void WWDG_Feed(void) {
    // 必须在窗口内喂狗
    // 读取当前计数器值
    uint8_t cnt = WWDG->CR & 0x7F;
    // 如果计数器值小于窗口值，可以喂狗
    if (cnt < (WWDG->CFR >> 7)) {
        WWDG->CR = (cnt & 0x7F) | 0x80;
    }
}

注意：WWDG的计数器是递减的。从0x7F开始往下减，减到0x3F时触发复位。窗口值必须大于0x3F。我一般设窗口值为0x60，计数器初始值0x7F，这样喂狗窗口是0x60到0x40之间。

20.2 数据校验：CRC—— 揪出“隐形错误”

AGV控制器里，数据在内存、外设、通信链路之间频繁传输。电磁干扰、硬件老化，都可能导致数据位翻转。一个bit错了，可能让电机转错方向，或者让路径规划算出离谱的轨迹。

CRC（循环冗余校验）就是用来检测这种错误的。它把数据当做一个多项式，通过除法运算生成一个校验码。接收方用同样的方法计算，如果结果不一致，说明数据被篡改了。

STM32内置了CRC计算单元，硬件算起来飞快。我一般在两个地方用：

  • 固件校验： 启动时计算Flash中固件的CRC，和预存的CRC比较，确保固件没被破坏。
  • 通信数据包： 每个CAN或串口数据包末尾加4字节CRC，接收方校验。

硬件CRC配置代码：

// 使能CRC时钟
RCC->AHB1ENR |= RCC_AHB1ENR_CRCEN;

// 计算32位数据的CRC
uint32_t CRC_Calc(uint32_t data) {
    CRC->DR = data;  // 写入数据寄存器
    return CRC->DR;   // 读取结果
}

// 计算一块内存的CRC
uint32_t CRC_CalcBlock(uint32_t *buf, uint32_t len) {
    // 复位CRC计算器
    CRC->CR = CRC_CR_RESET;
    
    for (uint32_t i = 0; i < len; i++) {
        CRC->DR = buf[i];
    }
    
    return CRC->DR;
}

避坑指南：我曾经在AGV的CAN通信里，只用了简单的累加和校验。结果有一次现场干扰特别大，累加和居然碰巧对了，但数据已经错了。车直接撞上了货架。从那以后，所有关键通信我都改用CRC32。多花4字节，换来的是安心。

20.3 异常处理与系统恢复—— 让系统“自己救自己”

看门狗和CRC都是“被动防御”。真正的高手，还要设计“主动恢复”机制。当系统检测到异常时，不是傻等看门狗复位，而是尝试自己恢复。

我设计AGV控制器时，会建立一个三级异常处理体系：

级别 异常类型 处理方式
一级 轻微异常（如通信超时一次） 记录日志，重试，不中断当前任务
二级 中等异常（如传感器数据CRC错误） 丢弃错误数据，使用上一帧有效数据，报警
三级 严重异常（如电机驱动器故障） 紧急停车，保存关键状态，触发看门狗复位

具体实现上，我习惯用状态机来管理：

typedef enum {
    SYS_NORMAL,       // 正常
    SYS_WARNING,      // 警告（一级异常）
    SYS_ERROR,        // 错误（二级异常）
    SYS_FAULT,        // 故障（三级异常）
    SYS_RECOVERY      // 恢复中
} SystemState;

SystemState g_sysState = SYS_NORMAL;

void System_ExceptionHandler(ExceptionType type) {
    switch(type) {
        case EXCEP_COMM_TIMEOUT:
            if (g_sysState == SYS_NORMAL) {
                g_sysState = SYS_WARNING;
                Log_Write("通信超时，重试中...");
                Comm_Retry();
            }
            break;
            
        case EXCEP_CRC_ERROR:
            g_sysState = SYS_ERROR;
            Log_Write("CRC错误，使用旧数据");
            Sensor_UseLastValidData();
            break;
            
        case EXCEP_MOTOR_FAULT:
            g_sysState = SYS_FAULT;
            Log_Write("电机故障，紧急停车");
            Motor_EmergencyStop();
            // 保存关键状态到备份寄存器
            RTC->BKPDR0 = g_agvState;
            // 触发软件复位
            NVIC_SystemReset();
            break;
            
        default:
            break;
    }
}

// 系统恢复函数（在main循环中调用）
void System_RecoveryCheck(void) {
    if (g_sysState == SYS_WARNING) {
        // 检查警告是否消除
        if (Comm_IsHealthy()) {
            g_sysState = SYS_NORMAL;
            Log_Write("系统恢复正常");
        }
    }
    
    if (g_sysState == SYS_FAULT) {
        // 从备份寄存器恢复状态
        g_agvState = RTC->BKPDR0;
        // 执行恢复流程
        AGV_RecoveryProcedure();
        g_sysState = SYS_RECOVERY;
    }
}

重要提醒：异常处理里千万别做复杂操作。比如在HardFault_Handler里调用printf，那只会让情况更糟。我一般只在异常处理里做三件事：保存现场、设置标志位、触发复位。其他事情等系统重启后再做。

最后说一句：安全设计不是功能，而是习惯。我每次写代码，都会问自己：如果这里出错了，系统会怎样？如果答不上来，说明设计还不够安全。AGV控制器是跑在路上的，容不得半点马虎。
