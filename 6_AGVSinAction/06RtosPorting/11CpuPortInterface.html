11 移植层接口（CPU Port）：寄存器上下文保存与恢复、PendSV异常处理、任务切换触发机制

好，我们直接进入RTOS移植中最核心、也最容易出bug的部分——CPU移植层。

说白了，这部分就是让RTOS内核跟你的CPU架构“对上话”。内核不知道你用的是Cortex-M3还是RISC-V，它只认一套标准接口。我们作为移植工程师，就是要把这些接口用CPU的“方言”实现出来。

11.1 寄存器上下文保存与恢复

先问一个问题：任务切换的本质是什么？

其实就是“保存当前任务的现场，恢复下一个任务的现场”。这个“现场”，就是CPU寄存器组。

我个人习惯把寄存器上下文分为两类：

  • 自动保存的：比如Cortex-M3在进入异常时，硬件会自动压栈PC、xPSR、R0-R3、R12等。这部分我们不用操心。
  • 需要手动保存的：R4-R11这些通用寄存器，硬件不管，得我们自己动手。

我在项目中遇到过一个问题：有个同事移植FreeRTOS到某国产Cortex-M0芯片上，任务跑着跑着就飞了。查了两天，发现是R4-R11的保存顺序跟内核期望的不一致。嗯，这种坑踩一次就记住了。

下面是一个典型的上下文保存代码（汇编），我习惯用portSAVE_CONTEXT宏来实现：

portSAVE_CONTEXT:
    ; 手动保存R4-R11
    STMDB   SP!, {R4-R11}
    ; 保存当前任务的SP到TCB
    LDR     R0, =pxCurrentTCB
    LDR     R0, [R0]
    STR     SP, [R0]

恢复上下文就是逆操作：

portRESTORE_CONTEXT:
    ; 从TCB加载新任务的SP
    LDR     R0, =pxCurrentTCB
    LDR     R0, [R0]
    LDR     SP, [R0]
    ; 恢复R4-R11
    LDMIA   SP!, {R4-R11}
    ; 最后一条指令触发异常返回
    BX      LR

关键点：保存和恢复的顺序必须严格对称。你保存时先压R4再压R5，恢复时就得先弹R11再弹R4。搞反了，任务栈就乱套了。

11.2 PendSV异常处理

PendSV是Cortex-M系列里一个特殊的异常。它的优先级可以设为最低，而且可以“挂起”——也就是等当前高优先级的事情处理完了再执行。

为什么RTOS要用PendSV做任务切换？

你想想看，如果我们在SysTick中断里直接切换任务，万一此时有一个更高优先级的中断正在执行，你强行切换，那个中断的现场就丢了。PendSV的好处是：它永远等到所有中断都处理完了，才轮到它干活。

我曾经在一个电机控制项目里，因为没处理好这个优先级关系，导致PendSV和PWM中断抢CPU时间，电机直接抖成了筛子。后来我把PendSV优先级设为最低，世界清净了。

PendSV的入口代码通常长这样：

PendSV_Handler:
    ; 先判断是否需要切换
    LDR     R0, =xNeedSwitch
    LDR     R0, [R0]
    CMP     R0, #0
    BEQ     ExitPendSV

    ; 保存当前任务上下文
    portSAVE_CONTEXT

    ; 调用任务选择函数
    BL      vTaskSwitchContext

    ; 恢复新任务上下文
    portRESTORE_CONTEXT

ExitPendSV:
    BX      LR

小技巧：我习惯在PendSV入口加一个“是否需要切换”的判断。如果不需要切换，直接跳过保存恢复流程，能省下几十个时钟周期。在实时性要求高的场景下，这点时间很宝贵。

11.3 任务切换触发机制

任务切换不会自己发生，得有人“踢一脚”。RTOS里通常有三种触发方式：

触发方式 触发源 典型场景
时间片轮转 SysTick中断 每个任务运行固定时间后切换
任务主动让出 调用taskYIELD() 任务等待信号量、队列时
中断后切换 ISR中调用portYIELD_FROM_ISR() 外设中断唤醒高优先级任务

这三种方式最终都会做同一件事：触发PendSV异常。

怎么触发？很简单，往ICSR寄存器的bit28写1：

; 触发PendSV
LDR     R0, =0xE000ED04    ; ICSR寄存器地址
LDR     R1, =0x10000000    ; PendSV挂起位
STR     R1, [R0]

就这么三条指令，任务切换就“排队”了。等当前中断或任务执行完，PendSV就会自动被响应。

注意：在中断服务函数里调用portYIELD_FROM_ISR时，一定要先检查是否需要切换。如果当前中断结束后没有更高优先级的任务就绪，就别触发PendSV。否则白白浪费一次上下文切换的开销。

我的建议：刚开始移植时，先别急着写完整代码。把这三个模块的汇编框架搭好，然后用一个简单的两个任务来回切换测试。能跑通，再往里填业务逻辑。我每次移植新平台都是这个套路，稳得很。

嗯，这一章的内容就这些。寄存器上下文保存恢复是基本功，PendSV是Cortex-M的“天选之子”，触发机制是任务切换的“扳机”。三者配合好了，你的RTOS就能在目标平台上跑得稳稳当当。

避坑总结：

  • 保存恢复顺序必须对称，少一个寄存器都不行
  • PendSV优先级设为最低，别跟其他中断抢
  • 触发PendSV前先判断是否真的需要切换
  • 中断里调用切换函数，记得用portYIELD_FROM_ISR而不是taskYIELD

我曾经在一个项目里，因为PendSV优先级没设对，导致系统响应延迟从10微秒飙到200微秒。查了整整一个下午，最后发现是优先级寄存器写错了值。从那以后，我每次移植完第一件事就是打印所有异常优先级，确认无误再往下走。
