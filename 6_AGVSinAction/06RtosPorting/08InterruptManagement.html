8 中断管理：中断优先级配置、中断嵌套处理、临界区保护

中断管理，说白了就是RTOS的“神经系统”。

你想想看，一个AGV控制器，要同时处理电机编码器脉冲、激光雷达数据、急停信号、通信报文……这些事件哪个都不能等。如果中断处理不好，轻则丢数据，重则车撞墙。

我个人习惯，做RTOS移植时，中断管理这块花的时间最多。因为它是硬实时性的核心保障。今天我们就来聊聊中断优先级怎么配、嵌套怎么处理、临界区怎么保护。

8.1 中断优先级配置——别让优先级“打架”

先问个问题：你的MCU支持多少级中断优先级？

以Cortex-M3/M4为例，它支持8~256级优先级（具体看芯片厂商实现）。但RTOS通常只用了4~16级。为什么？因为优先级太多，调度开销反而大。

核心原则：RTOS内核中断优先级必须高于所有用户中断。

为什么？因为内核需要管理任务切换、时间片轮转。如果用户中断优先级比内核高，那内核可能被“饿死”。

我在项目中遇到过一个问题：某AGV在高速运行时，电机编码器中断频繁触发，导致系统滴答定时器中断被延迟。结果任务调度乱了，车开始抖动。查了半天，发现是编码器中断优先级设得比SysTick还高。

配置建议：

  • SysTick中断：最高优先级（通常为0或1）
  • PendSV中断：次高优先级（用于触发任务切换）
  • SVC中断：与PendSV同级或略低
  • 用户外设中断：低于上述三个

以FreeRTOS为例，在移植时你需要设置一个宏：

/* FreeRTOSConfig.h */
#define configLIBRARY_LOWEST_INTERRUPT_PRIORITY    0x1F  /* 最低优先级 */
#define configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY 5   /* 可调用API的最高中断优先级 */

嗯，这里要注意：不同MCU的优先级寄存器位数不同。比如STM32F4只用了高4位，所以优先级值要左移4位。我刚开始移植时没注意这个，结果中断优先级完全乱套了。

8.2 中断嵌套处理——别让嵌套变成“套娃”

中断嵌套，说白了就是一个中断正在处理，另一个更高优先级的中断来了，CPU先处理高优先级的，处理完再回来继续。

RTOS里中断嵌套有个关键点：中断嵌套不能导致内核数据结构损坏。

你想想看，如果低优先级中断正在修改一个队列，高优先级中断来了，也去修改同一个队列——那数据就乱套了。

RTOS的解决方案：

  • 中断服务函数（ISR）里只能调用“FromISR”结尾的API
  • 这些API内部会检查当前是否在中断中，如果是，则使用特殊路径
  • 中断嵌套时，内核会维护一个嵌套计数器，确保只有最外层中断退出时才触发任务切换

我曾经在一个项目中，同事在ISR里直接调用了vTaskDelay()——这个函数不能在中断里用。结果系统随机死机，查了两天才找到原因。所以记住：ISR里只能用FromISR版本的API。

小技巧：写ISR时，尽量让它短小精悍。只做必要的硬件操作，然后通过信号量或消息队列通知任务去处理。这样中断嵌套深度自然就浅了。

8.3 临界区保护——关中断 vs 锁调度器

临界区，就是一段不能被打断的代码。比如修改任务链表、操作队列、更新全局变量。

RTOS提供了两种保护方式：

保护方式 原理 影响范围 适用场景
关中断 关闭所有可屏蔽中断 整个系统 极短的操作（几个指令周期）
锁调度器 禁止任务切换，但中断仍可响应 仅任务调度 较长的操作（几十到几百微秒）

关中断（taskENTER_CRITICAL() / taskEXIT_CRITICAL()）

这个宏会保存当前中断状态，然后关中断。退出时恢复。注意：它不能嵌套使用——或者说，FreeRTOS支持嵌套，但内部维护了一个嵌套计数器。

void vAGV_SetSpeed(int32_t speed) {
    taskENTER_CRITICAL();
    /* 修改共享的电机控制变量 */
    g_agv_speed = speed;
    g_agv_speed_updated = 1;
    taskEXIT_CRITICAL();
}

锁调度器（vTaskSuspendAll() / xTaskResumeAll()）

这个函数只禁止任务切换，但中断仍然可以响应。中断里可以继续使用队列、信号量等，只是不会触发任务切换。

void vAGV_ProcessPath(void) {
    vTaskSuspendAll();
    /* 处理路径规划数据，可能耗时较长 */
    for (int i = 0; i < path_len; i++) {
        /* 计算路径点 */
    }
    xTaskResumeAll();
}

警告：关中断的时间一定要短！我见过有人在一个循环里关中断处理大量数据，结果导致看门狗超时复位。一般建议关中断不超过10微秒。如果操作时间较长，用锁调度器代替。

8.4 实战经验：中断延迟的“隐形杀手”

做AGV控制器，最怕的就是中断延迟抖动。比如激光雷达数据来了，但CPU正在关中断处理别的，结果雷达数据没及时读取，导致建图出错。

我总结了几条经验：

  • 关中断的代码要放在RAM里执行——Flash访问有等待周期，放RAM里能快不少
  • 中断优先级分组要统一——Cortex-M支持抢占优先级和子优先级，整个项目必须用同一种分组方式
  • ISR里不要做浮点运算——浮点运算会占用大量寄存器，增加中断保存恢复时间
  • 用DMA配合中断——比如UART接收，让DMA把数据搬到内存，中断只做标志通知，这样中断处理时间极短

我记得有一次，AGV在仓库里突然“抽风”，电机一顿一顿的。用逻辑分析仪抓了中断响应时间，发现SysTick中断的响应时间从1微秒抖到了50微秒。最后定位到是一个第三方库的关中断操作没配对，导致中断被关了很长时间。

8.6 总结

中断管理这块，说白了就是三个字：快、准、稳。

  • 快——ISR要短，关中断要短
  • 准——优先级配准，API用准
  • 稳——临界区保护稳，嵌套处理稳

做AGV控制器，中断处理不好，车就跑不稳。希望今天的分享能帮你少踩几个坑。如果你在移植过程中遇到什么奇怪的问题，欢迎交流。
