7 调度器实现：优先级抢占调度算法、时间片轮转调度、空闲任务与阻塞机制

调度器，说白了就是RTOS的「大脑」。它决定哪个任务该运行，哪个任务该歇着。我做了这么多年嵌入式，见过太多系统崩溃，十有八九是调度策略没搞对。今天咱们就把这块硬骨头啃下来。

7.1 优先级抢占调度算法

这是RTOS最核心的调度方式。它的规则很简单：谁优先级高，谁先跑。但实现起来，坑不少。

我个人习惯把优先级分为0到255级，0最高，255最低。为什么这么分？因为ARM Cortex-M内核的NVIC就是这么设计的，直接映射到硬件中断优先级，省事。

7.1.1 就绪队列设计

每个优先级对应一个就绪队列。任务就绪了，就挂到对应队列的尾部。调度时，从最高优先级队列头部取任务。

/* 就绪队列结构 */
typedef struct {
    uint32_t    priority;           /* 优先级 */
    List_t      task_list;          /* 任务链表 */
} ReadyQueue_t;

/* 全局就绪队列表 */
static ReadyQueue_t ready_queue[CONFIG_MAX_PRIORITY];

这里有个关键点：如何快速找到最高优先级的就绪任务？

我曾经在项目里用for循环遍历，结果在256级优先级下，每次调度要扫描256次。系统跑起来后，调度开销占了CPU的30%！后来改用位图法，一个32位变量就能表示256个优先级，用CLZ指令一条指令搞定。

/* 位图法查找最高优先级 */
static inline uint32_t get_highest_ready_priority(void) {
    uint32_t bit = __CLZ(ready_bitmap);  /* 前导零计数 */
    return 31 - bit;
}

避坑指南：我曾经在STM32F103上移植FreeRTOS，就栽在优先级位数上。Cortex-M3只支持8位优先级，你硬要搞256级，结果就是优先级反转。记住：硬件支持多少级，软件就用多少级。

7.1.2 抢占时机

抢占不是随时都能发生的。它发生在以下三个时刻：

  • 任务创建时：新任务优先级更高，立即抢占
  • 任务唤醒时：被唤醒的任务优先级高于当前任务
  • 时钟节拍中断时：时间片用完，检查是否有更高优先级任务

嗯，这里要注意：中断服务函数里不能直接做任务切换。我见过新手在ISR里调用调度器，结果系统直接死机。正确做法是设置一个标志位，在中断退出时检查并触发PendSV异常，在PendSV里完成切换。

7.2 时间片轮转调度

优先级抢占保证了实时性，但有个问题：如果两个任务优先级相同，谁先跑？

答案就是时间片轮转。每个任务跑一个固定时间片（比如10ms），时间到了就换下一个。说白了就是「轮流坐庄」。

7.2.1 时间片实现

时间片依赖于系统时钟节拍。每个任务有一个剩余时间片计数器，每次时钟中断减1，减到0就触发调度。

/* 任务控制块增加时间片字段 */
typedef struct {
    TaskStack_t    *stack;           /* 栈指针 */
    uint32_t        priority;        /* 优先级 */
    uint32_t        slice_remain;    /* 剩余时间片 */
    uint32_t        slice_total;     /* 总时间片 */
    /* ... 其他字段 */
} TCB_t;

/* 时钟节拍中断处理 */
void SysTick_Handler(void) {
    TCB_t *current = get_current_task();
    
    if (current->slice_remain > 0) {
        current->slice_remain--;
    }
    
    if (current->slice_remain == 0) {
        need_schedule = 1;  /* 触发调度 */
    }
}

我的经验：时间片别设太短。我见过有人设1ms，结果系统80%的时间都在做任务切换。一般10-50ms比较合适。如果任务对响应时间要求高，用优先级抢占就够了，别开时间片。

7.2.2 轮转策略

时间片用完的任务，放到同优先级队列的尾部。下一个任务从队列头部取。这样大家轮流来，谁也不吃亏。

你想想看，如果某个任务一直不主动让出CPU，时间片机制就是最后的保障。但要注意：时间片只对同优先级任务有效。高优先级任务来了，低优先级的立马靠边站。

7.3 空闲任务与阻塞机制

系统里没有任务可运行时，谁来干活？答案是空闲任务。它是系统自动创建的，优先级最低（255级）。

7.3.1 空闲任务的作用

  • 统计CPU利用率：空闲任务运行的时间占比，就是CPU的空闲率
  • 清理任务资源：被删除的任务，由空闲任务释放内存
  • 进入低功耗模式：没事干就睡觉，省电
/* 空闲任务实现 */
void idle_task(void *param) {
    (void)param;
    
    while (1) {
        /* 统计空闲时间 */
        idle_count++;
        
        /* 清理已删除任务 */
        cleanup_deleted_tasks();
        
        /* 进入低功耗模式 */
        #ifdef CONFIG_POWER_SAVE
        __WFI();  /* 等待中断 */
        #endif
    }
}

警告：空闲任务里不能调用任何可能阻塞的函数！比如获取信号量、等待队列消息。我曾经在空闲任务里加了个延时，结果系统直接死锁——空闲任务阻塞了，没有任务能释放它。

7.3.2 阻塞机制

任务为什么会被阻塞？说白了就是「等资源」。等信号量、等消息队列、等延时结束。阻塞状态的任务不在就绪队列里，调度器不会选它。

阻塞的实现很简单：任务调用阻塞API时，把自己从就绪队列移除，挂到对应的等待队列。条件满足时，再移回就绪队列。

/* 任务延时阻塞 */
void task_delay(uint32_t ticks) {
    TCB_t *current = get_current_task();
    
    /* 从就绪队列移除 */
    remove_from_ready_queue(current);
    
    /* 挂到延时队列 */
    current->delay_remain = ticks;
    add_to_delay_list(current);
    
    /* 触发调度 */
    schedule();
}

这里有个细节：时钟节拍中断里要检查延时队列。每个节拍把延时任务的计数器减1，减到0就唤醒。

7.5 调度器性能对比

不同调度策略各有优劣。我整理了一张表，方便你选型时参考：

调度策略 实时性 公平性 CPU开销 适用场景
优先级抢占 高 低 低 强实时控制
时间片轮转 中 高 中 人机交互
优先级+时间片 高 中 中 综合系统
空闲任务 - - 极低 后台处理

我的建议：AGV控制器这种实时性要求高的场景，用「优先级抢占+同优先级时间片」的组合最稳妥。高优先级任务保证急停、避障等关键操作，同优先级任务用时间片保证公平。别搞太复杂，简单可靠才是王道。
