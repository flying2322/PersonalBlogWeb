18 调试与性能分析：断言机制、任务栈溢出检测、CPU利用率统计

各位同学，今天我们来聊聊RTOS调试中三个最实用的工具。说实话，我刚开始做AGV控制器那会儿，系统跑着跑着就莫名其妙死机，查半天找不到原因。后来才明白，不是代码写得不够好，而是调试手段没跟上。

断言、栈溢出检测、CPU利用率统计，这三样东西就像是嵌入式开发的「三把刀」。用好了，能帮你省下大把抓头发的时间。

断言（assert）机制：代码里的「安全气囊」

断言是什么？说白了就是一个检查点。你告诉编译器：「这里的情况必须是这样，如果不是，你就给我停下来报错。」

我在项目中遇到过最典型的例子：某个任务接收到的消息队列指针突然变成NULL了。如果没有断言，程序会继续跑，然后访问非法地址，系统崩溃。有了断言，当场就能定位到问题。

核心思路：断言用于捕获「不可能发生」的情况。一旦触发，说明你的假设被打破了。

RTOS里常用的断言写法：

// 自定义断言宏
#define ASSERT(expr) \
    do { \
        if (!(expr)) { \
            printf("ASSERT FAILED: %s, file %s, line %d\n", \
                   #expr, __FILE__, __LINE__); \
            while(1); /* 挂起系统 */ \
        } \
    } while(0)

// 使用示例
void task_send_msg(QueueHandle_t q, void *msg) {
    ASSERT(q != NULL);      // 队列不能为空
    ASSERT(msg != NULL);    // 消息不能为空
    xQueueSend(q, msg, 0);
}

我的习惯：在产品发布版本中，我会把ASSERT宏定义为空。只在调试版本中启用。这样既保证了开发效率，又不影响最终性能。

嗯，这里要注意：断言不是错误处理。错误处理是应对「可能发生」的异常，比如内存分配失败。断言是应对「理论上绝对不可能」的情况。别搞混了。

任务栈溢出检测：别让栈「爆」了

你想想看，每个任务都有自己的栈空间。如果任务里递归调用太深，或者局部变量太大，栈就会溢出。溢出的后果是什么？踩到别的任务的数据，或者踩到内核数据。系统行为变得诡异，时好时坏。

FreeRTOS提供了两种检测方式：

检测方式 原理 开销
方法1：栈末尾填充标记 创建任务时在栈底写入已知值，定期检查是否被覆盖 低
方法2：寄存器检测 利用CPU的栈指针寄存器，检查是否越界 较高

我个人更推荐方法1，因为它简单可靠。配置方法如下：

// 在FreeRTOSConfig.h中开启
#define configCHECK_FOR_STACK_OVERFLOW    1   // 启用方法1
// 或
#define configCHECK_FOR_STACK_OVERFLOW    2   // 启用方法2

// 实现钩子函数
void vApplicationStackOverflowHook(TaskHandle_t xTask, 
                                   char *pcTaskName) {
    printf("栈溢出！任务: %s\n", pcTaskName);
    ASSERT(0);  // 触发断言，立即停止
}

我曾经踩过的坑：有个AGV项目，任务栈分配了512字节，觉得够用了。结果加了几个日志打印函数后，栈就爆了。后来我养成了习惯：每个任务至少预留20%的余量。别抠门，栈空间省下来的那点内存，不够你调试一个通宵的。

为什么会这样？因为很多库函数（比如printf）内部会使用不小的栈空间。你看着自己代码只用了200字节，但调个printf可能就吃掉300字节。

CPU利用率统计：你的CPU在忙什么？

做AGV控制器，CPU利用率是个硬指标。如果CPU跑满了，紧急刹车指令可能延迟响应，后果很严重。

FreeRTOS的CPU利用率统计原理其实很简单：

  1. 创建一个优先级最低的「空闲任务」
  2. 空闲任务运行时，记录它占用的时间
  3. 总时间减去空闲时间，就是CPU利用率

配置方法：

// FreeRTOSConfig.h中开启
#define configGENERATE_RUN_TIME_STATS    1
#define configUSE_STATS_FORMATTING_FUNCTIONS  1

// 需要提供一个高精度定时器
// 比如使用SysTick的计数器
volatile uint32_t ulHighFrequencyTimerTicks = 0;

void vConfigureTimerForRunTimeStats(void) {
    // 配置定时器，每1us递增一次
    ulHighFrequencyTimerTicks = 0;
}

// 在定时器中断中调用
void timer_isr(void) {
    ulHighFrequencyTimerTicks++;
}

获取统计信息：

void print_cpu_usage(void) {
    char pcWriteBuffer[512];
    
    // 获取各任务CPU占用率
    vTaskGetRunTimeStats(pcWriteBuffer);
    printf("任务CPU占用率:\n%s\n", pcWriteBuffer);
    
    // 获取总体CPU利用率
    // 空闲任务占用的时间比例 = 空闲率
    // CPU利用率 = 100% - 空闲率
}

实战经验：我一般会在AGV控制器的调试串口上，每隔5秒打印一次CPU利用率。正常情况应该在30%-60%之间。如果超过80%，就要考虑优化了。低于20%？嗯，说明你任务栈可能分配得太奢侈了。

三者的配合使用

这三个工具不是孤立的。我通常这样搭配：

  • 开发阶段：断言全开 + 栈溢出检测 + CPU统计，跑压力测试
  • 测试阶段：保留栈溢出检测，断言选择性开启
  • 发布阶段：关闭断言，保留CPU统计（用于远程监控）

你想想看，如果系统在客户现场突然卡死，你能通过远程日志看到「最后时刻CPU利用率飙升到95%，同时栈溢出触发」，定位问题就快多了。

一个小技巧：在断言触发时，除了打印信息，我还会把当前所有任务的栈使用情况一并dump出来。这样能立刻知道是哪个任务吃掉了太多栈空间。

好了，这三个工具讲完了。记住：调试不是靠猜，是靠数据。断言给你确定性，栈检测给你安全性，CPU统计给你可见性。三管齐下，AGV控制器才能跑得稳、跑得久。
