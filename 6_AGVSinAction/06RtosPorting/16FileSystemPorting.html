16 文件系统移植：FatFS文件系统集成、SD卡驱动、日志记录与配置存储

AGV控制器跑起来了，任务调度也稳了，但有个问题一直让我头疼——数据怎么存？

路径规划的参数、电机PID的系数、运行日志……这些总不能每次都烧固件吧？

嗯，这时候就需要文件系统上场了。说白了，就是给嵌入式设备装个“硬盘”，让它可以像电脑一样读写文件。

16.1 为什么选FatFS？

嵌入式文件系统有不少选择，但我个人习惯用FatFS。原因很简单：

  • 轻量：最小配置下ROM占用不到10KB，RAM更是只有几十字节
  • 标准兼容：FAT12/16/32全支持，拔下SD卡插电脑就能读
  • 硬件无关：它只负责文件系统的逻辑，底层读写由你实现

我在项目中遇到过用其他文件系统结果PC读不了的情况，调试起来特别麻烦。从那以后，只要涉及数据导出，我首选FatFS。

16.2 FatFS移植三步走

移植FatFS其实不复杂，核心就三步：

  1. 下载源码：从官网获取ff.c、ff.h、diskio.c、diskio.h
  2. 配置ffconf.h：裁剪功能，定义宏开关
  3. 实现底层接口：写diskio.c里的六个函数

我们重点说第三步。FatFS通过diskio.c与硬件交互，你需要实现这些函数：

函数 作用 我的经验
disk_initialize 初始化存储设备 记得加超时，有些劣质SD卡初始化很慢
disk_status 获取设备状态 返回0表示正常，非0表示异常
disk_read 读取扇区 注意对齐，有些SDIO控制器要求4字节对齐
disk_write 写入扇区 写之前检查写保护，别问我怎么知道的
disk_ioctl 控制命令 GET_SECTOR_COUNT必须实现，否则挂载失败
get_fattime 获取当前时间 没有RTC就返回固定值，但文件时间戳会不准

核心要点：disk_read和disk_write是性能关键。我建议用DMA方式传输，一次读多个扇区，效率能提升好几倍。

16.3 SD卡驱动：从SPI到SDIO

AGV控制器上，SD卡是最常用的存储介质。驱动方式有两种：

  • SPI模式：引脚少，速度慢（一般不超过20MHz），适合资源紧张的场景
  • SDIO模式：速度快（可达50MHz以上），但引脚多，驱动复杂

我个人建议：如果MCU有SDIO外设，优先用SDIO。AGV需要记录高频数据，SPI那点带宽真不够用。

SD卡驱动初始化流程大概是这样的：

// SD卡初始化伪代码
void SD_Init(void) {
    // 1. 上电延时，至少74个时钟周期
    delay_ms(10);
    
    // 2. 发送CMD0，进入空闲状态
    if (SD_SendCmd(CMD0, 0, 0x95) != 0x01) {
        error("SD卡无响应");
    }
    
    // 3. 发送CMD8，检查SD卡版本
    if (SD_SendCmd(CMD8, 0x1AA, 0x87) == 0x01) {
        // SD 2.0卡，继续初始化
        SD_SendCmd(CMD55, 0, 0);
        SD_SendCmd(ACMD41, 0x40000000, 0);
    } else {
        // SD 1.x或MMC卡，用老方式
    }
    
    // 4. 读取OCR，获取工作电压范围
    SD_SendCmd(CMD58, 0, 0);
    
    // 5. 设置块长度（通常为512字节）
    SD_SendCmd(CMD16, 512, 0);
}

注意：SD卡初始化时序非常严格。我曾经因为延时不够，折腾了两天才发现是上电后没等够74个时钟周期。嗯，这种坑踩过一次就记住了。

16.4 日志记录：别小看这个功能

AGV跑着跑着突然停了，你怎么办？

没有日志，你只能对着代码发呆。有了日志，你就能知道是电机堵转、传感器超时还是路径规划死循环。

我设计日志系统时，遵循几个原则：

  • 分级记录：DEBUG、INFO、WARN、ERROR，生产环境只记录WARN及以上
  • 循环写入：日志文件满了就覆盖最早的，别让日志撑爆SD卡
  • 时间戳：每条日志都带毫秒级时间，方便定位问题

代码实现很简单：

// 日志写入函数
void Log_Write(uint8_t level, const char *fmt, ...) {
    FIL fil;
    char buffer[256];
    va_list args;
    
    // 打开日志文件（追加模式）
    if (f_open(&fil, "0:/agv.log", FA_OPEN_ALWAYS | FA_WRITE) != FR_OK) {
        return;
    }
    
    // 定位到文件末尾
    f_lseek(&fil, f_size(&fil));
    
    // 格式化日志内容
    va_start(args, fmt);
    vsnprintf(buffer, sizeof(buffer), fmt, args);
    va_end(args);
    
    // 写入文件
    f_printf(&fil, "[%lu] %s\r\n", HAL_GetTick(), buffer);
    
    // 关闭文件
    f_close(&fil);
}

小技巧：频繁打开关闭文件会影响性能。我习惯在系统初始化时打开日志文件，运行时只写入不关闭，等系统停机前再统一关闭。但要注意异常断电可能丢失最后几条日志。

16.5 配置存储：让参数可调

AGV的配置参数很多：最大速度、加速度、PID系数、传感器阈值……

把这些参数写死在代码里？那每次调参都要重新编译烧录，太麻烦了。

我的做法是：

  1. 定义配置结构体：把所有参数打包成一个结构体
  2. 存储为二进制文件：直接读写结构体内存，效率高
  3. 提供默认值：如果配置文件损坏或不存在，使用代码里的默认值
// 配置结构体
typedef struct {
    uint16_t max_speed;        // 最大速度 mm/s
    uint16_t accel;            // 加速度 mm/s²
    float    pid_kp;           // PID比例系数
    float    pid_ki;           // PID积分系数
    float    pid_kd;           // PID微分系数
    uint8_t  sensor_threshold; // 传感器阈值
    uint16_t crc;              // 校验和
} AGV_Config_t;

// 读取配置
AGV_Config_t g_config;

void Config_Load(void) {
    FIL fil;
    UINT bytes_read;
    
    // 先加载默认值
    Config_LoadDefault();
    
    // 尝试读取配置文件
    if (f_open(&fil, "0:/config.bin", FA_READ) == FR_OK) {
        f_read(&fil, &g_config, sizeof(g_config), &bytes_read);
        f_close(&fil);
        
        // 校验CRC，防止文件损坏
        if (g_config.crc != Config_CalcCRC(&g_config)) {
            // CRC校验失败，使用默认值
            Config_LoadDefault();
        }
    }
}

重要：配置文件一定要加CRC校验。我遇到过SD卡文件系统损坏导致配置全乱的情况，加了CRC后至少能保证系统用默认值启动，不至于直接死机。

16.6 文件系统移植的避坑指南

做文件系统移植这些年，我踩过的坑不少，分享几个典型的：

  • 扇区大小不匹配：SD卡物理扇区是512字节，但有些Flash模拟的磁盘是4096字节。ffconf.h里的_MAX_SS要设置正确。
  • 长文件名支持：默认只支持8.3短文件名。要支持长文件名，需要在ffconf.h里开启_USE_LFN，并分配足够的缓冲区。
  • 多任务访问：RTOS下多个任务同时读写文件会冲突。我习惯加一个互斥锁，或者用消息队列串行化文件操作。
  • 异常断电：FatFS在写入时断电可能损坏文件系统。我建议用f_sync定期刷新缓存，或者使用支持日志的文件系统变体。

嗯，文件系统移植说难不难，说简单也不简单。关键是把底层驱动调稳了，上层应用就省心很多。

我的习惯：每次移植完文件系统，我都会做三个测试：1）反复挂载卸载100次；2）写入1MB数据然后读出校验；3）在写入过程中随机断电10次。这三个测试过了，基本就稳了。

文件系统移植完成后，AGV控制器才算真正有了“记忆”。参数可以调，日志可以查，数据可以导出——这才是工业级产品该有的样子。
