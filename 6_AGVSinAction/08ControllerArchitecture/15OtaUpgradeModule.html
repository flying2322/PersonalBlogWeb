15 OTA远程升级模块设计：固件分区设计、升级包校验（CRC/MD5）、断点续传、回滚机制

OTA远程升级，说白了就是让AGV在跑着的时候，能把固件给换了。这事儿看着简单，做起来坑不少。我最早做AGV那会儿，OTA升级失败导致小车变砖，维修工程师扛着笔记本满车间跑的场景，至今记忆犹新。

今天咱们就聊聊，怎么把OTA升级这个模块设计得靠谱。核心就四个东西：分区怎么划、校验怎么做、断了怎么续、坏了怎么回。

15.1 固件分区设计——别把所有鸡蛋放一个篮子里

AGV的MCU或者MPU，Flash空间通常有限。但再有限，也得给升级留出余地。我个人习惯的做法是：至少分三个区。

分区名称 作用 大小建议
Bootloader区 引导加载，负责校验和跳转 64KB~128KB
App主区（A区） 当前运行的应用固件 根据固件大小定
App备份区（B区） 升级时的备用固件 与A区等大
参数/配置区 存放校准数据、网络配置等 16KB~32KB
升级标志区 记录升级状态、版本号 4KB

你可能会问：为什么非要两个App区？

嗯，这里有个血泪教训。我曾经在一个项目里只留了一个App区，升级写到一半断电了。重启后Bootloader发现App校验失败，直接卡死在引导阶段。那台AGV当时正在仓库里执行任务，硬是让整个产线停了两个小时。

所以我现在坚持用A/B双区切换的方案。Bootloader永远只从标记为"有效"的区启动。升级时，把新固件写到备用区，校验通过后再切换启动标志。这样就算升级过程中断电，最多就是备用区数据坏了，主区还能正常跑。

核心原则：升级过程中，永远不要破坏当前正在运行的程序区。

15.2 升级包校验——CRC还是MD5？

校验这事儿，说白了就是确保你下载下来的固件，跟服务器上的一模一样。没人想在AGV上跑一个被篡改或者传错的文件。

我常用的校验方式有两种：

  • CRC32：速度快，硬件支持好。适合在MCU上做实时校验。比如每收到一个包，就累加计算CRC，最后跟服务器下发的CRC值比对。
  • MD5：安全性更高，但计算量稍大。适合在升级包下载完成后，做一次全量校验。

我的建议是：两者都用。

具体做法是这样的：

  1. 服务器生成固件包时，同时计算CRC32和MD5值，打包进升级包头部。
  2. AGV在接收每个数据包时，用硬件CRC模块做实时校验。一旦发现CRC不对，立刻请求重传这个包。
  3. 整个固件包下载完成后，再对完整文件做一次MD5校验。确保没有漏掉任何错误。

这里有个小技巧：CRC校验可以用MCU自带的硬件模块，基本不占CPU时间。MD5就得纯软件算了，我一般放在后台低优先级任务里跑，不影响AGV的正常控制。

避坑指南：我曾经遇到过CRC32碰撞的情况——两个不同的数据块算出来一样的CRC值。虽然概率极低，但在关键系统里，我建议加上MD5做双重保险。

15.3 断点续传——别让AGV从头再来

AGV在车间里跑，Wi-Fi信号时好时坏是常态。一个固件包动不动几MB甚至几十MB，下载到一半断连了，要是从头再来，那体验太糟糕了。

断点续传的核心就一句话：记录已经下载了哪些数据，下次从断点接着下。

具体实现上，我习惯把固件包分成固定大小的块（比如每块1KB）。然后维护一个位图（Bitmap），每一位代表一个块是否已经下载成功。

// 断点续传的位图示例
#define BLOCK_SIZE 1024        // 每块1KB
#define TOTAL_BLOCKS 4096      // 总共4096块，对应4MB固件

uint8_t bitmap[TOTAL_BLOCKS / 8];  // 位图，每个bit代表一个块

// 检查第n块是否已下载
bool is_block_downloaded(uint32_t block_index) {
    return (bitmap[block_index / 8] & (1 << (block_index % 8))) != 0;
}

// 标记第n块下载成功
void mark_block_downloaded(uint32_t block_index) {
    bitmap[block_index / 8] |= (1 << (block_index % 8));
}

每次连接恢复后，AGV把位图发给服务器。服务器就知道哪些块需要重发。这样就算断了十次八次，每次也只补传丢失的块，效率高得多。

注意：位图数据要定期写入Flash保存。我一般每下载完10个块就写一次。不然突然断电，位图丢了，又得从头开始。

15.4 回滚机制——给升级留条后路

升级失败怎么办？这是每个做OTA的人必须回答的问题。

我的方案是三级回滚：

  • 第一级：启动时校验失败，自动回滚。Bootloader在启动App前，先校验App区的CRC。如果校验失败，直接跳转到备份区启动。
  • 第二级：运行时异常，手动回滚。新固件跑起来后，如果AGV频繁死机、传感器异常、或者通信中断，维护人员可以通过远程指令强制回滚到旧版本。
  • 第三级：升级过程中断电，自动恢复。这个前面说过了，靠A/B分区机制保证。

回滚的触发条件，我一般这样设计：

// 回滚判断逻辑（伪代码）
if (bootloader_crc_check(pAppA) == FAIL) {
    // A区坏了，尝试从B区启动
    if (bootloader_crc_check(pAppB) == PASS) {
        switch_to_boot_from(pAppB);
    } else {
        // 两个区都坏了，进入恢复模式
        enter_recovery_mode();
    }
}

if (app_runtime_health_check() == ABNORMAL) {
    // 运行时健康检查失败，标记当前区为无效
    mark_current_partition_invalid();
    // 重启后Bootloader会自动切到另一个区
    system_reset();
}

这里有个细节：回滚之后，要不要自动再尝试升级？我的做法是不自动重试。回滚后把升级状态标记为"失败"，然后上报给服务器。由运维人员分析原因后，再决定是否重新下发升级指令。不然AGV反复升级、反复失败，那画面太美我不敢看。

我的经验：回滚机制不是万能的。如果新固件改了Flash布局或者参数结构，回滚后旧固件可能无法正确读取新格式的数据。所以升级前，一定要做好参数区的版本兼容性设计。

15.5 整体升级流程

把上面这些串起来，一个完整的OTA升级流程大概是这样的：

  1. AGV上报当前固件版本号给服务器。
  2. 服务器判断有新版本，下发升级包信息（大小、CRC、MD5、分块数）。
  3. AGV检查备用分区空间是否足够。不够则擦除备用区。
  4. AGV逐块下载固件数据，每块用CRC实时校验。下载进度记录在位图中。
  5. 下载过程中如果断连，重连后从断点继续。
  6. 全部下载完成后，对完整固件做MD5校验。
  7. 校验通过，将备用分区标记为"待激活"。
  8. AGV重启，Bootloader检测到待激活标志，将启动分区切换到备用区。
  9. 新固件启动后，做自检和健康检查。如果正常，将旧分区标记为备份区。
  10. 如果自检异常，触发回滚，切回旧固件。

你看，每一步都有校验，每一步都有兜底。这就是嵌入式系统该有的样子——宁可慢一点，不能错一次。

最后说一句：OTA升级模块写好了，能省掉你无数跑现场的时间。我当年要是早点把回滚机制做完善，也不至于大半夜被电话叫起来去仓库救砖。嗯，都是经验啊。
