12 调度系统与多车协同：交通管制

各位同学，今天我们来聊聊多车协同里最让人头疼、也最有趣的部分——交通管制。说实话，单台AGV跑起来不难，难的是几十台车在一个仓库里穿梭，还不撞车、不堵死。我最早做这个的时候，以为只要给每台车画条路就行，结果第一次联调就撞了……嗯，从那以后我再也不敢小看调度系统了。

12.1 交通管制的核心：区域锁与路径锁

多车协同的本质，说白了就是「谁先占，谁先用」。但怎么占、占多大范围，这里就有讲究了。

12.1.1 区域锁（Zone Lock）

区域锁是最直观的方式。我们把地图划分成一个个格子或区域，每台AGV进入前，先申请锁定这个区域。离开时释放。

关键点：区域锁的粒度决定了系统的并发效率。区域太大，车等得久；区域太小，锁管理开销大。

我在项目中遇到过一个问题：仓库里有个十字路口，我一开始把整个路口设为一个区域锁。结果A车从东往西，B车从南往北，明明不会撞，但因为锁了整个路口，B车只能干等。后来我把路口拆成四个象限锁，并发度直接翻倍。

区域锁的典型实现逻辑：

// 伪代码：区域锁申请
bool requestZoneLock(AGV_ID, ZoneID) {
    if (zoneLocks[ZoneID] == FREE) {
        zoneLocks[ZoneID] = LOCKED_BY(AGV_ID);
        return true;
    } else {
        // 加入等待队列
        waitQueue[ZoneID].push(AGV_ID);
        return false;
    }
}

void releaseZoneLock(AGV_ID, ZoneID) {
    zoneLocks[ZoneID] = FREE;
    // 唤醒下一个等待的AGV
    if (!waitQueue[ZoneID].empty()) {
        notify(waitQueue[ZoneID].pop());
    }
}

12.1.2 路径锁（Path Lock）

路径锁更精细一些。AGV不是锁一个区域，而是锁它即将行驶的一段路径。这段路径通常由多个路径段（Segment）组成。

你想想看，路径锁的好处是什么？它允许两辆车在同一个区域里「擦肩而过」，只要它们走的路径不重叠。这在窄通道场景下特别有用。

锁类型 粒度 并发度 实现复杂度 适用场景
区域锁 粗 低 低 简单环境、小规模
路径锁 细 高 中 复杂通道、高密度
混合锁 动态 最高 高 大型仓库、动态场景

我的建议：实际项目中，我习惯用混合策略。路口、窄道用路径锁，开阔区域用区域锁。这样既保证了安全性，又不会让调度器忙死。

12.2 多车避让策略

锁是预防机制，但总有意外。比如一台车故障停在路中间，后面的车怎么办？这时候就需要避让策略了。

12.2.1 常见的避让策略

  • 等待策略：最简单。前车不走，后车就等。适合短时间阻塞。
  • 绕行策略：后车重新规划路径，绕过障碍车。需要地图支持动态障碍物。
  • 倒车策略：后车倒车到最近的避让点，让前车先过。适合窄通道。
  • 优先级策略：根据任务紧急程度，低优先级车让高优先级车。

我曾经踩过一个坑：某次项目里，两台AGV在通道里面对面相遇了。我设计的策略是「谁先到谁先走」，结果两台车同时到达，互相等对方倒车……死锁了。后来我加了一条规则：任务紧急度高的车优先，紧急度相同则ID小的车倒车。这才解决问题。

12.2.2 死锁检测与恢复

多车系统里，死锁是绕不开的话题。我常用的死锁检测方法是「资源等待图」——每台车等哪些锁，锁被谁占着，画成图。如果图里有环，那就是死锁了。

注意：死锁检测不能太频繁，否则调度器CPU吃不住。我一般设置每200ms检测一次，或者当某台车等待超过5秒时触发检测。

死锁恢复的方法：

  1. 选择一个「牺牲者」，通常是任务最不紧急的那台车。
  2. 让牺牲者倒车到安全区域，释放它占用的所有锁。
  3. 其他车继续执行，牺牲者重新规划路径。

12.3 任务动态分配与负载均衡

调度系统不只是管交通，还得管「谁干什么活」。任务分配得好，整个车队效率就高；分配得不好，有的车忙死，有的车闲死。

12.3.1 任务分配策略

我个人习惯把任务分配分为两个层次：

  • 全局分配：调度中心根据所有车的状态，把新任务分配给最合适的车。
  • 局部调整：执行过程中，如果某台车故障或任务变更，动态调整任务归属。

常用的分配算法：

// 基于最短路径+负载均衡的任务分配
AGV_ID assignTask(Task task) {
    float bestScore = -INF;
    AGV_ID bestAGV = -1;
    
    for (auto &agv : allAGVs) {
        if (agv.isAvailable()) {
            float distance = calcDistance(agv.position, task.startPoint);
            float loadFactor = agv.getTaskQueueLength() / MAX_QUEUE_LENGTH;
            // 综合评分：距离越近越好，负载越轻越好
            float score = 1.0 / (distance + 1) * (1.0 - loadFactor * 0.3);
            if (score > bestScore) {
                bestScore = score;
                bestAGV = agv.id;
            }
        }
    }
    return bestAGV;
}

一个小技巧：评分公式里的权重系数（比如上面的0.3），我建议在项目初期设小一点，优先保证最短路径。等系统跑稳定了，再慢慢加大负载均衡的权重。这样不容易出现「为了均衡而绕远路」的尴尬情况。

12.3.2 负载均衡的实战要点

负载均衡不是简单的「谁闲给谁」。你想想看，如果一台车在仓库东边，你给它分配一个西边的任务，它光跑过去就要5分钟。这5分钟里，它既没干活，还占了路。

所以我的做法是：

  • 空间局部性优先：尽量把任务分配给离任务起点最近的车。
  • 时间窗口预测：预估每台车未来5-10分钟的空闲时间窗口，把任务塞进窗口里。
  • 动态调整阈值：当某台车的任务队列超过80%时，不再给它分配新任务。

这张图里，任务从队列出发，经过分配、管制、避让、死锁处理，最后到执行。执行结果反馈回来，又影响下一次分配。说白了，这是一个闭环系统。

核心总结：调度系统不是万能的，但没有调度系统是万万不能的。区域锁和路径锁是基础，避让策略是保障，任务分配是灵魂。三者缺一不可。
