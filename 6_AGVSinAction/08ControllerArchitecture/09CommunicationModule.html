9 通信模块设计：CAN总线协议、Modbus协议、TCP/UDP通信、ROS通信机制

通信模块，说白了就是AGV的“神经系统”。没有它，控制器再聪明也白搭。我做了这么多年AGV，见过太多因为通信问题导致整车趴窝的案例。今天咱们就把这块彻底聊透。

9.1 CAN总线协议：AGV的“脊梁骨”

CAN总线在AGV领域，地位不可撼动。为什么？因为它实时性好、抗干扰能力强、而且成本可控。我最早接触CAN是在一个重载AGV项目上，那车拉着几吨的货物在车间里跑，电机驱动器、传感器、IO模块全挂在CAN总线上。嗯，当时选型时也考虑过RS485，但后来发现CAN的多主通信机制实在太香了。

核心要点：CAN总线采用差分信号传输，两条线（CAN_H和CAN_L）绞在一起，抗共模干扰能力极强。这在电机频繁启停的AGV上，简直是救命稻草。

我个人习惯，在AGV上至少部署两条CAN总线：

  • 动力CAN（高速CAN，500kbps）：连接电机驱动器、转向控制器。要求实时性极高，数据量不大但必须准时。
  • 车身CAN（中速CAN，250kbps）：连接传感器、IO模块、灯光、喇叭等。数据量稍大，但对实时性要求没那么苛刻。

我曾经在一个项目里，把激光雷达的数据也丢到CAN总线上，结果发现数据量太大，导致电机控制指令延迟。后来果断把激光雷达挪到独立串口上，问题才解决。所以，千万别让非实时数据污染了实时总线。

CAN报文结构速览

字段 长度 说明
ID 11位（标准帧）或29位（扩展帧） 标识报文优先级，ID越小优先级越高
DLC 4位 数据长度，0~8字节
Data 0~8字节 实际数据

避坑指南：我曾经在ID分配上吃过亏。多个节点同时发送高优先级报文，导致总线冲突。后来我定了个规矩：电机控制指令ID设为0x100~0x1FF，传感器数据ID设为0x200~0x2FF，诊断信息ID设为0x300~0x3FF。这样优先级一目了然，再也没出过问题。

9.2 Modbus协议：老当益壮的“老兵”

Modbus协议，说实话，在AGV上用得不如CAN多。但如果你要对接PLC、变频器、或者一些老旧的传感器，Modbus几乎是绕不开的。我有个项目，客户指定要用西门子S7-1200做上位机，那AGV控制器就必须支持Modbus TCP。

Modbus有两种常见变体：

  • Modbus RTU（串口）：基于RS232/RS485，数据紧凑，适合长距离传输。波特率通常设为115200或9600。
  • Modbus TCP（以太网）：基于TCP/IP，配置简单，但实时性不如RTU。适合与上位机通信。

我个人建议，在AGV内部尽量少用Modbus。它的主从架构决定了从机不能主动上报数据，必须靠主机轮询。这在需要快速响应的场景下，效率很低。但如果你非要用它，记得把轮询周期控制在10ms以内，否则AGV的反应会像“老年痴呆”。

注意：Modbus RTU的报文里没有校验和？不，它用的是CRC16校验。我曾经遇到一个坑：某款国产传感器，CRC计算方式跟标准Modbus不一样，导致通信时好时坏。排查了整整两天，最后用逻辑分析仪抓波形才找到原因。所以，对接第三方设备时，一定要先验证CRC算法是否标准。

9.3 TCP/UDP通信：AGV的“远程大脑”

AGV不是孤岛。它需要跟调度系统、MES、甚至云端通信。这时候，TCP和UDP就派上用场了。

我一般这样区分使用场景：

  • TCP：用于任务下发、状态上报、日志传输。要求数据完整，不能丢包。比如调度系统给AGV发“去A点取货”的指令，必须确保AGV收到。
  • UDP：用于实时数据流，比如激光雷达点云、摄像头图像。丢几个包没关系，但延迟必须低。我曾经在一个项目中，用UDP传输激光雷达数据，延迟控制在2ms以内，效果非常好。

你想想看，如果调度系统用UDP下发任务指令，万一丢包了，AGV可能就停在原地不动了。所以，关键指令必须走TCP，实时数据可以走UDP。这个原则，我至今没变过。

经验之谈：在AGV上实现TCP通信时，一定要加心跳机制。我见过太多因为网线松动、交换机死机导致TCP连接断开，AGV却毫不知情的案例。心跳包每隔1秒发一次，连续3次没收到回复，就判定连接断开，AGV立即进入安全模式。

9.4 ROS通信机制：Topic/Service/Action

ROS在AGV领域越来越流行。它提供了三种通信机制，各有各的用途。我最早接触ROS是在一个科研项目上，后来发现它在工业AGV上也能大放异彩。

9.4.1 Topic：发布-订阅模式

Topic是ROS里最常用的通信方式。一个节点发布消息，多个节点可以同时订阅。比如，激光雷达节点发布/scan话题，导航节点和避障节点都可以订阅它。

我个人习惯，把高频数据（传感器、里程计、速度指令）都用Topic传输。因为它是异步的，发布者不用等订阅者处理完，效率极高。

// 发布者示例（C++）
ros::Publisher cmd_pub = nh.advertise<geometry_msgs::Twist>("/cmd_vel", 10);
geometry_msgs::Twist msg;
msg.linear.x = 0.5;
msg.angular.z = 0.2;
cmd_pub.publish(msg);

9.4.2 Service：请求-响应模式

Service适合那些需要立即得到结果的场景。比如，AGV调用一个服务来查询当前电池电量，或者请求一个路径规划结果。

我曾经在一个项目中，用Service来实现“AGV请求充电桩对接”。AGV发送请求，充电桩返回“允许对接”或“正在使用”。这种一问一答的模式，用Service再合适不过了。

// 服务端示例（C++）
bool chargeCallback(agv_srvs::Charge::Request &req, agv_srvs::Charge::Response &res) {
    if (charger_available) {
        res.success = true;
        res.message = "开始充电";
    } else {
        res.success = false;
        res.message = "充电桩被占用";
    }
    return true;
}

避坑指南：Service不能用于长时间运行的任务。如果充电过程需要10分钟，用Service会导致调用方一直阻塞。这时候，就该Action出场了。

9.4.3 Action：带反馈的任务执行

Action是ROS里最强大的通信机制。它支持任务下发、进度反馈、结果返回，甚至可以在任务执行过程中取消它。说白了，它就是Service的“升级版”。

在AGV上，Action的应用场景太多了：

  • 导航任务：下发目标点，实时反馈当前位置和状态，到达后返回结果。
  • 充电任务：下发充电指令，反馈充电进度（0%~100%），充满后返回。
  • 取货任务：下发取货指令，反馈机械臂状态，完成或失败都返回结果。
// Action客户端示例（C++）
actionlib::SimpleActionClient<move_base_msgs::MoveBaseAction> ac("move_base", true);
move_base_msgs::MoveBaseGoal goal;
goal.target_pose.header.frame_id = "map";
goal.target_pose.pose.position.x = 2.0;
goal.target_pose.pose.position.y = 1.0;
ac.sendGoal(goal);

// 等待结果
ac.waitForResult();
if (ac.getState() == actionlib::SimpleClientGoalState::SUCCEEDED) {
    ROS_INFO("AGV到达目标点");
} else {
    ROS_WARN("导航失败");
}

总结一下：Topic用于高频数据流，Service用于简单请求-响应，Action用于复杂任务执行。我在设计AGV控制器时，会这样分配：传感器数据→Topic，参数查询→Service，导航/充电/取货→Action。这个架构，我用了好几年，稳定可靠。
