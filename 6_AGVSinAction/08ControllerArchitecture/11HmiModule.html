11 人机交互模块设计：HMI界面设计、语音提示、状态指示灯、远程监控与调试接口

人机交互模块，说白了就是AGV跟人“说话”的窗口。你想想看，一台AGV在仓库里跑得再溜，如果操作员不知道它当前在想什么、下一步要干什么，那心里肯定没底。我个人习惯把HMI设计分成两个维度：一是现场操作员能直接看到的物理交互，二是远程工程师能调用的调试接口。

这一章，我们就来拆解这四个核心部分：HMI界面、语音提示、状态指示灯、远程监控与调试接口。

11.1 HMI界面设计：让操作员一眼看懂

HMI界面不是越花哨越好。我在项目中遇到过，有的团队把3D渲染的AGV模型放上去，结果刷新率跟不上，操作员点一下按钮要等两秒才有反应。嗯，这其实是个坑。

我建议HMI界面遵循“三秒原则”：操作员扫一眼，三秒内必须看懂AGV的状态。核心信息就这几项：

  • 当前运行模式：自动/手动/调试/急停
  • 电池电量与续航：百分比 + 预估剩余分钟数
  • 当前任务状态：空闲/执行中/任务完成/异常
  • 位置与路径：地图上实时显示AGV位置
  • 故障报警：红色高亮显示，带故障码

核心原则：HMI上的每一个元素，都必须有明确的“存在理由”。如果某个数据显示了但操作员从来不看，那就删掉它。

我常用的HMI框架是分层设计：

  1. 顶层：全局状态栏（电量、模式、报警）
  2. 中间层：地图与路径可视化
  3. 底层：操作按钮与任务列表

举个例子，一个典型的HMI界面布局：

+--------------------------------------------------+
| [自动模式] 电量: 78%  续航: 4h20m   [报警: 无]    |
+--------------------------------------------------+
|                                                    |
|          [AGV实时位置地图]                          |
|          当前任务: 从A点取货到B点                   |
|          路径: A → C → D → B                       |
|                                                    |
+--------------------------------------------------+
| [暂停] [继续] [急停] [手动控制] [任务列表]         |
+--------------------------------------------------+

这里要注意，急停按钮必须物理独立，不能只靠软件实现。我曾经见过一个项目，急停按钮放在触摸屏上，结果触摸屏死机了，AGV停不下来……那场面，你懂的。

11.2 语音提示：不是所有场景都需要看屏幕

操作员在AGV旁边工作时，很多时候眼睛是盯着货物的，没空看屏幕。这时候语音提示就派上用场了。

我建议语音提示分三级：

级别 场景 示例
信息级 正常状态切换 "任务已接收，正在前往A点"
警告级 潜在风险 "电量低于20%，请安排充电"
紧急级 立即处理 "前方障碍物，已紧急制动"

避坑指南：我曾经在项目里把所有语音都做成女声，结果在嘈杂的仓库里根本听不清。后来改用男声+女声混合，信息级用女声，紧急级用男声，辨识度明显提升。

语音提示的实现方式，我推荐用离线语音合成芯片，比如SYN6288或者科大讯飞的离线方案。为什么不用在线？你想想看，AGV在仓库里网络信号可能不稳定，万一语音播报到一半断网了，那不就尴尬了？

11.3 状态指示灯：最简单的交互往往最可靠

状态指示灯是AGV最古老的交互方式，但也是最可靠的。我见过很多AGV，HMI屏幕坏了，语音喇叭坏了，但指示灯从来没坏过。

我常用的指示灯定义：

  • 绿色常亮：正常运行，空闲状态
  • 绿色闪烁：正在执行任务
  • 黄色常亮：等待指令或充电中
  • 红色常亮：故障，需要人工干预
  • 红色闪烁：急停或严重故障
  • 蓝色常亮：手动模式

这里有个细节：指示灯的颜色选择要考虑色盲人群。红绿色盲在人群中比例不低，所以我建议在指示灯旁边加一个小标签，或者用闪烁频率来辅助区分。

注意：指示灯驱动电路一定要加限流电阻，并且用PWM控制亮度。我见过一个项目，LED直接接GPIO，结果电流过大把MCU的引脚烧了。嗯，这种低级错误其实挺常见的。

11.4 远程监控与调试接口：工程师的“远程手”

AGV一旦部署到现场，工程师不可能每次都跑到车旁边去调试。远程监控和调试接口，就是工程师的“远程手”。

我建议远程接口包含以下功能：

  1. 实时状态上报：位置、速度、电量、任务进度，每100ms上报一次
  2. 日志远程拉取：支持按时间范围拉取系统日志
  3. 远程命令下发：暂停、恢复、取消任务、切换模式
  4. 参数在线修改：比如修改PID参数、调整速度限制
  5. 远程桌面/SSH：直接登录AGV的工控机

通信协议我推荐用MQTT + Protobuf。MQTT轻量级，支持QoS，适合物联网场景。Protobuf序列化效率高，带宽占用小。

一个典型的状态上报数据格式：

message AGVStatus {
    string agv_id = 1;
    float battery_percent = 2;
    float speed_mps = 3;
    float pos_x = 4;
    float pos_y = 5;
    float heading_deg = 6;
    enum Mode { IDLE = 0; RUNNING = 1; CHARGING = 2; ERROR = 3; }
    Mode mode = 7;
    string current_task_id = 8;
    uint32 error_code = 9;
    uint64 timestamp_ms = 10;
}

安全第一：远程调试接口必须做身份认证和权限控制。我见过一个项目，远程接口没有任何认证，结果有人用手机APP就能控制AGV……这要是被恶意攻击，后果不堪设想。

我个人习惯在远程接口上加一个“心跳超时”机制：如果AGV超过5秒没有上报心跳，远程监控系统就自动报警。这样即使AGV死机了，工程师也能第一时间知道。

11.5 知识体系总览

下面这张图，把本章的核心内容串起来了：

你看，人机交互模块其实就这四个方面。HMI负责“看”，语音负责“听”，指示灯负责“扫一眼就知道”，远程接口负责“远程管”。四者配合好了，AGV才能真正做到“好用、好管、好修”。

我个人经验是，很多团队把精力都花在HMI界面的美化上，却忽略了语音和指示灯这些“低成本高回报”的交互方式。其实，操作员最需要的不是炫酷的动画，而是“一眼就知道AGV现在怎么了”。

最后一个小建议：在设计阶段，就把人机交互模块的测试用例写出来。比如“当电量低于20%时，指示灯变黄、语音播报、HMI显示充电建议”。这样开发的时候就不会漏掉任何一个交互细节。
