18 AGV控制器的状态机设计：空闲态、运行态、充电态、异常态、状态转换条件与动作

状态机这东西，说白了就是AGV的“大脑决策器”。

我刚开始做AGV那会儿，总觉得状态机不就是几个if-else嘛，有啥好设计的？结果第一次上路测试，车子在充电桩前反复横跳，差点把电池搞废了。嗯，从那以后我再也不敢小看状态机了。

今天咱们就聊聊AGV控制器的核心——状态机。我习惯把AGV的状态归纳为四大类：空闲态、运行态、充电态、异常态。你想想看，AGV一辈子就在这几个状态里转悠，设计得好，它就是个靠谱的搬运工；设计得烂，它就是台“神经病”机器。

核心观点：状态机不是简单的状态罗列，而是状态之间的“交通规则”。规则定好了，AGV才不会乱跑、乱充、乱报错。

18.1 四大核心状态定义

先给这四个状态画个像，咱们心里有个底。

状态名称 状态标识 典型场景 核心特征
空闲态 IDLE 待命、等待任务 电机抱闸、通信待机、低功耗
运行态 RUNNING 执行导航、搬运任务 电机运转、传感器全开、实时控制
充电态 CHARGING 自动回充、手动充电 电池管理、充电接触器闭合、限流
异常态 ERROR 故障、急停、保护 停止运动、上报故障、等待恢复

我在项目中遇到过一种情况：某款AGV在低电量时直接进入异常态，结果卡在通道中间，后面的车全堵死了。后来我改成先尝试进入充电态，实在充不上才报异常。你看，状态顺序也很重要。

18.2 状态转换条件与动作

状态转换，说白了就是“什么情况下，AGV该干什么事”。我习惯用一张图把逻辑理清楚，然后再写代码。

这张图我画了好几个版本才定下来。你看，异常态可以回到空闲态，但绝对不能直接回到运行态。为什么？因为故障恢复后必须重新确认安全，这是底线。

18.3 状态转换条件详解

咱们把每个转换条件拆开揉碎了讲。我习惯用表格来整理，这样写代码时直接对着抄就行。

源状态 目标状态 转换条件 转换动作
空闲态 运行态 收到调度任务 & 电量充足 & 无故障 唤醒电机、加载路径、开启传感器
运行态 空闲态 任务完成 & 到达目标点 停止电机、释放路径、进入低功耗
空闲态 充电态 电量低于阈值(如20%) 或 收到充电指令 导航至充电桩、对接充电触点
充电态 空闲态 电量充满(如95%) 或 收到停止充电指令 断开充电接触器、退出充电模式
任意态 异常态 急停按下、碰撞检测、电机过流、通信超时等 紧急制动、记录故障码、上报调度
异常态 空闲态 故障排除 & 手动复位 & 自检通过 清除故障码、恢复默认参数

避坑指南：我曾经在异常态转换时忘记做“自检通过”这个条件，结果操作员一按复位，AGV直接冲出去撞墙了。从那以后，我规定异常态恢复必须经过完整的自检流程，少一步都不行。

18.4 状态机代码实现框架

理论讲完了，咱们看看代码怎么写。我习惯用枚举+状态表的方式，清晰又好维护。

// 状态枚举定义
typedef enum {
    STATE_IDLE     = 0,
    STATE_RUNNING  = 1,
    STATE_CHARGING = 2,
    STATE_ERROR    = 3
} agv_state_t;

// 状态转换表结构
typedef struct {
    agv_state_t  src_state;
    agv_state_t  dst_state;
    uint8_t      (*condition)(void);  // 条件函数指针
    void         (*action)(void);     // 动作函数指针
} state_transition_t;

// 转换表实例
state_transition_t g_trans_table[] = {
    {STATE_IDLE,    STATE_RUNNING,  is_task_ready,     action_start_task},
    {STATE_RUNNING, STATE_IDLE,    is_task_done,      action_stop_task},
    {STATE_IDLE,    STATE_CHARGING, is_battery_low,   action_goto_charge},
    {STATE_CHARGING, STATE_IDLE,   is_battery_full,   action_stop_charge},
    {STATE_ANY,     STATE_ERROR,   is_fault_detected, action_emergency_stop},
    {STATE_ERROR,   STATE_IDLE,    is_fault_cleared,  action_reset_system}
};

// 状态机主循环
void agv_state_machine_run(void) {
    for (int i = 0; i < sizeof(g_trans_table)/sizeof(g_trans_table[0]); i++) {
        state_transition_t *t = &g_trans_table[i];
        if (current_state == t->src_state || t->src_state == STATE_ANY) {
            if (t->condition()) {
                t->action();
                current_state = t->dst_state;
                printf("状态转换: %d -> %d\n", t->src_state, t->dst_state);
                break;
            }
        }
    }
}

这段代码我用了好多年，核心思想就一个：把状态转换逻辑和数据分离。你想想看，如果以后要加一个新状态，比如“待充电态”，只需要在转换表里加一行，主循环完全不用动。

个人经验：我建议把条件函数和动作函数都做成弱耦合的模块。比如条件函数只返回true/false，动作函数只执行具体操作。这样调试的时候，你可以单独测试每个条件，不用跑整个状态机。

18.5 状态机设计中的常见陷阱

做状态机设计，有几个坑我踩过，你们注意避开。

  • 状态爆炸：别把每个子动作都搞成一个状态。比如“左转”、“右转”这些，应该归到运行态下的子状态，而不是顶层状态。
  • 转换死锁：两个状态互相转换，比如空闲->充电->空闲->充电，循环不停。我一般会加一个“转换次数计数器”，超过阈值就强制进异常态。
  • 遗漏异常处理：每个状态都要考虑“如果这时候出故障怎么办”。比如充电态时通信断了，是继续充还是报异常？我建议直接报异常，安全第一。
  • 状态持久化：AGV断电重启后，状态应该恢复成空闲态，而不是记住断电前的状态。我曾经遇到过重启后直接进入运行态，结果车子自己跑了的尴尬事。

嗯，状态机设计就聊到这儿。说白了，状态机就是AGV的“行为准则”，定好了规矩，车子才能乖乖听话。你们在实际项目中，一定要把状态转换条件想清楚，尤其是异常处理路径，宁可多写几个条件，也别漏掉。
