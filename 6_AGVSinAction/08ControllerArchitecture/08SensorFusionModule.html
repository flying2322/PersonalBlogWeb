8 传感器融合模块设计：卡尔曼滤波（KF）、扩展卡尔曼滤波（EKF）、多传感器数据对齐与时间戳同步

各位同学，今天我们来聊聊AGV控制器里最核心、也最“烧脑”的一个模块——传感器融合。说实话，我做了这么多年AGV，见过太多因为传感器数据“打架”导致车子撞墙、定位漂移的案例。说白了，单个传感器都有它的脾气：激光雷达怕灰尘，IMU会漂，轮式里程计打滑就废了。我们得想办法把它们“揉”在一起，取长补短。

这一章，我会从最基础的卡尔曼滤波讲起，再到它的升级版EKF，最后聊聊那个经常被忽略、但坑最多的数据对齐问题。嗯，咱们开始吧。

8.1 为什么需要传感器融合？

先问大家一个问题：你开车的时候，是只看后视镜，还是只看仪表盘？肯定都不是，你得综合看。AGV也一样。

我个人的习惯是，把传感器分成两类：

  • 绝对传感器：比如激光雷达、UWB、GPS。它们能告诉你“我在哪里”，但更新频率低，还容易受干扰。
  • 相对传感器：比如IMU、轮式里程计。它们更新快，能告诉你“我动了多少”，但误差会随时间累积。

融合的目的，就是用绝对传感器去“校准”相对传感器的累积误差，同时用相对传感器填补绝对传感器的更新间隙。说白了，就是让它们互相兜底。

核心思想：传感器融合不是简单的“取平均”，而是基于各自的不确定性（协方差）进行加权最优估计。

8.2 卡尔曼滤波（KF）—— 线性系统的“黄金标准”

卡尔曼滤波，我愿称之为“控制界的瑞士军刀”。它假设系统是线性的，噪声是高斯分布的。虽然现实世界很少完美线性，但很多场景下，它已经足够好用。

KF的核心就两个步骤，像个循环：

  1. 预测（Predict）：根据上一时刻的状态和控制输入，猜一下当前状态。
  2. 更新（Update）：用当前传感器的观测值，修正这个猜测。

我记得第一次在AGV上跑KF时，看着滤波后的轨迹从“毛刺”变成“丝滑”，那种感觉真的很爽。下面是一个简化的KF实现，用于一维位置估计：

// 简化的一维卡尔曼滤波
typedef struct {
    float x;      // 状态：位置
    float P;      // 状态协方差
    float Q;      // 过程噪声协方差
    float R;      // 观测噪声协方差
} KalmanFilter_t;

void KalmanFilter_Predict(KalmanFilter_t *kf, float u, float dt) {
    // 预测状态：x = x + u * dt (假设速度控制)
    kf->x += u * dt;
    // 预测协方差：P = P + Q
    kf->P += kf->Q;
}

void KalmanFilter_Update(KalmanFilter_t *kf, float z) {
    // 计算卡尔曼增益
    float K = kf->P / (kf->P + kf->R);
    // 更新状态：x = x + K * (z - x)
    kf->x += K * (z - kf->x);
    // 更新协方差：P = (1 - K) * P
    kf->P = (1 - K) * kf->P;
}

避坑指南：我曾经在一个项目中，Q和R参数调了整整两天。Q设太大，滤波结果跟着传感器噪声乱跳；Q设太小，又跟不上真实变化。我的经验是：先让系统跑起来，记录一段数据，然后离线调参，最后再固化到代码里。

8.3 扩展卡尔曼滤波（EKF）—— 对付非线性问题

现实中的AGV，哪有那么多线性系统？比如，激光雷达的观测模型是距离和角度，这明显是非线性的。这时候，EKF就登场了。

EKF的原理很简单：把非线性函数在当前估计点附近做一阶泰勒展开（也就是求雅可比矩阵），然后套用KF的框架。说白了，就是用切线去近似曲线。

你想想看，如果系统是非线性的，直接用KF会怎样？结果就是状态估计会严重偏离真实值，甚至发散。我见过一个项目，工程师直接用KF处理IMU的欧拉角，结果角度一超过30度，滤波就崩了。后来换成EKF，问题迎刃而解。

EKF的流程和KF几乎一样，只是多了个雅可比矩阵的计算：

// EKF 更新步骤中的雅可比矩阵示例（简化）
// 假设观测模型：z = atan2(y, x)  (激光雷达测角)
// 雅可比矩阵 H 对状态 [x, y] 的偏导：
// H[0][0] = -y / (x^2 + y^2)
// H[0][1] =  x / (x^2 + y^2)

void EKF_ComputeJacobian(float x, float y, float H[][2]) {
    float denom = x*x + y*y;
    if (denom < 0.0001f) denom = 0.0001f; // 防止除零
    H[0][0] = -y / denom;
    H[0][1] =  x / denom;
}

注意：EKF的雅可比矩阵计算非常容易出错。我建议你在仿真环境里先用数值方法（比如有限差分）验证一下解析推导的结果。我曾经因为一个符号写反，让AGV在仿真里原地转圈，排查了三个小时。

8.4 多传感器数据对齐与时间戳同步

这部分，我觉得是传感器融合里最“脏”的活，但也是最重要的。你想想看，激光雷达的数据是10Hz，IMU是100Hz，轮式里程计是50Hz。如果时间戳不对齐，你拿10Hz的数据去修正100Hz的预测，结果就是“牛头不对马嘴”。

我个人的经验是，必须建立一个统一的时间基准。通常的做法是：

  1. 硬件同步：如果硬件支持，用PPS（秒脉冲）信号同步所有传感器的时钟。这是最理想的方式。
  2. 软件插值：如果硬件不支持，那就用软件方法。比如，IMU数据频率高，我们可以把激光雷达的数据通过时间戳插值到IMU的时间轴上。

下面是一个常用的时间戳对齐策略：

传感器 频率 对齐方式
激光雷达 10 Hz 作为“主传感器”，触发EKF更新
IMU 100 Hz 作为“预测驱动”，每次新数据都做预测
轮式里程计 50 Hz 与IMU时间戳对齐，作为预测的辅助输入

具体实现时，我会维护一个“传感器数据队列”，每个数据包都带有硬件时间戳。EKF的预测步骤由IMU数据触发，而更新步骤则由激光雷达数据触发。当激光雷达数据到来时，我会从队列里取出时间戳最接近的IMU数据，然后执行更新。

核心原则：永远不要假设传感器数据是同步到达的。每个数据包都必须携带时间戳，并且融合算法必须能处理“乱序”和“延迟”的数据。

8.6 总结与个人心得

传感器融合这块，说白了就是“用数学把不确定性管起来”。KF和EKF是基础工具，但真正决定系统好坏的，往往是那些“看不见”的细节：时间戳对不对齐？协方差矩阵初值设得合不合理？雅可比矩阵算没算对？

我建议初学者，先在一个简单的仿真环境里把KF跑通，再逐步加入EKF和非线性模型。等你在仿真里把坑都踩一遍了，再上真车。这样能省下不少调试时间。

最后，记住一句话：没有完美的传感器，只有好的融合算法。
