10 安全与异常处理模块设计：急停逻辑、碰撞检测与避障、低电量自动回充、故障诊断与日志记录

做AGV控制器这么多年，我越来越觉得安全模块才是整个系统的灵魂。你想想看，导航再精准、调度再高效，一旦出了安全事故，前面所有的努力都白费了。今天我们就来聊聊这个“保命”的模块——安全与异常处理。

说白了，安全模块就是AGV的“本能反应”。它不需要经过复杂的路径规划，也不需要等待调度指令。一旦检测到危险，必须立刻、马上做出响应。我个人习惯把安全模块分成四个层次：急停逻辑、碰撞检测与避障、低电量自动回充、故障诊断与日志记录。咱们一个一个来看。

核心原则：安全模块必须独立于主控逻辑运行。我曾经见过一个项目，把急停信号直接接到主控芯片的GPIO上，结果主控死机了，急停也失效了。这是大忌！

10.1 急停逻辑：最后一道防线

急停按钮，是AGV上最不起眼但最重要的零件。它必须做到“按下即停，绝不犹豫”。

急停逻辑的设计，我总结了三个关键点：

  • 硬件直连：急停信号不经过任何处理器，直接切断电机驱动器的使能信号。这样即使主控芯片挂了，急停依然有效。
  • 双通道冗余：对于高安全等级（如SIL3）的AGV，急停回路必须采用双通道设计。两个通道独立检测，任何一个触发都立即停车。
  • 手动复位：急停触发后，必须由人工手动旋转复位按钮才能解除。这是为了防止误触后AGV突然启动伤人。

嗯，这里要注意一个细节：急停后的制动距离。我曾经在测试一款重载AGV时，发现急停后车子还滑行了将近半米。后来加了电磁制动器，才把距离控制在10厘米以内。所以，急停逻辑不仅要“停”，还要“停得住”。

避坑指南：我曾经遇到过急停按钮被误碰的情况。后来我们在软件里加了一个“急停确认”机制——急停触发后，必须等待3秒才能复位。这3秒足够操作员反应过来，确认是否真的安全了。

10.2 碰撞检测与避障：主动防御

急停是被动的，碰撞检测才是主动的。AGV的碰撞检测，我一般分三级：

级别 传感器 作用距离 响应动作
一级（远距离） 激光雷达、3D相机 5-20米 减速、重新规划路径
二级（中距离） 超声波、红外 0.5-3米 急停、等待障碍物移开
三级（近距离） 碰撞条、触边传感器 0-0.3米 立即急停、上报故障

你看，三级检测是层层递进的。激光雷达负责“看远”，超声波负责“看近”，碰撞条则是最后的“肉盾”。我个人习惯把碰撞条设计成“常闭”信号——一旦被撞开，回路断开，立即触发急停。这样即使线断了，也能触发保护。

避障算法方面，我推荐使用动态窗口法（DWA）。它能在保证安全的前提下，找到一条平滑的绕障路径。代码实现大致如下：

// 动态窗口法核心逻辑（伪代码）
void dwa_plan(robot_state_t *state, obstacle_list_t *obs) {
    // 1. 生成速度采样窗口
    velocity_window_t window = calc_velocity_window(state);
    
    // 2. 对每个采样速度进行轨迹预测
    for (int i = 0; i < window.num_samples; i++) {
        trajectory_t traj = predict_trajectory(state, window.samples[i]);
        
        // 3. 评估轨迹：安全性、速度、朝向
        float cost = evaluate_trajectory(traj, obs, state->goal);
        
        // 4. 选择最优轨迹
        if (cost < best_cost) {
            best_cost = cost;
            best_traj = traj;
        }
    }
    
    // 5. 执行最优轨迹
    execute_trajectory(best_traj);
}

为什么选DWA？因为它计算量小，实时性好。在嵌入式平台上，几百微秒就能算完一轮。你想想看，AGV以1m/s的速度行驶，每100ms就要重新规划一次路径。DWA完全扛得住。

注意：碰撞检测不能只依赖一种传感器。激光雷达在玻璃、镜面面前会失效，超声波在吸音材料面前会衰减。多传感器融合才是王道。我一般用卡尔曼滤波把激光和超声波的数据融合在一起，效果还不错。

10.3 低电量自动回充：别让AGV“饿死”在路上

低电量回充，听起来简单，做起来坑不少。核心逻辑就一句话：在电量耗尽之前，安全地回到充电站。

我设计的回充策略是这样的：

  1. 三级电量预警：
    • 电量 > 30%：正常作业
    • 电量 15%-30%：提示回充，但可继续执行当前任务
    • 电量 < 15%：强制回充，中断所有任务
  2. 回充路径规划：系统会预留一条“绿色通道”，确保回充路径上没有任何障碍物。如果通道被堵，AGV会原地等待并报警。
  3. 对接精度：充电桩的对接，我要求定位精度在±5mm以内。一般用激光雷达+红外引导的组合方式。

这里有个血泪教训。我曾经遇到过AGV在回充途中电量耗尽，直接瘫在通道中间，堵死了后面所有车。后来我加了一个“应急电源”设计——当电量低于5%时，AGV会启动一个独立的备用电池，只够它再走10米。这10米，足够它挪到路边或者充电桩旁边了。

小技巧：电池的SOC（荷电状态）估算，不要只看电压。锂电池的电压在放电后期会急剧下降，容易误判。我习惯用“安时积分法+开路电压校正”的组合方式，精度能到±2%。

10.4 故障诊断与日志记录：事后诸葛亮也得当

故障诊断，说白了就是“出了事能查清楚”。我见过太多AGV项目，出了问题只能靠工程师现场连串口看log，效率极低。

一个好的故障诊断系统，应该具备三个能力：

  • 实时监控：关键参数（电机电流、电池电压、温度、通信状态）每100ms记录一次。
  • 故障分级：
    • 一级（致命）：电机堵转、电池过热、通信中断 → 立即停车
    • 二级（严重）：传感器异常、定位偏差过大 → 减速并报警
    • 三级（警告）：电量偏低、轮胎磨损 → 记录并提示
  • 日志存储：采用环形缓冲区，保留最近24小时的数据。掉电不丢失。

日志记录的格式，我推荐用结构化日志。别再用printf乱打了，用JSON或者Protobuf格式，方便后期分析。举个例子：

{
    "timestamp": 1712345678.123,
    "module": "motor_left",
    "level": "ERROR",
    "code": 0x12,
    "message": "Motor stall detected",
    "data": {
        "current": 12.5,
        "speed": 0,
        "temperature": 85
    }
}

你看，这种日志一目了然。时间、模块、等级、错误码、上下文数据，全都有。出了问题，直接扔到数据分析平台里，几分钟就能定位根因。

我的习惯：每个故障码都对应一个文档链接。工程师在现场用手机扫一下二维码，就能看到详细的故障处理步骤。这比翻手册快多了。
