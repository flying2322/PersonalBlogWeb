19 代码规范与单元测试：命名规范、注释规范、Google Test框架、Mock测试与覆盖率

说实话，代码规范这件事，我年轻的时候也觉得是「形式主义」。那时候觉得，代码能跑就行，管它命名好不好看？直到有一次，我接手了一个AGV项目，前任工程师离职了，留下了一堆变量名叫 a、b、temp1、temp2 的代码。我花了整整两周才理清楚一个电机控制模块的逻辑。嗯，从那以后，我再也不敢小看代码规范了。

今天我们就来聊聊，在AGV控制器开发中，怎么把代码写得既漂亮又可靠。说白了，就是两件事：让人看得懂，和让机器测得过。

命名规范：名字起得好，Bug少一半

我个人习惯，命名要遵循「自文档化」原则。什么意思？就是看名字就知道它干嘛的，不需要再翻注释。

变量命名

  • 局部变量：小驼峰，比如 motorSpeed、batteryVoltage
  • 全局变量：加前缀 g_，比如 g_systemState
  • 静态变量：加前缀 s_，比如 s_instanceCount
  • 常量：全大写加下划线，比如 MAX_WHEEL_SPEED

函数命名

  • 动作型函数：动词+名词，比如 calculatePath()、stopMotor()
  • 查询型函数：用 get 或 is 开头，比如 getBatteryLevel()、isObstacleDetected()
  • 回调函数：加 on 前缀，比如 onOdometryUpdate()
避坑指南：我曾经见过一个项目，变量名叫 data、data1、data2……你想想看，三个月后你自己都分不清哪个是哪个。所以，宁可名字长一点，也不要模糊。

注释规范：写给人看的，不是写给编译器看的

注释这件事，我有个原则：注释应该解释「为什么」，而不是「是什么」。代码本身已经说明了「是什么」，你再写一遍就是废话。

文件头注释

/**
 * @file motor_controller.cpp
 * @brief AGV电机控制模块，负责速度闭环与电流限幅
 * @author Zhang San
 * @date 2024-01-15
 */

函数注释

/**
 * @brief 计算AGV从当前位置到目标点的路径
 * @param start 起始坐标
 * @param goal 目标坐标
 * @param map 环境地图
 * @return 路径点列表，若无法到达则返回空列表
 * @note 使用A*算法，启发函数采用欧几里得距离
 */
std::vector<Point> planPath(const Point& start, const Point& goal, const Map& map);

行内注释

行内注释要少而精。我只在以下情况加注释：

  • 算法有特殊处理（比如边界条件）
  • 代码有历史原因（比如「这里先这样写，后续要优化」）
  • 有潜在的陷阱（比如「这个函数不是线程安全的」）
我的小技巧：如果你发现需要写一大段注释来解释一段代码，那说明这段代码本身太复杂了。不如重构它。

Google Test框架：让测试成为习惯

在AGV开发中，我最怕的就是「改了一行代码，整个系统跑偏了」。Google Test（简称GTest）就是来解决这个问题的。它让单元测试变得简单、高效。

基本用法

#include <gtest/gtest.h>

// 测试电机速度计算
TEST(MotorTest, SpeedCalculation) {
    MotorController motor;
    motor.setTargetSpeed(1.5);  // 目标速度 1.5 m/s
    motor.update(0.1);          // 模拟 100ms 控制周期
    
    EXPECT_NEAR(motor.getCurrentSpeed(), 1.5, 0.01);
    // 预期速度接近 1.5，误差不超过 0.01
}

// 测试急停功能
TEST(MotorTest, EmergencyStop) {
    MotorController motor;
    motor.setTargetSpeed(2.0);
    motor.emergencyStop();
    
    EXPECT_EQ(motor.getCurrentSpeed(), 0.0);
    EXPECT_TRUE(motor.isStopped());
}

测试夹具（Test Fixture）

当多个测试需要相同的初始化时，用 SetUp 和 TearDown：

class PathPlannerTest : public ::testing::Test {
protected:
    void SetUp() override {
        planner = new PathPlanner();
        map.loadFromFile("test_map.yaml");
    }
    
    void TearDown() override {
        delete planner;
    }
    
    PathPlanner* planner;
    Map map;
};

TEST_F(PathPlannerTest, SimplePath) {
    auto path = planner->planPath({0, 0}, {10, 10}, map);
    EXPECT_FALSE(path.empty());
    EXPECT_EQ(path.back(), Point(10, 10));
}
经验之谈：我在项目中遇到过，测试夹具里忘了清理动态内存，结果内存泄漏导致测试跑着跑着就崩了。所以，记得在 TearDown 里释放资源。

Mock测试：隔离依赖，专注逻辑

AGV系统里，很多模块依赖硬件。比如路径规划依赖激光雷达数据，但你总不能每次跑测试都搬个激光雷达吧？这时候就需要 Mock 了。

Google Mock 是 GTest 的搭档，专门用来模拟那些「不好测」的依赖。

Mock 示例

// 假设有一个 Lidar 接口
class LidarInterface {
public:
    virtual ~LidarInterface() = default;
    virtual std::vector<Point> scan() = 0;
};

// 创建 Mock 类
class MockLidar : public LidarInterface {
public:
    MOCK_METHOD(std::vector<Point>, scan, (), (override));
};

// 测试路径规划在遇到障碍物时的行为
TEST(PathPlannerTest, AvoidObstacle) {
    MockLidar mockLidar;
    PathPlanner planner(&mockLidar);
    
    // 模拟激光雷达返回障碍物数据
    std::vector<Point> obstacleData = {{5, 5}, {5, 6}, {6, 5}};
    EXPECT_CALL(mockLidar, scan())
        .WillOnce(::testing::Return(obstacleData));
    
    auto path = planner.planPath({0, 0}, {10, 10});
    // 验证路径绕过了障碍物
    EXPECT_TRUE(pathDoesNotIntersect(path, obstacleData));
}
注意：Mock 测试容易犯的一个错误是「过度模拟」。你想想看，如果所有东西都 Mock 了，那测试就变成了「自己测自己」，失去了意义。我的建议是：只 Mock 外部依赖（硬件、网络、文件系统），核心逻辑不要 Mock。

覆盖率：不是越高越好，但太低肯定不行

覆盖率是个双刃剑。我见过团队把覆盖率目标定到 90%，结果大家为了凑覆盖率，写了一堆「测了等于没测」的测试用例。也见过覆盖率只有 20% 的项目，一上线就出 Bug。

常用的覆盖率指标

指标 含义 AGV开发中的建议
行覆盖率 代码中有多少行被执行过 核心模块 ≥ 80%，非核心 ≥ 50%
分支覆盖率 if/else、switch 等分支是否都覆盖 安全相关模块 ≥ 90%
函数覆盖率 有多少函数被调用过 所有公开函数 ≥ 100%
条件覆盖率 布尔表达式的每个条件是否都测到 建议 ≥ 70%

如何生成覆盖率报告

在 CMake 项目中，配合 gcov 和 lcov 可以生成漂亮的 HTML 报告：

# 编译时开启覆盖率
cmake -DCMAKE_CXX_FLAGS="--coverage" ..
make

# 运行测试
./run_tests

# 生成报告
lcov --capture --directory . --output-file coverage.info
genhtml coverage.info --output-directory coverage_report
我的建议：别盯着覆盖率数字看。先保证核心逻辑（比如路径规划、安全急停、电机控制）的覆盖率。这些模块出问题，AGV 可是会撞墙的。
