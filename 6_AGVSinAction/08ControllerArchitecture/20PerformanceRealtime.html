20 性能优化与实时性保障：任务优先级调度、中断服务程序优化、内存池管理、看门狗定时器

做AGV控制器这么多年，我最大的体会就是：性能优化不是锦上添花，而是生死存亡。你想想看，一台AGV在仓库里跑着，突然因为某个中断响应慢了半拍，撞上了货架——这可不是闹着玩的。

今天咱们就聊聊AGV控制器里最核心的几个优化手段。我个人习惯把这四个点称为「实时系统的四大护法」：任务优先级调度、中断服务程序优化、内存池管理、看门狗定时器。它们各自解决不同的问题，但目标只有一个——让控制器在正确的时间做正确的事。

20.1 任务优先级调度：谁急谁先跑

先说任务调度。RTOS里最核心的概念就是优先级。我见过不少新手，上来就把所有任务优先级设成一样，结果系统跑起来跟没头苍蝇似的——哪个任务都抢不到CPU，哪个任务都完不成。

正确的做法是什么？ 把任务分成几个等级：

优先级等级 典型任务 响应时间要求
最高（0-3） 急停处理、碰撞检测、电机过流保护 < 1ms
高（4-7） 编码器读取、PID控制循环、激光雷达数据采集 1-10ms
中（8-11） 路径规划、定位解算、传感器融合 10-100ms
低（12-15） 日志记录、状态上报、UI刷新 > 100ms

我个人习惯用抢占式调度。说白了就是：高优先级任务一旦就绪，立刻抢走CPU。低优先级任务？等着吧。这听起来有点粗暴，但AGV这种硬实时系统就得这么干。

关键原则： 优先级反转是最大的坑。我曾经在一个项目里，低优先级的任务拿着互斥锁不放，高优先级任务干等着，结果电机控制周期直接崩了。解决方案？用优先级继承协议，或者干脆别让不同优先级的任务共享同一个资源。

20.2 中断服务程序优化：快进快出

中断服务程序（ISR）是实时系统的命门。你想想看，中断来了，CPU正在干的事全得停下来。如果ISR里磨磨蹭蹭，整个系统的实时性就完蛋了。

ISR优化的铁律： 能多短就多短。我一般把ISR控制在几十微秒以内。超过100微秒？那得好好想想是不是设计有问题。

具体怎么做？

  • ISR里只做最必要的事： 比如读取硬件寄存器、清除中断标志、把数据塞进队列。剩下的处理？交给任务去做。
  • 避免在ISR里调用阻塞函数： printf？malloc？想都别想。这些函数一调用，ISR就变成无底洞了。
  • 合理使用临界区： 如果ISR和任务共享数据，记得关中断保护。但关中断的时间越短越好——我一般控制在10条指令以内。
// 一个典型的ISR优化示例
void TIM2_IRQHandler(void) {
    // 1. 清除中断标志（必须）
    TIM2->SR = ~TIM_SR_UIF;
    
    // 2. 读取关键数据（极简）
    uint32_t encoder_val = TIM2->CNT;
    
    // 3. 通过消息队列通知任务（非阻塞）
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    xQueueSendFromISR(xEncoderQueue, &encoder_val, &xHigherPriorityTaskWoken);
    
    // 4. 如果有高优先级任务就绪，触发上下文切换
    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}
我的小技巧： 在ISR入口和出口各放一个GPIO翻转，用示波器看脉冲宽度。如果脉冲宽度超过预期，说明ISR里干了不该干的事。这招我用了十年，屡试不爽。

20.3 内存池管理：告别动态分配

说到内存管理，很多嵌入式工程师第一反应是malloc/free。但AGV控制器里，我强烈建议你别用标准库的动态内存分配。为什么？

  • 碎片问题： 频繁分配释放，内存碎片越来越多。跑着跑着，突然malloc失败——系统直接挂掉。
  • 不确定性： malloc的执行时间不固定。最坏情况下，它可能要遍历整个空闲链表。这对实时系统是致命的。
  • 内存泄漏： 你永远不知道哪个任务忘了free。AGV连续跑几个月，内存一点点被吃掉，最后系统崩溃。

解决方案：内存池（Memory Pool）。说白了就是提前把内存分成固定大小的块，需要的时候直接拿一块，用完还回去。没有碎片，执行时间固定，而且简单到不可能出错。

// 一个简单的内存池实现
#define POOL_SIZE 10
#define BLOCK_SIZE 64

typedef struct {
    uint8_t buffer[BLOCK_SIZE];
    uint8_t used;
} MemoryBlock;

static MemoryBlock pool[POOL_SIZE];

void* pool_alloc(void) {
    for (int i = 0; i < POOL_SIZE; i++) {
        if (!pool[i].used) {
            pool[i].used = 1;
            return pool[i].buffer;
        }
    }
    return NULL;  // 池子满了
}

void pool_free(void* ptr) {
    for (int i = 0; i < POOL_SIZE; i++) {
        if (pool[i].buffer == ptr) {
            pool[i].used = 0;
            return;
        }
    }
}
注意： 内存池的大小要仔细算。我曾经在一个项目里，把内存池设小了，结果AGV在复杂场景下频繁申请失败。后来我根据最坏情况（同时处理10个障碍物、5条路径候选、3个传感器数据）来估算，才彻底解决问题。

20.4 看门狗定时器：最后的防线

看门狗（Watchdog Timer）是什么？说白了就是一个「心跳检测器」。你每隔一段时间去喂它一次，告诉它「我还活着」。如果你没喂它——比如系统死锁了、任务卡住了——它就认为系统挂了，然后自动复位。

AGV这种无人驾驶设备，看门狗是必须的。没有看门狗，系统死机了都没人知道。

看门狗的设计要点：

  • 喂狗时机： 别在主循环里喂。万一主循环卡住了，看门狗也救不了你。我习惯在最高优先级的任务里喂狗，确保核心控制逻辑还在跑。
  • 超时时间： 设得太短容易误触发，设得太长又起不到保护作用。一般AGV控制器，我设100-500ms。
  • 多级看门狗： 有些高端MCU支持两级看门狗。第一级超时触发中断，可以尝试软件恢复；第二级超时直接硬件复位。这招对付偶发故障特别好用。
// 看门狗初始化示例（STM32 HAL库）
void Watchdog_Init(void) {
    IWDG_HandleTypeDef hiwdg;
    hiwdg.Instance = IWDG;
    hiwdg.Init.Prescaler = IWDG_PRESCALER_64;   // 分频系数
    hiwdg.Init.Reload = 1250;                    // 重装载值，约1秒超时
    HAL_IWDG_Init(&hiwdg);
}

// 喂狗函数，在最高优先级任务中调用
void FeedTheDog(void) {
    HAL_IWDG_Refresh(&hiwdg);
}
避坑指南： 我曾经在一个项目里，看门狗超时时间设得太短，结果AGV在急转弯时因为CPU负载瞬间升高，来不及喂狗，系统反复复位。后来我把超时时间从200ms改成500ms，同时优化了任务调度，问题才解决。记住：看门狗是防死的，不是防慢的。

20.5 四个要素的协同工作

这四个优化手段不是孤立的。它们需要协同工作：

  • 任务优先级调度 确保关键任务优先执行
  • 中断优化 保证外部事件快速响应
  • 内存池管理 提供稳定可靠的内存分配
  • 看门狗定时器 作为最后一道防线

举个例子：AGV的激光雷达数据来了，触发中断。ISR快速读取数据，通过消息队列发给高优先级的避障任务。避障任务从内存池里拿一块内存，处理完再还回去。如果避障任务因为某种原因卡住了，看门狗会在超时后复位系统。

你看，这四个环节环环相扣。少了任何一个，系统的实时性都会打折扣。嗯，这就是我这么多年做AGV控制器的核心心得。希望对你有帮助。
