22 AGV控制器固件架构：裸机架构、FreeRTOS架构、Linux RT架构对比与选型

做AGV控制器这么多年，我经常被问到的一个问题是：“到底该用裸机、FreeRTOS还是Linux RT？”

说实话，这个问题没有标准答案。但选错了，后面会非常痛苦。我自己就踩过不少坑。

今天咱们就掰开揉碎了聊聊这三种架构。我会结合项目经验，帮你理清思路。

一、三种架构的核心差异

先看一张图，直观感受一下它们的定位。

二、裸机架构：简单但脆弱

裸机架构，说白了就是一个while(1)大循环，加上几个中断服务函数。我最早做AGV时用的就是这种。

典型结构：

void main(void)
{
    // 初始化硬件
    init_gpio();
    init_timer();
    init_motor();
    
    while(1)
    {
        read_sensors();    // 读传感器
        process_data();    // 处理数据
        control_motor();   // 控制电机
        check_comm();      // 检查通信
    }
}

看着简单吧？但问题来了——如果某个函数执行时间长了，其他任务就得等着。

我遇到过的一个坑：有一次做一款小型AGV，用裸机跑。传感器读取和电机控制都在主循环里。结果传感器偶尔会卡住几十毫秒，电机控制就跟着抖。AGV走起来一窜一窜的，像喝醉了酒。

裸机的优缺点：

  • 优点：代码简单、资源占用极低、实时性理论上最高（没有OS调度开销）
  • 缺点：任务耦合严重、扩展性差、维护成本高、多任务协调困难

我的建议：裸机只适合非常简单的AGV，比如只有几个传感器、一个电机、没有复杂通信的场景。但凡任务超过3个，就别用裸机了。

三、FreeRTOS架构：轻量级的多任务方案

FreeRTOS是我个人最常用的方案。它轻巧、稳定、实时性好。

它的核心思想是：把不同功能拆成独立任务，由调度器统一管理。

典型结构：

void task_sensor(void *pvParameters)
{
    while(1)
    {
        read_sensors();
        vTaskDelay(pdMS_TO_TICKS(10));  // 10ms周期
    }
}

void task_control(void *pvParameters)
{
    while(1)
    {
        process_control();
        vTaskDelay(pdMS_TO_TICKS(5));   // 5ms周期
    }
}

void task_comm(void *pvParameters)
{
    while(1)
    {
        handle_communication();
        vTaskDelay(pdMS_TO_TICKS(20));  // 20ms周期
    }
}

你看，每个任务各干各的，互不干扰。传感器任务10ms跑一次，控制任务5ms跑一次，通信任务20ms跑一次。调度器会保证它们都能按时执行。

FreeRTOS的优势：

  • 任务隔离，一个任务卡了不影响其他任务
  • 支持优先级抢占，紧急任务可以优先执行
  • 提供队列、信号量、互斥锁等同步机制
  • 内存占用小，一般几KB到几十KB
  • 生态丰富，STM32、ESP32等主流MCU都支持

注意：FreeRTOS虽然好，但也不是万能的。它没有文件系统、没有网络协议栈、没有设备驱动框架。如果你需要这些，得自己移植或找第三方库。

我个人的经验：对于中等复杂度的AGV，比如有4-6个传感器、2个电机、需要简单通信的，FreeRTOS是最佳选择。我做过一个项目，用STM32F4 + FreeRTOS，跑了8个任务，稳得很。

四、Linux RT架构：强大但复杂

Linux RT，就是给Linux内核打上实时补丁（PREEMPT_RT），让它具备硬实时能力。

说实话，Linux RT在AGV领域用得越来越多。尤其是那些需要视觉导航、多传感器融合、复杂路径规划的AGV。

典型结构：

// 用户空间实时线程
pthread_t rt_thread;
struct sched_param param;
param.sched_priority = 80;

pthread_create(&rt_thread, NULL, rt_control_loop, NULL);
pthread_setschedparam(rt_thread, SCHED_FIFO, ¶m);

void *rt_control_loop(void *arg)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    
    while(1)
    {
        // 控制周期 1ms
        ts.tv_nsec += 1000000;
        clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &ts, NULL);
        
        read_encoder();
        calculate_pid();
        set_motor_pwm();
    }
}

Linux RT的优势：

  • 完整的操作系统生态：文件系统、网络、USB、GPU驱动等
  • 支持复杂应用：ROS、OpenCV、PCL等
  • 多进程隔离，一个进程崩溃不会影响整个系统
  • 丰富的调试工具：gdb、perf、strace等

但代价也不小：

  • 启动慢，一般需要几秒到几十秒
  • 资源占用高，至少需要64MB RAM、几百MB存储
  • 实时性不如裸机和FreeRTOS，中断延迟在几十微秒级别
  • 开发复杂，需要懂Linux内核、驱动、进程管理等

我的建议：如果你的AGV需要运行ROS、需要视觉处理、需要WiFi/4G通信、需要数据库存储，那就上Linux RT。否则，别给自己找麻烦。

五、选型决策表

为了方便你快速决策，我整理了一个表格：

考量因素 裸机 FreeRTOS Linux RT
任务数量 ≤3个 3-15个 ≥10个
实时性要求 极高（μs级） 高（μs-ms级） 中等（ms级）
内存需求 几KB 几十KB ≥64MB
开发周期 短（1-2周） 中等（2-4周） 长（1-3月）
维护成本 高 低 中等
功能扩展 困难 容易 非常容易

适用场景 简单传感器驱动 中等复杂度AGV 复杂AGV、机器人

六、我的选型建议

说了这么多，到底怎么选？我总结几条实战经验：

  1. 先看任务数量：如果只有1-2个任务，裸机就够了。超过3个，果断上FreeRTOS。
  2. 再看实时性：如果控制周期需要10μs以内，裸机或FreeRTOS。如果1ms以上，Linux RT也能搞定。
  3. 然后看功能需求：需要视觉、ROS、网络？那就Linux RT。不需要？FreeRTOS更省心。
  4. 最后看团队能力：团队熟悉Linux？上Linux RT。团队只会单片机？用FreeRTOS更稳妥。

我个人的推荐：

  • 入门级AGV（简单循迹、避障）：裸机或FreeRTOS
  • 中级AGV（多传感器、简单路径规划）：FreeRTOS
  • 高级AGV（视觉导航、多机协同、ROS）：Linux RT

记住，没有最好的架构，只有最合适的。选型时多想想你的项目需求、团队能力、开发周期和成本预算。
