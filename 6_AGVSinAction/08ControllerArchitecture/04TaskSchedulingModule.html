4 任务调度模块设计：任务队列管理、任务优先级、任务分配策略

各位同学，今天我们来聊聊AGV控制器里最核心的一个模块——任务调度。说实话，我在这个领域摸爬滚打了十几年，见过太多因为调度设计不合理导致AGV“死锁”、“空跑”甚至“撞车”的案例。任务调度模块，说白了就是AGV的“大脑决策中心”。它决定了哪个任务先做、哪个车去执行、走哪条路。

我个人习惯把任务调度模块拆成三个子模块来看：任务队列管理、任务优先级、任务分配策略。这三个东西缺一不可，而且相互影响。你想想看，如果队列管理不好，优先级再高也没用；如果分配策略不对，优先级再合理也是白搭。

4.1 任务队列管理

任务队列，说白了就是任务的“候车室”。所有待执行的任务都在这里排队。我建议用双向链表来实现，因为AGV任务经常需要插入、删除、调整顺序。数组？嗯，不太推荐，因为频繁的插入删除会导致大量数据搬移，实时性会受影响。

核心要点：任务队列必须支持动态增删改查，且时间复杂度要控制在O(1)或O(log n)。

我在项目中遇到过一个问题：任务队列里同时有100多个任务，结果因为队列设计成单向链表，每次查找某个任务都要从头遍历，导致调度延迟飙升到200ms。后来改成哈希表+双向链表，延迟直接降到5ms以下。

任务队列的数据结构，我一般这样设计：

typedef struct {
    uint32_t task_id;           // 任务唯一ID
    uint8_t  priority;          // 优先级 0-255
    uint32_t create_time;       // 创建时间戳
    uint32_t deadline;          // 截止时间
    uint8_t  status;            // 0:等待 1:执行中 2:完成 3:取消
    float    path_length;       // 预估路径长度(米)
    uint8_t  assigned_robot;    // 分配的AGV编号
    struct list_head list;      // 链表节点
} agv_task_t;

这里要注意，path_length 不是固定的。我建议在任务入队时，先做一次粗粒度路径规划，估算出大概的行驶距离。这样后面做最短路径优先策略时，才有数据支撑。

避坑指南：我曾经在任务队列里忘记加“取消”状态，结果某个任务执行到一半，用户想取消，但系统还在傻傻地调度。后来加了个状态机，才彻底解决这个问题。

4.2 任务优先级

任务优先级，是调度模块的“指挥棒”。AGV场景里，优先级通常分这么几类：

优先级等级 典型任务 说明
0-15（紧急） 急停、故障处理、安全任务 必须立即执行，抢占所有资源
16-63（高） 生产线急料、充电任务 优先于普通任务
64-127（普通） 常规搬运、入库出库 大部分任务属于此类
128-255（低） 巡检、数据采集、空闲回库 可被高优先级任务抢占

我个人习惯用位图法来实现优先级调度。为什么？因为AGV控制器资源有限，位图法查找最高优先级任务的时间复杂度是O(1)，而且内存占用极小。我曾经试过用红黑树，虽然也能用，但在嵌入式环境里，位图法更轻量。

代码实现大概是这样：

// 优先级位图，256位，每个bit代表一个优先级是否有任务
uint32_t priority_bitmap[8];  // 256位 = 8个32位

// 设置某优先级有任务
void set_priority(uint8_t prio) {
    priority_bitmap[prio / 32] |= (1 << (prio % 32));
}

// 获取当前最高优先级
uint8_t get_highest_priority() {
    for (int i = 0; i < 8; i++) {
        if (priority_bitmap[i] != 0) {
            // 找到第一个非0的32位块
            uint32_t bits = priority_bitmap[i];
            // 用内置函数找最低位
            uint8_t offset = __builtin_ctz(bits);
            return i * 32 + offset;
        }
    }
    return 255; // 无任务
}

小技巧：如果编译器不支持 __builtin_ctz，可以用查表法代替。256字节的表，查一次就能找到最低位，速度也很快。

这里有个容易踩的坑：优先级反转。比如低优先级任务占着某个资源，高优先级任务等着用，结果中优先级任务插进来，把低优先级任务挤到一边，高优先级任务反而被阻塞了。我曾经在项目里吃过这个亏，后来加了优先级继承协议才解决。具体做法是：当高优先级任务等待低优先级任务释放资源时，临时把低优先级任务的优先级提升到相同等级。

4.3 任务分配策略

任务分配策略，就是决定“哪个AGV去执行哪个任务”。常用的策略有两种：最短路径优先和先来先服务。我分别说说。

4.3.1 最短路径优先（SPF）

最短路径优先，说白了就是“谁离得近谁去”。这个策略在AGV数量多、任务密集的场景下特别有效。我建议的实现方式是：

  1. 任务入队时，先计算每个空闲AGV到任务起点的距离
  2. 选出距离最短的AGV
  3. 如果多个AGV距离相同，再比较它们的剩余电量、当前负载等因素

代码逻辑大致如下：

uint8_t select_robot_by_spf(agv_task_t *task) {
    float min_distance = 999999.0;
    uint8_t selected_robot = 0xFF;
    
    for (int i = 0; i < robot_count; i++) {
        if (robots[i].status != ROBOT_IDLE) continue;
        
        float dist = calculate_distance(robots[i].position, task->start_point);
        if (dist < min_distance) {
            min_distance = dist;
            selected_robot = i;
        } else if (fabs(dist - min_distance) < 0.1) {
            // 距离相同，比较电量
            if (robots[i].battery > robots[selected_robot].battery) {
                selected_robot = i;
            }
        }
    }
    return selected_robot;
}

注意：最短路径优先不是万能的。如果所有AGV都挤在同一个区域，而任务分布在远处，这个策略会导致AGV分布不均。我建议配合负载均衡策略一起使用。

4.3.2 先来先服务（FCFS）

先来先服务，就是“谁先来谁先得”。这个策略实现简单，公平性好，但效率不一定高。你想想看，如果先来的任务要去最远的角落，后来的任务就在旁边，但后来的任务只能等着，这显然不合理。

我一般在任务量少、AGV数量少的场景下用FCFS。比如小型仓库，只有3-5台AGV，任务也不密集，FCFS完全够用。但在大型工厂，几十台AGV同时跑，FCFS就会导致严重的效率问题。

FCFS的实现很简单，就是维护一个先进先出的队列：

// 任务入队
void enqueue_task(agv_task_t *task) {
    list_add_tail(&task->list, &task_queue);
}

// 取出最早的任务
agv_task_t* dequeue_task() {
    if (list_empty(&task_queue)) return NULL;
    return list_first_entry(&task_queue, agv_task_t, list);
}

4.3.3 混合策略

在实际项目中，我很少只用一种策略。我建议用混合策略：

  • 紧急任务（优先级0-15）：直接抢占，不管什么策略
  • 高优先级任务（16-63）：用最短路径优先，但要考虑AGV负载
  • 普通任务（64-127）：用最短路径优先，如果距离差超过阈值，才重新分配
  • 低优先级任务（128-255）：用先来先服务，避免频繁切换

这样做的好处是：紧急任务能快速响应，普通任务效率高，低优先级任务稳定。我曾经在一个汽车零部件工厂的项目里用这个混合策略，AGV的整体效率提升了30%以上，而且死锁率降到了0.1%以下。

避坑指南：混合策略虽然好，但参数调优很关键。比如“距离差阈值”设多少？设大了，策略退化成FCFS；设小了，AGV频繁切换任务，反而增加空跑。我一般建议先设为10米，然后根据实际运行数据调整。

4.5 总结与建议

任务调度模块设计，说白了就是三个字：快、准、稳。快，就是调度延迟要低；准，就是任务分配要合理；稳，就是系统不能死锁、不能崩溃。

我个人建议，在设计任务调度模块时，先想清楚这几个问题：

  • 你的AGV数量是多少？10台以内和100台以上，设计思路完全不同
  • 任务的到达频率是多少？是均匀到达还是突发性到达？
  • 对实时性的要求有多高？毫秒级还是秒级？

想清楚这些，再去选数据结构和策略，就不会走弯路。嗯，今天就讲到这里，大家有什么问题可以随时交流。
