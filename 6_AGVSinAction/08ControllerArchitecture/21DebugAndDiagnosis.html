21 AGV控制器调试与诊断：串口调试工具、ROS2命令行工具（rqt、rviz2）、逻辑分析仪使用

做AGV这些年，我最大的体会就是：调试能力决定了开发效率。代码写得再漂亮，遇到问题抓瞎，一样白搭。今天咱们就聊聊AGV控制器调试与诊断的三大法宝——串口工具、ROS2可视化全家桶、还有逻辑分析仪。

说白了，这三样东西覆盖了从底层硬件到上层算法的全链路调试。我习惯把它们分成三个层次：

  • 串口调试：看电机转没转、传感器通没通
  • ROS2工具：看路径规没规划对、定位准不准
  • 逻辑分析仪：看时序对不对、信号有没有毛刺

嗯，咱们一个一个来。

21.1 串口调试工具：最朴素的救命稻草

别小看串口。我见过太多人一上来就开rviz2，结果车都不动，折腾半天发现是电机驱动没初始化。这时候一个串口终端就能救命。

21.1.1 常用串口工具

工具 平台 特点
PuTTY Windows 轻量、稳定，适合快速连接
MobaXterm Windows 支持多标签、SFTP，我常用
screen Linux 命令行神器，一句搞定
minicom Linux 功能全面，配置稍复杂
Arduino IDE串口监视器 跨平台 调试MCU时顺手就用

我个人习惯在Linux下用screen，命令简单：

# 查看串口设备
ls /dev/ttyUSB* /dev/ttyACM*

# 连接串口，波特率115200
screen /dev/ttyUSB0 115200

# 退出：Ctrl+A，然后按K
小技巧： 如果screen退出后提示"Terminated"，可以加个参数：screen -L /dev/ttyUSB0 115200，这样日志会自动保存到screenlog.0文件里。

21.1.2 串口调试的典型场景

我在项目中遇到过最典型的场景——AGV走直线时总往右偏。查了PID参数、查了轮子直径，都没问题。最后用串口打印电机编码器数据，发现左轮每圈脉冲数比右轮少了12个。嗯，编码器线松了。

串口调试的核心思路就三条：

  • 打印关键状态：电机速度、编码器值、传感器触发标志
  • 加时间戳：判断数据更新频率是否正常
  • 格式化输出：用逗号分隔，方便导入Excel分析
// 格式化输出示例
printf("%lu,%d,%d,%d\n", millis(), left_encoder, right_encoder, imu_yaw);
注意： 串口打印不要太频繁。我见过有人每1ms打印一次，结果电机控制线程被阻塞，车直接抖成筛子。建议10ms以上间隔，或者用DMA+环形缓冲区。

21.2 ROS2命令行工具：可视化调试的利器

串口能看底层，但想看全局——路径、地图、TF树——还得靠ROS2的工具链。rqt和rviz2是我每天必开的两个窗口。

21.2.1 rqt：数据监控的瑞士军刀

rqt说白了就是一个插件化的仪表盘。你想想看，不用写一行代码，就能看到所有topic的数据变化，多爽。

常用插件：

  • Topic Monitor：实时查看topic频率、带宽、最新值
  • Plot：把数据画成曲线，看速度、位置变化趋势
  • Console：集中显示ros2日志，按级别过滤
  • Graph：可视化节点之间的连接关系

启动方式：

# 启动rqt
rqt

# 或者直接加载特定插件
rqt --force-discover

我记得有一次，AGV在转弯时突然卡住。用rqt的Plot插件同时画了左轮速度、右轮速度和IMU角速度，发现右轮在转弯时速度掉到0了。查代码，发现是电机驱动库的一个bug——速度指令超过阈值后自动保护了。

核心经验： 调试AGV时，我习惯同时监控3-5个关键topic。比如：/cmd_vel（指令速度）、/odom（里程计）、/imu/data（IMU数据）。哪个异常，问题就在哪。

21.2.2 rviz2：三维世界的眼睛

rviz2是AGV调试的终极武器。你写的路径规划算法对不对？定位准不准？在rviz2里一眼就能看出来。

我常用的显示项：

显示项 作用 调试场景
RobotModel 显示机器人模型 检查URDF是否正确
LaserScan 显示激光雷达数据 判断雷达是否被遮挡
Map 显示栅格地图 检查建图质量
Path 显示规划路径 验证路径是否平滑
TF 显示坐标系变换 检查坐标树是否完整 
# 启动rviz2
rviz2

# 保存配置，下次直接加载
rviz2 -d my_agv_config.rviz
避坑指南： 我曾经在rviz2里看不到激光雷达数据，折腾了两小时。最后发现是frame_id写错了——代码里写的是laser_frame，但URDF里定义的是laser_link。记住：frame_id必须和TF树里的名称完全一致。

21.3 逻辑分析仪：硬件调试的显微镜

软件层面的问题用串口和ROS2基本能搞定。但遇到硬件问题——比如电机不转、传感器数据跳变——就得请出逻辑分析仪了。

21.3.1 什么时候需要逻辑分析仪

  • PWM信号频率或占空比不对
  • UART/I2C/SPI通信失败
  • 编码器AB相脉冲异常
  • 中断信号有毛刺

说白了，只要涉及到时序和电平的问题，逻辑分析仪就是最好的诊断工具。

21.3.2 常用逻辑分析仪

型号 通道数 采样率 价格区间
Saleae Logic 8 8 100MHz ￥300-500
DSLogic Plus 16 400MHz ￥600-1000
国产CY7C68013A方案 24 24MHz ￥50-100

21.3.3 实战：调试编码器信号

我记得有一次，AGV的里程计数据总是跳变。用逻辑分析仪抓了编码器的A相和B相信号，发现B相有一个毛刺——在应该高电平的时候突然拉低了几个微秒。

原因是什么？电机线缆和编码器线缆绑在一起，电机启动时的大电流干扰了编码器信号。

解决方案：

  • 编码器线加屏蔽
  • 信号线上加RC滤波（100Ω+100nF）
  • 软件里做去抖处理
// 编码器去抖示例
#define DEBOUNCE_US 10

void encoder_isr() {
    static uint64_t last_time = 0;
    uint64_t now = micros();
    
    if (now - last_time < DEBOUNCE_US) {
        return;  // 小于10微秒的脉冲，忽略
    }
    last_time = now;
    
    // 正常处理编码器计数
    if (digitalRead(ENC_A) == digitalRead(ENC_B)) {
        encoder_count++;
    } else {
        encoder_count--;
    }
}
重要提醒： 逻辑分析仪的接地很重要。探头的地线夹子一定要夹到目标板子的GND上，否则抓到的信号全是噪声。我刚开始用的时候犯过这个错，抓了一堆乱七八糟的波形，还以为芯片坏了。

最后说一句：工具再好，也得靠人用。我见过有人拿着Saleae Logic Pro抓了8个通道的波形，结果不会分析，白费功夫。调试的核心不是工具多高级，而是你知不知道自己要查什么。
