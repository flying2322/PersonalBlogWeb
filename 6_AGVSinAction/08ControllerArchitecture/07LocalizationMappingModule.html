7 定位与建图模块设计：SLAM概述、激光SLAM、视觉SLAM、里程计融合

各位同学，今天我们来聊聊AGV控制器里最核心、也最让人头疼的模块——定位与建图。说白了，就是让机器人知道「我在哪」、「周围长什么样」。我做了这么多年AGV，见过太多因为定位不准导致撞墙、迷路的案例。嗯，这一章我们就把SLAM的底裤扒干净。

7.1 SLAM概述：先搞清楚它要解决什么问题

SLAM，全称是Simultaneous Localization and Mapping，同时定位与地图构建。你想想看，一个机器人进入陌生环境，它没有GPS，也没有预先的地图。它只能靠自己的传感器，一边走一边猜自己在哪里，同时还要把周围的环境画出来。这就是SLAM要干的事。

我个人习惯把SLAM分成三个流派：

  • 激光SLAM：用激光雷达测距，精度高，但成本也高。适合室内结构化环境。
  • 视觉SLAM：用摄像头图像，成本低，但受光照影响大。适合特征丰富的场景。
  • 多传感器融合SLAM：把激光、视觉、IMU、轮式编码器全揉在一起。这是工业级AGV的标配。

核心要点：SLAM的本质是一个状态估计问题。我们用一个概率模型来描述机器人的位姿和地图特征点的不确定性。常用的框架是图优化（Graph-based SLAM）和滤波器（EKF/粒子滤波）。

我在项目中遇到过最坑的事：一个客户非要只用单线激光做SLAM，结果在长走廊里直接漂移了十几米。为什么？因为激光在长走廊里缺乏纵向特征，无法约束前进方向的位移。所以，别迷信单一传感器。

7.2 激光SLAM：Gmapping与Cartographer

激光SLAM是目前最成熟、最稳定的方案。我们重点讲两个：Gmapping和Cartographer。

7.2.1 Gmapping：经典但已过时

Gmapping是基于粒子滤波的2D激光SLAM。它的核心思想是用一堆粒子来近似机器人的位姿后验概率分布。每个粒子都维护一张地图，然后根据观测更新粒子的权重。

优点很明显：实现简单，小场景下效果不错。缺点也很致命：粒子数量随环境增大指数级增长，而且没有回环检测。说白了，它不认路，走一圈回来它不知道这是同一个地方。

避坑指南：我曾经在50m×50m的仓库里用Gmapping，粒子数设到500个，CPU直接跑满。后来换成Cartographer，粒子数降到50个，效果反而更好。所以，大场景别用Gmapping。

7.2.2 Cartographer：工业级首选

Cartographer是Google开源的激光SLAM方案。它采用图优化框架，支持2D和3D。核心创新点有两个：

  • 子图（Submap）机制：把地图切成小块，每个子图独立优化，最后再全局优化。这样计算量可控。
  • 回环检测：用分支定界法快速搜索历史子图，找到闭环后做全局优化。这是Gmapping没有的。

我建议你在实际项目中这样配置Cartographer：

# 典型配置参数（2D激光）
TRAJECTORY_BUILDER_2D:
  min_range: 0.3
  max_range: 30.0
  use_imu_data: true
  ceres_scan_matcher:
    occupied_space_weight: 1.0
    translation_weight: 10.0
    rotation_weight: 40.0

POSE_GRAPH:
  optimize_every_n_nodes: 90
  constraint_builder:
    loop_closure_translation_weight: 1.1e4
    loop_closure_rotation_weight: 1.0e5
  max_num_final_iterations: 200

注意：Cartographer对IMU依赖很大。如果没有IMU，纯激光的Cartographer在快速旋转时容易丢位置。我踩过这个坑，后来加了IMU才稳定。

7.3 视觉SLAM：ORB-SLAM3

视觉SLAM用摄像头代替激光雷达。成本低，但计算量大。目前最成熟的是ORB-SLAM系列，最新版是ORB-SLAM3。

ORB-SLAM3的核心是：

  • ORB特征点：旋转不变、尺度不变，比SIFT快很多。
  • 三线程架构：跟踪线程、局部建图线程、回环检测线程。并行处理，实时性不错。
  • 支持单目、双目、RGB-D：灵活适配不同硬件。

但说实话，纯视觉SLAM在AGV上不太实用。为什么？因为AGV经常在纹理稀疏的环境（比如白墙、地板）运行，ORB特征点提取不出来。我试过在纯白走廊里跑ORB-SLAM，直接初始化失败。

我的建议：视觉SLAM适合做辅助定位，比如在特征丰富的区域修正激光SLAM的累积误差。别指望它独当一面。

7.4 里程计融合：IMU+轮式编码器

里程计融合是SLAM的「地基」。没有好的里程计，SLAM就是空中楼阁。我们通常把IMU和轮式编码器融合，得到高频、低延迟的位姿估计。

7.4.1 轮式编码器：简单但会打滑

轮式编码器直接测量车轮转速，通过运动学模型推算位移。优点是频率高（100Hz以上），缺点是打滑时完全失效。我见过一个案例：AGV在湿滑地面急刹车，编码器显示走了2米，实际只走了1.5米。这就是打滑误差。

7.4.2 IMU：不依赖轮子但会漂

IMU测量加速度和角速度，通过积分得到位姿。优点是不受打滑影响，缺点是积分漂移严重。你想想看，加速度积分一次得速度，再积分一次得位移，误差随时间平方增长。10秒后位置可能偏了十几米。

7.4.3 融合策略：互补滤波 vs EKF

把两者融合起来，取长补短。常用方法有两种：

方法 优点 缺点 适用场景
互补滤波 计算简单，延迟低 精度一般，无协方差估计 低成本MCU
扩展卡尔曼滤波（EKF） 精度高，可估计不确定性 计算量大，需要调参 高性能ARM/FPGA

我个人习惯用EKF。下面是一个简化的融合模型：

// 状态向量: [x, y, theta, v, w]
// 预测方程（基于IMU）
x_k = x_{k-1} + v * cos(theta) * dt
y_k = y_{k-1} + v * sin(theta) * dt
theta_k = theta_{k-1} + w * dt

// 观测方程（基于编码器）
z_v = v_encoder + noise_v
z_w = w_encoder + noise_w

实战技巧：当检测到轮子打滑（比如编码器速度突变但IMU加速度正常），我建议临时降低编码器的观测权重。这样EKF会更信任IMU，避免被错误数据带偏。
