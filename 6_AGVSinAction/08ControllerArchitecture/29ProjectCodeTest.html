29 AGV控制器项目实战（二）：编码实现、单元测试、集成测试、系统联调

好，咱们接着上一章聊。上一章我们把架构搭好了，模块接口也定下来了。这一章，就是真正动手写代码的时候了。

说实话，每次到这一步，我都挺兴奋的。架构设计就像画图纸，而编码实现就是把图纸变成真家伙。但我也得提醒你——写代码只是开始，真正的考验在后面：单元测试、集成测试、系统联调。这三关过不去，代码写得再漂亮也是白搭。

一、编码实现：从接口到实现

我个人习惯，编码实现分三步走：

  1. 先写头文件——把上一章定义的接口用C/C++代码固定下来
  2. 再写桩代码——每个函数先返回一个假值，让编译能通过
  3. 最后填逻辑——一个一个函数去实现，边写边测

举个例子，我们AGV控制器的核心模块——运动控制模块，它的头文件大概长这样：

// motion_controller.h
#ifndef MOTION_CONTROLLER_H
#define MOTION_CONTROLLER_H

#include <stdint.h>

typedef enum {
    MOTION_STOP = 0,
    MOTION_FORWARD,
    MOTION_BACKWARD,
    MOTION_TURN_LEFT,
    MOTION_TURN_RIGHT
} MotionState_t;

typedef struct {
    float linear_velocity;   // m/s
    float angular_velocity;  // rad/s
    MotionState_t state;
} MotionCmd_t;

int Motion_Init(void);
int Motion_SetCmd(MotionCmd_t *cmd);
int Motion_GetStatus(MotionCmd_t *status);
int Motion_EmergencyStop(void);

#endif

嗯，这里要注意：接口参数尽量用结构体指针。为什么？因为AGV控制器里数据交互频繁，用指针传递效率高，而且方便扩展。我在项目中遇到过，一开始用单个参数传，后来要加字段，改得那叫一个痛苦。

二、单元测试：把每个零件单独拧出来测

单元测试，说白了就是验证每个函数对不对。我见过太多人跳过这一步，结果集成的时候bug一堆，查都查不过来。

我个人推荐用CUnit或者Unity这种轻量级测试框架。咱们AGV控制器是嵌入式系统，资源有限，测试框架不能太臃肿。

来看一个运动控制模块的单元测试例子：

// test_motion_controller.c
#include "unity.h"
#include "motion_controller.h"

void setUp(void) {
    Motion_Init();
}

void tearDown(void) {
    // 清理资源
}

void test_Motion_Init_Should_Return_OK(void) {
    TEST_ASSERT_EQUAL_INT(0, Motion_Init());
}

void test_Motion_SetCmd_Forward_Should_Work(void) {
    MotionCmd_t cmd = {0.5, 0.0, MOTION_FORWARD};
    int ret = Motion_SetCmd(&cmd);
    TEST_ASSERT_EQUAL_INT(0, ret);
    
    MotionCmd_t status;
    Motion_GetStatus(&status);
    TEST_ASSERT_EQUAL_FLOAT(0.5, status.linear_velocity);
    TEST_ASSERT_EQUAL(MOTION_FORWARD, status.state);
}

void test_Motion_EmergencyStop_Should_Stop_Immediately(void) {
    MotionCmd_t cmd = {1.0, 0.0, MOTION_FORWARD};
    Motion_SetCmd(&cmd);
    
    Motion_EmergencyStop();
    
    MotionCmd_t status;
    Motion_GetStatus(&status);
    TEST_ASSERT_EQUAL_FLOAT(0.0, status.linear_velocity);
    TEST_ASSERT_EQUAL(MOTION_STOP, status.state);
}

你想想看，如果每个函数都这样测一遍，集成的时候心里是不是踏实多了？

我的小技巧：单元测试要覆盖正常路径、边界路径和异常路径。比如速度值传负数会怎样？传个NULL指针会怎样？这些都要测到。

三、集成测试：把零件组装起来

单元测试过了，不代表模块之间能配合好。集成测试就是干这个的。

AGV控制器的集成测试，我一般分两层：

  • 模块间集成：比如运动控制模块和传感器模块能不能协同工作
  • 子系统集成：比如导航子系统和底盘子系统能不能配合

我曾经在一个项目里，单元测试全过了，但一集成就出问题。查了两天才发现，是两个模块对同一个数据结构的字节对齐理解不一致。从那以后，我集成测试时一定会检查结构体大小：

// 集成测试：检查数据结构一致性
void test_DataStructure_Consistency(void) {
    // 确保发送端和接收端结构体大小一致
    TEST_ASSERT_EQUAL_INT(sizeof(MotionCmd_t), 12);
    // 检查关键字段偏移
    TEST_ASSERT_EQUAL_INT(offsetof(MotionCmd_t, linear_velocity), 0);
    TEST_ASSERT_EQUAL_INT(offsetof(MotionCmd_t, angular_velocity), 4);
    TEST_ASSERT_EQUAL_INT(offsetof(MotionCmd_t, state), 8);
}
注意：集成测试环境要尽量接近真实硬件。如果条件不允许，至少要用硬件在环（HIL）仿真。我在一个项目中偷懒用了纯软件仿真，结果到现场才发现电机响应延迟比仿真大了一倍。

四、系统联调：让整个AGV跑起来

系统联调，是项目实战中最刺激也最折磨人的阶段。所有模块都装到AGV上，在真实场景里跑。

我一般按这个顺序来：

  1. 空载调试——AGV不载货，跑基本路径
  2. 负载调试——加上额定负载，看控制参数要不要调
  3. 极限测试——最大速度、最大转弯、急停
  4. 长时间跑——连续跑8小时以上，看稳定性

这里有个坑，我踩过好几次：系统联调时一定要有日志记录。别光靠眼睛看，AGV跑起来你根本来不及反应。把关键数据都打出来，出问题了回头分析。

五、实战中的避坑指南

做AGV控制器项目，有些坑是绕不开的。我把自己踩过的坑整理了一下：

阶段 常见问题 我的建议
编码实现 接口定义频繁修改 先定接口再写实现，接口评审要拉上所有相关模块的人
单元测试 测试覆盖率低 用gcov等工具看覆盖率，低于80%不放过
集成测试 模块间时序问题 加日志时间戳，分析时序关系
系统联调 现场环境与测试环境不一致 尽早把AGV放到真实场地跑，别等全部开发完

核心总结：编码实现要稳，单元测试要全，集成测试要细，系统联调要狠。每一步都扎实了，AGV才能跑得稳、跑得久。
