14 数据持久化与日志模块：SQLite数据库设计、运行日志记录（CSV/JSON）、关键数据备份与恢复

各位同学，今天我们来聊聊AGV控制器里一个看似不起眼，但关键时刻能救命的东西——数据持久化与日志模块。

说实话，我早年做AGV项目时，最怕的就是半夜接到现场电话：“车撞了，但不知道为啥撞的。” 那时候日志系统做得稀烂，连个像样的记录都没有。后来我痛定思痛，把数据持久化和日志模块重新设计了一遍。今天就把这些经验分享给你们。

14.1 为什么需要数据持久化？

AGV跑起来，会产生大量数据。比如：

  • 配置参数：地图信息、站点坐标、速度限制等
  • 运行状态：当前电量、位置、任务ID等
  • 历史轨迹：过去24小时的行驶路径
  • 故障记录：什么时候报了什么错

这些数据，掉电就丢？那肯定不行。所以我们需要一个可靠的存储方案。

核心原则：关键数据必须持久化，非关键数据可以按策略清理。

14.2 SQLite数据库设计

我个人习惯在嵌入式AGV上用SQLite。为什么？因为它轻量、零配置、单文件存储，而且SQL语法大家都会用。

我设计数据库时，一般会分这么几张表：

表名 用途 关键字段
config 系统配置参数 key, value, updated_at
task_log 任务执行记录 task_id, status, start_time, end_time
fault_record 故障报警记录 fault_code, description, timestamp
position_history 位置历史轨迹 x, y, theta, timestamp

嗯，这里要注意：position_history 表的数据量会非常大。我曾经有个项目，AGV一天跑下来，位置记录能到几十万条。所以一定要加索引，并且定期清理。

建表SQL示例：

CREATE TABLE IF NOT EXISTS config (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL,
    updated_at INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS task_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id TEXT NOT NULL,
    status INTEGER NOT NULL,
    start_time INTEGER,
    end_time INTEGER
);

CREATE INDEX idx_task_log_task_id ON task_log(task_id);

我的小技巧：时间字段我习惯用Unix时间戳（INTEGER），而不是TEXT。排序快，跨平台也方便。

14.3 运行日志记录（CSV/JSON）

数据库存的是结构化数据。但有些场景，我们需要更灵活的日志格式。比如调试时，我想看每一帧的传感器原始数据。这时候CSV和JSON就派上用场了。

14.3.1 CSV日志

CSV适合记录时序数据，比如：

  • 电机转速、电流
  • 激光雷达扫描数据
  • IMU加速度、角速度

我一般会按天生成文件，文件名带上日期。比如 motor_log_2025-01-15.csv。

timestamp,left_motor_rpm,right_motor_rpm,left_current,right_current
1705305600,1200,1180,2.3,2.1
1705305601,1210,1190,2.4,2.2

CSV的好处是，用Excel或者Python的pandas直接就能分析。我曾经在现场调试时，把CSV拖进Excel，画个折线图，电机抖动问题一眼就看出来了。

14.3.2 JSON日志

JSON适合记录结构复杂的数据。比如：

  • 任务调度信息
  • 路径规划结果
  • 多传感器融合后的位姿
{
  "timestamp": 1705305600,
  "event": "TASK_START",
  "data": {
    "task_id": "TASK-001",
    "from": "A01",
    "to": "B03",
    "priority": 1
  }
}

避坑指南：我曾经在日志文件里写JSON时，没处理好换行符。结果日志文件里一行JSON几万字符，用文本编辑器打开直接卡死。后来我强制每条JSON日志只占一行，并且限制单条日志大小不超过4KB。

14.4 关键数据备份与恢复

数据存好了，但万一存储介质坏了呢？或者系统崩溃导致数据库损坏呢？所以备份机制必不可少。

我一般会设计三级备份策略：

  1. 实时备份：关键配置参数，每次修改后立即写入备份区
  2. 定时备份：每天凌晨3点，自动备份整个数据库到另一个分区
  3. 手动备份：提供接口，运维人员可以随时触发备份

备份文件命名规则：agv_data_backup_20250115_030000.db

恢复流程也很重要。我见过有人备份做得很好，但恢复时发现备份文件也是坏的。所以：

  • 每次备份后，要校验文件完整性（比如计算MD5）
  • 定期做恢复演练，确保备份真的能用

我的经验：在AGV上，我还会保留最近3次备份。万一最新的备份有问题，还能回退到前一个版本。这个习惯救过我一次——有一次数据库升级脚本写错了，导致所有配置丢失。还好有前一天的备份，10分钟就恢复了。

14.6 总结

数据持久化与日志模块，说白了就是AGV的“黑匣子”。平时你可能感觉不到它的存在，但一旦出问题，它就是你的救命稻草。

我个人建议，在设计阶段就把这个模块考虑进去。不要等到现场出了问题再补，那时候代价就大了。
