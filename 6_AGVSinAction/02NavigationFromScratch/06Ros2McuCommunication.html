6 ROS2与底层MCU通信

做AGV最头疼的是什么？我个人觉得，就是上层算法和底层电机之间的“沟通障碍”。ROS2跑在Linux上，MCU跑在裸机或RTOS上，这两个世界怎么对话？说白了，就是这一章要解决的问题。

我在做第一台AGV原型机时，就踩过这个坑。上层规划好了路径，下发了速度指令，结果车子原地打转。查了半天，发现是串口通信丢包了。嗯，从那以后，我对通信协议的设计就格外上心。

6.1 为什么需要ros2_serial？

ROS2的节点通信默认走DDS，这玩意儿在Linux上跑得飞起。但MCU呢？大部分MCU跑不了完整的DDS实现，资源不够。怎么办？

最简单的方案就是串口。串口硬件简单，几乎所有MCU都支持。我们需要一个桥梁——在ROS2端封装一个驱动节点，把速度指令通过串口发下去；在MCU端解析串口数据，控制电机，再把里程计数据传回来。

这个桥梁，就是ros2_serial。说白了，它就是一个自定义的串口通信协议，专门为AGV的上下位机通信设计的。

核心思路：ROS2节点 ↔ 串口驱动 ↔ 物理串口 ↔ MCU串口中断 ↔ 电机控制/编码器采集

6.2 自定义消息格式设计

通信协议设计，我建议遵循一个原则：简单、可扩展、带校验。别搞太复杂，否则调试起来想哭。

我常用的帧格式是这样的：

| 帧头(2字节) | 消息ID(1字节) | 数据长度(1字节) | 数据体(N字节) | 校验和(1字节) | 帧尾(1字节) |
| 0xAA 0x55    | 0x01          | 0x08            | ...           | XOR校验       | 0x0A        |

帧头用0xAA 0x55，帧尾用0x0A（换行符），方便调试时用串口助手直接看。消息ID用来区分是速度指令还是里程计反馈。

速度指令消息（ID=0x01）：

| 线速度(m/s) float32 | 角速度(rad/s) float32 |
| 4字节               | 4字节                 |

里程计反馈消息（ID=0x02）：

| 左轮里程(m) float32 | 右轮里程(m) float32 | 左轮速度(m/s) float32 | 右轮速度(m/s) float32 |
| 4字节               | 4字节               | 4字节                 | 4字节                 |

为什么用float32？因为精度够用，而且MCU处理float比double快。我在项目里试过double，结果STM32F103处理起来明显卡顿，后来全改成float了。

6.3 ROS2端驱动编写

ROS2端我们写一个串口驱动节点，用C++实现。核心逻辑就是：订阅/cmd_vel话题，打包成自定义帧，通过串口发出去；同时从串口读取数据，解析成里程计，发布到/odom话题。

代码骨架如下：

class SerialBridge : public rclcpp::Node {
public:
  SerialBridge() : Node("serial_bridge") {
    // 打开串口
    serial_.setPort("/dev/ttyUSB0");
    serial_.setBaudrate(115200);
    serial_.open();

    // 订阅速度指令
    cmd_vel_sub_ = this->create_subscription<geometry_msgs::msg::Twist>(
      "/cmd_vel", 10, std::bind(&SerialBridge::cmdVelCallback, this, _1));

    // 定时读取串口
    timer_ = this->create_wall_timer(
      std::chrono::milliseconds(10), std::bind(&SerialBridge::readSerial, this));
  }

private:
  void cmdVelCallback(const geometry_msgs::msg::Twist::SharedPtr msg) {
    // 打包成自定义帧，通过串口发送
    uint8_t frame[16];
    frame[0] = 0xAA; frame[1] = 0x55;
    frame[2] = 0x01; // 消息ID：速度指令
    frame[3] = 8;    // 数据长度
    memcpy(&frame[4], &msg->linear.x, 4);
    memcpy(&frame[8], &msg->angular.z, 4);
    frame[12] = calcChecksum(frame, 12);
    frame[13] = 0x0A;
    serial_.write(frame, 14);
  }

  void readSerial() {
    // 读取串口数据，解析里程计帧
    // ... 帧同步、校验、解析 ...
    // 发布odom消息
  }

  serial::Serial serial_;
  rclcpp::Subscription<geometry_msgs::msg::Twist>::SharedPtr cmd_vel_sub_;
  rclcpp::TimerBase::SharedPtr timer_;
};

个人经验：串口打开后，建议先发一个空帧测试MCU是否在线。我习惯在驱动初始化时发一个0xAA 0x55 0x00 0x00 0x00 0x0A的“心跳探测帧”，MCU收到后回复一个确认帧。这样一上电就知道通信链路是否正常。

6.4 MCU端接收与DMA收发

MCU端，我强烈建议用DMA接收。为什么？因为串口中断接收在高波特率下容易丢数据。115200波特率，每字节约87微秒，如果中断处理不及时，数据就丢了。

用DMA的话，数据直接由硬件搬运到内存缓冲区，CPU几乎不参与。等一帧数据收完了，再触发一次中断处理即可。

以STM32为例，配置思路：

// 初始化UART+DMA接收
void uart_dma_init(void) {

  // 配置DMA: 循环模式, 接收缓冲区256字节
  // 使能UART空闲中断 (IDLE interrupt)
}

// 空闲中断回调
void HAL_UART_IdleCallback(UART_HandleTypeDef *huart) {
  if (huart->Instance == USART1) {
    // 计算本次接收到的数据长度
    uint16_t len = DMA_RX_BUF_SIZE - __HAL_DMA_GET_COUNTER(huart->hdmarx);
    // 处理接收到的数据帧
    process_frame(rx_buffer, len);
    // 重新启动DMA接收
    HAL_UART_Receive_DMA(huart, rx_buffer, DMA_RX_BUF_SIZE);
  }
}

为什么用空闲中断？因为串口数据是一帧一帧发的，两帧之间会有短暂的“空闲时间”。利用这个空闲中断，可以精确知道一帧数据什么时候结束。这比用固定长度接收灵活多了。

注意：DMA接收缓冲区要足够大，至少是最大帧长的2倍。我曾经设了64字节的缓冲区，结果一帧数据超过64字节就溢出了，查了三天才找到原因。嗯，血的教训。

6.5 数据校验与丢包处理

串口通信在工业现场很容易受干扰。电机启停、电磁干扰，都可能导致数据出错。所以校验必不可少。

我常用的校验方式有两种：

  • 异或校验（XOR）：简单快速，MCU计算几乎不耗时。适合对实时性要求高的场景。
  • CRC8：比XOR可靠，但计算量稍大。我一般在里程计反馈这种关键数据上用CRC8。

丢包处理策略：

  • 超时重发：ROS2端发送速度指令后，如果50ms内没收到MCU的确认帧，就重发一次。
  • 帧序号：在帧头后面加一个1字节的帧序号，MCU收到重复序号就丢弃。防止MCU重复执行同一条指令。
  • 看门狗：MCU端设一个500ms的看门狗定时器。如果超过500ms没收到ROS2的任何帧，就紧急停车。防止ROS2崩溃后AGV失控。

我曾经遇到过一个问题：AGV在仓库里跑得好好的，突然撞墙了。查日志发现，ROS2端发了停车指令，但MCU没收到。从那以后，我就在MCU端加了看门狗，只要通信断了就自动停车。安全第一。

6.6 心跳机制

心跳机制，说白了就是“你还活着吗？”的定期问候。ROS2端每隔100ms发一个心跳帧（ID=0x00），MCU收到后回复一个心跳响应。

心跳帧格式：

| 0xAA | 0x55 | 0x00 | 0x01 | 0x00 | 0x0A |
| 帧头  | 帧头  | ID=0 | 长度1 | 数据0 | 帧尾  |

MCU端的心跳响应：

| 0xAA | 0x55 | 0x00 | 0x01 | 状态字节 | 0x0A |
| 帧头  | 帧头  | ID=0 | 长度1 | 0x01=正常 | 帧尾  |

状态字节可以携带MCU的健康信息，比如：

  • 0x01：一切正常
  • 0x02：电机过流
  • 0x03：编码器故障
  • 0x04：电池电量低

ROS2端如果连续3次没收到心跳响应，就认为通信断了，触发紧急停车流程。这个机制在AGV长时间运行时特别重要。我记得有一次测试，AGV跑了8小时后突然不动了，查日志发现是MCU看门狗复位了，但ROS2端没收到任何通知。加了心跳机制后，这种问题就能第一时间发现。

6.8 调试与测试

通信调试，我建议分三步走：

  1. 裸串口测试：用串口助手直接发十六进制数据，看MCU能不能正确响应。这一步排除硬件问题。
  2. 单帧测试：ROS2端手动发一帧速度指令，看MCU电机是否转动。同时看MCU返回的里程计数据是否正确。
  3. 压力测试：让ROS2以最高频率（比如100Hz）连续发指令，跑一两个小时，看有没有丢包或死机。

我常用的测试工具：

  • Linux端：screen /dev/ttyUSB0 115200 或 minicom
  • Windows端：SSCOM、Putty
  • ROS2端：ros2 topic pub /cmd_vel geometry_msgs/Twist "{linear: {x: 0.5}}"

避坑指南：我曾经在调试时发现，MCU收到的数据总是少一个字节。查了半天，发现是串口线接触不良。嗯，从那以后我调试前都会先检查物理连接。另外，串口波特率一定要两边一致，115200就是115200，别搞成115200和1152000这种低级错误。
