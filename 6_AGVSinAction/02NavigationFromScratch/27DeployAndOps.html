27 AGV部署与运维——从现场到云端，让机器人真正跑起来

说实话，很多团队做AGV项目，研发阶段跑得挺欢，一到现场就翻车。我见过太多案例了——实验室里精度±1cm，到了工厂地面一滩油，直接偏了10cm。所以这一章，我想跟你聊聊真正的「落地」经验。

AGV部署不是把车放地上、画个地图就完事。它是个系统工程。我个人习惯把部署分为三个阶段：环境勘察、地图构建、路径规划。而运维，则是让系统持续稳定运行的生命线。

27.1 现场部署流程

27.1.1 环境勘察——别急着开机，先看场地

我每次去现场，第一件事不是开电脑，而是拿个卷尺和激光测距仪，绕着场地走一圈。为什么？因为很多问题在图纸上看不出来。

环境勘察清单（我自己的checklist）：
  • 地面条件：平整度、摩擦系数、是否有油污/积水。我遇到过环氧地坪反光太强，激光雷达直接「瞎」了的情况。
  • 空间尺寸：通道宽度、转弯半径、门洞高度。AGV的转弯半径不是算出来的，是试出来的。
  • 环境干扰：强光直射（尤其是阳光）、金属反射面、电磁干扰源。嗯，这里要注意——AGV在电梯口附近经常丢定位，因为金属门框反射太严重。
  • 基础设施：充电桩位置、网络覆盖、地面标识（二维码/磁条）是否需要预埋。

我曾经在一个汽车零部件工厂做部署，现场有大量铁屑和切削液。结果AGV的轮子打滑，里程计积分直接漂移。后来我们加了地面清洁流程，才算解决。所以，环境勘察不只是「看」，还要「测」。

27.1.2 地图构建——SLAM不是万能的

地图构建是AGV导航的基础。现在主流是用激光SLAM，但说实话，纯激光SLAM在长走廊、空旷区域容易「飘」。

我建议的流程是这样的：

  1. 手动建图：先让AGV走一遍全场，生成初始地图。这一步要慢，速度控制在0.3m/s以内。
  2. 地图优化：用回环检测修正累积误差。如果场地有电梯或自动门，要单独建子图。
  3. 地图标注：标记禁行区、减速区、充电桩位置、上下料点。这些信息要写入地图文件，而不是写在文档里。
小技巧： 我习惯在地图上额外标注「虚拟墙」——比如AGV不能靠近的货架边缘、不能压到的地标线。这些用多边形区域表示，比单纯依赖传感器避障更可靠。

地图格式我推荐用YAML+PGM的组合，或者用更现代的JSON格式。下面是一个典型的地图配置文件：

# map_config.yaml
map_name: "factory_floor_v2"
resolution: 0.05  # 5cm/pixel
origin: [0.0, 0.0, 0.0]
negate: 0
occupied_thresh: 0.65
free_thresh: 0.25
mode: "trinary"

# 自定义区域
zones:
  - name: "charging_station"
    type: "polygon"
    points: [[12.5, 8.3], [14.2, 8.3], [14.2, 9.8], [12.5, 9.8]]
    action: "dock"
  - name: "slow_down_zone"
    type: "circle"
    center: [20.0, 15.0]
    radius: 2.0
    speed_limit: 0.5  # m/s

27.1.3 路径规划——不是最短路径，是最优路径

很多人以为路径规划就是A*算法找最短路径。但实际部署时，要考虑的东西多得多：

  • 路径平滑性：AGV不能直角转弯，要用贝塞尔曲线或样条曲线做平滑。我见过AGV在直角弯处卡住，因为轮子差速跟不上。
  • 交通管制：多车协同时要避免死锁。我习惯用「路段占用」的方式——每个路段同一时间只允许一辆AGV通过。
  • 动态避障：路径规划要实时更新。遇到临时障碍物，不是重新规划全局路径，而是局部调整。
避坑指南： 我曾经在一个仓库部署时，所有AGV都走同一条主通道，结果高峰期堵成一锅粥。后来我们加了「路径代价动态调整」——拥堵路段自动增加代价，引导AGV绕行。这才解决问题。

下面是一个简单的路径规划伪代码，展示了代价地图的思路：

def plan_path(start, goal, cost_map):
    # cost_map 包含静态障碍物 + 动态拥堵信息
    open_list = PriorityQueue()
    open_list.put(start, 0)
    came_from = {}
    cost_so_far = {start: 0}
    
    while not open_list.empty():
        current = open_list.get()
        if current == goal:
            break
        
        for next in neighbors(current):
            # 基础移动代价 + 拥堵代价 + 安全距离代价
            new_cost = cost_so_far[current] + move_cost(current, next)
            new_cost += congestion_cost(next)  # 动态调整
            new_cost += safety_cost(next)      # 远离货架边缘
            
            if next not in cost_so_far or new_cost < cost_so_far[next]:
                cost_so_far[next] = new_cost
                priority = new_cost + heuristic(goal, next)
                open_list.put(next, priority)
                came_from[next] = current
    
    return reconstruct_path(came_from, start, goal)

27.2 系统运维——让AGV持续稳定运行

部署完了，运维才是大头。我见过太多项目「上线即瘫痪」，就是因为运维没跟上。

27.2.1 日志分析——从日志里看出问题

AGV的日志是诊断问题的第一手资料。我建议日志至少包含以下信息：

日志类型 关键字段 常见问题
定位日志 时间戳、坐标(x,y,theta)、置信度 定位丢失、漂移
运动日志 目标速度、实际速度、轮子编码器值 打滑、电机过载
传感器日志 激光雷达点云数量、IMU加速度 传感器脏污、通信中断
任务日志 任务ID、起点、终点、状态 任务超时、路径阻塞

我个人习惯写一个日志分析脚本，每天自动跑一遍，标记异常。比如定位置信度连续低于0.8超过5秒，就触发告警。你想想看，如果等用户报修才发现问题，那得多被动。

27.2.2 远程升级——别让升级变成灾难

远程升级是运维的必备能力。但升级有风险，操作需谨慎。我总结了几条铁律：

  • 灰度发布：先升级1-2台车，观察24小时，没问题再全量升级。
  • 回滚方案：每次升级前备份当前版本。我遇到过升级后地图格式不兼容，直接回滚才救回来。
  • 升级窗口：选择非生产时段升级。比如夜班或周末。
我的做法： 升级包用差分方式传输，只传变更的文件。一个完整的AGV固件可能有500MB，但每次升级可能只改几个KB。差分升级能节省大量带宽和时间。

27.2.3 故障诊断——快速定位问题

AGV常见的故障就那么几类，我整理了一个快速诊断表：

现象 可能原因 排查步骤
AGV定位丢失 激光雷达被遮挡、地面特征变化 1. 检查雷达窗口是否脏污
2. 查看最近是否有货架移动
AGV走偏 轮子磨损、编码器故障 1. 检查轮子胎压
2. 对比左右编码器数值
任务超时 路径阻塞、交通管制死锁 1. 查看任务路径
2. 检查其他AGV位置
通信中断 WiFi信号弱、路由器重启 1. 检查信号强度
2. 查看网络日志

我曾经遇到一个诡异的问题——AGV每天下午3点准时丢定位。排查了三天，最后发现是那个时间段太阳光正好直射到激光雷达接收窗口。嗯，这种环境问题，光看代码是看不出来的。

27.3 OTA升级方案——让AGV自己「进化」

OTA（Over-The-Air）升级是AGV运维的终极形态。不用派人到现场，不用插U盘，远程就能完成固件升级、地图更新、参数调整。

一个完整的OTA方案包含这几个部分：

  • 升级服务器：管理版本、分发升级包、记录升级日志。
  • 升级客户端：运行在AGV上，负责下载、校验、安装。
  • 升级策略：什么时候升级、怎么升级、失败了怎么办。

下面是一个简化的OTA升级流程：

# OTA升级流程（伪代码）
def ota_update(agv_id, target_version):
    # 1. 检查当前版本
    current_version = get_current_version(agv_id)
    if current_version == target_version:
        return "already up-to-date"
    
    # 2. 获取升级包
    update_package = download_package(agv_id, target_version)
    if not verify_checksum(update_package):
        return "checksum error"
    
    # 3. 备份当前系统
    backup_system(agv_id)
    
    # 4. 应用升级
    apply_update(update_package)
    
    # 5. 重启验证
    reboot_agv(agv_id)
    if verify_version(agv_id, target_version):
        return "success"
    else:
        rollback(agv_id)
        return "rollback"
注意： OTA升级一定要有「断点续传」和「失败回滚」机制。我见过一个项目，升级到一半网络断了，AGV直接变砖。后来我们加了双分区设计——一个分区运行当前系统，另一个分区用来安装升级包。安装成功后再切换启动分区。

OTA升级的版本管理也很重要。我习惯用语义化版本号：主版本.次版本.修订号。比如v2.1.3，主版本2表示大架构变更，次版本1表示新功能，修订号3表示bug修复。这样一看版本号，就知道升级的影响范围。
