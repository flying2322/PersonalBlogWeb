22 AGV仿真环境搭建

说实话，做AGV导航最怕什么？不是算法调不通，而是你写了几千行代码，一上真车就把价值几十万的设备撞了。我入行第三年就干过这事——那天晚上调试路径规划，一个参数没设对，AGV直接怼上了货架腿。还好速度不快，但从此以后，我养成了个习惯：先仿真，再上车。

这一章，咱们就聊聊怎么搭一套完整的AGV仿真环境。从Gazebo配置、URDF模型编写，到传感器配置、地图构建，最后跑通多车仿真。嗯，内容不少，但每一步我都会把踩过的坑告诉你。

核心目标：搭建一个可复用的AGV仿真测试平台，让算法验证成本降到零。

22.1 Gazebo仿真环境搭建

Gazebo这东西，说白了就是一个带物理引擎的3D仿真器。它和ROS是天生的搭档——你发布/cmd_vel，它就让小车动起来；小车撞墙了，它会反馈真实的碰撞力。

我个人习惯用Gazebo 9以上的版本，配合ROS Melodic或Noetic。安装其实很简单：

sudo apt-get install ros-noetic-gazebo-ros-pkgs ros-noetic-gazebo-ros-control

装完之后，跑一下gazebo命令，如果能看到一个空荡荡的世界窗口，那就成了。

但这里有个坑——Gazebo默认的物理引擎是ODE，精度一般。我在做重载AGV仿真时，发现ODE算出来的轮胎摩擦力总是不对。后来换成了Bullet引擎，效果好了不少。切换方法：

<physics type="bullet">
  <max_step_size>0.001</max_step_size>
  <real_time_update_rate>1000</real_time_update_rate>
</physics>

小技巧：仿真步长设0.001秒，更新率1000Hz，这样碰撞检测才够准。步长设大了，小车可能会“穿模”——直接穿过障碍物。

22.2 AGV模型URDF编写

URDF是啥？就是描述机器人长什么样的XML文件。轮子多大、底盘多重、传感器装在哪，全写在这里面。

我刚开始写URDF时，总想把所有细节都画进去——螺丝、倒角、散热孔……后来发现完全没必要。Gazebo仿真里，碰撞模型越简单越好。你想想看，一个带48个螺丝孔的底盘，碰撞检测要算多久？

下面是一个典型的AGV底盘URDF结构：

<robot name="agv_base">
  <link name="base_link">
    <visual>
      <geometry>
        <box size="0.8 0.6 0.3"/>
      </geometry>
      <material name="blue"/>
    </visual>
    <collision>
      <geometry>
        <box size="0.8 0.6 0.3"/>
      </geometry>
    </collision>
    <inertial>
      <mass value="50.0"/>
      <inertia ixx="1.0" ixy="0.0" ixz="0.0"
               iyy="1.0" iyz="0.0" izz="1.0"/>
    </inertial>
  </link>

  <joint name="left_wheel_joint" type="continuous">
    <parent link="base_link"/>
    <child link="left_wheel"/>
    <origin xyz="-0.3 0.4 -0.15" rpy="0 0 0"/>
    <axis xyz="0 1 0"/>
  </joint>
</robot>

这里要注意几个点：

  • visual和collision要分开：视觉模型可以精细，碰撞模型用简单几何体包络就行
  • 惯性参数别乱填：质量设对了，惯性矩阵用0.1 * mass * size^2估算
  • 关节类型选对：驱动轮用continuous，转向轮用revolute

我曾经踩过的坑：URDF里忘了加<gazebo>标签配置传动，结果小车在仿真里怎么发指令都不动。折腾了两天才发现，原来是少了<transmission>和<hardwareInterface>。

22.3 仿真传感器配置

AGV导航离不开传感器。最常用的就是激光雷达和IMU。在Gazebo里配置传感器，其实就是在URDF里加对应的<gazebo>插件。

先看激光雷达的配置：

<gazebo reference="laser_link">
  <sensor type="ray" name="head_laser">
    <pose>0 0 0.2 0 0 0</pose>
    <visualize>true</visualize>
    <update_rate>10</update_rate>
    <ray>
      <scan>
        <horizontal>
          <samples>360</samples>
          <resolution>1</resolution>
          <min_angle>-3.14159</min_angle>
          <max_angle>3.14159</max_angle>
        </horizontal>
      </scan>
      <range>
        <min>0.1</min>
        <max>30.0</max>
        <resolution>0.01</resolution>
      </range>
      <noise>
        <type>gaussian</type>
        <mean>0.0</mean>
        <stddev>0.01</stddev>
      </noise>
    </ray>
  </sensor>
</gazebo>

这里有个细节——噪声模型一定要加。我见过很多人在仿真里用完美传感器数据，算法跑得飞起，一上真车就崩。为什么？因为真实激光雷达是有噪声的，距离越远噪声越大。加上高斯噪声，才能模拟真实场景。

IMU的配置相对简单：

<gazebo reference="imu_link">
  <sensor type="imu" name="imu_sensor">
    <pose>0 0 0 0 0 0</pose>
    <update_rate>100</update_rate>
    <imu>
      <noise>
        <type>gaussian</type>
        <rate>
          <mean>0.0</mean>
          <stddev>0.0002</stddev>
        </rate>
      </noise>
    </imu>
  </sensor>
</gazebo>

我的建议：传感器更新率别设太高。激光雷达10Hz、IMU 100Hz就够用了。设太高了，CPU扛不住，仿真就跑不动了。

22.4 仿真地图构建

地图是导航的基础。Gazebo里建地图有两种方式：

  1. 用Building Editor手绘：适合简单场景，拖拽墙壁、添加障碍物
  2. 导入CAD模型：适合工厂级场景，把真实的厂房布局导进来

我个人更推荐第二种。为什么？因为仿真最终要服务于真车部署。你拿一张和真实工厂一模一样的地图来测算法，测出来的结果才有参考价值。

下面是一个简单的地图文件示例（world格式）：

<sdf version="1.6">
  <world name="warehouse">
    <include>
      <uri>model://sun</uri>
    </include>
    <include>
      <uri>model://ground_plane</uri>
    </include>
    <model name="wall_01">
      <static>true</static>
      <link name="body">
        <collision name="collision">
          <geometry>
            <box size="10 0.2 2"/>
          </geometry>
        </collision>
        <visual name="visual">
          <geometry>
            <box size="10 0.2 2"/>
          </geometry>
        </visual>
      </link>
      <pose>0 5 1 0 0 0</pose>
    </model>
  </world>
</sdf>

地图建好后，记得用map_server生成栅格地图。这一步很多人会忘——Gazebo里跑的是3D世界，但导航算法用的是2D代价地图。你需要把3D世界投影成2D栅格，算法才能用。

22.5 多AGV仿真测试

单台AGV跑通了，接下来就是多车协同。这才是真正考验系统的地方。

多AGV仿真，核心要解决三个问题：

  • 命名空间隔离：每台AGV的topic不能冲突，比如/agv1/cmd_vel、/agv2/cmd_vel
  • 碰撞避免：多车在同一场景里跑，不能互相撞上
  • 资源调度：交叉路口、狭窄通道，谁先过谁后过

启动多车仿真的launch文件大概长这样：

<launch>
  <group ns="agv1">
    <include file="$(find agv_description)/launch/spawn_agv.launch">
      <arg name="x" value="0.0"/>
      <arg name="y" value="0.0"/>
      <arg name="yaw" value="0.0"/>
    </include>
  </group>

  <group ns="agv2">
    <include file="$(find agv_description)/launch/spawn_agv.launch">
      <arg name="x" value="2.0"/>
      <arg name="y" value="0.0"/>
      <arg name="yaw" value="0.0"/>
    </include>
  </group>
</launch>

这里有个关键点——每台AGV的初始位置不能重叠。我曾经犯过这个错，两台车刷在同一个坐标上，结果Gazebo物理引擎直接炸了，两台车疯狂抖动，最后飞出了地图。

多车仿真的核心逻辑：

多车仿真调试时，我建议先用rqt_graph看看节点和topic的连接关系。如果发现/agv1/odom被/agv2的节点订阅了，那肯定有问题——命名空间没隔离干净。

重要提醒：多车仿真对电脑性能要求很高。每增加一台AGV，CPU占用率大概涨15%-20%。我一般最多同时跑4台车，再多就卡成PPT了。如果非要跑更多，可以考虑用分布式仿真——把不同AGV分配到不同电脑上跑。

好了，仿真环境搭好了，接下来就可以愉快地调算法了。记住一句话：仿真里跑不通的，真车上一定跑不通；仿真里跑得通的，真车上也不一定跑得通。但至少，仿真能帮你过滤掉80%的低级错误。
