17 AGV调度系统架构设计：调度系统功能需求（任务分配/路径规划/交通管制）、调度系统架构（中心化/去中心化）、RESTful API设计、WebSocket实时通信

调度系统，说白了就是AGV车队的「大脑」。

我做了这么多年AGV项目，见过太多「车跑起来了，但调度一塌糊涂」的案例。车多了，没有调度系统，那就是一锅粥。今天咱们就把这个大脑的架构拆开看看。

17.1 调度系统的三大核心功能

调度系统要干的事，其实就三件：任务分配、路径规划、交通管制。这三件事环环相扣，缺一不可。

17.1.1 任务分配

任务分配，就是「谁来干这个活」。系统收到一个搬运指令，比如「把A点的货送到B点」，它得决定派哪台车去。

我习惯把任务分配策略分为两类：

  • 就近分配：谁离任务起点近，谁去。简单粗暴，但容易造成「热门区域车扎堆」。
  • 负载均衡：看每台车的任务队列长度，谁的任务少，谁去。适合长距离、多任务的场景。

我在项目中遇到过一个问题：某工厂有30台AGV，用了就近分配，结果仓库门口堵了8台车等着接单，远处的车却闲着。后来改成了「综合评分法」——把距离、电量、当前任务数加权打分，才解决了。

避坑指南：任务分配时，一定要考虑「电量阈值」。我曾经见过一台车电量只剩10%，还被分配了一个需要跑20分钟的任务，结果半路趴窝，堵了整条产线。

17.1.2 路径规划

路径规划，就是「怎么走」。注意，这里的路径规划和单车的路径规划不一样。单车规划只考虑自己，调度系统的路径规划要考虑全局。

调度系统通常维护一张全局路网图，所有AGV都在这张图上跑。路径规划的核心算法，我常用的是：

  • A* 算法：静态路径规划，适合已知环境。计算快，但遇到动态障碍物就抓瞎。
  • D* Lite：动态路径规划，适合环境变化频繁的场景。我有个项目在电商仓库，货架经常变动，D* Lite 比 A* 好使多了。

嗯，这里要注意：路径规划的结果不是一成不变的。车走到一半，前面突然有障碍物，调度系统要能实时重规划。

17.1.3 交通管制

交通管制，是调度系统最头疼的部分。多台AGV在狭窄通道里相遇，谁让谁？

我总结了几种常见的管制策略：

策略 原理 适用场景
路口互斥锁 每个路口一把锁，谁先申请到谁先过 简单路口，车流量小
优先级通行 根据任务紧急程度决定谁先走 产线对接，有急单时
死锁检测与恢复 检测到死锁后，让某台车倒车让路 复杂多岔路口

我曾经在一个项目里，两台AGV在T型路口面对面堵了3分钟，就是因为死锁检测没做好。后来我加了一个「超时回退」机制——如果某台车在路口等待超过5秒，自动后退1米，给对面让路。

注意：交通管制不能只靠单车决策。单车看到对面有车，可能会「礼貌让行」，但两台车互相让，反而堵死了。必须由调度系统统一裁决。

17.2 调度系统架构：中心化 vs 去中心化

架构选型，是调度系统的「灵魂」。选错了，后面全是坑。

17.2.1 中心化架构

中心化架构，就是所有AGV都听一个「中央大脑」的指挥。这个大脑负责所有任务分配、路径规划和交通管制。

优点很明显：

  • 全局最优：大脑能看到所有车的状态，能做出全局最优决策。
  • 实现简单：所有逻辑集中在一处，调试方便。

缺点也致命：

  • 单点故障：大脑挂了，所有车都瘫痪。
  • 性能瓶颈：车多了（比如超过50台），大脑的CPU和网络带宽可能扛不住。

我个人的习惯是：50台以下，用中心化。简单、稳定、好维护。

17.2.2 去中心化架构

去中心化架构，就是每台AGV自己决策，通过「协商」来完成任务。没有中央大脑，每台车都是「小脑」。

优点：

  • 高可用：一台车挂了，其他车不受影响。
  • 可扩展：加车容易，不用升级中央服务器。

缺点：

  • 局部最优：每台车只考虑自己，容易产生「囚徒困境」。
  • 实现复杂：需要设计复杂的通信协议和协商机制。

我建议：100台以上，或者对可用性要求极高的场景（比如港口、机场），考虑去中心化。但要做好心理准备，调试起来很痛苦。

我的经验：很多项目其实用的是「混合架构」——任务分配和路径规划中心化，交通管制去中心化。这样既保证了全局最优，又避免了单点故障。

17.3 RESTful API 设计

调度系统不是孤岛，它要和MES、WMS、上位机等系统交互。RESTful API 就是它们之间的「语言」。

我设计API时，遵循几个原则：

  • 资源导向：每个API对应一个资源，比如 /tasks、/robots、/maps。
  • 动词用HTTP方法：GET查、POST创建、PUT更新、DELETE删除。
  • 版本控制：URL里带版本号，比如 /v1/tasks。

举个例子，任务相关的API：

// 创建任务
POST /v1/tasks
{
    "type": "transport",
    "from": "A01",
    "to": "B03",
    "priority": 1
}

// 查询任务状态
GET /v1/tasks/{task_id}

// 取消任务
DELETE /v1/tasks/{task_id}

嗯，这里要注意：API的响应要统一格式。我习惯用：

{
    "code": 200,
    "message": "success",
    "data": { ... }
}

这样前端和第三方系统解析起来就方便多了。

避坑指南：我曾经见过一个项目，API返回的字段名一会儿用下划线（task_id），一会儿用驼峰（taskId），结果前端解析时各种报错。统一命名规范，很重要。

17.4 WebSocket 实时通信

RESTful API 适合「一问一答」，但AGV的状态是实时变化的——位置、速度、电量、任务进度……这些信息如果靠前端轮询，效率太低。

这时候就需要 WebSocket 了。它建立一条长连接，服务端可以主动推送数据给客户端。

我常用的WebSocket消息格式：

// 服务端推送AGV位置更新
{
    "type": "robot_position",
    "robot_id": "AGV_001",
    "x": 12.5,
    "y": 8.3,
    "timestamp": 1700000000
}

// 服务端推送任务状态变更
{
    "type": "task_status",
    "task_id": "TASK_123",
    "status": "in_progress",
    "robot_id": "AGV_001"
}

WebSocket 的好处是：

  • 低延迟：毫秒级推送，适合实时监控。
  • 节省带宽：不用频繁建立HTTP连接。

但也要注意：WebSocket 连接数有限。如果同时有几十个监控客户端，每个都建立一条WebSocket，服务端压力会很大。我建议用「订阅模式」——客户端只订阅自己关心的数据，比如只订阅某台车的状态。

我的习惯：WebSocket 只推送「变化的数据」。比如AGV位置，如果没变化，就不推送。这样可以大幅减少网络流量。
