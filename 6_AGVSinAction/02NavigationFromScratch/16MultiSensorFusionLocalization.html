16 AGV多传感器融合定位：扩展卡尔曼滤波（EKF）原理、robot_localization包使用、IMU+里程计+激光雷达融合、全局定位与局部定位切换

各位同学，欢迎来到第16章。今天聊的话题，是AGV导航里最核心、也最容易让人头疼的一块——多传感器融合定位。

说实话，单传感器定位在实验室里跑得挺欢，一上产线就原形毕露。轮子打滑、激光被遮挡、IMU漂移……哪个都能让你的AGV“迷路”。我当年调试第一台AGV时，就吃过这个亏。轮子在地面有水渍的地方空转，里程计直接报出两倍距离，车一头撞上了货架。从那以后，我再也不敢只用单一传感器了。

多传感器融合，说白了就是“三个臭皮匠，顶个诸葛亮”。今天我们就来拆解这个“诸葛亮”——扩展卡尔曼滤波（EKF），以及它在ROS生态里的实战工具robot_localization。

核心观点：EKF不是银弹，但它是目前工业AGV上最成熟、最稳定的融合方案。理解它的“线性化”本质，你就掌握了80%的调试技巧。

16.1 扩展卡尔曼滤波（EKF）原理：从线性到非线性的跨越

经典卡尔曼滤波（KF）假设系统是线性的。但AGV的运动模型、观测模型，几乎没有线性的。你想想看，激光雷达测距是极坐标，里程计是增量编码，IMU输出的是加速度和角速度——这些怎么线性？

EKF的思路很直接：把非线性函数在当前状态附近做一阶泰勒展开，近似成线性模型。说白了，就是“用切线代替曲线”。

EKF的核心流程分两步：预测（Predict）和更新（Update）。

16.1.1 预测阶段

预测阶段，我们用运动模型（比如两轮差速模型）来推算下一时刻的状态。假设状态向量为 x = [x, y, yaw, vx, vy, yaw_rate]，那么预测方程就是：

x_k|k-1 = f(x_{k-1}|k-1, u_k) + w_k

其中 f 是非线性函数，u_k 是控制输入（比如里程计的线速度和角速度），w_k 是过程噪声。

同时，我们还要预测协方差矩阵 P：

P_k|k-1 = F_k * P_{k-1}|k-1 * F_k^T + Q_k

这里的 F_k 就是 f 的雅可比矩阵。嗯，这里要注意：雅可比矩阵算不对，EKF直接发散。我早期写代码时，雅可比矩阵的偏导算错了一个符号，结果滤波器输出疯狂震荡，查了两天才找到问题。

16.1.2 更新阶段

更新阶段，我们用观测数据（比如激光雷达的点云匹配结果、IMU的姿态）来修正预测值。

y_k = z_k - h(x_k|k-1)   // 残差
S_k = H_k * P_k|k-1 * H_k^T + R_k   // 残差协方差
K_k = P_k|k-1 * H_k^T * S_k^{-1}   // 卡尔曼增益
x_k|k = x_k|k-1 + K_k * y_k   // 状态更新
P_k|k = (I - K_k * H_k) * P_k|k-1   // 协方差更新

H_k 是观测模型 h 的雅可比矩阵。R_k 是观测噪声协方差矩阵——这个参数调得好不好，直接决定融合效果。

个人经验：调EKF时，我习惯先调 R 矩阵（观测噪声），再调 Q 矩阵（过程噪声）。因为 R 更直观——激光雷达的噪声水平你可以通过静态测量估算出来。而 Q 更多是玄学，需要根据运动剧烈程度反复试。

16.2 robot_localization包使用：ROS生态里的EKF利器

自己手写EKF？没必要。robot_localization 是ROS社区里最成熟的EKF实现，支持多传感器输入、时间戳管理、协方差传递。我所有项目都直接用这个包，省心。

16.2.1 安装与配置

sudo apt install ros-noetic-robot-localization

核心配置文件是一个YAML文件，定义传感器输入、输出坐标系、频率等。下面是一个典型配置：

ekf_filter_node:
  ros__parameters:
    frequency: 30.0
    sensor_timeout: 0.1
    two_d_mode: true
    publish_tf: true
    map_frame: map
    odom_frame: odom
    base_link_frame: base_link
    world_frame: odom

    odom0: /odom
    odom0_config: [true, true, false,
                   false, false, true,
                   false, false, false,
                   false, false, false,
                   false, false, false]
    odom0_queue_size: 10
    odom0_differential: false
    odom0_relative: false

    imu0: /imu/data
    imu0_config: [false, false, false,
                  false, false, false,
                  true, true, true,
                  false, false, false,
                  false, false, false]
    imu0_queue_size: 10
    imu0_differential: false
    imu0_relative: false

注意 odom0_config 和 imu0_config 这两个数组。每个数组有15个布尔值，对应状态向量的15个维度（x, y, z, roll, pitch, yaw, vx, vy, vz, vroll, vpitch, vyaw, ax, ay, az）。true 表示该传感器提供这个维度的信息。

避坑指南：我曾经把 odom0_config 的yaw维度设成了 false，结果里程计的航向信息没有被融合，AGV在原地打转。检查配置时，一定要确认每个传感器的有效维度都正确标记了。

16.2.2 启动文件

<launch>
  <node pkg="robot_localization" type="ekf_node" name="ekf_filter_node">
    <rosparam command="load" file="$(find my_robot)/config/ekf.yaml" />
  </node>
</launch>

16.3 IMU+里程计+激光雷达融合：实战配置

现在我们来搭建一个完整的融合系统。传感器配置如下：

传感器 频率 提供信息 噪声特性
里程计（轮式编码器） 50 Hz x, y, yaw, vx, vyaw 低频漂移，打滑时误差大
IMU（9轴） 100 Hz roll, pitch, yaw, angular_velocity, linear_acceleration 高频噪声大，但短期精度高
激光雷达（2D） 10 Hz x, y, yaw（通过AMCL或ICP匹配） 绝对精度高，但更新慢，易受环境遮挡

融合策略：

  • 高频更新：IMU和里程计以50-100Hz的频率进行EKF预测，提供平滑的位姿估计。
  • 低频修正：激光雷达以10Hz的频率进行EKF更新，消除里程计和IMU的累积误差。
  • 时间戳对齐：robot_localization 内部会处理时间戳，但你需要确保所有传感器消息的时间戳是准确的。我遇到过IMU时间戳是0的情况，导致滤波器直接罢工。

配置示例（在原有YAML基础上增加激光雷达输入）：

    odom0: /odom
    odom0_config: [true, true, false,
                   false, false, true,
                   true, false, false,
                   false, false, true,
                   false, false, false]

    imu0: /imu/data
    imu0_config: [false, false, false,
                  false, false, false,
                  false, false, false,
                  true, true, true,
                  true, true, true]

    laser0: /laser_odom
    laser0_config: [true, true, false,
                    false, false, true,
                    false, false, false,
                    false, false, false,
                    false, false, false]
    laser0_queue_size: 5

个人习惯：我会把激光雷达的协方差矩阵设得比里程计小一些（比如 R 矩阵对角线元素设为0.01），因为激光雷达的绝对精度更高。但如果你在动态环境中（比如人走来走去），激光雷达的匹配可能会失败，这时需要适当增大协方差，或者加入异常检测逻辑。

16.4 全局定位与局部定位切换：从“我在哪”到“我该去哪”

AGV的定位系统通常分两层：

  • 全局定位：在全局地图（map坐标系）中确定AGV的绝对位姿。通常由AMCL或基于激光雷达的全局匹配算法提供。
  • 局部定位：在里程计坐标系（odom坐标系）中，通过EKF融合IMU和里程计，提供高频、平滑的相对位姿。

切换策略：

  1. 启动时：先进行全局定位（比如AMCL初始化），得到初始位姿后，将map到odom的变换发布出去。
  2. 正常运行时：以局部定位为主（EKF输出odom到base_link的变换），全局定位作为“慢速修正”。
  3. 异常恢复：当局部定位误差超过阈值（比如位置偏差>0.5m），触发全局重定位。

在ROS中，robot_localization 的 world_frame 参数决定了定位的参考系：

  • world_frame: odom：输出odom到base_link的变换，用于局部定位。
  • world_frame: map：输出map到base_link的变换，用于全局定位。

我通常的做法是：运行两个EKF节点，一个输出odom->base_link（局部），另一个输出map->base_link（全局）。然后通过一个状态机来切换使用哪个位姿。

避坑指南：千万不要在运行时直接切换 world_frame 参数，这会导致坐标系跳变。正确的做法是：保持局部EKF一直运行，全局EKF只在需要时激活，并通过一个平滑过渡（比如线性插值）来切换位姿。

16.6 总结与避坑清单

最后，我整理了一份避坑清单，都是我在项目中踩过的坑：

  • 时间戳问题：所有传感器消息的时间戳必须准确。IMU和里程计的时间戳偏差超过10ms，EKF就会震荡。
  • 协方差初始化：不要用默认值。激光雷达的协方差设太小，会导致EKF过度信任它，一旦匹配失败就发散。
  • 坐标系一致性：确保所有传感器发布的坐标系与 base_link 的变换关系正确。我见过有人把IMU装在车尾，但配置里写的是车头，结果融合出来的姿态一直在抖。
  • 频率匹配：EKF的更新频率不要低于所有传感器的最低频率。如果激光雷达只有10Hz，EKF频率设为30Hz就够了，设太高反而浪费算力。
  • 全局定位切换：切换时一定要做平滑过渡，否则AGV会“瞬移”，导致路径规划崩溃。
