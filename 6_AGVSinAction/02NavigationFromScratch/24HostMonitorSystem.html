24 AGV上位机监控系统开发

说到AGV的上位机监控，我脑子里第一个蹦出来的画面，就是几年前在客户现场调试的场景。几十台AGV在地图上跑来跑去，调度系统疯狂发指令，而我盯着那个简陋的监控界面，心里只有一个念头——这玩意儿必须重做。

上位机监控系统，说白了就是AGV车队的「驾驶舱」。你坐在办公室里，通过这个界面就能知道每台车在哪儿、跑多快、还有多少电、有没有报错。甚至可以直接给某台车发指令，让它去充电或者紧急停车。

我个人习惯把监控系统分成三层：数据采集层、业务逻辑层、前端展示层。今天咱们重点聊前端展示层，也就是你用Qt或者Web技术做出来的那个界面。

24.1 技术选型：Qt还是Web？

这个问题我经常被问到。我的回答是：看场景。

对比项 Qt（C++/QML） Web（Vue/React）
实时性 极高，直接操作硬件 高，依赖WebSocket
跨平台 需要编译 浏览器即可
开发效率 中等 高
部署难度 需要安装包 打开浏览器就行
典型场景 工厂现场、工控机 远程监控、多用户

我在项目中遇到过这样的情况：客户要求监控界面必须跑在工控机上，而且不能装浏览器。那没得选，只能用Qt。但如果是给管理层看的大屏展示，或者需要远程访问，Web前端明显更合适。

我的建议： 如果你刚开始做，先用Web快速出原型。等业务稳定了，再考虑用Qt做本地化部署。别一上来就搞Qt，调试起来真的挺折磨人的。

24.2 实时数据显示：位置、速度、电量、状态

实时数据是监控系统的灵魂。你想想看，如果数据延迟了5秒，那地图上的AGV位置就是错的，调度指令发出去可能就撞车了。

我一般用WebSocket来推送数据。后端每100ms发一次数据包，前端收到后直接更新UI。数据格式长这样：

{
  "agv_id": "AGV-001",
  "timestamp": 1712345678,
  "position": {
    "x": 12.5,
    "y": 8.3,
    "theta": 1.57
  },
  "speed": 1.2,
  "battery": 85,
  "status": "running"
}

前端拿到数据后，要做三件事：

  • 更新地图上的位置：把AGV图标移动到新的坐标点
  • 刷新仪表盘：速度表、电量条、状态灯
  • 记录历史点：用于轨迹回放

这里有个坑，我曾经踩过。如果数据更新频率太高（比如10ms一次），UI会疯狂重绘，CPU直接拉满。后来我加了防抖和节流，把渲染频率控制在50ms一次，效果好了很多。

注意： 电量显示不要直接用百分比，要加一个「电压补偿」算法。因为AGV在加速时电压会瞬间下降，直接显示会导致电量条来回跳。我一般取最近10秒的平均值。

24.3 历史轨迹回放

轨迹回放这个功能，说实话，平时用得不多。但一旦出问题，它就是救命稻草。

我记得有一次，客户说AGV在某个拐角处突然急停，但日志里没有任何报错。我调出轨迹回放，一帧一帧地看，发现AGV在那个位置的速度曲线有一个诡异的尖峰。后来查出来是地面有个小坑，轮子打滑了。

实现轨迹回放，核心是数据存储和播放控制：

// 伪代码：轨迹回放逻辑
class TrajectoryPlayer {
  constructor(data) {
    this.data = data;  // 历史数据数组
    this.index = 0;
    this.speed = 1.0;  // 播放速度倍率
  }

  play() {
    setInterval(() => {
      const point = this.data[this.index];
      updateMapPosition(point);
      updateDashboard(point);
      this.index++;
      if (this.index >= this.data.length) {
        this.stop();
      }
    }, 100 / this.speed);
  }

  pause() { /* 清除定时器 */ }
  seek(time) { /* 跳转到指定时间点 */ }
}

前端展示时，我习惯用两种模式：

  • 实时模式：AGV走过的路径用淡蓝色线条显示，当前点用亮色
  • 回放模式：可以拖动进度条，速度可调（0.5x、1x、2x、4x）

数据量大的时候要注意。如果AGV跑了8小时，每秒存一个点，那就是28800个点。全部渲染到地图上，浏览器会卡死。我的做法是：回放时只加载当前视野内的点，或者做降采样处理。

24.4 远程控制指令下发

远程控制，说白了就是你在办公室里点一下按钮，AGV就得执行。这个功能看着简单，但安全性要求极高。

我一般把指令分成几个等级：

指令等级 示例 安全要求
L1 - 普通 修改速度、切换任务 需要二次确认
L2 - 重要 去充电、回原点 需要密码验证
L3 - 紧急 急停、锁定 一键执行，但记录日志

前端发送指令的流程是这样的：

  1. 用户点击按钮，弹出确认框（L1/L2）或直接发送（L3）
  2. 前端生成指令JSON，通过WebSocket发送到后端
  3. 后端校验权限和AGV状态，转发给对应的AGV
  4. AGV执行后返回结果，前端更新状态
// 前端发送指令示例
function sendCommand(agvId, command, params) {
  const msg = {
    type: "command",
    agv_id: agvId,
    command: command,
    params: params,
    timestamp: Date.now()
  };
  websocket.send(JSON.stringify(msg));
}

// 调用：让AGV-001去充电
sendCommand("AGV-001", "goto_charge", { station: "C-01" });
核心原则： 远程控制一定要有「指令确认」和「执行反馈」两个环节。我曾经见过一个系统，指令发出去了，但AGV没收到，操作员以为执行了，结果AGV还在原地。后来我们加了一个「指令超时重发」机制，才彻底解决这个问题。

24.6 开发中的几个实用技巧

最后分享几个我在实际开发中积累的小技巧：

  • 地图坐标系统一：AGV的坐标、地图的坐标、前端显示的坐标，必须用同一个坐标系。我吃过这个亏，AGV明明在A点，地图上显示在B点，查了半天发现是坐标系没对齐。
  • 数据缓存：前端不要只依赖实时推送。如果网络断了，界面就全黑了。我一般会在本地缓存最近5分钟的数据，断网时显示「离线模式」，至少让操作员知道AGV最后的位置。
  • 状态机设计：AGV的状态不要用字符串，用枚举。比如：0=空闲、1=运行、2=充电、3=故障、4=急停。这样前端做状态判断时，直接比较数字，效率高很多。
  • 日志分级：监控系统会产生大量日志。我一般分三级：INFO（正常操作）、WARN（异常但可恢复）、ERROR（需要人工介入）。前端只显示WARN和ERROR，INFO存到后台文件里。
一个小彩蛋： 我习惯在监控界面上加一个「心跳灯」。如果WebSocket连接正常，绿灯闪烁；如果断开，红灯常亮。这个小东西帮我在现场快速定位过好几次网络问题。

嗯，关于AGV上位机监控系统的开发，核心内容差不多就是这些。从技术选型到实时数据显示，从轨迹回放到远程控制，每一步都有坑，但也都有解法。你动手做的时候，肯定会遇到比我更多的奇葩问题——没关系，这就是工程师的日常。
