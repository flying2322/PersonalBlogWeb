18 AGV交通管制与多车协同：多AGV冲突检测、交通管制策略（锁区/优先级/等待）、死锁检测与解除、编队行驶算法、多车协同仿真

多车协同，说白了就是让一群AGV在同一个场地里干活，还不打架、不堵车、不卡死。

我刚开始做AGV系统时，觉得单机导航搞定就行了。结果第一次多车联调，三台车在十字路口堵成一团，调度员直接崩溃。嗯，从那以后我才真正重视起交通管制这块。

18.1 多AGV冲突检测

冲突检测是交通管制的前提。你连冲突都发现不了，谈何解决？

常见的冲突类型有三种：

  • 节点冲突：多台AGV同时要占用同一个路径节点
  • 相向冲突：两台AGV在同一条路径上面对面行驶
  • 交叉冲突：AGV在交叉路口路径交叉

我个人习惯用时空占用网格法来做冲突检测。说白了就是把地图划分成网格，每台AGV预占未来N秒内的网格，然后检查是否有重叠。

// 伪代码：时空占用网格冲突检测
function detectConflict(agvList, mapGrid, timeHorizon):
    for each agv in agvList:
        // 预测未来路径
        path = predictPath(agv, timeHorizon)
        for each (position, time) in path:
            gridKey = hash(position, time)
            if gridKey in occupiedGrids:
                return CONFLICT_DETECTED(agv, occupiedGrids[gridKey])
            occupiedGrids[gridKey] = agv.id
    return NO_CONFLICT
我的经验：时间窗口别设太大，3-5秒就够了。设太大反而容易误报，AGV稍微停一下就被判定为冲突。

18.2 交通管制策略

检测到冲突后，怎么处理？我常用的策略有三种：锁区、优先级、等待。

18.2.1 锁区策略

锁区是最简单粗暴的方式。把冲突区域锁起来，只允许一台AGV进入。

  • 静态锁区：提前划分好锁区区域，比如十字路口、窄通道
  • 动态锁区：根据AGV实时位置动态生成锁区范围

我在项目中遇到过一个问题：锁区范围设太大，导致整体效率下降30%。后来改成动态锁区，只锁AGV前后2米的范围，效率明显提升。

18.2.2 优先级策略

给每台AGV分配优先级，高优先级的先走。

优先级类型 说明 适用场景
任务优先级 紧急任务优先 产线急单、异常处理
距离优先级 离冲突点近的优先 减少绕路成本
时间优先级 先到先服务 公平调度

你想想看，如果两台AGV同时要过同一个路口，让离得近的先走，是不是更合理？

18.2.3 等待策略

低优先级的AGV在冲突点前等待，直到高优先级的通过。

注意：等待策略容易引发死锁。我曾经遇到过三台AGV互相等待，形成一个环，谁都不让谁。这种情况必须配合死锁检测机制。

18.3 死锁检测与解除

死锁，说白了就是AGV们互相卡住了，谁也动不了。

死锁检测我推荐用资源分配图法。把AGV看作进程，把路径资源看作资源，检测是否存在循环等待。

// 死锁检测算法（简化版）
function detectDeadlock(agvList):
    // 构建等待图
    waitGraph = {}
    for each agv in agvList:
        if agv.isWaiting():
            waitGraph[agv.id] = agv.waitingFor
    
    // 检测环
    visited = set()
    for each agv in agvList:
        if dfsCycleDetect(agv.id, waitGraph, visited):
            return DEADLOCK_DETECTED(extractCycle(visited))
    return NO_DEADLOCK

解除死锁的方法：

  • 撤销法：强制让一台AGV退出，比如让某台AGV倒车让路
  • 资源抢占法：临时释放部分资源，比如让AGV先让出路口
  • 回退法：让AGV回退到上一个安全点
避坑指南：我曾经在死锁解除时直接让AGV倒车，结果撞上了后面的AGV。后来我加了一个"倒车安全检测"，确保后面没车才倒车。

18.4 编队行驶算法

编队行驶，就是让多台AGV像火车一样排成一列走。好处是节省空间、提高通行效率。

常用的编队算法：

  • 领航-跟随法：一台领航车，其他车跟随。简单可靠，我项目里用得最多
  • 虚拟结构法：所有车保持固定的相对位置。适合编队转弯
  • 行为法：每台车根据局部信息自主决策。灵活性高，但控制复杂
// 领航-跟随法编队控制
class FormationController:
    def __init__(self, leader_id, follow_distance=2.0):
        self.leader_id = leader_id
        self.follow_distance = follow_distance
    
    def computeFollowVelocity(self, follower, leader):
        // 计算跟随车的目标速度
        dx = leader.x - follower.x
        dy = leader.y - follower.y
        distance = sqrt(dx*dx + dy*dy)
        
        if distance > self.follow_distance + 0.5:
            // 距离太远，加速跟上
            return maxSpeed
        elif distance < self.follow_distance - 0.5:
            // 距离太近，减速
            return minSpeed
        else:
            // 保持跟车距离
            return leader.speed

编队行驶要注意转弯时的内轮差。我见过编队转弯时，后面的AGV直接切内线撞上了路沿。后来我加了转弯半径补偿，让后面的车走更大的弧线。

18.5 多车协同仿真

仿真，是验证多车协同策略最有效的手段。你不可能在真实产线上调试死锁解除，万一撞了车，损失就大了。

我常用的仿真工具：

  • Gazebo + ROS：物理仿真，精度高，适合验证编队控制
  • MATLAB/Simulink：算法验证快，适合死锁检测算法调试
  • 自研轻量仿真器：针对特定场景，效率最高

仿真时重点关注：

  1. 冲突检测的准确率（有没有漏报、误报）
  2. 交通管制的响应时间（检测到冲突到发出指令的延迟）
  3. 死锁检测的覆盖率（能不能发现所有死锁）
  4. 编队行驶的稳定性（转弯时会不会散架）

核心要点：多车协同不是简单的"加个锁"就能解决的。冲突检测、交通管制、死锁处理、编队控制，这四个环节环环相扣。任何一个环节出问题，整个系统都会崩。

我建议你在做多车协同系统时，先从仿真开始。把各种极端情况都跑一遍，比如突然断电、通信延迟、路径阻塞。等仿真跑稳了，再上真车。这样能省下不少维修费。
