14 行为树（Behavior Tree）在AGV中的应用

各位同学，今天我们来聊聊行为树。说实话，我刚入行那会儿，AGV的逻辑控制基本都是用有限状态机（FSM）写的。那时候调试一个复杂的避让逻辑，状态图能画满一整块白板，改一个分支就得重新梳理所有状态转换——太痛苦了。

后来接触到行为树，我才发现：原来机器人决策逻辑可以写得这么优雅。今天我就把这几年的实战经验掰开揉碎讲给你听。

14.1 行为树节点类型：四种核心构件

行为树本质上是一棵有层次的决策树。每个节点代表一个行为或判断。我个人习惯把节点分成四类，你记好了：

节点类型 英文名 作用 返回值
动作节点 Action 执行具体操作（如移动、充电） Success / Failure / Running
条件节点 Condition 检查某个条件是否成立 Success / Failure
控制节点 Control 控制子节点的执行逻辑 取决于子节点
装饰节点 Decorator 修饰子节点的行为 取决于子节点

动作节点是最常用的。比如让AGV往前走、举起货叉、发出警报。注意，动作节点可以返回Running——这意味着它正在执行中，还没结束。这一点跟FSM很不一样。

条件节点只做判断，不做事。比如检查电量是否低于20%、检查前方是否有障碍物。它要么成功，要么失败，不会卡在Running状态。

控制节点是行为树的灵魂。最常见的两种：

  • Sequence（序列）：从左到右依次执行子节点，全部成功才算成功。任何一个失败就立即返回失败。
  • Fallback（回退）：从左到右尝试子节点，只要有一个成功就算成功。全部失败才算失败。

嗯，这里要注意：Sequence和Fallback的区别，说白了就是“都要做”和“挑一个做”的区别。我在项目中见过有人把两者搞混，结果AGV该充电时跑去干活，该避让时愣在原地——调试了一下午才发现是节点类型选错了。

装饰节点是个好东西。它可以给子节点加各种“特效”：比如重试3次、超时5秒、取反结果。我经常用RetryUntilSuccessful装饰器来处理那些偶尔会失败的通信操作——重试两次基本就能搞定。

核心要点：行为树的执行是“滴答驱动”的。每个控制周期（比如10Hz），树从根节点开始遍历一次。Running状态的节点会在下一周期继续执行，直到返回Success或Failure。

14.2 Nav2默认行为树解析

ROS2的Nav2导航栈内置了一套行为树，用于控制机器人的导航行为。我当初第一次打开它的XML文件时，说实话有点懵——节点嵌套了五六层。但看懂了之后，不得不佩服这个设计的巧妙。

Nav2默认行为树的核心逻辑是这样的：

<root main_tree_to_execute="MainTree">
  <BehaviorTree ID="MainTree">
    <Sequence name="root_sequence">
      <Action ID="ComputePathToPose" path="..." />
      <Action ID="FollowPath" controller="..." />
    </Sequence>
  </BehaviorTree>
</root>

你看，最外层是一个Sequence。它先计算路径，再跟随路径。如果计算路径失败，FollowPath就不会执行——这很合理，路径都没算出来，你跟着走什么呢？

但实际场景比这复杂得多。Nav2默认树里还包含了：

  • 全局定位恢复：当定位丢失时，先尝试旋转，不行就重新初始化位姿。
  • 路径规划恢复：如果路径规划失败，先清除代价地图，再重试。
  • 控制器恢复：如果路径跟踪卡住，尝试后退再前进。

这些恢复逻辑都是用Fallback节点组织的。我举个例子：

<Fallback name="recovery_fallback">
  <Action ID="Spin" spin_dist="1.57"/>
  <Action ID="Wait" wait_duration="2.0"/>
  <Action ID="BackUp" backup_dist="0.5"/>
</Fallback>

这段代码的意思是：先尝试旋转90度，不行就等2秒，还不行就后退0.5米。任何一个成功了，整个Fallback就返回成功。我曾经在一个仓库项目里，把Spin的旋转角度从90度改成了45度——因为货架间距太窄，转90度会撞到。这种小调整，改一行XML就行，不用动C++代码。

我的经验：Nav2的默认行为树是一个很好的学习范本。我建议你把它下载下来，一行一行读。读懂了它，你就掌握了行为树80%的设计模式。

14.3 自定义行为树节点：充电/卸货/避让

Nav2的默认节点能满足导航需求，但AGV还有更多业务逻辑。比如充电、卸货、避让行人。这些都需要我们自己写节点。

下面我以三个典型场景为例，带你手写自定义节点。

14.3.1 充电节点

AGV电量低于20%时，需要自动回桩充电。这个节点需要做三件事：

  1. 导航到充电桩位置
  2. 对接充电桩（精确停靠）
  3. 等待充电完成
class ChargeAction : public BT::StatefulActionNode
{
public:
  ChargeAction(const std::string& name, const BT::NodeConfig& config)
    : BT::StatefulActionNode(name, config) {}

  BT::NodeStatus onStart() override {
    // 1. 发送导航目标到充电桩
    // 2. 启动对接程序
    return BT::NodeStatus::RUNNING;
  }

  BT::NodeStatus onRunning() override {
    // 检查充电状态
    if (battery_full) {
      return BT::NodeStatus::SUCCESS;
    }
    if (docking_failed) {
      return BT::NodeStatus::FAILURE;
    }
    return BT::NodeStatus::RUNNING;
  }

  void onHalted() override {
    // 停止充电，断开对接
  }
};

注意，这里我用了StatefulActionNode。它比普通ActionNode更适合长时间运行的任务。onStart只调用一次，onRunning在每个周期被调用。我曾经犯过一个错误：把充电逻辑写在onStart里，结果每次滴答都重新开始充电——AGV永远充不满。

14.3.2 卸货节点

卸货看起来简单，但实际坑很多。比如货叉伸出时，AGV必须保持静止；货叉收回时，要确认货物已完全脱离。

class UnloadAction : public BT::SyncActionNode
{
public:
  UnloadAction(const std::string& name, const BT::NodeConfig& config)
    : BT::SyncActionNode(name, config) {}

  BT::NodeStatus tick() override {
    // 1. 检查货叉状态（是否已举升到位）
    if (!fork_raised) return BT::NodeStatus::FAILURE;
    
    // 2. 伸出货叉
    extend_forks();
    
    // 3. 微降货叉，使货物脱离
    lower_forks_slightly();
    
    // 4. 收回货叉
    retract_forks();
    
    return BT::NodeStatus::SUCCESS;
  }
};

这里我用的是SyncActionNode，因为卸货动作通常很快（几秒钟），而且需要一次性完成。如果中途被打断，货物可能卡在半空中——嗯，我在项目里遇到过，那次差点把货架掀翻。所以后来我加了一个onHalted回调，确保中断时货叉能安全收回。

14.3.3 避让节点

AGV在行驶中遇到障碍物，需要判断是绕行、等待还是重新规划。这个节点我通常设计成条件+动作的组合：

class AvoidObstacleAction : public BT::StatefulActionNode
{
public:
  BT::NodeStatus onStart() override {
    // 获取障碍物信息
    obstacle = get_obstacle_data();
    
    // 判断避让策略
    if (obstacle.is_static && obstacle.width < 0.5) {
      // 静态小障碍物，绕行
      strategy = Strategy::DETOUR;
    } else if (obstacle.is_dynamic && obstacle.speed < 0.3) {
      // 慢速动态障碍物，等待
      strategy = Strategy::WAIT;
    } else {
      // 其他情况，重新规划路径
      strategy = Strategy::REPLAN;
    }
    return BT::NodeStatus::RUNNING;
  }

  BT::NodeStatus onRunning() override {
    switch (strategy) {
      case DETOUR:  return execute_detour();
      case WAIT:    return execute_wait();
      case REPLAN:  return execute_replan();
    }
  }
};

这个节点的巧妙之处在于：它把决策和执行分开了。onStart里做决策，onRunning里做执行。如果障碍物突然移动了，你可以在onRunning里重新评估策略——我一般每3秒重新评估一次，避免频繁切换导致AGV“犹豫不决”。

避坑指南：我曾经在避让节点里直接调用了全局路径规划，结果导致行为树卡死——因为路径规划本身就是一个长时间任务。正确的做法是：把路径规划封装成另一个Action节点，用Sequence串联起来。行为树的设计原则是“一个节点只做一件事”。

这张图展示了一个典型的AGV导航行为树。根节点下是一个Sequence，它依次执行三个子任务：避让处理、导航执行、任务执行。每个子任务内部又用Fallback或Sequence组织。你想想看，这种层次化的结构，是不是比FSM的状态转换图清晰多了？

好了，今天的内容就到这里。行为树的核心思想其实很简单：用树状结构组织决策逻辑，让每个节点只关心自己的事。你在写节点时，记住一句话：一个节点只做一件事，并且把它做好。这样你的行为树才能像乐高积木一样，灵活组合，易于维护。
