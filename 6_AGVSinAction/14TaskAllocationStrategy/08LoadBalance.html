8 负载均衡策略：车辆利用率均衡、任务队列长度均衡、基于阈值的触发式重分配

各位同学，今天我们来聊聊负载均衡。说实话，这个策略在AGV调度里，属于那种「看着简单，做起来全是坑」的模块。

我刚开始做调度系统时，觉得负载均衡不就是「谁闲给谁派活」吗？结果上线第一天，三台车堵在同一个路口，另外两台车闲得发慌。嗯，现实狠狠给了我一巴掌。

负载均衡的核心目标是什么？说白了就两件事：别让某些车累死，别让某些车闲死。但具体怎么实现，这里头门道不少。

8.1 车辆利用率均衡

先讲第一种思路——看车辆的利用率。

什么叫利用率？就是一辆车在单位时间内，真正干活的时间占比。比如一辆车8小时里跑了6小时，利用率就是75%。

我个人习惯用滑动窗口来计算这个值。取最近30分钟的数据，算一下这辆车跑了多少米、干了多少活。为什么用30分钟？太短了容易受瞬时波动影响，太长了又反应迟钝。这个值是我在项目里反复试出来的。

分配任务时，系统会优先把任务派给利用率最低的车。逻辑很简单：
「老王跑了半天了，让小李去接这单吧。」

但这里有个坑——利用率均衡不等于效率最优。我记得有一次，一台新车利用率低，系统拼命给它派活。结果它路径不熟，绕了好大一圈，反而拖慢了整体进度。所以我现在做方案时，会把利用率作为权重之一，而不是唯一标准。

核心公式（简化版）：

车辆评分 = α × (1 - 利用率) + β × 路径效率 + γ × 剩余电量

α、β、γ 是权重系数，需要根据现场情况调参。我一般从 α=0.4, β=0.4, γ=0.2 开始试。

8.2 任务队列长度均衡

第二种思路，看任务队列的长度。

每辆车都有一个待执行的任务队列。有的车队列里排了5个任务，有的车队列是空的。这时候，新任务应该给谁？

你可能会说：「给空的那辆啊！」

不一定。为什么？因为队列短的车，可能正在执行一个超长距离的任务。它虽然队列短，但短时间内根本接不了新活。而队列长的车，可能都是些顺路的小任务，很快就能消化掉。

所以，队列长度不能只看数量，还要看总执行时间。我一般会计算队列中所有任务的预估总时长，用这个值来做均衡。

我的经验：

我曾经在一个仓库项目里，只用了队列数量做均衡。结果有一台车队列里全是远距离任务，排了6个，但每个都要跑10分钟。另一台车队列里只有2个任务，但都是近距离的，3分钟就能搞定。系统把新任务给了队列短的车，结果那台车忙得飞起，另一台车反而闲下来了。

后来我改成用「预估总时长」做判断，问题就解决了。

8.3 基于阈值的触发式重分配

前面两种策略，都是「任务来了，决定给谁」。但还有一种情况：任务已经分配了，但情况变了，要不要重新分配？

这就是触发式重分配。

举个例子：你给A车派了个任务，结果A车半路没电了，或者被堵死了。这时候如果死等A车，整个系统就卡住了。所以我们需要一个机制，在特定条件下把任务「抢回来」，重新分配给其他车。

触发条件我一般设三个阈值：

  • 时间阈值：任务分配后超过N分钟还没开始执行，触发重分配。N我通常设3-5分钟，看现场节奏。
  • 状态阈值：车辆状态变为异常（故障、低电量、离线），立即触发。
  • 效率阈值：如果另一台车完成任务的时间比当前车快30%以上，触发重分配。这个阈值要小心，调太低了会导致任务频繁切换，反而浪费系统资源。

注意：

触发式重分配不是越多越好。我曾经在一个项目里把阈值设得太敏感，结果一个任务在5分钟内被重分配了3次。三台车都往那个任务点跑，然后又都被撤走，现场乱成一锅粥。

后来我加了一个「冷却时间」——同一个任务在30秒内只能被重分配一次。这才稳住局面。

8.4 三种策略怎么选？

你可能会问：这三种策略，到底用哪个？

我的建议是：组合使用。

日常情况下，用「任务队列长度均衡」做主策略。因为它反应快，计算量小，适合高频调度。

当系统负载较低时，切换到「车辆利用率均衡」。因为这时候更关注车辆的长期健康，避免某些车过度使用。

而「触发式重分配」作为兜底策略，永远开着，但阈值要设得保守一些。

8.5 代码片段：触发式重分配的核心逻辑

最后，给大家看一段我项目里用过的伪代码。不算复杂，但很实用。

// 触发式重分配检查
function checkReassignment(task, vehicle, currentTime) {
    // 1. 检查时间阈值
    if (currentTime - task.assignTime > TIME_THRESHOLD && task.status == 'pending') {
        return true;  // 超时未执行，重分配
    }
    
    // 2. 检查车辆状态
    if (vehicle.status == 'fault' || vehicle.status == 'low_battery') {
        return true;  // 车辆异常，重分配
    }
    
    // 3. 检查效率阈值
    let bestVehicle = findBestVehicle(task);
    if (bestVehicle.estimatedTime < vehicle.estimatedTime * 0.7) {
        // 另一台车能快30%以上
        if (currentTime - task.lastReassignTime > COOLDOWN) {
            return true;  // 效率优化，重分配
        }
    }
    
    return false;
}

避坑指南：

我曾经把COOLDOWN设成10秒，结果任务在高峰期被来回踢皮球。后来改成30秒，配合一个「重分配次数上限」（每个任务最多重分配3次），系统就稳了。

另外，重分配时别忘了通知原来的车辆取消任务。我有一次忘了写这行代码，结果两台车同时去抢一个货架，差点撞上。

好了，负载均衡这块就聊到这儿。三种策略各有适用场景，关键是根据现场情况灵活组合。记住一句话：没有最好的策略，只有最合适的策略。
