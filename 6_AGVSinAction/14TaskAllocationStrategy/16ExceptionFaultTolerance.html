16 异常处理与容错机制：AGV故障检测、任务超时处理、降级运行模式

各位同学，今天我们来聊聊调度系统里最「烧脑」的部分——异常处理与容错机制。

说实话，我见过太多系统在演示时跑得飞起，一到现场就各种「翻车」。为什么？因为异常处理没做好。AGV这东西，说白了就是在不确定的环境中干活。地面不平、网络波动、电池老化……你永远猜不到下一秒会发生什么。

我个人习惯，在设计调度系统时，会把异常处理当作「一等公民」来对待。不是先写正常流程再补异常，而是反过来——先想清楚「如果这里出错了怎么办」。

16.1 AGV故障检测：别等撞墙了才发现

故障检测，核心就一句话：尽早发现，快速定位。

我在项目中遇到过一台AGV，明明轮子卡住了，系统还一直给它派任务。结果呢？它原地空转了半小时，电池耗光，还把地面磨出一道沟。嗯，从那以后，我就在检测机制上下了狠功夫。

16.1.1 心跳检测

这是最基础的手段。AGV每隔一段时间（比如1秒）向调度系统发送一个「我还活着」的信号。

  • 正常情况：心跳稳定，延迟在50ms以内
  • 异常情况：连续3次心跳丢失，触发告警
  • 严重情况：连续10次心跳丢失，系统自动将该AGV标记为「离线」
我的经验：心跳间隔别设太短，也别太长。1秒是个不错的起点。太短了网络负担重，太长了故障发现不及时。我曾经见过有人设了10秒的心跳，结果AGV撞了墙，系统过了半分钟才知道。

16.1.2 状态自检

AGV自身也要有「体检」能力。每次任务执行前后，都应该做一次快速自检：

// 伪代码：AGV自检流程
function selfCheck() {
    checkMotorStatus();      // 电机状态
    checkBatteryLevel();     // 电量
    checkLidarSensor();      // 激光雷达
    checkWheelEncoder();     // 轮子编码器
    checkCommunication();    // 通信链路
    
    if (anyCheckFailed()) {
        reportFault(faultCode);
        enterSafeMode();
    }
}

16.1.3 异常行为检测

有些故障不是「死」的，而是「抽风」。比如AGV走着走着突然偏航，或者速度忽快忽慢。这时候就需要行为检测了。

我常用的方法是：轨迹偏差检测。AGV实际走的路径和规划路径一对比，偏差超过阈值（比如20cm），立刻报警。

注意：偏差阈值不能设得太死。AGV在转弯、过坎时，偏差会自然增大。我一般会根据不同路段设置动态阈值——直道严格，弯道宽松。

16.2 任务超时处理：别让系统死等

任务超时，说白了就是「活干不完了」。原因很多：AGV堵在路上、货架被挪走了、二维码被磨花了……

你想想看，如果一个任务超时了，系统还在那傻等，后面的任务全堵住了。这就像高速公路上一辆车抛锚了，后面的车全停下来等——这不合理。

16.2.1 超时时间怎么设？

我一般用「动态超时」策略。不是拍脑袋定一个固定值，而是根据任务类型和历史数据来算：

任务类型 基础时间 额外缓冲 超时阈值
空车移动 路径时间 × 1.2 30秒 基础时间 + 30秒
取货任务 路径时间 × 1.5 60秒 基础时间 + 60秒
放货任务 路径时间 × 1.5 60秒 基础时间 + 60秒
充电任务 预估充电时间 120秒 预估时间 + 120秒

16.2.2 超时后的处理策略

任务超时了，不能一刀切。我总结了三种处理方式：

  1. 重试：如果是临时性故障（比如网络抖动），重试1-2次即可。重试次数别太多，我一般设3次上限。
  2. 重新分配：如果当前AGV搞不定，把任务转给另一台空闲的AGV。这招在集群里特别好用。
  3. 人工介入：如果重试和重新分配都失败了，那就别硬撑了。把任务标记为「异常」，通知运维人员处理。

核心原则：超时处理的目标不是「完成任务」，而是「不让系统卡死」。有时候放弃一个任务，比死磕到底更明智。

16.3 降级运行模式：系统不能停

降级运行，说白了就是「保底方案」。系统出问题了，不能直接瘫痪，得能「带病工作」。

我记得有一次，客户的调度系统数据库挂了。正常情况下，所有任务记录都要写库。但当时我们启动了降级模式——任务照常执行，只是记录先写到本地缓存，等数据库恢复了再同步。嗯，这个设计救了他们一命。

16.3.1 降级等级划分

我习惯把降级分为三个等级：

  • L1 - 轻微降级：关闭非核心功能（如报表统计、历史查询），核心调度不受影响
  • L2 - 中度降级：关闭路径优化算法，改用最短路径；关闭任务优先级，改为FIFO
  • L3 - 严重降级：只执行紧急任务（如充电、回库），暂停所有普通任务

16.3.2 降级触发条件

降级不是手动开关的，得自动触发。我常用的触发条件：

// 降级触发逻辑
if (systemLoad > 80%) {
    enterDegradeMode(L1);  // 系统负载过高，关闭非核心功能
}
if (databaseResponseTime > 500ms) {
    enterDegradeMode(L2);  // 数据库响应慢，关闭优化算法
}
if (availableAGVCount < 3) {
    enterDegradeMode(L3);  // 可用AGV太少，只执行紧急任务
}

16.3.3 降级恢复

降级不是终点，恢复才是。我一般会设计一个「健康检查」线程，定期检查系统状态：

  • 如果系统负载降到60%以下，自动恢复到L2
  • 如果系统负载降到40%以下，自动恢复到L1
  • 如果所有指标恢复正常，自动恢复到正常模式
避坑指南：恢复的时候要小心「抖动」。我曾经遇到过系统在降级和正常之间反复横跳——刚恢复又触发降级，降级后又恢复。后来我加了一个「稳定时间」窗口，比如持续正常5分钟才真正恢复。

我的建议：刚开始做调度系统时，别想着把所有异常都处理完。先把「心跳检测」、「任务超时重试」、「L3降级」这三个最基础的做扎实。其他的，慢慢补。我曾经见过一个团队，花了一个月做各种花哨的异常处理，结果上线第一天，心跳检测没配好，AGV离线了系统都不知道——这就尴尬了。

好了，这一章的内容就到这里。异常处理这东西，说难不难，说简单也不简单。关键是要有「底线思维」——先想清楚最坏的情况是什么，然后针对性地设计容错方案。你想想看，是不是这个道理？
