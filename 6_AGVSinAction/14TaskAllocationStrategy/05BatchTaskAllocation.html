5 多任务批量分配策略：匈牙利算法原理、任务-车辆二分图匹配、最小化总行驶距离

各位同学，今天我们来聊聊多任务批量分配。说实话，这是AGV调度里最让我头疼，也最有成就感的一块。

单任务分配，说白了就是「来一个活，找一辆车」。但现实哪有这么简单？仓库里可能同时冒出几十个搬运任务，几十辆车都在待命。怎么一次性把这些任务都分出去，让总行驶距离最短？这就是我们今天要啃的硬骨头。

5.1 为什么需要批量分配？

我刚开始做AGV项目时，犯过一个低级错误。当时系统用的是「先到先服务」策略——来一个任务，找最近的车。结果呢？

  • 任务A来了，分配给车1，距离10米
  • 任务B来了，分配给车2，距离15米
  • 任务C来了，分配给车3，距离20米

看起来每个任务都挺合理。但后来我算了一笔账：如果让车1去任务C（20米），车2去任务A（10米），车3去任务B（15米），总距离反而更短！

核心问题：局部最优 ≠ 全局最优。批量分配就是要找到全局最优解。

你想想看，一个仓库里几十辆车同时跑，每辆车多跑1米，总距离就多几十米。一天下来，电池消耗、轮胎磨损、任务延迟……全是成本。

5.2 匈牙利算法：解决分配问题的经典方法

匈牙利算法，名字听着挺唬人。其实它就是个「找最优配对」的数学方法。1955年由匈牙利数学家库恩提出，专门解决指派问题。

我当年在课本上第一次看到它时，觉得这玩意儿太抽象了。直到有一次在项目里，面对30个任务和30辆车，手动算了一下午没算出来……嗯，从那以后我老老实实把算法写进了代码。

5.2.1 算法核心思想

说白了，匈牙利算法就干一件事：在代价矩阵里，找到一组「行和列都不重复」的元素，让它们的和最小。

举个例子。假设我们有3个任务（T1, T2, T3）和3辆车（V1, V2, V3）。每辆车到每个任务的距离如下：

T1 T2 T3
V1 10 15 20
V2 12 8 25
V3 18 22 5

匈牙利算法会找出一种分配方式，比如：V1→T1（10），V2→T2（8），V3→T3（5），总距离=23。这是不是最优？我们后面验证。

5.2.2 算法步骤（简化版）

我不打算把数学证明全讲一遍，那太枯燥了。咱们直接看实操步骤：

  1. 行归约：每行减去该行最小值
  2. 列归约：每列减去该列最小值
  3. 试分配：用最少的线覆盖所有0元素
  4. 调整矩阵：如果线数小于任务数，继续调整
  5. 得到最优解

我的经验：实际编码时，别自己手写匈牙利算法。用现成的库（比如Python的scipy.optimize.linear_sum_assignment），稳定又高效。我曾经手写过一次，调试了三天才发现一个边界条件没处理好……

5.3 任务-车辆二分图匹配

匈牙利算法背后，其实是一个二分图模型。左边是任务节点，右边是车辆节点，边上的权重就是行驶距离。

为什么要用二分图？因为任务和车辆是两类不同的东西，它们之间没有内部连接。任务之间不会互相抢路（至少在分配阶段不考虑），车辆之间也不会互相干扰。这种结构天然适合二分图。

5.4 最小化总行驶距离

好了，理论讲完了。咱们看看实际怎么用。

5.4.1 代价矩阵的构建

在真实系统里，距离不是简单的直线距离。我一般会考虑三个因素：

  • 曼哈顿距离：仓库里AGV走的是网格路径，不是直线
  • 交通拥堵系数：某些路段高峰期要加权
  • 车辆当前电量：电量低的车辆，尽量分配近的任务

注意：千万别只用欧氏距离！我在一个项目里吃过亏，AGV按直线距离分配，结果车被货架挡住了，绕了一大圈。后来改成曼哈顿距离，问题才解决。

5.4.2 代码实现示例

下面是一个简化版的Python实现。实际项目中，你还需要处理任务数量不等于车辆数量的情况（比如任务多于车，或者车多于任务）。

import numpy as np
from scipy.optimize import linear_sum_assignment

# 构建代价矩阵：行=车辆，列=任务
# 这里用曼哈顿距离作为示例
cost_matrix = np.array([
    [10, 15, 20],   # V1到各任务的距离
    [12, 8, 25],    # V2到各任务的距离
    [18, 22, 5]     # V3到各任务的距离
])

# 匈牙利算法求解
row_ind, col_ind = linear_sum_assignment(cost_matrix)

# 输出结果
print("最优分配方案：")
for i, j in zip(row_ind, col_ind):
    print(f"车辆V{i+1} → 任务T{j+1}，距离={cost_matrix[i][j]}")

total_distance = cost_matrix[row_ind, col_ind].sum()
print(f"总行驶距离：{total_distance}")

运行结果：

最优分配方案：
车辆V1 → 任务T1，距离=10
车辆V2 → 任务T2，距离=8
车辆V3 → 任务T3，距离=5
总行驶距离：23

你看，总距离23，比随便分配要短得多。

5.5 实际项目中的避坑指南

讲几个我踩过的坑，希望对你有帮助。

坑1：任务数量不等于车辆数量

我曾经遇到一个场景：15个任务，但只有12辆车空闲。匈牙利算法要求矩阵是方阵。怎么办？我的做法是添加3个「虚拟车辆」，它们到所有任务的距离设为一个很大的数（比如9999）。这样算法会自动把最难的任务分配给虚拟车——实际上就是不分配，留给下一批。

坑2：动态更新代价矩阵

任务分配不是一次性的。新任务会不断进来，车辆的状态也在变化。我建议每5-10秒重新运行一次匈牙利算法，而不是等所有任务都攒够了再算。这样既能保证全局最优，又能快速响应变化。

坑3：别忽略约束条件

匈牙利算法默认每个任务只能分配给一辆车，每辆车只能做一个任务。但实际中，一辆车可以连续做多个任务。这时候你需要把问题拆解成「任务序列」而不是「单任务」。我一般会用两阶段法：先用匈牙利算法做初始分配，再用局部搜索优化任务顺序。

5.6 小结

多任务批量分配，核心就三件事：

  • 建模：把问题抽象成二分图匹配
  • 求解：用匈牙利算法找到全局最优
  • 落地：处理好实际工程中的各种约束

我个人觉得，匈牙利算法是AGV调度里性价比最高的算法之一。它不复杂，但效果立竿见影。你想想看，同样的硬件，换一套分配策略，吞吐量可能提升20%以上。这笔账，怎么算都划算。
