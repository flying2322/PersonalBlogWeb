6 时间窗约束下的分配：硬时间窗与软时间窗、时间窗冲突检测、基于时间窗的可行解搜索

各位同学，咱们今天聊一个实战中绕不开的话题——时间窗约束。

说实话，很多刚入行的朋友觉得任务分配就是“谁近谁去”。但在真实工厂里，哪有这么简单？你想想看，一个任务要求8:00送到，结果车8:05才到，产线可能就停线了。这就是时间窗约束在起作用。

我个人习惯把时间窗分成两类：硬时间窗和软时间窗。这两者的区别，说白了就是“能不能商量”。

6.1 硬时间窗与软时间窗

硬时间窗，就是死命令。AGV必须在[最早开始时间, 最晚完成时间]内完成任务。早到不行，晚到更不行。我在项目中遇到过一条汽车总装线，物料必须在工位需求前2分钟到达，早了没地方放，晚了产线停。这就是典型的硬时间窗。

硬时间窗的数学表达：

任务j的时间窗：[ET_j, LT_j]
AGV到达时间：A_j
约束条件：ET_j ≤ A_j ≤ LT_j

软时间窗，就有商量余地了。你可以早到或晚到，但会有惩罚成本。比如早到1分钟扣0.5分，晚到1分钟扣1分。嗯，这里要注意：软时间窗不是没有约束，而是把约束变成了优化目标。

我的经验：软时间窗在电商仓储里特别常见。订单有优先级，高优先级订单的惩罚系数大，低优先级的可以稍微等等。我曾经帮一家仓库调过参数，把惩罚系数从线性改成指数型，效果反而更好——因为操作员更怕“超时太多”而不是“超时一点”。

类型 特点 适用场景 惩罚机制
硬时间窗 不可违反 汽车总装、半导体晶圆搬运 无惩罚，直接不可行
软时间窗 可违反但有成本 电商分拣、仓库补货 线性/指数惩罚函数

6.2 时间窗冲突检测

冲突检测，是调度系统里最烧脑的部分之一。为什么？因为冲突不是“有没有”的问题，而是“什么时候有”的问题。

我举个例子。两辆AGV，A车要在8:00-8:10占用路段R1，B车要在8:05-8:15占用同一路段。你一看就知道，8:05-8:10这段时间重叠了，这就是冲突。

但实际场景更复杂。比如A车8:00到路口，B车8:01到，看起来只差1秒，但如果路口只能单向通行，那这1秒就是冲突。

我曾经踩过的坑：早期我写冲突检测时，只检查了“时间区间是否重叠”。结果有一次，两辆车同时到达同一个充电站，但充电站只有一个接口。我这才意识到——资源冲突不仅要看时间，还要看资源类型和容量。从那以后，我的冲突检测函数里多了个参数叫“resource_capacity”。

冲突检测的核心算法其实不复杂：

def detect_conflict(task1, task2):
    # 检查时间窗是否重叠
    if task1.end_time < task2.start_time or task2.end_time < task1.start_time:
        return False  # 无冲突
    
    # 检查资源是否冲突
    if task1.resource != task2.resource:
        return False  # 不同资源，无冲突
    
    # 检查资源容量
    if task1.resource.capacity < 2:
        return True   # 单容量资源，有冲突
    
    return False      # 多容量资源，暂时无冲突

你可能会问：为什么最后返回False？因为多容量资源需要进一步计算“剩余容量”，不能简单判定冲突。嗯，这里留个思考题给你。

6.3 基于时间窗的可行解搜索

找到冲突只是第一步。真正的难题是：如何在冲突中找到可行解？

我个人习惯用“时间窗滑动法”。说白了，就是给每个任务一个“可调整范围”，在这个范围内寻找不冲突的时间点。

举个例子。任务A的时间窗是[8:00, 8:10]，任务B的时间窗是[8:05, 8:15]，两者在路段R1上冲突。怎么办？

  1. 尝试滑动A：把A的开始时间从8:00滑到8:10之后，但这样可能超出A的硬时间窗。
  2. 尝试滑动B：把B的开始时间从8:05滑到8:15之后，同样可能超时。
  3. 尝试交换顺序：让B先走，A后走。但B的到达时间可能比A晚，需要重新计算路径。

可行解搜索的伪代码：

function search_feasible_solution(tasks):
    sort tasks by start_time  # 按开始时间排序
    for each task in tasks:
        while task has conflict with any assigned task:
            # 尝试滑动当前任务
            new_time = slide_task(task, step=1min)
            if new_time is within task's time window:
                update task.start_time = new_time
            else:
                # 尝试滑动已分配的任务
                if can_slide_previous_tasks(task):
                    slide_previous_tasks(task)
                else:
                    return "无可行解"
    return "找到可行解"

你想想看，这个算法其实很暴力。但在实际项目中，任务数量通常不超过50个，这种暴力搜索完全够用。我见过有人用遗传算法、粒子群算法来搜，说实话，杀鸡用牛刀了。

一个小技巧：搜索时优先滑动“时间窗较宽”的任务。因为宽时间窗的任务弹性大，调整后对其他任务影响小。我在一个项目中把这个启发式规则加进去后，搜索时间从3秒降到了0.2秒。

6.4 实战中的时间窗管理

最后，我想分享几个实战中的经验。

第一，时间窗不是越紧越好。有些工程师喜欢把时间窗设得很窄，觉得这样“精确”。但实际运行中，AGV的行驶时间会有波动——地面湿滑、电池电量、负载重量都会影响速度。时间窗太窄，系统会频繁报冲突，调度员会疯掉。

第二，软时间窗的惩罚系数要调参。我建议用历史数据来拟合。比如统计过去一个月里，任务延迟时间与产线停线时间的相关性，然后反推惩罚系数。别拍脑袋定系数，会出事的。

第三，冲突检测要实时。不要等任务分配完了再检测。我习惯在每次分配任务时，就做一次增量冲突检测。这样能提前发现潜在问题，而不是事后补救。

我曾经犯过的错：有一次，我把所有任务都分配完了，然后统一做冲突检测。结果发现30个任务里有12个冲突，而且互相嵌套，根本没法局部调整。最后只能全部重新分配，浪费了整整一个下午。从那以后，我再也不敢“先分配后检测”了。

好了，时间窗这块的内容就讲到这里。记住一句话：时间窗不是限制，而是保护。它保护你的AGV不会撞车，保护你的产线不会停线，保护你的调度系统不会崩溃。
