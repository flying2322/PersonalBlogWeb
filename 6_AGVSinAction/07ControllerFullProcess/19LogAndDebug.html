19 日志与调试——AGV开发者的“眼睛”

做AGV控制器开发，说白了就是跟看不见摸不着的逻辑打交道。你写了一大堆代码，电机转不转？传感器读没读到？PID参数调没调对？这些信息，都得靠日志和调试工具来告诉你。

我个人习惯，在项目一开始就把调试手段搭好。别等到车跑起来发现抖得像跳舞，才想起来加日志。那时候你连问题出在哪都不知道。

1.1 SEGGER RTT日志——实时、低开销的“黑匣子”

先说说SEGGER RTT。这玩意儿我用了好几年，真心推荐。它全称是Real-Time Transfer，是SEGGER公司搞出来的一种调试接口技术。

为什么不用串口？

串口打印日志，速度慢，还占CPU。你想想看，AGV在高速运行时，串口每打印一行，可能就耽误了几毫秒的控制周期。RTT就不一样，它通过JTAG/SWD接口，直接在内存里读写数据，几乎不占用CPU时间。

RTT的核心优势：

  • 极低延迟：微秒级响应
  • 不影响实时性：不打断主循环
  • 双向通信：既能输出日志，也能输入命令
  • 支持多通道：可以分不同优先级输出

我在项目中遇到过一个问题：AGV在转弯时突然卡顿。用串口打印PID数据，结果一开打印，卡顿更严重了。后来换成RTT，数据实时输出，才发现是积分项饱和了。嗯，这就是工具选对的好处。

RTT的基本配置

在SEGGER Embedded Studio或者J-Link驱动里，都有RTT的源码。你只需要把SEGGER_RTT.c和SEGGER_RTT.h加到工程里，然后调用SEGGER_RTT_printf()就行。

// 初始化（一般放在main函数开头）
SEGGER_RTT_Init();

// 打印日志，类似printf
SEGGER_RTT_printf(0, "电机速度: %d rpm, 目标: %d rpm\n", current_speed, target_speed);

// 带时间戳的打印
SEGGER_RTT_printf(0, "[%u] 编码器计数: %ld\n", HAL_GetTick(), encoder_count);

我的小技巧： 用通道0做普通日志，通道1做错误日志，通道2做调试命令。这样在J-Link RTT Viewer里可以分别查看，不会乱。

1.2 串口调试助手——最朴素的“听诊器”

虽然RTT很强大，但串口调试助手依然是每个嵌入式工程师的必备工具。为什么？因为它简单、通用、不挑硬件。

我记得刚入行时，带我的师傅说：“串口是嵌入式世界的通用语言。” 后来我深有体会。不管你是STM32、GD32还是国产MCU，只要引出TX/RX，就能通信。

串口调试的常见坑

  • 波特率不匹配： 我见过有人调了一下午，结果是115200和9600没对上
  • 电平不匹配： 3.3V的MCU接5V的USB转串口，不烧IO口算运气好
  • 缓冲区溢出： 打印太快，串口缓冲区满了，数据就丢了

避坑指南： 我曾经在AGV的电机控制循环里直接放了一个printf()，结果电机直接停了。后来才发现，printf是阻塞的，会等串口发送完才返回。在实时控制里，千万别这么干！

正确的做法是：用DMA+环形缓冲区。把日志先写到内存里，然后由DMA后台慢慢发送。这样主循环不会被阻塞。

// 伪代码：非阻塞串口日志
void log_printf(const char *fmt, ...) {
    // 1. 格式化字符串到环形缓冲区
    va_list args;
    va_start(args, fmt);
    vsnprintf(ring_buf + write_idx, ...);
    va_end(args);
    
    // 2. 启动DMA传输（如果上一次传输已完成）
    if (dma_idle) {
        HAL_UART_Transmit_DMA(&huart1, ring_buf + send_idx, len);
    }
}

1.3 逻辑分析仪——数字世界的“示波器”

做AGV控制，免不了要跟各种数字信号打交道：PWM波、编码器脉冲、I2C/SPI通信、CAN总线……这时候，逻辑分析仪就是你的第三只眼。

我个人觉得，逻辑分析仪比示波器更适合调试数字信号。为什么？因为它通道多（一般8-16通道），能同时看多路信号，还能解码协议。

什么时候该用逻辑分析仪？

  • 电机PWM频率不对，怀疑定时器配置错了
  • 编码器读数跳变，怀疑AB相时序有问题
  • I2C设备不响应，想看SCL/SDA波形
  • CAN总线通信失败，想看报文有没有发出去

我记得有一次，AGV的里程计数据总是偏大。用逻辑分析仪抓了编码器的A、B相波形，发现B相的上升沿和下降沿有毛刺，导致计数器多计了脉冲。后来在硬件上加了个RC滤波，问题就解决了。

逻辑分析仪使用要点：

  1. 采样率要够： 至少是信号频率的4倍，建议10倍以上
  2. 触发设置： 用上升沿或下降沿触发，别傻等
  3. 协议解码： 现在的逻辑分析仪都支持UART、I2C、SPI、CAN等解码，直接用
  4. 导出数据： 可以把波形导出成CSV，用Python做进一步分析

1.4 性能分析（Profiling）——找到代码的“瓶颈”

AGV控制是个实时系统。主循环跑一圈，必须在规定时间内完成（比如1ms）。如果超时，轻则控制精度下降，重则电机失控。

性能分析，就是找出代码里最耗时的部分。说白了，就是看时间都花在哪了。

常用的性能分析方法

方法 原理 适用场景
GPIO翻转法 在代码段前后翻转GPIO，用示波器测脉宽 快速定位，不需要额外工具
定时器捕获 用定时器记录代码段的执行时间 需要精确到微秒级
IDE Profiler 用IDE自带的性能分析工具（如IAR的C-SPY） 需要看函数调用关系和耗时占比
RTT+时间戳 在关键位置打印时间戳，事后分析 长时间运行，看趋势

我个人最常用的是GPIO翻转法。简单粗暴，不依赖任何工具。你只需要在代码里加两行：

// 在要测量的代码段开始处
HAL_GPIO_WritePin(DEBUG_GPIO_Port, DEBUG_Pin, GPIO_PIN_SET);

// ... 要测量的代码 ...

// 在代码段结束处
HAL_GPIO_WritePin(DEBUG_GPIO_Port, DEBUG_Pin, GPIO_PIN_RESET);

然后用示波器或者逻辑分析仪看这个GPIO的脉宽。嗯，一目了然。

我的经验： 在AGV的主循环里，我一般会测量这几个关键段的耗时：传感器读取、控制算法计算、电机输出。如果总时间超过1ms，就逐个排查。通常问题出在浮点运算或者数学库函数上。
