18 固件升级与OTA：Bootloader设计、固件签名与校验、差分升级、远程升级流程

说到AGV的固件升级，我估计不少工程师都经历过那种痛苦——抱着笔记本电脑，蹲在AGV旁边，一根线接着一根线地刷程序。一台两台还行，要是仓库里跑着几十台车，那真是要命。所以，OTA（Over-The-Air）升级，说白了就是AGV控制器的“远程换血”能力。这一章，我把这些年踩过的坑和积累的经验，掰开了揉碎了讲给你听。

18.1 Bootloader设计：升级的“守门员”

Bootloader是什么？你可以把它理解成AGV控制器的“BIOS”。它是一段独立的、固化在芯片起始地址的小程序。每次上电，CPU先跑Bootloader，再由它决定：是跳转到用户程序，还是进入升级模式。

我个人习惯把Flash分区设计成三块：

  • Bootloader区： 64KB，只读，几乎不改动。
  • App区（主程序）： 存放当前运行的固件。
  • Download区（下载缓存区）： 存放新固件包，校验通过后再拷贝到App区。

为什么要多一个Download区？我在项目中遇到过直接往App区写数据，写到一半断电了，结果AGV变砖了。有了Download区，就算升级失败，Bootloader还能从App区启动，保证系统不瘫。

核心设计原则：

  • Bootloader必须支持“看门狗”喂狗，防止升级过程中死机。
  • Bootloader要能识别固件版本号，避免“降级刷写”。
  • Bootloader代码要精简，最好用汇编或纯C写，别依赖操作系统。

下面是一个简化的Bootloader跳转逻辑，我习惯用这种结构：

// 伪代码：Bootloader主流程
void bootloader_main(void) {
    // 1. 检查是否有升级请求（比如GPIO电平、Flash标志位）
    if (check_update_request() == TRUE) {
        // 2. 进入升级模式，接收新固件
        enter_update_mode();
        // 3. 校验固件签名（后面会讲）
        if (verify_firmware_signature() == PASS) {
            // 4. 擦除App区，写入新固件
            flash_erase(APP_START_ADDR);
            flash_write(APP_START_ADDR, download_buffer);
            // 5. 设置启动标志
            set_boot_flag(APP_VALID);
        } else {
            // 签名失败，保持旧固件
            set_boot_flag(APP_VALID);
        }
    }
    // 6. 跳转到App区
    jump_to_app(APP_START_ADDR);
}

小技巧： 我习惯在Bootloader里加一个“强制升级”引脚。如果这个引脚在启动时被拉低，不管App区有没有程序，都强制进入升级模式。这招救过我很多次，尤其是调试初期。

18.2 固件签名与校验：别让恶意固件混进来

你想想看，AGV在工厂里跑来跑去，要是被人刷了个恶意固件，那后果不堪设想。所以，固件签名不是可选项，是必选项。

我常用的方案是： 用RSA-2048签名，用SHA-256做哈希校验。具体流程是这样的：

  1. PC端（开发机）： 编译出固件.bin文件，计算SHA-256哈希值，然后用私钥对这个哈希值加密，生成签名文件。
  2. AGV端（Bootloader）： 收到固件包后，先计算固件的SHA-256哈希值，然后用公钥解密签名文件，得到原始的哈希值。两个哈希值对比，一致则通过。

这里有个坑——公钥存哪里？我曾经直接把公钥写在Bootloader代码里，结果被同事吐槽说“这不等于把钥匙挂在门上吗？”后来我学乖了，把公钥的哈希值也存进去，启动时先校验公钥本身有没有被篡改。

警告： 千万不要用MD5做签名校验！MD5已经被证明可以碰撞。我见过有同行图省事用MD5，结果被黑客轻松绕过。至少用SHA-256，有条件上SHA-3更好。

18.3 差分升级：省流量、省时间、省带宽

AGV的固件动不动就几百KB甚至几MB，如果每次升级都全量传输，那OTA的效率太低了。尤其是用4G或者LoRa这种窄带通信时，差分升级几乎是必须的。

差分升级的原理很简单： 只传输新旧固件之间的差异部分。AGV端收到差异数据后，用旧固件加上差异数据，合成新固件。

我推荐用 bsdiff 算法，它专门针对二进制文件做了优化。在项目中实测，一个1MB的固件，如果只改了10%的代码，差分包可能只有50KB左右，压缩比非常可观。

差分升级的流程：

  1. 云端/服务器： 用bsdiff生成差分补丁包（patch文件）。
  2. AGV端： 下载patch文件，用bspatch工具将旧固件 + patch = 新固件。
  3. 校验： 合成后的新固件做一次全量校验（签名+哈希），确保合成过程没出错。

注意： 差分升级对Flash空间有要求。你需要同时保留旧固件、下载的patch文件、以及合成中的新固件。我一般会预留至少2倍App区大小的Flash空间，否则容易爆内存。

18.4 远程升级流程：从云端到AGV的完整链路

好了，前面都是基础组件，现在把它们串起来，看看完整的远程升级流程是什么样的。

我习惯把流程分成四个阶段：

阶段 动作 关键点
1. 触发阶段 云端下发升级通知，AGV上报当前版本号 AGV必须处于“空闲”或“充电”状态，不能正在执行任务
2. 下载阶段 AGV下载差分补丁包，存到Download区 支持断点续传，网络中断后能接着下
3. 合成与校验 bspatch合成新固件，RSA+SHA256校验 校验失败则回滚，不破坏旧固件
4. 生效阶段 设置启动标志，软重启，Bootloader加载新固件 如果新固件启动失败（比如卡死），Bootloader要能自动回滚

实战经验： 我建议在AGV端维护一个“升级状态机”。状态包括：IDLE、DOWNLOADING、VERIFYING、UPDATING、ROLLBACK。这样一旦升级过程中断电，重新上电后Bootloader能根据状态机决定是继续升级还是回滚。这个状态机要保存在非易失性存储器里，比如EEPROM或者Flash的最后几个扇区。

18.5 避坑指南：我踩过的那些雷

最后，分享几个我亲身经历过的教训，希望能帮你少走弯路：

  • 千万别在升级过程中关看门狗。 我曾经为了省事，在升级时把看门狗关了，结果有一次网络卡顿，升级卡住了，AGV彻底死机。后来我改成在升级循环里喂狗，问题解决。
  • 差分升级前，一定要校验旧固件的完整性。 如果旧固件本身已经损坏了，差分合成出来的新固件也是坏的。我吃过这个亏，后来在合成前先对旧固件做一次CRC校验。
  • OTA升级的通信协议要设计“心跳”和“超时重传”。 尤其是用Wi-Fi或者4G时，信号不稳定是常态。我习惯把每个数据包控制在1KB以内，并加上序号，接收方收到后回复ACK，超时则重传。
  • 升级完成后，让AGV自动重启一次。 不要依赖人工确认。我见过有同事升级完了忘了重启，结果AGV还在跑旧程序，白忙活一场。

嗯，关于固件升级和OTA，核心就是这些。Bootloader是地基，签名校验是门锁，差分升级是省钱的妙招，而完整的流程则是把这些串起来的绳子。你想想看，把这些都做好了，AGV的远程维护能力就真正落地了。
