16 系统集成与测试：硬件在环（HIL）测试、单元测试框架（Unity/CMock）、集成测试用例设计

各位同学，咱们今天聊点硬核的——系统集成与测试。说实话，很多做AGV开发的工程师，代码写得飞起，一到测试环节就头大。我见过太多项目，开发阶段顺风顺水，联调时直接翻车。为什么？因为测试没做到位。

我个人习惯，把测试分成三个层次：单元测试、集成测试、系统测试。今天重点讲前两个，再加上硬件在环（HIL）测试。这三个东西，说白了就是给你的AGV控制器上三道保险。

16.1 单元测试框架：Unity/CMock

先说说单元测试。很多嵌入式工程师觉得单元测试是“浪费时间”，我刚开始也这么想。直到有一次，我在一个AGV的电机控制模块里，发现了一个极其隐蔽的溢出bug——那个bug在仿真环境里根本跑不出来，但实际跑起来，电机偶尔会抽风。从那以后，我再也不敢跳过单元测试了。

嵌入式C语言的单元测试，我推荐Unity + CMock。Unity是测试框架，CMock是模拟框架。为什么选它们？轻量、无依赖、纯C实现，跑在MCU上毫无压力。

16.1.1 Unity 基础用法

Unity的用法极其简单。你只需要包含一个头文件，然后写测试用例就行。看个例子：

#include "unity.h"
#include "motor_control.h"

void setUp(void) {
    // 每个测试用例执行前调用
    motor_init();
}

void tearDown(void) {
    // 每个测试用例执行后调用
    motor_deinit();
}

void test_motor_set_speed_normal(void) {
    // 正常速度设置
    TEST_ASSERT_EQUAL(MOTOR_OK, motor_set_speed(1000));
    TEST_ASSERT_EQUAL(1000, motor_get_current_speed());
}

void test_motor_set_speed_overflow(void) {
    // 超速限制测试
    TEST_ASSERT_EQUAL(MOTOR_ERROR, motor_set_speed(99999));
}

int main(void) {
    UNITY_BEGIN();
    RUN_TEST(test_motor_set_speed_normal);
    RUN_TEST(test_motor_set_speed_overflow);
    return UNITY_END();
}

嗯，这里要注意：setUp和tearDown是Unity自动调用的，你不需要手动调用。每个测试用例之间是隔离的，这一点非常重要。

我的小技巧： 测试用例的命名，我习惯用“test_模块名_功能_场景”的格式。比如 test_motor_set_speed_overflow，一看就知道测的是电机模块、设置速度功能、溢出场景。这样后期维护时，找问题快得多。

16.1.2 CMock 模拟外部依赖

AGV控制器不可能孤立运行。它要读传感器、写PWM、和上位机通信。这些外部依赖，在单元测试里必须被“模拟”掉。CMock就是干这个的。

举个例子，你的电机控制模块依赖一个I2C驱动来读写寄存器。测试时你不想真的去操作I2C总线，对吧？用CMock生成一个模拟的I2C驱动：

// 假设你的I2C接口定义在 i2c_driver.h 中
// 用CMock生成模拟版本
// 命令行：ruby cmock.rb -o i2c_driver.h

#include "mock_i2c_driver.h"

void test_motor_read_register(void) {
    // 设置模拟返回值
    i2c_read_ExpectAndReturn(0x50, 0x01, 0x55);
    
    // 执行被测函数
    uint8_t value = motor_read_register(0x01);
    
    // 验证结果
    TEST_ASSERT_EQUAL(0x55, value);
}

你看，CMock会自动生成ExpectAndReturn这样的函数。你只需要告诉它：“我期望调用i2c_read，参数是0x50和0x01，然后返回0x55”。如果实际代码没有按预期调用，测试就会失败。

我曾经踩过的坑： CMock生成的模拟函数，默认是“严格模式”——参数必须完全匹配。但有时候你并不关心某些参数，比如超时时间。这时候可以用 Ignore 系列函数来忽略特定参数。否则测试用例会写得非常痛苦。

16.2 硬件在环（HIL）测试

单元测试跑完了，代码逻辑没问题。但你的AGV控制器真的能在真实硬件上跑吗？不一定。这就是HIL测试要解决的问题。

HIL测试，说白了就是把你的控制器代码，跑在一个模拟真实硬件的环境里。这个环境通常包含：

  • 实时仿真机：模拟电机、传感器、电池等物理设备
  • 信号接口：PWM、CAN、GPIO等真实电气信号
  • 故障注入：模拟短路、断线、过压等异常情况

我参与过一个项目，AGV在仓库里跑得好好的，一到电梯口就死机。后来HIL测试发现，是电梯的电磁干扰导致CAN总线偶尔丢帧。如果没有HIL，这种问题在现场排查，成本高得吓人。

16.2.2 HIL测试用例设计

HIL测试用例，我一般分三类：

测试类型 测试内容 典型用例
功能测试 验证基本控制逻辑 直线行驶、原地转弯、加减速
边界测试 验证极限工况 最大速度、最小转弯半径、满载爬坡
故障测试 验证异常处理 电机堵转、传感器断线、通信超时

举个例子，故障测试的用例可以这样写：

// 故障测试：左轮电机编码器断线
void HIL_Test_LeftEncoderFault(void) {
    // 1. 初始化：AGV以0.5m/s直线行驶
    HIL_SetSpeed(0.5);
    HIL_SetSteeringAngle(0);
    
    // 2. 等待2秒，让系统稳定
    HIL_Delay(2000);
    
    // 3. 注入故障：断开左轮编码器信号
    HIL_FaultInject(FAULT_LEFT_ENCODER, FAULT_TYPE_OPEN);
    
    // 4. 等待500ms，观察控制器响应
    HIL_Delay(500);
    
    // 5. 验证：控制器应检测到故障并进入安全模式
    TEST_ASSERT_EQUAL(SAFE_MODE_ACTIVE, HIL_GetControllerState());
    TEST_ASSERT_TRUE(HIL_GetMotorSpeed(LEFT_MOTOR) < 0.1);
}
关键点： HIL测试的“实时性”非常重要。你的仿真机必须能在微秒级响应控制器的输出。如果仿真步长太大，测出来的结果没有意义。我个人建议仿真步长不超过100微秒。

16.3 集成测试用例设计

单元测试测的是单个函数，HIL测试测的是整个系统。那集成测试呢？它测的是模块之间的接口和交互。

我举个例子。AGV的导航模块和电机控制模块之间，通过一个速度指令接口通信。单元测试时，这两个模块各自都测过了。但合在一起时，导航模块发的指令，电机模块能不能正确解析？会不会有时序问题？这就是集成测试要干的活。

16.3.1 集成测试策略

我常用的集成测试策略是“自底向上”+“关键路径优先”：

  1. 先测底层驱动：比如I2C、SPI、CAN驱动，确保数据能正确收发
  2. 再测中间层：比如传感器数据融合、电机控制算法
  3. 最后测应用层：比如路径规划、任务调度

但这里有个坑：如果完全按顺序测，周期太长。所以我一般会先挑“关键路径”来测。什么是关键路径？就是一旦出问题，整个AGV就趴窝的那些功能。比如“刹车指令”这条路径，必须优先测。

16.3.2 集成测试用例示例

下面是一个集成测试用例，测的是“导航模块下发速度指令 -> 电机控制模块执行”这条路径：

// 集成测试：导航到电机指令传递
void Integration_Test_NavToMotor(void) {
    // 1. 初始化两个模块
    nav_init();
    motor_init();
    
    // 2. 导航模块计算目标速度
    nav_set_target(10.0, 5.0);  // 目标位置 (10m, 5m)
    nav_update();               // 计算控制指令
    
    // 3. 获取导航模块输出的速度指令
    float target_speed = nav_get_output_speed();
    float target_steering = nav_get_output_steering();
    
    // 4. 将指令传递给电机模块
    motor_set_speed(target_speed);
    motor_set_steering(target_steering);
    
    // 5. 验证电机模块正确接收
    TEST_ASSERT_FLOAT_WITHIN(0.01, target_speed, motor_get_current_speed());
    TEST_ASSERT_FLOAT_WITHIN(0.01, target_steering, motor_get_current_steering());
    
    // 6. 验证执行结果（通过编码器反馈）
    HIL_Delay(100);  // 等待一个控制周期
    float actual_speed = motor_get_encoder_speed();
    TEST_ASSERT_FLOAT_WITHIN(0.05, target_speed, actual_speed);
}
我的经验： 集成测试最容易忽略的是“时序问题”。两个模块各自都正常，但一个模块更新数据的频率是10Hz，另一个是50Hz，中间就可能丢数据。我建议在集成测试里，故意制造一些时序抖动，看看系统能不能扛住。

16.4 测试覆盖率与持续集成

测试写完了，怎么知道测够了没有？看覆盖率。我一般关注三个指标：

  • 语句覆盖率：每行代码都被执行过吗？目标≥90%
  • 分支覆盖率：每个if-else分支都走到过吗？目标≥85%
  • MC/DC覆盖率：每个条件独立影响结果吗？目标≥80%（安全关键功能要求100%）

这些覆盖率数据，可以用gcov、lcov等工具自动生成。我习惯把覆盖率检查集成到CI流水线里，每次提交代码自动跑。如果覆盖率下降，构建直接失败。

注意： 覆盖率不是万能的。100%覆盖率不代表没有bug。我见过一个项目，覆盖率95%以上，但现场还是出了严重问题——因为测试数据全是“正常数据”，从来没测过异常数据。所以，测试用例的质量比数量更重要。

好了，关于系统集成与测试，我就讲这么多。记住：测试不是开发完成后的“附加工作”，而是开发过程中不可或缺的一部分。你投入在测试上的每一分钟，都会在后期调试中加倍回报给你。
