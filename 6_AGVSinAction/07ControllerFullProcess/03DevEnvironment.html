3 开发环境搭建：工欲善其事，必先利其器

各位同学，大家好。我是你们的老朋友，一个在AGV控制领域摸爬滚打了十几年的工程师。今天咱们正式开始《AGV控制器开发全流程实战》的第一课——开发环境搭建。

说实话，我见过太多新手，一上来就急着写代码，结果环境没配好，编译报错就卡了半天。我自己刚入行那会儿也犯过这毛病。嗯，磨刀不误砍柴工，咱们先把家伙事儿备齐了。

本章核心目标：搭建一套稳定、可复用的AGV控制器开发环境，包括IDE安装、交叉编译链配置、版本控制以及项目模板创建。

1.1 IDE的选择与安装

AGV控制器开发，说白了就是嵌入式开发。主流的IDE就那么几个：Keil MDK、IAR EWARM、STM32CubeIDE。我个人习惯是，项目初期用CubeIDE做快速原型验证，量产阶段切到Keil或IAR。为什么？因为Keil和IAR的编译器优化更成熟，代码体积和性能都更好。

IDE 适用芯片 编译器 特点
Keil MDK ARM Cortex-M全系列 ARMCC v6/v5 行业标准，调试器支持好
IAR EWARM ARM Cortex-M/R/A IAR C/C++ 代码优化极强，适合量产
STM32CubeIDE STM32全系列 GCC 免费，集成CubeMX配置

我的建议：如果你刚开始学，直接用STM32CubeIDE。免费、开箱即用，而且集成了HAL库配置工具。等你项目做大了，再考虑Keil或IAR。

安装过程我就不啰嗦了，官网下载、一路Next就行。但有一点要注意——安装路径不要有中文和空格。我在项目中遇到过，有人把Keil装到了"Program Files (x86)"里，结果编译某些老项目时路径解析出错，折腾了半天。

1.2 交叉编译工具链配置

交叉编译，说白了就是在PC上编译出能在ARM芯片上跑的程序。你想想看，你的电脑是x86架构，AGV控制器是ARM架构，不搞交叉编译怎么行？

我个人推荐用ARM GCC工具链，开源、免费、社区活跃。配置步骤如下：

  1. 下载ARM GCC：gcc-arm-none-eabi 最新版
  2. 解压到 C:\arm_gcc 或 /opt/arm_gcc
  3. 添加环境变量：把 bin 目录加到 PATH 里
  4. 验证安装：打开终端，输入 arm-none-eabi-gcc --version
# 验证命令
arm-none-eabi-gcc --version
# 输出示例：
arm-none-eabi-gcc (GNU Arm Embedded Toolchain 10.3-2021.10) 10.3.1 20210824
Copyright (C) 2020 Free Software Foundation, Inc.

注意：我曾经遇到过，下载了错误的版本（比如x86_64的Linux版本用在Windows上），结果编译出来的程序一运行就崩溃。一定要选对操作系统和架构！

如果你用STM32CubeIDE，它自带GCC工具链，不需要额外配置。但如果你像我一样，喜欢在命令行里编译、用Makefile管理项目，那手动配置工具链就是必修课了。

1.3 Git版本控制：你的后悔药

做AGV控制器开发，代码迭代非常快。今天改个PID参数，明天加个路径规划算法，后天又要回退到上个版本。没有Git？那简直是灾难。

我刚开始带团队时，有个同事用"main.c.bak"、"main.c.final"、"main.c.really_final"这种命名方式。结果有一次误删了关键代码，找了一下午才从备份里恢复。从那以后，我强制团队所有项目必须用Git。

基本操作就这几个：

# 初始化仓库
git init

# 添加文件到暂存区
git add .

# 提交到本地仓库
git commit -m "初始提交：AGV控制器基础框架"

# 关联远程仓库（比如GitHub、GitLab）
git remote add origin https://github.com/yourname/agv_controller.git

# 推送到远程
git push -u origin main

我的习惯：每次提交前，先写一个.gitignore文件，把编译生成的.o、.hex、.bin以及IDE的临时文件都忽略掉。这样仓库里只保留源码，干净利落。

这里给新手一个建议：分支管理用Git Flow模型。main分支只放稳定版本，develop分支做日常开发，feature分支做新功能。这样即使某个功能写崩了，也不会影响主线。

1.4 项目模板创建：一次配置，到处复用

每次新建项目都要从头配置？太浪费时间了。我一般会创建一个项目模板，包含以下结构：

agv_controller_template/
├── .gitignore
├── README.md
├── Makefile
├── src/
│   ├── main.c
│   ├── motor_control.c
│   ├── sensor_fusion.c
│   └── ...
├── inc/
│   ├── main.h
│   ├── motor_control.h
│   └── ...
├── drivers/
│   ├── stm32f4xx_hal_driver/
│   └── ...
├── startup/
│   └── startup_stm32f407xx.s
├── linker/
│   └── STM32F407VGTx_FLASH.ld
└── scripts/
    └── flash.py

这个模板是我多年经验的结晶。你想想看，每次新建项目，只需要复制这个模板，改个名字，然后开始写业务逻辑就行了。底层驱动、链接脚本、启动文件都不用再碰。

核心思路：把硬件相关的代码（驱动、启动文件、链接脚本）和业务逻辑代码（电机控制、传感器融合、路径规划）分开。这样换芯片时，只需要改驱动层，业务层几乎不用动。

具体怎么创建模板？我建议用STM32CubeMX生成初始代码，然后手动整理成上面的结构。把CubeMX生成的.ioc文件也保留在模板里，方便以后重新配置外设。

嗯，这里要注意一点：Makefile要写得通用一些。我一般会把芯片型号、优化等级、调试信息等参数提取成变量，这样换芯片时只需要改几个变量就行。

# Makefile 示例片段
TARGET = agv_controller
MCU = STM32F407VG
OPT = -O2
DEBUG = -g3

# 编译器和链接器
CC = arm-none-eabi-gcc
LD = arm-none-eabi-gcc
OBJCOPY = arm-none-eabi-objcopy

# 源文件
SRCS = $(wildcard src/*.c)
OBJS = $(SRCS:.c=.o)

# 编译规则
%.o: %.c
    $(CC) -c $(CFLAGS) $< -o $@

# 链接
$(TARGET).elf: $(OBJS)
    $(LD) $(LDFLAGS) $^ -o $@

# 生成hex
$(TARGET).hex: $(TARGET).elf
    $(OBJCOPY) -O ihex $< $@

这个Makefile虽然简单，但已经能覆盖大部分AGV控制器项目了。你可以在模板里预置好，每次新建项目时直接复制过去。

避坑指南：我曾经在模板里忘了加-specs=nano.specs和-specs=nosys.specs这两个链接参数，结果程序一运行就卡死在_exit()函数里。后来查了半天才发现是标准库的问题。所以模板里的链接参数一定要配全。

好了，第一章的内容就到这里。环境搭建是基础中的基础，但也是最容易出问题的地方。把这一步走稳了，后面的开发才会顺畅。
