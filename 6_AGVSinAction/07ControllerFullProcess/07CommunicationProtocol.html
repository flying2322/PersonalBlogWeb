7 通信协议实现——CAN总线基础与CANopen协议栈移植、UART自定义协议（Modbus RTU）、Wi-Fi TCP/UDP通信

各位同学，大家好。这一章我们聊聊AGV的“神经系统”——通信协议。说白了，AGV要能跑起来，控制器和电机、传感器、上位机之间必须能“说上话”。我见过不少项目，硬件选型都挺好，结果死在通信不稳定上。嗯，这一章我们就来把这些坑填上。

7.1 CAN总线基础：为什么AGV离不开它？

先问大家一个问题：AGV上那么多电机、编码器、IO模块，如果用传统的RS485轮询，会怎样？

答案很简单：实时性跟不上。你想想看，一个电机急停指令，如果等上位机轮询一圈才发下去，车早就撞上了。

CAN总线（Controller Area Network）的优势就在这里：

  • 多主通信：任何节点都可以主动发消息，不用等主机问
  • 实时性高：优先级仲裁机制，紧急指令插队发送
  • 错误处理强：5种错误检测机制，自动重发
  • 差分信号：抗干扰能力强，适合工业现场

核心参数速查表

参数典型值说明
波特率125kbps ~ 1MbpsAGV常用250k或500k
帧类型标准帧(11位ID) / 扩展帧(29位ID)AGV一般用标准帧就够了
最大节点数理论110个，实际建议不超过40个跟收发器驱动能力有关
总线长度@250kbps最长250mAGV车体内部完全够用

我个人习惯，在AGV项目中把CAN总线分成两路：一路给驱动电机和转向电机，另一路给传感器和IO模块。这样即使传感器那路出问题，电机还能安全停车。

7.2 CANopen协议栈移植——从零到跑起来

光有CAN硬件还不够，你得有协议。CANopen就是工业领域最常用的高层协议。我最早接触CANopen时，觉得这东西好复杂——对象字典、PDO、SDO、NMT……后来发现，其实核心就几个概念。

7.2.1 对象字典（Object Dictionary）

说白了，就是一张大表。每个设备把自己的参数、状态、命令都放在这张表里。比如电机驱动器的目标转速，索引是0x6040，子索引0x00。

我曾经在一个项目中，发现电机死活转不起来。查了半天，原来是对象字典里0x6040的默认值写错了。嗯，这种低级错误，犯过一次就记住了。

7.2.2 PDO与SDO

  • PDO（过程数据对象）：实时性高，1个PDO最多传8字节。适合传转速、电流、位置这些周期性数据。
  • SDO（服务数据对象）：用于配置参数，有应答机制。适合初始化时设置参数。

实战建议：

把电机控制指令映射到PDO1，把状态反馈映射到PDO2。这样一个CAN帧就能搞定控制和反馈，延迟控制在1ms以内。

7.2.3 协议栈移植步骤

我常用的是CANfestival开源协议栈。移植步骤其实不复杂：

  1. 驱动层适配：实现CAN收发函数（发送、接收、中断处理）
  2. 定时器适配：提供1ms和1us的定时基准
  3. 对象字典配置：用EDS文件生成，或者手动定义
  4. NMT状态机：实现初始化、预操作、操作、停止四个状态
  5. 心跳/节点守护：检测节点是否在线
// 伪代码示例：CANopen初始化流程
void CANopen_Init(void)
{
    // 1. 初始化CAN硬件
    CAN_Init(500000);  // 500kbps
    
    // 2. 启动CANopen协议栈
    canopen_node_t *node = canopen_init(0x01);  // 节点ID=1
    
    // 3. 配置PDO映射
    PDO_Map_Input(node, 0x180, 0x6040, 0x00);  // 控制字
    
    // 4. 进入操作状态
    NMT_SendCommand(node, NMT_START_REMOTE_NODE);
}

避坑指南：

我曾经在移植时忽略了CAN控制器的FIFO深度。如果发送频率太高，FIFO溢出会导致丢帧。解决办法：在发送前检查FIFO剩余空间，或者用DMA传输。

7.3 UART自定义协议——Modbus RTU实战

CAN虽好，但不是所有传感器都支持。很多激光雷达、超声波模块还是走UART。这时候Modbus RTU就是最稳妥的选择。

Modbus RTU的核心就三点：

  • 主从模式：AGV控制器做主站，传感器做从站
  • 功能码：03读保持寄存器、06写单个寄存器、16写多个寄存器
  • CRC校验：16位循环冗余校验，保证数据完整性

7.3.1 帧结构

字段长度说明
地址码1字节从站地址，1~247
功能码1字节03/06/16等
数据区N字节寄存器地址+数据
CRC校验2字节低字节在前
// Modbus RTU 读取保持寄存器示例
// 发送：01 03 00 00 00 01 84 0A
// 含义：从站1，读寄存器，起始地址0x0000，读1个寄存器

// 接收：01 03 02 00 64 79 85
// 含义：从站1，功能码03，2字节数据，数值0x0064=100

我个人习惯，在AGV上把Modbus的波特率固定为115200，8数据位，1停止位，无校验。这样兼容性最好，而且115200在1米以内的线缆上基本不会出错。

7.3.2 自定义协议扩展

有时候Modbus RTU不够灵活，比如要传浮点数、字符串。我的做法是在Modbus基础上做一层封装：

  • 用功能码0x64（自定义）传浮点数
  • 用功能码0x65传字符串
  • 数据区前加一个类型标识符

注意：自定义功能码一定要跟标准Modbus不冲突。我见过有人用0x10（标准写多个寄存器）来传浮点数，结果跟标准设备冲突，调试了三天才发现。

7.4 Wi-Fi TCP/UDP通信——远程监控与调度

AGV不能总在本地跑，得跟调度系统通信。Wi-Fi是最常见的选择。这里有两个选择：TCP和UDP。

7.4.1 TCP vs UDP 怎么选？

特性TCPUDP
可靠性有确认重传，可靠无确认，可能丢包
实时性稍差，有握手延迟好，无连接
适用场景任务下发、状态上报实时位置广播、心跳

我的做法是：

  • 控制指令：走TCP，确保指令不丢失
  • 位置广播：走UDP，每秒发10次，丢几帧无所谓
  • 心跳包：TCP和UDP各发一份，双重保险

7.4.2 实战代码片段

// TCP客户端连接示例（基于lwIP）
int tcp_connect_to_server(ip_addr_t *server_ip, uint16_t port)
{
    struct tcp_pcb *pcb = tcp_new();
    if (pcb == NULL) return -1;
    
    // 注册回调函数
    tcp_recv(pcb, tcp_recv_callback);
    tcp_err(pcb, tcp_err_callback);
    
    // 连接服务器
    err_t err = tcp_connect(pcb, server_ip, port, tcp_connected_callback);
    if (err != ERR_OK) return -1;
    
    return 0;
}

// UDP发送广播
void udp_broadcast_position(float x, float y, float angle)
{
    struct udp_pcb *pcb = udp_new();
    ip_addr_t broadcast_ip = IPADDR_BROADCAST;
    
    // 打包数据
    uint8_t buffer[12];
    memcpy(buffer, &x, 4);
    memcpy(buffer+4, &y, 4);
    memcpy(buffer+8, &angle, 4);
    
    // 发送
    udp_sendto(pcb, buffer, 12, &broadcast_ip, 5000);
    udp_remove(pcb);
}

避坑指南：

Wi-Fi在AGV上有个大问题——漫游切换。AGV移动时，如果从一个AP切换到另一个AP，TCP连接会断开。我曾经遇到过AGV跑到仓库角落，Wi-Fi信号弱，调度指令发不过去，车直接停在原地。

解决办法：

  • 使用快速漫游协议（802.11r）
  • 在AGV上做断线重连机制，超时3秒自动重连
  • 关键指令走CAN总线备份

7.5 本章知识体系总览

说了这么多，我画了一张图帮大家理清思路。三种通信方式各司其职，共同构成AGV的通信骨架。

从这张图可以看出来，AGV的通信不是单一方案，而是分层组合。CAN负责实时控制，UART负责传感器采集，Wi-Fi负责远程调度。三者缺一不可。

我的个人经验总结：

做AGV通信，最忌讳的就是“一把抓”。我见过有人想用Wi-Fi把所有数据都传了，结果延迟大到电机都抖。记住：实时性要求高的走CAN，数据量大的走UART，远程交互的走Wi-Fi。各司其职，系统才稳定。

好了，这一章的内容就到这里。三种通信方式，每一种都有它的脾气。CAN要小心终端电阻和波特率，Modbus要注意超时和重试，Wi-Fi要处理断线重连。把这些细节都处理好，你的AGV通信系统才算真正“靠谱”。
