14 状态机与任务管理：AGV状态机设计（空闲、导航、充电、异常）、任务队列与优先级、多AGV协同逻辑

各位同学，今天我们来聊聊AGV的“大脑”怎么运转。说白了，就是状态机与任务管理。这东西听起来玄乎，其实就像我们人一样——什么时候该干活，什么时候该休息，出问题了怎么办。AGV也得有这套逻辑。

我个人习惯把状态机比作AGV的“意识”。没有它，车就是一堆电机和传感器的集合。有了它，车才知道自己是谁，该干嘛去。

14.1 AGV核心状态机设计

先看最基础的状态机。我做过那么多项目，发现不管多复杂的AGV，核心状态就那么几个：空闲、导航、充电、异常。你想想看，是不是这个理？

核心状态定义：

  • 空闲（Idle）：等待任务，低功耗待机
  • 导航（Navigation）：执行路径规划与运动控制
  • 充电（Charging）：自动对接充电桩，管理电池
  • 异常（Error）：处理故障，进入安全模式

嗯，这里要注意：状态转移不是随便跳的。比如从“导航”直接跳到“充电”，必须满足电量低于阈值且附近有充电桩。我在项目中遇到过，有人把状态转移条件写得太宽松，结果AGV在运输途中突然跑去充电，把产线搞乱了。

实战小技巧：状态机实现时，我建议用枚举类型 + switch-case 结构。别用 if-else 嵌套，后期维护会想哭的。

// 状态机核心代码片段
typedef enum {
    STATE_IDLE,
    STATE_NAVIGATION,
    STATE_CHARGING,
    STATE_ERROR
} agv_state_t;

agv_state_t current_state = STATE_IDLE;

void agv_state_machine_run(void) {
    switch (current_state) {
        case STATE_IDLE:
            // 等待任务分配
            if (task_queue_has_task()) {
                current_state = STATE_NAVIGATION;
            }
            if (battery_level < BATTERY_LOW_THRESHOLD) {
                current_state = STATE_CHARGING;
            }
            break;
            
        case STATE_NAVIGATION:
            // 执行导航
            if (navigation_complete()) {
                current_state = STATE_IDLE;
            }
            if (fault_detected()) {
                current_state = STATE_ERROR;
            }
            if (battery_level < BATTERY_CRITICAL) {
                current_state = STATE_CHARGING;
            }
            break;
            
        case STATE_CHARGING:
            // 充电管理
            if (battery_level >= BATTERY_FULL) {
                current_state = STATE_IDLE;
            }
            if (charging_fault()) {
                current_state = STATE_ERROR;
            }
            break;
            
        case STATE_ERROR:
            // 异常处理
            if (error_cleared()) {
                current_state = STATE_IDLE;
            }
            break;
    }
}

14.2 任务队列与优先级管理

状态机搞定了，接下来就是任务管理。AGV不可能只干一件事，它得排队干活。我见过很多新手，直接把任务塞进一个链表里，结果高优先级的任务被堵在后面，急死人。

任务队列的设计，说白了就是三个问题：谁来插队？谁先执行？插队后原来的任务怎么办？

任务优先级划分（我常用的方案）：

优先级 任务类型 说明
0（最高） 紧急停止 / 安全任务 不可抢占，立即执行
1 异常处理 / 故障恢复 高优先级，可中断当前任务
2 充电任务 电量低于阈值时触发
3 普通运输任务 按FIFO顺序执行
4（最低） 维护 / 自检任务 空闲时执行

为什么会这样设计？你想想看，如果AGV正在运输途中，突然传感器报错，这时候必须暂停运输，先处理异常。我曾经在项目里吃过亏——没做优先级抢占，结果AGV带着故障继续跑，最后撞了货架。

避坑指南：我曾经遇到过任务队列死锁的问题。高优先级任务一直插队，低优先级任务永远得不到执行。解决方案是加一个“老化机制”——任务等待超过一定时间，自动提升优先级。

// 任务队列管理示例
typedef struct {
    uint8_t priority;       // 0-4, 0最高
    uint32_t task_id;
    uint32_t timestamp;     // 入队时间戳
    void (*task_func)(void);
} task_t;

// 优先级队列插入（带老化提升）
void task_queue_insert(task_t *new_task) {
    // 老化处理：等待超过30秒的任务，优先级+1
    for (int i = 0; i < queue_size; i++) {
        if ((get_tick() - task_queue[i].timestamp) > 30000) {
            if (task_queue[i].priority > 0) {
                task_queue[i].priority--;
            }
        }
    }
    // 按优先级插入
    int insert_pos = 0;
    while (insert_pos < queue_size && 
           task_queue[insert_pos].priority <= new_task->priority) {
        insert_pos++;
    }
    // 插入逻辑...
}

14.3 多AGV协同逻辑

单台AGV好搞，多台一起跑就麻烦了。我记得第一次做多AGV项目，三台车在十字路口堵成一锅粥。后来我总结了一套协同逻辑，核心就四个字：资源互斥。

多AGV协同，说白了就是解决“谁先过”的问题。我常用的方案是分布式令牌+区域锁：

  • 区域锁：把地图划分成网格，每个网格同一时间只能有一台AGV占用
  • 分布式令牌：AGV进入关键区域前，先申请令牌，拿到才能进
  • 死锁检测：定期检查是否有AGV互相等待，超时则强制解锁

多AGV协同的核心规则：

  1. 每台AGV维护自己的状态机，独立运行
  2. 共享资源（路径段、充电桩）通过中央调度器分配
  3. 低优先级AGV主动让行高优先级AGV
  4. 死锁发生时，由调度器发起“回退-重规划”流程

嗯，这里有个细节：多AGV协同不能全靠中央调度。万一调度器挂了，所有车都得停。我建议采用去中心化+心跳检测的方案。每台AGV广播自己的位置和状态，其他车收到后自行避让。中央调度只做宏观分配，不参与微观控制。

// 多AGV协同 - 区域锁申请
bool request_area_lock(uint8_t agv_id, uint16_t area_id) {
    // 检查区域是否被占用
    if (area_lock[area_id] == 0xFF) {
        // 空闲，锁定
        area_lock[area_id] = agv_id;
        return true;
    }
    // 被占用，检查优先级
    uint8_t current_owner = area_lock[area_id];
    if (agv_priority[agv_id] < agv_priority[current_owner]) {
        // 高优先级AGV可以抢占
        // 通知原车主退出
        send_preempt_message(current_owner, area_id);
        area_lock[area_id] = agv_id;
        return true;
    }
    return false;  // 等待
}

实战经验：多AGV协同最怕的是“活锁”——两辆车互相让，结果谁都不走。我解决的办法是引入随机退避时间。就像WiFi的CSMA/CA一样，退避时间不同，自然就分出了先后。

最后总结一下：状态机是AGV的“骨架”，任务管理是“血液”，多AGV协同是“神经系统”。这三者配合好了，你的AGV才能跑得稳、跑得快、不出乱子。我在实际项目中，光状态机就迭代了三个版本，才达到满意的效果。所以别急，慢慢调，总会调顺的。
