11 定位与建图——让AGV知道自己在哪里，世界长什么样

各位同学，欢迎来到整个AGV控制器开发中最有“灵魂”的一章。前面我们讲了电机怎么转、传感器怎么读，但说句实话，那些都是“手脚”。定位与建图，才是AGV的“大脑和眼睛”。没有它，你的车就是个盲人，撞墙了都不知道自己在哪里。

我个人习惯把这一章拆成四个核心模块来讲：里程计模型、粒子滤波定位、栅格地图构建、以及ROS里那两个大名鼎鼎的工具——Gmapping和Cartographer。咱们一个一个啃。

11.1 里程计模型——AGV的“直觉”

里程计是什么？说白了，就是靠轮子转了多少圈，来推算车走了多远、转了多少角度。这是最原始、最直觉的定位方式。你想想看，人闭着眼睛走路，靠的就是脚底的感觉——里程计就是AGV的“脚底感觉”。

对于最常见的差分驱动AGV，模型其实很简单。左右轮各装一个编码器，假设左轮走了ΔL，右轮走了ΔR，那么车体的位移ΔD和转角Δθ就是：

ΔD = (ΔL + ΔR) / 2
Δθ = (ΔR - ΔL) / 轮距

然后更新位姿（x, y, θ）：

x += ΔD * cos(θ + Δθ/2)
y += ΔD * sin(θ + Δθ/2)
θ += Δθ

嗯，这里要注意：这个模型假设轮子不打滑、地面绝对平整。但现实世界哪有那么完美？我在项目中遇到过，AGV在瓷砖地面上跑，稍微有点水，里程计就开始“漂移”。跑个10米，实际位置能偏出去20厘米。

⚠️ 避坑指南： 我曾经在一个仓储项目中，只靠里程计做定位，结果AGV跑了三圈之后，地图上的位置和实际位置差了将近1米。后来我加上了激光雷达的观测校正，才把误差压下来。记住：里程计只能做短时、短距离的位姿推测，千万别指望它单独完成全局定位。

11.2 粒子滤波定位——用“猜”来逼近真相

既然里程计会飘，那怎么办？我们换个思路：不直接算位置，而是用一堆“粒子”去猜。每个粒子代表一个可能的位姿，一开始均匀撒在整个地图上。然后随着AGV移动和观测，不断更新这些粒子的权重，最后收敛到真实位置附近。

这就是蒙特卡洛定位（MCL），也叫粒子滤波。流程大致分三步：

  1. 预测：根据里程计模型，让每个粒子都动一下（加一点噪声）
  2. 更新：用激光雷达或其它传感器观测环境，计算每个粒子的“像真度”（权重）
  3. 重采样：扔掉权重低的粒子，复制权重高的粒子

循环这三步，粒子就会像“磁铁吸铁屑”一样，慢慢聚集到真实位置周围。

💡 关键点： 粒子数量怎么选？太少容易发散，太多算不过来。我一般建议：室内环境用500~2000个粒子，室外大场景可以到5000个。如果算力够，用自适应粒子滤波（KLD采样）动态调整数量，效果更好。

为什么粒子滤波比卡尔曼滤波更适合AGV？因为AGV的位姿估计是非线性、非高斯的。卡尔曼滤波假设噪声是高斯分布，但实际中AGV可能被推了一下、轮子打滑了——这些“异常”用粒子滤波处理起来更自然。

11.3 栅格地图构建——把世界变成“像素”

地图怎么表示？最常用的就是占用栅格地图（Occupancy Grid Map）。把环境划分成一个个小格子，每个格子存一个概率值：0表示空闲，1表示占用，0.5表示未知。

构建过程其实是个“贝叶斯更新”的过程。每次激光雷达扫到某个格子，就更新它的概率：

// 伪代码：更新栅格占用概率
void updateGrid(GridCell &cell, bool isOccupied) {
    float prob = cell.getOccupancyProb();
    if (isOccupied) {
        prob = prob * 0.9 / (prob * 0.9 + (1-prob) * 0.1);
    } else {
        prob = prob * 0.1 / (prob * 0.1 + (1-prob) * 0.9);
    }
    cell.setOccupancyProb(prob);
}

这里有个细节：栅格分辨率怎么选？5cm一格？还是2cm一格？我个人的经验是：

场景 推荐分辨率 说明
仓库通道（2m宽） 5cm 够用，内存省
精密装配车间 2cm 需要识别小物体
室外大场景 10~20cm 地图太大，必须压缩
🎯 实战技巧： 我习惯在构建地图时，把栅格更新阈值设得保守一点。比如占用概率超过0.7才标记为障碍物，低于0.3才标记为空闲。这样可以避免激光噪声导致的“鬼影”栅格。

11.4 ROS中的SLAM工具——Gmapping vs Cartographer

好了，理论讲完了，咱们看看实际工程中怎么用。ROS里有两个主流SLAM工具包，我都有过“血泪史”。

11.4.1 Gmapping——轻量级选手

Gmapping基于粒子滤波+栅格地图，是ROS里最经典的SLAM方案。它的优点是：配置简单、计算量小、对小场景效果好。你只需要提供激光雷达数据和里程计数据，它就能跑起来。

启动命令也很简单：

roslaunch gmapping slam_gmapping_pr2.launch

但Gmapping有个硬伤：它不处理闭环检测。也就是说，如果AGV绕了一大圈回到原点，Gmapping不会主动去修正累积误差。我曾在2000平米的仓库里试过，跑完一圈回来，地图首尾对不上，差了30多厘米。

11.4.2 Cartographer——工业级方案

Cartographer是Google开源的SLAM库，它引入了子图（Submap）和闭环检测。说白了，它把地图切成很多小块，每块内部用激光数据优化，块与块之间做匹配。一旦检测到AGV回到之前去过的地方，就触发全局优化，把误差“抹平”。

配置稍微复杂一点，但效果确实好：

# 关键参数配置示例
TRAJECTORY_BUILDER_2D.min_range = 0.3
TRAJECTORY_BUILDER_2D.max_range = 30.0
TRAJECTORY_BUILDER_2D.submaps.num_range_data = 90
POSE_GRAPH.optimize_every_n_nodes = 90
🔧 选型建议：
  • 如果场景小于500平米、路径简单 → 用Gmapping，省事
  • 如果场景大、有回环、要求高精度 → 用Cartographer，值得花时间调参
  • 如果算力有限（比如用树莓派）→ Gmapping更友好

我记得有一次给客户做方案，他们要求AGV在1000平米的展厅里自主导航。一开始用Gmapping，地图建出来总是有重影。后来换成Cartographer，调了两天参数，地图精度从10cm提升到了2cm以内。客户当场就竖了大拇指。

⚠️ 重要提醒： 不管用哪个工具，里程计的质量决定了SLAM的上限。如果里程计数据噪声太大，再好的SLAM算法也救不回来。我建议你在跑SLAM之前，先单独标定一下里程计，确保它的误差在可接受范围内。

好了，这一章的内容就到这里。定位与建图是AGV的“地基”，地基不稳，上层控制全是空中楼阁。希望各位同学在实际项目中，能把这些理论真正用起来，而不是停留在“看过就算”的阶段。
