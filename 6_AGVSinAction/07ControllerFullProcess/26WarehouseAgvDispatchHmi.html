26 仓储AGV任务调度与多车协同、上位机集成

各位同学，今天我们来聊聊仓储AGV项目中最核心、也最让人头疼的部分——任务调度与多车协同。说实话，我在这个领域摸爬滚打了十几年，见过太多AGV在仓库里“打架”的场景。有一次在华南某大型电商仓，12台AGV同时运行，结果有3台在同一个巷道里堵了整整20分钟，现场主管差点把对讲机摔了。嗯，从那以后，我对调度算法的敬畏心就特别重。

1.1 任务调度的本质：不是“谁有空谁干”

很多人以为任务调度就是“哪个车空闲，就把任务派给谁”。其实没那么简单。你想想看，仓库里几十台AGV，有的在充电，有的在搬运，有的在待命。如果单纯按空闲分配，很可能出现“近车不干活，远车跑断腿”的情况。

我个人习惯把任务调度拆成三个层次：

  • 任务分配层：决定哪个任务由哪台车执行
  • 路径规划层：为每台车规划无冲突的行驶路径
  • 交通管理层：实时处理多车交汇、死锁等问题

这三个层次缺一不可。我曾经在一个项目中只做了任务分配，忽略了路径规划，结果两台车在同一个货架前“面面相觑”，谁也动不了。那场面，尴尬得很。

1.2 多车协同的核心：避免“死锁”与“碰撞”

多车协同说白了就是两件事：别撞上，别堵死。但实现起来，坑特别多。

核心原则：任何时刻，任何两台AGV的行驶路径不能有交集，除非它们有明确的优先级规则。

我常用的方法是“预留路径段”策略。每台AGV在行驶前，会向调度系统申请一段路径的独占权。系统批准后，其他AGV就不能进入这段路径。等AGV通过了，再释放这段路径。

这里有个关键点：路径段的粒度。粒度太粗，比如整条巷道，那其他车就得等很久；粒度太细，比如每米一个段，那系统通信开销就爆炸了。我个人建议按AGV车身长度的1.5倍来划分，既安全又高效。

1.3 上位机集成的那些事

上位机，就是仓库管理系统（WMS）或者制造执行系统（MES）。AGV调度系统需要和它对接，接收任务指令，反馈执行状态。

我见过最坑的集成方式是“轮询”。上位机每隔几秒问一次“有任务吗？”，AGV调度系统再问每台车“你忙完了吗？”——这延迟简直没法看。正确的做法是“事件驱动+消息队列”。

下面是我常用的一个集成接口示例：

// 任务下发接口（上位机 -> AGV调度系统）
POST /api/v1/tasks
{
  "task_id": "TASK20240101_001",
  "type": "PICKUP",        // 取货
  "source": "A-01-02",     // 起始货架
  "destination": "B-03-01", // 目标货架
  "priority": 1,           // 优先级，1最高
  "deadline": 3600         // 超时时间（秒）
}

// 状态反馈接口（AGV调度系统 -> 上位机）
POST /api/v1/status
{
  "agv_id": "AGV_003",
  "task_id": "TASK20240101_001",
  "status": "EXECUTING",   // 状态：IDLE/EXECUTING/COMPLETED/FAILED
  "position": {"x": 12.5, "y": 8.3},
  "battery": 78,
  "timestamp": 1704067200
}

小技巧：状态反馈一定要带上时间戳。我曾经遇到上位机因为网络延迟，把旧状态当成新状态处理，导致任务重复下发。加上时间戳后，调度系统可以判断消息是否过期。

1.4 任务调度算法：从简单到复杂

任务调度算法有很多种，我按实战经验给大家排个序：

算法 适用场景 复杂度 我的评价
先来先服务（FCFS） 任务少、车少 低 入门级，但容易饿死
最短路径优先（SPF） 任务均匀分布 中 比FCFS好，但会忽略优先级
拍卖算法 多车、多任务 高 我项目中最常用的，灵活
遗传算法 超大规模调度 极高 效果好，但实时性差，慎用

我个人最推荐拍卖算法。每台AGV根据自身位置、电量、当前任务状态，对每个新任务“报价”。调度系统选择“性价比最高”的AGV来执行。这样既考虑了距离，也考虑了负载均衡。

避坑指南：我曾经在一个项目中用了遗传算法，结果每次调度计算要花3-5秒。仓库里任务密集的时候，AGV经常停在原地等指令。后来我换成了拍卖算法，计算时间降到50毫秒以内。所以，实时性要求高的场景，别碰遗传算法。

1.5 多车协同的实战经验

多车协同最怕什么？死锁。两台车在交叉口互相等待，谁也不让谁。我遇到过最离谱的一次，4台车在十字路口形成了一个“完美闭环”，每台车都在等前车让路，结果全堵死了。

解决死锁，我总结了三个方法：

  1. 资源预分配：每台车在进入交叉口前，先申请所有需要的路径段。申请不到就原地等待，不进入交叉口。
  2. 优先级回退：给每台车一个动态优先级。等待时间越长，优先级越高。这样死锁时，等待最久的车会获得通行权。
  3. 人工干预接口：留一个手动解锁的API。万一算法失效，操作员可以手动指定哪台车先走。

嗯，这里要注意，方法3是最后的保底手段。我一般只在调试阶段用，正式上线后很少用到。

1.6 上位机集成的关键点

上位机集成，说白了就是“对上位机说人话”。很多AGV调度系统喜欢用自己定义的协议，结果上位机那边对接起来痛苦得要命。我建议直接用RESTful API，JSON格式，简单明了。

另外，一定要做“心跳检测”。AGV调度系统每隔5秒向上位机发送一次心跳，上位机如果连续3次没收到，就认为调度系统挂了，触发报警。这个机制救过我很多次。

下面是一个心跳的示例：

// 心跳请求（AGV调度系统 -> 上位机）
GET /api/v1/heartbeat
Response:
{
  "status": "OK",
  "agv_count": 15,
  "active_tasks": 23,
  "system_load": 0.65
}

核心要点：心跳里带上系统负载信息，上位机可以根据负载动态调整任务下发频率。负载高的时候少发任务，负载低的时候多发。这样整个系统会更稳定。
