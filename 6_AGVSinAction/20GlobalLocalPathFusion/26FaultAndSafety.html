26 故障处理与安全机制

各位做AGV的朋友，你们有没有遇到过这种情况——车跑着跑着突然卡住了，规划器报错，然后整个系统就傻在那了？

我遇到过。而且不止一次。

说实话，路径规划做得再漂亮，如果故障处理和安全机制没跟上，那这车就是个定时炸弹。今天咱们就聊聊这个「保命」的话题。

26.1 规划失败恢复：别让车死在那

规划失败，说白了就是算法算不出路来了。原因很多：地图变了、障碍物堵死了、或者单纯就是计算超时。

我个人习惯把恢复策略分成三级：

级别 触发条件 恢复动作
L1 - 轻量恢复 单次规划超时 重新规划，最多重试3次
L2 - 中等恢复 连续3次规划失败 切换规划算法（如A*→RRT）
L3 - 重度恢复 所有算法都失败 请求远程干预或原地待命

核心原则：不要无限重试。我见过一个项目，规划失败后一直重试，结果电机堵转烧了。设定最大重试次数，这是底线。

代码实现上，我习惯这样写：

class RecoveryManager:
    def __init__(self, max_retries=3):
        self.retry_count = 0
        self.max_retries = max_retries
        self.planners = [AStarPlanner(), RRTPlanner(), HybridAStarPlanner()]
    
    def attempt_recovery(self, current_pose, goal):
        while self.retry_count < self.max_retries:
            planner = self.planners[self.retry_count % len(self.planners)]
            path = planner.plan(current_pose, goal)
            if path is not None:
                self.retry_count = 0
                return path
            self.retry_count += 1
            # 每次失败后，稍微放松一下约束
            planner.relax_constraints()
        return None  # 所有尝试都失败

我的经验：每次重试时，可以稍微放松一下约束条件。比如把碰撞检测的膨胀半径缩小5%，或者允许路径更曲折一些。有时候就是差那么一点点空间。

26.2 紧急制动：该停就得停

紧急制动不是简单的「刹车」两个字。你想想看，AGV上可能载着几百公斤的货物，急刹车会导致货物移位甚至翻倒。

我建议把制动分成三个等级：

  • 一级制动（预警）：减速到0.5m/s，同时发出声光报警。适用于检测到前方有动态障碍物但距离还够。
  • 二级制动（紧急）：立即停车，但保持电机力矩。适用于突然闯入的行人或跌落物。
  • 三级制动（急停）：切断动力源，机械刹车抱死。适用于传感器完全失效或通信中断。

注意：三级制动是最后的手段。我曾经遇到一个案例，三级制动触发太频繁，结果刹车片一个月就磨光了。能不用就别用。

紧急制动的触发条件，我一般这样设计：

def check_emergency_brake(self, state):
    # 1. 安全距离检查
    if self.front_distance < self.MIN_SAFE_DISTANCE:
        return BrakeLevel.EMERGENCY
    
    # 2. 速度异常检查
    if abs(state.velocity - state.target_velocity) > 0.5:
        return BrakeLevel.WARNING
    
    # 3. 传感器健康检查
    if self.sensor_health < 0.3:  # 传感器故障率超过70%
        return BrakeLevel.HARD_STOP
    
    return BrakeLevel.NONE

26.3 安全走廊：给车画个「安全区」

安全走廊这个概念，说白了就是给AGV规划一条「虚拟隧道」。车只能在隧道里走，出了隧道就触发保护。

我习惯用两种方式构建安全走廊：

  1. 静态安全走廊：基于地图预先生成。比如在货架通道里，左右各留30cm的余量。
  2. 动态安全走廊：实时计算。根据当前速度和转向角，动态调整走廊宽度。

动态安全走廊的计算公式其实不复杂：

def compute_dynamic_corridor(velocity, steering_angle):
    # 速度越快，走廊越宽（因为制动距离更长）
    base_width = 0.5  # 基础宽度0.5米
    speed_factor = velocity * 0.2  # 每1m/s加宽0.2米
    # 转向越大，走廊越宽（因为转弯半径更小）
    turn_factor = abs(steering_angle) * 0.3
    
    corridor_width = base_width + speed_factor + turn_factor
    return corridor_width

关键点：安全走廊不是越宽越好。太宽了，车就没法在狭窄通道里走了。我一般控制在0.5-1.2米之间，根据场景动态调整。

26.4 冗余规划器：多一个心眼

冗余规划器，说白了就是「备胎」。主规划器挂了，备用的顶上。

我一般配置三个规划器：

规划器 适用场景 计算速度 路径质量
A*（主） 常规场景，地图已知 快 高
RRT（备1） 动态障碍物多 中 中
DWA（备2） 局部避障，紧急情况 极快 低（但能用）

切换逻辑我这样设计：

class RedundantPlanner:
    def __init__(self):
        self.primary = AStarPlanner()
        self.backup1 = RRTPlanner()
        self.backup2 = DWAPlanner()
        self.active_planner = self.primary
    
    def plan(self, start, goal):
        # 主规划器先上
        path = self.active_planner.plan(start, goal)
        if path is not None:
            return path
        
        # 主规划器失败，切到备1
        print("主规划器失败，切换到RRT")
        self.active_planner = self.backup1
        path = self.active_planner.plan(start, goal)
        if path is not None:
            return path
        
        # 备1也失败，切到备2（DWA只做局部规划）
        print("RRT也失败，切换到DWA局部规划")
        self.active_planner = self.backup2
        path = self.active_planner.plan(start, goal)
        return path  # 即使路径质量差，也比没有强

我的建议：冗余规划器之间要定期做「健康检查」。我习惯每10秒让备胎规划器也跑一次，看看它能不能正常工作。别等到主规划器挂了才发现备胎也坏了。

26.5 整体架构：把这些串起来

好了，上面说的这些机制，怎么整合到一起？我画了一张图，你们看看：

这张图展示了整个流程：

  • 主规划器先上，不行就切备1，再不行切备2
  • 恢复管理器负责协调切换逻辑和重试策略
  • 安全走廊和紧急制动是两条并行的安全线
  • 最终所有指令都落到执行层

重要提醒：安全机制不能依赖单一传感器。我见过一个项目，只靠激光雷达做安全检测，结果激光雷达被灰尘遮住了，车直接撞墙。一定要多传感器融合，比如激光+超声波+碰撞条。

好了，这一章的内容就这些。故障处理和安全机制，说白了就是「防患于未然」和「亡羊补牢」的结合。你想想看，AGV在工厂里跑，万一出事故，轻则损坏货物，重则伤人。所以这些机制，一个都不能少。

我个人习惯在项目初期就把这些安全机制写进代码框架里，而不是等出问题了再补。因为——嗯，等你出问题再补，可能就没机会补了。
