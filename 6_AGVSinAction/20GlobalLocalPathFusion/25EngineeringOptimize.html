25 工程化与性能优化——规划频率提升、内存管理、多线程规划、实时性保障

各位同学，欢迎来到实战课的工程化环节。

前面我们聊了很多算法，A*、DWA、TEB，听起来都很酷。但说实话，把这些算法塞进一台真实的AGV里，让它跑得又快又稳，那才是真正的考验。我见过太多项目，算法仿真跑得飞起，一上实车就卡顿、丢路径、甚至撞墙。

为什么会这样？因为工程化没做好。今天我们就来聊聊，怎么把规划算法“打磨”成能上战场的武器。

核心观点： 规划算法的性能，不只看算法复杂度，更看工程实现的质量。一个优秀的规划器，是算法与工程完美结合的产物。

一、规划频率提升：从“慢吞吞”到“快准狠”

先问大家一个问题：你的AGV规划器，多久跑一次？

我见过很多团队，全局规划跑一次要100ms，局部规划跑一次要50ms。听起来还行？但你要知道，AGV在动态环境里，50ms的延迟可能就意味着一次急刹，甚至碰撞。

我个人习惯，把全局规划频率做到20Hz以上，局部规划做到50Hz以上。怎么做到的？

1.1 增量规划：别每次都从头算

全局规划里，A*算法每次都要从起点搜到终点。但你想过没有，如果环境变化不大，路径其实只需要微调。

我在项目中用过一种方法：路径缓存 + 局部修复。当障碍物出现时，只重新规划受影响的那一小段路径，而不是全盘重来。这招在仓储AGV里特别管用，因为货架位置很少变，变的只是临时障碍物。

// 伪代码：增量路径修复
Path repairPath(Path oldPath, Obstacle newObs) {
    // 找到障碍物影响的路段
    int startIdx = findImpactStart(oldPath, newObs);
    int endIdx = findImpactEnd(oldPath, newObs);
    
    // 只重新规划这一段
    Path localPath = aStarSearch(
        oldPath[startIdx], 
        oldPath[endIdx],
        newObs.getBoundingBox()
    );
    
    // 拼接回原路径
    return splicePath(oldPath, localPath, startIdx, endIdx);
}

小技巧： 增量规划的关键是“影响范围”的判定。我一般用障碍物的AABB（轴对齐包围盒）加上一个安全裕度，来确定需要重新规划的路段。裕度设太大，优化效果不明显；设太小，可能漏掉影响。

1.2 轻量化计算：能算一次就别算两次

局部规划里，DWA算法要采样很多速度组合。我见过有人采样1000组，然后评估。其实没必要。

我的做法是：先粗筛，再精评。第一轮用简单的碰撞检测，快速过滤掉明显不可行的速度；第二轮再用完整的代价函数，对剩下的候选做精细评估。这样能把计算量降到原来的1/5。

二、内存管理：别让内存成为瓶颈

说到内存管理，很多做算法的同学不太在意。但你知道吗？在嵌入式AGV上，内存泄漏是导致系统崩溃的头号杀手。

我曾经在一个项目里，AGV跑了3个小时后突然死机。查了两天，发现是规划器里有个vector每次规划都push_back，但从来没clear。嗯，这种坑我踩过不止一次。

2.1 对象池：避免频繁new/delete

规划过程中，会频繁创建节点、路径点、代价地图。每次new/delete都很慢，而且会产生内存碎片。

我的习惯是：预分配一个对象池。比如A*的节点，提前分配好1000个，用的时候从池子里取，用完放回去。这样既快又稳。

class NodePool {
    std::vector<AStarNode> pool;
    std::vector<int> freeList;
public:
    AStarNode* acquire() {
        if (freeList.empty()) {
            pool.emplace_back();
            return &pool.back();
        }
        int idx = freeList.back();
        freeList.pop_back();
        return &pool[idx];
    }
    void release(AStarNode* node) {
        freeList.push_back(node - &pool[0]);
    }
};

注意： 对象池的大小要合理设置。太小了会频繁扩容，太大了浪费内存。我一般根据地图大小和路径长度，动态调整池子大小。比如100x100的栅格地图，节点池设5000个基本够用。

2.2 零拷贝：减少数据搬运

规划器经常要访问代价地图、障碍物列表。如果每次规划都拷贝一份，内存和CPU都受不了。

我的做法是：共享指针 + 只读访问。代价地图用智能指针管理，规划器只读不写。如果地图更新了，用原子操作替换指针，保证线程安全。

三、多线程规划：让CPU为你打工

现在的AGV控制器，基本都是多核处理器。如果你只用一个线程跑规划，那简直是暴殄天物。

但多线程不是简单的“开几个线程就完事”。我见过有人开了8个线程，结果性能还不如单线程，因为锁竞争太严重了。

3.1 任务拆分：把规划拆成独立模块

我的做法是：全局规划、局部规划、碰撞检测，各跑一个线程。它们之间通过消息队列通信。

  • 全局规划线程：负责生成宏观路径，频率可以低一些（10Hz）
  • 局部规划线程：负责跟踪全局路径并避障，频率要高（50Hz）
  • 碰撞检测线程：持续检测前方障碍物，一旦发现危险，立即通知局部规划

这样，三个线程各司其职，互不干扰。全局规划慢一点没关系，局部规划依然能高频运行。

3.2 锁优化：能不用锁就不用

线程间共享数据，最怕加锁。我推荐用无锁队列或者读写锁。

比如代价地图，大部分时间是读操作，写操作很少。用读写锁，多个读线程可以同时访问，只有写的时候才互斥。这样性能能提升好几倍。

// 读写锁示例
std::shared_mutex mapMutex;
CostMap globalMap;

// 读线程（规划器）
void plannerThread() {
    std::shared_lock lock(mapMutex);
    // 读取地图，多个线程可以同时读
    auto cost = globalMap.getCost(x, y);
}

// 写线程（地图更新）
void mapUpdateThread() {
    std::unique_lock lock(mapMutex);
    // 更新地图，只有一个线程能写
    globalMap.update(region, newCost);
}

避坑指南： 我曾经在一个项目里用了std::mutex，结果局部规划线程经常被全局规划线程阻塞，导致避障延迟。后来改成std::shared_mutex，问题就解决了。记住：读多写少的场景，读写锁是王道。

四、实时性保障：别让AGV“死机”

实时性，说白了就是：在规定的时间内，必须给出结果。AGV不像你的手机，卡顿一下没关系。AGV卡顿100ms，可能就撞上了。

4.1 看门狗：监控规划超时

我的每个规划器里，都内置一个看门狗定时器。如果规划时间超过阈值（比如全局规划50ms，局部规划20ms），就触发超时处理。

超时处理策略：

  • 降级： 如果局部规划超时，直接沿用上一帧的路径，同时降低速度
  • 回退： 如果连续超时3次以上，触发紧急制动，并上报调度系统
  • 日志： 记录超时时的上下文，方便事后分析

4.2 时间片管理：给每个任务分配预算

我习惯用时间触发架构。每个规划任务分配固定的时间片，比如：

任务 时间片 频率 超时处理
全局规划 30ms 20Hz 沿用旧路径
局部规划 15ms 50Hz 减速+沿用旧路径
碰撞检测 5ms 100Hz 紧急制动
状态监控 2ms 200Hz 系统复位

这样，即使某个任务超时，也不会影响其他任务的执行。AGV依然能保持基本的运动控制。

重要提醒： 时间片不是越短越好。太短会导致频繁切换，增加系统开销。我一般根据任务的计算量和重要性来分配。碰撞检测最重要，时间片最短；全局规划可以慢一点，但必须保证路径质量。

4.3 降级策略：从“最优”到“可行”

实时性的核心思想是：宁可要一个次优的路径，也不要一个没有路径。

我在项目中设计了三档降级策略：

  1. 正常模式： 完整规划，追求最优路径
  2. 轻量模式： 减少采样数量，简化代价函数，追求快速响应
  3. 安全模式： 放弃路径规划，直接沿当前方向减速，直到停止

当系统负载高或者环境复杂时，自动切换到轻量模式。当检测到传感器异常或通信中断时，直接进入安全模式。

好了，关于工程化与性能优化，今天就聊这么多。这些经验，都是我一个个项目踩坑踩出来的。你想想看，一个AGV在仓库里跑，每天几万次规划，如果每次都能稳定在20ms以内，那整个系统的可靠性就完全不一样了。

记住：算法决定上限，工程决定下限。把工程做好，你的AGV才能真正落地。

总结要点：

  • 规划频率提升：增量规划 + 轻量化计算
  • 内存管理：对象池 + 零拷贝
  • 多线程规划：任务拆分 + 读写锁
  • 实时性保障：看门狗 + 时间片 + 降级策略
