21 多AGV协同规划：交通管制、优先级调度、死锁避免、分布式与集中式对比

好，咱们今天聊点硬核的。单台AGV跑得再溜，也就是个“独行侠”。真正考验系统能力的，是几十台甚至上百台AGV在同一个车间里穿梭。这时候，协同规划就成了核心中的核心。

我见过不少项目，单机测试时一切完美，一上多车就乱成一锅粥——堵车、死锁、空跑，甚至撞车。说白了，多AGV协同不是简单的“1+1=2”，而是要把交通管制、优先级调度、死锁避免这些机制揉在一起。今天我就把这几块掰开揉碎了讲。

核心观点：多AGV协同的本质，是在有限的空间和时间内，让所有AGV安全、高效地完成各自任务。没有完美的算法，只有最适合场景的工程方案。

一、交通管制：别让AGV“堵车”

先说说交通管制。这玩意儿跟城市交通管理很像——你不能让所有车都同时冲进同一个路口。

在AGV系统里，交通管制通常分两级：路段级和节点级。

  • 路段级管制：把地图划分成若干路段，每个路段同一时间只允许一台AGV进入。这有点像单行线。
  • 节点级管制：在交叉口、转弯处设置“虚拟红绿灯”，AGV到达前需要申请通行权。

我个人习惯用资源锁的方式来实现。每个路段或节点就是一个资源，AGV要经过就必须先“上锁”。

// 伪代码：路段资源锁申请
bool RequestPathSegment(AGV_ID, Segment_ID) {
    if (segment_locks[Segment_ID] == FREE) {
        segment_locks[Segment_ID] = LOCKED_BY(AGV_ID);
        return true;
    } else {
        // 加入等待队列
        waiting_queue[Segment_ID].push(AGV_ID);
        return false;
    }
}

嗯，这里要注意：锁的粒度很关键。锁得太细（比如每个网格一个锁），管理开销大；锁得太粗（比如整条路径一个锁），效率低。我一般建议按AGV车身长度+安全距离来划分路段长度。

避坑指南：我曾经在一个项目里把路段划得太短，结果AGV频繁申请锁、释放锁，通信开销反而比执行任务还大。后来调整为“两倍车长”作为最小路段，问题就解决了。

二、优先级调度：谁先走？

交通管制解决了“能不能走”的问题，但没解决“谁先走”。这就轮到优先级调度上场了。

优先级不是随便定的。我总结了几种常见策略：

  1. 任务紧急度优先：交货时间越紧的AGV，优先级越高。
  2. 距离终点近优先：快到的AGV先走，避免它绕路。
  3. 负载类型优先：比如载有危险品的AGV优先通行。
  4. FCFS（先到先得）：最简单，但效率不一定高。

实际项目中，我通常把优先级设计成一个动态加权值：

priority = w1 * urgency + w2 * distance_to_goal + w3 * load_type

权重w1、w2、w3需要根据现场情况调参。我记得有一次在汽车工厂，因为物料配送有严格的节拍要求，我把w1（紧急度）调得特别高，结果其他AGV全被堵在后面。后来加了“最大等待时间”限制，才平衡过来。

注意：优先级调度不能“饿死”低优先级AGV。一定要设置超时机制——如果某台AGV等待超过阈值，自动提升它的优先级。

三、死锁避免：别让AGV“僵住”

死锁是多AGV系统里最头疼的问题。四台AGV互相堵住，谁也动不了——你想想看，这场景多尴尬。

死锁的四个必要条件（互斥、持有并等待、不可剥夺、循环等待）在AGV系统里很容易满足。所以我们要主动避免。

我常用的方法有三种：

方法 原理 适用场景
银行家算法 预分配资源，检查安全性 小规模系统（<10台）
资源排序法 给所有资源编号，AGV按序申请 地图结构简单
超时回退法 检测到死锁后，强制某台AGV后退 大规模系统

我个人最推荐资源排序法。为什么？因为它简单、可靠、计算量小。你想想看，只要所有AGV都按同一个顺序申请资源，循环等待就不可能发生。

// 资源排序法示例
// 所有路段按ID排序，AGV只能按递增顺序申请
bool RequestResource(AGV_ID, Resource_ID) {
    if (Resource_ID < last_acquired_id) {
        // 违反顺序，拒绝
        return false;
    }
    // 正常申请逻辑...
}

避坑指南：我曾经在一个项目里只用了超时回退法，结果死锁频繁触发，AGV反复后退、前进，效率极低。后来加上资源排序法作为预防，死锁基本没再出现过。

四、分布式 vs 集中式：选哪个？

这是架构层面的选择。两种方案各有千秋，我直接上对比表：

维度 集中式 分布式
决策速度 快（单点决策） 慢（需要协商）
扩展性 差（中心节点瓶颈） 好（可动态加入AGV）
鲁棒性 差（中心挂了全瘫） 好（单台故障不影响整体）
实现复杂度 低 高
典型算法 全局A* + 交通管制 拍卖算法、合同网协议

我的建议是：20台以下用集中式，20台以上考虑分布式。但这不是绝对的——如果对实时性要求极高（比如AGV速度超过2m/s），集中式可能扛不住。

我记得有个物流仓库项目，初期规划30台AGV，客户坚持用集中式。结果上线后，中心服务器CPU跑满，决策延迟从50ms飙升到500ms。后来我们改成“集中调度+局部自治”的混合架构——全局路径由中心规划，局部避障和交通管制由AGV自己处理。这才把问题解决。

我的经验：纯集中式或纯分布式都很少见。实际工程中，90%的系统都是混合架构——集中式做全局优化，分布式做局部应急。
