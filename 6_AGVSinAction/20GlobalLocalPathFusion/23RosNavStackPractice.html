23 ROS Navigation Stack实战：move_base配置、全局/局部规划器插件、参数调优

说到ROS Navigation Stack，我估计很多做AGV的朋友又爱又恨。爱的是它功能齐全，恨的是参数太多，调起来让人头大。我自己刚入行那会儿，光一个move_base的配置文件就折腾了两周，最后还是靠看源码才搞明白。

这一章，咱们就直奔主题。不扯虚的，直接讲怎么配、怎么调、怎么避坑。

23.1 move_base的核心架构

先看一张图，把整体逻辑理清楚。

说白了，move_base就是个调度中心。它接收目标点，让全局规划器算出一条大路，再让局部规划器边走边微调。两个规划器各自维护一张代价地图，互不干扰。

关键点：全局规划器只管「能不能到」，局部规划器管「怎么走安全」。两者分工明确，但参数会互相影响。

23.2 配置文件结构

我习惯把配置文件拆成四个文件，这样好管理：

  • move_base.launch — 启动文件，加载所有参数
  • costmap_common_params.yaml — 通用代价地图参数
  • global_costmap_params.yaml — 全局代价地图专属参数
  • local_costmap_params.yaml — 局部代价地图专属参数
  • base_local_planner_params.yaml — 局部规划器参数

嗯，这里要注意：全局和局部代价地图的resolution参数，我建议保持一致。否则地图对齐会出问题，我踩过这个坑。

23.3 全局规划器插件选择

ROS里默认的全局规划器有两个：

规划器 算法 适用场景 我个人的评价
navfn Dijkstra / A* 通用场景 稳定，但路径不够平滑
global_planner Dijkstra / A* / 二次规划 需要路径平滑时 功能更全，我推荐用这个

配置方法很简单，在move_base的launch文件里指定：

<param name="base_global_planner" value="global_planner/GlobalPlanner" />

我个人习惯用global_planner，因为它支持neutral_cost和cost_factor参数，能让路径更贴近障碍物边缘。不过要注意，调得太激进容易撞墙。

23.4 局部规划器插件对比

局部规划器是AGV避障的关键。常用的有三个：

规划器 核心思想 优点 缺点
dwa_local_planner 速度空间采样 响应快，适合差速底盘 容易陷入局部最优
teb_local_planner 轨迹优化 路径平滑，支持后退 计算量大，参数多
eband_local_planner 弹性带 简单轻量 不太适合复杂环境

我的建议：如果AGV是差速底盘，优先用DWA。如果是全向底盘或者需要倒车，用TEB。我曾经在一个仓库项目里，DWA死活过不去一个窄通道，换成TEB加了个min_obstacle_dist参数就搞定了。

23.5 参数调优实战

调参这件事，说白了就是试错。但有个顺序：先调代价地图，再调规划器。

23.5.1 代价地图参数

核心参数就这几个：

# costmap_common_params.yaml
obstacle_range: 2.5      # 障碍物检测范围
raytrace_range: 3.0      # 射线追踪范围
inflation_radius: 0.55   # 膨胀半径
cost_scaling_factor: 10.0 # 代价衰减因子

避坑指南：我曾经把inflation_radius设成1.0米，结果AGV在走廊里直接卡死，因为膨胀后的障碍物把路全堵死了。后来改成0.55米，配合cost_scaling_factor调到5.0，才顺畅起来。

23.5.2 DWA局部规划器参数

DWA的参数比较多，但核心就这几个：

# base_local_planner_params.yaml
max_vel_x: 0.5           # 最大线速度
min_vel_x: 0.0           # 最小线速度
max_vel_theta: 1.0       # 最大角速度
min_vel_theta: -1.0      # 最小角速度
acc_lim_x: 0.5           # 线加速度
acc_lim_theta: 0.5       # 角加速度
xy_goal_tolerance: 0.1   # 位置容差
yaw_goal_tolerance: 0.05 # 角度容差
sim_time: 1.5            # 模拟时间

注意：sim_time这个参数很关键。设得太小，规划器只看眼前，容易急转弯。设得太大，计算量暴增，实时性下降。我一般设在1.5到2.0之间。

23.5.3 TEB局部规划器参数

如果你用TEB，这几个参数要重点关注：

# teb_local_planner_params.yaml
min_obstacle_dist: 0.3   # 最小障碍物距离
inflation_dist: 0.6      # 膨胀距离
weight_obstacle: 50.0    # 障碍物权重
weight_dynamic_obstacle: 10.0 # 动态障碍物权重
weight_kinematics_forward_drive: 1000.0 # 前向驱动权重
weight_optimaltime: 1.0  # 时间最优权重

为什么TEB参数这么多？因为它本质上是在求解一个优化问题。每个权重都对应一个约束条件。调TEB就像调PID，需要耐心。

23.6 恢复行为配置

AGV卡住的时候怎么办？恢复行为就是干这个的。默认配置是这样的：

# move_base参数中
recovery_behaviors: [
  {name: 'conservative_reset', type: 'clear_costmap_recovery/ClearCostmapRecovery'},
  {name: 'rotate_recovery', type: 'rotate_recovery/RotateRecovery'},
  {name: 'aggressive_reset', type: 'clear_costmap_recovery/ClearCostmapRecovery'}
]

执行顺序是：先清代价地图，再原地旋转，最后再清一次。如果还不行，move_base就报错。

我的经验：在AGV项目里，我加了一个自定义恢复行为——先后退0.5米再重新规划。这个简单操作，让卡死率降低了60%。

23.7 性能监控与调试

调参的时候，光看AGV跑不跑是不够的。我建议用这几个工具：

  • rviz — 可视化代价地图和规划路径
  • rqt_graph — 看节点通信是否正常
  • rqt_reconfigure — 动态调参，不用重启节点
  • rostopic echo /move_base/status — 看规划状态

你想想看，如果AGV突然停下来，你连代价地图都看不到，怎么知道是膨胀半径设大了，还是传感器数据丢了？

23.8 常见问题与解决方案

问题现象 可能原因 解决方案
AGV原地打转 局部规划器参数不合理 调小sim_time，增大weight_kinematics_forward_drive
路径抖动严重 代价地图更新太快 增大update_frequency，减小publish_frequency
AGV撞到障碍物 膨胀半径太小或传感器盲区 增大inflation_radius，检查传感器配置
规划失败频繁 全局路径被障碍物堵死 检查地图完整性，调整obstacle_range

嗯，这里要特别说一下：如果AGV频繁规划失败，先别急着调参数。先看看地图是不是有问题。我遇到过好几次，都是因为激光雷达安装角度不对，导致地图里有「幽灵障碍物」。

23.9 总结

ROS Navigation Stack的调优，说白了就是三个字：看、调、试。看代价地图，调核心参数，试实际效果。没有一劳永逸的参数组合，每个项目都有自己的「脾气」。

我个人建议，先把DWA调通，再考虑换TEB。DWA的参数少，容易上手。等你对代价地图的理解到位了，再去折腾TEB那些权重参数，会轻松很多。

最后送大家一句话：参数调优没有捷径，但一定有规律可循。多记录、多对比、多总结，你也能成为调参高手。
