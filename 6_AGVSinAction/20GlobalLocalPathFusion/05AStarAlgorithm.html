5 A*算法详解：启发式函数设计、Open/Closed列表、路径平滑、工程实现中的内存优化

各位同学，今天我们来啃一块硬骨头——A*算法。说实话，我在刚入行那会儿，觉得A*不就是个寻路算法嘛，网上代码一抓一大把。直到我在一个仓储AGV项目里，车跑到一半突然卡死，排查了三天才发现是启发式函数设计出了问题。嗯，从那以后我再也不敢小看这个“经典算法”了。

A*算法说白了就是“贪心+最优”的结合体。它既不像Dijkstra那样傻傻地遍历所有节点，也不像贪心最佳优先那样容易撞墙。它用了一个巧妙的评价函数：f(n) = g(n) + h(n)。g(n)是起点到当前点的实际代价，h(n)是当前点到目标点的估计代价。你想想看，这个h(n)就是整个算法的灵魂所在。

5.1 启发式函数设计：算法的“眼睛”

启发式函数h(n)的设计，直接决定了A*的表现。我个人习惯把启发式函数分成三类：

类型 公式 特点 适用场景
曼哈顿距离 |x1-x2| + |y1-y2| 只允许四方向移动，计算快 仓储AGV网格地图
欧几里得距离 √((x1-x2)²+(y1-y2)²) 允许任意方向，精度高 自由导航AGV
对角线距离 max(|dx|,|dy|) + (√2-1)*min(|dx|,|dy|) 允许八方向移动，兼顾效率 工厂AGV（最常用）

这里有个关键点：h(n)必须满足可采纳性——它不能高估实际代价。我在项目中遇到过一个问题：用了欧几里得距离但地图有障碍物，结果A*扩展了比预期多3倍的节点。为什么？因为欧几里得距离穿墙而过，严重低估了实际路径长度。

核心原则：h(n)越接近真实代价，A*扩展的节点越少。但h(n)计算本身不能太复杂，否则得不偿失。

我的小技巧：对于动态障碍物多的场景，我会给h(n)加一个1.1~1.2的权重系数。这样A*会更快找到路径，虽然不一定是最优，但工程上够用了。这叫“加权A*”，我用了好多年。

5.2 Open/Closed列表：算法的“大脑”

Open列表存待考察的节点，Closed列表存已考察的节点。听起来简单，但实现起来坑不少。

我曾经在一个项目中用普通的List来存Open列表，每次取最小f值节点都要遍历一遍。地图稍微大一点（比如200x200），算法直接卡成PPT。后来我换成了二叉堆（Binary Heap），插入和取最小都是O(log n)，性能提升了一个数量级。

代码实现长这样：

// 二叉堆实现Open列表
public class BinaryHeap {
    private Node[] heap;
    private int size;
    
    public void push(Node node) {
        heap[size] = node;
        int i = size;
        while (i > 0 && heap[i].f < heap[(i-1)/2].f) {
            swap(i, (i-1)/2);
            i = (i-1)/2;
        }
        size++;
    }
    
    public Node pop() {
        Node min = heap[0];
        heap[0] = heap[--size];
        int i = 0;
        while (true) {
            int smallest = i;
            int left = 2*i + 1;
            int right = 2*i + 2;
            if (left < size && heap[left].f < heap[smallest].f) smallest = left;
            if (right < size && heap[right].f < heap[smallest].f) smallest = right;
            if (smallest == i) break;
            swap(i, smallest);
            i = smallest;
        }
        return min;
    }
}

注意：Closed列表用哈希表实现，不要用List。否则每次判断节点是否已访问，时间复杂度从O(1)变成O(n)。我见过有人用List存Closed列表，1000个节点时算法就慢得没法用了。

5.3 路径平滑：让AGV走得更优雅

A*找出来的路径有个毛病——全是锯齿状的折线。AGV如果按这个路径走，每到一个拐点就要停下来转向，效率极低。我在一个电商仓库项目里，AGV按原始路径走，平均速度只有0.5m/s，因为频繁加减速。

解决方案是路径后处理平滑。我常用的方法有两种：

  1. 拐点简化法：从起点开始，尝试跳过中间节点直接连接后面的节点，如果连线不碰障碍物就跳过。这样可以把锯齿路径拉直。
  2. 贝塞尔曲线插值：在拐点处用三次贝塞尔曲线做平滑过渡。AGV走起来就是一条流畅的弧线，不用停车。

代码实现拐点简化：

// 路径简化：去掉冗余拐点
public List<Point> simplifyPath(List<Point> path, boolean[][] obstacles) {
    List<Point> result = new ArrayList<>();
    result.add(path.get(0));
    int current = 0;
    for (int i = 2; i < path.size(); i++) {
        if (!hasLineOfSight(path.get(current), path.get(i), obstacles)) {
            result.add(path.get(i-1));
            current = i-1;
        }
    }
    result.add(path.get(path.size()-1));
    return result;
}

经验之谈：平滑后的路径一定要做碰撞检测。我曾经偷懒没做，结果AGV在拐弯时蹭到了货架。从那以后，我每条平滑路径都会用“膨胀后的障碍物地图”重新验证一遍。

5.4 工程实现中的内存优化

AGV的地图动不动就是1000x1000的网格，每个节点存一个对象，内存直接爆炸。我算过一笔账：每个节点对象约40字节，100万个节点就是40MB，再加上Open/Closed列表，轻松破100MB。嵌入式控制器根本扛不住。

我的优化策略：

  • 用数组代替对象：把节点的g值、h值、父节点索引用三个int数组存。这样每个节点只占12字节，内存降到原来的1/3。
  • 状态压缩：用一个byte数组标记节点状态（0=未访问，1=在Open列表，2=在Closed列表），比用HashSet省内存。
  • 延迟初始化：只有节点第一次被访问时才分配内存。地图上大部分节点其实用不到，没必要全部初始化。

优化后的内存布局：

// 内存优化版节点管理
public class AStarMemoryOptimized {
    private int[] gCost;      // 实际代价
    private int[] hCost;      // 启发式代价
    private int[] parent;     // 父节点索引
    private byte[] state;     // 0=未访问, 1=Open, 2=Closed
    private int width;
    
    public AStarMemoryOptimized(int width, int height) {
        int size = width * height;
        gCost = new int[size];
        hCost = new int[size];
        parent = new int[size];
        state = new byte[size];
        this.width = width;
        // 注意：这里只分配了数组，没有创建任何对象
    }
    
    private int getIndex(int x, int y) {
        return y * width + x;
    }
}

最终效果：同样的1000x1000地图，优化前内存占用120MB，优化后降到28MB。而且因为内存连续，CPU缓存命中率更高，算法速度反而提升了15%。

好了，A*算法的核心内容就这些。启发式函数是眼睛，Open/Closed列表是大脑，路径平滑是手脚，内存优化是骨架。四者缺一不可。我在实际项目中，光是调启发式函数的权重就花了两周时间——不同的地图、不同的AGV车型，最优参数都不一样。这东西没有银弹，只能多试。

最后说一句：别迷信论文里的最优参数。我见过一个团队照搬论文的A*参数，结果在真实仓库里AGV频繁死锁。工程上的东西，一定要在自己的地图上跑一遍，用数据说话。
