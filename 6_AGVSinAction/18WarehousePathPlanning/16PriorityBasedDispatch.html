16 基于优先级的调度：静态优先级、动态优先级、死锁避免

各位好，我是老张。今天聊的话题，说白了就是「谁先走，谁后走」的问题。

AGV调度里，优先级是个绕不开的坎。你想想看，仓库里几十台车同时跑，有的车拉着急单，有的车只是去补货。如果一视同仁，急单可能被堵死。我见过一个项目，就因为优先级没设好，结果VIP订单的AGV被普通补货车堵了整整8分钟——客户差点掀桌子。

所以，优先级调度不是「要不要」的问题，而是「怎么设」的问题。今天我把三种主流方案掰开揉碎了讲：静态优先级、动态优先级，还有死锁避免。

16.1 静态优先级：简单粗暴，但够用

静态优先级，就是给每台AGV、每个任务提前定好一个「等级」。比如：

  • 紧急订单：优先级 10
  • 普通补货：优先级 5
  • 空车回库：优先级 1

调度器每次选任务时，直接挑优先级最高的那个。代码实现也很直白：

// 静态优先级调度示例
typedef struct {
    int task_id;
    int priority;  // 数值越大优先级越高
    char* destination;
} Task;

Task* select_highest_priority(Task tasks[], int count) {
    Task* best = &tasks[0];
    for (int i = 1; i < count; i++) {
        if (tasks[i].priority > best->priority) {
            best = &tasks[i];
        }
    }
    return best;
}

嗯，这里要注意：静态优先级虽然简单，但有个致命问题——优先级反转。什么意思？就是低优先级的车占了路口，高优先级的车过不去。我在一个电商仓库就踩过这个坑，后来加了个「优先级继承」机制才解决。

我的经验：静态优先级适合任务类型固定的场景。比如分拣区和存储区之间，任务类型就那么几种，设好优先级基本不用动。但如果业务经常变，静态方案就有点僵了。

16.2 动态优先级：灵活，但别玩脱了

动态优先级，就是优先级会随着时间、状态、拥堵情况变化。说白了，让系统自己「看情况」调整。

常见的动态策略有：

  • 时间衰减：任务等得越久，优先级越高。防止饿死。
  • 拥堵反馈：某区域车太多，降低该区域任务的优先级，引导分流。
  • 电量感知：电量低于20%的AGV，优先级自动提升，让它赶紧去充电。

我做过一个项目，用了「时间+拥堵」双因子动态优先级。核心逻辑是这样的：

// 动态优先级计算
float calc_dynamic_priority(Task* task, float congestion_factor) {
    float base = task->base_priority;
    float wait_bonus = task->wait_time * 0.1;  // 每等1秒加0.1
    float congestion_penalty = congestion_factor * 0.5;  // 拥堵越严重，扣分越多
    return base + wait_bonus - congestion_penalty;
}

为什么会这样设计？因为单纯按等待时间提权，会导致所有车都往一个方向挤。加上拥堵惩罚后，系统会自动「绕路」——说白了，就是让车学会避高峰。

避坑指南：我曾经把动态优先级调得太灵敏，结果AGV频繁变道，反而增加了死锁概率。后来加了「最小变更间隔」——每台车5秒内只能改一次优先级，这才稳定下来。

16.3 死锁避免：优先级调度的「安全网」

优先级调度搞不好，就会死锁。什么叫死锁？就是两台车互相堵着，谁也别想走。我见过最夸张的一次，8台AGV在十字路口「打结」，整个仓库瘫痪了40分钟。

死锁避免的核心思路就四个字：提前预防。别等死锁发生了再解，而是在分配资源（比如路口、充电桩）之前，先检查一下「如果给了，会不会死锁」。

常用的方法是银行家算法的变体。简单说就是：

  1. 每台AGV申请资源时，先模拟分配
  2. 检查分配后系统是否处于「安全状态」
  3. 安全才给，不安全就排队等

代码实现大概长这样：

// 死锁避免检查（简化版）
bool is_safe_state(AGV* agvs, int count, Resource* res) {
    // 模拟分配资源
    Resource temp = *res;
    for (int i = 0; i < count; i++) {
        if (agvs[i].request <= temp.available) {
            temp.available -= agvs[i].request;
            temp.allocated[i] += agvs[i].request;
        } else {
            return false;  // 资源不够，不安全
        }
    }
    return true;  // 所有AGV都能满足，安全
}

嗯，这里要注意：银行家算法虽然理论完美，但实际项目中很少全量使用。为什么？因为计算量太大。仓库里几十台车，每台车申请资源都跑一遍模拟，调度周期会变长。

我的做法：只在关键资源（比如单行道入口、充电桩）上做死锁避免检查。普通路口用「超时回退」——如果一台车在路口等超过10秒，自动倒车让路。简单，但有效。

16.4 三种方案的对比与选择

说了这么多，到底怎么选？我整理了一张表，方便你对照：

方案 优点 缺点 适用场景
静态优先级 实现简单，性能高 不灵活，可能饿死 任务类型固定，业务稳定
动态优先级 适应性强，利用率高 参数调优复杂，可能震荡 业务波动大，多品种订单
死锁避免 安全性高，系统稳定 计算开销大，降低吞吐 高密度、高价值场景

我个人习惯是：动态优先级 + 关键点死锁避免。说白了，用动态优先级保证效率，用死锁避免兜底。这样既不会太死板，也不会太冒险。

最后说一句：优先级调度没有银弹。你想想看，每个仓库的布局、订单结构、AGV数量都不一样。最好的方案，永远是「试出来的」。我每次做新项目，都会先在仿真环境里跑三天，调参数调到吐——但值得。

一个小技巧：在调度日志里加上「优先级变更记录」。这样出了问题，你能回溯到「哪台车在什么时间因为什么原因改了优先级」。排查死锁时，这个日志比什么工具都好使。
