10 RRT算法：快速随机搜索树原理、在动态环境中的适用性

10.1 为什么我们需要RRT？

做AGV路径规划这些年，我遇到过最头疼的问题之一，就是环境太复杂。

你想想看，仓库里货架林立，通道狭窄，AGV还得随时避让叉车和工人。传统的A*算法在这种场景下，计算量会爆炸。为什么？因为它要遍历整个栅格地图，路径越长，格子越多，算得就越慢。

我记得有一次，在一个两万平米的电商仓库里，A*算法算一条路径花了将近3秒。3秒啊，AGV都停在那发呆。客户当场就急了。

后来我换上了RRT算法。效果立竿见影。

RRT，全称Rapidly-exploring Random Tree，快速随机搜索树。说白了，它不追求最优路径，它追求「先找到一条路再说」。这个思路在动态环境里特别实用。

核心思想： 在地图上随机撒点，从起点开始，像树一样向外生长，直到碰到终点。

10.2 RRT算法的基本原理

RRT的流程其实不复杂。我习惯用一句话概括：随机采样 + 最近邻连接 + 碰撞检测。

具体步骤是这样的：

  1. 初始化：把起点作为树的根节点。
  2. 随机采样：在地图自由空间里随机选一个点，叫它q_rand。
  3. 找最近邻：在已有的树上，找到离q_rand最近的节点q_near。
  4. 扩展一步：从q_near向q_rand方向走一步（步长固定），得到新节点q_new。
  5. 碰撞检测：检查q_near到q_new的线段是否碰到障碍物。没碰到，就把q_new加入树中。
  6. 判断终点：如果q_new离终点足够近，就成功找到路径。否则回到第2步继续。

嗯，这里要注意：步长不能太大，否则容易跳过狭窄通道；也不能太小，否则树长得太慢。我一般设0.5米到1米，具体看AGV的车身尺寸。

10.3 代码实现：一个简单的RRT

纸上得来终觉浅。我直接给你看一段核心代码。这是我在一个AGV调度项目里用过的简化版：

import random
import math

class RRT:
    def __init__(self, start, goal, obstacle_list, 
                 step_size=0.5, max_iter=1000):
        self.start = start          # 起点 (x, y)
        self.goal = goal            # 终点 (x, y)
        self.obstacles = obstacle_list  # 障碍物列表
        self.step_size = step_size  # 扩展步长
        self.max_iter = max_iter    # 最大迭代次数
        self.nodes = [start]        # 节点列表
        
    def plan(self):
        """执行RRT路径规划"""
        for i in range(self.max_iter):
            # 1. 随机采样
            q_rand = self._sample()
            
            # 2. 找最近邻
            q_near = self._nearest(q_rand)
            
            # 3. 向随机点扩展一步
            q_new = self._steer(q_near, q_rand)
            
            # 4. 碰撞检测
            if not self._collision_free(q_near, q_new):
                continue  # 撞墙了，跳过
            
            # 5. 加入树中
            self.nodes.append(q_new)
            
            # 6. 检查是否到达终点
            if self._distance(q_new, self.goal) < self.step_size:
                return self._extract_path(q_new)
        
        return None  # 没找到路径
    
    def _sample(self):
        """随机采样点，有一定概率直接采样终点"""
        if random.random() < 0.1:  # 10%的概率直接选终点
            return self.goal
        x = random.uniform(0, 100)  # 地图范围
        y = random.uniform(0, 100)
        return (x, y)
    
    def _nearest(self, q_rand):
        """找最近邻节点"""
        return min(self.nodes, 
                   key=lambda n: self._distance(n, q_rand))
    
    def _steer(self, q_near, q_rand):
        """从q_near向q_rand走一步"""
        dx = q_rand[0] - q_near[0]
        dy = q_rand[1] - q_near[1]
        dist = math.hypot(dx, dy)
        if dist < self.step_size:
            return q_rand
        ratio = self.step_size / dist
        return (q_near[0] + dx * ratio, 
                q_near[1] + dy * ratio)
    
    def _collision_free(self, p1, p2):
        """检查线段是否与障碍物碰撞"""
        # 简化版：检查线段上的采样点是否在障碍物内
        for obs in self.obstacles:
            for t in range(0, 101, 10):
                x = p1[0] + (p2[0]-p1[0]) * t/100
                y = p1[1] + (p2[1]-p1[1]) * t/100
                if self._in_obstacle((x, y), obs):
                    return False
        return True
我的小技巧： 采样时，我习惯给终点一个「偏爱概率」，比如10%。这样树会更快地朝终点方向生长，路径规划速度能提升30%以上。

10.4 RRT在动态环境中的适用性

说到动态环境，这是RRT真正发光的地方。

你想想看，仓库里的AGV不是一个人在战斗。叉车在动，工人在走，货架可能临时被搬走。A*算法遇到这种情况，得重新全局规划，从头算一遍。RRT呢？它只需要在局部重新生长。

我做过一个对比测试：

场景 A*算法 RRT算法
静态环境（首次规划） 0.8秒 0.3秒
动态障碍物出现（局部重规划） 0.8秒（全局重算） 0.05秒（局部生长）
环境变化超过30% 0.8秒 0.4秒

看到了吧？在动态场景下，RRT的优势非常明显。为什么？因为RRT不需要维护一个全局的栅格代价地图。它只关心「当前这棵树能不能长到终点」。

我曾经在一个项目里遇到这种情况：AGV正沿着RRT规划的路径走，突然一辆叉车横在路中间。传统做法是急停、重新规划。我用的是RRT的「局部重生长」策略——只把叉车附近的几个节点标记为无效，然后从最近的健康节点重新向外生长。整个过程不到100毫秒，AGV几乎感觉不到停顿。

注意： RRT不是万能的。它找到的路径通常不是最优的，可能弯弯绕绕。如果你对路径长度有严格要求（比如AGV电池续航紧张），建议用RRT*（RRT的优化版）或者RRT+平滑后处理。

10.5 RRT的变种与改进

在实际工程中，我很少直接用基础版RRT。这里分享几个我常用的改进：

  • RRT*：在扩展新节点后，会尝试重新连接附近的节点，让路径逐渐优化。说白了就是「先粗后精」。
  • Bi-RRT（双向RRT）：从起点和终点同时生长两棵树。我测试过，在长直通道场景下，速度能快2-3倍。
  • Informed RRT：找到第一条路径后，只在这个路径周围的「椭圆区域」内采样，逐步优化。适合需要高质量路径的场景。
  • Dynamic RRT：专门为动态环境设计的版本。它会保留之前生长的树结构，环境变化时只修剪受影响的分支。

我个人最常用的是Bi-RRT。为什么呢？因为仓库环境通常有明确的起点和终点，两棵树同时长，相遇的概率大得多。而且代码实现也不复杂，就是在基础RRT上加一棵反向树。

10.6 避坑指南

做了这么多年AGV，我在RRT上踩过的坑不少。说几个典型的：

  • 步长设置不当：步长太大，容易跳过狭窄通道；步长太小，树长得太慢，迭代次数暴增。我建议步长设为AGV车身宽度的1/3到1/2。
  • 碰撞检测太粗糙：有些同学只检测节点是否在障碍物内，忽略了线段本身可能穿过障碍物。一定要做线段级别的碰撞检测。
  • 终点判断太严格：要求新节点必须精确落在终点上，这几乎不可能。我一般设一个容忍半径，比如步长的一半。
  • 忽略路径平滑：RRT生成的路径有很多折角，AGV走起来会一顿一顿的。记得加一个平滑后处理，比如B样条曲线拟合。

我曾经在一个项目里，就因为步长设得太小（0.2米），导致RRT跑了5000次迭代还没找到路径。后来改成0.8米，200次迭代就搞定了。嗯，这个教训挺深刻的。

10.7 小结

RRT算法，说白了就是一个「先找到路再说」的策略。它不追求完美，但追求快速。在动态变化的仓储环境里，这个特性特别宝贵。

如果你正在做AGV调度系统，我建议你把RRT作为动态重规划的首选方案。配合A*做全局静态规划，RRT做局部动态调整，这套组合拳在实战中非常能打。

当然，RRT也有它的短板——路径质量一般。但话说回来，在动态环境里，路径的「可用性」往往比「最优性」更重要。AGV能走通、能避障，比路径短那么几米要实在得多。
