17 集中式路径规划：多AGV A*、CBS（基于冲突的搜索）原理

各位工程师朋友，今天我们来聊聊多AGV路径规划里最经典的两个方法：多AGV A*和CBS。说实话，我在刚入行那会儿，觉得单台AGV能跑起来就挺厉害了。后来项目一上量，十几台车在仓库里同时跑，我才发现——真正的坑，全在“多车协同”上。

17.1 为什么需要集中式规划？

先问大家一个问题：如果每台AGV都自己算自己的路径，会发生什么？

我在一个电商仓库项目里就吃过这个亏。当时用的是分布式规划，每台车独立跑A*。结果呢？两台车在同一个巷道里面对面堵死了。一个要往东，一个要往西，谁也不让谁。最后靠人工去搬货，场面一度非常尴尬。

集中式规划的核心思路很简单：有一个中央大脑，同时为所有AGV规划路径。这个大脑知道每台车的起点、终点、当前状态，然后统一算出一套“不打架”的路径方案。

集中式 vs 分布式：

  • 集中式：全局最优，但计算量大，适合车数不多（通常≤30台）的场景
  • 分布式：计算快，但容易死锁，需要额外的协调机制

17.2 多AGV A*：把多车问题变成单车问题

多AGV A*的思路，说白了就是“按顺序规划，后车避让前车”。

具体怎么做呢？我习惯这样操作：

  1. 给所有AGV排个优先级（比如任务紧急的先走）
  2. 用A*给第一台车算路径
  3. 把第一台车的路径占用的时空信息，标记为“障碍”
  4. 用A*给第二台车算路径，避开这些时空障碍
  5. 重复直到所有车都规划完

听起来很简单对吧？但这里有个大坑——顺序依赖。你想想看，如果优先级排错了，后面的车可能绕一大圈，甚至无路可走。

我的经验：我曾经在一个项目里，把充电返回的AGV优先级设得很高。结果它慢悠悠往回走，把后面急着送货的车全堵死了。后来我改成“任务截止时间越近，优先级越高”，情况就好多了。

下面是一个简化的多AGV A*伪代码，大家可以感受一下：

function multiAGV_AStar(agents, map):
    // agents: 所有AGV的列表，每个包含起点、终点
    // map: 栅格地图
    
    paths = []
    reserved = {}  // 时空占用表：{时间步: [坐标列表]}
    
    // 按优先级排序
    sorted_agents = sort_by_priority(agents)
    
    for agent in sorted_agents:
        // 把已占用的时空点作为动态障碍
        dynamic_obstacles = get_dynamic_obstacles(reserved, agent.start_time)
        
        // 调用单AGV A*，避开动态障碍
        path = AStar(map, agent.start, agent.goal, dynamic_obstacles)
        
        if path is None:
            return FAIL  // 无解，需要重新调度
        
        // 记录这条路径的时空占用
        for t, pos in enumerate(path):
            reserved[agent.start_time + t] = pos
        
        paths.append(path)
    
    return paths

17.3 CBS：更优雅的冲突解决方式

多AGV A*虽然简单，但有个硬伤：它假设先规划的路径是“神圣不可侵犯”的。后车只能绕着走，不能要求前车改道。

这就引出了CBS（Conflict-Based Search）。我第一次接触CBS是在读一篇论文时，当时觉得这算法真聪明——它把多车路径规划拆成了两层：

  • 高层：检测冲突，给冲突的车加约束（比如“车A在时间t不能出现在坐标(x,y)”）
  • 低层：每台车在约束条件下，各自跑A*算路径

这两层反复迭代，直到所有车的路径都没有冲突为止。

CBS的核心思想：与其让后车一味忍让，不如让冲突双方都做出调整。这就像两个人过独木桥——不是一个人永远让着另一个人，而是双方各退一步，找到都能接受的方案。

17.5 CBS中的冲突类型

在实际项目中，我遇到的冲突主要有两种：

冲突类型 描述 约束示例
顶点冲突 两车在同一时间到达同一位置 车A在时间t不能到(x,y)
边冲突 两车在同一时间交换位置（迎面相遇） 车A在时间t不能从(x1,y1)到(x2,y2)

注意：边冲突比顶点冲突更难处理。我曾经在一个窄巷道仓库里，两台车在通道中间迎面相遇，CBS花了7轮迭代才找到解。后来我加了一条规则——窄巷道强制单向通行，问题就简单多了。

17.6 CBS的优缺点

我用了这么多年CBS，总结下来就是：

  • 优点：
    • 能找到最优解（如果低层A*用的是最优算法）
    • 比多AGV A*更灵活，冲突双方都能调整
    • 适合车数较少（≤20台）的场景
  • 缺点：
    • 计算时间可能很长（最坏情况是指数级）
    • 对地图大小敏感，地图越大，搜索空间越大
    • 不适合动态变化的环境（比如突然有新的任务插入）

我的建议：如果你车数少于10台，CBS是很好的选择。如果车数在10-30台之间，可以考虑用改进版的ICBS（Improved CBS），它加入了优先级启发式，收敛更快。超过30台？嗯，我建议你考虑分层规划或者交通管制方案。

17.7 实际项目中的选择

最后，我想说说在实际项目中怎么选。我个人的经验是：

  • 场景一：小仓库，5-8台AGV → 用CBS，追求最优路径
  • 场景二：中型仓库，10-20台AGV → 用多AGV A*，配合合理的优先级策略
  • 场景三：大型仓库，30+台AGV → 别用集中式了，考虑分区规划或交通管制

我记得有一次，一个客户非要让50台AGV用CBS跑。我劝了半天没用，结果算法跑了3分钟还没出结果。最后我改成区域管制——把仓库分成4个区，每个区独立规划，区之间用缓冲区过渡。效果立竿见影，响应时间降到了2秒以内。

所以说，算法再好，也要看场景。做工程嘛，实用才是硬道理。
