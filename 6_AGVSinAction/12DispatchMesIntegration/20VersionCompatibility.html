20 版本升级与兼容：接口版本兼容策略、数据迁移方案、灰度升级、回滚机制

做MES和AGV调度系统对接，最怕什么？

我最怕半夜接到电话说：「系统升级后，AGV不走了。」

嗯，这不是开玩笑。版本升级这件事，搞不好就是生产事故。我做了这么多年集成，见过太多因为升级导致产线停摆的案例。今天咱们就聊聊，怎么把升级这件事做得稳当。

接口版本兼容策略

先说接口版本兼容。说白了，就是新版本上线了，老版本还能不能用。

我个人习惯的做法是：永远不要删除接口字段，只做新增。

核心原则：向前兼容，向后兼容

  • 向前兼容：新版本接口能处理老版本发来的数据
  • 向后兼容：老版本客户端能调用新版本接口

我在项目中遇到过这样一个坑：某次升级，我们把AGV任务状态字段从「枚举值」改成了「字符串+枚举值混合」。结果老版本的MES系统解析不了新格式，直接报错。产线停了2小时。

后来我定了个规矩：接口版本号必须显式声明。

// 请求头中携带版本号
Accept: application/vnd.agv.v2+json

// 响应头中返回版本号
Content-Type: application/vnd.agv.v2+json

这样，新老版本可以共存。MES发v1请求，AGV调度系统用v1逻辑处理；发v2请求，用v2逻辑处理。

我的经验：接口版本号建议用「主版本.次版本」格式。主版本变更意味着不兼容，次版本变更意味着兼容。别学某些大厂，版本号随便跳，最后自己都搞不清哪个版本能用。

数据迁移方案

升级往往伴随着数据迁移。AGV调度系统里的数据，比如任务记录、路径规划、设备状态，这些都不能丢。

我常用的数据迁移策略有三种：

迁移方式 适用场景 风险等级
全量迁移 数据量小，停机窗口充足 低
增量迁移 数据量大，不能长时间停机 中
双写迁移 要求零停机，高可用场景 高

全量迁移最简单，但耗时长。我记得有一次迁移AGV的历史轨迹数据，300万条记录，跑了整整4个小时。产线停了4小时，厂长差点没把我吃了。

后来我改用增量迁移：先全量迁移历史数据，然后实时同步增量数据。这样停机时间从4小时缩短到10分钟。

避坑指南：我曾经遇到过增量迁移时，数据源和目标库的ID生成策略不一致，导致数据冲突。后来我强制要求：所有迁移任务必须使用「源ID+时间戳」作为唯一标识，避免冲突。

灰度升级

灰度升级，说白了就是「先让一小部分AGV试试水」。

我建议的灰度策略是这样的：

  1. 1%灰度：选1台AGV，跑新版本。观察24小时
  2. 10%灰度：扩大到10%的AGV。观察48小时
  3. 50%灰度：扩大到一半AGV。观察72小时
  4. 全量发布：没问题了，全部升级

为什么会这样分步走？因为AGV调度系统一旦出问题，影响的是整个产线物流。你想想看，如果100台AGV同时升级，新版本有个bug导致路径规划异常，那场面...我不敢想。

我在项目中实现灰度升级时，用了一个简单的配置中心：

// 灰度配置示例
{
  "version": "v2.1.0",
  "grayStrategy": {
    "type": "percentage",
    "value": 10,
    "whitelist": ["AGV-001", "AGV-002"]
  }
}

配置中心实时更新，AGV每隔30秒拉取一次。如果发现自己的版本和配置中心指定的版本不一致，就触发升级流程。

我的小技巧：灰度升级时，一定要监控「任务完成率」和「异常率」这两个指标。如果任务完成率下降超过5%，立刻停止灰度，回滚。

回滚机制

回滚，是最后一道防线。但很多人把回滚想得太简单了。

「不就是把旧版本部署回去吗？」

嗯，如果真这么简单，就不会有那么多回滚失败的事故了。

我总结的回滚三要素：

  • 数据回滚：新版本产生的数据怎么处理？是保留还是删除？
  • 状态回滚：AGV当前正在执行的任务怎么处理？
  • 配置回滚：灰度策略、路由规则等配置怎么恢复？

我曾经遇到过一次回滚事故：新版本上线后，AGV的路径规划算法出了问题，导致多台AGV在交叉口死锁。我们紧急回滚到旧版本，但发现旧版本不识别新版本产生的任务数据。结果就是：回滚后，所有AGV都处于「等待任务」状态，产线还是停的。

后来我设计了一套「快照回滚」机制：

// 升级前，自动创建快照
snapshot create --name "pre-upgrade-v2.1.0" \
  --include-data --include-config --include-state

// 回滚时，一键恢复
rollback --snapshot "pre-upgrade-v2.1.0"

快照包含三部分：

  • 数据库全量备份
  • 配置文件备份
  • AGV运行状态快照

这样，回滚时就能恢复到升级前的完整状态，不会出现「数据对不上」的问题。

回滚的黄金法则：

  • 升级前必须做快照
  • 回滚必须在30分钟内完成
  • 回滚后必须做全量功能验证
  • 回滚失败时，要有「回滚的回滚」方案

知识体系总览

下面这张图，是我对版本升级与兼容的整体理解：

版本升级这件事，说白了就是「在保证产线不停的前提下，把新功能安全地部署上去」。接口兼容是基础，数据迁移是保障，灰度升级是手段，回滚机制是底线。四者缺一不可。

我见过太多人只关注新功能开发，忽略了升级策略。结果上线那天，手忙脚乱，最后还得求着运维帮忙回滚。嗯，别做那种人。
