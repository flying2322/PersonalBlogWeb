18 测试策略：单元测试、集成测试、压力测试、混沌工程、模拟器测试

说实话，很多做AGV调度系统的人，都栽在测试这个环节上。

我见过太多项目，代码写完了，功能跑通了，就直接往现场丢。结果呢？上线第一天就出幺蛾子——AGV撞了、任务卡死了、数据库爆了。然后一群人扑上去救火，狼狈不堪。

为什么会这样？因为大家总觉得「测试是测试工程师的事」。但AGV调度系统不一样，它是个实时、分布式、高并发的系统。你想想看，几十台AGV同时在车间里跑，调度算法稍微出点bug，那就是真金白银的损失。

所以这一章，我把自己多年踩坑的经验总结出来。咱们从五个维度来聊：单元测试、集成测试、压力测试、混沌工程、模拟器测试。每个维度我都会讲清楚：为什么要做、怎么做、以及我踩过哪些坑。

18.1 单元测试：守住代码的第一道防线

单元测试，说白了就是测你写的每个函数、每个方法对不对。

我个人习惯，写调度算法的时候，先写测试用例，再写实现代码。这叫测试驱动开发（TDD）。刚开始会觉得别扭，但习惯了之后，你会发现代码质量提升一大截。

核心原则： 每个函数只测一件事，且不依赖外部环境（数据库、网络、文件系统）。

举个例子，我们有个任务分配算法，需要根据AGV的当前位置、电量、任务优先级来打分。我一般会这样写测试：

// 伪代码示例
@Test
public void testTaskScoreCalculation() {
    // 准备数据
    AGV agv = new AGV("AGV-01", 50.0, 80); // 位置50，电量80%
    Task task = new Task("TASK-001", 100, Priority.HIGH);
    
    // 执行
    double score = taskAllocator.calculateScore(agv, task);
    
    // 验证
    Assert.assertTrue(score > 0);
    Assert.assertEquals(85.5, score, 0.1); // 允许0.1的误差
}

我曾经犯过一个低级错误：在单元测试里直接连了数据库。结果测试跑一次要30秒，团队没人愿意跑。后来改成mock数据库，测试时间降到0.1秒，大家才愿意频繁执行。

我的建议： 单元测试覆盖率至少要达到80%以上。重点关注调度算法、路径规划、任务分配这些核心逻辑。像getter/setter这种，测了也没啥意义。

18.2 集成测试：验证模块间的握手

单元测试过了，不代表系统能跑通。模块之间的交互，才是最容易出问题的地方。

集成测试，就是验证各个模块能不能正常「握手」。比如：调度模块和通信模块之间、任务管理模块和AGV状态管理模块之间。

我一般会这样设计集成测试：

  1. 接口契约测试： 确保A模块调用B模块时，参数格式、返回值类型都对得上。
  2. 状态流转测试： 模拟一个任务从创建到完成的全流程，看各个模块的状态更新是否正确。
  3. 异常场景测试： 比如通信模块突然断开，调度模块能不能正确处理。
注意： 集成测试不要覆盖所有分支，否则维护成本太高。我建议只覆盖核心业务流程和关键异常场景。一个项目有20-30个集成测试用例就差不多了。

我记得有一次，集成测试发现了一个隐藏很深的bug：任务完成后，AGV状态更新了，但数据库里的任务记录还是「执行中」。原因是事务提交顺序有问题。这种bug，单元测试根本发现不了，只有集成测试才能抓到。

18.3 压力测试：看看系统能扛多少

压力测试，就是给系统上强度。看看在极限负载下，系统会不会崩。

AGV调度系统的压力测试，我一般关注三个指标：

指标 说明 我的经验值
吞吐量 每秒能处理多少任务 单机至少500 TPS
响应时间 从任务下发到AGV开始执行的时间 P99 < 200ms
资源消耗 CPU、内存、网络带宽 CPU < 70%，内存 < 80%

怎么做压力测试？我推荐用JMeter或者Locust。模拟100台、200台、500台AGV同时请求调度。看看系统什么时候开始变慢，什么时候彻底崩溃。

关键点： 压力测试不是一次性的。每次代码有重大变更，都要重新跑一遍。我见过一个团队，压力测试通过后就再也不跑了，结果三个月后系统上线，性能直接腰斩——因为中间加了个没注意到的死循环。

18.4 混沌工程：故意搞破坏

混沌工程，说白了就是故意给系统制造故障，看看它能不能自己恢复。

这个理念最早是Netflix提出来的。他们搞了个叫Chaos Monkey的工具，在生产环境里随机杀死服务。为什么？因为故障一定会发生，与其被动应对，不如主动演练。

在AGV调度系统里，我常用的混沌实验有：

  • 网络延迟： 在调度服务器和AGV之间增加100ms、500ms的延迟。
  • 服务宕机： 随机停掉一个调度节点，看其他节点能不能接管。
  • 数据库故障： 模拟数据库连接超时，看系统会不会雪崩。
  • 消息队列积压： 突然往消息队列里塞10万条消息，看消费端能不能扛住。

我曾经做过一个实验：在AGV正在执行任务的时候，突然断掉它的网络连接。结果发现，调度系统等了30秒才判定AGV离线，然后才重新分配任务。这30秒的窗口期，现场操作员急得跳脚。后来我们把超时时间改成了5秒，并增加了心跳检测机制。

我的建议： 混沌工程不要一开始就在生产环境搞。先在测试环境跑一个月，确认所有故障场景都有预案了，再逐步推广到生产环境。而且最好在业务低峰期做。

18.5 模拟器测试：低成本验证

模拟器测试，是我个人最推崇的一种测试方式。为什么？因为便宜、快速、可重复。

你想想看，要是在现场测试，你得协调几十台AGV、安排场地、准备物料。一次测试下来，成本少说几万块。而且出了问题，还得等下一轮测试窗口。

模拟器就不一样了。我在电脑上跑一个模拟器，可以同时模拟100台AGV的行为。每台AGV的坐标、速度、电量、任务状态，全部虚拟出来。调度系统根本不知道它连的是真AGV还是模拟器。

模拟器测试能覆盖的场景：

  1. 大规模并发： 模拟200台AGV同时请求任务分配。
  2. 异常行为： 模拟AGV突然离线、电量耗尽、路径阻塞。
  3. 时间加速： 把1小时压缩成1分钟，快速验证长时间运行的稳定性。
  4. 回归测试： 每次代码变更后，自动跑一遍全量场景。
核心思路： 模拟器和真实AGV使用相同的通信协议。这样调度系统不需要做任何修改，就能在模拟器和真实环境之间无缝切换。

我参与的一个项目，就是用模拟器发现了调度算法的一个严重bug：当AGV数量超过50台时，任务分配时间从10ms飙升到2秒。原因是一个循环里用了O(n²)的算法。在模拟器上跑一遍就发现了，要是在现场，估计得折腾好几天。

18.6 五种测试策略的协同

这五种测试策略，不是孤立的。它们应该形成一个完整的测试体系：

从这张图可以看出来：单元测试是地基，成本最低但覆盖最广。越往上，测试成本越高，但能发现的问题也越深。模拟器测试虽然成本高，但能模拟真实场景，价值最大。

我个人习惯的测试流程是：

  1. 开发阶段：写单元测试，保证每个函数正确。
  2. 联调阶段：跑集成测试，验证模块间交互。
  3. 预发布阶段：做压力测试和混沌工程，确保系统能扛住极限。
  4. 持续集成：每次代码提交，自动跑模拟器测试，做全量回归。
避坑指南： 我曾经犯过一个错误——把所有测试都放在上线前集中做。结果发现bug太多，根本改不完。后来改成「小步快跑」模式：每次提交代码，都跑一遍完整的测试流水线。虽然前期慢一点，但后期几乎不用加班救火。

好了，这五种测试策略，说白了就是一套组合拳。单元测试保底，集成测试查漏，压力测试看极限，混沌工程练应急，模拟器测试省成本。把这五招练好了，你的AGV调度系统上线，心里就有底了。
