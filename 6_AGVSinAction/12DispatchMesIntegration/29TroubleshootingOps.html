29 故障排查与运维：常见问题排查手册、日志分析技巧、性能瓶颈定位、应急响应流程

各位同行，做AGV调度系统与MES对接，最怕什么？

怕半夜电话响。怕系统突然卡住，AGV全停在巷道里。怕MES那边催着要数据，调度系统却报了一堆看不懂的错误码。

说实话，我干这行十几年，踩过的坑比走过的路还多。今天这篇，我就把压箱底的排查经验掏出来，跟大伙儿聊聊。

一、常见问题排查手册：先别慌，按套路来

遇到故障，我个人的习惯是——先看现象，再查日志，最后动配置。千万别一上来就重启服务，那是野路子。

核心原则： 先恢复生产，再定位根因。如果AGV堵在路上，优先手动释放车辆，别急着分析代码。

1.1 连接类故障

MES连不上调度系统，这是最常见的。我遇到过一家客户，IT说网络没问题，结果我一查，防火墙把8080端口给封了。

  • 现象： MES报“连接超时”或“服务不可用”
  • 排查步骤：
    1. 先ping一下调度服务器的IP，看网络通不通
    2. 再用telnet测试端口，比如 telnet 192.168.1.100 8080
    3. 检查调度系统的服务状态，是不是挂了
    4. 看MES的配置文件，IP和端口有没有写错
小技巧： 我习惯在调度系统里加一个健康检查接口，比如 /health，MES那边定时调用。如果连续3次失败，自动告警。这招帮我提前发现过好几次网络抖动问题。

1.2 数据交互类故障

MES下发任务了，AGV没反应。或者AGV上报了位置，MES那边没收到。

  • 现象： 任务状态卡在“已下发”或“执行中”，就是不更新
  • 排查步骤：
    1. 检查消息队列（比如RabbitMQ或Kafka）有没有积压
    2. 看调度系统的日志，有没有收到MES的请求
    3. 检查数据格式，是不是JSON字段名对不上
    4. 确认AGV的通信模块是否在线
注意： 我曾经遇到一个坑，MES那边把任务ID字段名从“taskId”改成了“task_id”，调度系统没同步更新，结果所有任务都解析失败。所以，接口文档一定要版本控制，变更前双方确认。

二、日志分析技巧：别大海捞针，要精准定位

日志是排查问题的第一手资料。但很多新手一打开日志文件就懵了，几万行数据，看哪条？

我的方法是——先定时间，再定级别，最后定关键字。

2.1 日志分级与过滤

调度系统的日志一般分几个级别：DEBUG、INFO、WARN、ERROR。生产环境建议只开INFO及以上，否则日志量太大，磁盘撑不住。

级别 含义 排查时关注点
ERROR 系统异常，需要立即处理 优先看，通常伴随堆栈信息
WARN 潜在风险，不影响当前运行 记录一下，后续分析
INFO 正常业务流程记录 用于追踪任务流转
DEBUG 调试信息，非常详细 只在开发环境或临时开启

2.2 常用日志分析命令

如果你在Linux服务器上，这几个命令一定要熟：

# 查看最近100行日志
tail -n 100 scheduler.log

# 实时跟踪日志输出
tail -f scheduler.log

# 查找包含"ERROR"的行，并显示前后5行
grep -n "ERROR" scheduler.log | head -20

# 统计某个时间段内的错误次数
grep "2025-01-15 14:" scheduler.log | grep "ERROR" | wc -l

# 提取关键字段，比如任务ID
grep -oP 'taskId["\s]*:["\s]*"\K[^"]+' scheduler.log | sort | uniq -c | sort -nr
个人经验： 我习惯在日志里加上“请求ID”或“追踪ID”。每次MES调用接口，调度系统生成一个唯一ID，贯穿整个任务生命周期。这样排查时，只要grep这个ID，就能把整个流程串起来，特别方便。

三、性能瓶颈定位：别瞎猜，用数据说话

系统变慢了，是网络问题？数据库问题？还是调度算法本身的问题？

说白了，性能瓶颈定位就是——找到那个最慢的环节。

3.1 常见性能瓶颈点

  • 数据库查询慢： 任务表数据量大了，没加索引，查询耗时飙升
  • 消息队列积压： 生产者太快，消费者处理不过来
  • AGV通信延迟： 无线网络信号差，指令下发超时
  • 调度算法计算量大： 路径规划时，地图节点太多，计算耗时过长

3.2 定位方法

我一般用“分段计时法”。在关键代码前后打上时间戳，看哪一段耗时最长。

// 伪代码示例
long start = System.currentTimeMillis();
// 1. 接收MES任务
receiveTaskFromMES();
long t1 = System.currentTimeMillis();
log.info("接收任务耗时：{}ms", t1 - start);

// 2. 路径规划
planPath();
long t2 = System.currentTimeMillis();
log.info("路径规划耗时：{}ms", t2 - t1);

// 3. 下发指令给AGV
sendCommandToAGV();
long t3 = System.currentTimeMillis();
log.info("下发指令耗时：{}ms", t3 - t2);

如果发现路径规划耗时特别长，那就得优化算法了。比如，我遇到过地图上有2000个节点，每次规划都遍历所有节点，后来改成只计算当前区域附近的节点，性能提升了10倍。

避坑指南： 我曾经遇到一个性能问题，排查了半天，最后发现是日志打印太多，把CPU吃满了。所以，生产环境千万别开DEBUG日志，否则系统性能直接腰斩。

四、应急响应流程：有预案，不慌张

故障发生了，怎么处理？我建议每个团队都制定一个应急响应流程，并且定期演练。

4.1 应急响应步骤

  1. 发现与告警： 系统自动检测到异常（比如AGV离线超过30秒），通过短信或钉钉通知运维人员
  2. 评估与分级： 判断故障等级。P0级（系统瘫痪）需要立即响应，P1级（部分功能异常）可以稍后处理
  3. 隔离与恢复： 先让系统恢复运行。比如，手动将AGV切换到手动模式，或者重启调度服务
  4. 根因分析： 故障恢复后，再慢慢查原因。查日志、查监控、查配置变更记录
  5. 复盘与改进： 写故障报告，更新排查手册，避免同类问题再次发生

4.3 应急工具包

我建议每个运维人员都准备一个“应急工具包”，里面包含：

  • 调度系统的管理员账号和密码（加密存储）
  • 数据库的备份文件和恢复脚本
  • AGV的手动控制操作手册
  • MES对接接口的测试工具（比如Postman的测试集合）
  • 常见故障的排查清单（打印出来，贴在工位上）
最后说一句： 故障不可怕，可怕的是没有预案。我见过太多团队，出了事才临时抱佛脚，结果越搞越乱。所以，平时多演练，关键时刻才能稳得住。
