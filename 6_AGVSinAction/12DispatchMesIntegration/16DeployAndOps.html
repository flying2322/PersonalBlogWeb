16 系统部署与运维：Docker容器化部署、Kubernetes编排、CI/CD流水线、灰度发布策略

各位同行，今天我们来聊聊AGV调度系统真正上线后的那些事。说实话，很多项目在开发阶段跑得挺好，一到部署运维就翻车。我见过太多因为环境不一致导致的“在我机器上能跑”的尴尬局面。

所以这一章，我重点讲四个核心话题：Docker容器化、Kubernetes编排、CI/CD流水线、灰度发布策略。这些都是我踩过坑之后，觉得必须分享给你的实战经验。

为什么必须容器化？

AGV调度系统依赖的东西太多了。数据库、消息队列、地图服务、算法模块……每个组件都有各自的版本要求。你想想看，如果每个现场都手动部署一遍，不出错才怪。

我个人习惯，从项目第一天就用Docker。把调度系统、地图服务、甚至数据库都打包成镜像。这样不管部署到哪个现场，环境都是一模一样的。

核心原则：一次构建，到处运行。别让环境差异成为你的噩梦。

Dockerfile 怎么写才专业？

我见过很多人的Dockerfile写得像流水账。其实有讲究。给你看一个我常用的模板：

# 多阶段构建，减小镜像体积
FROM mcr.microsoft.com/dotnet/sdk:6.0 AS build
WORKDIR /app
COPY . .
RUN dotnet publish -c Release -o out

FROM mcr.microsoft.com/dotnet/aspnet:6.0 AS runtime
WORKDIR /app
COPY --from=build /app/out .
EXPOSE 5000
ENTRYPOINT ["dotnet", "AGVScheduler.dll"]

这里有个坑：基础镜像别用太大的。我曾经用了一个带完整SDK的镜像，结果镜像体积2个多G，传到现场慢得要死。后来改用runtime镜像，体积直接降到200M。

我的经验：多阶段构建是标配。第一阶段编译，第二阶段只放运行环境。这样镜像又小又安全。

Kubernetes 编排：让调度系统自动恢复

AGV调度系统不能停。一旦调度服务挂了，整个车队的任务就乱了。Kubernetes的自动恢复机制，说白了就是给你的系统上了双保险。

我建议你至少配置这些资源：

  • Deployment：管理调度服务的副本数，保证最少2个实例
  • Service：提供稳定的访问入口，AGV小车通过这个地址连接
  • ConfigMap：存放配置参数，比如数据库连接串、MQTT地址
  • PersistentVolume：持久化日志和地图数据

给你看一个简单的Deployment配置：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: agv-scheduler
spec:
  replicas: 2
  selector:
    matchLabels:
      app: agv-scheduler
  template:
    metadata:
      labels:
        app: agv-scheduler
    spec:
      containers:
      - name: scheduler
        image: registry.agv.com/scheduler:v2.1
        ports:
        - containerPort: 5000
        livenessProbe:
          httpGet:
            path: /health
            port: 5000
          initialDelaySeconds: 30
          periodSeconds: 10

嗯，这里要注意：一定要加健康检查。我遇到过调度服务进程还在，但内部线程池已经卡死的情况。没有健康检查，K8s不会自动重启，AGV小车就会一直等响应。

CI/CD 流水线：从代码到上线自动化

以前我部署一次要半小时：编译、打包、上传、登录服务器、停服务、替换文件、重启……现在用GitLab CI + Jenkins，提交代码后自动完成所有步骤。

我的流水线一般分三个阶段：

  1. 构建阶段：代码检查、单元测试、编译打包
  2. 镜像阶段：构建Docker镜像，推送到私有仓库
  3. 部署阶段：更新K8s的Deployment，触发滚动更新

避坑指南：我曾经把测试环境的数据库连接串写死在代码里，结果CI构建时自动跑了测试，把测试库的表给清了。后来我强制要求：所有敏感信息必须通过环境变量注入，代码里只留占位符。

灰度发布：如何安全升级调度系统？

AGV调度系统升级最怕什么？怕新版本有bug，导致整个车队瘫痪。灰度发布就是让你先让一小部分AGV用新版本，观察没问题再全量切换。

在K8s里实现灰度发布，我常用两种方式：

方式 原理 适用场景
蓝绿部署 同时运行两套环境，切换流量 版本差异大，需要快速回滚
金丝雀发布 新版本只接收少量流量 逐步验证，风险可控

我个人更推荐金丝雀发布。举个例子：

# 先部署1个新版本实例
kubectl set image deployment/agv-scheduler scheduler=registry.agv.com/scheduler:v2.2
kubectl scale deployment agv-scheduler --replicas=3

# 观察10分钟，确认没问题
# 再逐步增加新版本实例，减少旧版本
kubectl set image deployment/agv-scheduler scheduler=registry.agv.com/scheduler:v2.2
kubectl scale deployment agv-scheduler --replicas=5

重要提醒：灰度发布期间，一定要监控AGV的任务完成率。如果发现异常，立即执行回滚命令：kubectl rollout undo deployment/agv-scheduler。别犹豫，我曾经犹豫了3分钟，结果20台AGV全部卡在路口。
