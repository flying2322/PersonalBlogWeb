26 二次开发与扩展：插件化架构设计、自定义任务类型、自定义报表、自定义告警规则

各位做MES-AGV集成的朋友，大家好。这一章我们聊点“硬核”的——二次开发与扩展。

说实话，我做了这么多年系统集成，最怕听到的一句话就是：“这个功能标准产品不支持，你们改代码吧。” 改代码一时爽，维护火葬场。所以，一个优秀的AGV调度系统，必须预留好扩展接口。今天我就把我在几个大型项目中积累的插件化设计经验，掰开揉碎了讲给你听。

26.1 为什么需要插件化架构？

先问大家一个问题：你见过那种“大泥球”式的调度系统吗？所有逻辑揉在一起，加一个自定义任务类型，要改十几个文件。我见过，而且我接手过。

插件化架构，说白了就是把系统核心和扩展功能解耦。核心负责调度引擎、路径规划、交通管制这些“硬骨头”。而像自定义任务、报表、告警这些，都做成插件。插上去就能用，拔下来也不影响核心。

这样做的好处很明显：

  • 隔离性：插件出问题，不会拖垮整个调度系统
  • 可维护性：升级插件不用停系统，热插拔
  • 团队协作：不同团队可以并行开发不同插件

核心观点：插件化不是“炫技”，而是为了应对工厂现场“千奇百怪”的需求。你想想看，每个客户的MES接口都不一样，每个车间的AGV任务逻辑都有差异。没有插件化，你就是在给自己挖坑。

26.2 自定义任务类型：让AGV听懂你的“方言”

标准AGV调度系统，通常只支持“从A点搬到B点”这种基础任务。但实际现场呢？我遇到过客户要求“AGV先到质检台，如果合格再送到仓库，不合格送到返修区”。这种带条件判断的任务，标准系统根本搞不定。

26.2.1 任务类型插件接口设计

我的做法是定义一个抽象的任务接口。所有自定义任务类型，都实现这个接口。核心调度引擎只认接口，不认具体实现。

// 任务接口定义
public interface ICustomTask
{
    string TaskTypeId { get; }          // 任务类型唯一标识
    string Description { get; }         // 任务描述
    
    // 任务执行前的校验
    Task<bool> ValidateAsync(TaskContext context);
    
    // 任务执行逻辑
    Task<TaskResult> ExecuteAsync(TaskContext context);
    
    // 任务状态变更回调
    Task OnStatusChangedAsync(TaskStatus oldStatus, TaskStatus newStatus);
}

嗯，这里要注意一点：ValidateAsync 和 ExecuteAsync 必须分开。为什么？我在一个项目里吃过亏——把校验逻辑写在执行里，结果任务跑到一半才发现条件不满足，AGV卡在半路上，进退两难。

26.2.2 实战：实现一个“质检分流任务”

我给大家看一个实际案例。这个任务类型，AGV接到指令后，先去质检台，然后根据质检结果决定下一步。

public class QualityInspectionTask : ICustomTask
{
    public string TaskTypeId => "QUALITY_INSPECTION";
    public string Description => "质检分流任务：先到质检台，根据结果分流";
    
    public async Task<bool> ValidateAsync(TaskContext context)
    {
        // 检查质检台是否空闲
        var qcStation = context.GetStation("QC01");
        if (qcStation == null || qcStation.IsBusy)
        {
            return false;  // 质检台忙，不执行
        }
        return true;
    }
    
    public async Task<TaskResult> ExecuteAsync(TaskContext context)
    {
        // 第一步：导航到质检台
        await context.NavigateTo("QC01");
        
        // 第二步：等待质检结果（通过MES接口获取）
        var result = await context.WaitForExternalSignal("QC_RESULT", timeout: 300);
        
        // 第三步：根据结果分流
        if (result == "PASS")
        {
            await context.NavigateTo("WH01");  // 送到仓库
        }
        else
        {
            await context.NavigateTo("REWORK"); // 送到返修区
        }
        
        return TaskResult.Success;
    }
    
    public Task OnStatusChangedAsync(TaskStatus oldStatus, TaskStatus newStatus)
    {
        // 记录日志，或者通知MES
        Console.WriteLine($"任务状态变更: {oldStatus} -> {newStatus}");
        return Task.CompletedTask;
    }
}

避坑指南：我曾经在 WaitForExternalSignal 里忘记设置超时，结果MES那边网络断了，AGV在质检台前傻等了两个小时。记住，所有外部等待都要加超时，超时后要有兜底逻辑。

26.3 自定义报表：数据要“看得见”

MES那边天天要报表：AGV利用率、任务完成率、平均等待时间...标准报表往往不够用。客户会说：“我要看每个工位在8:00-10:00这个时段，AGV来了多少次，平均等待多久。”

这种需求，写死代码？太傻了。我习惯用报表插件+模板引擎的方式。

26.3.1 报表插件接口

public interface IReportPlugin
{
    string ReportId { get; }
    string ReportName { get; }
    
    // 报表数据源
    Task<DataSet> GetDataAsync(ReportFilter filter);
    
    // 报表模板（HTML/Excel）
    string GetTemplate();
    
    // 报表导出格式
    List<string> SupportedFormats { get; }  // ["HTML", "Excel", "PDF"]
}

我个人习惯用 Razor模板引擎 来生成HTML报表。为什么？因为HTML可以直接嵌入图表，用ECharts或者Chart.js画出来，客户看了直呼专业。

26.3.2 一个简单的报表插件示例

public class AGVUtilizationReport : IReportPlugin
{
    public string ReportId => "AGV_UTILIZATION";
    public string ReportName => "AGV利用率报表";
    
    public async Task<DataSet> GetDataAsync(ReportFilter filter)
    {
        // 从数据库查询AGV运行数据
        var sql = @"
            SELECT agv_id, 
                   SUM(working_time) as working_time,
                   SUM(idle_time) as idle_time,
                   SUM(charging_time) as charging_time
            FROM agv_status_log
            WHERE timestamp BETWEEN @start AND @end
            GROUP BY agv_id";
        
        return await DbHelper.QueryAsync(sql, filter);
    }
    
    public string GetTemplate()
    {
        return @"
<h2>AGV利用率报表</h2>
<table border='1'>
    <tr><th>AGV编号</th><th>工作时间</th><th>空闲时间</th><th>充电时间</th><th>利用率</th></tr>
    @foreach(var row in Model.Tables[0].Rows)
    {
        var utilization = row.working_time / (row.working_time + row.idle_time) * 100;
        <tr>
            <td>@row.agv_id</td>
            <td>@row.working_time 分钟</td>
            <td>@row.idle_time 分钟</td>
            <td>@row.charging_time 分钟</td>
            <td>@utilization.ToString(""F2"")%</td>
        </tr>
    }
</table>";
    }
    
    public List<string> SupportedFormats => new List<string> { "HTML", "Excel" };
}

关键点：报表插件的数据源和模板是分离的。这样，即使MES那边的数据库结构变了，你只需要改 GetDataAsync 方法，模板不用动。反之亦然。

26.4 自定义告警规则：别让AGV“带病工作”

AGV调度系统里，告警规则是最容易“众口难调”的。有的客户觉得AGV电量低于30%就要告警，有的觉得20%才告警。还有的客户要求“如果AGV在同一个位置停留超过5分钟，就发告警”。

标准系统通常只提供几个固定的告警类型。怎么办？用规则引擎插件。

26.4.1 告警规则插件接口

public interface IAlertRule
{
    string RuleId { get; }
    string RuleName { get; }
    int Priority { get; }  // 优先级，数值越小越优先
    
    // 评估规则是否触发
    Task<AlertResult> EvaluateAsync(AlertContext context);
    
    // 告警动作（邮件、短信、Webhook等）
    Task ExecuteActionAsync(AlertResult result);
}

26.4.2 实战：实现“AGV长时间停留告警”

public class LongStayAlertRule : IAlertRule
{
    public string RuleId => "LONG_STAY";
    public string RuleName => "AGV长时间停留告警";
    public int Priority => 5;
    
    public async Task<AlertResult> EvaluateAsync(AlertContext context)
    {
        // 获取所有AGV的当前位置和停留时间
        var agvs = context.GetAllAGVs();
        var alerts = new List<AlertItem>();
        
        foreach (var agv in agvs)
        {
            if (agv.Status == AGVStatus.Idle && 
                agv.StayDuration.TotalMinutes > 5)
            {
                alerts.Add(new AlertItem
                {
                    AGVId = agv.Id,
                    Level = AlertLevel.Warning,
                    Message = $"AGV {agv.Id} 在 {agv.CurrentStation} 停留超过5分钟",
                    Timestamp = DateTime.Now
                });
            }
        }
        
        return new AlertResult { Items = alerts };
    }
    
    public async Task ExecuteActionAsync(AlertResult result)
    {
        foreach (var item in result.Items)
        {
            // 发送邮件告警
            await EmailService.SendAsync(
                to: "operator@factory.com",
                subject: "AGV长时间停留告警",
                body: item.Message
            );
            
            // 同时写入告警日志
            await AlertLogger.WriteAsync(item);
        }
    }
}

注意：告警规则不要写得太“敏感”。我曾经遇到一个客户，把停留告警时间设为30秒，结果AGV在路口等交通管制，30秒很正常，结果告警邮件把运维人员的邮箱塞爆了。建议默认值设为5分钟以上，并且支持动态调整。

26.5 插件热加载与配置管理

插件做出来了，怎么部署？总不能每次加个插件就重启调度系统吧？

我推荐用 MEF（Managed Extensibility Framework） 或者 MAF（Managed Add-in Framework）。这两个都是.NET平台下的插件框架，支持热加载。

26.5.1 插件配置示例

// 插件配置文件 (plugin.config)
{
  "plugins": [
    {
      "id": "QUALITY_INSPECTION",
      "type": "task",
      "assembly": "Plugins.QualityInspection.dll",
      "enabled": true,
      "config": {
        "qcStationId": "QC01",
        "timeoutSeconds": 300
      }
    },
    {
      "id": "LONG_STAY",
      "type": "alert",
      "assembly": "Plugins.LongStayAlert.dll",
      "enabled": true,
      "config": {
        "stayThresholdMinutes": 5,
        "emailRecipients": ["operator@factory.com"]
      }
    }
  ]
}

核心调度引擎启动时，扫描这个配置文件，加载所有 enabled: true 的插件。如果某个插件崩溃了，引擎会自动把它标记为 disabled，并继续运行其他插件。这就是隔离性的好处。

26.6 总结

好了，这一章的内容就这些。插件化架构设计，说白了就是“预留接口，开放扩展”。自定义任务类型让你能应对千奇百怪的搬运逻辑；自定义报表让数据展示随心所欲；自定义告警规则让系统更“懂”你的现场。

记住一句话：好的架构，不是把所有功能都做出来，而是让其他人能轻松地做出你想要的功能。

最后送大家一个经验：做插件化设计时，接口定义一定要“稳”。接口一旦发布，就不要轻易修改。因为你的插件可能来自不同的团队、不同的供应商。接口变了，所有插件都得跟着改，那就失去了插件化的意义。
