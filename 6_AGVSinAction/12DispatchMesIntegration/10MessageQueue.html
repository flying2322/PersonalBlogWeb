10 消息队列集成：RabbitMQ/Kafka在AGV-MES中的应用

消息队列这东西，说白了就是系统之间的「快递员」。AGV调度系统和MES之间要传的数据量不小，而且实时性要求高。你想想看，MES下发一个搬运任务，如果直接走HTTP接口，万一网络抖一下，任务丢了怎么办？AGV报了个状态变更，MES没收到，整个生产节拍就乱了。

我在好几个项目里都吃过这个亏。早期有个项目，AGV和MES直接走Socket长连接，看起来挺美。结果MES那边一升级重启，连接全断了，AGV还在那傻等指令。从那以后，我所有的集成方案都强制上消息队列。

核心观点：消息队列不是可选项，是AGV-MES集成的标配。它解决了三个核心问题：解耦、削峰、异步。

10.1 RabbitMQ vs Kafka：怎么选？

先别急着选技术，先看场景。我个人习惯这样区分：

对比维度 RabbitMQ Kafka
消息模型 队列/交换机 Topic/分区
吞吐量 万级/秒 百万级/秒
消息顺序 单队列有序 分区内有序
消息持久化 支持（需配置） 天生持久化
典型场景 任务指令、状态变更 日志采集、轨迹回放

我的建议是：AGV任务调度用RabbitMQ，数据采集用Kafka。为什么？AGV的任务指令和状态变更，每条消息都很重要，不能丢，而且需要灵活的路由。RabbitMQ的交换机模型正好干这个。而AGV的运行轨迹、电量日志这些海量数据，用Kafka的吞吐能力更合适。

实战经验：我在一个汽车零部件工厂的项目里，AGV数量超过80台，每秒状态变更消息接近2000条。RabbitMQ扛得住，但需要做集群和镜像队列。如果超过这个量级，建议上Kafka。

10.2 消息持久化：别让数据睡在内存里

嗯，这里要注意。消息队列默认不一定持久化。RabbitMQ的消息默认是存在内存里的，一重启就没了。Kafka好一点，但也要配置确认机制。

我曾经遇到过一个坑：客户现场突然断电，RabbitMQ重启后，MES下发的50个搬运任务全部丢失。AGV系统里任务列表是空的，但AGV还在路上跑。那叫一个乱。

正确的做法：

  • RabbitMQ：声明队列时设置 durable=true，发送消息时设置 delivery_mode=2（持久化）
  • Kafka：设置 acks=all，确保所有副本都写入成功才返回
// RabbitMQ 生产者示例（Java）
channel.queueDeclare("agv.task.queue", true, false, false, null);
AMQP.BasicProperties props = new AMQP.BasicProperties.Builder()
    .deliveryMode(2)  // 持久化
    .build();
channel.basicPublish("", "agv.task.queue", props, messageBody);
// Kafka 生产者配置
Properties props = new Properties();
props.put("acks", "all");
props.put("retries", 3);
props.put("enable.idempotence", true);  // 幂等性，防止重复

注意：持久化不是万能的。RabbitMQ的持久化消息是先写磁盘再确认，性能会下降30%左右。如果对性能敏感，可以设置 lazy queue 模式，消息直接写磁盘，但读取慢一些。看你的场景取舍。

10.3 消息去重：同一个任务别执行两次

AGV系统最怕什么？同一个搬运任务被重复执行。AGV跑到一半，又收到一个一模一样的任务，它可能就懵了。

消息重复的原因很多：生产者重试、网络闪断、消费者确认超时。说白了，分布式系统里「至少一次」是常态，「恰好一次」需要额外努力。

我的去重方案分三层：

  1. 生产者幂等：每条消息带唯一ID（UUID或业务流水号）
  2. 消息队列去重：Kafka开启幂等性（enable.idempotence=true），RabbitMQ没有原生去重，需要消费者自己处理
  3. 消费者去重：用Redis或数据库记录已处理的消息ID
// 消费者去重逻辑（伪代码）
public void handleTask(String messageId, Task task) {
    // 1. 检查Redis中是否已处理
    if (redisClient.exists("processed:" + messageId)) {
        log.info("消息已处理，跳过: {}", messageId);
        return;
    }
    
    // 2. 执行业务逻辑
    agvDispatcher.dispatch(task);
    
    // 3. 标记已处理（设置过期时间，比如24小时）
    redisClient.setex("processed:" + messageId, 86400, "1");
}

避坑指南：我曾经在去重逻辑上犯过一个低级错误——用数据库的唯一索引去重。结果高并发下，多条相同消息同时插入，数据库报唯一约束冲突，事务回滚，任务反而没执行。后来改成Redis的SETNX原子操作，才彻底解决。

10.4 消息顺序保证：AGV的路径不能乱

AGV调度最讲究顺序。比如：

  • 先发「移动到A点」指令
  • 再发「装载货物」指令
  • 最后发「移动到B点」指令

如果顺序乱了，AGV可能还没到A点就收到了装载指令，直接报错。

消息队列的顺序保证是个老大难问题。Kafka只能在分区内保证顺序，RabbitMQ只能在单队列内保证顺序。一旦涉及多个消费者或者网络延迟，顺序就可能乱。

我的做法：

  • 按AGV ID分区：同一台AGV的消息发到同一个分区/队列
  • 单消费者：每个AGV的消息只由一个消费者线程处理
  • 业务层排序：消息里带时间戳和序列号，消费者收到后先排序再执行
// Kafka 按AGV ID分区
ProducerRecord<String, String> record = 
    new ProducerRecord<>("agv.command", agvId, messageJson);
// 同一个agvId会进入同一个分区，保证顺序

注意：不要依赖消息队列的「全局顺序」。分布式系统里，全局顺序几乎不可能做到，而且会严重牺牲性能。按业务维度（比如AGV ID）分区，保证局部顺序，这才是工程上可行的方案。

10.6 总结一下

消息队列集成这块，说白了就是三个要点：

  • 选型：任务调度用RabbitMQ，数据采集用Kafka
  • 可靠性：持久化+确认机制，别让消息睡在内存里
  • 一致性：去重+顺序保证，用业务ID和分区策略解决

我在项目里见过太多人把消息队列当成「黑盒」，出了问题就甩锅给中间件。其实大部分问题都是配置不当或者业务逻辑没处理好。记住一句话：消息队列只是工具，真正的可靠性在业务代码里。
