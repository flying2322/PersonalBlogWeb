4 数据模型定义：任务订单模型、AGV状态模型、位置坐标模型、异常事件模型

数据模型这东西，说白了就是MES和AGV调度系统之间的“共同语言”。

我刚开始做集成那会儿，吃过不少亏。有一次两个系统联调，MES发过来的任务单里缺了优先级字段，AGV这边直接按默认顺序跑，结果紧急订单被堵在仓库里半小时。嗯，从那以后，我对数据模型的定义就特别较真。

4.1 任务订单模型：调度的“灵魂”

任务订单是MES发给AGV的指令。我个人习惯，把它拆成三块：任务头、任务行、任务状态。

核心原则：任务订单必须包含“谁、去哪、运什么、多紧急”这四个要素。少一个，调度系统就得猜，一猜就容易出乱子。

先看一个我常用的任务订单模型结构：

{
  "taskId": "TASK20240115001",        // 任务唯一ID
  "taskType": "TRANSPORT",            // 任务类型：搬运/充电/待命
  "priority": 1,                      // 优先级：0-紧急，1-高，2-普通
  "sourcePoint": "WH-01-A",           // 起点：仓库A区01货架
  "targetPoint": "PL-03-B",           // 终点：产线3号工位B点
  "materialCode": "MAT-88012",        // 物料编码
  "materialQty": 10,                  // 数量
  "deadline": "2024-01-15 14:30:00",  // 最晚完成时间
  "createTime": "2024-01-15 14:00:00" // 创建时间
}

这里有个坑，我提醒一下：起点和终点的编码规则，MES和AGV系统必须提前对齐。我曾经遇到一个项目，MES用“WH-01”表示仓库1区，AGV系统里却叫“WH01”，结果任务发过去，AGV直接报“位置不存在”。

我的经验：建议在MES和AGV之间加一个“位置映射表”。MES发过来的位置编码，先查表转成AGV内部编码。这样两边各改各的，互不影响。

4.2 AGV状态模型：调度决策的“眼睛”

AGV状态模型，说白了就是告诉调度系统：你现在有几辆车？每辆车在干嘛？能不能接新活？

我一般把AGV状态分成两大类：运行状态和任务状态。

状态类别 状态值 说明
运行状态 IDLE 空闲，可接任务
MOVING 正在行驶
LOADING 正在装货/卸货
CHARGING 充电中
任务状态 ASSIGNED 已分配任务，前往起点
EXECUTING 正在执行任务（已取货）
COMPLETED 任务完成，等待新指令

你想想看，如果AGV的状态更新不及时，调度系统就会做出错误决策。我记得有个项目，AGV明明在充电，但状态还卡在“空闲”，调度系统又给它派了个任务，结果车动不了，整条产线都等着。

避坑指南：我曾经要求AGV每500毫秒上报一次状态。别小看这个频率，太低了调度会滞后，太高了网络扛不住。500ms是我试出来的平衡点。

4.3 位置坐标模型：导航的“地图”

位置坐标模型，就是AGV的“导航地图”。我习惯用节点-路径的方式建模。

每个位置点，我定义为：

{
  "pointId": "P-001",          // 位置点ID
  "x": 12.5,                   // X坐标（米）
  "y": 8.3,                    // Y坐标（米）
  "angle": 90,                 // 朝向角度（度）
  "type": "STATION",           // 类型：STATION/CHARGER/WAIT_POINT
  "allowedActions": ["LOAD", "UNLOAD"]  // 允许的操作
}

路径的话，我一般用邻接表存：

{
  "pathId": "PATH-01",
  "fromPoint": "P-001",
  "toPoint": "P-002",
  "length": 15.2,              // 路径长度（米）
  "direction": "BIDIRECTIONAL", // 单向/双向
  "speedLimit": 1.0            // 限速（米/秒）
}

为什么会这样设计？因为实际项目中，AGV不是所有位置都能停、都能转弯。有些点只能卸货不能装货，有些点只能直行不能转弯。把这些信息写进模型，调度系统才能做出合理的路径规划。

我的习惯：坐标模型里一定要预留一个“扩展字段”。因为项目后期，客户往往会加新需求，比如“这个位置要加个RFID读取点”。有扩展字段，就不用改数据库结构了。

4.4 异常事件模型：系统的“保险丝”

异常事件模型，说白了就是当系统出问题时，怎么告诉MES“我出事了”。

我见过太多项目，AGV撞了、迷路了、没电了，MES那边完全不知道，还在傻等任务完成。所以，异常事件模型必须定义清楚。

我常用的异常事件结构：

{
  "eventId": "EVT-20240115-001",
  "eventType": "OBSTACLE",       // 类型：OBSTACLE/LOW_BATTERY/COMM_LOST
  "severity": "HIGH",            // 严重级别：LOW/MEDIUM/HIGH/CRITICAL
  "agvId": "AGV-03",            // 发生异常的AGV
  "location": "P-015",          // 异常发生位置
  "timestamp": "2024-01-15 14:35:22",
  "description": "AGV-03在P-015处检测到障碍物，已停止",
  "suggestedAction": "MANUAL_INTERVENTION"  // 建议处理方式
}

这里有个关键点：异常事件必须包含“建议处理方式”。MES收到异常后，可以根据这个字段决定是自动重试、切换AGV，还是通知人工介入。

我曾经踩过的坑：一开始我只定义了异常类型，没定义严重级别。结果有一次AGV电量低（其实还能跑10分钟），MES那边直接停了整条产线。后来我加了严重级别，电量低只算“MEDIUM”，系统会先尝试调度它去充电，而不是直接停线。

这四个模型不是孤立的。我画了张图，帮你理清它们之间的关系：

从这张图你能看出来：MES下发任务订单，调度系统根据AGV状态和位置坐标来分配任务，一旦出问题，异常事件模型就负责“喊救命”。四个模型环环相扣，缺一个都不行。

总结一下：任务订单模型是“要做什么”，AGV状态模型是“谁能做”，位置坐标模型是“在哪做”，异常事件模型是“做砸了怎么办”。把这四个模型定义清楚，MES和AGV的对接就成功了一半。
