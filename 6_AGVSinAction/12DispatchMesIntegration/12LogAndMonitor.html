12 日志与监控：ELK日志收集、Prometheus+Grafana监控、告警规则配置、日志级别管理

调度系统跑起来之后，最怕什么？

怕半夜三点手机响了，AGV堵成一锅粥，你却不知道原因。

怕MES那边说“订单没下发成功”，你翻遍日志找不到线索。

怕磁盘写满了，系统挂了，你还在睡大觉。

这些我都经历过。所以今天这章，咱们聊聊怎么把日志和监控搞扎实。说白了，就是给系统装上“黑匣子”和“仪表盘”。

12.1 日志体系：从分散到集中

AGV调度系统一跑起来，少则三五台车，多则上百台。每台车的日志、调度引擎的日志、MES接口的日志……全散落在不同机器上。你想想看，出问题的时候，难道要一台台登录上去翻文件？

我个人习惯，从一开始就上ELK。Elasticsearch存日志，Logstash收日志，Kibana看日志。这套组合拳打下来，日志管理基本就稳了。

12.1.1 日志采集架构

我建议用Filebeat代替Logstash做采集端。为什么？Filebeat轻量，不占资源。Logstash太重，放在AGV工控机上不合适。

# filebeat.yml 配置示例
filebeat.inputs:
- type: log
  enabled: true
  paths:
    - /var/log/agv_scheduler/*.log
  fields:
    service: agv_scheduler
    env: production

output.logstash:
  hosts: ["192.168.1.100:5044"]

Logstash这边，我习惯做一层解析。把原始日志里的时间戳、日志级别、线程名、类名、消息体拆成结构化字段。这样在Kibana里就能直接按级别筛选、按时间排序。

# logstash.conf 解析规则
filter {
  grok {
    match => { "message" => "%{TIMESTAMP_ISO8601:timestamp} %{LOGLEVEL:level} \[%{DATA:thread}\] %{DATA:class} - %{GREEDYDATA:message}" }
  }
  date {
    match => [ "timestamp", "ISO8601" ]
  }
}
我的经验：日志格式一定要统一。我见过最头疼的项目，每个模块的日志格式都不一样，解析规则写了十几条。后来我强制要求所有模块用同一套格式，省心多了。

12.2 监控体系：Prometheus + Grafana

日志是事后分析，监控是实时预警。这两者缺一不可。

Prometheus负责拉取指标，Grafana负责展示。AGV调度系统里，我主要监控这几类指标：

  • 系统级：CPU、内存、磁盘、网络
  • 应用级：任务队列长度、AGV在线数、任务完成率
  • 业务级：MES接口响应时间、订单积压量

12.2.1 指标暴露与采集

在调度系统里，我用Spring Boot Actuator + Micrometer暴露指标。自定义一些业务指标，比如当前等待任务数、AGV状态分布。

// Java代码：自定义指标
@Bean
public MeterRegistryCustomizer<MeterRegistry> metricsCommonTags() {
    return registry -> registry.config().commonTags("application", "agv-scheduler");
}

// 记录AGV在线数量
Gauge.builder("agv.online.count", agvService, AgvService::getOnlineCount)
     .description("当前在线AGV数量")
     .register(meterRegistry);

Prometheus配置里，我设置每15秒拉一次。这个频率够用，也不会给系统太大压力。

# prometheus.yml
scrape_configs:
  - job_name: 'agv-scheduler'
    scrape_interval: 15s
    metrics_path: '/actuator/prometheus'
    static_configs:
      - targets: ['192.168.1.10:8080']

12.2.2 Grafana看板设计

Grafana的看板，我一般分三层：

  1. 总览层：一眼看到系统整体健康状态。AGV在线数、任务完成率、错误率。
  2. 详细层：每个AGV的详细指标，比如电量、速度、当前任务。
  3. 接口层：MES接口的调用量、成功率、响应时间。

我曾经帮一个客户搭看板，对方说“我要一个页面看完所有东西”。结果那个页面密密麻麻，根本看不清。后来我坚持分层设计，每个看板聚焦一个维度，反而更实用。

核心原则：看板不是数据堆砌，而是决策辅助。每个图表都要回答一个问题。

12.3 告警规则配置

监控有了，告警才是关键。没有告警的监控，等于没监控。

Prometheus的告警规则，我一般分三个级别：

级别 触发条件 响应方式
WARNING AGV离线超过5分钟 钉钉/企业微信通知
CRITICAL 任务队列积压超过100 电话告警
EMERGENCY 调度引擎进程挂掉 电话+短信+自动重启 
# alert.rules
groups:
- name: agv_alerts
  rules:
  - alert: AgvOffline
    expr: agv_online_count < 10
    for: 5m
    labels:
      severity: warning
    annotations:
      summary: "AGV离线数量过多"

  - alert: TaskQueueBacklog
    expr: task_queue_length > 100
    for: 1m
    labels:
      severity: critical
    annotations:
      summary: "任务队列积压严重"
避坑指南：我曾经把告警阈值设得太敏感，结果半夜被“AGV离线”告警轰炸。后来发现只是网络波动。加了个“持续5分钟”的条件，清净多了。告警规则一定要加持续时间，避免抖动误报。

12.4 日志级别管理

日志级别这事，看着简单，实际坑不少。

生产环境我一般用INFO级别。DEBUG日志太详细，一天能写几个G的日志，磁盘扛不住。但出问题的时候，又需要DEBUG级别的信息来排查。

我的做法是：运行时动态调整日志级别。不需要重启服务，通过Actuator的/loggers端点就能改。

# 查看当前日志级别
GET /actuator/loggers/com.agv.scheduler

# 动态修改为DEBUG
POST /actuator/loggers/com.agv.scheduler
{
  "configuredLevel": "DEBUG"
}

嗯，这里要注意：改完之后记得改回来。我见过有人调成DEBUG后忘了改，第二天磁盘报警了。

另外，我习惯在代码里加一些“关键节点日志”。比如AGV接到任务、到达站点、完成任务，这些节点必须打日志。配合ELK，就能画出每台AGV的完整轨迹。

// 关键节点日志示例
log.info("AGV[{}] 接收到任务[{}]，起点:{}，终点:{}", agvId, taskId, startPoint, endPoint);
log.info("AGV[{}] 到达站点[{}]，当前电量:{}%", agvId, station, battery);
log.warn("AGV[{}] 任务[{}]执行超时，已耗时:{}秒", agvId, taskId, elapsed);
我的习惯：每个关键节点打一条INFO日志，异常情况打WARN或ERROR。这样在Kibana里按级别筛选，就能快速定位问题。我曾经靠这个习惯，半小时定位了一个MES接口超时的bug，客户直呼专业。

下面这张图，是我对日志与监控体系的整体理解。你可以把它当作一个检查清单，看看自己还缺哪块。

日志和监控，就像系统的两只眼睛。一只看过去（日志分析），一只看现在（实时监控）。两只眼睛都亮着，你才能睡个安稳觉。

我个人觉得，这一块投入的时间是值得的。刚开始可能觉得麻烦，但一旦系统出问题，你就会感谢当初的自己。
