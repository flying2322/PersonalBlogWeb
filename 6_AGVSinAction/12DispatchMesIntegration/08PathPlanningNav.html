8 路径规划与导航：拓扑地图构建、A*算法应用、交通管制、死锁检测与解除

各位同行，今天我们来聊聊AGV调度系统里最硬核的部分——路径规划与导航。说实话，我做了这么多年AGV项目，见过太多系统跑着跑着就卡死在路口，或者几台车互相堵着不动弹。这些问题的根子，往往就出在路径规划这个环节上。

我个人习惯把路径规划拆成四个层次来看：地图怎么建、路线怎么算、路口怎么管、死锁怎么解。咱们一个一个说。

一、拓扑地图构建

AGV用的地图，不是给人看的那种带建筑物的地图。它是一张抽象的网络图。说白了，就是把实际场地抽象成「节点」和「边」。

  • 节点：代表路口、工位、充电站、缓存点。每个节点有唯一ID和坐标。
  • 边：代表两节点之间的可行路径。每条边有长度、方向（单向/双向）、限速等属性。

我在项目中遇到过一个问题：某客户工厂地面有坡度，但拓扑图里没体现。结果AGV上坡时电机过载报警。后来我强制要求每条边必须加一个「坡度系数」字段，这才把问题解决。

核心原则：拓扑地图必须与实际物理环境一一对应。节点不能多，多了计算慢；节点不能少，少了路径不灵活。

构建步骤大致如下：

  1. 现场测绘，确定所有关键点位坐标
  2. 根据AGV转弯半径、通道宽度，确定哪些点之间可以直连
  3. 给每条边赋值：长度、方向、限速、优先级
  4. 导入调度系统，生成邻接矩阵或邻接表

嗯，这里要注意：邻接矩阵适合节点数少于200的场景，超过200我建议用邻接表，否则内存扛不住。

二、A*算法应用

A*算法，说白了就是「带方向感的广度优先搜索」。它比Dijkstra聪明的地方在于，它知道目标在哪，会优先往目标方向探索。

核心公式就一个：

F(n) = G(n) + H(n)
  • G(n)：从起点到当前节点n的实际代价（走过的路）
  • H(n)：从当前节点n到终点的预估代价（直线距离）
  • F(n)：总代价，越小越优先探索

我建议在实际项目中，H(n)不要只用欧几里得距离。为什么？因为AGV走的是网格或拓扑图，不是直线。用曼哈顿距离往往更准。我曾经在一个仓库项目里，用欧几里得距离导致A*绕了远路，换成曼哈顿距离后路径长度缩短了12%。

代码实现的核心逻辑：

// 伪代码，实际项目用C++或Java实现
openList.add(startNode);
while (!openList.isEmpty()) {
    current = openList.getLowestF();
    if (current == goal) return reconstructPath(current);
    
    openList.remove(current);
    closedList.add(current);
    
    for (neighbor : current.getNeighbors()) {
        if (closedList.contains(neighbor)) continue;
        
        tentativeG = current.g + distance(current, neighbor);
        if (!openList.contains(neighbor)) {
            openList.add(neighbor);
        } else if (tentativeG >= neighbor.g) {
            continue; // 这条路更差，跳过
        }
        
        neighbor.g = tentativeG;
        neighbor.h = heuristic(neighbor, goal);
        neighbor.f = neighbor.g + neighbor.h;
        neighbor.parent = current;
    }
}
return null; // 无路可走
避坑指南：我曾经在openList用线性查找最低F值，节点一多（超过500）性能直接崩了。后来改成二叉堆（优先队列），计算时间从秒级降到毫秒级。记住：调度系统里，路径计算必须控制在50ms以内。

三、交通管制

多台AGV同时跑，路口就是瓶颈。没有交通管制，两车在路口相遇，那就是「狭路相逢勇者胜」——谁都不让，系统死锁。

我常用的交通管制策略有三种：

策略 原理 适用场景 缺点
路口锁 每个路口一个信号量，AGV进入前申请锁 节点数少、路口密集 容易死锁
路段锁 每条边同一时间只允许一台AGV占用 通道狭窄、单向行驶 利用率低
时间窗 为每台AGV规划通过路口的时间段 高密度、高节拍产线 计算复杂

我个人最推荐时间窗策略。虽然实现起来麻烦点，但它能提前预判冲突，而不是等车到了路口再处理。你想想看，等车到了路口再刹车，那效率能高吗？

时间窗的实现思路：

  1. 每台AGV规划路径时，同时计算到达每个节点的时间
  2. 将时间窗信息注册到全局时间窗表
  3. 新AGV规划路径时，检查时间窗是否有冲突
  4. 有冲突则等待或重新规划
注意：时间窗的精度取决于AGV的定位精度和速度控制精度。如果AGV定位误差超过±10cm，时间窗就形同虚设。我见过一个项目，AGV定位误差±30cm，时间窗完全失效，最后只能降级成路段锁。

四、死锁检测与解除

死锁，说白了就是「你等我让路，我等你让路，谁都不动」。AGV系统里最常见的死锁场景：四台车在十字路口各占一个方向，互相堵死。

死锁产生的四个必要条件（Coffman条件）：

  • 互斥：资源一次只能给一台AGV
  • 持有并等待：AGV占着资源不放，同时等别的资源
  • 不可剥夺：资源不能被强制收回
  • 循环等待：形成资源等待环

我建议在调度系统里做两件事：

1. 死锁预防（事前）

打破循环等待条件。具体做法：给所有资源（节点、路段）编号，强制AGV只能按编号递增的顺序申请资源。这样就不会形成环。但这个方法太死板，实际项目里很少用。

2. 死锁检测与解除（事后）

这才是实战中的主流方案。系统每隔100ms检测一次资源分配图，如果发现环，就强制解除。

检测算法：

// 资源分配图检测环
boolean detectDeadlock() {
    for (AGV agv : allAGVs) {
        if (dfs(agv, new HashSet<AGV>())) {
            return true; // 发现死锁
        }
    }
    return false;
}

boolean dfs(AGV current, Set<AGV> visited) {
    if (visited.contains(current)) return true; // 成环
    visited.add(current);
    
    Resource res = current.getWaitingResource();
    if (res == null) return false;
    
    AGV holder = res.getHolder();
    if (holder != null && holder != current) {
        return dfs(holder, visited);
    }
    return false;
}

解除死锁的方法，我按优先级排序：

  1. 剥夺资源：强制让某台AGV让出占用的路段，退回到上一个节点。这是最常用的方法。
  2. 回退重规划：让死锁环中的某台AGV退回原点，重新规划路径。
  3. 人工介入：实在不行，发报警让现场人员手动处理。但这种情况我尽量不让它发生。
我的经验：死锁解除时，优先选择「任务优先级最低」或「距离最近缓存点」的AGV进行剥夺。我曾经踩过一个坑：每次都剥夺同一台AGV，结果那台车永远完不成任务。后来改成轮询剥夺，公平多了。
