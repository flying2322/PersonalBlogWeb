6 AGV状态上报：心跳机制、位置上报、电量上报、任务状态变更上报、异常报警上报

AGV调度系统跟MES对接，最核心的一件事是什么？

我个人觉得，不是任务下发的有多快，而是状态上报。

你想想看，MES那边眼巴巴等着知道AGV现在在哪儿、活儿干完了没有、还有没有电。如果状态上报不及时，MES就会以为AGV还在干活，实际上它早就趴窝了。我在项目里见过太多次这种乌龙了。

今天咱们就把AGV状态上报的五个核心维度掰开揉碎讲清楚。

6.1 心跳机制：证明我还活着

心跳机制，说白了就是AGV每隔几秒跟调度系统说一声「我还活着」。

为什么需要这个？因为AGV和调度系统之间的网络随时可能断掉。如果没有心跳，调度系统根本不知道AGV是死是活。

核心要点：

  • 心跳频率：一般3~5秒一次，太频繁浪费带宽，太慢影响实时性
  • 心跳内容：AGV编号、当前时间戳、运行模式（自动/手动/离线）
  • 超时判定：连续3次未收到心跳，调度系统判定AGV离线

我习惯在心跳包里加一个序列号。比如第1次心跳序列号是1，第2次是2。这样调度系统能发现有没有丢包。如果收到序列号5和7，中间缺了6，说明网络有抖动。

// 心跳报文示例（JSON格式）
{
  "msgType": "HEARTBEAT",
  "agvId": "AGV-001",
  "timestamp": 1712345678000,
  "sequence": 128,
  "mode": "AUTO",
  "batteryLevel": 85
}

避坑指南：

我曾经遇到过一个项目，AGV的心跳频率设成了1秒1次。结果100台AGV同时上线，调度系统直接被打挂了。后来改成3秒一次，配合消息队列缓冲，问题就解决了。

6.2 位置上报：AGV到底在哪儿

位置上报比心跳复杂得多。MES要知道AGV当前在哪个站点、哪条路径上，甚至精确到厘米级。

位置上报通常分两种：

  • 站点级上报：AGV到达某个站点时上报，精度到站点编号
  • 连续位置上报：AGV在行驶过程中持续上报坐标，精度到厘米

我个人建议，站点级上报用于MES，连续位置上报用于调度系统内部。为什么？因为MES不需要知道AGV在路径上的每一厘米，它只需要知道「AGV到了A站」或者「AGV正在去B站的路上」。

// 位置上报报文示例
{
  "msgType": "POSITION_REPORT",
  "agvId": "AGV-001",
  "positionType": "STATION",  // STATION 或 COORDINATE
  "stationId": "ST-05",
  "x": 125.3,
  "y": 78.6,
  "angle": 90.0,
  "speed": 0.5,
  "timestamp": 1712345679000
}

注意：

位置上报的频率不能太高。我见过有人把连续位置上报设成100毫秒一次，结果AGV的工控机CPU直接跑满。一般500毫秒到1秒一次就够了。

6.3 电量上报：别让AGV半路趴窝

电量上报看似简单，其实坑很多。

MES需要根据电量做决策：

  • 电量低于20%：强制返回充电站
  • 电量低于30%：不再分配长距离任务
  • 电量低于50%：优先分配近距离任务

我在项目中遇到过一个问题：AGV上报的电量是百分比，但不同AGV的电池容量不一样。有的AGV电池是200Ah，有的是300Ah。MES只看百分比，结果200Ah的AGV显示50%电量，实际只能跑2小时；300Ah的AGV显示50%，能跑3小时。

所以我建议，电量上报同时包含百分比和剩余续航时间。

// 电量上报报文示例
{
  "msgType": "BATTERY_REPORT",
  "agvId": "AGV-001",
  "batteryLevel": 65,        // 百分比
  "remainingMinutes": 120,   // 剩余续航时间（分钟）
  "isCharging": false,       // 是否正在充电
  "voltage": 48.5,           // 当前电压
  "current": 12.3            // 当前电流
}

小技巧：

电量上报不要只在电量变化时才上报。我习惯每30秒上报一次，哪怕电量没变。这样调度系统能持续监控电池健康状态。如果连续几次上报电量都没变，说明电池传感器可能坏了。

6.4 任务状态变更上报：MES最关心的

任务状态变更，是MES最敏感的上报类型。MES下发一个任务，AGV执行过程中，状态每变一次，MES都要知道。

任务状态变更的典型流程：

  1. 任务已接收：AGV确认收到任务
  2. 任务已开始：AGV开始执行任务
  3. 到达取货点：AGV到达取货站点
  4. 取货完成：AGV完成取货
  5. 到达放货点：AGV到达放货站点
  6. 放货完成：AGV完成放货，任务结束

嗯，这里要注意：每个状态变更都必须上报，不能跳状态。我曾经遇到一个供应商，他们AGV从「任务已开始」直接跳到「放货完成」，跳过了中间四个状态。MES那边直接报错，因为MES的逻辑是必须按顺序接收状态。

// 任务状态变更报文示例
{
  "msgType": "TASK_STATUS_CHANGE",
  "agvId": "AGV-001",
  "taskId": "TASK-20240315-001",
  "fromStatus": "ARRIVED_PICKUP",
  "toStatus": "PICKUP_COMPLETED",
  "timestamp": 1712345680000,
  "stationId": "ST-05",
  "errorCode": null
}

关键点：

任务状态变更必须包含时间戳和站点ID。MES需要根据这些信息计算每个环节的耗时，做效率分析。

6.5 异常报警上报：出事了赶紧说

异常报警上报，是AGV状态上报里优先级最高的。一旦AGV出问题，必须立刻通知MES。

常见的异常类型：

异常类型 严重级别 处理方式
碰撞传感器触发 紧急 AGV立即停止，通知维护人员
导航丢失 严重 AGV原地等待，调度系统重新下发路径
电机过温 警告 AGV降速运行，完成当前任务后返回维修区
通信超时 警告 AGV尝试重连，重连失败则停车
电量过低 警告 AGV强制返回充电站

我习惯在异常上报里加一个恢复建议字段。比如「导航丢失」的恢复建议是「请检查地面二维码是否被遮挡」。这样MES操作员看到报警，能立刻知道该怎么做，不用翻手册。

// 异常报警报文示例
{
  "msgType": "ALARM_REPORT",
  "agvId": "AGV-001",
  "alarmCode": "E-1005",
  "alarmLevel": "CRITICAL",
  "description": "导航丢失，无法定位当前位置",
  "suggestion": "请检查地面二维码是否被遮挡或损坏",
  "timestamp": 1712345685000,
  "position": {
    "x": 125.3,
    "y": 78.6
  }
}

重要提醒：

异常报警上报不能有延迟。我见过有些系统把报警和心跳混在一起，心跳3秒一次，报警也3秒一次。结果AGV撞了东西，3秒后才上报，黄花菜都凉了。报警应该立即上报，走独立的、高优先级的通道。
