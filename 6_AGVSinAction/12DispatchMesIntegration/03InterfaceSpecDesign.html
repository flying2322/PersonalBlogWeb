3 接口规范设计：RESTful API设计原则、接口文档编写（Swagger/OpenAPI）、版本管理策略

好，咱们进入第三章。接口规范设计。

说实话，我在MES和AGV调度系统对接的项目里，踩过最多的坑就是接口规范不统一。有的项目组用RPC，有的用SOAP，还有的直接扔过来一个Excel说“这就是接口文档”。嗯，那场面，简直是一场灾难。

所以这一章，我把自己这些年总结的经验掰开揉碎了讲给你听。咱们就聚焦三件事：RESTful API怎么设计、接口文档怎么写、版本怎么管。

3.1 RESTful API设计原则——别把REST玩成RPC

很多人一听说RESTful，就觉得“哦，用HTTP嘛，GET/POST/PUT/DELETE”。其实没那么简单。我个人习惯把RESTful API看作是对资源的操作，而不是对功能的调用。

举个例子，AGV要上报当前位置。很多新手会设计成：

POST /api/reportPosition
{
  "agvId": "AGV001",
  "x": 12.5,
  "y": 34.2
}

这其实是个RPC风格。RESTful应该怎么设计？

PUT /api/agvs/AGV001/position
{
  "x": 12.5,
  "y": 34.2
}

看出来区别了吗？前者是“我要执行一个上报位置的动作”，后者是“我要更新AGV001这个资源的位置属性”。资源是名词，不是动词。

核心原则：

  • 使用名词复数表示资源集合：/agvs、/tasks、/orders
  • 使用HTTP方法表达操作语义：GET查、POST创建、PUT全量更新、PATCH部分更新、DELETE删除
  • 资源间的关系用路径层级表达：/agvs/{agvId}/tasks
  • 查询参数用于过滤、排序、分页：?status=idle&page=1&size=20

我在项目中遇到过最典型的问题，就是有人把POST既当创建又当查询用。你想想看，一个接口既会新增数据又会返回查询结果，这谁受得了？

3.2 接口文档编写——Swagger/OpenAPI是救命稻草

没有文档的接口，就是耍流氓。我见过太多项目，接口写好了，但没人知道怎么调。最后全靠“你问一下开发”、“你看一下代码”来传递信息。效率极低。

我个人强烈推荐使用OpenAPI 3.0规范配合Swagger工具链。为什么？因为它既是文档，又是测试工具，还能生成客户端代码。

来看一个AGV状态上报接口的OpenAPI定义示例：

openapi: 3.0.0
info:
  title: AGV调度系统接口
  version: 1.0.0
paths:
  /api/v1/agvs/{agvId}/status:
    put:
      summary: 更新AGV状态
      parameters:
        - name: agvId
          in: path
          required: true
          schema:
            type: string
          description: AGV编号
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              properties:
                status:
                  type: string
                  enum: [idle, moving, charging, error]
                battery:
                  type: number
                  description: 电量百分比
      responses:
        '200':
          description: 更新成功
        '400':
          description: 请求参数错误

我的经验：写接口文档时，一定要把枚举值和错误码写清楚。我曾经因为没写清楚AGV状态枚举值，导致MES那边传了个“空闲”进来，而我这边只认“idle”。结果就是AGV一直显示离线，排查了整整一下午。

Swagger的好处是，你写完这个YAML文件，直接扔到Swagger UI里，就能生成一个可交互的API测试页面。前后端可以同时开发，前端看着文档就能mock数据，后端写完接口就能自测。

3.3 版本管理策略——别让接口变“接囗”

接口版本管理，说白了就是向前兼容的问题。AGV调度系统一旦上线，MES那边可能同时对接了几十台AGV，你这边一改接口，那边全崩。

我常用的版本管理策略有三种：

策略 实现方式 适用场景
URL路径版本 /api/v1/agvs、/api/v2/agvs 最直观，适合大版本升级
请求头版本 Accept: application/vnd.agv.v1+json 更优雅，适合微服务架构
查询参数版本 /api/agvs?version=1 简单粗暴，但不推荐长期使用

我个人习惯用URL路径版本。为什么？因为一眼就能看出来当前调的是哪个版本，排查问题的时候特别方便。你想想看，生产环境出了故障，运维人员打开日志，看到/api/v1/agvs和/api/v2/agvs，马上就能定位到版本问题。

避坑指南：我曾经在一个项目里，为了省事，直接修改了v1接口的返回字段。结果MES那边缓存了旧的字段名，数据解析全部报错。从那以后，我定了个铁律：v1接口一旦发布，只增不减，只加不改。真要改，就上v2，然后给MES留足迁移时间。
