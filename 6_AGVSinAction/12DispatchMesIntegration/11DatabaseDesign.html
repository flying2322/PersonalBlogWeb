11 数据库设计：MySQL/PostgreSQL表结构设计、Redis缓存应用、时序数据库（InfluxDB）存储AGV轨迹

各位同行，今天我们来聊聊AGV调度系统与MES对接时，数据库这块到底该怎么设计。说实话，我见过不少项目，系统跑着跑着就卡死了，查来查去，十有八九是数据库没设计好。你想想看，AGV调度系统每秒要处理多少位置数据？MES那边又不断下发任务，这数据量可不是闹着玩的。

我个人习惯把数据库设计分成三层：关系型数据库管业务逻辑，缓存数据库扛高并发，时序数据库存轨迹数据。这三兄弟各司其职，缺一不可。

11.1 关系型数据库：MySQL还是PostgreSQL？

先说说关系型数据库。MySQL和PostgreSQL我都用过，说实话，各有千秋。但如果你问我个人偏好，我倾向于PostgreSQL。为什么？因为AGV调度系统里有很多复杂的地理位置查询，PostgreSQL的PostGIS扩展简直是神器。

不过，如果你的团队对MySQL更熟悉，用MySQL也完全没问题。关键是把表结构设计好。

11.1.1 核心表结构设计

我直接上干货，这是我在多个项目中沉淀下来的表结构。先看任务表：

-- 任务主表
CREATE TABLE agv_task (
    task_id BIGSERIAL PRIMARY KEY,
    task_code VARCHAR(64) NOT NULL UNIQUE,  -- 任务编号，如 TASK20240101001
    task_type INT NOT NULL,                 -- 任务类型：1-搬运 2-充电 3-维修
    priority INT DEFAULT 5,                 -- 优先级 1-10，数字越小优先级越高
    source_point VARCHAR(32) NOT NULL,      -- 起点编码
    target_point VARCHAR(32) NOT NULL,      -- 终点编码
    status INT DEFAULT 0,                   -- 状态：0-待分配 1-已分配 2-执行中 3-已完成 4-异常
    create_time TIMESTAMP DEFAULT NOW(),
    update_time TIMESTAMP DEFAULT NOW(),
    complete_time TIMESTAMP,
    mes_order_id VARCHAR(64),               -- MES工单ID
    remark TEXT
);

-- 任务执行记录表
CREATE TABLE agv_task_execution (
    exec_id BIGSERIAL PRIMARY KEY,
    task_id BIGINT NOT NULL REFERENCES agv_task(task_id),
    agv_id INT NOT NULL,                    -- 执行AGV编号
    start_time TIMESTAMP,
    end_time TIMESTAMP,
    distance FLOAT,                         -- 行驶距离（米）
    energy_consumed FLOAT,                  -- 能耗（kWh）
    error_code INT DEFAULT 0,               -- 异常码
    error_msg TEXT
);

这里有个坑，我必须要提醒你。任务编号千万别用自增ID，MES那边传过来的工单号可能是字符串格式的。我曾经在一个项目里直接用自增ID做关联，结果MES系统升级后，两边对不上号，排查了整整两天。

避坑指南：任务表一定要加唯一索引，而且建议用业务编码做主键关联。MES和AGV系统之间的任务ID映射，最好单独建一张映射表。

11.1.2 AGV车辆表与站点表

AGV车辆表相对简单，但有几个字段我建议一定要加上：

CREATE TABLE agv_vehicle (
    agv_id SERIAL PRIMARY KEY,
    agv_code VARCHAR(32) NOT NULL UNIQUE,   -- AGV编号
    vehicle_type INT NOT NULL,              -- 车型：1-潜伏式 2-叉车式 3-牵引式
    battery_level FLOAT DEFAULT 100.0,      -- 当前电量百分比
    status INT DEFAULT 0,                   -- 状态：0-空闲 1-执行任务 2-充电 3-离线 4-故障
    current_point VARCHAR(32),              -- 当前位置编码
    last_heartbeat TIMESTAMP,               -- 最后心跳时间
    software_version VARCHAR(32),           -- 软件版本
    total_mileage FLOAT DEFAULT 0           -- 总行驶里程
);

站点表我习惯用分层设计。物理站点和逻辑站点分开：

CREATE TABLE agv_station (
    station_id SERIAL PRIMARY KEY,
    station_code VARCHAR(32) NOT NULL UNIQUE,
    station_type INT NOT NULL,              -- 1-充电站 2-上下料点 3-暂存区 4-维修区
    x_coord FLOAT NOT NULL,                 -- X坐标（米）
    y_coord FLOAT NOT NULL,                 -- Y坐标（米）
    angle FLOAT DEFAULT 0,                  -- 朝向角度
    is_enabled BOOLEAN DEFAULT TRUE,
    max_queue INT DEFAULT 1,                -- 最大排队数量
    current_queue INT DEFAULT 0             -- 当前排队数量
);

11.2 Redis缓存应用：扛住高并发

说实话，没有Redis的AGV调度系统，我都不敢想象怎么扛住高峰期。MES下发任务的时候，那可是毫秒级的响应要求。你想想看，一条产线几十台AGV同时请求任务，如果每次都查MySQL，数据库不崩才怪。

11.2.1 缓存什么？

我总结了几类必须缓存的数据：

  • 任务队列：待分配的任务列表，用Redis的List结构
  • AGV状态：每台AGV的实时状态，用Hash结构
  • 路径规划结果：高频路径缓存，用String结构，设置TTL
  • 站点占用状态：用Set或Bitmap，快速判断站点是否可用

举个实际例子，任务队列的Redis设计：

// 任务队列 - 按优先级排序
// Key: agv:task:queue:{priority}
// Value: 任务ID列表（有序集合）
ZADD agv:task:queue:1 100 "TASK20240101001"
ZADD agv:task:queue:1 95  "TASK20240101002"

// AGV实时状态
// Key: agv:status:{agv_id}
// Value: Hash
HSET agv:status:AGV001 status "idle" battery 85.5 point "A01"
经验之谈：Redis的Key命名一定要规范。我习惯用「业务域:对象:属性」的格式，这样后期维护起来特别清晰。另外，记得给缓存设置合理的过期时间，别让垃圾数据占着内存。

11.2.2 缓存与数据库的一致性

这个问题我踩过坑。有一次AGV状态更新了，但Redis没及时同步，导致调度系统分配了重复任务。后来我采用了「先更新数据库，再删除缓存」的策略。说白了，就是保证数据库是权威数据源，缓存只是加速用的。

// 伪代码示例
public void updateAgvStatus(AgvStatus status) {
    // 1. 先更新数据库
    database.updateAgvStatus(status);
    
    // 2. 再删除缓存
    redis.delete("agv:status:" + status.getAgvId());
    
    // 3. 下次查询时自动回填缓存
}

11.3 时序数据库：InfluxDB存储AGV轨迹

AGV的轨迹数据，说白了就是时间序列数据。每台AGV每隔几百毫秒上报一次位置，一天下来就是几百万条记录。用MySQL存？我试过，查询最近一小时轨迹要等好几秒，根本没法用。

InfluxDB就是专门干这个的。它的设计理念就是「写多读少」，写入速度极快，压缩率也高。

11.3.1 数据模型设计

InfluxDB的数据模型和关系型数据库不太一样。它没有表的概念，而是用「Measurement」来组织数据。我一般这样设计：

-- Measurement: agv_trajectory
-- Tags: agv_id, task_id (用于快速过滤)
-- Fields: x, y, angle, speed, battery (实际数值)
-- Time: 时间戳（自动生成）

-- 写入示例（Line Protocol格式）
agv_trajectory,agv_id=AGV001,task_id=TASK001 x=12.5,y=34.2,angle=90.0,speed=1.2,battery=85.3 1704067200000000000
agv_trajectory,agv_id=AGV001,task_id=TASK001 x=12.8,y=34.5,angle=92.0,speed=1.3,battery=85.2 1704067200500000000

这里有个关键点：Tag的基数不能太高。Tag是InfluxDB的索引，如果Tag值太多（比如把坐标也做成Tag），性能会急剧下降。我一般只把AGV编号和任务编号作为Tag，其他都放Fields里。

11.3.2 查询实战

查询最近10分钟AGV001的轨迹：

SELECT x, y, angle, speed 
FROM agv_trajectory 
WHERE agv_id = 'AGV001' 
  AND time > now() - 10m
ORDER BY time

查询某台AGV在某个时间段内的平均速度：

SELECT MEAN(speed) AS avg_speed 
FROM agv_trajectory 
WHERE agv_id = 'AGV001' 
  AND time >= '2024-01-01T00:00:00Z' 
  AND time <= '2024-01-01T01:00:00Z'
核心要点：InfluxDB的保留策略（Retention Policy）一定要设置好。我一般设置原始数据保留7天，聚合数据保留30天。这样既能保证实时查询的速度，又能满足历史分析的需求。

11.4 三种数据库的协同工作流

说了这么多，这三种数据库到底怎么配合？我画了一张图，你看完就明白了。

你看，整个数据流是这样的：MES下发任务到Redis队列，调度引擎从Redis取任务分配给AGV。AGV执行过程中，实时位置上报到InfluxDB。同时，关键业务数据定期从Redis同步到MySQL做持久化。这样各司其职，系统才能跑得稳。

我的建议：刚开始做的时候，别想着一步到位。先把MySQL和Redis搭起来跑通，等轨迹数据量上来了，再引入InfluxDB。我见过太多人一开始就搞得很复杂，结果连基础功能都没跑通。

好了，数据库设计这块就聊到这儿。记住一句话：没有最好的数据库，只有最合适的组合。根据你的实际场景，灵活搭配才是王道。
