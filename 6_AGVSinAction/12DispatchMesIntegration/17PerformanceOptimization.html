17 性能优化：接口响应优化、数据库查询优化、消息队列吞吐优化、AGV调度算法优化

各位，咱们今天聊点硬核的。AGV调度系统跟MES对接，跑起来容易，跑得稳、跑得快，那才是真本事。我见过太多项目，上线第一天看着挺好，一到大促、双十一，系统直接卡成PPT。说白了，性能优化就是给系统“减负”和“提速”。

这一章，我把自己这些年踩过的坑、总结的经验，拆成四个部分来讲：接口、数据库、消息队列、调度算法。咱们一个一个啃。

17.1 接口响应优化：别让MES等你

AGV调度系统和MES之间，最直接的交互就是接口调用。MES下发一个任务，调度系统得赶紧响应。如果接口响应慢，MES那边就会超时重试，重试多了，系统就雪崩了。

我个人的习惯是，接口响应时间控制在200ms以内。 超过这个数，就得找原因了。

17.1.1 减少不必要的网络开销

  • 连接复用： 别每次请求都新建TCP连接。用HTTP连接池，或者直接用gRPC长连接。我在一个项目里，光是把HTTP改成gRPC，响应时间就从800ms降到了150ms。
  • 数据压缩： 接口返回的数据，尤其是任务列表、路径信息，动不动就几MB。开启Gzip压缩，传输量能减少70%以上。
  • 精简字段： MES问你要“当前AGV状态”，你返回一堆坐标、电量、任务历史……没必要。只返回对方需要的字段，减少序列化和传输时间。

17.1.2 异步处理与缓存

有些操作，比如更新AGV位置，MES其实不关心实时性。这时候就别同步阻塞了。

// 伪代码示例：异步处理位置更新
public void updatePosition(AgvPosition pos) {
    // 1. 立即返回成功
    // 2. 将位置信息丢进内存队列
    positionQueue.offer(pos);
    // 3. 后台线程批量写入数据库
}

缓存也是利器。 比如AGV的当前任务状态，MES频繁查询。如果每次都查数据库，压力很大。我建议用Redis缓存，设置5秒过期。MES查的时候，直接从缓存拿，快得很。

小技巧： 接口设计时，尽量支持批量操作。比如MES要下发100个任务，别拆成100次请求，一次传一个数组过去。我见过一个客户，单次请求改批量后，接口吞吐量提升了5倍。

17.2 数据库查询优化：别让SQL拖后腿

AGV调度系统里，数据库是核心。任务表、位置表、路径表……数据量一上来，查询慢得让人抓狂。我记得有一次，客户反馈“AGV任务下发后，等了10秒才动”。查了半天，发现是一条SQL没走索引。

17.2.1 索引优化

  • 复合索引： 查询条件里经常有“任务状态 + 创建时间”。这时候建一个复合索引 (status, create_time)，比两个单列索引快得多。
  • 覆盖索引： 如果查询只需要某几个字段，比如只查AGV的ID和位置，那就建一个覆盖索引，避免回表查询。
  • 避免索引失效： 不要在索引列上做函数操作，比如 WHERE DATE(create_time) = '2024-01-01'。改成 WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02'。

17.2.2 读写分离与分表

AGV调度系统，读多写少。MES查任务状态、查AGV位置，都是读操作。调度系统更新任务、记录位置，是写操作。

我建议做读写分离。 主库负责写，从库负责读。这样写操作不会影响读性能。

如果数据量特别大，比如位置表一天几千万条，那就得考虑分表了。按时间分表，比如 position_202401、position_202402。查询时带上时间范围，直接定位到对应的表。

注意： 分表之后，跨表查询就麻烦了。比如要查某个AGV最近一周的位置，得遍历多张表。这时候可以考虑用Elasticsearch或者时序数据库（如InfluxDB）来存位置数据。

17.3 消息队列吞吐优化：别让消息堵在路上

AGV调度系统里，消息队列是“血管”。MES下发的任务、AGV上报的状态、调度指令……都靠消息队列流转。如果消息队列吞吐上不去，整个系统就瘫痪了。

我常用的消息队列是RabbitMQ和Kafka。 对于AGV调度场景，Kafka更适合高吞吐、持久化的场景。

17.3.1 批量发送与消费

别一条一条地发消息。比如AGV位置上报，每秒可能有几百条。如果每条都单独发送，网络开销很大。

// 伪代码：批量发送位置消息
List<PositionMessage> batch = new ArrayList<>();
while (true) {
    PositionMessage msg = positionQueue.poll(100, TimeUnit.MILLISECONDS);
    if (msg != null) {
        batch.add(msg);
    }
    if (batch.size() >= 100 || (msg == null && !batch.isEmpty())) {
        kafkaProducer.send(batch);
        batch.clear();
    }
}

消费端也一样，批量拉取、批量处理。我调优过一个项目，批量大小从1调到100，吞吐量从每秒2000条涨到了每秒5万条。

17.3.2 分区与并行消费

Kafka的主题可以设置多个分区。分区越多，并行度越高。但要注意，分区数不是越多越好。分区太多，会导致文件句柄占用过多，反而影响性能。

我建议分区数等于消费者线程数的2-3倍。 这样既能充分利用CPU，又不会造成太多资源浪费。

避坑指南： 我曾经遇到过一个坑，消息队列消费速度跟不上生产速度，导致消息积压。后来发现是消费者处理逻辑里有一个数据库写操作，耗时太长。解决办法是把写操作异步化，先写到内存队列，再批量写入数据库。

17.4 AGV调度算法优化：让AGV跑得更聪明

前面说的都是“外围”优化，调度算法才是核心。算法不好，AGV就会绕路、死锁、空跑。我见过一个仓库，AGV利用率只有30%，优化算法后直接提升到70%。

17.4.1 路径规划优化

AGV的路径规划，说白了就是找一条最短、最不堵的路。传统的A*算法，在静态地图上很好用。但仓库里AGV多，路况是动态的。

我建议用“时间窗”A*算法。 每个AGV在规划路径时，不仅要考虑距离，还要考虑其他AGV占用的时间窗。比如，某个路段在10:00-10:05被AGV-A占用，那AGV-B规划时就要避开这个时间段。

17.4.2 任务分配优化

MES下发一个任务，调度系统要决定派哪台AGV去。最简单的策略是“就近分配”，但有时候就近的AGV正在忙，或者电量不足。

我常用的策略是“综合评分”。 给每个AGV打分，考虑因素包括：距离、当前任务数、电量、是否在充电等。得分最高的AGV获得任务。

// 伪代码：综合评分算法
public double calculateScore(Agv agv, Task task) {
    double distanceScore = 1.0 / (agv.distanceTo(task) + 1);
    double taskScore = 1.0 / (agv.currentTaskCount + 1);
    double batteryScore = agv.batteryLevel / 100.0;
    double chargingScore = agv.isCharging ? 0.5 : 1.0;
    return distanceScore * 0.4 + taskScore * 0.3 + batteryScore * 0.2 + chargingScore * 0.1;
}

17.4.3 死锁预防与解除

AGV多了，死锁是难免的。两个AGV面对面堵住，谁也动不了。

预防死锁： 在路径规划时，预留“避让区”。如果AGV发现前方有冲突，提前在避让区等待。

解除死锁： 如果已经死锁了，就得有“死锁检测”机制。比如，每隔5秒检查一次，如果某个AGV超过30秒没移动，就判定为死锁。然后让其中一台AGV倒车、让路。

经验之谈： 调度算法优化，不要追求“最优解”，要追求“足够好”。因为AGV调度是实时系统，算法计算时间太长，反而会影响响应速度。我一般把算法计算时间控制在10ms以内。
