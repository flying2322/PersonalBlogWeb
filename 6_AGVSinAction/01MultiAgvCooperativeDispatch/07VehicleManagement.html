7 车辆管理模块——注册、监控、电量与异常处理

车辆管理模块，说白了就是AGV调度系统的“户口本”加“体检中心”。

一辆AGV要能干活，首先得在系统里有个合法身份。跑起来之后，你得盯着它别出乱子。电量低了要提醒，出故障了要处理。这些事，都归车辆管理模块管。

我个人习惯把这块拆成四个核心功能：车辆注册、状态监控、电量管理、异常处理。咱们一个一个说。

7.1 车辆注册——给AGV上户口

新买回来的AGV，不能直接让它满厂跑。你得先在系统里登记一下。就像新员工入职，得录入工号、姓名、部门一样。

注册时，系统会分配一个唯一的车辆ID。这个ID很重要，后续所有的调度指令、状态上报、日志记录，都靠它来识别是哪辆车。

我建议注册信息至少包含以下几项：

字段 说明 示例
vehicle_id 车辆唯一标识 AGV-001
vehicle_type 车型（如潜伏式、叉车式） 潜伏式
max_speed 最大速度（m/s） 1.5
battery_capacity 电池容量（Ah） 200
ip_address 通信IP地址 192.168.1.101
register_time 注册时间戳 2025-01-15 10:30:00

注册接口的设计，我一般用RESTful风格。简单直接：

POST /api/v1/vehicles/register
{
    "vehicle_type": "潜伏式",
    "max_speed": 1.5,
    "battery_capacity": 200,
    "ip_address": "192.168.1.101"
}

// 返回示例
{
    "code": 0,
    "message": "success",
    "data": {
        "vehicle_id": "AGV-001",
        "status": "idle"
    }
}
小提示：注册时最好做一次“心跳测试”。确认AGV能正常通信，再把它标记为可用。不然注册了一堆离线车，调度系统会懵。

7.2 状态监控——实时盯着每一辆车

车辆注册好了，接下来就是监控。AGV跑起来之后，状态是实时变化的。你得知道它当前在哪儿、在干嘛、有没有出问题。

状态监控的核心，是周期性上报。AGV每隔几百毫秒，就会向调度系统发一次状态包。我见过有些系统用1秒上报一次，其实太慢了。AGV跑得快的时候，1秒能跑出去好几米，位置误差会很大。

我个人建议上报频率设在200~500ms之间。状态包的内容大概长这样：

{
    "vehicle_id": "AGV-001",
    "timestamp": 1705300000123,
    "x": 12.5,
    "y": 8.3,
    "angle": 90.0,
    "speed": 1.2,
    "battery_level": 85,
    "status": "moving",
    "error_code": 0
}

这里有个坑，我得提醒你。状态上报的数据量很大，如果每辆车每秒发2~5个包，100辆车就是每秒200~500个包。后端处理不过来怎么办？

我曾经在一个项目里吃过这个亏。当时用的单线程处理，结果消息队列直接爆了。后来改成多线程+环形缓冲区的方案，才算稳住。

注意：状态监控模块一定要做“超时判断”。如果某辆车超过3秒没上报状态，系统应该自动标记为“通信异常”，并触发告警。别傻等着。

7.3 电量管理——别让AGV半路趴窝

AGV是电动的，没电了就跑不动。电量管理看似简单，其实挺考验策略。

最基本的做法是：当电量低于某个阈值（比如20%），系统自动给这辆车下发“回充电桩”的任务。但这里有个问题——如果多辆车同时低电量，充电桩不够用怎么办？

嗯，这就涉及到充电调度策略了。我常用的策略是：

  • 优先级排队：电量越低，优先级越高。低于10%的，插队也要先充。
  • 动态阈值：高峰期，把充电阈值降到15%，让车多跑几趟。低谷期，提到30%，提前回充。
  • 换电模式：有些场景用换电池的方式，比充电快得多。系统要支持电池更换后的电量重置。

电量上报的字段，一般包含当前电量和电压：

{
    "vehicle_id": "AGV-001",
    "battery_level": 18,
    "voltage": 23.5,
    "is_charging": false
}
核心原则：电量管理不是单纯看百分比。要结合任务队列、充电桩状态、当前时段综合决策。说白了，就是让AGV在“干活”和“充电”之间找到平衡。

7.4 异常处理——出事了怎么办

AGV在工厂里跑，难免遇到各种意外。撞到障碍物、轮子打滑、通信中断、急停被按下……这些都属于异常。

异常处理模块，就是用来兜底的。我把它分为三个层级：

7.4.1 异常检测

AGV自身会检测异常。比如电机过流、激光雷达被遮挡、安全触边被触发。检测到后，AGV会立即停车，并上报异常码。

常见的异常码：

异常码 含义 处理方式
1001 电机过流 停车，等待人工复位
1002 激光雷达异常 停车，检查传感器
1003 通信超时 尝试重连，重连失败则停车
1004 安全触边触发 急停，需人工确认
1005 定位丢失 停车，尝试重新定位

7.4.2 自动恢复

有些异常是可以自动恢复的。比如通信超时，AGV会自动重连。定位丢失，AGV会尝试重新匹配地图特征点。

我建议给每种异常配置一个“自动恢复策略”。比如：

  • 通信超时：重试3次，间隔1秒。失败则停车。
  • 定位丢失：尝试重新定位，超时30秒失败则停车。
  • 电机过流：不允许自动恢复，必须人工介入。

7.4.3 人工介入

对于无法自动恢复的异常，系统要能通知运维人员。通知方式可以是弹窗、短信、或者对接企业的告警平台。

我曾经遇到过一个场景：AGV在货架底下卡住了，自动恢复策略试了三次都动不了。最后运维人员远程查看视频，发现是一块包装膜缠住了轮子。派人过去清理一下就好了。

所以，异常处理模块最好能附带现场快照——比如AGV当前的位置、周围环境的截图、最近的日志。这样运维人员能快速判断问题，不用跑到现场去看。

避坑指南：异常处理千万别做成“死循环”。有些AGV卡住之后，反复尝试前进后退，结果把地面磨出一道沟。我曾经见过这样的案例……嗯，后来我们加了一个“尝试次数上限”，超过上限就彻底停车，等人来处理。
