17 性能优化：数据库优化、缓存策略、异步处理

各位同学，咱们今天聊点硬核的。

AGV调度系统跑起来之后，最怕什么？怕卡顿，怕延迟，怕数据库扛不住。我见过一个项目，调度中心每秒要处理上千条任务指令，数据库直接被打到CPU 100%，调度指令排队排到天荒地老。嗯，那场面，真是让人头大。

所以今天这节课，我就把压箱底的性能优化三板斧掏出来：数据库优化、缓存策略、异步处理。这三招用好了，你的调度系统就能从“勉强能用”变成“丝般顺滑”。

核心逻辑图：性能优化三板斧

17.1 数据库优化：别让数据库成为瓶颈

说实话，很多调度系统刚上线时跑得挺欢，数据量一上来就原形毕露。为什么？因为数据库没扛住。我个人习惯，在项目初期就会把数据库优化纳入设计，而不是等出问题了再补。

17.1.1 索引优化

AGV调度系统里，查询最频繁的是什么？任务表、位置表、路径表。这些表的查询条件往往集中在几个字段上：任务状态、AGV编号、时间戳。

我在项目中遇到过，一个任务表几百万条数据，查询耗时从0.1秒飙升到3秒。一查，全表扫描。加了个联合索引，瞬间回到0.05秒。

-- 错误示范：没有索引
SELECT * FROM task WHERE status = 'PENDING' AND agv_id = 'AGV-001';

-- 正确姿势：创建联合索引
CREATE INDEX idx_task_status_agv ON task(status, agv_id);

-- 覆盖索引（更狠）
CREATE INDEX idx_task_cover ON task(status, agv_id, create_time) INCLUDE (task_type, priority);

我的经验：索引不是越多越好。写多读少的表，索引多了反而拖慢写入。AGV调度系统里，任务状态变更频繁，索引控制在3-5个以内比较稳妥。

17.1.2 SQL语句优化

你想想看，很多性能问题其实不是数据库不行，是SQL写得烂。我见过有人写循环查数据库，一条一条查，那能不慢吗？

-- 反例：循环查询（千万别这么干）
for (String agvId : agvList) {
    Task task = jdbcTemplate.queryForObject("SELECT * FROM task WHERE agv_id = ?", agvId);
}

-- 正例：批量查询
SELECT * FROM task WHERE agv_id IN ('AGV-001', 'AGV-002', 'AGV-003');

17.1.3 连接池配置

数据库连接池的配置，说白了就是“够用就好，别浪费”。我建议根据并发量来调：

并发量 连接池大小 超时时间
100以下 10-20 30s
100-500 20-50 15s
500以上 50-100 10s

注意：连接池不是越大越好。我曾经把连接池设到200，结果数据库连接数爆了，反而更慢。建议配合压测来调优。

17.2 缓存策略：让数据离计算更近

数据库再快，也快不过内存。AGV调度系统里，很多数据是“读多写少”的，比如地图信息、AGV配置、路径模板。这些数据，缓存起来就对了。

17.2.1 缓存什么？

  • 热点数据：频繁查询但不常变的数据，比如地图节点、路径信息
  • 计算结果：路径规划结果、任务分配结果，可以缓存几秒到几分钟
  • 配置信息：AGV参数、调度策略配置，几乎不变

17.2.2 缓存策略怎么选？

我个人习惯用两级缓存：本地缓存 + Redis。本地缓存扛高频访问，Redis做分布式共享。

// 本地缓存（Caffeine）
Cache<String, PathInfo> localCache = Caffeine.newBuilder()
    .expireAfterWrite(5, TimeUnit.MINUTES)
    .maximumSize(10000)
    .build();

// Redis缓存
StringRedisTemplate redisTemplate;
ValueOperations<String, String> ops = redisTemplate.opsForValue();
ops.set("path:AGV-001", pathJson, 10, TimeUnit.MINUTES);

避坑指南：我曾经在缓存过期时间上栽过跟头。设得太短，缓存命中率低；设得太长，数据不一致。建议热点数据5-10分钟过期，非热点数据30分钟以上。

17.2.3 缓存穿透与雪崩

这两个问题，做缓存的人都会遇到。说白了：

  • 缓存穿透：查一个不存在的数据，每次都穿透到数据库。解决方案：布隆过滤器或缓存空值。
  • 缓存雪崩：大量缓存同时过期，请求全部打到数据库。解决方案：过期时间加随机值。
// 缓存空值防止穿透
String value = ops.get(key);
if (value == null) {
    // 查数据库
    value = queryFromDB(key);
    if (value == null) {
        // 缓存空值，过期时间短一点
        ops.set(key, "NULL", 30, TimeUnit.SECONDS);
    } else {
        ops.set(key, value, 10, TimeUnit.MINUTES);
    }
}

// 过期时间加随机值防止雪崩
long baseExpire = 10 * 60;
long randomExpire = baseExpire + ThreadLocalRandom.current().nextLong(0, 120);
ops.set(key, value, randomExpire, TimeUnit.SECONDS);

17.3 异步处理：别让调用方等着

AGV调度系统里，有些操作很耗时，比如路径规划、任务分配、日志记录。如果同步处理，调用方就得干等着。异步处理，说白了就是“你先去忙，我处理完了通知你”。

17.3.1 消息队列解耦

我建议用消息队列来处理耗时操作。比如任务分配完成后，把路径规划任务丢到队列里，后台慢慢算。

// 生产者：发送路径规划任务
rabbitTemplate.convertAndSend("path.plan.queue", taskMessage);

// 消费者：异步处理
@RabbitListener(queues = "path.plan.queue")
public void handlePathPlan(TaskMessage message) {
    // 计算路径
    PathResult result = pathPlanner.plan(message);
    // 更新数据库
    taskService.updatePath(result);
}

17.3.2 线程池异步

对于不需要跨服务的异步任务，用线程池就够了。比如日志记录、状态更新。

// 线程池配置
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    10,  // 核心线程数
    20,  // 最大线程数
    60,  // 空闲线程存活时间
    TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(1000),  // 队列大小
    new ThreadPoolExecutor.CallerRunsPolicy()  // 拒绝策略
);

// 异步执行
executor.submit(() -> {
    logService.saveOperationLog(log);
});

注意：线程池的拒绝策略很重要。我建议用CallerRunsPolicy，这样队列满了之后，由调用方自己执行，不会丢任务。但要注意，调用方可能会变慢。

17.3.3 异步处理的坑

嗯，这里要提醒一下。异步处理虽然好，但也会带来新问题：

  • 数据一致性：异步操作可能导致数据暂时不一致。比如任务状态更新了，但路径还没算完。解决方案：用状态机+补偿机制。
  • 异常处理：异步任务失败了怎么办？我习惯加个重试机制，最多重试3次，还失败就记录到异常表，人工处理。
  • 监控：异步任务一定要有监控。队列积压了多少？处理速度够不够？这些都要有指标。
// 带重试的异步处理
@Retryable(value = Exception.class, maxAttempts = 3, backoff = @Backoff(delay = 1000))
public void processAsyncTask(Task task) {
    try {
        // 处理任务
        doProcess(task);
    } catch (Exception e) {
        log.error("处理失败，重试中...", e);
        throw e;  // 触发重试
    }
}

// 重试失败后记录
@Recover
public void recover(Exception e, Task task) {
    errorTaskService.save(task, e.getMessage());
}

总结一下：数据库优化是基础，缓存策略是加速，异步处理是解耦。这三板斧用好了，你的AGV调度系统就能扛住高并发，跑得又快又稳。我在多个项目里验证过，效果立竿见影。
