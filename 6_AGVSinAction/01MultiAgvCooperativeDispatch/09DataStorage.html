9 数据存储方案：MySQL、Redis、时序数据库选型与设计

说到AGV调度系统的数据存储，我见过不少团队一上来就选MySQL，结果跑着跑着就崩了。也有团队啥都用Redis，数据丢了也不心疼。嗯，这里头其实有门道。

AGV调度系统里，数据分三类：结构化业务数据、高频缓存数据、时序监控数据。三类数据的特点完全不同，存储方案也得对症下药。

核心原则：没有银弹。MySQL、Redis、时序数据库各司其职，组合使用才是最优解。

9.1 三类数据的存储需求分析

先看看AGV调度系统里到底存什么数据。我把它拆成三块：

数据类型 典型内容 读写特点 数据量级
业务数据 任务单、车辆信息、用户权限、配置参数 低频读写，强一致性要求 百万级
缓存数据 车辆实时位置、任务队列、锁状态、会话 高频读写，毫秒级响应 千级/秒
时序数据 车辆轨迹、电量变化、传感器数据、告警记录 高频写入，低频查询，按时间聚合 亿级/天

你看，这三类数据对存储引擎的要求完全不同。MySQL擅长事务和关联查询，Redis擅长高速缓存，时序数据库擅长海量时间序列数据的写入和聚合。硬要用一个库扛所有活，迟早出问题。

9.2 MySQL：业务数据的基石

MySQL在AGV调度系统里主要负责持久化业务数据。我个人习惯把任务单、车辆档案、用户权限这些放MySQL里。为什么？因为这些数据需要事务保障和复杂查询。

举个例子，一个任务从创建到完成，中间要经历分配、执行、上报、结算多个状态。如果中间某个环节失败了，整个任务状态必须回滚。MySQL的ACID特性正好解决这个问题。

我的经验：任务表一定要加task_status和version字段。version用于乐观锁，防止并发更新导致状态错乱。我曾经遇到过两台AGV同时抢同一个任务，就是因为没加版本号，结果任务被分配了两次。

表结构设计上，我建议这样：

-- 任务主表
CREATE TABLE agv_task (
    task_id BIGINT PRIMARY KEY AUTO_INCREMENT,
    task_type TINYINT NOT NULL COMMENT '任务类型：1-搬运 2-充电 3-待命',
    source_point VARCHAR(32) NOT NULL,
    target_point VARCHAR(32) NOT NULL,
    priority TINYINT DEFAULT 5,
    task_status TINYINT DEFAULT 0 COMMENT '0-待分配 1-执行中 2-已完成 3-异常',
    version INT DEFAULT 0,
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_status (task_status),
    INDEX idx_create_time (create_time)
);

-- 车辆信息表
CREATE TABLE agv_vehicle (
    vehicle_id VARCHAR(16) PRIMARY KEY,
    vehicle_type VARCHAR(16) NOT NULL,
    battery_level INT DEFAULT 100,
    current_point VARCHAR(32),
    status TINYINT DEFAULT 0 COMMENT '0-空闲 1-工作中 2-充电中 3-离线',
    last_heartbeat DATETIME,
    INDEX idx_status (status)
);

嗯，这里要注意：MySQL不适合存高频写入的数据。比如车辆每秒上报的位置数据，如果全写MySQL，IO很快就扛不住了。所以MySQL只存最终结果，中间过程交给别的库。

9.3 Redis：调度系统的"高速公路"

Redis在AGV调度系统里扮演的角色，说白了就是加速器。调度决策需要毫秒级响应，MySQL根本做不到。我见过一个项目，调度决策走MySQL查询，结果任务分配延迟到了200ms，AGV在路口等得直跺脚。

Redis在调度系统里的典型用法：

  • 车辆实时位置缓存：用Hash结构，key是vehicle_id，field是坐标x/y/z
  • 任务队列：用List或Sorted Set，按优先级排序
  • 分布式锁：用SETNX实现，防止多调度器冲突
  • 路径锁状态：用String，0表示空闲，1表示占用

我举个例子，路径锁的实现：

// 申请路径锁
String lockKey = "path:lock:" + pathId;
Boolean locked = redisTemplate.opsForValue()
    .setIfAbsent(lockKey, vehicleId, 5, TimeUnit.SECONDS);
if (Boolean.TRUE.equals(locked)) {
    // 获得锁，可以通行
} else {
    // 路径被占用，等待或绕行
}

// 释放路径锁
redisTemplate.delete(lockKey);

避坑指南：我曾经犯过一个错误——Redis的key过期时间设得太短。结果AGV还在路径上走着，锁就自动释放了，另一台AGV以为路空了就冲进来，直接撞车。后来我把过期时间设成了路径通行时间的1.5倍，并且AGV完成通行后主动释放锁，才彻底解决。

Redis的数据持久化也要注意。我建议开启AOF持久化，每秒刷一次盘。这样即使Redis挂了，最多丢1秒的数据。调度系统可以容忍少量数据丢失，但不能容忍长时间不可用。

9.4 时序数据库：监控数据的"大胃王"

AGV调度系统里，时序数据是最"能吃"的。一台AGV每秒上报一次位置、电量、速度、温度，一天下来就是86,400条记录。如果系统里有50台AGV，一天就是432万条。一个月下来，数据量轻松过亿。

MySQL面对这种量级，查询性能会急剧下降。时序数据库就是为这种场景设计的。我推荐InfluxDB或TDengine，两者各有千秋。

特性 InfluxDB TDengine
写入性能 百万点/秒 千万点/秒
压缩比 5:1 ~ 10:1 10:1 ~ 20:1
查询语法 类SQL (InfluxQL/Flux) 标准SQL
部署复杂度 简单 中等
生态成熟度 高 国内生态较好

我个人更倾向TDengine，因为它的SQL兼容性好，团队上手快。而且它的超级表设计很适合AGV场景——每台AGV作为一个子表，查询时按车辆聚合非常方便。

时序数据的设计要点：

-- TDengine 创建超级表
CREATE STABLE agv_metrics (
    ts TIMESTAMP,
    battery_level INT,
    speed FLOAT,
    temperature FLOAT,
    x FLOAT,
    y FLOAT,
    error_code INT
) TAGS (vehicle_id VARCHAR(16), vehicle_type VARCHAR(16));

-- 为每台AGV创建子表
CREATE TABLE agv_001 USING agv_metrics TAGS ('AGV-001', '搬运型');
CREATE TABLE agv_002 USING agv_metrics TAGS ('AGV-002', '搬运型');

-- 查询某台AGV最近1小时的电量变化
SELECT ts, battery_level 
FROM agv_001 
WHERE ts >= NOW() - 1h 
ORDER BY ts;

我的建议：时序数据不要保留太久。一般保留7~30天就够了。更早的数据可以降采样后归档到MySQL或对象存储。比如把每分钟的数据聚合为每小时的平均值，数据量直接降到1/60。

三种数据库不是孤立的，它们需要协同工作。我画了一张图来说明它们之间的关系：

实际项目中，数据流转是这样的：

  1. 调度决策时：先查Redis获取车辆实时位置和路径锁状态，毫秒级返回
  2. 任务分配时：写MySQL持久化任务记录，同时更新Redis缓存
  3. 监控数据采集时：直接写入时序数据库，不经过MySQL
  4. 历史查询时：从时序数据库聚合查询，从MySQL查业务详情

总结一下：MySQL管"是什么"，Redis管"现在在哪"，时序数据库管"过去怎么样"。三者各司其职，缺一不可。选型时别贪心，也别偷懒。该用MySQL的地方别用Redis，该用时序数据库的地方别用MySQL。这样搭出来的系统，才能扛得住AGV调度的高并发和低延迟要求。
