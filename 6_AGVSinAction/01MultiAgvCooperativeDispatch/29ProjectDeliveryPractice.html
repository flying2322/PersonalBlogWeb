29 项目实战——从需求分析到系统交付全流程

终于走到这一步了。

前面28章，我们把AGV调度系统的每个零件都拆开讲了一遍。从单车控制到多车协同，从路径规划到死锁避免，从仿真到真车调试。说实话，能坚持到这里的同学，已经具备了独立搭建一套调度系统的能力。

但有个问题——会做零件，不等于会造车。

这一章，我们就来走一遍完整的项目流程。从客户说“我要一套AGV调度系统”开始，到系统上线跑起来为止。我会用我亲身经历的一个项目做蓝本，把每个阶段的坑、经验、套路都抖出来。

29.1 需求分析：别急着写代码

我记得第一次带项目时，客户说“你们先做，需求我们边做边提”。结果呢？三个月后需求翻了三倍，代码重写了四遍。从那以后，我养成了一个习惯——需求阶段花多少时间，开发阶段就能省多少时间。

29.1.1 搞清楚三个核心问题

每次接项目，我都会先问自己三个问题：

  • 运什么？——物料类型、重量、尺寸、是否易碎
  • 从哪到哪？——地图布局、站点数量、路径拓扑
  • 多快多密？——节拍要求、同时运行车辆数、峰值流量

这三个问题搞不清楚，后面全是白干。我曾经遇到一个客户，说“就运点小零件”，结果到现场一看，是两米长的钢轴，AGV的货架根本放不下。嗯，那项目最后改方案改了一个月。

29.1.2 输出需求文档

需求分析完成后，我会输出一份《AGV调度系统需求规格说明书》。里面至少包含：

  • 系统功能列表（必须、可选、未来）
  • 接口定义（与MES/WMS对接方式）
  • 性能指标（单机效率、系统吞吐量）
  • 异常处理场景（没电了、撞人了、网络断了）
我的经验：需求文档一定要让客户签字确认。不是不信任，而是防止后面扯皮。白纸黑字，大家都省心。

29.2 系统设计：画图比写代码更重要

需求明确了，接下来就是设计阶段。我个人习惯先画架构图，再写代码。架构图就像房子的设计图，你总不能边砌墙边想房间怎么布局吧？

29.2.2 关键模块设计

设计阶段，有几个模块我会特别关注：

  • 任务队列：用优先级队列还是FIFO？我建议用优先级+时间戳组合，紧急任务能插队，普通任务按顺序来
  • 路径规划：静态地图还是动态地图？静态的简单，但遇到障碍物就傻眼。动态的复杂，但更实用
  • 死锁检测：这个必须做。我见过一个项目，10台车在交叉口堵成一锅粥，最后只能人工去搬车
注意：设计阶段最容易犯的错误是“过度设计”。别想着一次把所有功能都做全。先跑通核心流程，再迭代优化。我见过太多项目死在“想太多”上。

29.3 开发实现：从原型到可运行

设计文档评审通过后，就进入开发阶段了。我的习惯是先做原型，再做完整功能。

29.3.1 搭建开发环境

开发环境我一般这样配：

组件 选型 说明
开发语言 Python / Java Python适合快速原型，Java适合生产环境
数据库 PostgreSQL + Redis PostgreSQL存持久数据，Redis做缓存和队列
通信中间件 RabbitMQ / MQTT RabbitMQ适合内部通信，MQTT适合与设备通信
仿真工具 自建仿真器 先跑仿真，再上真车

29.3.2 核心代码示例

这里我贴一段任务调度的核心逻辑。说白了就是：从队列里拿任务，分配给空闲的AGV，然后监控执行状态。

class TaskScheduler:
    def __init__(self):
        self.task_queue = PriorityQueue()
        self.agv_pool = {}  # agv_id -> AGV对象
        self.running_tasks = {}  # task_id -> 状态
    
    def assign_task(self, task):
        """分配任务给最合适的AGV"""
        # 1. 找空闲AGV
        idle_agvs = [agv for agv in self.agv_pool.values() 
                     if agv.status == 'idle']
        if not idle_agvs:
            # 没空闲的，就排队等着
            self.task_queue.put(task)
            return False
        
        # 2. 选最近的AGV（贪心策略）
        best_agv = min(idle_agvs, 
                       key=lambda agv: self.calc_distance(agv, task.start))
        
        # 3. 下发任务
        best_agv.execute(task)
        self.running_tasks[task.id] = 'running'
        return True
    
    def calc_distance(self, agv, target):
        """计算AGV到目标点的距离（简化版）"""
        # 实际项目中用A*算法算路径长度
        return abs(agv.x - target.x) + abs(agv.y - target.y)

这段代码看着简单，但实际项目中要考虑的东西多得多。比如：AGV电量不够怎么办？任务执行超时怎么办？多台AGV同时抢一个任务怎么办？

避坑指南：我曾经在任务分配时只考虑了距离最近，结果导致某台AGV一直在干活，其他AGV闲着。后来加了“负载均衡”策略，每台AGV的任务数不能超过阈值。这才解决了问题。

29.4 测试验证：仿真先行，真车后上

代码写完了，别急着上真车。我见过太多人，代码没测就直接跑真车，结果AGV撞墙、撞人、撞货架。嗯，那场面，惨不忍睹。

29.4.1 仿真测试

我会先搭一个仿真环境，模拟真实场景：

  • 地图仿真：把真实地图导入，包括站点、路径、障碍物
  • 车辆仿真：模拟AGV的运动学模型，包括加减速、转弯半径
  • 任务仿真：按真实节拍生成任务，看系统能不能扛住

仿真跑个几百轮，把各种异常场景都覆盖到。比如：突然加车、突然减车、网络延迟、任务取消。这些在仿真里跑通了，才能上真车。

29.4.2 真车调试

真车调试我一般分三步走：

  1. 单车调试：先让一台AGV跑通所有路径，确认导航、定位、通信都没问题
  2. 双车调试：两台车在交叉口交互，测试交通管制和避让逻辑
  3. 多车压力测试：逐步增加车辆数量，直到达到设计容量
注意：真车调试时，一定要有急停按钮。我有个同事，调试时AGV突然失控，直接冲向货架。还好急停按得快，不然货架倒了，损失几十万。

29.5 系统交付：不是代码跑起来就完事了

系统能跑了，但交付工作才刚刚开始。我总结了一个交付清单，每次照着做：

29.5.1 交付物清单

  • 可执行程序：打包好的调度系统，包括安装包和配置文件
  • 操作手册：图文并茂，告诉客户怎么用、怎么配、怎么排查问题
  • 运维手册：系统架构、日志位置、常见故障处理
  • 测试报告：仿真测试和真车测试的结果，证明系统满足需求
  • 源代码：如果合同要求，提供完整源码和编译说明

29.5.2 现场部署

部署到客户现场时，我会特别注意：

  • 网络环境：确认WiFi覆盖无死角，延迟在可接受范围内
  • 地图校准：现场地图和设计地图可能有偏差，需要微调
  • 人员培训：教会客户的操作员怎么使用系统，怎么处理常见异常

我记得有一次，系统部署完第二天就出问题了。客户说“AGV不动了”。我远程一看，原来是操作员把急停按钮按下去忘了复位。嗯，从那以后，我在培训时专门强调：急停按钮按了要复位，不然车不会动。

29.6 项目复盘：每次交付都是一次成长

项目交付后，我会做一次复盘。不是走形式，是真的把经验教训记下来。

复盘我会问自己几个问题：

  • 需求分析阶段，有没有遗漏关键场景？
  • 设计阶段，有没有过度设计或设计不足？
  • 开发阶段，有没有走弯路？代码质量如何？
  • 测试阶段，有没有漏测的异常场景？
  • 交付阶段，客户满意度如何？有没有遗留问题？

这些复盘结果，我会整理成文档，作为下一个项目的参考。说白了，经验就是这么一点点积累起来的。

总结一下：

从需求分析到系统交付，每个阶段都有它的坑。需求阶段别急着写代码，设计阶段别过度设计，开发阶段先做原型再迭代，测试阶段仿真先行真车后上，交付阶段培训到位文档齐全。

这套流程，我用了好几年，踩过坑也填过坑。希望能帮你少走一些弯路。
