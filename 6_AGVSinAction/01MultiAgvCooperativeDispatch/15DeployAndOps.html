15 部署与运维：Docker容器化、Kubernetes编排、日志监控

说实话，AGV调度系统写好了代码，只是万里长征走了一半。另一半，是怎么让它稳定地跑在服务器上，出了问题能快速定位。我见过太多项目，代码写得漂亮，一上线就崩，运维的人手忙脚乱。说白了，部署和运维才是真正考验系统成熟度的地方。

这一章，我重点聊聊三件事：Docker容器化、Kubernetes编排、日志监控。这三板斧用好了，你的调度系统就能扛住生产环境的压力。

15.1 为什么非要用Docker？

你想想看，AGV调度系统依赖的东西太多了：Java环境、Redis、MySQL、MQTT Broker……每台服务器的系统版本还不一样。以前我部署一个项目，光配环境就要半天，还经常出现「在我电脑上能跑」的尴尬。

Docker就是来解决这个问题的。它把应用和所有依赖打包成一个镜像，走到哪都能跑。我个人的习惯是，每个微服务都单独打包，互不干扰。

核心思路： 一次构建，到处运行。环境不一致的问题，从此消失。

15.1.1 编写Dockerfile

以我们的调度核心模块为例，一个典型的Dockerfile长这样：

# 基础镜像，选稳定的Alpine版本
FROM openjdk:11-jre-slim

# 维护者信息
LABEL maintainer="agv-team@example.com"

# 创建应用目录
WORKDIR /app

# 复制jar包
COPY target/scheduler-core-1.0.0.jar app.jar

# 暴露端口
EXPOSE 8080

# 启动命令
ENTRYPOINT ["java", "-jar", "app.jar", "--spring.profiles.active=prod"]

嗯，这里要注意：基础镜像别选太大的。我刚开始用full版本的JDK镜像，一个镜像1个多G，传输和部署都慢。换成slim版本后，体积直接降到200M以内。

15.1.2 多服务编排：docker-compose

调度系统不止一个服务。有调度核心、路径规划、状态监控、还有数据库和消息队列。一个个手动启动太累了。我用docker-compose把它们串起来：

version: '3.8'
services:
  # 调度核心
  scheduler-core:
    image: agv/scheduler-core:1.0.0
    ports:
      - "8080:8080"
    environment:
      - SPRING_PROFILES_ACTIVE=prod
    depends_on:
      - redis
      - mysql

  # 路径规划服务
  path-planner:
    image: agv/path-planner:1.0.0
    ports:
      - "8081:8081"
    depends_on:
      - redis

  # 状态监控服务
  monitor:
    image: agv/monitor:1.0.0
    ports:
      - "9090:9090"

  # 基础设施
  redis:
    image: redis:6.2-alpine
    ports:
      - "6379:6379"

  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: root123
      MYSQL_DATABASE: agv_scheduler

我曾经犯过一个错：depends_on只保证容器启动顺序，不保证服务就绪。比如MySQL容器启动了，但数据库还没初始化好，调度核心连上去就报错。后来我加了健康检查脚本，才彻底解决。

小技巧： 可以用 wait-for-it.sh 脚本，在启动主服务前等待依赖服务就绪。

15.2 Kubernetes：让调度系统真正「多机协同」

单机Docker跑几个服务没问题，但AGV调度系统一旦上了规模，几十台AGV同时跑，单机扛不住。这时候就需要Kubernetes（K8s）来编排了。

说白了，K8s就是一个「容器管家」。它能自动帮你做几件事：

  • 自动扩缩容：AGV任务多了，自动加实例；闲了，自动减实例。
  • 故障自愈：某个服务挂了，自动重启或迁移到其他机器。
  • 负载均衡：请求自动分发到健康的Pod上。
  • 滚动更新：更新版本时，逐个替换，不影响线上服务。

15.2.1 核心概念速览

刚开始接触K8s时，我被一堆概念搞晕了。其实核心就这几个：

概念 类比 作用
Pod 一个「豆荚」 最小部署单元，里面跑一个或多个容器
Deployment 「管家」 管理Pod的副本数、更新策略
Service 「门牌号」 给Pod提供稳定的访问入口
ConfigMap 「配置本」 存储配置信息，与镜像解耦

15.2.2 部署调度核心到K8s

我直接给你看一个生产级的Deployment配置：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: scheduler-core
  labels:
    app: scheduler-core
spec:
  # 副本数：至少2个，保证高可用
  replicas: 2
  selector:
    matchLabels:
      app: scheduler-core
  template:
    metadata:
      labels:
        app: scheduler-core
    spec:
      containers:
      - name: scheduler-core
        image: agv/scheduler-core:1.0.0
        ports:
        - containerPort: 8080
        # 资源限制：防止某个服务占光所有资源
        resources:
          requests:
            memory: "512Mi"
            cpu: "500m"
          limits:
            memory: "1Gi"
            cpu: "1000m"
        # 健康检查
        livenessProbe:
          httpGet:
            path: /actuator/health
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /actuator/health
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 5
注意： 资源限制一定要配！我见过一个项目没配limits，结果某个服务内存泄漏，把整个集群搞崩了。配了limits，最多杀掉那个Pod，不影响其他服务。

15.2.3 暴露服务：Ingress

Pod的IP是动态的，不能直接对外暴露。我们用Service和Ingress来解决：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ags-scheduler-ingress
spec:
  rules:
  - host: scheduler.agv.internal
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: scheduler-core-service
            port:
              number: 8080

这样，外部通过scheduler.agv.internal/api就能访问到调度核心了。内部服务之间，直接用Service名通信，K8s自带的DNS会解析。

15.3 日志监控：出了问题别慌

系统跑起来之后，最怕什么？怕出问题找不到原因。日志监控就是你的「黑匣子」和「仪表盘」。

15.3.1 日志收集：ELK三件套

我推荐用ELK（Elasticsearch + Logstash + Kibana）这套组合。流程很简单：

  1. Filebeat：部署在每个节点上，收集容器日志。
  2. Logstash：解析日志格式，过滤无用信息。
  3. Elasticsearch：存储和索引日志。
  4. Kibana：可视化查询。

我曾经遇到一个棘手的问题：AGV偶尔会丢失任务。查了几天代码没找到原因。后来在Kibana里用level: ERROR AND message: "task_timeout"一搜，发现是网络抖动导致MQTT消息重发，任务被重复处理了。没有日志监控，这种偶发问题根本没法定位。

15.3.2 监控告警：Prometheus + Grafana

日志是事后分析，监控是实时预警。我习惯用Prometheus采集指标，Grafana展示仪表盘。

调度系统需要关注的核心指标：

指标 说明 告警阈值
任务处理延迟 从任务下发到AGV开始执行的时间 > 500ms 告警
AGV在线率 当前在线AGV数量 / 总AGV数量 < 90% 告警
CPU使用率 调度核心的CPU负载 > 80% 持续5分钟
内存使用率 JVM堆内存使用情况 > 85% 告警

在Grafana里，我会把AGV的实时位置、任务队列长度、系统吞吐量做成一个大屏。运维人员扫一眼就知道系统状态。

我的经验： 告警别设得太敏感。刚开始我把CPU超过50%就告警，结果半夜被电话吵醒，一看只是正常的任务高峰。后来改成「持续5分钟超过80%」才告警，清净多了。
