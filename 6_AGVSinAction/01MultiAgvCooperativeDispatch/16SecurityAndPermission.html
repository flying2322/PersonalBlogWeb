16 安全与权限：用户认证、角色管理、操作审计

说实话，做AGV调度系统最容易被忽视的，就是安全模块。

我见过不少团队，先把调度跑通了，权限什么的后面再说。结果呢？现场操作工误点了“清空任务队列”，整个仓库的AGV全停了。还有一次，一个实习生不小心删了地图数据，恢复花了两天。

所以我的习惯是——安全模块，从第一天就搭进去。哪怕功能简单点，骨架要在。

16.1 用户认证：谁在操作？

认证，说白了就是确认“你是谁”。

AGV调度系统里，用户认证不能只靠密码。为什么？因为现场环境复杂，操作员可能戴着脏手套，或者屏幕很小，输密码不方便。

16.1.1 认证方式选择

我个人推荐至少支持两种方式：

  • 密码认证：基础保障，密码要加密存储（别用MD5，用bcrypt或Argon2）
  • 扫码认证：操作员用工牌上的二维码扫一下，系统自动登录

我在项目中遇到过一个问题：操作员为了省事，把密码贴在显示器上。后来我们强制要求密码+动态验证码双因素认证，才把这个问题压下去。

核心原则：认证信息绝不在前端明文传输。用HTTPS + Token机制。

16.1.2 Token管理

用户登录后，系统签发一个JWT Token。我习惯把Token的有效期设短一点（比如2小时），配合Refresh Token使用。

// 伪代码：生成Token
function generateToken(userId, role) {
    return jwt.sign(
        { userId, role, exp: Math.floor(Date.now() / 1000) + 7200 },
        SECRET_KEY
    );
}

小技巧：Token里不要存敏感信息，比如密码。只存用户ID和角色就够了。

16.2 角色管理：能做什么？

认证完了，接下来就是授权。不同的人，权限不一样。

你想想看，一个仓库管理员，需要能修改AGV的路径规划算法吗？不需要。他只需要看状态、发任务就够了。

16.2.1 角色设计

我一般把角色分成四级：

角色 权限范围 典型用户
查看者 只能看实时状态、历史记录 产线班组长
操作员 查看 + 下发任务、暂停/恢复AGV 仓库操作工
调度员 操作员权限 + 修改地图、调整策略 调度主管
管理员 全部权限，包括用户管理、系统配置 IT运维

嗯，这里要注意：角色不要分得太细。我见过有人分了8个角色，结果没人记得住自己该用哪个。4个刚刚好。

16.2.2 权限控制粒度

角色是粗粒度，权限是细粒度。我习惯用“资源+操作”的方式定义权限：

// 权限定义示例
permissions = {
    "agv:control": ["start", "stop", "pause"],
    "map:edit": ["add_node", "delete_node", "modify_path"],
    "task:manage": ["create", "cancel", "reassign"],
    "user:admin": ["add_user", "delete_user", "reset_password"]
}

每个角色绑定一组权限。这样灵活，也容易扩展。

避坑指南：我曾经把权限写死在代码里，结果客户要加一个新角色，我得改代码重新部署。后来改成数据库配置，客户自己就能配了。

16.3 操作审计：干了什么？

审计，就是记录“谁在什么时间做了什么”。

为什么重要？出了事故要追责。比如AGV撞了货架，你得查出来是操作员误操作，还是系统bug。

16.3.1 审计日志内容

每条审计日志，至少包含：

  • 用户ID：谁操作的
  • 操作时间：精确到毫秒
  • 操作类型：登录、下发任务、修改地图、删除数据等
  • 操作对象：具体对哪个AGV、哪个任务、哪个节点
  • 操作结果：成功/失败 + 失败原因
  • IP地址：从哪台电脑操作的
// 审计日志示例
{
    "userId": "zhangsan",
    "timestamp": "2025-03-15 14:23:45.123",
    "action": "TASK_CANCEL",
    "target": "task_1024",
    "result": "success",
    "ip": "192.168.1.100",
    "detail": "取消任务：从A01到B05的运输任务"
}

16.3.2 日志存储与查询

审计日志不能存在内存里，一重启就没了。我建议：

  • 实时写入数据库：用单独的审计表，别跟业务数据混在一起
  • 定期归档：超过3个月的日志，压缩后存到冷存储
  • 支持检索：按用户、时间、操作类型快速过滤

我的习惯：审计日志只增不删。就算要清理，也是物理归档，不能逻辑删除。否则审计就失去了意义。

16.5 落地建议

最后，给几个实际落地的建议：

  1. 别追求完美：一开始不用把所有权限都做出来。先做“管理员”和“操作员”两个角色，后面再细化。
  2. 审计日志要防篡改：我习惯用日志签名，每条日志带上上一条的哈希值。这样如果有人改日志，一眼就能看出来。
  3. 权限检查要快：每次操作都查数据库太慢了。把用户的权限缓存到Redis里，过期时间设短一点（比如5分钟）。
  4. 默认拒绝：没明确授权的操作，一律拒绝。别搞“默认允许”，那是给自己挖坑。

再强调一次：安全不是功能，是习惯。从第一行代码开始，就把认证、授权、审计写进去。后面再补，成本高得多。
