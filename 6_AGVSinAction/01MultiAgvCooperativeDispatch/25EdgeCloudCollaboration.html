25 边缘计算与云端协同：本地决策、云端优化、混合架构

说到AGV调度，很多朋友一上来就想着把所有计算都扔到云端。嗯，这个想法很美好，但现实往往很骨感。我在几个大型仓储项目里吃过亏，才真正理解了「边缘+云端」这套混合架构有多重要。

说白了，AGV调度对实时性的要求极高。你想想看，一辆AGV在巷道里以1.5m/s的速度行驶，如果等数据传到云端再返回指令，黄花菜都凉了。我见过一个项目，纯云端调度，网络抖动一下，三台车就在路口撞上了——虽然装了防撞雷达，但效率直接腰斩。

为什么需要边缘计算？

边缘计算的核心价值就四个字：就地决策。

AGV车身上搭载的工控机，或者部署在车间里的边缘服务器，可以处理那些对延迟敏感的任务。比如：

  • 路径跟踪：实时调整舵轮角度，保证AGV沿着规划路径走
  • 避障决策：遇到临时障碍物，立即停车或绕行
  • 交通管制：在交叉路口，判断谁先通过
  • 状态监控：电池电量、电机温度、轮子磨损等

这些任务如果都走云端，延迟通常在50-200ms，而边缘计算可以做到5ms以内。我个人习惯把延迟超过30ms就算作「不可接受」，尤其是在多车密集作业的场景下。

核心原则：边缘负责「快」，云端负责「全」。边缘做不了的事，才交给云端。

云端优化的价值在哪？

云端虽然慢，但它有全局视野。边缘节点只能看到自己周围几十米的情况，而云端能看到整个仓库、整个园区、甚至跨厂区的所有AGV。

云端主要做三件事：

  1. 全局路径规划：基于所有AGV的任务、位置、电量，计算出最优的任务分配和路径方案
  2. 交通流预测：分析历史数据，预测哪些路段会拥堵，提前调整
  3. 模型训练与更新：用机器学习算法优化调度策略，然后把模型下发给边缘节点

我记得有个项目，刚开始所有AGV都是各自为政，边缘节点只做局部路径规划。结果到了下午高峰期，仓库北区堵成一锅粥。后来上了云端优化，每5分钟重新计算一次全局路径，把任务分散到不同区域，拥堵率下降了70%。

边缘节点上的代码长啥样？

我拿一个简单的交通管制逻辑举例。边缘节点收到云端下发的全局路径后，在本地执行实时调度：

# 边缘节点上的交通管制模块（Python伪代码）
class EdgeTrafficController:
    def __init__(self, zone_id):
        self.zone_id = zone_id
        self.active_agvs = {}  # agv_id -> {position, speed, path}
        self.reserved_segments = {}  # segment_id -> agv_id
    
    def request_pass(self, agv_id, segment_id):
        """AGV请求通过某个路段"""
        if segment_id in self.reserved_segments:
            # 路段已被占用，拒绝或排队
            return {"status": "wait", "queue_position": 3}
        else:
            self.reserved_segments[segment_id] = agv_id
            return {"status": "granted", "speed_limit": 1.2}
    
    def release_segment(self, agv_id, segment_id):
        """AGV通过后释放路段"""
        if self.reserved_segments.get(segment_id) == agv_id:
            del self.reserved_segments[segment_id]
    
    def sync_to_cloud(self):
        """定期将本地状态上报云端"""
        # 压缩数据，只上报关键信息
        report = {
            "zone": self.zone_id,
            "agv_count": len(self.active_agvs),
            "congestion_level": self._calc_congestion(),
            "incidents": self._get_recent_incidents()
        }
        # 通过MQTT发送
        mqtt_client.publish("edge/status", json.dumps(report))

避坑指南：我曾经在边缘节点上直接跑完整的A*路径规划，结果CPU飙到90%，AGV反应迟钝。后来改成只做局部重规划（比如只规划前方50米），全局规划全交给云端。记住：边缘节点不是万能的，别让它干重活。

断网怎么办？

这是混合架构里最容易被忽视的问题。你想想看，仓库里信号死角多，Wi-Fi偶尔断一下很正常。如果边缘节点完全依赖云端，断网就等于瘫痪。

我的做法是：边缘节点必须支持「离线自治」模式。

具体来说：

  • 云端会提前下发未来30分钟的「预测性调度方案」到边缘节点
  • 断网后，边缘节点按照这个方案继续执行
  • 如果遇到方案里没覆盖的情况（比如突发障碍物），边缘节点用本地规则引擎做决策
  • 网络恢复后，边缘节点把离线期间的数据补传到云端，云端重新优化后续方案

我曾经在一个项目里测试过，断网15分钟，边缘节点靠着本地缓存和规则引擎，硬是没让AGV停过一台车。当然，效率下降了大概20%，但至少没停产。

数据同步的节奏怎么定？

这里有个表格，是我在实际项目中总结出来的经验值：

数据类型 同步方向 同步频率 说明
AGV实时位置 边缘 → 云端 200ms 用于云端全局监控和预测
任务状态变更 边缘 → 云端 事件触发 任务完成、失败、取消时上报
全局路径规划 云端 → 边缘 5分钟 云端定期下发优化后的路径
交通管制规则 云端 → 边缘 30分钟 规则变更不频繁，可批量下发
设备固件/模型 云端 → 边缘 按需 版本升级时下发，支持断点续传

注意：别把所有数据都实时同步。我见过有人把AGV的每个传感器读数都往云端传，结果带宽被占满，关键指令反而延迟了。边缘节点要做数据预处理，只上传「有价值」的信息。

混合架构的收益到底有多大？

我直接说数据吧。在一个200台AGV的仓库项目里，纯云端调度时，平均任务响应时间是180ms，高峰期拥堵概率是15%。上了混合架构后：

  • 边缘决策延迟降到8ms
  • 拥堵概率降到3%以下
  • 云端负载降低了60%（因为大部分计算在边缘消化了）
  • 断网场景下，系统可用性从0%提升到95%

说白了，混合架构不是锦上添花，而是大规模AGV调度的必选项。你想想看，如果只有100台车，纯云端也许还能凑合。但到了500台、1000台，没有边缘计算兜底，系统根本跑不起来。

嗯，这套架构我前后迭代了三个版本才稳定下来。如果你正在搭建自己的调度系统，建议从边缘层开始，先把本地决策做扎实了，再逐步接入云端优化。别一上来就搞大而全的云端方案——我吃过这个亏，希望你不用再吃一次。
