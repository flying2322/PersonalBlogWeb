8 通信协议设计：TCP/UDP、MQTT、REST API、自定义协议

通信协议这东西，说白了就是AGV之间、AGV和调度系统之间「怎么说话」的问题。我刚开始做多车调度时，觉得协议嘛，能传数据就行。结果第一次联调，三台车在交叉路口撞在一起——不是因为算法不对，而是因为消息传慢了。嗯，从那以后，我对协议设计再也不敢马虎。

今天咱们就把AGV调度中常用的几种协议捋一遍。每种协议都有它的脾气，选对了事半功倍，选错了...你想想看，让一个急性子的TCP去干广播的活，那不是找罪受吗？

核心观点：没有最好的协议，只有最合适的场景。AGV调度系统往往是多协议混合使用的。

8.1 TCP/UDP：实时控制的左膀右臂

先说说TCP和UDP。这两个是传输层的老祖宗了，AGV调度里几乎绕不开。

TCP，面向连接、可靠传输。我习惯用它来做AGV的实时控制指令下发。比如「AGV-03，立刻停止！前方有障碍物」，这种指令丢不得，也乱不得。TCP的重传机制和顺序保证，在这里就是保命符。

UDP呢，无连接、速度快，但不保证到达。我一般在广播AGV的实时位置时用UDP。为什么？因为位置信息每秒刷10次甚至20次，丢一帧无所谓，下一帧马上补上。你想想看，如果用TCP去传位置，万一丢包了还要重传，反而造成延迟堆积，车都跑过路口了才收到上一帧的位置，那才叫坑。

我的经验：在同一个局域网内，AGV数量少于20台时，TCP完全够用。超过50台，建议把高频状态数据切到UDP上，否则TCP的连接管理和重传开销会让调度服务器CPU飙升。我曾经在一个项目里见过，60台AGV全部用TCP长连接，结果调度服务器网卡先扛不住了。

特性 TCP UDP
连接方式 面向连接 无连接
可靠性 可靠（重传+确认） 不可靠（尽力而为）
适用场景 指令下发、任务分配 位置广播、心跳包
AGV数量建议 ≤50台 无限制

8.2 MQTT：让消息飞一会儿

MQTT这几年在工业物联网里火得不行。它基于发布/订阅模式，说白了就是有个消息中间件（Broker），AGV和调度系统都连到Broker上，谁想发消息就发到某个「主题」，谁想收消息就订阅这个主题。

我个人特别喜欢MQTT的一点是——解耦。AGV不需要知道调度系统在哪，调度系统也不需要知道AGV的IP。大家只认主题。比如主题 agv/status/03 就是3号AGV的状态，调度系统订阅 agv/status/# 就能收到所有AGV的状态。

MQTT的QoS（服务质量）有三个级别：

  • QoS 0：最多发一次，丢了不管。适合位置广播。
  • QoS 1：至少发一次，可能重复。适合状态上报。
  • QoS 2：恰好发一次，最可靠但最慢。适合任务指令。

注意：MQTT的Broker是单点故障风险。我曾经在一个仓库项目里，Broker服务器宕机了，所有AGV瞬间失联。后来我们做了Broker集群+本地缓存，AGV在断连时自动切换到本地决策模式，才算彻底解决。

8.3 REST API：管理员的瑞士军刀

REST API，说白了就是HTTP接口。它不适合做实时控制，因为HTTP的请求-响应模式太慢了。但它特别适合做管理操作，比如：

  • 查询AGV列表和状态
  • 下发任务（非实时）
  • 修改配置参数
  • 查看历史轨迹

我一般把REST API放在调度系统的管理后台和第三方系统对接上。比如MES系统要下发一个生产任务给AGV，走REST API就很合适——任务不要求毫秒级响应，但要求接口清晰、文档完善。

// 一个典型的REST API示例：下发任务给AGV
POST /api/v1/tasks
{
  "agv_id": "AGV-05",
  "task_type": "transport",
  "source": "A-12",
  "destination": "B-08",
  "priority": 1,
  "deadline": "2025-06-15T14:30:00Z"
}

// 响应
{
  "task_id": "TASK-20250615-0037",
  "status": "accepted",
  "estimated_time": 120
}

小建议：REST API一定要做版本控制，比如 /api/v1/、/api/v2/。我见过一个项目，API升级后老版本直接废弃，结果第三方系统没来得及更新，整个生产线停了半天。血的教训。

8.4 自定义协议：性能至上的选择

什么时候需要自定义协议？当标准协议满足不了你的性能要求时。

举个例子，AGV的底层运动控制，要求指令延迟小于5毫秒。TCP的握手和重传太慢，UDP又不可靠。怎么办？自己造一个协议。

我做过一个自定义协议，结构很简单：

| 帧头(2B) | 长度(1B) | 命令字(1B) | 数据区(NB) | 校验(2B) | 帧尾(2B) |
| 0xAA 0x55 |   N+6    |  0x01~0xFF |  实际数据   |  CRC16   | 0x0D 0x0A |

这个协议的特点：

  • 帧头帧尾做同步，防止粘包
  • 命令字区分不同指令（停止、前进、转弯等）
  • CRC校验保证数据完整性
  • 总长度不超过256字节，适合嵌入式处理

实际测试下来，在100M局域网内，端到端延迟稳定在2-3毫秒。比TCP快了一个数量级。

但是！自定义协议是把双刃剑。它性能好，但调试困难、可维护性差。我建议只在以下情况使用：

  • 延迟要求 < 10ms
  • 嵌入式设备资源受限（内存< 64KB）
  • 需要透传特殊数据（如激光雷达原始数据）

其他情况，能用标准协议就用标准协议。别为了炫技给自己挖坑。

8.5 协议选型：我的决策框架

说了这么多，到底怎么选？我一般按这个思路来：

  1. 先看延迟要求：< 10ms 考虑自定义协议或UDP；10-100ms 考虑TCP；> 100ms 考虑MQTT或REST API。
  2. 再看数据量：高频小数据（位置、状态）用UDP或MQTT QoS 0；低频重要数据（任务、指令）用TCP或MQTT QoS 2。
  3. 最后看系统规模：10台以内随便选；10-50台推荐TCP+MQTT混合；50台以上必须考虑UDP和MQTT的扩展性。

实际项目中，我常用的组合是：TCP做实时控制 + MQTT做状态上报 + REST API做管理配置。这个组合在大多数场景下都能打，既保证了实时性，又兼顾了可维护性。

一句话总结：协议设计没有银弹。理解每种协议的脾气，根据场景灵活搭配，才是AGV调度系统架构师的功力所在。
