14 系统集成测试：接口测试、压力测试、稳定性测试

系统集成测试，说白了就是把各个模块拼在一起，看看它们能不能好好配合。AGV调度系统不是单打独斗的，它要和MES、WMS、RCS、PLC等一堆系统打交道。我见过太多项目，每个模块单独跑都没问题，一联调就崩了。

为什么会这样？因为接口协议没对齐、数据格式不匹配、并发压力扛不住。嗯，这一章我们就来聊聊怎么把这些坑填上。

14.1 接口测试：打通数据通道

接口测试是集成测试的第一步。AGV调度系统对外暴露的接口，主要是RESTful API和WebSocket。我个人习惯，先做接口功能验证，再做异常场景覆盖。

14.1.1 接口清单梳理

先列清楚有哪些接口要测。我一般用表格来管理：

接口名称 方法 路径 输入参数 预期输出
下发任务 POST /api/v1/task 任务ID、起点、终点、优先级 任务状态、预计执行时间
查询AGV状态 GET /api/v1/agv/{id} AGV编号 位置、电量、任务状态
取消任务 DELETE /api/v1/task/{id} 任务ID 取消结果
实时位置推送 WebSocket /ws/agv/position 订阅AGV列表 实时坐标流

接口测试不能只测正常流程。我曾经遇到过一个坑：MES系统下发任务时，把起点和终点字段写反了。我们的调度系统没做校验，结果AGV直接往反方向跑。所以，异常输入、边界值、空值、超长字符串，都得测一遍。

核心原则：接口测试要覆盖三类场景——正常流程、异常输入、超时重试。缺一不可。

14.1.2 接口自动化测试脚本

手动测接口太慢了，我习惯用Python写自动化脚本。下面是一个简单的测试框架示例：

import requests
import json
import time

class AGVInterfaceTest:
    def __init__(self, base_url):
        self.base_url = base_url
        self.session = requests.Session()
    
    def test_create_task(self):
        """测试下发任务接口"""
        url = f"{self.base_url}/api/v1/task"
        payload = {
            "task_id": "TASK_001",
            "start_point": "A01",
            "end_point": "B03",
            "priority": 1
        }
        resp = self.session.post(url, json=payload)
        assert resp.status_code == 200
        data = resp.json()
        assert data["status"] == "accepted"
        print(f"[PASS] 任务创建成功: {data}")
    
    def test_create_task_invalid_params(self):
        """测试异常参数"""
        url = f"{self.base_url}/api/v1/task"
        # 缺少必填字段
        payload = {"task_id": "TASK_002"}
        resp = self.session.post(url, json=payload)
        assert resp.status_code == 400
        print(f"[PASS] 异常参数校验通过: {resp.text}")
    
    def run_all(self):
        self.test_create_task()
        self.test_create_task_invalid_params()
        print("所有接口测试通过")

if __name__ == "__main__":
    tester = AGVInterfaceTest("http://localhost:8080")
    tester.run_all()

小技巧：接口测试最好集成到CI/CD流水线里。每次代码提交后自动跑一遍，能提前发现接口不兼容的问题。我在项目中吃过这个亏——开发改了接口字段名，测试环境没同步，上线直接炸了。

14.2 压力测试：看看系统能扛多少

压力测试，说白了就是给系统上强度。AGV调度系统在高峰期可能同时处理几百台AGV的任务调度，接口请求量会暴增。扛不住？那就等着现场报警吧。

14.2.1 压测指标定义

我个人习惯，先定好压测目标：

  • QPS（每秒查询数）：目标值500，峰值1000
  • 响应时间：95%的请求在200ms以内
  • 错误率：低于0.1%
  • CPU/内存：CPU不超过70%，内存不超过80%

你想想看，如果调度接口响应时间超过1秒，AGV在路口等指令，后面的车全堵住了。这就是连锁反应。

14.2.2 使用JMeter进行压测

JMeter是我常用的压测工具。下面是一个典型的压测配置：

# JMeter测试计划配置要点
1. 线程组设置：
   - 线程数：100（模拟100个并发用户）
   - Ramp-Up时间：10秒（逐步增加负载）
   - 循环次数：100（每个用户发100次请求）

2. HTTP请求默认值：
   - 协议：http
   - 服务器：192.168.1.100
   - 端口：8080
   - 内容编码：UTF-8

3. 监听器：
   - 聚合报告（查看平均响应时间、吞吐量）
   - 图形结果（观察趋势）
   - 查看结果树（调试用）

压测过程中，我会重点关注几个点：

  • 响应时间有没有突然飙升？那可能是线程池满了
  • 错误率是不是在增加？可能是数据库连接池不够
  • CPU有没有打满？看看是不是死循环或者GC频繁

注意：压测一定要在独立环境做，别在生产环境搞。我曾经见过有人直接在线上压测，结果把数据库打挂了，整个仓库停了半小时。嗯，那场面...很酸爽。

14.2.3 压测结果分析

压测完不是看一眼报告就完事了。我会把结果和指标对比，找出瓶颈：

场景 QPS 平均响应时间 95%响应时间 错误率 结论
单接口压测（任务下发） 800 45ms 120ms 0.02% 通过
混合场景（任务+查询+取消） 600 85ms 210ms 0.05% 接近阈值
极限压测（持续10分钟） 1200 320ms 890ms 2.3% 不通过，需优化

看到极限压测不通过，我就知道问题出在哪了。数据库连接池太小，导致请求排队。把连接池从20调到50，重新压测，QPS上去了，响应时间也降下来了。

14.3 稳定性测试：跑它个三天三夜

稳定性测试，说白了就是看系统能不能长时间不出问题。AGV调度系统是7×24小时运行的，不能三天两头重启。我见过一个项目，系统跑48小时就内存溢出，最后发现是日志框架有内存泄漏。

14.3.1 稳定性测试方案

我个人习惯，稳定性测试至少跑72小时。测试方案包括：

  • 持续负载：模拟70%的峰值负载，持续运行
  • 周期性波动：每4小时模拟一次高峰，持续30分钟
  • 异常注入：随机断掉某个AGV的连接，看系统能否自动恢复
  • 数据积累：持续产生任务记录，观察数据库增长对性能的影响

为什么要模拟周期性波动？因为实际场景中，上午10点和下午3点是出货高峰期，其他时间负载较低。系统要能扛住这种节奏。

14.3.2 监控指标与告警

稳定性测试期间，我会盯着几个关键指标：

监控项 正常范围 告警阈值 处理方式
JVM堆内存 使用率<70% >85%持续5分钟 检查GC日志，排查内存泄漏
数据库连接数 活跃连接<30 >50 检查慢查询，优化SQL
任务队列长度 <100 >500 检查调度算法，增加消费者
AGV心跳超时率 <0.1% >1% 检查网络，排查AGV端问题

经验之谈：稳定性测试最容易发现内存泄漏和线程泄漏。我建议在测试前后各做一次堆转储（heap dump），对比分析对象增长情况。有一次我发现一个HashMap只增不减，原来是缓存没设过期时间。

14.3.3 稳定性测试报告

测试结束后，我会输出一份详细的报告。报告里要有：

  • 测试时间、环境、负载模型
  • 关键指标的趋势图（内存、CPU、响应时间）
  • 异常事件记录（时间点、现象、根因）
  • 优化建议（按优先级排序）

举个例子，有一次稳定性测试发现，系统运行到第48小时，任务下发接口的响应时间从50ms涨到了500ms。查了半天，发现是数据库里任务表的数据量太大，索引失效了。解决方案很简单：加一个定时任务，每天凌晨清理历史数据。

14.4 知识体系总览

下面这张图，是我对系统集成测试的整体理解。你可以把它当作一个检查清单：

这三类测试，环环相扣。接口测试保证功能正确，压力测试保证性能达标，稳定性测试保证长期可靠。少一个都不行。

最后说一句：测试不是走过场，而是为了发现问题。我见过太多项目，测试报告写得漂漂亮亮，上线第一天就出问题。为什么？因为测试环境和生产环境不一样，数据量不一样，并发模型也不一样。所以，尽量让测试环境接近生产环境，别偷懒。
