13 仿真环境搭建：基于Python的仿真框架、事件驱动模拟

做AGV调度系统，最怕什么？

怕算法写好了，一上线就撞车。怕逻辑跑通了，实际场景里死锁。

所以，仿真环境不是「锦上添花」，而是「保命工具」。今天我们就来搭一套基于Python的仿真框架，核心思想是事件驱动模拟。这套东西，我在好几个项目里都用过，效果不错。

13.1 为什么选事件驱动？

你可能见过一些仿真工具，用的是时间步长法——每过0.1秒，把所有AGV的位置更新一遍。听起来挺合理，对吧？

但实际跑起来，问题就来了：

  • 大部分时间，AGV都在空跑，CPU全浪费了
  • 遇到紧急事件（比如碰撞预警），响应不够及时
  • 仿真速度慢，跑一天的真实场景要等好久

事件驱动就不一样了。它只关心「什么时候发生了什么」，没事件的时候就跳过。说白了，就是「没事别吵我，有事叫我」。

核心思想：仿真时钟不是均匀跳动的，而是从一个事件跳到下一个事件。两个事件之间，系统状态不变。

13.2 框架整体设计

我个人习惯把仿真框架拆成三层：

  1. 核心引擎层——管理事件队列、推进仿真时钟
  2. 实体层——AGV、地图、任务、路径等对象
  3. 调度逻辑层——你的算法、避碰策略、任务分配

这三层各司其职，互不干扰。我在项目中遇到过最头疼的事，就是有人把调度逻辑写进了AGV类里，结果改个参数要改三个地方。嗯，千万别这么干。

13.3 核心引擎实现

先看最核心的部分——事件队列和仿真时钟。代码其实不长，但逻辑要清晰。

import heapq
from dataclasses import dataclass, field
from typing import Any

@dataclass(order=True)
class Event:
    time: float          # 事件发生时间
    priority: int = 0    # 同时间下的优先级
    data: Any = field(compare=False)  # 事件数据

class SimEngine:
    def __init__(self):
        self._queue = []      # 事件队列（最小堆）
        self._time = 0.0      # 当前仿真时间
        self._running = True

    def schedule(self, delay: float, event_data, priority=0):
        """在 delay 秒后插入一个事件"""
        event_time = self._time + delay
        heapq.heappush(self._queue, Event(event_time, priority, event_data))

    def run(self):
        while self._queue and self._running:
            event = heapq.heappop(self._queue)
            self._time = event.time
            self._process(event)

    def _process(self, event):
        """子类重写这个方法，处理具体事件"""
        raise NotImplementedError

    @property
    def current_time(self):
        return self._time

    def stop(self):
        self._running = False

你想想看，这段代码的核心就两个操作：schedule 往队列里塞事件，run 不断取出最早的事件处理。用最小堆实现，取事件的时间复杂度是 O(log n)，跑几万个事件都不带卡的。

小技巧：我习惯在事件里加一个 priority 字段。比如同一时刻既有「AGV到达」又有「任务下发」，我会让「AGV到达」优先级更高，避免逻辑冲突。

13.4 实体层：AGV与地图

有了引擎，我们得往里面塞「演员」。AGV和地图就是最基本的实体。

@dataclass
class Position:
    x: float
    y: float

class AGV:
    def __init__(self, agv_id: str, start_pos: Position, speed: float = 1.0):
        self.id = agv_id
        self.pos = start_pos
        self.speed = speed
        self.status = "idle"  # idle, moving, loading, unloading
        self.path = []        # 待走路径

    def move_to(self, target: Position, engine: SimEngine):
        """向目标位置移动，生成到达事件"""
        distance = ((target.x - self.pos.x)**2 + (target.y - self.pos.y)**2)**0.5
        travel_time = distance / self.speed
        self.status = "moving"
        engine.schedule(travel_time, {"type": "arrive", "agv_id": self.id, "pos": target})

class Map:
    def __init__(self):
        self.obstacles = []   # 障碍物列表
        self.stations = {}    # 站点字典 {station_id: Position}

    def is_path_clear(self, start: Position, end: Position) -> bool:
        """检查两点之间是否有障碍物（简化版）"""
        # 实际项目中这里要做线段与多边形的碰撞检测
        return True

这里有个细节：move_to 方法不是真的让AGV一步步走，而是直接计算到达时间，然后往事件队列里塞一个「到达事件」。这就是事件驱动的精髓——中间过程全部跳过，只关心结果。

注意：这种「跳步」方式在简单场景下没问题。但如果要模拟AGV的加减速、转弯半径，就得把路径拆成多个小段，每段生成一个事件。我曾经在这个坑里摔过——仿真结果和实际差了30%，就是因为忽略了加速度。

13.5 调度逻辑层：让AGV动起来

现在，我们把引擎和实体串起来。写一个具体的仿真类：

class AGVSimulation(SimEngine):
    def __init__(self):
        super().__init__()
        self.agvs = {}
        self.map = Map()
        self.task_queue = []

    def add_agv(self, agv: AGV):
        self.agvs[agv.id] = agv

    def add_task(self, task: dict):
        """添加一个任务：{'agv_id': 'A1', 'target': Position(10,20)}"""
        self.task_queue.append(task)
        # 立即调度任务分配事件
        self.schedule(0, {"type": "assign_task"})

    def _process(self, event):
        if event.data["type"] == "arrive":
            self._handle_arrive(event.data)
        elif event.data["type"] == "assign_task":
            self._handle_assign(event.data)
        elif event.data["type"] == "collision_check":
            self._handle_collision_check(event.data)

    def _handle_arrive(self, data):
        agv = self.agvs[data["agv_id"]]
        agv.pos = data["pos"]
        agv.status = "idle"
        print(f"[T={self.current_time:.2f}] AGV {agv.id} 到达 ({agv.pos.x:.1f}, {agv.pos.y:.1f})")
        # 到达后检查是否有新任务
        self.schedule(0, {"type": "assign_task"})

    def _handle_assign(self, data):
        # 简化版：给空闲AGV分配任务
        for agv in self.agvs.values():
            if agv.status == "idle" and self.task_queue:
                task = self.task_queue.pop(0)
                agv.move_to(task["target"], self)
                print(f"[T={self.current_time:.2f}] AGV {agv.id} 开始执行任务，目标 ({task['target'].x:.1f}, {task['target'].y:.1f})")

    def _handle_collision_check(self, data):
        # 碰撞检测逻辑（略）
        pass

跑一下看看效果：

sim = AGVSimulation()
sim.add_agv(AGV("A1", Position(0, 0)))
sim.add_agv(AGV("A2", Position(5, 0)))

sim.add_task({"agv_id": "A1", "target": Position(10, 0)})
sim.add_task({"agv_id": "A2", "target": Position(15, 0)})

sim.run()

输出大概是这样：

[T=0.00] AGV A1 开始执行任务，目标 (10.0, 0.0)
[T=0.00] AGV A2 开始执行任务，目标 (15.0, 0.0)
[T=10.00] AGV A1 到达 (10.0, 0.0)
[T=10.00] AGV A2 到达 (15.0, 0.0)

你看，仿真时钟直接从0跳到了10，中间没有逐帧计算。这就是事件驱动的威力——快、准、省资源。

13.6 避坑指南与扩展思路

框架搭好了，但真正用起来，有几个坑你得注意：

  • 事件无限循环——比如「到达」事件又触发了「移动」事件，而「移动」又生成「到达」，如果不加条件，队列会无限膨胀。我建议每个事件处理时都检查一下状态变化。
  • 时间精度问题——浮点数比较时，别用 ==，用 abs(t1 - t2) < 1e-6。否则两个事件明明该同时发生，却因为浮点误差被分开了。
  • 死锁检测——多AGV场景下，很容易出现互相等待。我习惯在仿真里加一个「看门狗」事件，每隔一段时间检查所有AGV的状态，如果长时间没有进展，就触发死锁恢复逻辑。

扩展思路：这个框架稍加改造，就能支持：

  • 可视化回放（把每个事件的状态快照存下来）
  • 分布式仿真（多个引擎通过消息队列通信）
  • 硬件在环仿真（用真实AGV的通信协议替换模拟逻辑）

好了，今天的框架就搭到这里。代码量不大，但结构清晰，后续加什么功能都不费劲。你拿回去跑一跑，有问题随时调。
