2 调度系统架构设计：集中式、分布式、混合式架构对比

聊到AGV调度系统的架构，我见过不少团队一上来就选型，结果做到一半发现扛不住，又回头重构。说白了，架构选型这事儿，没有银弹。你得先搞清楚自己的场景：多少台车？任务密度多大？对实时性要求有多变态？

今天我就把三种主流架构——集中式、分布式、混合式——掰开揉碎了讲。每种架构我都会结合自己踩过的坑，给你讲明白它的适用场景和潜在风险。

2.1 集中式架构：一个大脑管所有

集中式架构，顾名思义，就是整个系统只有一个调度中心。所有AGV的状态上报、任务分配、路径规划，全由这一台服务器说了算。

核心特征：

  • 单点决策：所有AGV听命于中央调度器
  • 全局最优：理论上能算出全局最优路径
  • 实现简单：逻辑都在一个进程里，调试方便

我记得2018年做第一个项目时，用的就是集中式架构。当时只有12台AGV，跑在一个2000平米的仓库里，效果还不错。中央调度器跑在一台工控机上，每100ms轮询一次所有AGV的状态，然后统一分配任务。

代码结构大概是这样的：

class CentralScheduler:
    def __init__(self):
        self.agvs = {}  # 所有AGV的状态
        self.tasks = [] # 待分配任务队列
    
    def tick(self):
        # 1. 收集所有AGV状态
        for agv_id in self.agvs:
            status = self.agvs[agv_id].get_status()
        
        # 2. 全局路径规划
        paths = self.global_planner.plan_all()
        
        # 3. 分配任务
        for task in self.tasks:
            best_agv = self.select_optimal_agv(task)
            best_agv.assign(task)

优点很明显：

  • 全局视野，能避免死锁和路径冲突
  • 部署简单，一台服务器搞定
  • 调试方便，所有日志集中在一起

缺点也很致命：

  • 单点故障——中央调度器挂了，所有AGV原地瘫痪
  • 性能瓶颈——AGV数量超过50台时，计算量指数级增长
  • 网络延迟——AGV离调度器越远，响应越慢

我曾经踩过的坑：有一次客户现场，AGV数量从20台扩展到35台，中央调度器的CPU直接飙到95%。原因是路径规划算法没做优化，每次都要重新计算所有AGV的路径。后来加了增量规划才解决。所以，集中式架构在30台以下还行，超过这个数，你得掂量掂量。

2.2 分布式架构：各自为政，协同作战

分布式架构，就是把调度能力下放到每台AGV上。没有中央大脑，每台AGV自己决策，通过通信协议互相协商。

核心特征：

  • 去中心化：没有单点故障
  • 自主决策：每台AGV有自己的局部规划器
  • 协商机制：通过消息传递解决冲突

说实话，分布式架构听起来很美好，但实现起来坑特别多。我做过一个实验性的分布式系统，每台AGV跑一个轻量级的调度节点，通过广播消息来协调路径。

核心逻辑大概是这样：

class DistributedAGV:
    def __init__(self, agv_id):
        self.id = agv_id
        self.local_map = {}  # 局部地图
        self.peers = []      # 邻居AGV列表
    
    def negotiate_path(self, target):
        # 1. 广播路径请求
        broadcast(f"AGV_{self.id} 请求路径到 {target}")
        
        # 2. 收集其他AGV的反馈
        conflicts = self.collect_conflicts()
        
        # 3. 协商解决冲突
        if conflicts:
            priority = self.calculate_priority()
            if priority > conflicts[0].priority:
                proceed()  # 我优先级高，我先走
            else:
                wait()     # 我优先级低，让路

优点：

  • 高可用——单台AGV故障不影响整体
  • 可扩展——加AGV只需要配置网络，不用升级服务器
  • 低延迟——决策在本地完成，不依赖网络

缺点：

  • 全局最优难保证——每台AGV只看到局部信息
  • 通信开销大——AGV数量多时，广播风暴很吓人
  • 调试困难——问题复现需要多台AGV同时跑

我的建议：分布式架构适合AGV数量多（100+）、任务随机性强的场景。但如果你对路径的全局最优性有要求，比如要最小化总行驶距离，那分布式可能不是最佳选择。我见过一个项目，用了分布式架构后，AGV之间频繁让路，整体效率反而下降了15%。

2.3 混合式架构：取长补短

混合式架构，说白了就是集中式和分布式的结合。通常的做法是：有一个轻量级的中央协调器，负责宏观调度；每台AGV有自己的局部决策能力，处理微观路径调整。

核心特征：

  • 分层决策：中央层做任务分配，本地层做路径执行
  • 松耦合：中央和本地可以异步通信
  • 容错设计：中央挂了，AGV还能按本地缓存的任务继续跑

我个人最喜欢这种架构。它既保留了集中式的全局视野，又吸收了分布式的弹性。我最近一个项目，80台AGV跑在3万平米的厂区，用的就是混合式架构。

实现上，中央调度器只做两件事：任务分配和区域拥堵管理。具体的路径规划，交给AGV自己处理。

class HybridScheduler:
    def __init__(self):
        self.zone_manager = ZoneManager()  # 区域管理
        self.task_dispatcher = TaskDispatcher()  # 任务分配
    
    def assign_task(self, task):
        # 中央只分配任务到区域
        zone = self.zone_manager.get_best_zone(task)
        agv = self.task_dispatcher.pick_agv(zone)
        agv.assign_task(task, local_plan=True)  # 本地规划路径

class HybridAGV:
    def execute_task(self, task):
        # 本地执行路径规划
        path = self.local_planner.plan(task)
        while not self.is_finished():
            # 遇到拥堵，向中央请求区域信息
            if self.detect_congestion():
                zone_info = self.scheduler.get_zone_info()
                self.adjust_path(zone_info)
            self.move_next()

优点：

  • 兼顾全局和局部——中央管大局，本地管细节
  • 弹性好——中央压力小，AGV数量扩展容易
  • 容错性强——中央短暂故障，AGV还能继续跑

缺点：

  • 设计复杂——需要定义清晰的中央/本地职责边界
  • 调试难度大——问题可能出在中央，也可能出在本地
  • 通信协议复杂——中央和本地之间需要高效的通信机制

避坑指南：我曾经在混合式架构中犯过一个错误——中央和本地都做了路径规划，结果两者冲突了。中央说走A路，本地说走B路，AGV在路口打转。后来我加了一条规则：中央只做任务分配和区域拥堵管理，路径规划完全交给本地。职责清晰了，问题就解决了。

2.4 三种架构对比总结

为了让你一目了然，我把三种架构的核心差异整理成了表格：

维度 集中式 分布式 混合式
决策方式 中央统一决策 本地自主决策 中央+本地分层决策
全局最优性 高 低 中高
单点故障 有 无 部分容错
扩展性 差（30台以下） 好（100+台） 好（50-200台）
实现复杂度 低 高 中高
调试难度 低 高 中
典型场景 小规模、固定路线 大规模、动态环境 中大规模、复杂场景

2.5 架构选型决策流程

你可能会问：那我到底该选哪种？嗯，这里我分享一个我自己的决策流程：

  1. 先看AGV数量：30台以下，集中式够用；30-100台，混合式最稳；100台以上，考虑分布式
  2. 再看任务密度：任务密集、路径冲突多，集中式或混合式更优；任务稀疏，分布式也能跑
  3. 最后看可靠性要求：不能停机的场景，必须上分布式或混合式；允许短时停机，集中式也能凑合

我的经验：如果你刚开始做AGV调度系统，我建议从集中式入手。先把逻辑跑通，再考虑分布式或混合式。别一上来就搞复杂的架构，容易把自己绕进去。我见过太多团队，分布式搞了半年，连基本的功能都没跑通。
