18 故障恢复：主备切换、数据备份、容灾方案

做AGV调度系统这些年，我最怕听到的一句话就是：「调度挂了」。

你想想看，几十台AGV在仓库里跑着，突然调度中心宕机了。车停的停、撞的撞，整个现场乱成一锅粥。说实话，这种场景我经历过不止一次。所以今天咱们聊聊故障恢复，说白了就是——怎么让系统在出问题的时候，还能撑住场面。

18.1 主备切换：别让单点成为你的噩梦

先讲最核心的：主备切换。我个人习惯把调度系统部署成「一主一备」或者「一主多备」的模式。主节点干活，备节点待命。一旦主节点挂了，备节点立刻顶上。

这里有个关键点：切换速度。我曾经见过一个项目，主备切换花了30秒。30秒啊，AGV早就乱套了。所以我的建议是，切换时间必须控制在3秒以内。

核心指标：

  • 切换时间：≤3秒
  • 数据丢失：0（至少要做到接近0）
  • 切换过程：对AGV无感

怎么实现？我常用的方案是心跳检测 + 虚拟IP漂移。主节点每隔1秒发一次心跳，备节点如果连续3次没收到，就认为主节点挂了，然后备节点接管虚拟IP，开始提供服务。

# 伪代码：心跳检测逻辑
if (heartbeat_count >= 3) {
    // 主节点失联
    standby_node.takeover();
    // 切换虚拟IP
    vip.move_to(standby_node);
    // 通知所有AGV重新连接
    notify_all_agv("new_master: " + standby_node.ip);
}

嗯，这里要注意：备节点接管后，必须保证它拿到的数据是最新的。否则就会出现「车还在跑，但调度系统不知道车在哪」的尴尬局面。

18.2 数据备份：别等丢了才后悔

数据备份这件事，我吃过亏。有一次现场调试，不小心把数据库表给删了。当时冷汗就下来了。还好有备份，不然几十台AGV的路径数据、任务记录全没了。

所以我现在做项目，数据备份是强制要求。分三层：

备份层级 频率 存储位置 用途
实时备份 每5秒 备节点内存 主备切换用
增量备份 每小时 本地磁盘 日常恢复
全量备份 每天 远程存储 灾难恢复

说白了，实时备份是为了「秒级恢复」，增量备份是为了「小时级恢复」，全量备份是为了「天级恢复」。三层叠加，基本能覆盖所有场景。

我的小技巧：备份文件命名一定要带时间戳。比如 backup_20250118_143000.sql。这样恢复的时候一眼就能找到最新的备份。别问我为什么强调这个——我曾经在凌晨3点恢复数据，文件名全是 backup_final.sql、backup_final_v2.sql，差点崩溃。

18.3 容灾方案：异地容灾才是真保险

主备切换解决的是「单点故障」，数据备份解决的是「数据丢失」。但万一整个机房都炸了呢？比如火灾、断电、网络瘫痪。这时候就需要异地容灾了。

我参与过一个大型物流园区的项目，调度系统部署在两个不同的机房，相距5公里。两个机房之间通过专线连接，数据实时同步。主机房挂了，备机房自动接管。

注意：异地容灾不是万能的。它解决的是「机房级故障」，但解决不了「数据逻辑错误」。比如有人误删了表，这个操作会同步到备库，两个库一起完蛋。所以数据备份和容灾方案要配合使用，缺一不可。

18.4 故障恢复的实战流程

说了这么多理论，咱们看看实际怎么操作。我总结了一套标准流程：

  1. 故障检测：监控系统发现主节点心跳丢失
  2. 切换决策：确认主节点确实挂了，不是网络抖动
  3. 备节点接管：备节点启动，加载最新数据
  4. 服务恢复：虚拟IP漂移到备节点，AGV重新连接
  5. 数据校验：检查所有AGV的状态是否一致
  6. 故障修复：修复主节点，恢复成备节点

我曾经遇到过一个坑：切换之后，备节点发现数据库里有一条任务记录是「执行中」，但对应的AGV其实已经完成了。为什么？因为主节点挂了的时候，这条任务的状态还没来得及同步。所以我在切换流程里加了一步「数据校验」，强制所有AGV上报当前状态，和数据库做比对。不一致的，以AGV上报为准。

避坑指南：我曾经在切换后忘记更新AGV的连接地址，结果所有车还在往旧IP发请求。所以切换完成后，一定要广播通知所有AGV：「调度系统换地址了，重新连我！」

18.5 总结一下

故障恢复这件事，说白了就是「防患于未然」。主备切换解决的是「单点故障」，数据备份解决的是「数据丢失」，容灾方案解决的是「机房级灾难」。三者缺一不可。

我个人习惯，每个项目交付前都会做一次「故障演练」——人为制造故障，看看系统能不能扛住。第一次演练的时候，十有八九会出问题。发现问题、修复问题、再演练，直到系统能稳定应对各种故障。

嗯，最后说一句：别等到出事了才想起做容灾。那时候就晚了。
