5 多车路径规划：冲突检测、死锁避免、交通管制策略

各位同学，咱们今天聊点硬核的。多车路径规划，说白了就是让一群AGV在仓库里跑起来，还不撞车、不堵死。我刚开始做这个的时候，以为只要给每辆车算条路就行了，结果第一次联调，三台车在十字路口怼成一团，调度日志里全是"冲突！冲突！"的报警。嗯，从那以后我就明白了——多车调度，核心不在"路径"，而在"协同"。

5.1 冲突检测：你得知道什么时候会撞

冲突检测，是交通管制的前提。你连什么时候会撞都不知道，怎么管？

我个人习惯把冲突分成两类：

  • 节点冲突：两辆车同时要占用同一个路口或站点
  • 边冲突：两辆车在同一条路段上相向而行或同向追尾

我在项目中遇到过最头疼的，是那种"看起来不冲突，实际上一刹车就冲突"的情况。比如两辆车在T型路口，一辆直行，一辆左转，路径交叉点其实不在同一个格子上，但车体有长度，转弯有半径，一不留神就蹭上了。

所以，冲突检测不能只看"路径点"，还得看"路径段"和"时间窗"。我常用的方法是：

  1. 把每辆车的路径拆成一系列路径段（起点→终点）
  2. 给每个路径段加上时间窗（进入时间、离开时间）
  3. 检查不同车辆的时间窗是否有重叠

来看一个简单的冲突检测逻辑：

def detect_conflict(path_a, path_b):
    """
    path_a, path_b: 每辆车的路径，格式为 [(x,y,t_enter,t_exit), ...]
    返回冲突列表
    """
    conflicts = []
    for seg_a in path_a:
        for seg_b in path_b:
            # 检查空间重叠
            if seg_a[0] == seg_b[0] and seg_a[1] == seg_b[1]:
                # 检查时间重叠
                if not (seg_a[3] <= seg_b[2] or seg_a[2] >= seg_b[3]):
                    conflicts.append((seg_a, seg_b))
    return conflicts

这段代码看着简单，但实际项目里要复杂得多。我曾经因为没考虑"车辆长度"导致误判——两辆车虽然路径点不同，但车头车尾已经交叉了。后来我加了一个"安全缓冲区"，每个路径段前后各延伸半米，才算稳当。

核心要点：冲突检测不是"点对点"的碰撞检查，而是"段对段"的时间窗重叠检查。别忘了车体尺寸和转弯半径。

5.2 死锁避免：别让AGV们互相"堵死"

死锁，是多车调度里最让人头疼的问题。你想想看，四台车在十字路口各占一个方向，谁都想走，谁都不让，最后全停在那——这就是典型的死锁。

死锁产生的四个必要条件（嗯，跟操作系统里的死锁是一个道理）：

  • 互斥：一个路段一次只能有一辆车
  • 持有并等待：每辆车占着当前路段，等着下一个路段
  • 不可剥夺：不能强行把车挪走
  • 循环等待：A等B的路段，B等C的路段，C等A的路段

怎么避免？我总结了三种策略：

5.2.1 资源预留法

每辆车在出发前，就把整条路径上的所有路段"预约"好。别人不能再用。这方法简单粗暴，但缺点是——如果路径很长，资源利用率极低。我在一个3000平米的仓库里试过，预约法导致吞吐量下降了40%。

5.2.2 银行家算法

借鉴操作系统的思路。每辆车申请资源（路段）时，系统先模拟分配，看看会不会导致死锁。如果会，就拒绝申请。这方法靠谱，但计算量大，实时性差。我一般只在离线规划阶段用。

5.2.3 死锁检测+恢复

不预防，只检测。发现死锁后，强制让某辆车倒车或绕路。这方法实时性好，但需要预留"逃生路径"。我在一个汽车零部件仓库里用过，效果不错，但前提是——你得有足够的备用路径。

我的建议：实际项目中，我倾向于"资源预留+死锁检测"混合使用。关键路径（如十字路口、窄通道）用预留法，非关键路径用检测法。既保证安全，又不牺牲效率。

5.3 交通管制策略：像交警一样指挥

冲突检测和死锁避免，都是"被动防御"。真正高效的调度，需要主动的交通管制。说白了，就是给AGV们定规矩。

我常用的交通管制策略有四种：

策略名称 核心思想 适用场景 我踩过的坑
优先级调度 给每辆车设优先级，高优先级的先走 任务有紧急程度之分 优先级低的车辆可能永远走不了（饥饿）
时间窗调度 给每个路段分配时间片，车辆按时间片通行 高密度、高频率场景 时间片太短会导致频繁启停，磨损严重
区域管制 把地图分成若干区域，每个区域限制车辆数量 大面积仓库，分区管理 区域边界容易成为新的拥堵点
动态路径重规划 检测到冲突时，实时给某辆车重新算路 路径灵活、有备用路线 重规划耗时，可能导致连锁反应

这里我重点说说时间窗调度。这是我个人比较推崇的一种策略，因为它把"冲突检测"和"交通管制"合二为一了。

具体做法是：

  1. 把地图上的每个路段（包括路口）看作一个"资源"
  2. 每个资源维护一个"时间窗表"，记录已被占用的时间段
  3. 车辆申请通行时，查时间窗表，找一个空闲的时间段
  4. 如果找不到，就等待或绕路

来看一个时间窗调度的核心代码：

class TrafficController:
    def __init__(self):
        self.resource_windows = {}  # 路段 -> [(start_time, end_time), ...]
    
    def request_passage(self, vehicle_id, road_segment, duration):
        """车辆申请通行某个路段，duration为预计通行时间"""
        if road_segment not in self.resource_windows:
            self.resource_windows[road_segment] = []
        
        # 找一个空闲时间窗
        windows = self.resource_windows[road_segment]
        # 简单起见，从当前时间开始找
        start_time = max(0, windows[-1][1] if windows else 0)
        end_time = start_time + duration
        
        # 检查是否与其他窗口冲突
        for w in windows:
            if not (end_time <= w[0] or start_time >= w[1]):
                # 冲突，需要等待
                start_time = w[1]
                end_time = start_time + duration
        
        # 分配时间窗
        windows.append((start_time, end_time))
        windows.sort(key=lambda x: x[0])
        
        return start_time, end_time

这段代码我简化了很多。实际项目中，你还要考虑：

  • 车辆加减速时间（不是瞬间就能到最高速的）
  • 路口转向耗时（转弯比直行慢）
  • 异常情况处理（比如某辆车突然故障停在路中间）
注意：时间窗调度虽然好用，但有一个致命弱点——对时间同步要求极高。如果AGV的时钟不准，或者通信有延迟，时间窗就会错位。我曾经因为WiFi延迟导致两辆车的时间窗重叠了200毫秒，结果在路口撞上了。后来我换成了有线通信+本地时钟同步，才算解决。

5.5 避坑指南

最后，我把自己这些年踩过的坑总结一下，你们遇到了能少走弯路：

  • 我曾经以为冲突检测越精细越好，结果把每个路径点都做碰撞检测，导致计算量爆炸，调度周期从100ms变成了2秒。后来发现，只需要检测关键节点（路口、站点、窄道）就够了。
  • 我曾经在死锁恢复时，让车辆"原地等待"，结果三台车互相等了一整天。后来我加了"超时强制绕路"机制，超过5秒没动静就重新规划。
  • 我曾经在时间窗调度里，把时间片设得太短（0.5秒），结果AGV频繁启停，电机过热保护了。后来我根据车辆加减速性能，把时间片设为2~3秒，既保证了通行效率，又保护了硬件。

嗯，多车路径规划这块，说白了就是"平衡"——在安全、效率、硬件寿命之间找平衡点。没有银弹，只有不断调优。

一句话总结：冲突检测是眼睛，死锁避免是大脑，交通管制是手脚。三者配合，才能让AGV车队跑得又快又稳。
