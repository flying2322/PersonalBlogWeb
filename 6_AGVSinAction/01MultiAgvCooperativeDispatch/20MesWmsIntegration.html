20 与MES/WMS集成：接口设计、数据同步、业务流程对接

做AGV调度系统这么多年，我最大的感触就是：单机跑得再快，不如跟MES/WMS好好谈恋爱。说白了，AGV只是执行层的一双手，真正的大脑是MES和WMS。这一章，我就把集成这块的坑和经验，一次性倒给你们。

20.1 为什么要集成？不集成行不行？

你想想看，AGV自己在那跑，它知道哪个工单急吗？知道哪个料架空了需要补料吗？不知道。它就是个听话的搬运工。

我见过一些工厂，AGV和MES各玩各的。操作员得先在MES里下任务，再到AGV系统里手动输入目的地。这不扯吗？效率反而更低了。

所以，集成要解决三个核心问题：

  • 任务自动下发：MES/WMS产生任务，AGV自动接收执行
  • 状态实时反馈：AGV干了什么、干完了没有，MES得知道
  • 数据一致性：库存、位置、状态，两边不能对不上

20.2 接口设计：选REST还是WebSocket？

接口设计这块，我个人习惯分场景来选协议。别一上来就拍脑袋说用REST，也别迷信WebSocket万能。

场景 推荐协议 原因
任务下发（MES→AGV） REST API 请求-响应模式，简单可靠
状态上报（AGV→MES） WebSocket / MQTT 实时推送，减少轮询压力
批量数据同步 REST + 批量接口 数据量大，需要事务保证
心跳检测 WebSocket 长连接，低延迟

我在项目中遇到过一个问题：用REST做状态上报，每台AGV每秒上报一次，100台车就是100次/秒。MES那边扛不住，直接挂了。后来改成WebSocket，压力瞬间降下来。

20.3 数据同步：别让库存对不上账

数据同步是集成里最容易出幺蛾子的地方。我见过最离谱的案例：AGV说料已经送到了，WMS说没收到。两边扯皮，最后发现是同步延迟导致的。

我的建议是：采用"最终一致性"模型，别追求实时同步。为什么？因为AGV执行任务需要时间，你非要实时同步，反而会频繁触发冲突。

核心同步策略：

  • 任务级同步：任务创建、开始、完成三个节点必须同步
  • 库存级同步：AGV取货/放货完成后，触发库存变更
  • 心跳级同步：AGV位置、电量等状态，按固定频率上报

嗯，这里要注意：同步一定要有幂等性。我曾经因为网络抖动，同一个任务完成消息发了两次，WMS那边库存扣了两次。后来加了个唯一ID校验，才解决。

20.4 业务流程对接：画清楚谁该干什么

业务流程对接，说白了就是把业务语言翻译成系统语言。MES说"我要补料"，AGV得知道去哪取、送到哪、取多少。

我一般用状态机来设计业务流程。举个例子：

// 任务状态机示例
状态：待接收 → 已接收 → 执行中 → 已完成
触发条件：
  - MES下发任务 → 待接收
  - AGV确认接单 → 已接收
  - AGV开始移动 → 执行中
  - AGV到达并完成 → 已完成

// 异常状态
  - 超时未接单 → 任务取消
  - 执行中故障 → 任务挂起

你想想看，如果没有这个状态机，MES和AGV各说各话，根本对不上。我建议你们在设计阶段，就把状态流转图画出来，两边确认签字。

20.6 避坑指南：我踩过的那些坑

做集成这么多年，我踩过的坑能写一本书。挑几个典型的说说：

  • 接口超时设置：我曾经把超时设成3秒，结果AGV在充电站里没信号，任务全超时了。后来改成10秒，配合重试机制，稳了。
  • 数据格式不一致：MES传过来的时间格式是"2024-01-01 12:00:00"，AGV系统认的是时间戳。两边没对齐，导致任务排程全乱套。
  • 并发控制：MES同时下发100个任务，AGV调度系统没做限流，直接OOM。后来加了消息队列，慢慢消费。

警告：千万不要在集成初期就追求完美。先跑通一个最简单的流程，比如"MES下发任务→AGV执行→状态回传"，然后再逐步加功能。我见过太多团队一开始就想做全功能，结果半年了还在联调。

20.7 总结一下

跟MES/WMS集成，说白了就是三件事：接口怎么连、数据怎么同步、流程怎么对。接口选REST还是WebSocket，看场景；数据同步要保证最终一致性；业务流程一定要画状态机。

我个人习惯，每次做集成项目都会先花一周时间，跟MES/WMS团队把接口文档和状态流转图对齐。别看这一周好像没写代码，它能省下后面一个月的联调时间。

嗯，最后说一句：集成不是技术问题，是沟通问题。两边团队坐在一起，把话说清楚，比什么都重要。
