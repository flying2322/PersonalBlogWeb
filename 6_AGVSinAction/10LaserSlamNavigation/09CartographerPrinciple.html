9 Cartographer算法原理：Ceres优化、子图(Submap)概念、回环检测、分支定界搜索

聊到Cartographer，很多朋友第一反应就是“这玩意儿太复杂了”。其实拆开来看，核心就四个东西：Ceres优化、子图(Submap)、回环检测、分支定界搜索。今天我就把这四个东西串起来，用我实际调参踩过的坑，给你讲明白。

核心逻辑一句话：激光帧先跟当前子图匹配（前端），匹配好了就塞进子图；子图积累到一定数量，就触发全局回环检测（后端），用分支定界加速搜索，最后用Ceres做图优化，把整个轨迹和地图拉平。

9.1 子图(Submap)概念——别把它想得太玄乎

子图是什么？说白了，就是一小块局部地图。Cartographer不会一上来就建一张全局大地图，那样计算量太大了。它把整个建图过程切成很多个小段，每一段就是一个子图。

我习惯这么理解：子图就像拼图里的一块碎片。激光雷达每扫一帧，就跟当前正在构建的这块碎片做匹配，匹配上了就把这帧数据“贴”进去。等这块碎片贴满了（比如积累了N帧），就把它封存起来，开始拼下一块。

我的经验：子图大小直接影响建图效果。子图太小，回环检测频繁但容易误检；子图太大，内存占用高，回环检测延迟大。我一般在室内场景设子图包含200-300帧激光数据，室外开阔场景可以适当放大到500帧。

每个子图内部维护一个概率栅格地图。新来的激光点命中某个栅格，概率就增加；激光束穿过的栅格，概率就降低。这个机制很简单，但很有效。

9.2 Ceres优化——前端匹配的“心脏”

Ceres是Google开源的非线性最小二乘优化库。Cartographer用它来做什么？做帧到子图的匹配。

你想想看，激光雷达扫了一帧数据，怎么知道它跟当前子图对齐了？传统方法是用ICP或者相关性匹配。Cartographer的做法是：把这个问题建模成一个优化问题，用Ceres来求解。

具体来说，优化的目标函数长这样：

// 伪代码：Ceres优化目标函数
struct ScanMatcherCostFunction {
  template <typename T>
  bool operator()(const T* const pose, T* residual) const {
    // 把激光点根据当前位姿投影到子图坐标系
    // 计算投影点与子图栅格概率的差异
    // 差异越小，说明匹配越好
    residual[0] = T(1.0) - grid_.GetProbability(projected_point);
    return true;
  }
};

// 调用Ceres求解
ceres::Problem problem;
ceres::CostFunction* cost_function = 
    new ceres::AutoDiffCostFunction<ScanMatcherCostFunction, 1, 3>(new ScanMatcherCostFunction);
problem.AddResidualBlock(cost_function, nullptr, pose);

这里有个细节：Ceres优化的是位姿（x, y, θ），每次迭代都会微调位姿，让所有激光点投影到子图上的概率之和最大。说白了，就是让激光点尽量落在“墙壁”上，而不是落在“空白区域”。

我曾经踩过的坑：一开始我把Ceres的迭代次数设得太少（默认10次），结果在长廊场景下匹配经常发散。后来我改成50次迭代，收敛稳定多了。但迭代次数太多又影响实时性，这个平衡需要根据实际传感器频率来调。

9.3 回环检测——把“漂移”拉回来

建图最怕什么？怕漂移。机器人走了一大圈回来，发现地图对不上了。这就是累积误差。

回环检测就是用来解决这个问题的。当机器人再次经过之前去过的地方时，Cartographer会把当前帧跟所有已完成的子图做匹配。如果匹配上了，就建立一个回环约束。

这个约束会被加到全局图优化中。Ceres后端会调整所有子图的位姿，让回环约束得到满足，同时尽量保持原有的局部一致性。

回环检测的触发条件有两个：

  • 距离触发：机器人运动了一定距离（默认约10米）
  • 时间触发：距离上次检测过去了若干秒

我个人习惯把距离阈值设小一点（比如5米），这样回环检测更频繁，但计算量会增大。如果你的机器人计算资源有限，可以适当放大阈值。

9.4 分支定界搜索——加速回环匹配的“杀手锏”

回环检测时，需要在一个很大的搜索空间里找最优匹配。暴力搜索的话，假设搜索范围是10米×10米，角度范围是±30°，步长0.05米、0.5°，那搜索次数是：

搜索次数 = (10/0.05) * (10/0.05) * (60/0.5) = 200 * 200 * 120 = 4,800,000次

四百八十万次！每帧都这么搜，CPU直接冒烟。

分支定界就是用来解决这个问题的。它的核心思想是：先粗搜，再精搜。

具体做法是构建一个搜索树：

  • 最顶层：步长最大（比如1.6米），覆盖整个搜索范围
  • 中间层：步长逐渐减小
  • 最底层：步长最小（比如0.05米），精度最高

搜索时，从顶层开始，计算每个节点的得分上限。如果某个节点的得分上限已经低于当前最优解，就把这个节点及其所有子节点全部剪掉，不再搜索。

关键点：分支定界能加速的关键在于“得分上限”的计算。Cartographer用了低分辨率预计算地图的技巧——把子图降采样到低分辨率，在低分辨率地图上计算得分，这个得分就是真实得分的上界。

我实测过，用分支定界后，回环检测的搜索时间从几百毫秒降到了十几毫秒。效果非常明显。

9.5 四者的协作流程

最后，我把这四个东西串起来，给你一个完整的流程：

  1. 前端匹配：新来一帧激光数据，用Ceres优化找到它在当前子图中的最佳位姿
  2. 插入子图：把匹配好的激光帧插入当前子图，更新栅格概率
  3. 子图完成：当前子图积累到一定帧数，封存，开始构建新子图
  4. 回环检测：每帧都检查是否可能形成回环，用分支定界加速搜索
  5. 全局优化：找到回环约束后，Ceres后端优化所有子图的位姿
  6. 反馈更新：优化结果反馈给前端，更新当前帧的位姿估计

这个流程在Cartographer的代码里对应着几个核心类：LocalTrajectoryBuilder2D（前端）、PoseGraph2D（后端）、Submap2D（子图）。有兴趣的朋友可以去看看源码，注释写得还不错。

我的建议：刚开始接触Cartographer时，不要一上来就调参数。先把这四个核心概念理解透，知道每个参数影响的是哪个环节。比如submaps.num_range_data控制子图大小，constraint_builder.sampling_ratio控制回环检测频率，ceres_scan_matcher.occupied_space_weight控制Ceres优化的权重。理解了原理，调参就是水到渠成的事。

好了，这一章的内容就到这里。Cartographer的这四个核心机制，你只要搞懂了子图怎么构建、Ceres怎么优化、回环怎么检测、分支定界怎么加速，整个算法框架就清晰了。剩下的就是动手实践，在自己的数据集上跑一跑，感受一下参数变化带来的影响。
