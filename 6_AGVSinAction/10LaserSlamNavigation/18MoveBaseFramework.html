18 move_base框架：actionlib通信、全局/局部规划器配置、代价地图层、恢复行为

各位同学，今天我们来啃一块硬骨头——move_base框架。说实话，这个框架是ROS导航的“大脑”，也是我当年入行时花时间最多、踩坑最深的一个模块。你想想看，AGV要自主导航，从A点到B点，中间要避开障碍物、要规划路径、要处理突发情况，所有这些逻辑都靠move_base来调度。

我个人习惯把move_base拆成四个核心部分来理解：通信机制、规划器配置、代价地图、恢复行为。咱们一个一个说。

18.1 actionlib通信：move_base的“神经”

move_base和外部模块怎么通信？靠的是actionlib。不是简单的topic，也不是service，而是actionlib。为什么？因为导航是一个长时间、可取消、有反馈的任务。

举个例子，你给AGV下了一个“去仓库3号货架”的指令。它可能走了一半发现路被堵了，需要重新规划。这时候如果用的是service，你只能等它完成或者超时，中间没法干预。但actionlib不一样——你可以随时取消、可以收到进度反馈、可以知道它当前在干嘛。

核心概念：actionlib基于三个topic实现——goal（目标）、feedback（反馈）、result（结果）。客户端发送goal，服务端持续发布feedback，最终返回result。

我在项目中遇到过一个问题：AGV在狭窄通道里反复规划失败，客户端一直收不到result，导致任务卡死。后来发现是actionlib的超时机制没配好。默认的timeout是无限等待，这在工业现场是致命的。

# 客户端调用示例
from actionlib import SimpleActionClient
from move_base_msgs.msg import MoveBaseAction, MoveBaseGoal

client = SimpleActionClient('move_base', MoveBaseAction)
client.wait_for_server()

goal = MoveBaseGoal()
goal.target_pose.header.frame_id = "map"
goal.target_pose.pose.position.x = 5.0
goal.target_pose.pose.position.y = 3.0
goal.target_pose.pose.orientation.w = 1.0

# 设置超时，避免死等
client.send_goal(goal)
finished = client.wait_for_result(timeout=rospy.Duration(30.0))
if not finished:
    client.cancel_goal()
    rospy.logwarn("导航超时，已取消任务")

避坑指南：我曾经因为忘记设置timeout，导致AGV在死胡同里反复尝试了10分钟，电池都耗光了。建议生产环境中timeout设置在30-60秒之间，配合恢复行为使用。

18.2 全局/局部规划器配置

move_base内部有两个规划器：全局规划器和局部规划器。说白了，全局规划器负责“看地图”，规划出一条从起点到终点的宏观路径；局部规划器负责“看眼前”，根据实时传感器数据避开动态障碍物。

我刚开始做的时候，以为全局规划器配好就行了。结果AGV一跑起来，要么撞墙，要么原地打转。后来才明白——两个规划器必须协同工作。

全局规划器配置

常用的全局规划器是navfn/NavfnROS或global_planner/GlobalPlanner。我个人更推荐后者，因为它支持A*和Dijkstra两种算法，灵活性更高。

# 全局规划器参数示例
GlobalPlanner:
  use_dijkstra: false          # 用A*，速度更快
  use_quadratic: true          # 二次插值，路径更平滑
  use_grid_path: false         # 不使用网格路径
  old_navfn_behavior: false    # 兼容旧版本
  visualize_potential: false   # 可视化势场，调试用

这里有个关键点：use_quadratic一定要设为true。为什么？因为如果不做插值，全局路径就是锯齿状的，局部规划器跟着走会很吃力，AGV会频繁左右摇摆。

局部规划器配置

局部规划器我主要用过两种：base_local_planner/TrajectoryPlannerROS（DWA算法）和dwa_local_planner/DWAPlannerROS。DWA是动态窗口法的缩写，核心思想是：在速度空间里采样，找一条不撞障碍物、又最接近全局路径的轨迹。

# DWA局部规划器参数示例
DWAPlannerROS:
  max_vel_x: 0.5               # 最大前进速度
  min_vel_x: -0.1              # 最小前进速度（允许后退）
  max_vel_theta: 1.0           # 最大旋转速度
  min_vel_theta: -1.0          # 最小旋转速度
  
  acc_lim_x: 0.5               # 加速度限制
  acc_lim_theta: 0.5           # 角加速度限制
  
  # 代价权重
  path_distance_bias: 32.0     # 路径跟踪权重
  goal_distance_bias: 24.0     # 目标吸引权重
  occdist_scale: 0.01          # 障碍物惩罚权重

注意：这三个权重是调参的核心。path_distance_bias太大，AGV会死板地跟着全局路径，不会灵活避障；occdist_scale太大，AGV会离障碍物太远，在狭窄通道里过不去。我一般先设成32/24/0.01，然后根据实际场景微调。

18.3 代价地图层

代价地图是move_base的“眼睛”。它把激光雷达、深度相机等传感器的数据融合起来，生成一张栅格地图，每个格子都有一个代价值。代价值越高，表示这个格子越危险。

move_base支持多层代价地图，每一层负责不同的数据源。常用的层有：

层名称 作用 数据来源
static_layer 静态地图层，加载预先建好的地图 map_server
obstacle_layer 障碍物层，实时检测动态障碍物 激光雷达、深度相机
inflation_layer 膨胀层，给障碍物周围增加安全距离 基于其他层计算
voxel_layer 体素层，3D障碍物投影到2D 3D传感器

我在项目中遇到过一个问题：AGV在仓库里总是莫名其妙地绕远路。排查了半天，发现是inflation_layer的膨胀半径设得太大了。默认是0.55米，但我们的AGV宽度只有0.6米，膨胀后几乎没路可走。

# 代价地图参数示例
local_costmap:
  global_frame: odom
  robot_base_frame: base_link
  update_frequency: 5.0        # 更新频率，越高越灵敏
  publish_frequency: 2.0
  width: 4.0                   # 局部代价地图大小
  height: 4.0
  resolution: 0.05
  
  plugins:
    - {name: obstacle_layer, type: "costmap_2d::ObstacleLayer"}
    - {name: inflation_layer, type: "costmap_2d::InflationLayer"}
    
  obstacle_layer:
    observation_sources: laser_scan
    laser_scan: {data_type: LaserScan, topic: /scan, marking: true, clearing: true}
    
  inflation_layer:
    inflation_radius: 0.3      # 根据实际车宽调整
    cost_scaling_factor: 10.0  # 代价衰减速度

经验之谈：inflation_radius建议设为车宽的一半再加0.1米。比如车宽0.6米，就设0.4米。cost_scaling_factor控制代价从障碍物边缘向外衰减的速度，值越大衰减越快，路径越靠近障碍物。

18.4 恢复行为

AGV在导航过程中，难免会遇到“卡住”的情况——比如被箱子挡住了、在狭窄通道里进退两难。这时候就需要恢复行为来救场。

move_base内置了几种恢复行为：

  • 旋转恢复：原地旋转一定角度，重新规划路径
  • 后退恢复：后退一段距离，再尝试
  • 清除代价地图：清除障碍物层，重新感知环境

这些行为是按顺序执行的。如果旋转一次不行，就旋转两次；还不行，就后退；再不行，就清除地图重新感知。如果所有行为都试过了还是不行，move_base就会放弃，返回失败状态。

# 恢复行为配置示例
recovery_behaviors:
  - {name: rotate_recovery, type: "rotate_recovery/RotateRecovery"}
  - {name: clear_costmap, type: "clear_costmap_recovery/ClearCostmapRecovery"}
  
rotate_recovery:
  frequency: 20.0
  sim_granularity: 0.017
  angular_vel: 0.5             # 旋转速度
  
clear_costmap:
  reset_distance: 3.0          # 清除半径

我曾经踩过的坑：恢复行为配了，但AGV卡住后一直旋转，就是不后退。后来发现是rotate_recovery的angular_vel设得太小，旋转速度慢，还没转完一圈就被新的障碍物挡住了。建议设到0.5以上。

还有一个容易被忽略的点：恢复行为的触发条件。默认情况下，move_base在局部规划失败后才会触发恢复行为。但有时候全局规划也会失败——比如目标点被障碍物包围了。这时候需要手动设置planner_frequency和planner_patience参数，让全局规划器也具备重试机制。

嗯，到这里move_base的核心内容就讲完了。你可能会问：这些参数怎么调？说实话，没有万能参数，每个场景都要微调。我建议你先用默认参数跑一遍，然后根据AGV的表现逐步调整——先调速度限制，再调代价权重，最后调恢复行为。别想着一步到位，调参是个迭代的过程。

最后说一句：move_base虽然强大，但也不是万能的。如果现场环境特别复杂——比如有玻璃墙、镜面反射、或者地面反光严重——光靠move_base是不够的，还需要结合IMU、轮式里程计做多传感器融合。这部分内容，我们后面会讲到。

核心要点回顾：

  • actionlib实现长时间导航任务的通信，记得设timeout
  • 全局规划器用A*，局部规划器用DWA，权重参数要配合调
  • 代价地图多层叠加，inflation_radius根据车宽设定
  • 恢复行为是最后一道防线，按旋转→后退→清除的顺序配置
