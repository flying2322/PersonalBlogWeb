11 Hector SLAM原理：高斯牛顿法、扫描匹配、多分辨率地图、无里程计模式

Hector SLAM，这个名字在激光SLAM圈子里挺特别的。它不像Gmapping那样依赖里程计，也不像Cartographer那样需要IMU辅助。说白了，它就是一个「纯激光」的SLAM方案。我最早接触它是在一个轮式机器人项目上，当时底盘编码器坏了，临时用Hector顶着，居然还能跑——嗯，这就是它的魅力所在。

11.1 核心思想：无里程计也能定位

Hector SLAM的核心假设很简单：激光雷达的帧率足够高，且环境中有足够的几何特征。它不需要轮式里程计，也不需要IMU，完全靠激光点云与已有地图的匹配来估计位姿。

你想想看，如果激光雷达每秒扫描40次，那么相邻两帧之间的位移其实很小。利用这个「小位移」假设，我们可以用优化方法直接求解位姿变换。这就是Hector的底气所在。

适用场景：

  • 地面平坦、无明显打滑的环境
  • 激光雷达帧率 ≥ 20Hz
  • 环境中有足够的垂直结构（墙壁、柱子等）

注意：Hector SLAM对激光雷达的安装角度很敏感。我曾经在一个项目中把雷达装歪了2度，结果建图时走廊直接变成了「梯形」——后来花了半天才排查出来。

11.2 高斯牛顿法：优化位姿的数学工具

Hector SLAM的位姿优化，用的是高斯牛顿法。这个方法说白了就是：用一阶导数（梯度）和二阶导数（海森矩阵）来逼近目标函数的最小值。

在SLAM里，我们的目标函数是：

minimize: Σ [1 - M(S_i(ξ))]²

其中：

  • ξ 是待优化的位姿（x, y, θ）
  • S_i(ξ) 是将第i个激光点转换到地图坐标系下的函数
  • M(·) 是地图在该点的占据概率值

高斯牛顿法的迭代公式是：

ξ ← ξ + (JᵀJ)⁻¹ Jᵀ r

这里的 J 是雅可比矩阵，r 是残差向量。我习惯把 JᵀJ 理解为「信息矩阵」，它反映了每个参数对误差的贡献程度。

我的经验：高斯牛顿法对初始值比较敏感。如果初始位姿离真值太远（比如超过0.5米或10度），很容易收敛到局部最优。所以Hector通常会用上一帧的位姿作为初始值——这要求帧率足够高。

11.3 扫描匹配：如何把激光点「贴」到地图上

扫描匹配是Hector SLAM的核心环节。它的任务很简单：找到当前帧激光点云与已有地图的最佳对齐方式。

具体流程是这样的：

  1. 投影：将当前帧的激光点从雷达坐标系转换到世界坐标系
  2. 查值：在世界地图上查找每个投影点的占据概率值
  3. 优化：调整位姿参数，使得所有投影点的占据概率之和最大

这里有个关键点：地图是离散的栅格，而激光点的坐标是连续的。所以我们需要双线性插值来获取连续的地图值。Hector的作者在论文里特别强调了这一点——没有插值，梯度就没法算。

// 双线性插值的核心代码（伪代码）
float bilinearInterpolation(const GridMap& map, float x, float y) {
    int x0 = floor(x), x1 = x0 + 1;
    int y0 = floor(y), y1 = y0 + 1;
    
    float dx = x - x0, dy = y - y0;
    
    float v00 = map.getValue(x0, y0);
    float v10 = map.getValue(x1, y0);
    float v01 = map.getValue(x0, y1);
    float v11 = map.getValue(x1, y1);
    
    // 先沿x方向插值，再沿y方向插值
    float v0 = v00 * (1 - dx) + v10 * dx;
    float v1 = v01 * (1 - dx) + v11 * dx;
    
    return v0 * (1 - dy) + v1 * dy;
}

避坑指南：我曾经在实现双线性插值时，忘记处理地图边界的情况。结果激光点一旦打到地图边缘，程序就崩溃了。后来加了个边界检查，问题解决。

11.4 多分辨率地图：从粗到细的匹配策略

多分辨率地图是Hector SLAM的一个亮点。它的思路很简单：先用低分辨率地图做粗匹配，再用高分辨率地图做精匹配。

为什么要这么做？因为高斯牛顿法容易陷入局部最优。低分辨率地图相当于「模糊处理」，能平滑掉很多局部极值点，让优化更容易找到全局最优。

Hector通常使用2~3层分辨率：

层级 分辨率 作用
第1层（最粗） 0.2米/像素 快速粗匹配，避免局部最优
第2层（中等） 0.1米/像素 中等精度匹配
第3层（最细） 0.05米/像素 精匹配，输出最终位姿

匹配时，先在最粗层上优化，把结果作为下一层的初始值，依次类推。我习惯把这种策略叫做「由粗到细的漏斗式匹配」——每一层都在缩小搜索范围。

我的建议：如果你的计算资源有限，可以只用两层分辨率。我试过在树莓派上跑Hector，只用两层（0.2m和0.1m），效果也还行，帧率能到15Hz左右。

11.5 无里程计模式：Hector的独门绝技

无里程计模式，说白了就是完全依赖激光雷达自身的运动估计。Hector通过连续帧之间的扫描匹配，累积出机器人的运动轨迹。

这个模式有几个特点：

  • 优点：不受轮子打滑、编码器误差的影响
  • 缺点：长时间运行会有累积误差，且无法处理纯旋转（激光雷达在旋转时，前后帧的重叠区域很小）

我记得有一次在户外测试，地面是沙土地，轮子一直在打滑。Gmapping直接崩了，但Hector还能正常工作——因为它根本不关心轮子转没转。

注意：无里程计模式对激光雷达的视场角有要求。如果用的是单线激光雷达，视场角最好在270度以上。我曾经用180度的雷达试过，结果机器人一转弯就丢失了——因为前后帧的重叠区域太小，匹配失败。

11.7 实际使用中的注意事项

最后，分享几个我在实际项目中使用Hector SLAM的体会：

  • 初始化很重要：Hector启动时，需要先建立初始地图。如果初始位置周围没有足够的特征（比如在空旷的广场上），建图会失败。我一般会先让机器人对着墙壁或角落启动。
  • 地图分辨率要匹配：地图分辨率不是越细越好。0.05米的分辨率在室内够用，但在室外大场景下，0.1米反而更稳定——因为点云稀疏时，高分辨率地图会有很多空洞。
  • 小心纯旋转：Hector在纯旋转时容易丢失。如果机器人需要原地转弯，建议放慢速度，或者配合IMU使用（虽然Hector本身不支持IMU，但可以在外部做融合）。

一句话总结：Hector SLAM是「纯激光派的代表」，它用高斯牛顿法做扫描匹配，用多分辨率地图避免局部最优，用无里程计模式应对打滑场景。简单、直接、有效——但前提是你的激光雷达够快、环境够有特征。
