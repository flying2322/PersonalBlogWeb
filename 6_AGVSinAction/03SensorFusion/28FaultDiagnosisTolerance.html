28 故障诊断与容错：传感器故障检测、冗余设计、降级策略

各位做AGV的朋友，咱们聊点实在的。传感器故障，这玩意儿就像感冒发烧，谁都躲不过。你想想看，一台AGV在仓库里跑得好好的，突然激光雷达被灰尘糊住了，或者IMU数据开始飘——这时候系统要是没点“免疫力”，那后果就是撞货架、丢定位，甚至伤人。

我做了这么多年AGV，最怕的不是算法难调，而是传感器“装死”。你明明看着它还在输出数据，其实早就坏了。嗯，今天咱们就把这套“免疫系统”拆开看看。

核心思想：故障诊断是“看病”，容错是“带病工作”。两者缺一不可。

28.1 传感器故障检测：别等撞了墙才发现

故障检测说白了就两件事：数据对不对，逻辑通不通。我个人习惯把检测方法分成三类，咱们一个个说。

28.1.1 基于物理模型的检测

这种方法最直观。比如激光雷达，理论上扫描一圈应该能检测到地面和墙壁。如果连续几帧都只返回“无穷远”，那八成是坏了。

// 伪代码：激光雷达故障检测
bool checkLidarHealth(LidarData data) {
    // 1. 检查数据帧率
    if (data.frequency < 8.0 Hz) return false;
    
    // 2. 检查有效点数
    int validPoints = countValidPoints(data);
    if (validPoints < 100) return false;
    
    // 3. 检查距离突变
    float delta = abs(data.ranges[0] - data.ranges[last]);
    if (delta > 10.0) return false;  // 相邻点距离突变超过10米
    
    return true;
}

我曾经遇到过一个案例：AGV在仓库里突然“失明”，但激光雷达明明还在转。后来发现是镜片被透明胶带粘住了——数据全反射回来了。这种物理模型检测就抓不住，得靠别的办法。

28.1.2 基于统计的检测

这个方法更聪明。你给每个传感器建个“健康档案”，记录它过去100帧的数据分布。如果新数据偏离了历史分布，就报警。

传感器类型 统计特征 故障阈值
IMU加速度计 方差 超过历史均值3σ
轮式编码器 脉冲计数 连续5帧为0
激光雷达 点云密度 低于正常值50%

避坑指南：我曾经把IMU的故障阈值设得太严，结果AGV过减速带时老是误报。后来改成“连续3帧超阈值”才稳定下来。记住：单帧异常可能是噪声，持续异常才是故障。

28.1.3 基于冗余的检测

这个最靠谱——用两个传感器互相验证。比如AGV装了双激光雷达，一个看左边，一个看右边。如果左边雷达说“前方有障碍”，右边雷达说“前方空旷”，那肯定有一个在撒谎。

我习惯用一致性检验：

bool checkConsistency(LidarData left, LidarData right) {
    // 取重叠区域的数据
    vector<float> overlapLeft = left.getOverlapRegion();
    vector<float> overlapRight = right.getOverlapRegion();
    
    // 计算相关系数
    float correlation = computeCorrelation(overlapLeft, overlapRight);
    
    // 如果相关系数低于0.8，说明有传感器故障
    return correlation > 0.8;
}

28.2 冗余设计：别把所有鸡蛋放一个篮子里

冗余设计不是简单堆硬件。你想想看，如果两个传感器用同一路电源、同一个通信总线，那一个坏了另一个也跑不掉。这叫“共因失效”，是冗余设计的大忌。

我一般把冗余分成三个层次：

  • 硬件冗余：双激光雷达、双IMU、双编码器。注意要异构——比如一个用TOF激光雷达，一个用三角法激光雷达，这样不会被同一种干扰搞死。
  • 信息冗余：同一个物理量用不同方式测量。比如AGV的速度，可以用轮式编码器算，也可以用IMU积分算，还可以用视觉光流算。三个数据互相校验。
  • 算法冗余：同一个传感器数据，用不同算法处理。比如定位，既用EKF，也用粒子滤波。如果两个算法输出差异太大，说明数据有问题。

注意：冗余不是越多越好。我见过一个项目，AGV上装了4个激光雷达，结果数据融合算法复杂度爆炸，延迟从10ms飙到100ms。最后反而因为处理不过来导致撞车。冗余要适度，够用就行。

28.3 降级策略：带病也能跑

故障检测出来了，冗余也用了，但传感器还是坏了怎么办？这时候就要降级。说白了就是：别让AGV趴窝，让它“瘸着腿”也能跑回充电桩。

我总结了一套降级策略，按严重程度分：

  1. 轻度降级：比如激光雷达被遮挡了30%视野。这时候可以降低速度，开启“谨慎模式”，用IMU和编码器辅助定位。
  2. 中度降级：比如IMU完全失效。这时候只能用激光雷达和编码器做定位，但要注意——没有IMU的话，AGV过坡道时姿态估计会飘。我建议这时候强制AGV走平路。
  3. 重度降级：比如激光雷达和IMU都坏了。这时候只能靠编码器“盲走”。我会让AGV沿着预设的磁条或二维码路径走，速度降到0.2m/s，同时发出警报。
// 降级策略示例
void handleDegradation(SensorStatus status) {
    switch (status) {
        case LIDAR_FAILURE:
            setSpeed(0.5);  // 降速
            enableIMUAiding(true);  // 启用IMU辅助
            break;
        case IMU_FAILURE:
            setSpeed(0.3);
            enablePathConstraint(true);  // 强制走直线
            break;
        case ALL_FAILURE:
            setSpeed(0.1);
            enableEmergencyStop(true);  // 准备急停
            break;
    }
}

我的经验：降级策略一定要做“平滑切换”。我曾经见过一个AGV，激光雷达一坏，速度直接从1m/s降到0.1m/s，结果后面跟着的工人差点追尾。现在我都用“渐变降速”，比如每帧降0.1m/s，持续5帧。

28.4 知识体系总览

下面这张图是我自己画的，把故障诊断与容错的整个逻辑串起来了。你仔细看看，会发现每个环节都环环相扣。

你看，整个流程就是：传感器数据进来，先做故障检测。如果发现异常，立刻启用冗余设计来验证。确认故障后，执行降级策略。最后输出一个“虽然不完美但安全”的导航指令。

嗯，这套体系我用了好几年，帮我在好几个项目里避免了重大事故。最惊险的一次，AGV在自动化仓库里跑着，激光雷达突然被叉车撞歪了。还好冗余检测及时发现了，降级到编码器+磁条导航，AGV自己慢慢开回了维修区。要是没有这套机制，那天估计得赔几十万的货架。

最后说一句：故障诊断和容错不是“锦上添花”，而是“雪中送炭”。你花80%的精力做算法，可能只提升了10%的性能；但你花20%的精力做容错，能避免90%的事故。这笔账，你自己算算。
