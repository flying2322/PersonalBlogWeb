30 综合项目实战——从零搭建AGV导航系统、传感器融合调试、现场部署经验

终于到了最后一章。

前面29章，我们把理论、算法、传感器、滤波、标定、仿真全过了一遍。但说实话，真正让一个AGV跑起来，跟纸上谈兵完全是两码事。我记得第一次在工厂现场调试AGV时，那个场景至今难忘——激光雷达被叉车撞歪了，IMU数据飘得像喝醉了酒，轮式里程计打滑到怀疑人生。

这一章，我就带你走一遍完整的实战流程。从硬件选型、系统搭建，到传感器融合调试，再到现场部署踩坑。你想想看，如果能把这一套走通，基本上就能独立搞定一个AGV项目了。

核心目标：搭建一个基于多传感器融合的AGV导航系统，实现室内环境下的自主定位、路径跟踪与避障。融合传感器包括：2D激光雷达、IMU、轮式里程计、UWB（可选）。

30.2 传感器融合调试——那些年我踩过的坑

调试阶段是最磨人的。我分几个关键步骤来讲。

30.2.1 时间同步——第一道坎

为什么先说时间同步？因为所有融合算法都建立在「同一时刻的数据」上。如果时间戳对不上，融合结果就是一团浆糊。

我曾经在一个项目里，激光雷达用的是ROS时间戳，IMU用的是板载硬件时间戳，两者差了200多毫秒。结果AGV原地转圈时，融合出来的位姿居然在漂移。查了两天才发现是时间同步的问题。

我的做法：统一使用ROS的ros::Time::now()作为主时钟源。IMU数据到达时，用硬件时间戳减去一个固定的传输延迟（实测得到）。激光雷达数据则直接用接收时刻的时间戳。

代码示例——时间同步的核心逻辑：

// 时间同步回调函数
void sensorSyncCallback(
    const sensor_msgs::LaserScan::ConstPtr& laser_msg,
    const sensor_msgs::Imu::ConstPtr& imu_msg,
    const nav_msgs::Odometry::ConstPtr& odom_msg)
{
    // 检查时间差
    double dt_laser_imu = fabs(laser_msg->header.stamp.toSec() - 
                                imu_msg->header.stamp.toSec());
    double dt_laser_odom = fabs(laser_msg->header.stamp.toSec() - 
                                 odom_msg->header.stamp.toSec());
    
    // 如果时间差超过50ms，丢弃这帧数据
    if (dt_laser_imu > 0.05 || dt_laser_odom > 0.05) {
        ROS_WARN("时间同步超差: laser-imu=%.3f, laser-odom=%.3f", 
                 dt_laser_imu, dt_laser_odom);
        return;
    }
    
    // 执行融合
    fusionCore(laser_msg, imu_msg, odom_msg);
}

30.2.2 EKF参数调优——别被默认参数坑了

EKF的参数调起来真的很玄学。我刚开始用robot_localization包时，直接用了默认参数，结果定位精度惨不忍睹。

核心要调三个东西：

  • 过程噪声协方差矩阵Q——控制你对运动模型的信任程度
  • 测量噪声协方差矩阵R——控制你对传感器数据的信任程度
  • 初始协方差矩阵P——控制初始不确定性

我总结了一个经验公式：

传感器 测量噪声标准差（建议值） 说明
激光雷达（位置） 0.05 ~ 0.15 m 室内环境取小值，室外取大值
激光雷达（角度） 0.02 ~ 0.05 rad 取决于激光雷达角分辨率
IMU（加速度） 0.1 ~ 0.5 m/s² 低端IMU取大值
IMU（角速度） 0.01 ~ 0.05 rad/s 温漂严重时取大值
轮式里程计 0.02 ~ 0.10 m 打滑场景取大值

注意：千万别把Q和R设得太极端。Q太小会导致滤波器发散，R太大会让传感器数据几乎不起作用。我见过有人把R设成0.001，结果滤波器完全跟着激光雷达走，IMU和里程计全废了。

30.3 现场部署——从实验室到工厂的鸿沟

实验室里跑得好好的，一到现场就崩。这是常态。我经历过三次现场部署，每次都有新惊喜。

30.3.1 地面材质的影响

实验室是环氧地坪，工厂是水泥地，仓库是金刚砂地。轮式里程计的打滑特性完全不一样。

我的解决方案：

  • 部署前先做「打滑标定」——让AGV走一段已知距离，对比编码器读数与实际位移
  • 动态调整里程计噪声协方差——检测到打滑时自动增大R值

30.3.2 光照变化对激光雷达的影响

你可能觉得激光雷达不受光照影响。错！强光直射下，某些激光雷达的接收器会饱和，导致测距误差增大。

我记得有一次在仓库部署，下午三点阳光从窗户射进来，AGV在阳光区域定位突然跳变。排查后发现是激光雷达在强光下测距值偏大了5cm。

解决办法：在激光雷达上方加装遮光罩，或者在算法中剔除阳光直射方向的扫描点。

30.3.3 多AGV协同的干扰问题

多台AGV同时运行时，激光雷达之间会互相干扰。你发射的激光可能被另一台AGV接收，产生虚假点云。

我建议的做法：

  • 给每台AGV的激光雷达设置不同的调制频率（如果硬件支持）
  • 或者在时间上错开扫描周期
  • 最笨但有效的方法：在算法中做「一致性检查」，剔除短时间内变化过大的点

30.4 融合调试的实战流程

下面是我个人总结的调试流程，按顺序来，能省掉80%的排查时间。

  1. 单传感器验证——先确保每个传感器单独工作正常。激光雷达能建图吗？IMU静止时输出稳定吗？里程计走直线吗？
  2. 时间同步检查——录制bag包，用rostopic echo查看各传感器时间戳，确保偏差在50ms以内
  3. 静态融合测试——AGV静止不动，观察融合输出的位姿是否稳定。如果漂移超过1cm/s，说明参数有问题
  4. 直线运动测试——让AGV走一条10米直线，检查终点误差。我一般要求误差小于5cm
  5. 旋转测试——原地旋转360度，检查角度误差。要求小于3度
  6. 闭环测试——走一个矩形路径回到起点，检查闭环误差。这是最综合的测试
  7. 压力测试——连续运行8小时，观察定位精度是否随时间退化

避坑指南：我曾经跳过第1步，直接做融合测试。结果发现定位不准，排查了三天，最后发现是IMU的Z轴加速度计坏了。从那以后，我再也不敢跳过单传感器验证。
