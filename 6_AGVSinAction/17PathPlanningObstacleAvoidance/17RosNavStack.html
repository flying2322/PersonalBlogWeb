17 ROS导航栈详解：move_base框架、costmap_2d、global_planner与local_planner配置

各位同行，今天我们来聊聊ROS导航栈。说实话，这是AGV实战中最核心、也最容易出问题的一环。我见过太多团队，算法理论一套一套的，结果一上真车就撞墙。为什么？因为对导航栈的理解停留在表面。

ROS导航栈，说白了就是一个“大脑”。它告诉机器人：你在哪，要去哪，路上有没有坑，怎么绕过去。今天我就把move_base、costmap_2d、global_planner和local_planner这四块掰开揉碎了讲。

17.1 move_base：导航调度中心

move_base是整个导航栈的“项目经理”。它不干活，但它知道谁该干活。我个人习惯把move_base理解成一个状态机：接收目标点→调用全局规划器算路径→交给局部规划器跟踪→遇到障碍物触发重规划。

它的核心工作流程是这样的：

  • 接收目标：通过actionlib接口接收MoveBaseActionGoal
  • 全局规划：调用global_planner生成从起点到终点的路径
  • 局部跟踪：local_planner沿着全局路径走，同时避障
  • 状态反馈：实时发布机器人的位置、速度、规划状态

关键参数配置示例（move_base.launch）：

<node pkg="move_base" type="move_base" name="move_base" output="screen">
  <param name="base_global_planner" value="global_planner/GlobalPlanner"/>
  <param name="base_local_planner" value="dwa_local_planner/DWAPlannerROS"/>
  <param name="controller_frequency" value="10.0"/>
  <param name="planner_frequency" value="1.0"/>
  <param name="recovery_behavior_enabled" value="true"/>
</node>

这里有个坑：controller_frequency和planner_frequency的比值很关键。我曾经在一个项目中把planner_frequency设成5Hz，结果机器人每0.2秒就重规划一次，路径抖得像帕金森。后来改成1Hz，稳了。

17.2 costmap_2d：机器人的“电子皮肤”

costmap_2d，说白了就是一张带代价的栅格地图。每个格子都有一个代价值：0表示完全空闲，255表示绝对不可通行。机器人规划路径时，会尽量走代价值低的区域。

costmap_2d采用分层架构，我特别喜欢这个设计——各层各司其职：

层名称 作用 数据来源
静态地图层 加载预先建好的地图 map_server
障碍物层 实时检测动态障碍物 激光雷达、深度相机
膨胀层 给障碍物加“安全距离” 基于障碍物层计算
自定义插件层 比如禁止区域、减速区域 用户自定义

我的经验：膨胀半径的设置直接影响通过性。设太大，窄通道过不去；设太小，容易刮蹭。我一般取机器人半径的1.2倍作为起步值，然后根据实际测试微调。

配置costmap_2d时，observation_sources这个参数特别容易搞错。我记得有一次调试，激光雷达数据明明有，但costmap就是不更新。查了半天，发现是topic名字写错了——代码里写的是/scan，实际发布的是/lidar/scan。嗯，这种低级错误，谁没犯过呢？

17.3 global_planner：全局路径规划

global_planner负责在全局代价地图上找一条从起点到终点的路径。ROS默认用的是A*算法，也可以换成Dijkstra或其它。

我个人更倾向于A*，因为它在大多数场景下效率更高。但要注意：A*的启发函数设计不好，容易走“贴墙路径”。

global_planner参数调优：

GlobalPlanner:
  use_dijkstra: false          # true用Dijkstra，false用A*
  use_quadratic: true          # 二次近似，路径更平滑
  use_grid_path: false         # 是否只走网格线
  old_navfn_behavior: false    # 兼容旧版navfn
  visualize_potential: true    # 可视化势场，调试利器

这里有个技巧：visualize_potential设为true后，你可以在Rviz里看到势场图。颜色越亮表示代价值越高。我曾经靠这个功能，一眼就发现地图上有个“幽灵障碍物”——原来是静态地图层和障碍物层重叠导致的。

避坑指南：我曾经在一个工厂项目里，机器人总是绕远路。排查后发现是use_grid_path设为true，导致路径只能走网格线，无法斜着穿过去。改成false后，路径直接缩短了30%。

17.4 local_planner：局部轨迹跟踪

local_planner是真正“开车”的模块。它接收全局路径，然后结合当前传感器数据，实时生成速度指令。ROS里最常用的是DWA（Dynamic Window Approach）和TEB（Timed Elastic Band）。

DWA的原理很简单：在速度空间里采样，找一条“不撞墙、走得快、靠近目标”的轨迹。我刚开始学的时候觉得这算法太暴力了，后来发现——暴力往往最有效。

参数 作用 推荐值
max_vel_x 最大前进速度 0.5 ~ 1.0 m/s
min_vel_x 最小前进速度 0.0 ~ 0.1 m/s
max_vel_theta 最大旋转速度 0.5 ~ 1.0 rad/s
acc_lim_x X轴加速度限制 0.5 ~ 1.0 m/s²
acc_lim_theta 旋转加速度限制 0.5 ~ 1.0 rad/s²
sim_time 轨迹模拟时间窗口 1.5 ~ 3.0 s

为什么sim_time这么重要？你想想看，模拟时间太短，机器人只看眼前几步，容易钻死胡同；模拟时间太长，计算量暴增，实时性就保不住了。我一般取2.0秒作为基准值。

我的调试心得：如果你发现机器人原地打转，多半是yaw_goal_tolerance和xy_goal_tolerance设得太小。给点余量，别让机器人为了“精确到毫米”而反复调整。毕竟AGV不是精密机床，差个几厘米不影响干活。

17.5 四者协同：一个完整的导航周期

这四个模块是怎么配合的？我画个时间线你就明白了：

  1. 第0秒：move_base收到目标点，调用global_planner
  2. 第0.1秒：global_planner在costmap上算出一条全局路径
  3. 第0.1~10秒：local_planner每0.1秒（10Hz）跟踪路径，同时costmap实时更新障碍物
  4. 第3秒：前方突然出现一个箱子，costmap障碍物层更新
  5. 第3.1秒：local_planner检测到路径被堵，触发move_base的规划重试机制
  6. 第3.2秒：global_planner重新规划，绕开箱子
  7. 第10秒：到达目标点，move_base发布成功状态

这个过程中，costmap_2d是“眼睛”，global_planner是“大脑”，local_planner是“手脚”，move_base是“神经中枢”。缺一个，机器人就废了。

曾经踩过的坑：有一次我在一个仓库里测试，机器人总是突然急刹车。查了三天，发现是costmap的update_frequency设成了50Hz，而激光雷达只有10Hz。costmap在“空转”，每次更新都以为前方有障碍物。后来把更新频率降到10Hz，问题解决。

17.6 实战配置清单

最后，我整理了一份配置清单。你照着这个顺序调，基本不会出大问题：

  • 第一步：确认传感器数据正常（激光雷达、里程计、IMU）
  • 第二步：配置costmap_2d的静态层和障碍物层
  • 第三步：设置膨胀半径（建议从0.3m开始）
  • 第四步：配置global_planner（选A*，关闭grid_path）
  • 第五步：配置local_planner（DWA，sim_time=2.0）
  • 第六步：设置move_base的controller_frequency=10，planner_frequency=1
  • 第七步：在Rviz中观察，逐步微调

嗯，这套流程我用了好几年，基本没翻过车。当然，每个项目都有它的脾气，关键还是多试、多看、多总结。
