24 路径规划性能评估——五个维度，缺一不可

做AGV这么多年，我见过太多“看起来很美”的路径规划算法。

有的路径最短，但机器人走起来像喝醉了酒，左右摇摆；有的平滑得像丝绸，但计算时间够泡三杯咖啡。说白了，没有评估体系，你根本不知道自己的算法到底行不行。

这一章，我们就来聊聊路径规划的性能评估。我个人习惯从五个维度去衡量：路径长度、时间消耗、平滑度、安全距离、计算资源占用。这五个指标，就像汽车的五个轮子，少一个都跑不稳。

核心观点：性能评估不是“打分”，而是“找平衡”。没有完美的路径，只有最适合当前场景的路径。

24.1 路径长度——最直观，但别迷信

路径长度，说白了就是机器人从A点到B点走了多少米。这是最基础的指标，也是大家最先关注的。

但我要泼一盆冷水：最短路径≠最优路径。

我在项目中遇到过一件事：一条路径长度只有20米，但中间要经过一个狭窄的通道，每次通过都要减速到0.2m/s。另一条路径25米，全程可以跑0.8m/s。结果呢？长路径反而快了30%。

所以，路径长度要结合时间消耗一起看。单独看长度，容易掉坑里。

场景 路径长度（m） 实际耗时（s） 结论
狭窄通道绕行 20 45 短但慢
宽敞大路绕行 25 32 长但快

我的习惯：路径长度作为“硬约束”，先保证不超过某个上限，然后再去优化其他指标。

24.2 时间消耗——用户最关心的指标

用户不会关心你的A*算法用了多少毫秒，他们只关心“这趟货什么时候能送到”。时间消耗，是最终交付的KPI。

时间消耗包括两部分：

  • 规划时间：算法从启动到输出路径的耗时
  • 执行时间：机器人实际走完路径的耗时

你想想看，如果规划时间占了总时间的30%，那这个算法在动态场景下基本没法用。我记得有一次调试，规划时间从50ms优化到15ms，整个系统的响应速度直接上了一个台阶。

嗯，这里要注意：执行时间受速度曲线影响很大。同样的路径，加减速策略不同，时间能差20%。所以评估时，一定要统一速度模型。

24.3 平滑度——机器人“舒服”吗？

平滑度，说白了就是路径拐弯的“柔和程度”。

为什么重要？两个原因：

  1. 机械损耗：急转弯多，轮子磨损快，电机电流大
  2. 货物安全：AGV上如果载着液体或精密仪器，急转弯就是灾难

我常用的平滑度评估方法：

  • 曲率分析：计算路径上每个点的曲率，看最大值和平均值
  • 转角累计：整条路径所有转角的总和
  • 急转弯次数：曲率超过阈值的点有多少
# 一个简单的平滑度评估函数
def evaluate_smoothness(path):
    curvatures = []
    for i in range(1, len(path)-1):
        # 计算三点曲率
        dx1 = path[i][0] - path[i-1][0]
        dy1 = path[i][1] - path[i-1][1]
        dx2 = path[i+1][0] - path[i][0]
        dy2 = path[i+1][1] - path[i][1]
        
        angle = abs(math.atan2(dy2, dx2) - math.atan2(dy1, dx1))
        curvatures.append(angle)
    
    return {
        'max_curvature': max(curvatures),
        'avg_curvature': sum(curvatures)/len(curvatures),
        'sharp_turns': sum(1 for c in curvatures if c > 0.5)  # 阈值0.5弧度
    }

避坑指南：我曾经遇到过平滑度很好，但路径严重偏离最优解的情况。原因是过度平滑导致路径“膨胀”了。平滑度一定要在路径长度约束下优化，不能无限制追求平滑。

24.4 安全距离——命根子

安全距离，是AGV导航的底线。路径规划出来的轨迹，离障碍物到底有多远？

我一般用两个指标：

  • 最小安全距离：路径上离障碍物最近的那个点
  • 平均安全距离：整条路径与障碍物的平均距离

为什么两个都要看？

最小安全距离告诉你“最危险的地方在哪里”，平均安全距离告诉你“整体安全水平”。

举个例子：一条路径大部分地方离障碍物1米，但有一个地方只有5厘米。最小安全距离是5厘米，这个路径就是不合格的。反过来，如果最小安全距离是30厘米，但平均只有35厘米，说明整条路径都贴着障碍物走，也不安全。

场景 最小安全距离（cm） 平均安全距离（cm） 评价
仓库通道 15 40 ✅ 合格
狭窄货架区 8 12 ⚠️ 需谨慎
开放区域 50 80 ✅ 优秀

我的经验：安全距离的阈值要根据AGV的尺寸和定位精度来定。定位误差±5cm的AGV，安全距离至少留15cm。别问我怎么知道的，问就是撞过。

24.5 计算资源占用——别让算法“吃”光CPU

这个指标，很多初学者会忽略。但在实际部署中，计算资源占用往往决定了算法能不能落地。

我主要看三个维度：

  • CPU占用率：规划过程中CPU的使用百分比
  • 内存占用：算法运行时占用的内存大小
  • 规划耗时：单次规划从输入到输出的时间

你想想看，如果规划一次要500ms，而AGV的控制器周期是100ms，那整个系统就会被卡住。我见过一个项目，算法工程师在PC上跑得好好的，部署到工控机上直接卡死——因为工控机的CPU只有PC的1/4性能。

所以，我建议在评估时：

  1. 用目标硬件平台跑测试，别用开发机
  2. 记录峰值占用和平均占用
  3. 考虑多任务并发的情况（比如同时规划+定位+通信）

24.6 五个维度的综合评估框架

说了这么多，怎么把五个维度串起来？我画了一张图，你看一眼就明白了。

这张图想表达什么？五个维度不是孤立的，它们相互制约。路径短了，可能平滑度差；平滑度好了，可能计算资源占用高。你要做的，是根据实际场景找到那个“甜点”。

24.7 实战中的评估流程

说了这么多理论，来点实际的。我在项目中是怎么做评估的？

  1. 先跑基准测试：用同一组地图和起终点，跑10次取平均值
  2. 记录原始数据：五个维度的原始数值，不要做任何处理
  3. 归一化处理：每个维度映射到0-100分，方便对比
  4. 加权综合评分：根据场景需求设置权重，比如仓库场景安全距离权重0.4，时间权重0.3
  5. 可视化输出：用雷达图展示，一眼看出短板在哪

重要提醒：评估不是一次性的。算法迭代后，一定要重新跑全套测试。我见过有人只改了一个参数，结果路径长度优化了20%，但安全距离下降了50%——这就是没做全面评估的后果。

24.8 写在最后

路径规划性能评估，说白了就是给算法“体检”。五个维度就像五项检查指标，每一项都不能落下。

我个人习惯在项目初期就建立评估框架，而不是等到算法写完了再回头补。这样能避免很多弯路。你想想看，如果一开始就知道安全距离是瓶颈，你还会花两周去优化路径长度吗？

嗯，这一章的内容就到这里。评估这件事，做一次不难，难的是每次都做、每次都认真做。但相信我，养成这个习惯后，你的算法质量会有质的飞跃。

最后一个小技巧：把评估流程写成自动化脚本，每次修改算法后一键运行。省时省力，还能避免人为失误。
