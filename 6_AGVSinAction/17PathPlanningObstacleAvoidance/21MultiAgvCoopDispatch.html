21 多AGV协同调度：交通管制、资源分配、死锁避免、集中式与分布式调度

多AGV协同调度，说白了就是让一群机器人别打架。

我刚开始做这个方向时，觉得单台AGV跑得好好的，多几台不就是复制粘贴吗？结果第一次联调，三台车在十字路口堵成一锅粥，调度中心疯狂报错。嗯，从那以后我再也不敢小看协同调度了。

21.1 交通管制：别让AGV在路口“亲密接触”

交通管制是多AGV系统最基础的问题。你想想看，工厂里几十台AGV同时跑，路口就那么几个，不管理肯定乱套。

我个人习惯把交通管制分为两级：

  • 全局交通管制：基于地图的拓扑结构，预先规划好哪些路段是单行道，哪些路口需要互斥访问
  • 局部交通管制：实时检测AGV之间的冲突，动态调整通行顺序

我在项目中遇到过最典型的场景：一个T型路口，三台AGV同时到达。如果没有管制，它们会互相等待，形成死锁。

核心思路：把路口抽象成“资源”，AGV需要先申请资源才能进入。资源被占用时，其他AGV在路口前等待。

实现上，我常用的是预留表（Reservation Table）方法。每台AGV在进入路口前，先向调度中心申请一个时间窗口。调度中心检查这个时间窗口是否与其他AGV冲突，如果冲突则拒绝或调整。

// 伪代码：路口资源申请
bool RequestIntersection(AGV_ID, Intersection_ID, Time_Window) {
    // 检查该路口在Time_Window内是否已被占用
    if (ReservationTable[Intersection_ID].IsOccupied(Time_Window)) {
        return false;  // 冲突，拒绝
    }
    // 预留该时间窗口
    ReservationTable[Intersection_ID].Reserve(AGV_ID, Time_Window);
    return true;
}

避坑指南：我曾经把时间窗口设得太小，结果AGV因为加减速误差，实际通过时间超出预留窗口，导致碰撞风险。后来我加了20%的缓冲时间，问题就解决了。

21.2 资源分配：谁先谁后？这是个问题

资源分配不只是路口，还包括充电桩、装卸站、维修区等。说白了，就是多个AGV竞争有限资源时，怎么决定优先级。

我常用的分配策略有几种：

策略 原理 适用场景
先到先服务（FCFS） 谁先申请谁先用 资源充足，冲突少
优先级调度 根据任务紧急程度分配 有紧急订单的场景
最短路径优先 离资源最近的AGV优先 减少空跑距离
拍卖机制 AGV出价竞争资源 复杂动态环境

我个人比较喜欢优先级+最短路径的组合策略。举个例子：一台AGV正在执行紧急订单，另一台只是回充电桩。即使回充电桩的AGV离路口更近，我也会让紧急订单先过。

注意：优先级不能一成不变。我见过一个项目，高优先级AGV一直占用资源，低优先级AGV永远等不到，最后电池耗尽停在路中间。所以一定要加超时机制，当低优先级AGV等待超过阈值时，自动提升优先级。

21.3 死锁避免：别让AGV互相“锁死”

死锁是多AGV系统最头疼的问题。四台AGV在十字路口各占一条路，谁都不让谁，这就是典型的死锁。

死锁发生的四个必要条件：

  1. 互斥：资源一次只能被一台AGV占用
  2. 持有并等待：AGV占着一个资源，同时等待另一个资源
  3. 不可剥夺：资源不能被强制释放
  4. 循环等待：AGV之间形成等待环

打破任意一个条件就能避免死锁。我常用的方法有：

  • 资源排序法：给所有资源编号，AGV必须按编号顺序申请资源。这样就不会形成循环等待。
  • 超时回退法：AGV等待资源超过一定时间，自动后退让出已占用的资源。
  • 死锁检测+恢复：定期检测是否有死锁，发现后强制让一台AGV退出。

我的经验：资源排序法最简单可靠，但需要全局规划。超时回退法灵活，但可能造成AGV反复进退。死锁检测+恢复适合大型系统，但恢复过程可能影响生产效率。

我曾经在一个项目中遇到死锁问题，排查了两天才发现：两台AGV在一条窄道上面对面相遇，谁都不肯倒车。后来我加了“窄道会车协议”——谁离出口近谁先走，另一个倒车让路。问题就解决了。

21.4 集中式调度：一个大脑管所有

集中式调度，就是有一个中央调度中心，掌握所有AGV的状态和任务信息，统一规划路径和分配资源。

优点很明显：

  • 全局最优：能看到全局信息，做出最优决策
  • 实现简单：所有逻辑集中在一处，调试方便
  • 冲突少：中央调度可以提前规避冲突

缺点也很突出：

  • 单点故障：中央挂了，所有AGV都停摆
  • 计算压力大：AGV数量多时，调度周期变长
  • 通信延迟：AGV和中央之间频繁通信，网络压力大

我做过一个集中式调度系统，管理30台AGV。刚开始还好，后来加到50台，调度周期从100ms变成了500ms，AGV反应明显变慢。嗯，这就是集中式的瓶颈。

21.5 分布式调度：各自为战，协同合作

分布式调度没有中央大脑，每台AGV自己决策，通过通信协商解决冲突。

常见实现方式：

  • 合同网协议：任务发布者广播任务，AGV投标，发布者选择最合适的AGV
  • 共识算法：AGV之间通过投票决定谁先通过路口
  • 市场机制：AGV用虚拟货币竞拍资源

我的建议：分布式调度适合AGV数量多、环境变化快的场景。但实现复杂度高，调试困难。我建议先从集中式做起，等系统稳定了再逐步引入分布式元素。

我个人习惯用混合架构：中央调度负责全局路径规划和资源分配，AGV本地负责局部避障和冲突协商。这样既保证了全局最优，又提高了实时性。

数量少（10台以内）用集中式就够了。数量多（50台以上）必须引入分布式。中间状态用混合架构最稳妥。
