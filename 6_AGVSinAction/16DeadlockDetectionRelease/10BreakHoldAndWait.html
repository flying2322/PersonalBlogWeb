10 死锁预防：破坏占有并等待（一次性申请所有资源）

死锁预防，说白了就是「从根上不让死锁发生」。

今天聊的这种方法，我个人觉得是最直观的一种——一次性申请所有资源。它的核心思想很简单：要么不给，要么全给。

10.1 什么是「占有并等待」？

先回顾一下死锁的四个必要条件。其中第二个条件就是「占有并等待」。

什么意思呢？

一个AGV已经占着某个资源（比如一段路径），但它不放手，还在等另一个资源（比如一个工位）。这就是典型的「占着茅坑不拉屎」。

我在项目中遇到过这种情况：两台AGV在十字路口相遇，A车占了东侧路段，B车占了西侧路段。两车都想往北走，但谁也不让谁。结果就是——死锁。

为什么会这样？因为每台车都是「先占一个，再等一个」。

10.2 一次性申请：打破「占有并等待」

破坏这个条件的方法，就是让AGV一次性申请所有需要的资源。

也就是说：

  • AGV在开始执行任务前，必须把整条路径上所有需要的资源都申请到手
  • 如果有一个资源申请不到，那就一个资源都不给
  • AGV要么拥有全部资源，要么一个都没有

嗯，这里要注意：这个「资源」不光是物理路径段，还包括工位、充电站、缓冲区等。

核心原则：资源分配要么全有，要么全无。不存在「先占一点，再等一点」的状态。

10.3 具体怎么实现？

我建议用资源预分配表来实现。每台AGV在出发前，先计算好它要走的路径，然后向调度系统申请整条路径上的所有资源。

伪代码大概是这样的：

// AGV任务请求
AGV task_request(agv_id, path_segments) {
    // 一次性申请所有路径段
    for each segment in path_segments {
        if (!request_resource(segment)) {
            // 只要有一段申请不到，就释放所有已申请的资源
            release_all_resources();
            return FAILED;
        }
    }
    // 全部申请成功，开始执行
    return SUCCESS;
}

你看，逻辑很清晰。申请不到就全部释放，绝不拖泥带水。

10.4 优点与缺点

优点 缺点
实现简单，逻辑直观 资源利用率低，容易造成资源浪费
彻底杜绝死锁 AGV等待时间长，可能阻塞后续任务
调度系统负担小 不适合长路径、多AGV的场景

我曾经在一个仓库项目里试过这种方法。仓库不大，AGV也就6台，路径也短。刚开始效果不错，死锁确实没了。但后来业务量上来，AGV增加到12台，问题就来了——AGV经常在起点等资源，一等就是十几秒，效率直线下降。

避坑指南：我曾经以为「一次性申请」是万能药。后来发现，它只适合路径短、AGV数量少、资源竞争不激烈的场景。如果你的系统有20台以上AGV，或者路径长度超过50米，建议慎用。

10.5 适用场景分析

那么，什么情况下适合用这种方法？

  • 小规模系统：AGV数量在10台以内
  • 短路径任务：单次任务路径长度不超过30米
  • 资源竞争不激烈：工位、充电站等资源充足
  • 对死锁零容忍：某些特殊场景（如危险品运输）不允许任何死锁风险

你想想看，如果你的系统符合这些条件，那一次性申请确实是个好选择。简单、可靠、容易维护。

10.7 实际项目中的一点体会

说实话，我在实际项目中很少单独用这种方法。更多时候，我会把它和资源预留、优先级调度结合起来用。

比如：

  • 高优先级的AGV可以一次性申请资源，低优先级的AGV则用其他方式
  • 或者，只在关键路径段（比如窄通道、单行道）使用一次性申请
  • 其他普通路径段，允许AGV分段申请

这样既避免了死锁，又不至于把资源利用率压得太低。

小技巧：如果你决定用一次性申请，建议给AGV设置一个「最大等待时间」。超过这个时间还没申请到全部资源，就让AGV放弃当前任务，去做其他事情。这样可以避免AGV在起点干等。

10.8 总结

一次性申请所有资源，是死锁预防里最直接的方法。它简单、可靠，但代价是资源利用率低。

我个人觉得，它最适合的场景是：小系统、短路径、低竞争。如果你的系统符合这些条件，不妨试试看。

如果不符，也别硬套。后面我们会聊到其他预防方法，比如资源排序、超时回退等，总有一款适合你。
