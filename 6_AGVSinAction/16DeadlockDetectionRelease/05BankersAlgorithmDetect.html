5 死锁检测算法：银行家算法在AGV调度中的应用

说到死锁检测，我第一个想到的就是银行家算法。这名字听着挺金融的，对吧？其实它最早确实是给操作系统设计的，用来避免多个进程争抢资源时卡死。后来我做AGV调度系统时发现，这玩意儿搬到咱们AGV场景里，简直天造地设的一对。

你想想看，AGV要抢的是路径资源，进程要抢的是内存或CPU。本质上一模一样——都是多个主体竞争有限资源，搞不好就互相堵死。我当年在做一个大型仓储项目时，就亲眼见过6台AGV在交叉路口堵成一团，调度中心怎么发指令都解不开。后来我硬是把银行家算法嵌进了调度模块，才彻底根治了这个问题。

5.1 银行家算法的核心思想

银行家算法的逻辑其实很朴素。它模拟了一个场景：银行家手里有一笔钱，多个客户来贷款。银行家不会一次性把钱全借出去，而是留一部分备用。每次客户申请贷款时，银行家会先算一笔账——如果我把钱借给你，剩下的钱还能不能保证其他客户完成他们的业务？如果不行，就拒绝这次申请。

放到AGV调度里，这个逻辑就变成了：

  • 银行家 = 调度系统
  • 资金总额 = 所有可用的路径段资源
  • 客户 = 每一台AGV
  • 贷款申请 = AGV请求前方路径段
  • 业务完成 = AGV到达目标站点并释放资源

说白了，调度系统在给AGV分配路径之前，先模拟一下：如果我把这段路给你，剩下的资源够不够让所有AGV都跑完？如果不够，那就先不给你，让你原地等着。

关键点：银行家算法不是等死锁发生了再去解，而是在分配资源之前就判断会不会导致死锁。这是一种预防性策略，比事后检测要优雅得多。

5.2 算法中的数据结构

要实现银行家算法，我们需要维护几张表。我在项目中习惯用以下数据结构：

数据结构 含义 AGV场景中的对应
Available 当前可用资源向量 当前空闲的路径段数量
Max 每个AGV最大需求矩阵 每台AGV完成任务所需的最大路径段数
Allocation 已分配资源矩阵 每台AGV当前占用的路径段
Need 每个AGV还需要的资源矩阵 每台AGV剩余行程需要的路径段

这里有个小细节要注意：Need = Max - Allocation。这个公式看起来简单，但我在实际项目中踩过坑——有些同事把Need理解成了"还需要多少资源才能到达下一个站点"，而不是"完成整个任务还需要多少"。这两个概念差远了，搞错了算法就完全失效。

5.3 安全性检查算法

银行家算法的核心是安全性检查。每次AGV申请资源时，调度系统会执行以下步骤：

  1. 检查申请是否超过Need（如果超过了，说明AGV的请求不合理，直接拒绝）
  2. 检查申请是否超过Available（如果超过了，说明当前资源不够，让AGV等待）
  3. 尝试分配资源，进入一个"预分配"状态
  4. 在预分配状态下，运行安全性检查算法
  5. 如果安全性检查通过，正式分配资源；否则回滚，拒绝申请

安全性检查算法长这样：

// 安全性检查算法伪代码
bool isSafeState(AGV[] agvs, Resource[] available) {
    Work = available;  // 工作向量，模拟资源分配过程
    Finish = [false, false, ..., false];  // 标记每台AGV是否完成

    // 找一个能完成的AGV
    for (int i = 0; i < agvs.length; i++) {
        if (!Finish[i] && Need[i] <= Work) {
            // 假设这台AGV完成，释放它占用的资源
            Work += Allocation[i];
            Finish[i] = true;
            i = -1;  // 从头开始找下一个能完成的
        }
    }

    // 检查是否所有AGV都能完成
    for (int i = 0; i < agvs.length; i++) {
        if (!Finish[i]) return false;  // 有AGV无法完成，不安全
    }
    return true;  // 所有AGV都能完成，安全
}

这段代码我当年手写过不下十遍。它的核心逻辑就是：模拟释放资源，看能不能让所有AGV都跑完。如果能，说明当前状态是安全的；如果不能，说明这个资源分配方案会导致死锁。

我的经验：在实际项目中，安全性检查不能做得太频繁。每台AGV每移动一步都检查一次的话，调度系统的CPU负载会飙升。我一般设置一个检查周期——比如每5秒检查一次，或者当AGV数量变化时才触发检查。这样既保证了安全性，又不会拖垮系统。

5.4 银行家算法的AGV适配改造

把银行家算法从操作系统搬到AGV调度，不能生搬硬套。我做过几个项目后，总结出几个必须改造的地方：

  • 资源粒度问题：操作系统里的资源是内存页、文件句柄，粒度比较粗。AGV的路径资源是连续的路径段，粒度很细。我建议把路径按交叉口分段，每段作为一个资源单位。
  • 资源释放时机：AGV不是一次性释放所有资源的。它每经过一个路径段，就会释放该段，同时申请下一段。所以Allocation和Need是动态变化的，需要实时更新。
  • 优先级问题：银行家算法默认所有进程平等。但AGV有优先级——紧急任务、充电任务、普通任务，优先级不一样。我改造时给每个AGV加了一个权重系数，安全性检查时优先满足高优先级AGV。
避坑指南：我曾经在一个项目中，直接把操作系统的银行家算法代码搬过来用。结果发现AGV的路径资源是"可抢占"的——比如一台AGV占用了A段，但它还没到B段，另一台AGV可以先申请B段。这种"部分资源可共享"的特性，标准银行家算法处理不了。后来我加了一个"资源类型标记"，把路径段分为"独占型"和"共享型"，才解决了这个问题。

5.5 一个简单的示例

假设我们有3台AGV，系统总共有10个路径段资源。当前状态如下：

AGV Max（最大需求） Allocation（已分配） Need（还需要）
AGV-1 5 2 3
AGV-2 4 2 2
AGV-3 6 3 3

当前Available = 10 - (2+2+3) = 3个空闲路径段。

现在AGV-1申请2个路径段。调度系统先检查：2 <= Need(3) 且 2 <= Available(3)，通过。然后预分配，进入安全性检查：

  • Work = Available - 2 = 1
  • AGV-2的Need(2) > Work(1)，无法完成
  • AGV-3的Need(3) > Work(1)，无法完成
  • AGV-1的Need(3-2=1) <= Work(1)，可以完成。释放资源：Work = 1 + (2+2) = 5
  • AGV-2的Need(2) <= Work(5)，可以完成。释放资源：Work = 5 + 2 = 7
  • AGV-3的Need(3) <= Work(7)，可以完成

所有AGV都能完成，安全！所以AGV-1的申请被批准。

你看，这个例子虽然简单，但已经能说明银行家算法的精髓了——它不是在"有没有资源"这个层面做判断，而是在"给了你之后，别人还能不能活"这个层面做判断。这种全局视角，正是AGV调度系统最需要的。

5.6 银行家算法的局限性

说了这么多好处，我也得泼点冷水。银行家算法不是万能的，我在实际使用中发现了几个问题：

  • 需要预知最大需求：AGV必须提前知道它整个行程需要多少路径段。这在固定路径的仓储场景还好说，但在动态路径规划的柔性产线里，AGV的路径是实时计算的，最大需求根本没法提前知道。
  • 资源利用率偏低：银行家算法偏保守，为了安全会拒绝一些实际上不会导致死锁的请求。说白了就是"宁可错杀一千，不可放过一个"。在资源紧张的系统里，这会导致AGV频繁等待，影响效率。
  • 计算复杂度高：AGV数量一多，安全性检查的循环次数就上去了。我测过，50台AGV时，每次检查大约需要0.5ms，还能接受。但到了200台，就飙到5ms了。对于实时性要求高的系统，这个开销不能忽视。
我的建议：银行家算法最适合用在AGV数量不多（20台以内）、路径相对固定的场景。如果AGV数量多或者路径动态变化，我建议改用"资源预留"或"死锁检测+恢复"的策略。后面几章我会详细讲这些替代方案。
