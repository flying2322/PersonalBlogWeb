19 死锁检测与解除实战：多交叉路口场景下的死锁处理

各位同行，今天我们来聊一个实战性很强的话题——多交叉路口场景下的死锁处理。

说实话，单路口死锁其实不难处理。但一旦场景变成多交叉路口，情况就复杂多了。我早期做AGV调度系统时，就吃过这个亏。当时觉得单路口死锁检测搞定了，结果多路口场景一上线，系统直接卡死，调度台上一片红。

嗯，那今天我就把这段经验拆开来讲。

19.1 多交叉路口死锁的本质

先想一个问题：多交叉路口死锁和单路口死锁，到底有什么区别？

单路口死锁，说白了就是几台车在同一个路口互相堵着。但多路口场景下，死锁可能跨越多个路口，形成一条“死锁链”。

举个例子：

  • 车A占着路口1，想去路口2
  • 车B占着路口2，想去路口3
  • 车C占着路口3，想去路口1

你看，这三台车不在同一个路口，但形成了一个环路。这就是多交叉路口死锁的典型特征——资源依赖链跨越多个节点。

核心要点：多交叉路口死锁检测，本质上是检测有向图中的环路。每个路口是一个节点，每台车的路径请求是一条有向边。

19.2 死锁检测算法：从单路口到多路口

我个人习惯用资源分配图（RAG）来做死锁检测。这个方法在单路口场景下很简单，但多路口场景需要扩展。

具体怎么做？我分三步来讲。

19.2.1 构建资源分配图

每个路口是一个资源节点。每台AGV请求占用某个路口，就画一条从AGV到资源节点的边。如果AGV已经占用了路口，就画一条从资源节点到AGV的边。

伪代码如下：

// 构建资源分配图
class ResourceAllocationGraph {
    Map<String, List<String>> adjacencyList;
    
    void addRequest(String agvId, String intersectionId) {
        // AGV请求路口：AGV -> 路口
        adjacencyList.get(agvId).add(intersectionId);
    }
    
    void addAllocation(String intersectionId, String agvId) {
        // 路口已分配给AGV：路口 -> AGV
        adjacencyList.get(intersectionId).add(agvId);
    }
}

19.2.2 环路检测

有了图之后，死锁检测就变成了环路检测。我用的是DFS（深度优先搜索）加染色法。

这里有个坑——我曾经以为只要检测到环路就是死锁，结果误报率很高。为什么呢？因为有些环路是暂时的，AGV正在移动中，环路会自然解除。

避坑指南：检测到环路后，必须判断环路中的每台AGV是否都处于“等待”状态。如果有一台AGV正在移动，这个环路就不是死锁。

改进后的检测逻辑：

boolean detectDeadlock(Graph graph) {
    List<List<String>> cycles = graph.findCycles();
    
    for (List<String> cycle : cycles) {
        boolean allWaiting = true;
        for (String node : cycle) {
            if (node.startsWith("AGV")) {
                AGV agv = getAgvById(node);
                if (agv.getState() != AGVState.WAITING) {
                    allWaiting = false;
                    break;
                }
            }
        }
        if (allWaiting) {
            return true;  // 真正的死锁
        }
    }
    return false;
}

19.2.3 多路口场景的特殊处理

多路口场景下，资源分配图会变得很大。我遇到过一张图里有50多个节点、上百条边的情况。这时候DFS的效率就很重要了。

我的优化策略：

  • 按区域分图：把整个工厂分成几个区域，每个区域单独建图。区域间的死锁单独处理。
  • 增量检测：不是每次都要全图扫描。只在AGV状态变化时，从变化节点开始局部检测。
  • 超时机制：如果检测时间超过50ms，直接判定为潜在死锁，先做预防性处理。

个人经验：增量检测能减少80%以上的计算量。但要注意，局部检测可能漏掉跨区域的环路。我的做法是：局部检测每5次，做一次全量检测兜底。

19.3 死锁解除策略：多路口场景下的选择

检测到死锁后，怎么解除？多路口场景下，解除策略比单路口复杂得多。

我常用的三种策略：

策略 适用场景 代价 我的评价
资源抢占 环路中有空闲路口 低 首选，但需要预留备用路径
AGV回退 环路中有可倒车的AGV 中 需要AGV支持倒车功能
路径重规划 以上都不行 高 最后手段，影响面大

19.3.1 资源抢占策略

资源抢占的核心思路是：找到环路中“代价最小”的AGV，让它让出占用的路口。

怎么定义“代价最小”？我一般看三个指标：

  1. 任务紧急度：紧急任务优先保留
  2. 距离最近备用路径的距离：越近越好
  3. 当前电量：低电量AGV优先保留

代码实现：

AGV selectVictim(List<AGV> deadlockedAgvs) {
    return deadlockedAgvs.stream()
        .min(Comparator.comparingInt(agv -> {
            int score = 0;
            score += agv.getTaskUrgency() * 10;   // 紧急度权重
            score += agv.distanceToAlternatePath(); // 距离权重
            score += (100 - agv.getBatteryLevel()); // 电量权重
            return score;
        }))
        .orElse(null);
}

19.3.2 AGV回退策略

如果AGV支持倒车，回退策略其实很有效。但要注意：回退不是简单的原路返回。

我在项目中遇到过一个问题：AGV回退时，后面的路口可能已经被其他AGV占用了。所以回退前必须做路径可用性检查。

回退流程：

  1. 标记死锁环路中的所有AGV
  2. 选择回退距离最短的AGV
  3. 检查回退路径上的路口是否可用
  4. 如果可用，执行回退；否则换一个AGV
  5. 回退完成后，重新检测死锁

注意：回退策略不能用于重载AGV。重载AGV倒车容易导致货物倾斜。我一般会在AGV配置里加一个“allowBackup”字段，只有轻载或空载AGV才允许回退。

19.3.3 路径重规划策略

这是最后的手段。当资源抢占和回退都不行时，只能让中央调度系统重新规划路径。

路径重规划的影响面比较大，因为：

  • 可能影响其他区域的AGV
  • 需要重新计算全局路径
  • 可能导致新的死锁

我的做法是：先局部重规划，不行再全局重规划。局部重规划只修改死锁环路中AGV的路径，其他AGV保持不变。

19.4 实战案例：一个三路口死锁的处理

讲个真实案例。去年我在一个汽车零部件工厂做项目，工厂有3个交叉路口呈三角形分布。某天生产高峰期，3台AGV在三个路口形成了死锁。

死锁情况：

  • AGV-01：占路口A，要去路口B
  • AGV-02：占路口B，要去路口C
  • AGV-03：占路口C，要去路口A

检测到死锁后，系统先尝试资源抢占。但三个路口都没有空闲的备用路径。然后尝试AGV回退，但AGV-03是重载状态，不允许倒车。

最后只能走路径重规划。我让系统重新计算了AGV-02的路径，让它绕过一个路口，从另一条路去路口C。死锁立刻解除。

经验总结：多路口死锁的解除，往往只需要打破环路中的一个点。找到那个“代价最小”的突破口，问题就解决了。

19.5 死锁预防：比解除更重要

说实话，死锁解除做得再好，也不如预防来得实在。我在项目中总结了几条预防措施：

  1. 路径预留：AGV进入路口前，提前预留后续路口的资源
  2. 最大等待时间：AGV在路口等待超过阈值，自动触发重新规划
  3. 流量控制：每个路口同时进入的AGV数量不超过3台
  4. 死锁预测：基于当前路径和速度，预测未来5秒内可能出现的死锁

其中，死锁预测是我觉得最有价值的。它用到了我们之前讲过的“资源分配图”思想，但提前了5秒做检测。这5秒足够系统做预防性调整。

我的建议：死锁检测和预防要配合使用。预防能挡住80%的死锁，检测负责兜底剩下的20%。别指望单靠一种方法解决所有问题。

19.6 本章小结

多交叉路口死锁处理，核心就三点：

  • 检测：用资源分配图加DFS，注意区分真死锁和暂时环路
  • 解除：优先资源抢占，其次AGV回退，最后路径重规划
  • 预防：路径预留、流量控制、死锁预测，三管齐下

嗯，这些方法我在多个项目里验证过，效果都不错。但每个工厂的布局不一样，AGV型号也不一样，具体实现时还是要根据实际情况调整。
