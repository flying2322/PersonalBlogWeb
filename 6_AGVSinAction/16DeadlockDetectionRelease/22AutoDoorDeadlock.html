22 死锁检测与解除实战：AGV与自动门交互的死锁处理

各位好，我是老张。今天咱们聊一个实战性很强的话题——AGV和自动门之间的死锁处理。

说实话，自动门这个场景，是我在项目里踩坑最多的地方之一。你想想看，AGV要进门，门要等AGV到位才开，AGV又等门开了才走……这不就是典型的“你等我、我等你”吗？搞不好就死锁了。

22.1 自动门交互中的典型死锁场景

先说说最常见的几种情况。我在某物流仓库项目里，遇到过三次类似的死锁，每次排查都花了大半天。

  • 场景一：双向门互锁——两台AGV同时从门的两侧请求通过，门只能开一边，结果两边都进不去。
  • 场景二：门状态丢失——AGV到达门前，门控系统没反馈“已打开”，AGV就一直等，后面的车也堵上了。
  • 场景三：优先级反转——低优先级的AGV先占了门资源，高优先级的车在后面干瞪眼，形成连锁阻塞。

嗯，这里要注意：自动门死锁和普通路径死锁不一样。普通死锁是“路被堵死了”，自动门死锁是“资源被占着但不释放”。

核心区别：自动门死锁涉及的是资源锁，不是路径锁。AGV可能停在门的一侧，但门资源被另一台车占着，谁也动不了。

22.2 死锁检测：怎么发现门交互死锁？

我个人习惯用资源等待图来检测。说白了，就是画一张图，看谁在等谁。

举个例子：

AGV_A → 门1（等待门1打开）
AGV_B → 门1（等待门1打开）
门1 → AGV_A（等待AGV_A离开感应区）

你看，这形成了一个环：AGV_A等门1，门1等AGV_A。死锁了。

我在实际项目中，会在调度系统里维护一张门资源占用表，每100ms扫描一次。如果发现某个门资源被占用超过5秒，且没有AGV在移动，就触发检测逻辑。

我的经验：不要等到死锁发生了再检测。我一般设置一个“预检测”机制——当AGV在门前等待超过2秒，就提前标记为“潜在死锁”，开始走预防流程。

22.3 死锁解除：四种实战策略

好，检测到了死锁，怎么解？我总结了一套“四步走”策略，按优先级排序：

策略 适用场景 操作方式 风险等级
策略一：优先级抢占 多台AGV争同一扇门 低优先级AGV让行，先退后 低
策略二：门状态强制复位 门控系统反馈丢失 调度系统强制发送“门已开”信号 中
策略三：路径重规划 门被长时间占用 让AGV绕行其他门或路径 中
策略四：AGV强制回退 以上都无效 让AGV倒车离开门区 高

我曾经在一个项目中，策略一和策略二都试过了，死锁还是解不开。最后发现是门控系统的PLC程序有bug——门明明开了，但状态位没更新。嗯，那次之后我加了个“门状态双重确认”机制。

22.4 实战代码：死锁检测与解除示例

下面是我在项目里用的一段简化代码，核心逻辑都在了：

// 死锁检测：扫描门资源等待图
bool detectDoorDeadlock() {
    for each door in doorList {
        if (door.occupiedBy != null) {
            AGV agv = door.occupiedBy;
            if (agv.status == WAITING_FOR_DOOR && 
                agv.waitingDoor == door) {
                // 发现循环等待
                logDeadlock(agv, door);
                return true;
            }
        }
    }
    return false;
}

// 死锁解除：优先级抢占
void resolveDoorDeadlock(AGV lowPriorityAGV, Door door) {
    // 让低优先级AGV后退3米
    lowPriorityAGV.executeCommand("BACKWARD", 3.0);
    // 释放门资源
    door.release();
    // 通知高优先级AGV通过
    highPriorityAGV.executeCommand("PASS_DOOR", door.id);
}

注意：强制回退策略一定要加安全距离检测。我曾经见过一台AGV倒车时撞到后面的车，就是因为没检查后方障碍物。现在我的代码里，回退前必须做三次超声波测距。

22.5 避坑指南：我踩过的三个坑

讲几个真实教训：

  • 坑一：门超时时间设太短。 有一次我把门等待超时设为3秒，结果AGV在门前稍微减速就被判定为死锁，频繁触发解除流程，系统乱成一锅粥。后来改成8秒，问题解决。
  • 坑二：没考虑多门联动。 有些仓库里，两扇门是联动的——开一扇必须关另一扇。我一开始没处理这个逻辑，结果死锁检测一直误报。
  • 坑三：死锁解除后没恢复路径。 强制让AGV后退后，原来的路径就断了。如果不重新规划，AGV会卡在半路上。我现在每次解除死锁后，都会自动触发一次路径重规划。

个人建议：在实际部署时，把死锁检测和解除做成独立的微服务。这样即使主调度系统挂了，死锁处理模块还能独立运行，不至于整个仓库瘫痪。我在上一个项目就是这么干的，效果不错。
