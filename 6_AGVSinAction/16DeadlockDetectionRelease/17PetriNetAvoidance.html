17 死锁避免：基于Petri网的建模与死锁避免

说实话，死锁检测与解除，就像消防队救火——火已经烧起来了，你再怎么扑救，损失已经造成了。那有没有办法让火根本烧不起来？

这就是死锁避免要做的事。我个人习惯，在系统设计阶段就把死锁扼杀在摇篮里。而Petri网，是我用过的最顺手的工具之一。

17.1 为什么是Petri网？

你想想看，AGV调度系统本质上是个什么？是一堆资源（路径段、站点、充电桩）被一堆任务（AGV小车）争抢的过程。这不就是典型的并发系统吗？

Petri网天生就是干这个的。它用四个基本元素就能描述整个系统：

  • 库所（Place）：表示资源状态，比如“路段A空闲”、“充电桩1被占用”
  • 变迁（Transition）：表示事件或动作，比如“AGV进入路段A”、“AGV离开充电桩”
  • 有向弧（Arc）：表示资源流向
  • 托肯（Token）：表示资源实例，比如AGV本身、路段可用数量

我在项目中遇到过好几次，用状态机画死锁条件，画着画着自己都绕晕了。换成Petri网之后，逻辑一下子就清晰了。

17.2 用Petri网建模AGV系统

咱们拿一个最简单的场景举例：两辆AGV，要经过一个十字路口。路口只有一条车道，一次只能过一辆车。

这个系统的Petri网模型长这样：

库所定义：
P1: AGV1 在路口前等待
P2: AGV2 在路口前等待  
P3: 路口空闲（初始有1个托肯）
P4: AGV1 通过路口
P5: AGV2 通过路口

变迁定义：
T1: AGV1 进入路口
T2: AGV2 进入路口
T3: AGV1 离开路口
T4: AGV2 离开路口

弧连接：
P1 → T1, T1 → P3(消耗), T1 → P4
P2 → T2, T2 → P3(消耗), T2 → P5
P4 → T3, T3 → P3(释放)
P5 → T4, T4 → P3(释放)

嗯，这里要注意：P3初始有1个托肯，代表路口只能被一辆车占用。T1和T2同时触发时，只有一个能拿到P3的托肯，另一个就得等着。这不就是互斥访问吗？

核心思想：Petri网中的资源库所（P3）的托肯数量，直接对应了系统中可用资源的数量。死锁发生的本质，就是多个进程各自占有一部分资源，同时又等待对方释放资源，形成循环等待。

17.3 死锁避免的Petri网方法

有了模型，怎么避免死锁？我常用的方法有三种：

17.3.1 可达性分析

说白了，就是把所有可能的状态都枚举一遍。如果某个状态是死锁状态（没有任何变迁可以触发），那就在系统设计阶段把这个状态对应的路径剪掉。

举个例子，如果系统有5个库所、3个变迁，理论上最多有2^5=32种状态。实际中会少很多，因为很多状态不合法。我建议用工具自动分析，手工算太容易出错了。

17.3.2 库所不变量（P-Invariant）

这个方法更优雅。库所不变量是指：某些库所中的托肯总数，在整个系统运行过程中保持不变。

比如上面那个例子，P1+P3+P4 的托肯总数始终是1（AGV1要么在等待，要么在占用路口，要么已经通过）。P2+P3+P5 的托肯总数也始终是1。

如果发现某个不变量被打破了，那就意味着资源分配出了问题，死锁可能就要来了。

避坑指南：我曾经在一个项目中，只关注了单个资源的不变量，忽略了跨资源的全局不变量。结果系统跑着跑着就卡死了。后来把所有资源的不变量都列出来，才发现有一个隐藏的循环依赖。所以，一定要检查全局不变量！

17.3.3 控制策略插入

这是最实用的方法。在Petri网模型中，插入额外的控制库所和变迁，强制系统避开死锁状态。

比如，在AGV进入路口前，加一个“信号灯”库所。只有信号灯是绿灯时，AGV才能进入。这个信号灯的逻辑，就是根据当前系统状态动态调整的。

控制策略示例：
IF (AGV1在等待 AND AGV2在等待) THEN
    优先放行AGV1（因为AGV1的目的地更近）
ELSE
    正常通行
END IF

17.4 一个完整的Petri网死锁避免流程

我总结了一套标准流程，每次做新项目都这么走：

  1. 建模：把AGV系统抽象成Petri网，定义库所、变迁、弧和初始托肯
  2. 分析：用可达图或矩阵方程，找出所有可能的状态
  3. 标记：标记出死锁状态和临界状态（再走一步就死锁的状态）
  4. 设计：针对每个临界状态，设计控制策略，阻止系统进入死锁状态
  5. 验证：重新分析加入控制策略后的Petri网，确认死锁状态不再可达
  6. 实现：把控制策略翻译成调度系统的代码逻辑

注意：控制策略不能太保守。我见过有人为了避免死锁，把所有并发路径都串行化了。系统确实不死锁了，但效率也降到了原来的1/10。死锁避免的目标是“安全且高效”，不是“安全但低效”。

17.6 实际项目中的经验

最后分享一点实战经验。Petri网建模死锁避免，理论很完美，但落地时要注意几个坑：

  • 模型规模爆炸：AGV数量一多，状态空间指数级增长。我建议用分层Petri网，先建模单个路口，再组合成整个厂区
  • 实时性要求：死锁避免决策必须在毫秒级完成。离线分析可以慢慢算，在线控制必须快
  • 异常处理：AGV可能故障、路径可能被临时占用。Petri网模型要预留异常处理变迁

我的习惯：每次上线新系统，我都会先跑一个月的死锁监控日志。看看实际运行中，Petri网模型预测的临界状态是否真的出现了。如果出现了，就说明控制策略还有优化空间。这套方法帮我避免了好几次生产事故。

好了，Petri网死锁避免就讲到这里。说白了，它就是一套“先建模、再分析、后控制”的方法论。工具本身不复杂，关键是你能不能把AGV系统的资源竞争关系，准确地映射到Petri网的库所和变迁上。这一步做好了，死锁避免就成功了一大半。
