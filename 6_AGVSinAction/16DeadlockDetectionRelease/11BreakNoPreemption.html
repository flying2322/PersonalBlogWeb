11 死锁预防：破坏非剥夺条件（资源超时机制）

各位，咱们继续聊死锁预防。前面讲了破坏互斥条件和破坏请求保持条件，今天轮到第三个——破坏非剥夺条件。

非剥夺条件是什么意思？说白了就是：一个AGV占着资源不放，别人不能强行拿走。你想想看，如果一辆车占着路口不走，后面的车只能干等着。这在现实交通里叫「路霸」，在调度系统里就是死锁的温床。

那怎么破？我个人的习惯是引入资源超时机制。给每个资源分配一个「使用时限」，超时不释放？系统强制回收。

11.1 超时机制的核心思想

资源超时机制，本质上就是给资源加一个「倒计时」。AGV申请到资源后，必须在规定时间内完成任务并释放。如果超时，系统判定该AGV「异常占用」，强制剥夺资源。

我在项目中遇到过这样一个场景：某工厂的AGV在交叉口因为传感器故障停住了，后面的车堵了一长串。当时没有超时机制，人工干预花了20分钟。后来我加了超时检测，30秒没动，系统自动把路口资源释放给其他车，故障车被拖走。效率提升很明显。

核心公式：

资源占用时间 ≤ 最大允许时间 → 正常

资源占用时间 > 最大允许时间 → 强制剥夺

11.2 超时时间怎么定？

这个值定多少，是个技术活。定太短，AGV正常作业被打断；定太长，死锁检测太慢。

我建议分场景设置：

场景类型 典型超时时间 说明
直行通过路口 5-10秒 正常通过时间，考虑加减速
转弯通过路口 10-20秒 转弯需要减速，时间略长
对接工位（装卸货） 30-60秒 包含定位、对接、动作时间
充电桩占用 按充电策略定 一般允许长时间占用，但需心跳检测

嗯，这里要注意：超时时间不是拍脑袋定的。我习惯先跑仿真，统计正常作业的耗时分布，取P95或P99作为基准。然后留20%-30%的余量。

11.3 超时检测的实现思路

代码层面其实不复杂。每个资源维护一个占用时间戳，调度系统定期扫描：

// 伪代码示例
class Resource {
    int id;
    AGV currentHolder;
    long acquireTimestamp;
    long timeoutMs;

    boolean isTimeout() {
        long now = System.currentTimeMillis();
        return (now - acquireTimestamp) > timeoutMs;
    }

    void forceRelease() {
        if (currentHolder != null) {
            // 记录日志：AGV xxx 超时，强制释放资源
            currentHolder = null;
            acquireTimestamp = 0;
            // 通知调度器重新分配
        }
    }
}

实际项目中，我不会用单线程轮询所有资源——性能太差。我一般用时间轮或者延迟队列，每个资源超时事件单独注册，到期自动触发。

避坑指南：

我曾经在某个项目里直接用sleep做超时检测，结果AGV一多，线程池爆了。后来改成Netty的HashedWheelTimer，轻量又高效。建议你也别走弯路。

11.4 超时后的处理策略

资源被强制释放了，然后呢？不能直接把AGV晾在那。我一般分三步走：

  1. 标记异常：记录AGV ID、资源ID、超时时长，写入异常日志
  2. 降级处理：该AGV进入「受限模式」，不再参与高优先级任务，只允许低速移动到维修区
  3. 人工介入：如果连续超时3次以上，触发报警，通知运维人员检查

你可能会问：强制剥夺资源，会不会导致AGV任务数据丢失？

会的。所以我在设计时，要求AGV在申请资源前，先把当前状态持久化到本地或调度中心。这样资源被剥夺后，AGV可以恢复状态，重新申请资源继续执行。说白了就是「先保存，再干活」。

11.5 超时机制的局限性

任何技术都不是银弹。超时机制也有短板：

  • 误判风险：如果超时时间设置不合理，正常AGV被误判为超时，造成不必要的资源抖动
  • 无法解决所有死锁：有些死锁不是因为单个资源占用超时，而是多个资源互相等待形成的循环。超时机制只能打破「单点阻塞」，对循环等待无能为力
  • 增加系统复杂度：超时检测、状态恢复、异常处理，这些逻辑写起来比想象中麻烦

注意：

超时机制是「预防」手段，不是「检测」手段。它降低死锁概率，但不能100%避免死锁。实际系统中，我通常把超时机制和死锁检测配合使用——超时预防大部分情况，死锁检测兜底。
