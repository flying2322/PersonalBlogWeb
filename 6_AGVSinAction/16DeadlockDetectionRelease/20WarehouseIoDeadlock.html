20 死锁检测与解除实战：仓库出入库区的死锁处理

仓库出入库区，是AGV系统里最容易“堵车”的地方。

我参与过不少仓储项目，说实话，十次死锁有八次都发生在出入库区。为什么？因为这里路径窄、车辆多、任务密集。你想想看，几台AGV同时抢着去同一个站台卸货，或者出库车辆和入库车辆在通道里顶牛，死锁就这么来了。

今天我们就拿一个真实的仓库场景，把死锁检测和解除的实战方法讲透。

场景描述：一个典型的出入库区布局

先看这个布局。仓库有4个入库站台（In1~In4），4个出库站台（Out1~Out4）。中间是一条双向通行的主通道。AGV从入库站台取货，送到存储区；或者从存储区取货，送到出库站台。

这个布局看起来简单，但实际跑起来，问题不少。

常见的死锁场景

我挑三个最典型的死锁场景，都是我在项目里踩过的坑。

场景一：出入库站台前的“顶牛”

AGV-A从入库站台1出来，要左转进入主通道。AGV-B从主通道过来，要右转进入入库站台2。两车在路口相遇，谁也不让谁。

为什么会这样？因为两车都认为“我的路径已经申请了，对方应该让我”。但调度系统没有做路口优先级仲裁，结果就是死锁。

核心问题：路口资源没有加锁，或者加锁粒度太粗。

场景二：主通道上的“对头车”

AGV-C从入库区往存储区走，AGV-D从存储区往出库区走。两车在主通道上迎面相遇。如果通道宽度只够一辆车通过，那就卡死了。

我记得有一次，客户现场12台AGV全部堵在主通道上，场面那叫一个壮观。后来一查，是路径规划时没有考虑双向通道的“方向锁”。

场景三：站台资源被“死等”

AGV-E占用了出库站台1，但货物还没到位，它不走。AGV-F要使用出库站台1，只能排队等。但AGV-F后面又堵了其他车。这种“链式等待”最容易引发大规模死锁。

死锁检测：怎么发现死锁？

检测死锁，我推荐用资源分配图（RAG）的方法。说白了，就是画一张图，把AGV和资源的关系标出来。

具体做法分三步：

  1. 建图：每个AGV是一个节点，每个资源（站台、路段、路口）也是一个节点。
  2. 画边：AGV申请资源，画一条从AGV到资源的边。资源被AGV占用，画一条从资源到AGV的边。
  3. 找环：用深度优先搜索（DFS）找图中的环。有环，就是死锁。

代码实现也不复杂。我贴一段核心的检测逻辑：

// 死锁检测 - 基于资源分配图
bool detectDeadlock() {
    // 1. 构建资源分配图
    Graph graph;
    for (auto& agv : allAGVs) {
        // AGV -> 它申请的资源
        for (auto& res : agv.requestedResources) {
            graph.addEdge(agv.id, res.id);
        }
        // AGV占用的资源 -> AGV
        for (auto& res : agv.occupiedResources) {
            graph.addEdge(res.id, agv.id);
        }
    }
    
    // 2. DFS找环
    vector<int> visited(graph.size(), 0);
    for (int i = 0; i < graph.size(); i++) {
        if (visited[i] == 0) {
            if (dfsFindCycle(graph, i, visited)) {
                return true;  // 发现死锁
            }
        }
    }
    return false;
}

// DFS辅助函数
bool dfsFindCycle(Graph& graph, int node, vector<int>& visited) {
    visited[node] = 1;  // 正在访问
    for (int neighbor : graph.adjList[node]) {
        if (visited[neighbor] == 1) {
            return true;  // 发现环
        }
        if (visited[neighbor] == 0) {
            if (dfsFindCycle(graph, neighbor, visited)) {
                return true;
            }
        }
    }
    visited[node] = 2;  // 访问完成
    return false;
}

我的经验：检测周期不要设太短，100ms一次就够了。太频繁反而增加系统负担。我曾经见过一个项目，检测周期设了10ms，结果CPU飙到80%，调度都卡了。

死锁解除：怎么“解套”？

检测到死锁，下一步就是解除。常用的方法有四种，我按推荐程度排个序：

方法 原理 优点 缺点
资源抢占 强制回收某台AGV占用的资源 解除快 可能影响任务
回退 让某台AGV倒车让路 对系统影响小 需要倒车空间
任务取消 取消某个任务，释放所有资源 彻底 任务丢失
路径重规划 为死锁中的AGV重新规划路径 灵活 计算量大

我个人习惯，优先用资源抢占。为什么？因为它快。死锁多拖一秒，整个仓库的吞吐量就掉一截。

具体怎么抢？我一般选“代价最小”的AGV来抢。代价怎么算？看三个因素：

  • 任务紧急度：紧急任务的车不抢
  • 已行驶距离：快到的车不抢
  • 占用的资源数：占得少的车优先抢

代码实现大概是这样的：

// 选择代价最小的AGV进行资源抢占
AGV selectVictim(vector<AGV>& deadlockedAGVs) {
    AGV victim;
    int minCost = INT_MAX;
    
    for (auto& agv : deadlockedAGVs) {
        int cost = 0;
        // 任务紧急度权重
        cost += agv.taskUrgency * 10;
        // 已行驶距离权重
        cost += agv.distanceTraveled * 1;
        // 占用资源数权重
        cost += agv.occupiedResources.size() * 5;
        
        if (cost < minCost) {
            minCost = cost;
            victim = agv;
        }
    }
    return victim;
}

// 执行资源抢占
void preemptResource(AGV& victim) {
    // 1. 通知AGV停车
    victim.stop();
    // 2. 释放所有占用的资源
    for (auto& res : victim.occupiedResources) {
        res.release();
    }
    // 3. 将AGV移到等待区
    victim.moveToWaitArea();
    // 4. 重新分配资源给等待的AGV
    reassignResources();
}

注意：资源抢占不是万能的。如果被抢的AGV正在执行“不可中断”的操作（比如举升货架），强行抢占可能造成安全事故。这时候，我建议改用“回退”方法。

实战中的避坑指南

做死锁处理，光有算法不够。我踩过的坑，今天一并告诉你：

  • 检测要快，解除要稳：检测可以激进一点，宁可误报，不能漏报。但解除操作要谨慎，别把正常任务搞乱了。
  • 别只盯着一个死锁：有时候解除了一个死锁，另一个死锁又冒出来了。我建议做“批量解除”，一次把整个环里的问题都处理掉。
  • 日志一定要打全：我曾经遇到一个死锁，查了两天才找到根因。后来我养成了习惯，每次检测到死锁，都把资源分配图dump下来。排查问题快多了。
  • 预留“逃生通道”：在出入库区设计时，我建议留一条备用通道。死锁发生时，可以让AGV从备用通道绕行。这个设计在高峰期特别管用。

小结

仓库出入库区的死锁处理，说白了就是三件事：检测要快、选择要准、解除要稳。

检测用资源分配图找环，选择用代价函数挑“受害者”，解除用资源抢占或回退。把这套组合拳打熟了，大部分死锁场景都能应对。

嗯，实战部分就讲到这里。代码和思路都给你了，关键还是要在自己的系统里跑一跑、调一调。毕竟，每个仓库的布局都不一样，死锁的表现也千奇百怪。

一句话总结：死锁不可怕，可怕的是没有检测机制和解除预案。提前设计好，出问题时不慌。
