8 死锁解除策略：杀死进程法（终止AGV）

说实话，死锁解除里最粗暴的方法，就是「杀死进程」。

在AGV调度系统里，这就意味着——直接终止某个AGV的任务。让它停下来，甚至把它拖走。听起来有点野蛮，对吧？但有时候，这反而是最有效的办法。

8.1 什么是「杀死进程法」？

简单说，就是强制结束一个或多个AGV的当前任务。释放它占用的资源（比如路径段、工位、充电桩）。这样，其他AGV就能继续跑了。

我习惯把它比作「交通管制里的拖车」。你想想看，路口堵死了，交警最直接的办法是什么？把其中一辆车拖走。虽然粗暴，但立竿见影。

核心思想：牺牲局部，保全整体。

终止一个AGV，让整个系统活过来。

8.2 什么时候该用这招？

不是所有死锁都要杀人。我一般只在以下情况才考虑：

  • 死锁范围太大——涉及5台以上AGV，回退法算不过来
  • 资源抢占严重——多个AGV互相等，谁也动不了
  • 系统实时性要求高——比如产线已经停了，必须秒级恢复
  • 其他方法都试过了——回退、资源抢占都无效

嗯，这里要注意：不要一上来就杀人。我曾经在一个项目里，新来的同事看到死锁就终止AGV，结果一天杀了十几次。后来发现，其实大部分死锁通过路径重规划就能解决。

8.3 怎么选「被杀」的AGV？

这是个关键问题。选谁？我总结了几条原则：

优先级 选择依据 说明
1 任务紧急度最低 先杀非紧急任务的AGV
2 占用资源最多 释放资源效率最高
3 距离最近 方便人工干预拖走
4 电量最低 反正也要充电，先停了

我个人习惯用加权评分法。给每个AGV打分，分数最高的「被杀」。代码大概长这样：

def select_victim(deadlocked_agvs):
    """
    选择要终止的AGV
    返回AGV ID
    """
    best_score = -999
    victim = None
    
    for agv in deadlocked_agvs:
        score = 0
        # 任务紧急度越低，分数越高
        score += (10 - agv.task_priority) * 3
        # 占用资源越多，分数越高
        score += agv.occupied_resources * 2
        # 距离越近，分数越高
        score += (100 - agv.distance_to_home) * 0.1
        # 电量越低，分数越高
        score += (100 - agv.battery_level) * 0.05
        
        if score > best_score:
            best_score = score
            victim = agv
    
    return victim.id

小技巧：权重可以动态调整。比如产线高峰期，任务紧急度的权重可以调高。我一般会在配置中心留个接口，方便现场调参。

8.4 终止AGV后，怎么善后？

杀了人，不是就完事了。后续处理很重要：

  1. 释放资源——立即释放该AGV占用的所有路径段、工位
  2. 通知其他AGV——广播消息，让它们重新规划路径
  3. 记录日志——谁被杀了、为什么杀、杀了多久
  4. 人工干预——派人去把AGV拖到安全区域
  5. 任务重分配——把被杀AGV的任务转给其他空闲AGV

我曾经遇到过一个坑：终止AGV后，忘了释放它占用的充电桩。结果其他AGV一直等那个桩，又死锁了。嗯，从那以后，我就在终止函数里加了个强制释放的步骤。

8.5 杀死进程法的优缺点

优点 缺点
解除速度快，秒级恢复 需要人工干预，增加运维成本
实现简单，代码量少 可能丢失任务进度
适用于复杂死锁场景 频繁使用会影响系统效率
不依赖复杂算法 对AGV硬件有损耗（频繁启停）

说白了，这就是个保底方案。能不用就不用，但必须得有。

8.6 核心逻辑流程图

警告：杀死进程法是一把双刃剑。用得好，系统秒恢复；用得不好，可能引发连锁反应。我建议你在生产环境里，把这个功能做成「半自动」模式——系统推荐受害者，但需要人工确认后再执行。

8.7 避坑指南

最后，分享几个我踩过的坑：

  • 不要连续杀人——终止一个AGV后，等几秒看看系统反应。我曾经连续杀了3台，结果系统资源过剩，反而更乱了。
  • 注意AGV的物理位置——如果AGV在狭窄通道里，终止后可能挡住其他AGV。最好先把它挪到安全区域。
  • 记录被杀原因——方便事后分析。我习惯在日志里加上「死锁ID、受害者ID、选择理由、解除耗时」等信息。
  • 设置最大终止次数——比如每小时最多杀3次。超过这个数，说明系统设计有问题，需要人工介入。
