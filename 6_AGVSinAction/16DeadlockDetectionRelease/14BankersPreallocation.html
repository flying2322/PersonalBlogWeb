14 死锁避免：银行家算法实现资源预分配

死锁检测与解除，说白了是「事后诸葛亮」。系统已经卡死了，我们再去想办法解开。那有没有办法在资源分配之前，就提前判断一下——这次分配会不会导致将来死锁？

有的。这就是银行家算法。

我个人习惯把银行家算法叫做「预分配检查器」。它不等到死锁发生，而是在每次申请资源时，模拟一下分配后的系统状态。如果模拟结果是安全的，那就真分配；如果不安全，就拒绝这次申请。

14.1 为什么叫「银行家」？

这个名字挺形象的。你想想看，银行家手里有一笔钱（总资源），多个客户（进程）来贷款（申请资源）。银行家不能把所有钱都贷出去，得留一部分备用，防止客户突然要求提现。

在AGV调度里，这个逻辑一模一样。

  • 银行家 = 调度系统
  • 资金 = 系统资源（比如路径段、充电桩、装卸站）
  • 客户 = 各个AGV进程
  • 贷款额度 = 每个AGV完成任务所需的最大资源量
  • 已贷出 = 当前已分配给AGV的资源
  • 还需 = AGV还需要的资源

银行家算法要保证：即使所有客户同时要求最大额度，银行家也能满足其中一部分，不至于资金链断裂。

核心思想：系统存在一个安全序列。按这个顺序分配资源，所有进程都能顺利完成。

14.2 算法需要哪些数据结构？

嗯，这里要记几个关键变量。我在项目中第一次实现时，就是被这些矩阵搞晕的。

符号 含义 举例（3个AGV，2种资源）
Available[m] 每种资源的可用数量 [3, 2] 表示资源1有3个，资源2有2个
Max[n][m] 每个AGV完成任务所需的最大资源 AGV0需要[7, 5]，AGV1需要[3, 2]
Allocation[n][m] 当前已分配给每个AGV的资源 AGV0已拿到[2, 1]
Need[n][m] 每个AGV还需要的资源 Need = Max - Allocation

其中 Need[i][j] = Max[i][j] - Allocation[i][j]。这个公式很简单，但容易写反。我曾经在代码里把减号写成了加号，结果系统一直拒绝所有资源申请，排查了整整一个下午。

14.3 安全性检查算法（核心）

当一个AGV申请资源时，系统先假装分配给它。然后运行安全性检查：

  1. 初始化：Work = Available（模拟可用资源），Finish[i] = false
  2. 找一个未完成的AGV：它的Need ≤ Work
  3. 假设它释放资源：Work = Work + Allocation[i]，Finish[i] = true
  4. 重复步骤2-3，直到所有AGV都Finish，或者找不到符合条件的AGV
  5. 判断：如果所有Finish都为true，系统安全；否则不安全

说白了，就是模拟一下「如果我把资源给你，将来我还能不能把其他人也喂饱」。

我的经验：安全性检查的复杂度是O(n²·m)，n是AGV数量，m是资源类型。在AGV数量超过50台时，这个计算量会明显增加。我建议每100ms做一次检查就够了，不用每次申请都跑。

14.4 完整代码示例（Python）

下面是我在项目中实际用过的简化版。去掉了一些工程细节，保留了核心逻辑。

class Banker:
    def __init__(self, available, max_matrix):
        self.n = len(max_matrix)      # AGV数量
        self.m = len(available)       # 资源类型数
        self.available = available[:] # 可用资源
        self.max = max_matrix         # 最大需求
        self.allocation = [[0]*self.m for _ in range(self.n)]
        self.need = [[max_matrix[i][j] for j in range(self.m)] 
                     for i in range(self.n)]

    def request_resources(self, agv_id, request):
        # 1. 检查请求是否超过Need
        for j in range(self.m):
            if request[j] > self.need[agv_id][j]:
                return False  # 超过声明需求，拒绝

        # 2. 检查是否有足够资源
        for j in range(self.m):
            if request[j] > self.available[j]:
                return False  # 资源不足，等待

        # 3. 模拟分配
        for j in range(self.m):
            self.available[j] -= request[j]
            self.allocation[agv_id][j] += request[j]
            self.need[agv_id][j] -= request[j]

        # 4. 安全性检查
        safe = self._is_safe_state()

        # 5. 如果不安全，回滚
        if not safe:
            for j in range(self.m):
                self.available[j] += request[j]
                self.allocation[agv_id][j] -= request[j]
                self.need[agv_id][j] += request[j]
            return False

        return True

    def _is_safe_state(self):
        work = self.available[:]
        finish = [False] * self.n
        safe_seq = []

        while len(safe_seq) < self.n:
            found = False
            for i in range(self.n):
                if not finish[i]:
                    # 检查Need[i]是否 ≤ Work
                    can_alloc = all(self.need[i][j] <= work[j] 
                                    for j in range(self.m))
                    if can_alloc:
                        for j in range(self.m):
                            work[j] += self.allocation[i][j]
                        finish[i] = True
                        safe_seq.append(i)
                        found = True
                        break
            if not found:
                return False  # 死锁风险
        return True

    def release_resources(self, agv_id):
        for j in range(self.m):
            self.available[j] += self.allocation[agv_id][j]
            self.allocation[agv_id][j] = 0
            self.need[agv_id][j] = self.max[agv_id][j]

注意：银行家算法要求每个AGV提前声明最大需求。这在AGV调度中是个痛点——因为任务路径是动态变化的，AGV自己也不知道最终需要多少资源。我的做法是：给每个AGV分配一个「最大资源上限」，比如最多同时占用3个路径段。这样既满足算法要求，又留有余量。

14.5 银行家算法的优缺点

任何算法都有两面性。银行家算法也不例外。

  • 优点：真正做到了「防患于未然」。只要算法说安全，系统就一定不会死锁。
  • 缺点：太保守了。很多明明不会死锁的分配，被算法拒绝了。资源利用率偏低。
  • 另一个缺点：AGV数量一多，计算量就上去了。我见过一个项目，60台AGV，每次申请都要跑几十毫秒的安全性检查，调度周期被拖慢了。

所以我的建议是：银行家算法适合AGV数量较少（比如20台以内）、任务相对固定的场景。如果AGV数量多、任务变化快，可以考虑用死锁检测+解除的方案，或者用更轻量的资源预留策略。

14.7 避坑指南

最后，分享几个我踩过的坑。

  • 最大需求声明不准确：AGV的任务是动态下发的，提前声明最大需求很难。我的做法是：给每个AGV一个「资源上限」，比如最多同时占用3个路径段。这样既满足算法要求，又不会太保守。
  • 资源释放不及时：AGV完成任务后，一定要立即释放资源。我见过一个项目，AGV已经卸货了，但资源还被占用着，导致其他AGV饿死。加一个超时强制释放机制会好很多。
  • 不要频繁运行安全性检查：每次申请都跑一遍，CPU开销很大。我建议：只在资源紧张时（比如可用资源低于阈值）才启用银行家算法。平时用简单的资源计数就够了。

银行家算法，说白了就是「先模拟，再执行」。它给AGV调度加了一层保险。虽然保守了点，但在关键场景下，这个保险值得买。
