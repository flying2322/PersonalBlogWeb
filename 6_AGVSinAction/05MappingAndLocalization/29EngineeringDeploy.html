29 工程化与部署——嵌入式部署、实时性优化、系统可靠性设计

好，聊到工程化与部署了。说实话，很多同学在仿真环境里跑得飞起，一到真车上就各种翻车。我当年第一次把导航算法部署到嵌入式板子上时，也是踩了不少坑。今天咱们就把这些实战经验掰开揉碎，好好聊聊。

一、嵌入式部署：从PC到ARM的迁移

AGV导航系统最终要跑在嵌入式平台上。最常见的是ARM Cortex-A系列，比如树莓派、RK3399、NVIDIA Jetson系列。迁移过程，说白了就是一场「资源瘦身战」。

核心差异点：

  • CPU主频从3GHz降到1.5GHz左右
  • 内存从16GB降到2-4GB
  • 没有独立显卡，全靠CPU算
  • 存储空间有限，不能装大库

我建议第一步先做依赖裁剪。别一股脑把ROS全套搬上去。我有个项目，原本依赖ros-noetic-desktop-full，光安装包就占了3GB。后来我改成只装ros-noetic-robot-core，再加几个必要的包，体积直接砍到500MB。

代码层面，要注意几个点：

  • 浮点运算优化：启用NEON指令集，编译时加 -mfpu=neon -mfloat-abi=hard
  • 内存池管理：避免频繁malloc/free，预分配固定大小的内存池
  • 日志降级：生产环境只保留ERROR级别日志，DEBUG日志全关掉
// 示例：内存池预分配
#define MAP_POOL_SIZE 1024 * 1024 * 50  // 50MB
static uint8_t map_pool[MAP_POOL_SIZE];
static size_t pool_offset = 0;

void* map_malloc(size_t size) {
    if (pool_offset + size > MAP_POOL_SIZE) {
        return NULL;  // 池满了，需要处理
    }
    void* ptr = &map_pool[pool_offset];
    pool_offset += size;
    return ptr;
}

我的小技巧：交叉编译时，一定要用目标平台的工具链。我见过有人用x86的gcc编译ARM代码，跑起来各种段错误。嗯，别问我怎么知道的。

二、实时性优化：让AGV反应快起来

AGV导航最怕什么？怕延迟。你想想看，传感器采到障碍物，到控制指令发出，中间如果延迟超过100ms，车可能已经撞上去了。

实时性优化的核心，就是缩短「感知-规划-控制」这个闭环的延迟。

2.1 任务优先级划分

我习惯把任务分成三个等级：

优先级 任务类型 最大延迟要求 示例
高 安全关键 <10ms 急停、碰撞检测
中 控制关键 <50ms 里程计融合、PID控制
低 非实时 <500ms 地图更新、日志记录

在Linux上，我用SCHED_FIFO实时调度策略。但要注意，别把所有线程都设成实时优先级，否则系统可能卡死。我曾经犯过这个错——把日志线程也设成高优先级，结果日志刷屏时，控制线程反而被抢占了。

2.2 算法层面的优化

路径规划这块，A*算法在嵌入式上跑，如果地图是1000x1000的网格，每次规划可能要几百毫秒。我常用的优化手段：

  • 分层规划：先做粗粒度规划（50cm网格），再做细粒度局部规划（5cm网格）
  • 增量式更新：环境变化不大时，复用上次的规划结果，只更新局部
  • 提前计算：在AGV行驶过程中，提前计算下一段路径

注意：实时性优化不能牺牲安全性。我见过有人为了提速，把碰撞检测的采样频率从100Hz降到20Hz，结果车撞了。安全相关的任务，优先级永远最高。

三、系统可靠性设计：别让AGV在产线上罢工

AGV在工厂里跑，一天24小时，一周7天。如果动不动就死机，产线负责人会疯掉的。可靠性设计，说白了就是「防呆」+「容错」。

3.1 看门狗机制

硬件看门狗是必须的。我一般设置3秒超时。主循环里每1秒喂一次狗。如果某个任务卡住了，看门狗会触发系统复位。

// 伪代码：看门狗任务
void watchdog_task() {
    while(1) {
        if (main_loop_healthy) {
            feed_watchdog();  // 喂狗
            main_loop_healthy = false;
        }
        sleep(1);  // 1秒检查一次
    }
}

void main_loop() {
    while(1) {
        // 执行导航任务
        navigate();
        main_loop_healthy = true;
    }
}

3.2 状态机与异常恢复

AGV不能一出错就傻站着。我设计的状态机包含这些状态：

  • INIT：初始化，自检
  • RUNNING：正常运行
  • ERROR：检测到异常，尝试恢复
  • SAFE_STOP：安全停车
  • EMERGENCY：紧急状态，需要人工介入

举个例子，如果激光雷达突然丢数据了，系统不会直接急停。它会先尝试重启雷达驱动，如果3秒内恢复，就继续运行。如果不行，才进入SAFE_STOP，缓慢停车。

避坑指南：我曾经遇到过一个问题——AGV在充电站附近反复重启。后来发现是看门狗复位后，系统重新初始化，但充电站的电磁干扰导致传感器数据异常，又触发复位。解决方案是：复位后先进入一个「稳定期」，等待5秒再开始正常导航。

3.3 数据冗余与掉电保护

地图数据、定位数据这些关键信息，不能只存在内存里。我习惯：

  • 每5分钟写一次地图到Flash
  • 每次定位更新时，同时写两份到不同存储区域
  • 掉电检测电路触发时，立即保存当前状态

嗯，这里要注意，Flash写入次数有限。我一般用环形缓冲区，只保存最近10份地图数据，避免频繁擦写。
