9 激光SLAM（下）：Cartographer算法原理、子图构建与回环检测

好，咱们接着聊激光SLAM。上一章我们把前端匹配、后端优化这些概念理了一遍。今天要聊的Cartographer，是Google开源的一个非常成熟的2D/3D SLAM方案。说实话，我最早接触它的时候，第一反应是“这玩意儿怎么这么复杂？”但真正啃下来之后，发现它的设计思路其实非常清晰——核心就三个词：子图、局部优化、回环检测。

我个人习惯把Cartographer比作一个拼图游戏。你每走一步，手里就多了一块拼图（激光帧）。你不能直接把所有拼图往桌上一倒，那肯定乱套。你得先拼出一个个小区域（子图），然后再把这些小区域拼成完整的地图。嗯，就是这么个道理。

9.1 Cartographer的整体架构

先看一张整体流程图，帮你快速建立认知。

你看，整个流程非常清晰。数据进来，先做前端匹配，然后构建子图，最后后端做回环检测和全局优化。其中回环检测的结果会反馈给前端，修正子图的位姿。这就是Cartographer的精髓。

9.2 子图构建：把局部地图拼起来

子图（Submap）是Cartographer里最核心的概念之一。说白了，它就是一小块局部地图。为什么不用一张大图？你想想看，如果机器人走了100米，直接把所有激光点都画在一张图上，那误差早就飞到天上去了。

Cartographer的做法是：每插入一定数量的激光帧（比如几十帧），就生成一个子图。子图内部用概率栅格表示，每个格子存储一个概率值，表示该格子被占用的可能性。

子图构建的关键步骤：

  1. 扫描匹配：将当前激光帧与子图进行匹配，得到最优位姿。
  2. 栅格更新：根据匹配结果，将激光点投影到子图的栅格中，更新占用概率。
  3. 位姿存储：将当前帧的位姿保存下来，作为后续回环检测的节点。

我在项目中遇到过一个问题：子图的大小怎么设？设得太小，子图数量太多，后端优化压力大；设得太大，子图内部的误差积累又太多。我的经验是，根据机器人的运动速度和环境复杂度来调。一般室内场景，子图包含50-100帧激光数据比较合适。

9.3 回环检测：把地图“拉”回来

回环检测是SLAM里最神奇的一步。没有它，地图就是歪的。有了它，地图就“啪”一下合上了。

Cartographer的回环检测策略非常聪明。它不会每帧都去检测，那样太慢了。它采用分支定界（Branch and Bound）的方法，快速搜索可能的回环候选。

回环检测的流程：

  • 候选搜索：当一个新的子图完成时，系统会检查当前帧是否与之前某个子图有重叠。
  • 快速匹配：使用多分辨率搜索，先在低分辨率下粗匹配，再在高分辨率下精匹配。
  • 约束添加：如果匹配得分超过阈值，就添加一个回环约束到后端优化中。

我曾经调试过一个场景：机器人绕着一个大柱子转了一圈，按理说应该形成闭环，但回环检测就是没触发。后来发现是激光雷达的视角被柱子挡住了，导致匹配得分不够。解决办法是适当降低回环检测的阈值，或者增加一个“视角一致性”检查。

9.4 后端优化：稀疏位姿调整

Cartographer的后端优化用的是稀疏位姿调整（SPA）。它把所有的子图位姿和激光帧位姿都当作节点，把扫描匹配和回环检测的结果当作约束，构建一个图优化问题。

你可能会问：为什么不用EKF？嗯，EKF在处理大规模地图时，协方差矩阵会变得非常大，计算量爆炸。而图优化只维护稀疏的约束关系，效率高得多。

方法 优点 缺点
EKF 实现简单，适合小场景 线性化误差，计算量随状态维度立方增长
图优化 (SPA) 处理大规模地图，支持回环 需要求解稀疏线性方程组

注意：SPA优化不是实时的。它通常在一个单独的线程中运行，每隔几秒触发一次。优化过程中，前端仍然可以继续构建新的子图，两者互不干扰。但优化完成后，所有子图的位姿都会被更新。

9.5 代码实战：配置一个Cartographer

光说不练假把式。我们来看看怎么配置一个最简单的2D Cartographer。以下是一个典型的.lua配置文件片段：

-- 2D Cartographer 配置示例
options = {
  map_builder = "MAP_BUILDER",
  trajectory_builder = "TRAJECTORY_BUILDER_2D",
  map_frame = "map",
  tracking_frame = "base_link",
  published_frame = "base_link",
  odom_frame = "odom",
  provide_odom_frame = true,
  publish_frame_projected_to_2d = false,
  use_odometry = false,
  use_nav_sat = false,
  use_landmarks = false,
  num_laser_scans = 1,
  num_multi_echo_laser_scans = 0,
  num_subdivisions_per_laser_scan = 1,
  num_point_clouds = 0,
  lookup_transform_timeout_sec = 0.2,
  submap_publish_period_sec = 0.3,
  pose_publish_period_sec = 5e-3,
  trajectory_publish_period_sec = 30e-3,
}

TRAJECTORY_BUILDER_2D = {
  use_imu_data = false,
  min_range = 0.1,
  max_range = 30.,
  missing_data_ray_length = 5.,
  num_accumulated_range_data = 1,
  voxel_filter_size = 0.025,
  adaptive_voxel_filter_max_length = 0.5,
  adaptive_voxel_filter_min_num_points = 200,
  ceres_scan_matcher = {
    occupied_space_weight = 1.,
    translation_weight = 10.,
    rotation_weight = 40.,
    ceres_solver_options = {
      use_nonmonotonic_steps = false,
      max_num_iterations = 20,
      num_threads = 1,
    },
  },
  submaps = {
    num_range_data = 90,
    grid_options_2D = {
      grid_type = "PROBABILITY_GRID",
      resolution = 0.05,
    },
    range_data_inserter = {
      hit_probability = 0.55,
      miss_probability = 0.49,
      insert_free_space = true,
    },
  },
}

这段配置里，有几个参数我特别想强调一下：

  • num_range_data：每个子图包含的激光帧数。我一般设90，也就是大约3秒的数据（30Hz雷达）。
  • hit_probability / miss_probability：栅格更新时的概率参数。这两个值越接近0.5，地图更新越慢，但越稳定。我曾经设成0.7/0.3，结果地图噪点特别多。
  • ceres_scan_matcher：Ceres求解器的权重。如果里程计不准，可以适当加大translation_weight。

9.6 避坑指南：我踩过的那些坑

最后，分享几个我在实际部署Cartographer时遇到的坑，希望能帮你少走弯路。

坑1：回环检测不触发

我曾经在一个长走廊里测试，机器人走了两个来回，回环检测就是没反应。后来发现是激光雷达的最大距离设得太短，导致走廊尽头的特征点没被采集到。把max_range从10米调到30米后，问题解决。

坑2：地图漂移

有一次在户外测试，地图越走越歪。排查了半天，发现是IMU没有启用。Cartographer在2D模式下虽然不强制使用IMU，但如果有IMU，它会用IMU的角速度来辅助旋转估计，效果会好很多。

坑3：CPU占用过高

Cartographer默认的voxel_filter_size是0.025米，也就是2.5厘米。这个值在室内没问题，但在空旷的室外，激光点非常多，CPU直接拉满。我建议在室外场景把voxel_filter_size调到0.05米，性能提升明显。
