8 激光SLAM（上）：Gmapping算法原理、代码实现与参数调优

聊到激光SLAM，Gmapping绝对是个绕不开的名字。我记得2010年左右刚接触机器人导航那会儿，Gmapping几乎是入门必备。说白了，它就是那个年代最靠谱的2D激光SLAM方案之一。虽然现在有Cartographer、Karto这些后起之秀，但Gmapping的粒子滤波思想，依然是理解SLAM底层逻辑的最好切入点。

今天我们就把它拆开揉碎了讲。从原理到代码，再到我踩过的那些坑，一次性说清楚。

8.1 Gmapping的核心思想：粒子滤波

Gmapping本质上是一个基于粒子滤波的SLAM算法。你想想看，机器人一边移动一边建图，它怎么知道自己在哪里？

答案是：用一堆粒子去猜。

每个粒子代表机器人可能的一个位姿（位置+朝向），以及对应的地图。一开始粒子均匀撒开，随着机器人移动，粒子会根据激光观测数据和里程计数据不断更新权重。权重高的粒子存活下来，权重低的被淘汰。这就是所谓的“重要性重采样”。

我个人习惯把粒子滤波理解成“优胜劣汰的进化算法”。每一代粒子都在试图解释“我看到的激光数据和地图匹配得上吗？”。匹配得好的，就多生几个后代；匹配得差的，就淘汰掉。

核心公式（简化版）：
P(x_t | z_{1:t}, u_{1:t}) ∝ P(z_t | x_t, m) * P(x_t | x_{t-1}, u_t) * P(x_{t-1} | z_{1:t-1}, u_{1:t-1})
其中：
  • x_t：t时刻的位姿
  • z_t：t时刻的激光观测
  • u_t：t时刻的里程计控制
  • m：地图

嗯，这里要注意：Gmapping之所以比早期的粒子滤波SLAM效果好，是因为它引入了“改进的提议分布”和“自适应重采样”。这两个改进，说白了就是让粒子更聪明地集中在高概率区域，而不是盲目撒网。

8.2 改进的提议分布

传统的粒子滤波直接用里程计模型作为提议分布。但里程计有累积误差，时间一长粒子就飘得没边了。

Gmapping的做法是：把最近的激光观测也考虑进来。具体来说，它会在当前粒子附近，根据激光匹配得分，生成一个高斯分布。然后从这个高斯分布里采样新的粒子。

我在项目中遇到过这样的情况：在长走廊里，里程计漂移很严重，但激光能看到两侧墙壁。Gmapping利用激光信息修正了提议分布，粒子收敛得非常好。换成纯里程计提议分布的话，粒子早就散成一锅粥了。

我的经验： 提议分布的改进是Gmapping的精髓。如果你自己写粒子滤波SLAM，一定要把激光观测融合到提议分布里，别只用里程计。效果天差地别。

8.3 自适应重采样

重采样是粒子滤波的标配。但Gmapping做了一个很聪明的改进：它不会每帧都重采样。

为什么？因为重采样会丢失粒子的多样性。如果频繁重采样，所有粒子都集中在几个高权重粒子的附近，一旦这些粒子是错的，整个系统就崩了。

Gmapping的做法是：计算粒子的“有效粒子数”（Neff）。当Neff低于某个阈值（通常是粒子数的一半）时，才触发重采样。这样既保证了粒子的多样性，又避免了粒子退化。

// 伪代码：自适应重采样逻辑
if (neff < particle_num * 0.5) {
    resample_particles();  // 执行重采样
} else {
    // 保持当前粒子集不变，只更新权重
    update_weights_only();
}

我曾经调试过一个场景：机器人原地旋转时，激光数据变化剧烈，Neff值骤降。如果不加这个自适应阈值，粒子每帧都在重采样，地图越建越模糊。加了之后，地图清晰度明显提升。

8.4 代码实现：ROS中的Gmapping

ROS里集成了Gmapping的现成包，叫gmapping。但如果你想真正理解它，我建议你读一读源码。核心文件就几个：

  • gridslamprocessor.h/.cpp：粒子滤波主循环
  • gridslamprocessor_tree.cpp：粒子树的维护
  • scanmatcher.cpp：激光扫描匹配

启动一个Gmapping节点的典型launch文件如下：

<launch>
  <node pkg="gmapping" type="slam_gmapping" name="slam_gmapping" output="screen">
    <param name="base_frame" value="base_footprint"/>
    <param name="odom_frame" value="odom"/>
    <param name="map_frame" value="map"/>
    <param name="map_update_interval" value="5.0"/>
    <param name="maxUrange" value="5.0"/>
    <param name="particles" value="30"/>
    <param name="srr" value="0.01"/>
    <param name="srt" value="0.02"/>
    <param name="str" value="0.01"/>
    <param name="stt" value="0.02"/>
    <param name="linearUpdate" value="1.0"/>
    <param name="angularUpdate" value="0.5"/>
    <param name="temporalUpdate" value="3.0"/>
    <param name="resampleThreshold" value="0.5"/>
  </node>
</launch>

这里我重点说几个参数：

参数名 作用 我的建议值
particles 粒子数量 30~80。室内小场景30够用，大场景建议50以上
linearUpdate 机器人移动多少米触发一次更新 0.5~1.0。太小了计算量大，太大了地图更新滞后
angularUpdate 机器人旋转多少弧度触发一次更新 0.3~0.5。转弯时建议小一点
srr/srt/str/stt 里程计噪声模型参数 根据实际机器人调。轮式机器人通常0.01~0.05
maxUrange 激光最大有效距离 比激光雷达实际量程小0.5米，避免边缘噪声
避坑指南： 我曾经把particles设到200，以为粒子越多越准。结果地图是准了，但CPU跑满，实时性完全跟不上。后来发现对于2D室内场景，30~50个粒子完全够用。别盲目堆粒子数。

8.5 参数调优实战经验

调参是门手艺活。我总结了一套“三步走”的方法：

  1. 先调里程计噪声：让机器人走直线，看地图有没有弯曲。如果有，增大srr和srt。
  2. 再调更新频率：linearUpdate和angularUpdate设小一点，观察地图是否抖动。抖动就调大。
  3. 最后调粒子数：从30开始，逐步增加，直到地图质量不再明显提升为止。

我记得有一次在工厂里调试AGV，地面是环氧树脂，反光很严重。激光打到地面上的点全是噪声。我一开始怎么调参数都不行，后来把maxUrange从10米降到4米，把地面反射点过滤掉，地图瞬间就干净了。

你想想看，有时候问题不在算法本身，而在数据质量。Gmapping再强，也架不住烂数据。

8.6 Gmapping的局限性

虽然Gmapping经典，但它不是万能的。我简单列几个痛点：

  • 不擅长闭环检测：Gmapping没有显式的闭环优化模块。如果机器人走大圈，累积误差会越来越大。
  • 对计算资源敏感：粒子数一多，CPU就扛不住。不适合超大规模地图。
  • 依赖里程计：如果里程计质量太差（比如打滑严重的轮式机器人），Gmapping效果会大打折扣。

所以现在很多项目开始转向Cartographer或Karto。但话说回来，理解Gmapping依然是理解现代SLAM的基石。你把它吃透了，再看其他算法，会发现很多思想都是相通的。

一句话总结： Gmapping用粒子滤波解决了“我在哪”和“周围长啥样”两个问题。改进的提议分布和自适应重采样是它的两大杀器。调参时，先调里程计噪声，再调更新频率，最后调粒子数。

这张图把Gmapping的核心流程串起来了。你从激光和里程计输入开始，经过改进的提议分布、权重更新，再到自适应重采样的判断，最后输出地图和位姿。每一步都环环相扣。
