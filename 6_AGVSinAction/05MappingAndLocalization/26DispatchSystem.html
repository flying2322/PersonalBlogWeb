26 AGV调度系统：多车调度、任务分配、交通管理

各位工程师朋友，今天我们来聊聊AGV调度系统里最核心的三个模块——多车调度、任务分配和交通管理。说实话，这三个东西就像调度系统的三驾马车，缺一个都跑不起来。我在做第一个调度项目时，就吃过交通管理的亏，几台车在交叉口堵成一团，场面一度非常尴尬。

26.1 多车调度：让车队有序运转

多车调度，说白了就是让多台AGV协同工作。你想想看，一个仓库里几十台车同时跑，如果没有好的调度策略，那画面简直不敢看。

调度策略主要分三种：

  • 集中式调度：一台中央服务器管所有车。优点是全局最优，缺点是单点故障。我建议小规模系统（10台以内）用这个。
  • 分布式调度：每台车自己决策。适合大规模系统，但容易产生局部最优。
  • 混合式调度：折中方案。中央服务器做宏观调度，车辆做微观调整。我个人比较推荐这种方式。

核心要点：多车调度的本质是资源分配问题。车辆、路径、充电桩、工作站都是资源。好的调度策略能让资源利用率最大化。

我在项目中遇到过一个问题：某工厂有15台AGV，采用集中式调度，结果中央服务器CPU跑满，调度延迟从50ms飙升到500ms。后来我们改成了混合式调度，把路径规划下放到每台车，服务器只负责任务分配和冲突检测，问题就解决了。

26.2 任务分配：谁有空谁干活

任务分配，就是决定哪台车去干哪个活。听起来简单，但里面门道不少。

常见的分配算法：

算法原理适用场景
最短距离优先选离任务点最近的车简单场景，任务量小
最早空闲优先选最先完成当前任务的车任务均匀分布
拍卖算法车辆对任务竞价大规模系统，动态性强
匈牙利算法全局最优匹配任务和车辆数量固定

嗯，这里要注意一点：任务分配不是一次性的。实际运行中，任务会不断到达，车辆状态也在变化。所以我们需要动态分配策略。

我的经验：曾经有个项目，我们用了最短距离优先算法，结果发现某台车总是被分配任务，因为它位置好。但它的电量已经很低了。后来我们加入了电量权重，让低电量的车优先去充电，而不是接任务。

任务分配的代码实现，我一般这样写：

class TaskAllocator:
    def __init__(self, vehicles):
        self.vehicles = vehicles  # 车辆列表
    
    def allocate(self, task):
        best_vehicle = None
        best_score = float('inf')
        
        for v in self.vehicles:
            if v.status == 'idle' and v.battery > 20:
                # 计算综合得分：距离 + 电量惩罚 + 任务优先级
                score = self.calc_score(v, task)
                if score < best_score:
                    best_score = score
                    best_vehicle = v
        
        return best_vehicle
    
    def calc_score(self, vehicle, task):
        dist = vehicle.distance_to(task.position)
        battery_penalty = max(0, 30 - vehicle.battery) * 2
        priority_bonus = task.priority * 10
        return dist + battery_penalty - priority_bonus

26.3 交通管理：避免撞车是底线

交通管理，说白了就是防止AGV撞在一起。这是调度系统的底线，也是我踩坑最多的地方。

交通管理三大策略：

  1. 路段锁机制：把地图分成若干路段，每段同时只允许一台车进入。简单粗暴，但效率低。
  2. 预留路径机制：车辆提前申请路径，调度系统分配时间窗。效率高，但实现复杂。
  3. 动态避障：车辆通过传感器检测障碍物，实时调整路径。作为前两种的补充。

我曾经踩过的坑：在某个项目中，我们只用了路段锁机制，结果在窄通道处，两台车面对面相遇，各自锁住了对方的路段，死锁了。后来我们加入了死锁检测和解除机制，才彻底解决这个问题。

26.4 死锁检测与解除

死锁是交通管理中最头疼的问题。四台车在十字路口互相等待，谁也动不了。我曾经在一个项目中遇到过这种情况，当时现场工程师打电话说「车不动了」，我远程一看，好家伙，四台车围成一个圈，每台车都在等前面的车让路。

死锁检测方法：

  • 资源等待图法：把车辆和路段画成图，检测是否有环。有环就是死锁。
  • 超时检测法：如果一台车等待超过阈值，就认为可能死锁了。

死锁解除策略：

  • 回退法：让其中一台车倒车，退出冲突区域。
  • 优先级法：低优先级的车让路。
  • 重规划法：重新规划路径，绕开冲突区域。

我的建议：死锁检测一定要做，而且要做在调度系统里，不要依赖车辆自己检测。车辆只能看到局部，调度系统才有全局视野。

26.5 实际项目中的调度系统架构

最后，我分享一下实际项目中调度系统的典型架构。这个架构我在三个项目中用过，效果都不错。

调度系统架构（分层设计）：
┌─────────────────────────────────┐
│         任务管理层               │
│   - 任务接收与解析              │
│   - 任务优先级管理              │
│   - 任务状态跟踪                │
├─────────────────────────────────┤
│         调度决策层               │
│   - 车辆分配算法                │
│   - 路径规划引擎                │
│   - 交通管理模块                │
├─────────────────────────────────┤
│         通信接口层               │
│   - 与AGV的通信协议             │
│   - 与MES/WMS的接口             │
│   - 状态上报与指令下发           │
└─────────────────────────────────┘

这个架构的好处是各层职责清晰，出了问题容易定位。我曾经在调试时发现任务分配不对，一看是任务管理层的问题；后来发现车辆不走，一看是通信接口层的问题。分层设计让排查效率高了很多。

小技巧：调度系统的日志一定要详细。我习惯在每个关键节点都打日志，包括任务到达时间、分配结果、路径规划耗时、交通管理决策等。这样出了问题，翻日志就能定位。
