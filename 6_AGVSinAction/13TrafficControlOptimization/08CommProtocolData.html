8 通信协议与数据交互：AGV与上位机通信协议、实时数据交互机制、通信延迟处理策略

通信这块，说白了就是AGV的“神经”和“语言”。

我见过太多项目，硬件选型一流，调度算法也漂亮，最后栽在通信上。AGV跑着跑着突然“失联”，或者指令发出去半天才响应——这种问题，比算法bug还难排查。

今天咱们就聊聊，AGV和上位机到底怎么“说话”，以及遇到延迟怎么办。

8.1 通信协议选型：别盲目追求“高大上”

我个人习惯，选协议之前先问三个问题：

  • 实时性要求多高？ 是100ms级别，还是10ms级别？
  • 数据量多大？ 只传位置和状态，还是带地图、任务列表？
  • 现场环境怎么样？ 有没有强干扰？WiFi稳不稳？

目前主流方案就几种，我列个表对比一下：

协议 实时性 可靠性 适用场景 我的评价
TCP 中等 高 任务下发、状态上报 最稳，但重传机制会引入延迟
UDP 高 低 实时位置、心跳 快，但丢包你得自己处理
MQTT 中等 高 多AGV、跨网络 适合云边协同，但QoS1/2有开销
WebSocket 高 高 Web端监控、HMI 全双工，浏览器友好
Modbus TCP 中等 高 PLC对接、老设备 工业现场最爱，但数据量有限

我的建议： 别只用一种协议。我习惯“双通道”设计——控制指令走TCP，保证不丢；实时位置走UDP，追求低延迟。你想想看，如果位置也用TCP，一旦丢包重传，调度系统看到的AGV位置就是“过去式”了。

8.2 数据交互机制：别让AGV“等回复”

很多新手设计交互时，喜欢搞“一问一答”。

上位机发个指令，AGV处理完再回复，上位机收到回复才发下一条。这种模式在单AGV时还行，AGV一多，调度系统就卡死了。

我推荐用“异步+事件驱动”模式。

核心思路就三点：

  1. 指令下发不等待回复。 上位机只管发，AGV收到后异步处理。
  2. 状态变化主动上报。 AGV完成指令、遇到障碍、电量低——这些事件主动推送给上位机。
  3. 心跳保活。 每隔1-2秒，AGV发一个心跳包，告诉上位机“我还活着”。

举个例子，我设计的数据帧格式长这样：

// 上位机 -> AGV：任务下发
{
    "msg_id": "20250321_001",
    "type": "task_assign",
    "timestamp": 1742548800,
    "payload": {
        "task_id": "T1001",
        "target": "A3-05",
        "action": "pickup"
    }
}

// AGV -> 上位机：状态上报（异步）
{
    "msg_id": "20250321_001_ACK",
    "type": "status_report",
    "timestamp": 1742548801,
    "payload": {
        "agv_id": "AGV_01",
        "status": "moving",
        "position": {"x": 12.5, "y": 8.3, "theta": 90.0},
        "battery": 78
    }
}

关键点： 每条消息都有唯一ID和时间戳。这样就算消息乱序到达，上位机也能根据时间戳判断谁先谁后。我在项目中遇到过AGV上报的位置比实际晚了两秒，就是因为没有时间戳，调度系统拿旧位置去算路径，差点撞车。

8.3 通信延迟处理策略：别让延迟“毁”了调度

为什么会延迟？原因无非三个：

  • 网络抖动： WiFi信号不稳定，丢包重传。
  • 处理瓶颈： AGV的控制器性能有限，处理不过来。
  • 数据量过大： 一次传太多数据，分包重组耗时。

我处理延迟的策略，总结下来就四个字：预测+补偿。

8.3.1 位置预测：用“外推”对抗延迟

AGV上报的位置，到你收到时，它已经往前走了。如果你直接用这个位置做决策，等于“开历史倒车”。

我的做法是：

  1. 记录AGV最近N个位置点（比如最近5个）。
  2. 根据时间戳，计算它的速度和方向。
  3. 用当前时间减去最后上报时间，算出延迟Δt。
  4. 用速度×Δt，外推出AGV此刻应该在的位置。

代码实现大概这样：

def predict_position(last_positions, current_time):
    # last_positions: [(x, y, theta, timestamp), ...]
    if len(last_positions) < 2:
        return last_positions[-1][:3]  # 数据不够，直接用
    
    # 取最近两个点算速度
    p1 = last_positions[-2]
    p2 = last_positions[-1]
    dt = p2[3] - p1[3]
    if dt <= 0:
        return p2[:3]
    
    vx = (p2[0] - p1[0]) / dt
    vy = (p2[1] - p1[1]) / dt
    
    # 计算延迟补偿
    delay = current_time - p2[3]
    pred_x = p2[0] + vx * delay
    pred_y = p2[1] + vy * delay
    
    return (pred_x, pred_y, p2[2])

注意： 预测不是万能的。如果AGV突然急转弯或急停，预测值会偏差很大。我曾经在AGV进电梯时吃过这个亏——预测位置还在电梯外，实际已经进去了。后来我加了一个“运动模式”字段，AGV在转弯或减速时主动上报，调度系统收到后暂停预测，改用最后上报值。

8.3.2 指令超时与重试：别让AGV“死等”

上位机发指令后，AGV可能因为网络问题没收到。如果一直等，任务就卡死了。

我的策略是：

  • 指令带超时。 每条指令有个“有效期”，比如5秒。AGV收到后，如果5秒内没处理完，自动丢弃。
  • 重试机制。 上位机发指令后，启动一个定时器。如果超时没收到ACK，就重发。重发次数一般设3次，再多就报错。
  • 幂等性设计。 同一指令重复下发，AGV不能重复执行。比如“移动到A点”，AGV已经在A点了，再收到这条指令应该忽略。

嗯，这里要注意：重试间隔不能太短。我见过有人设100ms重试一次，结果网络一抖，上位机疯狂重发，AGV被指令淹没了。我一般设1秒重试一次，给网络留点恢复时间。

8.3.3 数据压缩：少传一点，快一点

有些场景，AGV需要上传地图数据或日志，数据量很大。这时候如果还按常规方式传，延迟会飙升。

我的做法是：

  • 增量上传。 只传变化的部分。比如地图更新，只传新增的障碍物坐标。
  • 二进制编码。 别用JSON传大量数值，太浪费带宽。我习惯用Protobuf或MessagePack，数据量能减少60%以上。
  • 优先级队列。 实时位置、指令这些高优先级数据走“快车道”，日志、地图这些低优先级数据走“慢车道”。

一个小技巧： 如果AGV的控制器性能很弱（比如只有几百MHz的MCU），别让它做数据压缩。压缩计算本身也会消耗时间。我建议在上位机端做解压，AGV只管传原始数据。

8.5 避坑指南

最后分享几个我踩过的坑：

  • 别用NTP同步时间。 工业现场NTP服务器可能被防火墙挡住。我后来改用GPS授时，或者让AGV以上位机时间为准，每次通信时带上位机的时间戳。
  • 心跳超时别设太短。 有人设500ms，结果网络稍微波动就误报AGV离线。我一般设3秒，连续3次心跳丢失才判定离线。
  • 日志别和实时数据混传。 我曾经把日志和位置放在同一个通道里传，结果日志一多，位置更新就卡住了。后来强制分通道，问题解决。

总结一下： 通信协议选型要务实，数据交互要异步，延迟处理要预测+补偿。记住这三条，你的AGV调度系统至少能少踩一半的坑。
