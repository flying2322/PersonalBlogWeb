24 交通管制系统部署与运维：系统部署架构、容器化部署（Docker）、运维监控与自动化运维

24.1 系统部署架构：从单机到集群的演进

交通管制系统，说白了就是AGV调度的大脑。这个大脑要是宕机了，整个仓库的AGV都得趴窝。我最早做项目时，用的还是单机部署，一台工控机扛所有。结果有一次，系统升级时出了点小问题，重启花了5分钟，现场几十台AGV全堵在路口，那场面...嗯，后来我再也不敢用单机了。

我个人习惯，生产环境至少是双机热备。架构上分三层：

  • 接入层：负责跟AGV通信，处理报文解析。这一层要扛住高并发，我建议用Nginx做负载均衡。
  • 逻辑层：交通管制核心算法，包括路径规划、死锁检测、路口分配。这是最吃CPU的模块。
  • 数据层：存储地图数据、任务日志、AGV状态。我一般用Redis做缓存，MySQL做持久化。

你想想看，如果这三层全挤在一台机器上，一旦内存泄漏，整个系统就崩了。所以，我推荐微服务架构，每个模块独立部署，互不影响。

核心要点：交通管制系统必须支持水平扩展。当AGV数量超过50台时，单机肯定扛不住。我建议至少预留30%的性能冗余。

24.2 容器化部署：Docker让环境一致

我记得最早做部署时，最头疼的就是环境不一致。开发环境跑得好好的，一到现场就报错。后来用了Docker，这个问题才算彻底解决。

Docker的好处，说白了就是「一次构建，到处运行」。我把交通管制系统打包成镜像，里面包含了所有依赖——JDK版本、Redis客户端、甚至时区设置。现场运维人员只需要拉取镜像，启动容器就行。

下面是我常用的Dockerfile示例：

FROM openjdk:11-jre-slim
WORKDIR /app
COPY target/traffic-control.jar app.jar
COPY config/application.yml config/
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar", "--spring.config.location=config/application.yml"]

这里有个坑，我踩过好几次。就是时区问题。AGV调度对时间敏感，如果容器时区跟现场不一致，任务时间戳全乱套。我现在的做法是在Dockerfile里加一行：

RUN ln -sf /usr/share/zoneinfo/Asia/Shanghai /etc/localtime

另外，容器化部署后，日志管理也要跟上。我习惯把日志挂载到宿主机目录，方便统一收集：

docker run -d \
  --name traffic-control \
  -v /data/logs:/app/logs \
  -p 8080:8080 \
  traffic-control:latest

小技巧：用docker-compose管理多容器。我一般把交通管制、Redis、Nginx写在一个compose文件里，一条命令启动所有服务。

24.3 运维监控：别等出事了再看日志

我曾经有个项目，凌晨3点系统突然卡死，现场值班人员打电话给我，我才知道出事了。从那以后，我坚持所有系统必须上监控。

监控分三个维度：

  • 基础设施监控：CPU、内存、磁盘、网络。我用Prometheus + Grafana，一目了然。
  • 应用层监控：接口响应时间、任务处理吞吐量、死锁检测耗时。这些指标直接反映系统健康度。
  • 业务层监控：AGV等待时间、路口拥堵指数、任务完成率。这才是现场最关心的。

我建议设置三级告警：

级别 触发条件 响应方式
警告 CPU > 70% 持续5分钟 钉钉/微信通知
严重 CPU > 85% 或 接口超时率 > 5% 电话告警 + 自动扩容
紧急 系统宕机 或 死锁无法恢复 自动切换备用节点

你想想看，如果没有监控，系统慢了你都不知道是哪里瓶颈。我见过一个项目，AGV频繁报超时，查了半天才发现是磁盘IO满了，日志文件把空间吃光了。

注意：监控本身也会消耗资源。我建议监控系统单独部署，不要跟业务系统混在一起。否则监控挂了，你连它挂了都不知道。

24.4 自动化运维：能自动就别手动

说实话，运维工作最怕重复劳动。每次升级都要手动停服务、备份数据、启动新版本，既容易出错又浪费时间。我现在的做法是全部自动化。

自动化运维的核心是CI/CD流水线。我习惯用Jenkins + GitLab，流程是这样的：

  1. 开发提交代码到GitLab，触发Webhook
  2. Jenkins自动拉取代码，执行单元测试
  3. 测试通过后，自动构建Docker镜像
  4. 镜像推送到私有仓库
  5. 生产环境自动拉取新镜像，滚动更新

这里有个关键点——滚动更新。交通管制系统不能停服，所以我用Kubernetes的滚动更新策略，逐个替换Pod，保证服务不中断。

我曾经遇到过一个问题：新版本有bug，导致部分AGV任务失败。幸好我做了灰度发布，先让10%的流量走新版本，发现问题后立刻回滚。整个过程不到5分钟，现场几乎无感知。

自动化运维还包括：

  • 自动备份：每天凌晨备份数据库和配置文件，保留最近7天
  • 自动清理：日志文件超过30天自动删除，避免磁盘爆满
  • 自动扩缩容：根据CPU负载自动调整容器数量

我的经验：自动化运维不是一蹴而就的。我建议先从备份和监控自动化开始，逐步扩展到部署和扩缩容。步子迈太大，容易扯着蛋。

24.5 知识体系总览

下面这张图，是我对交通管制系统部署与运维的总结。你可以看到，从底层基础设施到上层业务监控，每一层都有对应的工具和策略。

这张图我画了好几次才满意。你看，从基础设施到自动化运维，每一层都依赖下一层。如果基础设施没做好，容器化部署就是空中楼阁。同样，没有监控，自动化运维就是盲人摸象。

最后说一句：部署与运维这件事，没有银弹。每个现场的环境都不一样，我建议你多去现场看看，跟运维人员聊聊。有时候，一个简单的网络抖动，就能让整个系统崩掉。经验，都是在坑里摔出来的。
