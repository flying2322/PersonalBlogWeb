22 交通管制系统接口设计：RESTful API设计、WebSocket实时通信接口、数据库接口设计

接口设计这件事，说白了就是定规矩。你想想看，AGV调度系统里那么多模块——路径规划、任务管理、车辆控制、状态监控——它们之间怎么说话？谁先开口？说完了怎么确认？这些都得靠接口来约束。

我个人习惯，在设计交通管制系统时，先把接口分成三类：RESTful API 负责“一问一答”的同步操作，WebSocket 负责“实时推送”的异步通信，数据库接口 负责“持久化存储”的数据管理。这三者各司其职，缺一不可。

核心观点：接口设计不是写代码，而是定契约。契约定好了，后面开发才不吵架。

22.1 RESTful API 设计

RESTful API 适合做那些“你问我答”的事情。比如前端要查询某台AGV的当前位置，或者管理员要下发一个交通管制指令，用 REST 就很合适。

我在项目中遇到过一个问题：一开始把 API 设计得太细，一个页面要调七八次接口才能渲染完。后来我学乖了，按资源粒度来设计，一个资源一个端点，不多不少。

22.1.1 资源端点设计

资源 HTTP 方法 端点 说明
AGV 状态 GET /api/v1/agvs/{id}/status 查询单台AGV的实时状态
交通管制区 POST /api/v1/zones 创建新的管制区域
交通管制区 PUT /api/v1/zones/{id} 更新管制区域参数
交通管制区 DELETE /api/v1/zones/{id} 删除管制区域
路径锁 POST /api/v1/locks 申请锁定某段路径
路径锁 DELETE /api/v1/locks/{id} 释放路径锁

嗯，这里要注意：路径锁的释放一定要有超时机制。我曾经见过一个项目，AGV 死机了锁没释放，后面的车全堵在那，整个仓库瘫痪了半小时。后来我们加了个 TTL（生存时间），锁超过 30 秒自动释放，这才解决问题。

22.1.2 请求与响应规范

我建议所有 API 都统一返回格式，前端和后端都省心。下面是我常用的模板：

// 成功响应
{
  "code": 200,
  "message": "success",
  "data": {
    "agvId": "AGV-001",
    "position": { "x": 12.5, "y": 8.3 },
    "speed": 1.2,
    "status": "moving"
  },
  "timestamp": 1712345678
}

// 错误响应
{
  "code": 4003,
  "message": "路径已被锁定，请稍后重试",
  "data": null,
  "timestamp": 1712345678
}

小技巧：错误码用 4 位数，前两位表示模块（40=交通管制），后两位表示具体错误（03=路径锁冲突）。这样查日志时一眼就能定位问题。

22.2 WebSocket 实时通信接口

RESTful API 有个硬伤——它只能“你问我答”。但交通管制系统里，很多信息是需要主动推送的。比如某段路径突然被占用，所有正在往那边走的 AGV 都得立刻收到通知，重新规划路线。这时候就得靠 WebSocket 了。

说白了，WebSocket 就是一条长连接，服务端可以随时往客户端“塞”数据。我习惯把推送的消息分成几类：

  • 状态变更通知：AGV 位置、速度、任务状态发生变化时推送
  • 交通管制事件：路径锁定、解锁、拥堵预警等
  • 系统告警：AGV 离线、通信超时、硬件故障等
  • 心跳保活：每 5 秒一次，确保连接不断

22.2.1 消息格式设计

我建议所有 WebSocket 消息都采用统一的 JSON 结构，方便客户端解析：

{
  "type": "traffic_lock",
  "payload": {
    "zoneId": "ZONE-A3",
    "lockedBy": "AGV-007",
    "lockedAt": "2025-04-01T10:30:00Z",
    "estimatedRelease": "2025-04-01T10:30:15Z"
  },
  "priority": "high",
  "timestamp": 1712345678
}

type 字段决定了客户端该用哪个处理器来处理这条消息。payload 里放具体数据。priority 字段我后来加的——有一次系统同时推送了 200 条状态更新，结果一条紧急的路径锁通知被淹没了，AGV 差点撞上。从那以后，高优先级的消息必须插队处理。

22.2.2 连接管理

WebSocket 连接不是建好就完事了。你想想看，AGV 在仓库里跑来跑去，Wi-Fi 信号时好时坏，连接随时可能断开。我总结了几点经验：

  • 自动重连：客户端检测到断开后，立即尝试重连，最多重试 5 次，间隔指数退避（1s, 2s, 4s, 8s, 16s）
  • 心跳超时：服务端 15 秒没收到心跳，主动断开连接，释放资源
  • 消息去重：每条消息带唯一 ID，客户端收到重复消息直接丢弃

避坑指南：我曾经遇到过 WebSocket 连接数暴涨导致服务端 OOM 的情况。后来加了连接数上限（单机 5000），超过上限的请求直接返回 503。别想着无限扩容，先限流再说。

22.3 数据库接口设计

RESTful API 和 WebSocket 处理的是“实时数据”，但历史数据、配置数据、日志数据这些，还是得靠数据库。数据库接口设计得好不好，直接影响查询性能和系统扩展性。

我习惯把数据库接口分成两层：数据访问层（DAO） 和 业务服务层。DAO 层只负责 CRUD，业务层负责组合逻辑。这样哪天要换数据库（比如从 MySQL 换到 PostgreSQL），只需要改 DAO 层，业务层完全不动。

22.3.1 核心表结构

表名 主要字段 用途
agv_status agv_id, position_x, position_y, speed, status, updated_at 存储 AGV 最新状态
traffic_zone zone_id, polygon, max_agv_count, current_count, status 交通管制区域定义
path_lock lock_id, path_id, agv_id, locked_at, released_at, ttl 路径锁记录
traffic_event_log event_id, type, agv_id, zone_id, timestamp, detail 交通事件日志

嗯，这里有个细节：agv_status 表只保留最新一条记录，历史轨迹数据另建一张表。为什么？因为查询最新状态时，如果表里有几亿条历史数据，索引再优化也扛不住。我见过一个项目把历史和最新混在一起，结果一个简单的状态查询跑了 3 秒多，后来拆表后降到 5 毫秒。

22.3.2 索引设计建议

数据库接口的性能，很大程度上取决于索引。我个人的经验是：

  • agv_id + updated_at 联合索引：用于查询某台 AGV 的最新状态
  • zone_id + status 联合索引：用于查询某个区域内的活跃锁
  • event_type + timestamp 联合索引：用于按类型和时间范围查询事件日志

小技巧：别在 text 类型字段上建索引，除非你用了全文检索。我曾经看到有人在 detail 字段上建了普通索引，结果索引比表还大，查询反而更慢。

22.3.3 事务与锁

交通管制系统里，路径锁的申请和释放必须保证原子性。我建议用数据库事务 + 乐观锁来实现：

-- 申请路径锁（伪代码）
BEGIN TRANSACTION;
  -- 检查路径是否已被锁定
  SELECT COUNT(*) FROM path_lock 
  WHERE path_id = ? AND released_at IS NULL;
  
  -- 如果未锁定，则插入锁记录
  IF count = 0 THEN
    INSERT INTO path_lock (path_id, agv_id, locked_at, ttl) 
    VALUES (?, ?, NOW(), 30);
    COMMIT;
    RETURN success;
  ELSE
    ROLLBACK;
    RETURN failed;
  END IF;

为什么不用悲观锁？因为悲观锁在高并发场景下容易死锁。我踩过这个坑——20 台 AGV 同时申请锁，结果 3 台死锁了，整个系统卡死。换成乐观锁后，虽然偶尔有重试，但系统稳定多了。

22.4 接口设计总结

三种接口各有各的用处，我画了张图帮你理清它们的关系：

你看这张图，RESTful API 和 WebSocket 负责“对外通信”，数据库接口负责“对内存储”。业务逻辑层在中间做协调。这样分层的好处是：任何一层发生变化，其他层都不受影响。

最后说一句：接口设计没有银弹。RESTful API 简单可靠，但实时性差；WebSocket 实时性好，但连接管理复杂；数据库接口性能高，但设计不好容易成为瓶颈。我的建议是——根据场景选型，不要为了用而用。你想想看，如果只是查个历史记录，非要用 WebSocket 推，那不是给自己找麻烦吗？

核心原则：接口是契约，不是实现。先定好契约，再写代码。契约稳定了，系统才能稳定。
