6 传感器接口设计：激光雷达（LiDAR）、IMU、编码器的接口协议与数据同步

传感器接口设计，说白了就是给AGV装上「眼睛」和「耳朵」。激光雷达、IMU、编码器这三样东西，是AGV感知层的铁三角。我做了这么多年AGV，见过太多因为接口没选对、数据没对齐导致的定位漂移、建图失败。今天咱们就把这三个传感器的接口协议和数据同步问题，掰开揉碎了讲清楚。

6.1 激光雷达（LiDAR）接口：从物理层到数据流

激光雷达是AGV的「主视觉」。它负责扫描环境，输出点云数据。接口选型上，我个人的习惯是：能用以太网，就别用串口。

6.1.1 主流接口协议对比

接口类型 速率 传输距离 典型应用场景 我的评价
UART（串口） 115200~921600 bps 1~3米 低端单线雷达、调试 速率瓶颈明显，点云稀疏
USB 2.0/3.0 480 Mbps / 5 Gbps 5米（带线） 室内AGV、原型验证 方便，但线缆可靠性差
Ethernet（UDP/TCP） 100 Mbps / 1 Gbps 100米 工业AGV、多雷达融合 首选！带宽足，易扩展
CAN/CAN-FD 1 Mbps / 8 Mbps 40米 车载网络、低延迟控制 适合传输触发信号，不适合点云

嗯，这里要注意：千万别用UART传高线束雷达的点云数据。我曾经在项目里试过用115200波特率传16线雷达的数据，结果一帧点云要传好几秒，AGV都撞墙了数据还没传完。后来换成千兆以太网，问题瞬间解决。

6.1.2 以太网接口的实战配置

我个人习惯用UDP协议接收雷达数据。为什么？因为雷达数据是周期性广播的，丢一帧没关系，下一帧马上补上。TCP虽然可靠，但重传机制会导致数据延迟抖动，对实时建图不友好。

下面是一个典型的雷达数据接收代码片段（基于C语言，嵌入式Linux环境）：

// 雷达数据接收线程（UDP）
void *lidar_receive_thread(void *arg) {
    int sock_fd;
    struct sockaddr_in local_addr;
    char buffer[65536];  // 足够容纳一帧点云

    sock_fd = socket(AF_INET, SOCK_DGRAM, 0);
    local_addr.sin_family = AF_INET;
    local_addr.sin_port = htons(2368);  // 常见雷达端口
    local_addr.sin_addr.s_addr = INADDR_ANY;
    bind(sock_fd, (struct sockaddr*)&local_addr, sizeof(local_addr));

    while (1) {
        int len = recvfrom(sock_fd, buffer, sizeof(buffer), 0, NULL, NULL);
        if (len > 0) {
            // 解析雷达协议头，提取时间戳和点云数据
            parse_lidar_frame(buffer, len);
            // 将数据推送到同步队列
            push_to_sync_queue(LIDAR_DATA, buffer, len, get_hw_timestamp());
        }
    }
}
小技巧： 雷达数据帧里通常自带时间戳。但硬件时间戳更准！我建议用FPGA或MCU的硬件定时器给每帧数据打上纳秒级时间戳，这样数据同步才有保障。

6.2 IMU接口：惯性数据的「快」与「准」

IMU（惯性测量单元）提供加速度和角速度。它的特点是：数据频率高（100Hz~1kHz），但误差会累积。接口选型上，我推荐用SPI或I²C。

6.2.1 SPI vs I²C：怎么选？

说白了，SPI快，I²C省引脚。但IMU数据量大、频率高，我个人强烈建议用SPI。

  • SPI（4线）：速率可达10MHz以上，适合高频IMU（如BMI088、ICM-20948）。
  • I²C（2线）：速率通常400kHz（标准模式）或1MHz（快速模式），适合低功耗场景。

为什么会这样？因为IMU的数据需要和编码器、雷达做时间对齐。SPI的时钟是主设备控制的，延迟可控。I²C有总线仲裁，万一多个设备抢总线，数据就乱了。

避坑指南： 我曾经在项目里用I²C接IMU，结果因为总线上还挂了其他传感器，导致IMU数据偶尔丢帧。AGV在转弯时IMU数据缺失，定位直接飘了。后来全部换成SPI，再也没出过问题。

6.2.2 IMU数据读取示例（SPI）

// SPI读取IMU加速度数据（以BMI088为例）
uint8_t imu_read_accel(int16_t *accel_x, int16_t *accel_y, int16_t *accel_z) {
    uint8_t tx_buf[7] = {0x12, 0, 0, 0, 0, 0, 0};  // 0x12是加速度X轴起始地址
    uint8_t rx_buf[7] = {0};

    // CS拉低，开始SPI传输
    HAL_GPIO_WritePin(IMU_CS_GPIO_Port, IMU_CS_Pin, GPIO_PIN_RESET);
    HAL_SPI_TransmitReceive(&hspi1, tx_buf, rx_buf, 7, 100);
    HAL_GPIO_WritePin(IMU_CS_GPIO_Port, IMU_CS_Pin, GPIO_PIN_SET);

    // 解析数据（BMI088数据为16位有符号，小端模式）
    *accel_x = (int16_t)((rx_buf[1] << 8) | rx_buf[2]);
    *accel_y = (int16_t)((rx_buf[3] << 8) | rx_buf[4]);
    *accel_z = (int16_t)((rx_buf[5] << 8) | rx_buf[6]);

    return 0;
}

6.3 编码器接口：轮子转了多少，心里要有数

编码器是AGV的「里程计」。它告诉你轮子转了多少圈，从而推算位置。接口上，主流是增量式编码器（ABZ）和绝对值编码器（SSI/BiSS）。

6.3.1 增量式 vs 绝对值

类型 输出信号 分辨率 上电位置 适用场景
增量式（ABZ） 两路正交脉冲+零位 几百~几千线/圈 未知，需回零 低成本AGV、室内导航
绝对值（SSI/BiSS） 时钟+数据（同步串行） 12~24位 上电即知 高精度、安全关键场景

嗯，这里有个坑：增量式编码器断电后位置丢失。我遇到过AGV断电重启后，编码器位置归零，但实际轮子没动，导致定位直接跳变。后来我加了个电池备份的RAM，专门存编码器位置。

6.3.2 编码器接口电路设计要点

编码器信号是高频脉冲，容易受干扰。我个人习惯在硬件上加这几样东西：

  • 差分接收器：用AM26LS32或MAX3096，把编码器的差分信号转成单端。
  • 施密特触发器：用74HC14对脉冲整形，消除毛刺。
  • 光耦隔离：如果编码器线缆长（超过5米），一定要隔离，防止共模干扰。
核心原则： 编码器接口的电气设计，直接决定了里程计的精度。一个毛刺就能让AGV多算几毫米，累积下来就是几米的误差。

6.4 数据同步：让三个传感器「说同一种时间」

数据同步是传感器接口设计的灵魂。雷达、IMU、编码器各自有各自的时钟，如果不做同步，融合出来的位姿就是「鸡同鸭讲」。

6.4.1 硬件同步方案（推荐）

我强烈推荐用硬件触发线做同步。具体做法：

  1. 主控（MCU/FPGA）产生一个PPS（每秒脉冲）信号。
  2. PPS信号同时接到雷达的触发输入、IMU的同步输入、编码器的锁存输入。
  3. 所有传感器在PPS上升沿同时采集数据，并打上统一的时间戳。

这样做的好处是：所有数据的时间基准完全一致，误差只有几纳秒。

6.4.2 软件同步方案（备选）

如果硬件不支持触发线，那就用软件同步。核心思路是：用一个高精度定时器（比如ARM的SysTick或FPGA的计数器）给每帧数据打时间戳，然后做插值对齐。

举个例子：

  • 雷达数据在t1时刻到达，时间戳为T_lidar。
  • IMU数据在t2时刻到达，时间戳为T_imu。
  • 编码器数据在t3时刻到达，时间戳为T_encoder。
  • 融合时，以雷达时间戳T_lidar为基准，对IMU和编码器数据做线性插值，得到T_lidar时刻的估计值。
注意： 软件同步的精度取决于定时器分辨率和数据频率。如果IMU是1kHz，雷达是10Hz，那插值误差可能在几毫秒级别。对于高速AGV（速度>2m/s），这个误差会导致厘米级的定位偏差。

你看，整个流程就是：选对接口 → 采到数据 → 对齐时间 → 融合输出。每一步都环环相扣，缺一不可。

我的经验： 如果你刚开始做AGV，别急着上多传感器融合。先把编码器接口调稳，再逐步加IMU和雷达。每一步都验证通过后，再做数据同步。这样出问题了，你能快速定位是哪个环节的锅。
