26 多控制器协同：主从控制器通信、心跳机制与故障切换

各位做AGV的朋友，你们有没有遇到过这种情况：一台AGV跑着跑着，主控板突然死机了，整车直接瘫在巷道中间，后面的车堵成一串。嗯，我早期做项目时就吃过这个亏。

说白了，单控制器方案在工业场景下就是一颗定时炸弹。你想想看，AGV要是载着几百公斤的货物在产线间穿梭，控制器一旦挂了，轻则堵线，重则撞车。所以，多控制器协同不是锦上添花，而是刚需。

为什么需要多控制器？

我个人习惯把AGV的控制系统拆成三个层面：

  • 运动控制层：负责电机驱动、速度环、电流环，要求实时性极高
  • 导航决策层：处理激光SLAM、路径规划、任务调度，计算量大
  • 安全监控层：检测急停、碰撞、超速等异常，必须独立于主控

把这三层塞进一个芯片里？不是不行，但风险太高。我在项目中遇到过，导航算法跑着跑着把CPU占满了，电机控制那边就丢脉冲了，车就开始跑偏。

核心原则：关键安全功能必须独立于主控芯片。这是AGV通过CE认证的硬门槛。

主从架构怎么搭？

我常用的方案是双STM32架构：一个H7系列做主控，负责导航和决策；一个G4系列做从控，专门管电机和IO。两个芯片之间用SPI通信，速率拉到10Mbps以上。

为什么选SPI而不是CAN？因为CAN的延迟不稳定，尤其在总线负载高的时候。SPI是全双工，延迟可预测，适合做周期性的控制数据交换。

下面是我实际项目中用过的通信协议结构：

// 主->从 数据帧 (20字节)
typedef struct {
    uint16_t sync_word;     // 同步字 0xAA55
    uint8_t  cmd_id;        // 命令ID
    int16_t  target_speed;  // 目标速度 mm/s
    int16_t  target_angle;  // 目标转角 0.1度
    uint8_t  brake_cmd;     // 刹车指令
    uint8_t  ctrl_mode;     // 控制模式
    uint32_t heartbeat;     // 心跳计数
    uint16_t crc16;         // CRC校验
} MasterToSlaveFrame;

// 从->主 数据帧 (20字节)
typedef struct {
    uint16_t sync_word;     // 同步字 0x55AA
    uint8_t  status;        // 状态码
    int16_t  actual_speed;  // 实际速度
    int16_t  actual_angle;  // 实际转角
    uint16_t motor_current; // 电机电流 mA
    uint8_t  fault_code;    // 故障码
    uint32_t heartbeat;     // 心跳计数
    uint16_t crc16;         // CRC校验
} SlaveToMasterFrame;

我的经验：CRC校验不能省。SPI虽然物理层可靠，但我在产线上遇到过电磁干扰导致数据错位的情况。加了CRC后，误码率从千分之一降到了百万分之一以下。

心跳机制怎么设计？

心跳机制说白了就是双方互相报平安。主控每隔10ms发一个递增的心跳计数，从控收到后回传同样的计数。如果主控连续3次没收到心跳回复，就认为从控挂了。

这里有个坑——我曾经把心跳超时设得太短，结果SPI偶尔丢一帧就触发故障切换，车频繁急停。后来我改成滑动窗口判断：连续5次中只要有3次成功，就算正常。

// 心跳检测逻辑
#define HEARTBEAT_TIMEOUT_MS  30   // 3个周期
#define HEARTBEAT_WINDOW_SIZE 5    // 滑动窗口大小

typedef struct {
    uint32_t last_beat;
    uint8_t  miss_count;
    uint8_t  window[HEARTBEAT_WINDOW_SIZE];
    uint8_t  window_idx;
} HeartbeatMonitor;

bool check_heartbeat(HeartbeatMonitor *hm, uint32_t now_ms) {
    uint32_t elapsed = now_ms - hm->last_beat;
    
    if (elapsed > HEARTBEAT_TIMEOUT_MS) {
        hm->window[hm->window_idx] = 0;  // 标记丢失
        hm->miss_count++;
    } else {
        hm->window[hm->window_idx] = 1;  // 标记成功
    }
    
    hm->window_idx = (hm->window_idx + 1) % HEARTBEAT_WINDOW_SIZE;
    hm->last_beat = now_ms;
    
    // 统计窗口内成功次数
    uint8_t success = 0;
    for (int i = 0; i < HEARTBEAT_WINDOW_SIZE; i++) {
        if (hm->window[i]) success++;
    }
    
    return (success >= 3);  // 5次中至少3次成功
}

注意：心跳计数不要用时间戳，要用独立的递增计数器。时间戳可能因为NTP同步或RTC漂移出现回退，导致误判。我吃过这个亏，排查了两天才找到原因。

故障切换怎么做？

故障切换分两个层面：

  1. 从控故障：主控检测到从控心跳丢失，立即执行安全停车，然后尝试复位从控。如果复位后仍然失败，上报调度系统请求救援。
  2. 主控故障：这个更棘手。从控发现主控心跳丢失后，不能傻等，要自动进入安全模式——减速、停车、拉手刹。

我设计过一个双机热备方案，用两个主控板互为备份：

// 故障切换状态机
typedef enum {
    FS_NORMAL,          // 正常
    FS_DEGRADED,        // 降级运行
    FS_FAILOVER,        // 正在切换
    FS_EMERGENCY_STOP   // 紧急停止
} FailoverState;

void failover_task(void) {
    switch (current_state) {
        case FS_NORMAL:
            if (heartbeat_lost > 3) {
                // 尝试切换
                backup_ctrl->takeover();
                current_state = FS_FAILOVER;
                log_info("主控故障，切换到备份控制器");
            }
            break;
            
        case FS_FAILOVER:
            if (backup_ctrl->is_ready()) {
                // 切换成功
                current_state = FS_DEGRADED;
                // 降速到0.5m/s运行
                set_speed_limit(500);
            } else {
                // 切换失败，紧急停车
                current_state = FS_EMERGENCY_STOP;
                emergency_brake();
            }
            break;
    }
}

关键点：故障切换不是简单的「谁活着谁上」。切换后必须降级运行，因为备份控制器的状态可能不是最新的。我一般把速度限制在正常值的50%，等人工确认后再恢复。

通信接口选型对比

接口类型 速率 延迟 可靠性 我推荐场景
SPI 10-50Mbps <1us 高（需CRC） 主从控制器间实时数据交换
CAN 1Mbps 10-100us 高（硬件CRC） 多节点传感器网络
UART 115200-921600 10-100us 中（无硬件校验） 调试日志、非关键数据
EtherCAT 100Mbps <1us 极高 高端AGV的伺服驱动网络

我个人习惯：主从之间用SPI，传感器网络用CAN，调试口用UART。EtherCAT虽然好，但成本高，一般用在几十万以上的高端AGV上。

实际项目中的避坑指南

我曾经在一个项目中，主从控制器之间用了一根20cm的排线连接SPI。结果在EMC测试时，辐射超标了。排查后发现是SPI时钟线没有做阻抗匹配，产生了振铃。

后来我改了三个地方：

  • SPI时钟线上串联22Ω电阻，抑制过冲
  • 数据线和时钟线之间加地线隔离
  • 排线换成屏蔽FPC，两端接GND

改完之后，辐射降了15dB，顺利过检。

小技巧：如果你用SPI做主从通信，建议把CS片选信号做成硬件握手。主控拉低CS表示「我要发数据」，从控检测到CS拉低后准备接收。这样比软件轮询效率高得多。

总结一下

多控制器协同的核心就三件事：

  • 通信要可靠：SPI+CRC，别省校验
  • 心跳要智能：滑动窗口判断，别一丢包就炸
  • 切换要安全：降级运行，别盲目全速

嗯，这些经验都是我在项目里一点点踩坑踩出来的。你照着做，至少能省下两个月的调试时间。
