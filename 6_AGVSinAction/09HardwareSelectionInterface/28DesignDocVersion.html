28 设计文档与版本管理：原理图、PCB、BOM的规范化管理工具（Git/Altium）

做AGV控制器硬件设计这几年，我踩过最大的坑，不是电路没调通，而是——版本搞乱了。

你想想看，一个AGV控制器，原理图改了七八版，PCB打了四五次样，BOM单更是满天飞。没有规范化的管理，光靠「V1.0_最终版_真最终版」这种命名方式，迟早要出事。

我个人习惯，从项目第一天就把Git和Altium的版本管理搭好。别嫌麻烦，后面省下的时间，够你喝好几杯咖啡。

为什么硬件设计也需要版本管理？

很多人觉得版本管理是软件的事。硬件嘛，改个电阻值，重新导个网表就行了。

真不是这样。

我在项目中遇到过一件事：一个AGV驱动板的BOM，采购部按旧版本买了100套MOS管。结果新版本把封装改了，焊不上。那批货全废了。原因？就是BOM版本没对齐。

硬件版本管理要管三样东西：

  • 原理图：电路逻辑的变更记录
  • PCB：布局布线的迭代历史
  • BOM：物料清单的版本对应关系

这三样东西，必须绑定在一起管理。不能原理图改了，BOM还是旧的。

Git在硬件管理中的用法

Git不是软件工程师的专利。我建议硬件团队也把Git用起来。

但要注意，Git对二进制文件（比如Altium的.PrjPcb、.SchDoc、.PcbDoc）没法做行级对比。它只能告诉你「这个文件变了」，不能告诉你「哪根线改了」。

所以，我的做法是：

  • 用Git管理文件版本，记录谁在什么时候改了什么东西
  • 配合Altium的本地历史，做细粒度的设计变更追踪

Git仓库的结构，我一般这样搭：

AGV_Controller_HW/
├── docs/                    # 设计文档、规格书
├── design/                  # Altium项目文件
│   ├── MCU_Board/           # 主控板
│   ├── Motor_Driver/        # 驱动板
│   └── Power_Module/        # 电源模块
├── BOM/                     # 物料清单（CSV/Excel）
├── manufacturing/           # 生产文件（Gerber、钻孔）
└── README.md                # 项目说明

每次提交，commit message要写清楚改了啥。比如：

fix: 修改电机驱动板R12阻值，从10k改为4.7k，解决过流检测阈值偏高问题

别写「修改了一些东西」——这种commit message，回头你自己都看不懂。

我的小技巧：在Git仓库里放一个CHANGELOG.md文件，每次发版时手动记录关键变更。这样项目经理问起来，直接甩链接给他看。

Altium的版本管理功能

Altium Designer本身带版本管理功能。它支持SVN和Git两种后端。

我个人更推荐用Git。原因很简单：Git是目前的主流，团队里软件同事都在用，出了问题好找人问。

在Altium里配置Git的步骤：

  1. 打开Altium，点击 DXP → Preferences → Version Control
  2. 选择 Git 作为版本控制系统
  3. 配置Git路径（指向你安装的git.exe）
  4. 在Projects面板里，右键项目 → Add to Version Control

配置好之后，每次保存文件，Altium会自动检测变更。你可以在Projects面板里看到哪些文件被修改了（带红色勾号）。

提交的时候，Altium会弹出一个对话框，让你写commit message。嗯，这里要注意：别偷懒，写清楚。

曾经踩过的坑：Altium的Git集成有个小毛病——如果文件被外部工具（比如文本编辑器）修改了，Altium可能检测不到变更。所以我习惯在提交前，手动刷新一下项目状态。

BOM的版本管理

BOM这东西，看着简单，管起来最头疼。

原理图改了，BOM要跟着改。PCB改了，BOM可能也要改（比如换封装）。更麻烦的是，同一个物料可能有多个替代料号。

我的做法是：

  • BOM文件放在Git仓库里，和原理图、PCB在同一分支
  • BOM文件名包含版本号，比如 BOM_MCU_Board_v2.1.xlsx
  • 每次发版时，BOM和原理图一起打Tag

BOM的格式，我推荐用CSV。虽然Excel看着方便，但CSV在Git里能做文本对比。Excel是二进制文件，Git只能告诉你「这个文件变了」，没法告诉你「哪一行变了」。

BOM的字段，我一般包含这些：

字段 说明 示例
Item 位号 R12
Value 标称值 4.7k
Package 封装 0805
MPN 制造商料号 RC0805FR-074K7L
Supplier 供应商 Yageo
Qty 用量 2
Remark 备注 替代料: RC0805JR-074K7L

规范化流程：从设计到发版

光有工具不够，还得有流程。我团队里用的流程是这样的：

  1. 日常开发：在 develop 分支上改原理图、PCB。每天下班前提交一次。
  2. 设计评审：评审前，从 develop 拉一个 review/v1.2 分支。评审意见改完后，合并回 develop。
  3. 打样发版：从 develop 拉 release/v1.2 分支。导出Gerber文件、BOM、装配图。打上Tag v1.2。
  4. 生产发版：打样验证通过后，把 release/v1.2 合并到 main 分支。打上Tag v1.2_production。

这个流程的好处是：任何时候，main 分支上的设计都是经过验证的。不会出现「打样版和生产版混在一起」的情况。

核心原则：原理图、PCB、BOM三者必须同版本。不能出现「原理图是v1.2，BOM是v1.1」的情况。每次发版，三样东西一起打Tag。

一些实用建议

最后，分享几个我这些年总结出来的经验：

  • 命名规范要统一：原理图文件名、PCB文件名、BOM文件名，都要包含项目代号和版本号。比如 AGV_MCU_v1.2.SchDoc。
  • 不要用中文文件名：Altium对中文支持不太好，有些版本会乱码。老老实实用英文。
  • 每次导出生产文件，都要重新生成BOM：别用上次的。我见过有人偷懒，结果BOM和原理图对不上，板子焊不出来。
  • Git的.gitignore要配好：Altium的临时文件（比如History文件夹、__Previews文件夹）不要提交到Git里。网上有现成的.gitignore模板，搜一下就能找到。
曾经踩过的坑：有一次我忘了配.gitignore，把Altium的History文件夹也提交上去了。结果仓库体积暴涨到2GB，clone一次要半小时。后来花了一下午才把历史清理干净。

版本管理这件事，说白了就是「把规矩定在前面」。刚开始可能觉得麻烦，但等你遇到「板子焊好了才发现BOM错了」这种问题，就知道规范化管理有多重要了。

嗯，今天就聊到这儿。工具和方法都给你了，关键还是得用起来。
